CloudThinker chạy AWS CLI trên tài khoản của bạn để trả lời các câu hỏi về compute, lưu trữ, danh tính, chi phí và giám sát. Bạn kết nối bằng IAM role mà CloudThinker assume để nhận thông tin xác thực ngắn hạn (khuyến nghị), hoặc bằng access key của một IAM user.

## Điều kiện tiên quyết

- Tài khoản AWS mà bạn có quyền tạo IAM role (hoặc IAM user, nếu dùng phương thức access key).
- Quyền dùng [AWS CloudShell](https://console.aws.amazon.com/cloudshell/home) trong tài khoản đó. Script thiết lập chạy trong CloudShell nên bạn không cần cài gì.
- Với câu hỏi về chi phí và [Optimize](/vi/guide/cost-optimization/overview): Cost Explorer phải được bật trong tài khoản (**Billing and Cost Management → Cost Explorer → Launch Cost Explorer**, trong management account nếu dùng organization). AWS có thể cần tới 24 giờ để kích hoạt Cost Explorer trên tài khoản mới.
- Trong AWS Organization, hãy kiểm tra các service control policy (SCP). SCP chặn `sts:AssumeRole` từ principal bên ngoài sẽ chặn role, còn SCP chặn region sẽ ẩn các region đó khỏi agent. Từ management account, liệt kê SCP của tài khoản tại **AWS Organizations → AWS accounts → tài khoản của bạn → Policies**, hoặc chạy `aws organizations list-policies-for-target --target-id <account-id> --filter SERVICE_CONTROL_POLICY`.
- Các region cần opt-in, như `ap-east-1` hoặc `me-south-1`, sẽ vô hình với agent cho đến khi bạn bật chúng tại **Account → AWS Regions** trong AWS console.

## Thiết lập

Trước tiên, mở hộp thoại kết nối: ở thanh bên, nhấn **More → Workspace settings → Connections**, chọn **Amazon Web Services**, rồi nhấn **Connect**. Sau đó làm theo tab tương ứng với phương thức bạn chọn ở đầu hộp thoại.

        Để đọc script trước, nhấn **View script** trong hộp thoại. Sau đó nhấn **Copy Script to Clipboard**, dán vào CloudShell và nhấn Enter. Script sẽ:

        1. Dừng lại nếu đã có role tên `CloudThinkerAccessRole`.
        2. Tạo `CloudThinkerAccessRole` với trust policy chỉ cho phép CloudThinker assume, và chỉ khi có External ID của bạn.
        3. Gắn policy AWS managed `ReadOnlyAccess`.
        4. In ra ARN của role.

        <Accordion title="Toàn bộ script, để bạn xem trước khi chạy">
        Hộp thoại điền sẵn External ID của bạn và principal của CloudThinker. Script cũng in các thông báo tiến trình, được lược bỏ ở đây.

        ```bash
        #!/bin/bash
        set -e
        ROLE_NAME="CloudThinkerAccessRole"

        # Stop if the role already exists
        if aws iam get-role --role-name "$ROLE_NAME" >/dev/null 2>&1; then
          echo "ERROR: Role '$ROLE_NAME' already exists!"
          exit 1
        fi

        # Trust policy: only the CloudThinker principal, only with your External ID
        cat > trust-policy.json <<'EOF'
        {
          "Version": "2012-10-17",
          "Statement": [
            {
              "Effect": "Allow",
              "Principal": { "AWS": "<CloudThinker principal shown in the dialog>" },
              "Action": "sts:AssumeRole",
              "Condition": { "StringEquals": { "sts:ExternalId": "<your External ID>" } }
            }
          ]
        }
        EOF

        aws iam create-role --role-name "$ROLE_NAME" \
          --assume-role-policy-document file://trust-policy.json \
          --description "Role for CloudThinker to access AWS resources"

        aws iam attach-role-policy --role-name "$ROLE_NAME" \
          --policy-arn arn:aws:iam::aws:policy/ReadOnlyAccess

        rm -f trust-policy.json
        aws iam get-role --role-name "$ROLE_NAME" --query 'Role.Arn' --output text
        ```
        </Accordion>


Mục này hiển thị trust policy đã điền sẵn External ID của bạn và principal của CloudThinker. Principal giống nhau cho mọi workspace. Chỉ External ID thay đổi theo từng hộp thoại. Với cách làm thủ công, bạn có thể đặt role bất kỳ tên nào, vì CloudThinker dùng ARN bạn dán vào. Cấu trúc như sau:

    ```json
    {
      "Version": "2012-10-17",
      "Statement": [
        {
          "Effect": "Allow",
          "Principal": { "AWS": "<CloudThinker principal shown in the dialog>" },
          "Action": "sts:AssumeRole",
          "Condition": {
            "StringEquals": { "sts:ExternalId": "<your External ID>" }
          }
        }
      ]
    }
    ```

    Cùng role đó viết bằng Terraform, với hai giá trị truyền vào dưới dạng biến:

    ```hcl
    variable "cloudthinker_principal" {}
    variable "cloudthinker_external_id" {}

    resource "aws_iam_role" "cloudthinker" {
      name = "CloudThinkerAccessRole"
      assume_role_policy = jsonencode({
        Version = "2012-10-17"
        Statement = [{
          Effect    = "Allow"
          Principal = { AWS = var.cloudthinker_principal }
          Action    = "sts:AssumeRole"
          Condition = { StringEquals = { "sts:ExternalId" = var.cloudthinker_external_id } }
        }]
      })
    }

    resource "aws_iam_role_policy_attachment" "read_only" {
      role       = aws_iam_role.cloudthinker.name
      policy_arn = "arn:aws:iam::aws:policy/ReadOnlyAccess"
    }

    output "role_arn" {
      value = aws_iam_role.cloudthinker.arn
    }
    ```

### Kết nối thêm tài khoản

Mỗi tài khoản AWS là một kết nối riêng. Nhấn **Connect** lần nữa trên **Amazon Web Services**, đặt alias riêng cho tài khoản, rồi chạy script từ hộp thoại đó trong CloudShell của tài khoản mới. Luôn sao chép script từ đúng hộp thoại bạn đang hoàn tất, để trust policy mang External ID mà hộp thoại đó hiển thị.

Hiện chưa hỗ trợ onboard hàng loạt. Mỗi hộp thoại sinh External ID riêng, nên một StackSet hay một lần Terraform apply không thể tạo role cho nhiều kết nối cùng lúc. Mỗi tài khoản cần hộp thoại riêng và role riêng. Với nhiều tài khoản, cách nhanh nhất là dùng module Terraform ở trên, apply một lần cho mỗi tài khoản với các giá trị từ hộp thoại đang mở của tài khoản đó.

Để xem chi phí trên toàn AWS Organization, hãy kết nối management account. Kết nối này chỉ cung cấp cho Optimize dữ liệu chi phí toàn tổ chức. Agent chỉ thấy tài nguyên trong một member account thông qua kết nối riêng của tài khoản đó.

## Chi tiết kết nối

| Trường | Phương thức | Mô tả | Ví dụ |
|---|---|---|---|
| **Alias** | Cả hai | Tên ngắn của tài khoản. Để trống thì hệ thống tự đặt. | `production` |
| **Description** | Cả hai | Tài khoản này dùng cho việc gì. Agent dựa vào đây để chọn giữa các tài khoản. | `Production AWS account` |
| **Default AWS region (optional)** | Cả hai | Region bắt đầu. Agent có thể dùng các region khác mà thông tin xác thực cho phép. | `us-east-1` |
| **AWS Role ARN** | Role-Based | ARN do script thiết lập in ra | `arn:aws:iam::123456789012:role/CloudThinkerAccessRole` |
| **AWS External ID** | Role-Based | Do CloudThinker sinh ra. Chỉ đọc, phải khớp với trust policy. | Được điền sẵn |
| **AWS_ACCESS_KEY_ID** | Access Keys | Access key ID của IAM user | `AKIA...` |
| **AWS_SECRET_ACCESS_KEY** | Access Keys | Secret key của IAM user | AWS chỉ hiển thị một lần |

**Environment** (**Production**, **Staging**, **Development** hoặc **Not set**) không có trong hộp thoại kết nối. Hãy đặt sau khi kết nối, như ở bước thiết lập cuối: trường này gắn nhãn tài khoản cho cả người dùng lẫn agent. [Rule phê duyệt](/vi/guide/approvals/rules) không đọc trường này, nên Rule muốn áp dụng cho một tài khoản phải nêu tên kết nối đó.

## Quyền yêu cầu

Script thiết lập gắn policy AWS managed `ReadOnlyAccess`. Policy này cho phép agent describe và list tài nguyên trên các dịch vụ, đọc metric CloudWatch và đọc Cost Explorer. Policy không thể tạo, thay đổi hay xóa bất cứ thứ gì.

| Bạn muốn | Cấp quyền |
|---|---|
| Câu hỏi về inventory, tình trạng và bảo mật | `ReadOnlyAccess` (policy mà script gắn) |
| Dữ liệu chi phí cho Optimize | Đã có trong `ReadOnlyAccess`. Nếu dùng policy tùy chỉnh, thêm `ce:Get*`. |
| Agent thực hiện một số thay đổi cụ thể | Chỉ thêm đúng các action đó vào role, rồi xem [Quyền ghi](#quyền-ghi) |

<Tip>
`ReadOnlyAccess` đọc được cả dữ liệu lẫn cấu hình, chẳng hạn object trong S3. Lựa chọn hẹp hơn là kết hợp AWS managed `ViewOnlyAccess` với `SecurityAudit`, cộng thêm quyền đọc `ce:Get*` cho Optimize. Bộ quyền này đủ để list và describe tài nguyên, nhưng không đọc được dữ liệu như nội dung object S3 hay log event. Thiếu quyền không bao giờ làm ngắt kết nối tài khoản: câu trả lời cần quyền đó sẽ thất bại với `AccessDenied`, kèm tên action bị thiếu, để bạn chỉ cần thêm đúng action đó vào inline policy.
</Tip>

Để chuyển một role hiện có sang bộ quyền hẹp hơn, hãy chạy lệnh sau trong CloudShell:

```bash
ROLE=CloudThinkerAccessRole
aws iam attach-role-policy --role-name $ROLE --policy-arn arn:aws:iam::aws:policy/job-function/ViewOnlyAccess
aws iam attach-role-policy --role-name $ROLE --policy-arn arn:aws:iam::aws:policy/SecurityAudit
aws iam put-role-policy --role-name $ROLE --policy-name CloudThinkerCostRead \
  --policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Action":"ce:Get*","Resource":"*"}]}'
aws iam detach-role-policy --role-name $ROLE --policy-arn arn:aws:iam::aws:policy/ReadOnlyAccess
```

Trong Terraform, thay attachment `read_only` bằng attachment cho hai policy ARN đó và một `aws_iam_role_policy` chứa statement `ce:Get*`.

## Khả năng của agent

| Lĩnh vực | CloudThinker làm gì |
|---|---|
| **Inventory** | Liệt kê và mô tả compute, lưu trữ, mạng và các dịch vụ managed trên các region |
| **Danh tính** | Rà soát IAM role, user và policy để tìm quyền truy cập rủi ro hoặc không dùng đến |
| **Chi phí** | Phân tích chi tiêu theo dịch vụ, tài khoản và tag, kiểm tra mức bao phủ của Reserved Instance và Savings Plans. Cung cấp dữ liệu cho [Optimize](/vi/guide/cost-optimization/overview). |
| **Giám sát** | Đọc metric và alarm CloudWatch để giải thích một đợt tăng đột biến hoặc sự cố ngừng hoạt động |
| **Thay đổi** | Chỉ chạy lệnh ghi của AWS CLI khi **Allow writes** đang bật, role cho phép, và cài đặt phê duyệt của bạn đồng ý |

## Quyền ghi

**Allow writes** trên bảng chi tiết của kết nối quyết định agent có được thay đổi gì trong AWS hay không. Với AWS, tùy chọn này bật theo mặc định, nhưng role do script tạo là chỉ đọc, nên chính AWS sẽ từ chối mọi thao tác ghi cho đến khi bạn cấp thêm quyền.

| Quyền IAM | Allow writes | Kết quả |
|---|---|---|
| Chỉ có `ReadOnlyAccess` | Bật hoặc tắt | Chỉ đọc. AWS từ chối mọi thay đổi. |
| Đã cấp thêm action ghi | Tắt | Chỉ đọc. CloudThinker từ chối mọi thay đổi trước khi yêu cầu tới AWS. |
| Đã cấp thêm action ghi | Bật | Agent có thể đề xuất thay đổi. [Rules và Approval mode](/vi/guide/approvals/overview) của bạn quyết định từng thay đổi. |

Để khóa thao tác ghi ngay trong CloudThinker, mở **Amazon Web Services** trong **More → Workspace settings → Connections** và tắt công tắc **Allow writes** trên bảng chi tiết.

## Khắc phục sự cố

<Accordion title="Script báo CloudThinkerAccessRole đã tồn tại">
**Nguyên nhân:** một lần thiết lập trước đó trong tài khoản này đã tạo role, nhiều khả năng với External ID khác.

**Cách khắc phục:** nếu không có kết nối CloudThinker nào khác dùng role đó, hãy gỡ các policy của role và xóa role, rồi chạy script mới. `delete-role` sẽ thất bại cho đến khi mọi policy được gắn và inline policy đều bị gỡ, nên hãy liệt kê chúng trước:

```bash
ROLE=CloudThinkerAccessRole
aws iam list-attached-role-policies --role-name $ROLE
aws iam list-role-policies --role-name $ROLE
# For each attached policy ARN:
aws iam detach-role-policy --role-name $ROLE --policy-arn <policy-arn>
# For each inline policy name:
aws iam delete-role-policy --role-name $ROLE --policy-name <policy-name>
aws iam delete-role --role-name $ROLE
```

Để kiểm tra một kết nối CloudThinker còn dùng role hay không, mở **Event history** của CloudTrail, lọc **Event name** = `AssumeRole`, rồi tìm các event gần đây trên `CloudThinkerAccessRole` có session name bắt đầu bằng `cloudthinker-`. Nếu còn kết nối dùng role, đừng thay External ID của role. Thay vào đó, dùng **Manual steps** để tạo role thứ hai với tên khác cho workspace này.
</Accordion>

<Accordion title="Kiểm tra thất bại với AccessDenied trên sts:AssumeRole">
**Nguyên nhân:** trust policy không khớp với thông tin CloudThinker gửi lên.

**Kiểm tra:** ARN bạn dán đúng là ARN do script in ra, và `sts:ExternalId` trong trust policy khớp chính xác với **AWS External ID** trong hộp thoại.

**Cách khắc phục:** kiểm tra thất bại thì kết nối không được lưu. Sửa trust policy, rồi nhấn **Connect** lại trong chính hộp thoại đó để External ID giữ nguyên. Nếu bạn đã đóng hộp thoại, hãy chạy lại thiết lập từ một hộp thoại mới. **Retry** chỉ xuất hiện trên kết nối đã lưu và sau đó hiển thị **Error**.
</Accordion>

<Accordion title="Kết nối hiển thị Error và các tác vụ theo lịch đã dừng">
**Nguyên nhân:** ba lần liên tiếp thông tin xác thực thất bại khi chạy nền (role bị xóa, trust policy hỏng, hoặc key bị thu hồi) sẽ chuyển kết nối sang **Error**. Việc làm mới chi phí của Optimize, các automation theo lịch và việc thăm dò của Pulse tạm dừng cho kết nối đó, và admin của workspace nhận một thông báo.

**Cách khắc phục:** sửa role hoặc key trong AWS, rồi nhấn **Retry** trên kết nối, hoặc **Replace credentials** để nhập key mới. Các tác vụ theo lịch chạy lại ở chu kỳ kế tiếp khi trạng thái trở về **Connected**.
</Accordion>

<Accordion title="Câu hỏi về chi phí không trả về dữ liệu">
**Kiểm tra:** Cost Explorer đã được bật trong AWS Billing console, và đã qua ít nhất 24 giờ kể từ khi bật. Với member account trong AWS Organizations, management account có thể chặn member account truy cập Cost Explorer.

**Cách khắc phục:** bật Cost Explorer, hoặc kết nối management account để xem chi phí của toàn tổ chức.
</Accordion>

<Accordion title="Kiểm tra hiển thị Timed out">
**Nguyên nhân:** bài kiểm tra không hoàn tất kịp thời. Endpoint của AWS là công khai, nên hiếm khi lỗi nằm ở mạng của bạn.

**Cách khắc phục:** kết nối lại. Nếu vẫn tiếp tục hết thời gian chờ, hãy [liên hệ với chúng tôi](https://cloudthinker.io/contact).
</Accordion>

<Accordion title="Một region hoặc dịch vụ trả về AccessDenied với explicit deny">
**Nguyên nhân:** một service control policy đang chặn. Lỗi của AWS cho biết yêu cầu bị từ chối `with an explicit deny in a service control policy`. Nếu SCP chặn `sts:AssumeRole`, chính bài kiểm tra kết nối sẽ thất bại.

**Kiểm tra:** liệt kê các SCP trên tài khoản, như trong mục [Điều kiện tiên quyết](#điều-kiện-tiên-quyết).

**Cách khắc phục:** nhờ admin AWS Organizations miễn trừ `CloudThinkerAccessRole` khỏi SCP, hoặc chấp nhận rằng agent không thấy được region hay dịch vụ đó.
</Accordion>


## Bảo mật

<ConnectionSecurity />

- **Ưu tiên dùng role.** CloudThinker assume role qua AWS STS và nhận thông tin xác thực ngắn hạn, nên không có secret dài hạn nào có thể bị lộ. External ID ngăn người khác dùng role của bạn thông qua CloudThinker.
- **Kiểm toán bằng CloudTrail.** Mọi lệnh gọi của agent đều là lệnh gọi AWS API thông thường. CloudThinker đặt tên mỗi role session là `cloudthinker-<8 ký tự đầu của workspace ID>-<Unix timestamp>`, và **Event history** của CloudTrail hiển thị session name đó ở cột **User name**. Để xem mọi lệnh gọi qua các session, lọc theo `userIdentity.sessionContext.sessionIssuer.userName` = `CloudThinkerAccessRole` trong CloudTrail Lake hoặc Athena. Với access key, lọc **Event history** theo **User name** = `CloudThinkerUser`.
