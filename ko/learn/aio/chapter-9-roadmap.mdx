*단계적이고 증거에 기반한 도입 경로: 첫 가치까지 90일, 새로운 운영 모델까지 12개월.*

이 챕터에서는 시작하기 전에 고칠 것, 첫 90일을 운영하는 방법, 확장하는 방법, 그리고 기다려야 할 때를 다룹니다. 9.6절은 각 파일럿 단계를 CloudThinker 설정에 대응시킵니다.

## 9.1 준비: 에이전트가 필요로 하는 것

에이전트는 물려받은 환경을 증폭합니다. 첫 배포 전에 다섯 가지 기반을 점검하세요.

| 기반 | "준비됨"의 모습 | 없을 경우 |
| :---- | :---- | :---- |
| **관측성** | 대상 영역을 적절히 커버하는 중앙 집중식 로그, 메트릭, 트레이스 | 에이전트는 존재하지 않는 신호를 추론할 수 없습니다. 이것부터 고치세요. |
| **접근 아키텍처** | 에이전트별로 발급할 수 있는 범위가 제한된 단기 자격 증명 | 모든 것이 하나의 관리자 키로 실행된다면, 에이전트가 행동하기 전에 고치세요. CloudThinker에서 자격 증명은 연결별입니다. [AWS](/ko/guide/connections/aws#필요한-권한), [Azure](/ko/guide/connections/azure), [Google Cloud](/ko/guide/connections/gcp) 설정처럼 각 파일럿 연결에 자체 읽기 전용 역할을 주세요. |
| **진실의 원천** | 부분적이라도 에이전트가 다룰 시스템에 대한 코드형 인프라(IaC) | 에이전트에게 안전한 변경 메커니즘이 없고, 비교 가능한 감사 추적을 잃습니다. |
| **문서화된 의도** | SLO, 런북, 아키텍처 노트. 불완전해도 괜찮습니다. | 에이전트가 시스템이 어떻게 동작해야 하는지에 대한 컨텍스트를 갖지 못합니다. |
| **책임 있는 담당자** | 자율성 정책을 정하고 온콜 로테이션을 이끌 위치에 있는, 이름이 정해진 시니어 엔지니어 | 프로그램이 조언 전용에서 정체되거나, 통제되지 않는 행동으로 흘러갑니다. |

## 9.2 90일 파일럿

이 표의 자율성 레벨은 [§3.2](/ko/learn/aio/chapter-3-what-is-aio)에서 왔습니다. **L0**는 관찰하고 보고하며, **L1**은 조사하고 권고하며, **L2**는 수정을 준비하고 승인을 기다리며, **L3**는 사전 승인된 작업 유형을 실행하고 나중에 사람에게 알립니다.

| 단계 | 주 | 할 일 | 종료 기준 |
| :---- | :---- | :---- | :---- |
| **기준선과 범위** | 1–2 | MTTR, 알림 볼륨, 호출 수, 반복 작업 시간을 기록합니다. 한 제품의 인시던트 대응이나 한 계정의 클라우드 비용처럼 범위가 제한된 영역 하나를 고릅니다. | 서명된 기준선, 범위가 정해진 영역, 합의된 성공 지표 |
| **관찰(L0–L1)** | 3–6 | 읽기 권한으로 텔레메트리와 도구를 연결합니다. 에이전트가 엔지니어와 함께 모든 인시던트를 조사하고, 온콜이 각 분석을 평가합니다. | 근본 원인 분석의 최소 70%가 온콜로부터 맞다고 표시됨 |
| **승인(L2)** | 7–10 | 에이전트가 증거와 함께 완전한 수정을 제안합니다. 사람이 각각을 승인합니다. 수락률과 롤백률을 추적합니다. | 최소 80% 수락, 해로운 작업 0건, MTTR이 눈에 띄게 개선 |
| **졸업(L3)** | 11–13 | 가장 안전하고 가장 자주 반복되는 작업 유형 5~10개를 사전 승인합니다. 에이전트가 행동한 다음 알립니다. 매주 모든 작업을 검토합니다. | 프로덕션에서의 첫 자율 해결, 기준선 대비 MTTR 변화 문서화 |

가장 어려운 문제부터 시작하지 마세요. 파일럿의 목적은 증거와 신뢰를 만드는 것입니다. 잦고 반복적인 인시던트가 있는 지루한 영역이 통계적 확신을 가장 빨리 쌓습니다. 좋은 후보: Kubernetes pod 재시작, 디스크 압박, 인증서 만료, 비용 이상.

하이퍼스케일러도 같은 형태를 권합니다. AWS의 [DevOps Agent 모범 사례](https://aws.amazon.com/blogs/devops/best-practices-for-deploying-aws-devops-agent-in-production/)는 집중된 범위로 시작하고 조사 결과를 바탕으로 확장하라고 말합니다. 벤더가 이 단계를 건너뛰라고 한다면 이유를 물어보세요.

## 9.3 확장: 4개월에서 12개월

| 조치 | 의미 |
| :---- | :---- |
| **자율성만이 아니라 영역을 확장하기** | 데이터베이스, 보안, 비용처럼 한 번에 한 영역씩 추가합니다. 각 영역은 같은 관찰, 승인, 졸업 순서를 거칩니다. |
| **거버넌스를 강제 가능하게 만들기** | 자율성 정책을 문서에서 강제되는 구성으로 옮깁니다. 감독 레이어를 추가하고, 에이전트 작업을 자동 증거와 함께 변경 관리에 넣습니다. |
| **메모리 레이어 구축하기** | 에이전트가 아는 것을 큐레이션합니다: 토폴로지, 규칙, 과거 인시던트, 팀 지식. 시간이 지나면 이것이 배포를 모방하기 어렵게 만듭니다. |
| **온콜 재구성하기** | 자율 해결이 늘어나면 로테이션을 통합하고, 되찾은 시니어 시간을 예방 작업으로 옮기고, [§7.2](/ko/learn/aio/chapter-7-humans-on-the-loop)의 에이전트 운영 및 자율성 정책 역할을 공식화합니다. |
| **매달 보고하기** | [§8.2](/ko/learn/aio/chapter-8-measuring)의 대시보드를 엔지니어링과 비즈니스에 게시합니다: MTTR 추세, 자율 해결률, 피한 호출, 절감한 비용. 예산을 받는 프로그램은 측정되는 프로그램입니다. |

## 9.4 취소되는 40%가 실패하는 방식

[Gartner는](https://www.gartner.com/en/newsroom/press-releases/2025-06-25-gartner-predicts-over-40-percent-of-agentic-ai-projects-will-be-canceled-by-end-of-2027) 2027년 말까지 에이전틱 AI 프로젝트의 40% 이상이 취소될 것으로 예측합니다. 세 가지 원인을 듭니다. 증가하는 비용, 불분명한 비즈니스 가치, 부적절한 위험 통제입니다. 운영에서는 이것이 다섯 가지 구체적인 실패로 나타납니다.

| 실패 | Gartner 원인 | 일어나는 일 | 해결책 |
| :---- | :---- | :---- | :---- |
| **졸업하지 못하는 파일럿** | 불분명한 가치 | 영원한 조언 전용은 안전하게 느껴지지만 아무것도 증명하지 못합니다. 갱신 시점이 와도 보여 줄 MTTR 변화가 없습니다. | 첫날 졸업 기준에 서명하고, 일정대로 지키세요. |
| **증거보다 앞선 자율성** | 부적절한 위험 통제 | 새벽 3시의 자신 있게 틀린 작업 하나가 좋은 작업 백 개가 얻은 것보다 많은 신뢰를 잃게 합니다. | 단계를 절대 건너뛰지 마세요. 수락률과 롤백률이 속도를 정하게 하세요. |
| **오케스트레이션 없는 도구 난립** | 증가하는 비용, 불분명한 가치 | 연결되지 않은 다섯 개의 단일 목적 에이전트가 추가 라이선스와 함께 회전의자 문제를 되살립니다. [§10.3](/ko/learn/aio/chapter-10-road-ahead)은 단일 클라우드 에이전트에서 같은 문제를 추적합니다. | 하나의 오케스트레이터, 하나의 감사 추적, 하나의 대시보드. |
| **제한 없는 모델 지출** | 증가하는 비용 | 모든 노이즈 신호에 대한 최첨단 추론이 첫 갱신 전에 수익을 지워 버립니다. | 첫날부터 2계층 감지와 인시던트별 비용 추적([§8.4](/ko/learn/aio/chapter-8-measuring)). |
| **도구 구매로 취급하기** | 세 가지 모두 | [챕터 1](/ko/learn/aio/chapter-1-complexity-crisis)의 실험과 프로덕션 사이의 격차는 기술 격차가 아니라 운영 모델 격차입니다. | 라이선스만이 아니라 역할 변화, 정책 작업, 신뢰 사다리에 예산을 잡으세요. |

## 9.5 배포하지 말아야 할 때

일부 경우에는 기다려야 합니다. 아래 각 항목은 영구적인 판정이 아니라 먼저 고쳐야 할 것입니다. 이 중 하나라도 무시하고 배포하면 값비싼 실망을 사게 됩니다.

| 결격 사유 | 막히는 이유 | 먼저 고칠 것 |
| :---- | :---- | :---- |
| **추론할 신호가 없음** | 관측성이 드물거나 파편화되어 있으면 에이전트는 노이즈로부터 자신 있게 추론합니다. 사각지대를 증폭하면 자신감 있는 사각지대가 됩니다. | 대상 영역의 로그, 메트릭, 트레이스를 중앙 집중화하세요. |
| **하나의 공유 관리자 자격 증명** | 에이전트의 영향 범위를 제한하거나 침해된 에이전트를 격리할 수 없습니다. | 자율 작업을 허용하기 전에 에이전트별(CloudThinker에서는 연결별)로 범위가 제한된 단기 자격 증명을 발급하세요. |
| **자율성 정책 담당자 없음** | 프로그램이 조언 전용에서 정체되거나 통제되지 않는 행동으로 치닫습니다. | 파일럿이 시작되기 전에 담당자를 지정하세요. 나중에 채울 역할이 아닙니다. |
| **변경 관리에 기계가 시작한 변경의 경로가 없음** | 에이전트 작업이 거버넌스를 우회하거나(규제 환경은 받아들일 수 없음), 완전히 차단됩니다. | 감사 추적이 있는, 기계가 제안하고 사람이 승인하는 변경의 경로를 추가하세요. |
| **첫 대상이 가장 중요하고 가장 되돌리기 어려운 시스템** | 잘못된 작업이 치명적인 곳에서 시작하면 신뢰 사다리가 뒤집힙니다. | 범위가 제한되고 되돌릴 수 있는 영역을 기다리거나 의도적으로 떼어 내세요. |

결격 사유가 하나 더 있는데, 인프라와는 관계가 없습니다. 조직이 라이선스만 사고 역할 재설계, 정책 작업, 신뢰 사다리에 예산을 쓸 수 없다면, 시스템이 아무리 준비되어 있어도 취소되는 40%에 들어갑니다.

## 9.6 CloudThinker에서 파일럿 실행하기

CloudThinker에서 파일럿을 실행한다면 각 단계는 확인할 수 있는 설정에 대응합니다.

| 단계 | CloudThinker에서 |
| :---- | :---- |
| **기준선과 범위** | 먼저 [Approval mode](/guide/approvals/approval-mode)를 **Manual**로 설정하고(**Settings → Workspace → Autonomy → Rules**의 **When no Rule matches**), [**Automations**도 **Manual**로 재정의](/guide/approvals/approval-mode#set-a-mode-for-a-run-type)하세요. 그 행은 워크스페이스를 따르지 않습니다. 그런 다음 하나의 AWS 계정이나 스테이징 Kubernetes 클러스터처럼 범위가 제한된 영역 하나에 대해서만 읽기 전용 자격 증명으로 [연결](/ko/guide/connections/overview)을 추가하세요. 기준선을 위해 페이징 도구에서 최근 90일간의 MTTR과 호출 수를 내보내세요. CloudThinker는 연결하기 전의 기간을 측정할 수 없습니다([§8.2](/ko/learn/aio/chapter-8-measuring)). |
| **관찰** | **Manual**을 유지하세요. 실행 유형, Automation, 채팅이 자체적으로 더 느슨한 모드를 고르지 않는 한, 읽기는 항상 실행되고 모든 쓰기는 사람을 기다립니다. 온콜이 인시던트의 **Was Resolve's diagnosis right?**에서 각 진단을 맞음 또는 틀림으로 표시하게 하세요. 평가에는 워크스페이스 Developer 또는 Admin 역할이 필요하므로, 평가자에게 최소 Developer 역할을 주거나 Developer나 Admin이 온콜의 판정을 기록하게 하세요. |
| **승인** | **Manual**을 유지하고, 제안된 수정이 올바른 사람에게 가도록 **Settings → Workspace → Autonomy → Approvers**에서 [Approvers](/guide/approvals/approvers) 그룹을 추가하세요. 승인 카드는 채팅에 표시되며 Google Chat에서도 동작합니다. Slack과 Microsoft Teams는 승인하기 위해 웹 앱으로 연결합니다. [알림](/ko/guide/notifications)에서 **Agent approvals**를 켜면 이메일이나 채팅으로 요청을 보냅니다. **Resolve → Insights → Accuracy and trust**에서 **Fix acceptance**를 추적하세요. |
| **졸업** | 변경 없이 약 95% 승인되고 롤백이 없었던([§8.2](/ko/learn/aio/chapter-8-measuring)) 특정 작업을 특정 연결에서 **Allow**하는 [Approval Rules](/guide/approvals/rules)를 수락하세요. 그런 다음 **Workspace mode**를 **Auto · Rules · Ask me**로 전환하세요. Allow Rules는 **Auto**에서만 쓰기를 단독으로 실행하며, AI 판단이 꺼져 있으면 Rule이 허용하지 않는 모든 쓰기는 여전히 사람을 기다립니다. |
| **보고** | [Resolve Insights](/guide/incident/insights)에서 MTTR, 자동 해결 비율, 노이즈 수치를 가져오세요. [§8.6](/ko/learn/aio/chapter-8-measuring)에 각 KPI가 있는 곳이 나열되어 있습니다. |

[CloudThinker 소개](/ko/learn/aio/about-cloudthinker)는 이 필드 가이드의 나머지를 제품 기능에 대응시킵니다.

**다음:** [챕터 10 · 앞으로의 길](/ko/learn/aio/chapter-10-road-ahead)은 다가올 변화와, 하이퍼스케일러 네이티브 에이전트와 모든 클라우드에 걸친 하나의 플랫폼 중에서 선택하는 방법을 다룹니다.
