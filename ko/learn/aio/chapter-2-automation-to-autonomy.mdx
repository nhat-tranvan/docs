이 챕터는 에이전트를 이미 운영 중인 도구 옆에 놓고, AIOps가 어디에서 멈췄는지 설명하며, 에이전트를 실용적으로 만든 세 가지 기술 변화를 다룹니다. 에이전트 플랫폼이 현재 스택의 어떤 부분을 재사용하고 어떤 공백을 채워야 하는지 판단하는 데 활용하세요.

## 2.1 운영의 네 세대

| 세대 | 핵심 아이디어 | 자동화한 것 | 수동으로 남은 것 |
| :---- | :---- | :---- | :---- |
| Gen 1: 수작업과 스크립트 | 사람이 시스템을 운영하고, 셸 스크립트가 반복 단계를 처리 | 단일하고 알려진 작업 | 무엇을 언제 실행할지 결정. 지식은 사람의 머릿속에 있었습니다. |
| Gen 2: Infrastructure as Code (IaC) | 원하는 상태를 코드로 선언하고 CI/CD 파이프라인이 적용 | 프로비저닝과 배포 | Day-2 작업: 드리프트, 인시던트, 튜닝, 정리 |
| Gen 3: AIOps | 머신러닝(ML)이 이상을 찾고, 이벤트를 연관 짓고, 노이즈를 줄임 | 문제 발견과 그룹화 | 원인 찾기, 수정 선택, 적용 |
| Gen 4: 에이전틱 운영 | 관찰하고, 추론하고, 행동하고, 결과를 확인하는 목표 지향 에이전트 | 사용자가 정한 정책 아래의 전체 루프 | 정책 설정, 위험한 변경 승인, 새로운 장애 처리 |

각 세대는 이전 세대를 대체하지 않고 그 위에 쌓입니다. 에이전트는 변경을 코드로 표현하고(Gen 2), 연관된 알림을 입력으로 받으며(Gen 3), 여전히 스크립트를 작성하고 실행합니다(Gen 1). 바뀌는 것은 누가 루프를 닫느냐입니다.

여기에는 실질적인 결과가 있습니다. 에이전트는 그 아래 스택만큼만 좋습니다. 시작하기 전에 네 가지를 확인하세요.

- **코드로 된 인프라.** 에이전트가 다룰 시스템이 적어도 부분적으로 Terraform이나 다른 IaC 도구로 정의되어 있습니다.
- **라우팅할 수 있는 알림.** 모니터링 도구가 웹훅으로 알림을 보낼 수 있습니다. [알림 소스 연결](/ko/guide/pulse/setup)을 참조하세요.
- **문서화된 런북.** 알려진 수정 방법이 Confluence, Git 리포지토리, Markdown 파일에 있습니다. [런북](/ko/guide/incident/runbooks)을 참조하세요.
- **읽기 전용 자격 증명.** 각 클라우드 계정이나 클러스터에 대해 범위가 한정된 읽기 전용 자격 증명을 발급할 수 있습니다. [연결](/ko/guide/connections/overview)을 참조하세요.

전체 준비 상태 점검은 [챕터 9](/ko/learn/aio/chapter-9-roadmap)에 있습니다.

## 2.2 AIOps가 부족했던 이유

AIOps는 제 몫을 했습니다. 이벤트 연관과 중복 제거는 작동하며 알림 양을 줄입니다. 하지만 도구는 "여기 알림 그룹이 있습니다"에서 멈췄고, 나머지는 여전히 사람이 해야 했습니다.

세 가지 공백이 한계를 정했습니다.

1. **인과 없는 연관.** 알림 50개를 하나의 인시던트로 묶는 것은 도움이 됩니다. 하지만 여전히 근본 원인이나 해야 할 일을 알려 주지 않습니다.
2. **추론 없는 답.** 설명 없는 ML 점수는 신뢰하기 어렵습니다. 엔지니어는 출력을 손으로 다시 확인했고, 그 바람에 절약한 시간의 대부분이 사라졌습니다.
3. **손이 없음.** AIOps는 티켓을 열거나 웹훅을 호출할 수 있었습니다. 조사하고, 가설을 테스트하고, 수정을 고르고, 적용하고, 작동을 확인할 수는 없었습니다. 행동하는 사람은 여전히 엔지니어였습니다.

## 2.3 무엇이 바뀌었나: 추론 모델, 도구, 프로토콜

세 가지 변화가 운영 작업에서 에이전트를 실용적으로 만들었습니다.

1. **추론 모델.** 대규모 언어 모델(LLM)은 이제 로그, 구성, 코드를 읽고, 원인에 대한 가설을 세우고, 범위가 잘 정해진 영역에서 다단계 수정을 계획할 수 있습니다.
2. **도구 사용.** 모델은 함수를 안정적으로 호출할 수 있습니다. CLI 명령 실행, API 쿼리, `kubectl`이나 Terraform 실행, 대시보드 읽기입니다. 이것이 추론을 행동으로 바꿉니다.
3. **도구를 연결하는 표준 방식.** Model Context Protocol(MCP)은 AI 에이전트에 도구를 노출하는 개방형 표준입니다. 팀이 내부 시스템 앞에 MCP 서버 하나를 두면 호환되는 모든 에이전트가 이를 사용할 수 있습니다.

운영이 에이전트에 적합한 이유가 하나 더 있습니다. 결과를 확인하기 쉽습니다. 수정은 지연 시간을 목표 아래로 되돌리거나 그렇지 못합니다. Terraform plan은 깔끔하게 적용되거나 실패합니다. 헬스 체크는 통과하거나 통과하지 못합니다. 피드백이 이렇게 명확하면 에이전트는 자신의 작업을 테스트할 수 있고, 사용자는 그 결과를 볼 수 있습니다.

## 2.4 업계는 에이전트를 어떻게 도입하고 있나

주요 클라우드 제공자는 이제 자체 운영 에이전트를 제공합니다. AWS DevOps Agent, Azure SRE Agent, Google Cloud의 Gemini Cloud Assist입니다(각각이 자율성을 다루는 방식은 [3.2](/ko/learn/aio/chapter-3-what-is-aio#32-자율성-스펙트럼)에서 다룹니다). 모두 같은 방식으로 출시했습니다. 먼저 조사하고, 모든 변경은 고객의 승인 뒤에 둡니다.

이 패턴이 자체 도입의 교훈입니다. 읽고 설명하는 에이전트로 시작하고, 그 분석을 엔지니어가 찾은 것과 비교한 뒤에야, 한 번에 한 종류의 작업씩 행동하게 하세요. [챕터 7](/ko/learn/aio/chapter-7-humans-on-the-loop)과 [챕터 9](/ko/learn/aio/chapter-9-roadmap)가 이를 단계별 계획으로 바꿉니다.

## 2.5 CloudThinker의 위치

CloudThinker의 프론티어 조사 에이전트는 이미 가진 스택에서 감지, 분석, 해결, 검증 루프를 실행하며, 각 계층을 대체하지 않고 재사용합니다.

| 기존 계층 | CloudThinker가 사용하는 방식 |
| :---- | :---- |
| 모니터링 및 알림(Gen 3) | [Signals](/ko/guide/pulse/overview)는 도구가 이미 보내는 알림을 받아 알려진 노이즈를 버리고 관련 알림을 클러스터로 묶습니다. |
| 클라우드, Kubernetes, IaC(Gen 2) | 에이전트는 [AWS](/ko/guide/connections/aws), [Kubernetes](/ko/guide/connections/kubernetes), [Terraform](/guide/connections/terraform) 등 [연결](/ko/guide/connections/overview)을 통해 읽고 행동합니다. |
| 내부 도구 | 자체 MCP 서버를 [MCP 연결](/ko/guide/connections/mcp)로 추가하면 에이전트가 그 도구를 호출할 수 있습니다. |
| 스크립트와 런북(Gen 1) | [런북](/ko/guide/incident/runbooks)이 알려진 수정 방법을 담습니다. 모든 변경은 [Approvals](/guide/approvals/overview)를 거치므로, 사용자가 정한 정책에 따라 실행되거나, 사람을 기다리거나, 거부됩니다. 새 워크스페이스는 **Auto · Rules + AI · Ask me**로 시작합니다. 읽기는 항상 실행되고, Rules가 허용하는 쓰기는 실행되며, AI 판단이 안전한 쓰기를 허용할 수 있고, 나머지는 사람을 기다립니다. **Settings → Workspace → Autonomy → Rules**의 **When no Rule matches** 아래에서 변경하세요. |

새 워크스페이스에서의 첫 1시간:

1. 읽기 전용 클라우드 또는 Kubernetes [연결](/ko/guide/connections/overview)을 추가합니다. [빠른 시작](/ko/quickstart)이 안내합니다.
2. 알림 소스 하나를 [Signals](/ko/guide/pulse/setup)로 지정합니다.
3. [Approvals](/guide/approvals/overview) 기본값을 확인합니다. 평가하는 동안 모든 쓰기를 사람이 승인하게 하려면 **Manual**로 전환하고, [실행 유형 행](/guide/approvals/approval-mode#set-a-mode-for-a-run-type)에서 **Automations**도 **Manual**로 재정의하세요. 그 행은 워크스페이스 설정을 따르지 않기 때문입니다. 채팅도 자체 모드를 고를 수 있습니다.
4. [Resolve 빠른 시작](/guide/incident/quickstart)으로 테스트 알림을 보내고 CloudThinker가 [Resolve](/ko/guide/incident/overview)에서 조사하는 것을 지켜보세요.

<Info>
**핵심 요점**

AIOps는 시스템을 보이게 만들었습니다. 에이전틱 운영은 시스템을 운영 가능하게 만듭니다. 차이는 닫힌 루프입니다. 관찰하고, 추론하고, 행동하고, 결과를 확인하며, 사람은 모든 단계를 직접 하는 대신 감독합니다.
</Info>
