프로덕션 배포가 수렴하고 있는 레퍼런스 아키텍처는 오케스트레이터, 전문가 팀, 닫힌 운영 루프, 컨텍스트 계층으로 구성됩니다.

## 4.1 단일 에이전트가 아닌 멀티 에이전트인 이유

이 챕터는 벤더 중립적인 패턴을 설명합니다. 4.2~4.4절은 각 부분이 CloudThinker의 어디에 있는지 보여 주며, [챕터 10.3](/ko/learn/aio/chapter-10-road-ahead#103-하이퍼스케일러-에이전트인가-클라우드-전반의-하나의-플랫폼인가)은 이를 하이퍼스케일러 자체 에이전트와 비교합니다.

프로덕션 시스템은 하나의 범용 에이전트 대신 오케스트레이션된 전문가 팀을 사용합니다. 이유는 실용적입니다.

1. **깊이가 폭을 이깁니다.** 엄선된 K8s 도구, 프롬프트, 학습된 패턴을 가진 Kubernetes 전문가는 K8s 문제에서 범용 에이전트보다 뛰어납니다. 사람 팀이 전문화하는 것과 같은 이치입니다.

2. **제한된 영향 범위.** 각 전문가는 자기 영역에 필요한 자격 증명만 가집니다. 데이터베이스 에이전트는 보안 그룹을 수정할 수 없고, 비용 에이전트는 테이블을 삭제할 수 없습니다.

3. **독립적인 발전.** 전문가는 독립적으로 업그레이드, 평가, 롤백할 수 있습니다. 마이크로서비스의 교훈을 에이전트에 적용한 것입니다.

4. **감사 가능한 인계.** 에이전트 간 위임은 누가 무엇을 결정했는지에 대한 명시적인 기록을 남기며, 단일 추론은 이를 숨깁니다.

설계상의 결과: 오케스트레이션 계층(작업 라우팅, 컨텍스트 관리, 오류 처리)에는 에이전트 자체만큼의 엔지니어링이 필요합니다.

공개된 두 사례가 한계를 정합니다.

- **전문화를 지지하는 사례.** Anthropic의 [멀티 에이전트 연구 시스템](https://www.anthropic.com/engineering/multi-agent-research-system)은 작업을 병렬 환경으로 나누는 리드 에이전트를 사용합니다. 단일 에이전트 대비 큰 품질 향상을 보고하지만 토큰 비용이 훨씬 높습니다. 이 비용 때문에 [4.3](#43-2계층-감지와-해결)의 2계층 설계가 중요합니다.
- **과도함을 경계하는 사례.** Microsoft의 Azure SRE Agent 팀은 100개 이상의 도구와 50개 이상의 좁은 에이전트로 시작해, 다섯 개의 핵심 도구와 소수의 범용 에이전트로 끝났다고 [썼습니다](https://techcommunity.microsoft.com/blog/appsonazureblog/-/4481200). 수십 개의 마이크로 에이전트가 아니라 영역과 자격 증명 경계로 전문화하세요. 추가하는 모든 에이전트와 도구는 컨텍스트, 토큰, 조율 비용을 발생시킵니다.

## 4.2 레퍼런스 아키텍처

프로덕션 에이전틱 운영 플랫폼에는 다섯 계층이 있습니다. 플랫폼을 평가하거나 직접 설계할 때 체크리스트로 사용하세요.

| 계층 | 역할 | 평가 시 확인할 것 | CloudThinker에서 |
| :---- | :---- | :---- | :---- |
| **오케스트레이터** | 목표와 인시던트를 받아 작업으로 나누고, 전문가에게 작업을 라우팅하고, 발견 사항을 합치고, 사람에게 에스컬레이션합니다 | 하나의 에이전트가 대화와 에스컬레이션 경로를 소유하나요? | 기본 제공 [CloudThinker](/ko/guide/agents/overview) 어시스턴트 |
| **전문가 에이전트** | 엄선된 도구와 범위가 정해진 자격 증명을 가진 영역 전문가(클라우드, 보안, 데이터베이스, Kubernetes) | 자체 전문가를 추가하고 각각의 연결을 제한할 수 있나요? | CloudThinker가 생성하는 임시 하위 에이전트와 직접 만드는 [커스텀 에이전트](/guide/agents/quickstart) |
| **운영 루프** | 감지, 분석, 해결, 검증. 검증 단계가 에이전트와 자동화를 구분합니다. 시스템이 자신의 작업을 확인합니다. | 플랫폼이 행동 후 결과를 확인하고 실패 시 롤백하나요? | [Signals](/ko/guide/pulse/overview)가 감지하고, [Resolve](/ko/guide/incident/overview)가 조사하고 수정하며, [Approvals](/guide/approvals/overview)가 어떤 쓰기를 실행할지 결정합니다 |
| **도구와 통합** | 에이전트별 최소 권한 자격 증명을 사용하는 클라우드 API, 관측성, CI/CD, ITSM, 채팅 | 자격 증명이 시스템별로 범위가 정해져 있고, 자체 도구를 연결할 수 있나요? | 자체 [MCP 서버](/ko/guide/connections/mcp)를 포함한 [연결](/ko/guide/connections/overview) |
| **컨텍스트와 메모리** | 토폴로지, 런북, 과거 인시던트, 팀 규칙, 환경 메타데이터. 에이전트의 역량이 누적되는 곳입니다. | 시스템이 배운 것을 기억하고, 그것을 보고 편집할 수 있나요? | [Memory](/guide/memory), [런북](/ko/guide/incident/runbooks), [인시던트 메모리](/ko/guide/incident/incident-memory) |

## 4.3 2계층 감지와 해결

단순한 에이전트 설계는 알림마다 모델 호출을 한 번씩 실행하며 프로덕션 규모에서 무너집니다. 성숙한 플랫폼은 두 계층을 분리합니다. 모든 신호를 지켜보는 저렴하고 항상 켜진 감지 계층과, 감지 계층이 가치 있는 것을 찾았을 때만 전체 다단계 조사를 실행하는 비싼 추론 계층입니다. 이것이 24시간 커버리지를 감당할 수 있게 만듭니다. 플랫폼을 평가할 때는 무엇이 비싼 계층에 도달하는지 어떻게 결정하는지 물어보세요. 그 결정이 모델 청구서를 좌우합니다.

CloudThinker에서는 [Signals](/ko/guide/pulse/overview)가 감지 계층입니다. 중복과 노이즈를 버리고, 관련 알림을 클러스터로 묶고, 조치 가능한 신호가 있는 클러스터만 분류(triage)로 보냅니다. 그곳에서 CloudThinker가 인시던트를 열거나 기존 인시던트와 일치시키고 조사합니다. 에스컬레이션 대상은 세 곳에서 조정합니다.

- [노이즈 억제](/ko/guide/pulse/clusters#노이즈-억제)의 **Snoozes**는 이미 알고 있는 이벤트를 버립니다.
- **Resolve → Issues**의 **AI auto-investigate** 스위치는 CloudThinker가 스스로 조사할지, 누군가 **Investigate**를 클릭할 때까지 기다릴지 결정합니다. [Resolve](/ko/guide/incident/overview#조사를-시작할-주체-선택)를 참조하세요.
- [Signals 설정](/ko/guide/pulse/setup)에서 연결하는 소스가 애초에 무엇이 Signals에 도달하는지 결정합니다.

## 4.4 파이프라인 내부의 데이터 보호

규제 산업에서 텔레메트리는 민감합니다. 로그와 쿼리는 고객 PII, 자격 증명, 계정 데이터를 유출합니다. 떠오르는 모범 사례는 토큰화 경계입니다. 데이터가 모델에 도달하기 전에 민감한 값을 토큰으로 대체하는 PII 인식 계층입니다. 비공개 배포와 결합하면 은행과 기타 규제 대상 기업이 원시 텔레메트리를 경계 밖으로 내보내지 않고 에이전틱 운영을 도입할 수 있습니다. [챕터 6](/ko/learn/aio/chapter-6-trust-governance#63-데이터-레지던시와-통제)이 데이터 레지던시와 통제를 깊이 다룹니다.

### CloudThinker에서

- **마스킹.** [Guardrails](/guide/security/custom-guardrails)는 에이전트가 읽기 전에 민감한 값을 플레이스홀더로 대체합니다. 이메일, 전화번호, 신용카드, IBAN, MAC 주소, API 키, 클라우드 자격 증명은 기본적으로 켜져 있습니다. IP 주소, 공개 키, 클라우드 계정 ID는 기본적으로 꺼져 있습니다. **Settings → Organization → Guardrails**에서 자체 ID 패턴을 추가할 수 있습니다.
- **배포.** CloudThinker Cloud, 자체 머신의 [Environments](/guide/workers)를 더한 Cloud, 그리고 얼리 액세스 프로그램을 통한 전용, 셀프 호스팅, 에어갭 배포. [배포 옵션](/ko/guide/deployment/overview)을 참조하세요.
- **자체 계정으로 모델 호출.** [BYOK](/ko/guide/byok)는 자체 모델 제공자 계정으로 모델 호출을 실행합니다.

## 아키텍처 체크리스트

모든 벤더나 자체 팀에 물어보세요.

1. 하나의 오케스트레이터가 횡단적 추론과 사람으로의 에스컬레이션을 소유하나요?
2. 각 전문가가 자기 영역에 필요한 자격 증명만 가지나요?
3. 모든 작업이 감지, 분석, 해결, 검증을 거치고, 행동 후 결과가 확인되나요?
4. 비싼 추론 계층 앞에 저렴한 감지 계층이 있고, 에스컬레이션 대상을 조정할 수 있나요?
5. 모델 호출 전에 개인 식별자와 시크릿이 마스킹되나요?
6. 규제 대상 워크로드를 위한 비공개 또는 셀프 호스팅 배포 옵션이 있나요?
7. 시스템이 인시던트 사이에 메모리를 유지해 매번 처음부터 시작하지 않나요?
