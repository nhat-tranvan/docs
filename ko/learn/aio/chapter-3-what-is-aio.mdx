*정의가 중요합니다. "에이전트"는 엔터프라이즈 소프트웨어에서 가장 남용되는 단어이기 때문입니다.*

이 챕터는 네 가지 도구를 제공합니다. 인용할 수 있는 정의, 에이전트가 스스로 할 수 있는 일을 정하는 5단계 자율성 척도, 에이전틱 운영이 아닌 것의 목록, 그리고 벤더를 위한 다섯 가지 질문 테스트입니다.

## 3.1 실용적 정의

<Info>
**정의**

에이전틱 인프라 운영(AgenticOps)은 AI 에이전트가 클라우드 및 온프레미스 인프라 전반에서 운영 작업의 핵심 루프(조건 감지, 원인 분석, 문제 해결, 결과 검증)를 실행하는 운영 모델입니다. 에이전트는 사람이 정의한 명시적 정책 아래에서 일합니다. 사람은 루프 *안에서* 실행하는 대신 루프 *위에서* 감독합니다.
</Info>

이 의미에서 에이전트는 런북이 달린 챗봇이 아니며, LLM을 덧붙인 스크립트도 아닙니다. 진정한 운영 에이전트는 다섯 가지 속성을 가집니다. 어떤 도구를 평가할 때든 체크리스트로 사용하세요.

| 속성 | 의미 | 확인할 것 |
| :---- | :---- | :---- |
| **목표 지향적** | 단계별 지침이 아니라 결과를 받습니다 | "keep checkout latency under 300ms"나 "keep monthly cloud spend within budget"라고 말할 수 있습니다 |
| **지각적** | 프롬프트를 기다리지 않고 텔레메트리를 지속적으로 읽습니다 | 메트릭, 로그, 트레이스, 이벤트, 구성 상태, 비용 데이터를 소비합니다 |
| **추론적** | 인과 가설을 세우고 테스트하며, 대안적 수정을 비교합니다 | 엔지니어가 감사할 수 있는 언어로 사고 과정을 설명합니다 |
| **도구 사용** | 엔지니어가 이미 사용하는 인터페이스를 통해 행동합니다 | 범위가 제한되고 감사 가능한 자격 증명으로 클라우드 API, kubectl, Terraform, SQL, CI/CD와 함께 동작합니다 |
| **자기 검증** | 행동한 후 결과가 달성되었는지 확인합니다 | 수정이 효과가 없으면 에스컬레이션하거나 롤백합니다 |

도구에 이 중 하나라도 없다면 에이전트가 아니라 어시스턴트로 취급하세요.

## 3.2 자율성 스펙트럼

자율성은 켜짐과 꺼짐으로 나뉘지 않습니다. 성숙한 에이전틱 플랫폼은 자율성을 정책 다이얼로 제공하며, 보통 작업 유형별(예: "pod 재시작")과 환경별(예: 프로덕션 대 스테이징)로 설정합니다.

| 레벨 | 이름 | 에이전트 동작 | 사람의 역할 |
| :---- | :---- | :---- | :---- |
| L0 | 관찰 | 모니터링하고 보고하며, 아무 조치도 하지 않습니다 | 모든 것을 실행합니다 |
| L1 | 조언 | 조사하고 증거와 함께 권고합니다 | 결정하고 실행합니다 |
| L2 | 승인 후 실행 | 전체 해결 조치를 준비하고 승인을 기다립니다 | 원클릭으로 승인/거부합니다 |
| L3 | 알림과 함께 실행 | 사전 승인된 작업 유형을 실행하고 사람에게 알립니다 | 사후에 검토합니다 |
| L4 | 영역 내 자율 | 정책 안에서 범위가 제한된 영역을 처음부터 끝까지 맡습니다 | 정책을 정하고 결과를 감사합니다 |

대부분의 조직은 여러 레벨을 동시에 운영합니다. 모든 작업 유형은 낮게 시작해 단계적으로 올라갑니다. 증거가 쌓인 후의 일반적인 상한:

| 작업 유형 | 예시 | 일반적인 상한 |
| :---- | :---- | :---- |
| 되돌릴 수 있고 영향 범위가 작음 | pod 재시작, 캐시 비우기, replica set 확장 | L3에서 L4 |
| 결과가 큰 변경 | 스키마 마이그레이션, 보안 그룹 변경, 페일오버, 자격 증명 교체(자격 증명을 사용하는 모든 곳이 깨질 수 있음) | L2 |
| 새로운 모든 것 | 에이전트가 이 환경에서 이전에 수행한 적 없는 해결 조치 | L1 |

현재 레벨에서 동작한다는 증거가 있을 때만 작업 유형을 한 레벨 올리세요. [챕터 8 KPI](/ko/learn/aio/chapter-8-measuring#82-운영-대시보드)를 관문으로 사용하세요. 그 작업 유형의 수락률이 약 95%를 넘고, 롤백 및 개입 비율이 그대로이거나 줄어들어야 합니다. 이보다 빠르게 올리지 마세요. [챕터 7](/ko/learn/aio/chapter-7-humans-on-the-loop#73-신뢰는-단계적으로-쌓입니다)은 이것을 단계별 신뢰 사다리로 정리합니다.

### CloudThinker에서는

CloudThinker는 L0에서 L4 같은 레이블을 사용하지 않습니다. 읽기는 항상 실행되며, 모든 쓰기는 **Settings → Workspace → Autonomy → Rules**의 **When no Rule matches**에서 설정하는 [Approvals](/guide/approvals/overview)를 거칩니다. 각 레벨은 다음 설정에 대응합니다.

| 레벨 | CloudThinker에서 얻는 방법 |
| :---- | :---- |
| L0에서 L1 | 조사만 요청하고, 에이전트가 절대 변경해서는 안 되는 연결에서는 **Allow writes**를 꺼 두세요. **Deny** [Rule](/guide/approvals/rules)이 두 번째 레이어를 더합니다. |
| L2 | [Approval mode](/guide/approvals/approval-mode)를 **Manual**로 설정하면 사람이 모든 쓰기를 승인합니다. **Ask first** Rule로 한 종류의 쓰기로 좁힐 수 있습니다. |
| L3 | **Auto** 모드가 설정된 상태에서, 수락된 **Allow** Rule이 지정된 연결에서 하나의 작업을 스스로 실행합니다. |
| L4 | 단일 스위치는 없습니다. 범위가 제한된 영역을 [Automation](/guide/automation/automations)으로 실행하고, 그 쓰기 작업에 **Allow** Rules를 둡니다. |

새 워크스페이스는 **Auto · Rules + AI · Ask me**로 시작합니다. AI 판단이 안전한 쓰기를 허용하고 나머지는 사람에게 묻습니다. 수락된 [Rule](/guide/approvals/rules)이 먼저 결정하며, Approval mode는 어떤 Rule과도 일치하지 않는 쓰기를 처리합니다.

<Info>
**하이퍼스케일러가 다이얼을 제공하는 방식**

- [Gemini Cloud Assist investigations](https://docs.cloud.google.com/cloud-assist/investigations)는 근본 원인 분석을 실행하고 관찰 결과를 보고합니다. 리소스를 변경하지 않습니다(L1).
- [AWS DevOps Agent](https://docs.aws.amazon.com/devopsagent/latest/userguide/about-aws-devops-agent.html)는 인시던트를 조사하고 실행할 완화 계획을 건넵니다(L1에서 L2).
- [Azure SRE Agent](https://learn.microsoft.com/en-us/azure/sre-agent/overview)에는 작업이 승인을 기다리는 Review 모드와, 허용한 작업을 위한 더 자율적인 모드가 있습니다(L2에서 L3).

세 가지 모두 에이전트를 낮은 신뢰로 시작하고 더 많은 신뢰를 얻어 내게 합니다.
</Info>

## 3.3 에이전틱 운영이 아닌 것

"에이전트 워싱(agent washing)"은 Gartner가 이름을 붙일 만큼 흔합니다. 실제 에이전틱 능력 없이 어시스턴트, 챗봇, RPA를 "에이전트"로 리브랜딩하는 벤더들입니다. [2025년 6월 보도자료](https://www.gartner.com/en/newsroom/press-releases/2025-06-25-gartner-predicts-over-40-percent-of-agentic-ai-projects-will-be-canceled-by-end-of-2027)에서 Gartner는 에이전틱 AI를 주장하는 수천 개의 벤더 중 실제는 약 130개뿐이라고 추정했습니다. 에이전틱 운영이 *아닌* 것을 아는 것이 구매자로서 최선의 방어입니다.

1. **대시보드 위의 챗봇이 아닙니다.** 텔레메트리와 채팅하는 것은 기능이지 운영 모델이 아닙니다. 사람이 답을 읽고 직접 가서 작업해야 한다면, 마케팅이 뭐라고 하든 여전히 3세대에 있는 것입니다([챕터 2](/ko/learn/aio/chapter-2-automation-to-autonomy) 참조).

2. **무인 운영이 아닙니다.** 신뢰할 만한 실무자 중 사람을 없애자고 주장하는 사람은 없습니다. 목표는 사람의 레버리지입니다. 한 명의 엔지니어가 예전에는 팀이 하던 작업을 감독하는 것입니다.

3. **엔지니어링 규율의 대체물이 아닙니다.** 에이전트는 주어진 환경을 증폭합니다. 약한 관측성, 없는 IaC, 문서화되지 않은 시스템은 약한 에이전트를 만듭니다. 쓰레기 컨텍스트가 들어가면 쓰레기 자율성이 나옵니다.

4. **모든 것을 하는 하나의 거대한 모델이 아닙니다.** 다음 챕터에서 보듯이, 프로덕션 시스템은 단일 초거대 모델이 아니라 오케스트레이션된 전문가 팀으로 수렴하고 있습니다.

<Warning>
**다섯 가지 질문 벤더 테스트**

"에이전틱" 벤더에게 물어보세요.

1. 시스템이 해결 조치를 처음부터 끝까지 실행할 수 있나요, 아니면 권고만 하나요?
2. 자신의 결과를 검증하고 실패 시 롤백하나요?
3. 자율성을 작업 유형별, 환경별로 설정할 수 있나요?
4. 모든 작업에 완전하고 변경 불가능한 추론 기록이 남나요?
5. 최근 세 번의 프로덕션 배포에서 롤백 및 개입 비율은 얼마였나요?

실제 플랫폼은 로드맵 슬라이드가 아니라 증거로 다섯 가지 모두에 답합니다. 에이전트 워싱은 보통 두 번째 질문에서 실패합니다.
</Warning>

## 3.4 오늘날 에이전트가 맡을 수 있는 운영 작업의 범위

첫 번째 영역을 고를 때 이 표를 사용하세요. 일반적인 자율성이 가장 높고 작업을 되돌리기 가장 쉬운 곳, 보통 클라우드 비용이나 Kubernetes 운영에서 시작한 다음 확장하세요. 마지막 열은 CloudThinker에서 시작할 곳을 보여 줍니다.

| 영역 | 대표적인 에이전트 작업 | 일반적인 자율성(2026) | CloudThinker에서 |
| :---- | :---- | :---- | :---- |
| 인시던트 대응 | 트리아지, 상관 분석, 근본 원인 분석, 해결 조치, 사후 보고서 | L1에서 L3 | [Resolve](/ko/guide/incident/overview) |
| 클라우드 비용(FinOps) | 적정 크기 조정, 유휴 리소스 정리, 약정 계획, 이상 탐지 | L2에서 L4 | [Optimize](/ko/guide/cost-optimization/overview) |
| Kubernetes 운영 | Pod/노드 상태, 리소스 튜닝, 업그레이드 지원, 용량 계획 | L2에서 L3 | [Kubernetes 연결](/ko/guide/connections/kubernetes) |
| 데이터베이스 운영 | 느린 쿼리 분석, 인덱스 조언, 복제 상태, 스토리지 예측 | L1에서 L3 | [PostgreSQL](/ko/guide/connections/postgresql) 같은 데이터베이스 연결 |
| 보안 운영 | 잘못된 구성 탐지, CVE 트리아지, IAM 위생, 컴플라이언스 증거 | L1에서 L2 | [Cyber](/guide/security/cyber-overview) |
| 변경 및 릴리스 | 배포 전 위험 분석, 카나리 모니터링, 자동 롤백 | L2에서 L3 | 배포 전 위험을 위한 [Review](/ko/guide/code-review/overview) |
| Infrastructure as Code | 드리프트 탐지, 모듈 생성, plan 검토, state 위생 | L1에서 L3 | [Terraform 연결](/guide/connections/terraform) |

여기의 자율성 범위는 2026년 업계의 일반적인 수준이며 고정된 한계가 아닙니다. 실제 레벨은 관측성, IaC, 런북이 얼마나 좋은지에 달려 있습니다.
