*에이전틱 운영은 기술의 옷을 입은 사람의 변화입니다.*

이 챕터에서는 운영 작업을 직접 하는 것에서 감독하는 것으로의 전환, 각 운영 역할의 변화, 그리고 에이전트에게 작업을 넘기는 4단계 신뢰 사다리를 다룹니다. 7.5절은 사다리의 각 단계를 CloudThinker 설정에 대응시킵니다.

## 7.1 실행자에서 감독자로

"루프 안의 인간(human in the loop)"은 사람이 실행 경로 안에 있다는 뜻입니다. 모든 단계가 그 사람을 기다립니다. "루프 위의 인간(human on the loop)"은 사람이 감독한다는 뜻입니다. 의도와 정책을 정하고, 결과가 큰 작업을 승인하고, 결과를 감사하고, 예외적인 경우에 개입합니다.

| | 루프 안의 인간 | 루프 위의 인간 |
| :---- | :---- | :---- |
| 각 단계를 실행하는 주체 | 엔지니어 | 에이전트 |
| 엔지니어가 하는 일 | 트리아지, 명령 실행, 수정 작성 | 정책 설정, 영향이 큰 쓰기 승인, 결과 검토 |
| 엔지니어가 필요한 때 | 모든 단계 | 새로운 장애와 결과가 큰 결정 |
| 처리량을 제한하는 것 | 엔지니어의 시간 | 정책이 허용하는 자율성의 양 |

손으로 비행기를 조종하는 조종사와 오토파일럿을 관리하는 조종사를 생각해 보세요. 두 번째 조종사가 덜 중요한 것이 아닙니다. 더 적은 수작업으로 항공기의 더 많은 부분을 책임지며, 판단이 가장 중요한 순간에 조종간을 잡습니다.

잘하는 팀은 의도적으로 역할을 재설계합니다. 그렇지 않은 팀은 더 이상 이해하지 못하는 승인에 도장만 찍는 엔지니어를 갖게 됩니다.

## 7.2 역할의 변화

| 현재 역할 | 줄어드는 것 | 늘어나는 것 |
| :---- | :---- | :---- |
| SRE 또는 온콜 엔지니어 | 수동 트리아지, 로그 뒤지기, 새벽 3시의 기계적인 수정 | 정책 설계, 에이전트 감독, 새로운 장애를 위한 엔지니어링, 신뢰성 아키텍처 |
| DevOps 또는 플랫폼 엔지니어 | 티켓 기반 프로비저닝, 반복되는 파이프라인 수정 | 에이전트 활성화: 연결, 컨텍스트와 런북, 골든 패스, 평가 |
| 운영 관리자 또는 IT 운영 리더 | 인원 기반 용량 계획, 워룸 조율 | 자율성 거버넌스, 에이전트가 맡는 작업 관리, 결과 기반 벤더 관리 |
| 보안 엔지니어 | 잘못된 구성의 수동 탐색, 컴플라이언스 스크린샷 수집 | 가드레일 설계, 에이전트 권한 설계, 지속적인 컴플라이언스 점검 |

두 가지 새로운 직무가 생깁니다. 둘 다 부수 업무가 아니라 커리어 경로로 다루세요.

- **에이전트 운영 엔지니어.** 에이전트 자체의 건강을 맡습니다: 지침, 연결, 스킬, 메모리, 평가, 비용.
- **자율성 정책 책임자.** 보통 시니어 SRE나 엔지니어링 관리자입니다. 어떤 종류의 작업이 신뢰 사다리를 올라갈지 결정하고, 에이전트와 사람의 의견이 다를 때 분쟁을 해결합니다.

## 7.3 신뢰는 단계적으로 쌓입니다

엔지니어는 예측 가능한 순서로 에이전트를 신뢰하게 됩니다. 단계를 건너뛰면 역효과가 납니다.

| 단계 | 에이전트가 하는 일 | 사람이 하는 일 | 다음으로 넘어가는 시점 |
| :---- | :---- | :---- | :---- |
| **1. 조사하는 모습 지켜보기** | 조사하고 권고합니다. 변경은 하지 않습니다. | 에이전트의 근본 원인 분석을 자신의 분석과 비교합니다. | 근본 원인 분석의 최소 70%가 온콜로부터 맞다고 평가받을 때. |
| **2. 작업 승인하기** | 완전한 수정을 제안하고 기다립니다. | 각 쓰기를 승인하거나 거부합니다. 모든 결정은 에이전트 판단에 대한 레이블이 붙은 데이터 포인트입니다. | 제안의 최소 80%가 수락되고 해로운 작업이 0건일 때. 작업 유형이 변경 없이 약 95% 승인되고 롤백이 없으면 하나씩 졸업시킵니다([§8.2](/ko/learn/aio/chapter-8-measuring)). |
| **3. 일상 작업 사전 승인하기** | 검증된 작업을 단독으로 실행합니다. | 알림을 받고, 나중에 기록을 검토합니다. | 영역 전체의 롤백 및 개입 비율이 그대로이거나 줄어들 때. |
| **4. 영역 위임하기** | 유휴 리소스 정리, 캐시 관리, 인증서 교체처럼 범위가 제한된 영역을 처음부터 끝까지 맡습니다. | 각 작업을 승인하는 대신 일정에 따라 결과를 감사합니다. | 마지막 단계. 인시던트가 있을 때마다, 그리고 예정된 감사 때마다 다시 검토합니다. |

70%와 80% 기준은 [§9.2](/ko/learn/aio/chapter-9-roadmap)의 파일럿 종료 기준과 일치합니다. CloudThinker에서는 온콜이 인시던트의 **Was Resolve's diagnosis right?**에서 각 근본 원인 분석을 평가하며, 워크스페이스 Developer와 Admin 역할만 그 평가를 기록할 수 있습니다. 평가자에게 최소 Developer 역할을 주거나, Developer나 Admin이 온콜의 판정을 기록하게 하세요.

실패 양상은 일관됩니다. 단계를 건너뛰면 새벽 3시에 자신 있게 틀리는 에이전트를 배포하게 됩니다. 그런 인시던트 하나가 에이전틱 프로그램을 몇 달씩 후퇴시킬 수 있습니다. 단계를 순서대로 밟으면 자율성이 누적됩니다.

1단계를 위한 실용적인 테스트: 팀이 이미 종료한 인시던트를 에이전트에게 주고 답을 비교하세요.

```text
Investigate why checkout-api returned 5xx errors between 14:00 and 14:20 UTC yesterday. Give the root cause, the evidence for it, and the fix you would propose. Don't change anything.
```

이렇게 종료된 인시던트 여러 개를 재현해 보세요. 최소 70%에서 포스트모템과 일치하는 증거와 함께 근본 원인을 맞히면 2단계로 넘어가세요.

## 7.4 되찾은 시간을 측정하기

감독자 모델의 성과는 시니어의 시간이 반복 작업에서 예방 작업으로 옮겨 가는 것입니다. 측정하지 않으면 비즈니스 케이스에 나타나지 않습니다.

- **온콜 부담:** 페이징 도구에서 집계한 엔지니어당 주간 호출 수, 업무 시간 외 호출은 별도로 계산([§8.2](/ko/learn/aio/chapter-8-measuring)).
- **반복 작업 시간:** 티켓 시스템이나 2주간의 시간 조사에서 집계한 주당 트리아지 및 증거 수집 시간([§8.3](/ko/learn/aio/chapter-8-measuring)).

파일럿 전과 사다리의 각 단계에서 둘 다 기록하세요.

## 7.5 CloudThinker의 신뢰 사다리

CloudThinker에서는 읽기가 항상 실행되며 모든 쓰기는 [Approvals](/guide/approvals/overview)를 거칩니다. 사다리의 각 단계는 보고 바꿀 수 있는 설정입니다.

| 단계 | Approval mode | 설정 방법 | 위치 |
| :---- | :---- | :---- | :---- |
| **1. 조사하는 모습 지켜보기** | **Manual** | 무엇이든 연결하기 전에 **Workspace mode**를 **Manual**로 설정하여 모든 쓰기가 사람을 기다리게 합니다. Automations를 실행할 예정이라면, **When no Rule matches**의 **Automations** 행에서 **Override**를 클릭하고 **Manual**도 고르세요. 그 행은 워크스페이스를 따르지 않습니다. 채팅도 컴포저에서 자체 모드를 고를 수 있으므로 워크스페이스 모드로 두세요. 조사를 요청하고 "don't change anything"이라고 말하세요. | **Settings → Workspace → Autonomy → Rules**의 **When no Rule matches** |
| **2. 작업 승인하기** | **Manual** 유지 | 채팅이나 [Google Chat](/guide/google-chat-integration)에서 각 승인 카드에 답합니다. [Slack](/ko/guide/slack-integration)과 [Microsoft Teams](/ko/guide/teams-integration)는 답하기 위해 웹 앱으로 연결합니다. [알림](/ko/guide/notifications)에서 **Agent approvals**를 켜면 이메일이나 채팅으로 요청을 받습니다. [Approvers](/guide/approvals/approvers) 그룹으로 답할 수 있는 사람을 정하고, 가장 위험한 쓰기에는 2인 규칙을 켜세요. | **Settings → Workspace → Autonomy → Approvers** |
| **3. 일상 작업 사전 승인하기** | **Auto · Rules · Ask me**로 전환 | 2단계 기준을 통과한 하나의 연결의 하나의 작업에 대해 **Allow** [Rule](/guide/approvals/rules)을 수락합니다. 에이전트는 작업하면서 Rule을 제안합니다. **Rules** 페이지에서 **Find rules**를 클릭하면 더 받을 수 있습니다. 제안은 **Needs your review**에서 기다리며, 대기 중인 제안이 있으면 **Review**가 있는 배너가 표시됩니다. 관리자가 수락할 때까지 아무것도 바뀌지 않습니다. 그런 다음 모드를 전환하세요. Allow Rules는 **Auto**에서만 쓰기를 단독으로 실행합니다. AI 판단이 꺼져 있으면 Rule이 허용하지 않는 모든 쓰기는 여전히 사람에게 묻습니다. | **Settings → Workspace → Autonomy → Rules** |
| **4. 영역 위임하기** | Automation에 **Auto · Rules + AI · Refuse** | 영역을 [Automation](/guide/automation/automations)으로 실행합니다. 각 일상적인 쓰기에 대해 **Runs from**에서 **Automations**로 범위를 정한 **Allow** Rule을 수락합니다. Rule이 허용하지 않고 AI 판단도 통과하지 못한 쓰기는 자리에 없는 누군가를 기다리는 대신 거부됩니다. 매주 **Rules** 페이지에서 **Activity**를 클릭하고, **Refused** 수와 **No Rule matched** 행을 확인하고, 거부된 일상적인 쓰기에 대해 Rule을 추가하세요. | **Settings → Workspace → Autonomy → Rules**의 **Activity** 대화상자 |

새 워크스페이스는 **Auto · Rules + AI · Ask me**로 시작합니다. 이 모드에서는 수락된 Rules가 실행되며, AI 판단이 Rule이 다루지 않는 쓰기를 안전하고 요청 범위 안에 있다고 판단하면 스스로 실행되게 할 수도 있습니다. 그런 쓰기에 대해서는 기본값이 3단계를 넘어서므로, 1단계에서는 **Manual**로 전환하세요. 팀이 시스템에 대한 에이전트의 판단을 신뢰하게 된 후에만 **Auto · Rules + AI · Ask me**로 옮기세요.
