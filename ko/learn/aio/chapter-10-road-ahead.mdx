*대비해야 할 다섯 가지 변화, 타이밍이 중요한 이유, 그리고 2026년의 모든 구매자가 마주하는 하나의 아키텍처 선택: 클라우드마다 네이티브 에이전트를 쓸 것인가, 모든 클라우드에 걸친 하나의 플랫폼을 쓸 것인가.*

이 장에서는 대비해야 할 다섯 가지 변화, 하이퍼스케일러 네이티브 에이전트와 클라우드 전반의 하나의 플랫폼 사이에서 선택하는 방법, 그리고 먼저 해야 할 일을 다룹니다. 각 실천 방법이 CloudThinker에서 어디에 대응하는지는 [CloudThinker 소개](/ko/learn/aio/about-cloudthinker)에 있습니다.

## 10.1 가까운 미래의 다섯 가지 변화

각 행은 변화 하나와 이번 분기에 할 수 있는 일 하나를 짝지어 보여 줍니다.

| 변화 | 바뀌는 것 | 지금 할 일 |
| :---- | :---- | :---- |
| **대응에서 예방으로** | 에이전트가 과거 인시던트를 기억하게 되면, 노력은 인시던트 수정에서 인시던트 방지로 옮겨 갑니다. 배포 전 위험 점검, 급증 전 용량 조정, 전체 환경의 패턴에서 도출한 설계 조언입니다. | 메모리 레이어를 의도적으로 채우세요: 토폴로지, 규칙, 과거 인시던트([§9.3](/ko/learn/aio/chapter-9-roadmap)). |
| **에이전트 간 운영** | 운영 에이전트가 클라우드 제공자의 지원 에이전트 같은 벤더 에이전트에게 작업을 넘기게 됩니다. MCP(Model Context Protocol)는 이미 에이전트를 도구에 연결합니다. 현재 Linux Foundation 산하에 있는 A2A(Agent2Agent) 프로토콜은 회사 경계를 넘는 에이전트 간 메시지를 다룹니다. AWS DevOps Agent는 이미 조사 내용을 첨부해 AWS Support로 에스컬레이션합니다. | MCP와 A2A를 지원하는 플랫폼을 선호하세요. CloudThinker에서는 [MCP 연결](/ko/guide/connections/mcp)이 나중에 추가하는 도구에 도달하고, [A2A API](/guide/api/a2a)로 ServiceNow 같은 외부 시스템이 CloudThinker 에이전트에게 질문할 수 있습니다(Scale 플랜). |
| **거버넌스가 법이 됨** | AI 거버넌스는 EU AI Act를 필두로 일부 산업에서 자발적 관행에서 법적 요건으로 옮겨 가고 있습니다. 규제 산업에서는 감사 증거를 내놓지 못하는 플랫폼은 조달을 통과하지 못합니다. | 규제 기관이 요구하기 전에 [챕터 6](/ko/learn/aio/chapter-6-trust-governance)의 통제를 구축하세요. |
| **자율성이 단계적으로 높아짐** | 증거가 쌓이면서 더 많은 작업 유형이 승인에서 사전 승인으로 옮겨 가고, 에이전트는 범위가 제한된 영역에서 전체 워크플로를 맡게 됩니다. | 측정된 결과를 바탕으로 작업 유형 하나씩 자율성을 높이세요([§7.3](/ko/learn/aio/chapter-7-humans-on-the-loop)). |
| **운영 모델이 곧 제품이 됨** | 모델이 서로 대체 가능해지면서, 벤더 간 차이는 오케스트레이션, 도메인 깊이, 축적된 컨텍스트, 신뢰 통제로 옮겨 갑니다. | 어떤 모델을 쓰는지가 아니라 이 네 가지로 벤더를 판단하세요. |

## 10.2 전략적 기회의 창

Gartner의 두 전망은 서로 모순되는 것처럼 보입니다.

- 2026년 말까지 [엔터프라이즈 애플리케이션의 40%에 작업 특화 에이전트](https://www.gartner.com/en/newsroom/press-releases/2025-08-26-gartner-predicts-40-percent-of-enterprise-apps-will-feature-task-specific-ai-agents-by-2026-up-from-less-than-5-percent-in-2025) 탑재. 2025년의 5% 미만에서 증가.
- 2027년 말까지 [에이전틱 AI 프로젝트의 40% 이상이 취소](https://www.gartner.com/en/newsroom/press-releases/2025-06-25-gartner-predicts-over-40-percent-of-agentic-ai-projects-will-be-canceled-by-end-of-2027)([§9.4](/ko/learn/aio/chapter-9-roadmap)).

두 전망은 충돌하지 않습니다. 함께 보면 조직을 두 그룹으로 나눕니다. 단계적 자율성, 실질적인 거버넌스, 정직한 측정으로 실험에서 프로덕션으로 나아가는 조직과, 정체되는 조직입니다.

일찍 프로덕션에 도달하면 효과가 누적됩니다.

- 해결된 인시던트 하나하나가 에이전트가 시스템에 대해 아는 것을 늘립니다.
- 줄어든 반복 작업 한 시간 한 시간이 엔지니어링 작업으로 돌아갑니다.
- 운영 비용이 환경 규모에 비례해 늘어나지 않게 됩니다.

## 10.3 하이퍼스케일러 에이전트인가, 클라우드 전반의 하나의 플랫폼인가?

이 책에서 다룬 하이퍼스케일러 에이전트(AWS DevOps Agent, Azure SRE Agent, Gemini Cloud Assist)는 만들어진 목적에 능숙합니다. 각각 자신의 홈 클라우드에서 가장 깊이 동작하고, 벤더의 가격 모델을 따르며, 조사에 집중하고, 자동 수정은 더 천천히 도입되고 있습니다.

단일 클라우드를 운영한다면 네이티브 에이전트가 강력한 기본 선택입니다. 하지만 대부분의 기업은 그렇지 않습니다. 동남아시아 금융 부문의 상당 부분을 포함해 많은 규제 대상 환경은 하이퍼스케일러를 로컬 또는 소버린 클라우드, 온프레미스 시스템과 섞어 사용합니다. 단일 클라우드 에이전트 세 개는 콘솔 세 개, 거버넌스 모델 세 개, 감사 추적 세 개를 뜻합니다. 이 책이 반대하는 바로 그 회전의자(swivel-chair) 문제가 한 층 위에서 반복되는 것입니다.

| 차원 | 하이퍼스케일러 네이티브 에이전트 | 클라우드 전반의 하나의 플랫폼 |
| :---- | :---- | :---- |
| 커버리지 | 홈 클라우드에서 가장 깊고, 다른 곳에서는 부분적 | 로컬 클라우드와 온프레미스 시스템을 포함해 운영하는 모든 클라우드 |
| 범위 | 조사 우선, 수정은 점진적으로 도입 | 하나의 정책 아래 감지, 분석, 해결, 검증의 전체 루프 |
| 거버넌스 | 벤더별로 별도의 통제와 감사 추적 | 하나의 승인 정책, 하나의 감사 추적, 하나의 승인 창구 |
| 데이터 통제 | 벤더의 클라우드에서 처리, 통제는 다양 | 식별자 마스킹, 자체 모델 계정, 프라이빗 배포 옵션 |
| 인센티브 | 벤더의 생태계 안에서 최적화 | 벤더의 청구액을 줄이는 결정을 포함해 클라우드 중립 |
| 단일 클라우드에서의 깊이 | 가장 깊음: 그 클라우드의 자체 팀이 만듦 | 어느 한 클라우드에서는 보통 그 클라우드 자체 에이전트보다 얕음 |
| 설정 노력 | 이미 가진 계정과 벤더 안의 홈 클라우드에서는 낮음 | 클라우드마다 연결과 자격 증명, 그리고 검토할 새 벤더 |

### 열 선택하기

네 가지 질문에 답하세요.

1. 현재 클라우드, 로컬 클라우드, 온프레미스 환경을 몇 개 운영하고 있으며, 2년 후에는 몇 개를 운영할 것인가?
2. 규제 기관이나 보안 팀이 그 모든 것에 걸친 하나의 감사 추적을 요구하는가?
3. 데이터가 특정 국가 안이나 자체 경계 안에 머물러야 하는가?
4. 승인 하에 수행되는 수정이 필요한가, 아니면 지금은 조사로 충분한가?

하나의 클라우드를 넘어서거나 조사를 넘어서는 답의 수를 세세요.

- **없음:** 네이티브 에이전트로 시작하세요.
- **하나:** 그 답이 데이터가 한 국가에 머물러야 하는 것 같은 엄격한 요건이 아니라면 네이티브 에이전트로 시작하세요. 엄격한 요건이라면 두 개로 취급하세요.
- **둘 이상:** 클라우드 전반에서 동작하는 플랫폼을 후보로 추리고, 각각 [§6.3](/ko/learn/aio/chapter-6-trust-governance)의 여덟 가지 데이터 통제 질문과 [§3.3](/ko/learn/aio/chapter-3-what-is-aio)의 다섯 가지 벤더 테스트 질문으로 검증하세요.

### 이해관계 공개

이 필드 가이드는 두 번째 열에 해당하는 제품을 만드는 CloudThinker가 발행합니다. 우리는 그 이해관계를 증거와 분리했습니다. 벤치마크는 출처를 밝혔고, 하이퍼스케일러 에이전트는 가장 강한 모습으로 소개했으며, 프레임워크 장들은 어떤 플랫폼을 선택하든 적용됩니다.

위 목록의 두 테스트를 우리에게도 똑같이 적용하세요. [CloudThinker 소개](/ko/learn/aio/about-cloudthinker)는 이 가이드의 각 실천 방법을 확인할 수 있는 제품 페이지에 대응시킵니다.

## 10.4 월요일에 할 일

1. **기준선을 확보하세요.** 페이징 및 티켓 도구에서 90일간의 MTTR, 알림 볼륨, 호출 수를 내보내세요([§8.2](/ko/learn/aio/chapter-8-measuring)).
2. 잦고, 반복적이고, 되돌릴 수 있는 인시던트가 있는 **범위가 제한된 영역 하나를 고르세요**([§9.2](/ko/learn/aio/chapter-9-roadmap)).
3. **모든 쓰기 작업을 승인으로 시작하세요.** CloudThinker에서는 무엇이든 연결하기 전에 Approval mode를 **Manual**로 설정하고, [실행 유형 행](/guide/approvals/approval-mode#set-a-mode-for-a-run-type)에서 **Automations**도 **Manual**로 재정의하세요. 채팅은 자체 모드를 고를 수 있으므로 채팅에서도 확인하세요.
4. 파일럿이 시작되기 전에 **자율성 정책 책임자를 지정하세요**([§7.2](/ko/learn/aio/chapter-7-humans-on-the-loop)).
