이 문서는 AgenticOps에 관한 CloudThinker 현장 가이드, *Agentic Infrastructure Operations, Leadership Edition*(2026년 6월, 최종 검토 2026년 10월)입니다. 사용자 환경에서 AI 에이전트가 운영 작업을 할지, 어디에서, 얼마나 빨리 하게 할지 결정하는 데 활용하세요.

## 이 가이드의 대상

호출기를 지니는 사람과 예산을 정하는 사람을 위해 썼습니다. SRE, DevOps 및 플랫폼 엔지니어, 인프라 리더, CTO, CIO입니다. 자율성을 얻고, 증명하고, 감사받아야 하는 규제 산업에는 특별히 주의를 기울였습니다. 모델 전 데이터 마스킹은 [4.4](/ko/learn/aio/chapter-4-architecture#44-파이프라인-내부의-데이터-보호)를, 데이터 레지던시와 감사 기록은 [챕터 6](/ko/learn/aio/chapter-6-trust-governance)을 참조하세요.

각 챕터는 활용할 무언가를 제공합니다. 벤더를 평가할 정의, 아키텍처 체크리스트, 거버넌스 모델, KPI 세트, 또는 90일 계획입니다.

| 당신이… | 시작할 곳 | 얻게 될 것 |
|---|---|---|
| 비즈니스 케이스를 만드는 CTO 또는 CIO | [챕터 1](/ko/learn/aio/chapter-1-complexity-crisis), [챕터 8](/ko/learn/aio/chapter-8-measuring) | 현상 유지의 비용과, 가치를 입증하거나 반증하는 KPI |
| 벤더를 평가하는 인프라 리더 | [챕터 3](/ko/learn/aio/chapter-3-what-is-aio) | 실무 정의와 "에이전트 워싱"을 가려내는 다섯 가지 질문 |
| 시스템을 설계하는 플랫폼 엔지니어 또는 SRE | [챕터 4](/ko/learn/aio/chapter-4-architecture), [챕터 6](/ko/learn/aio/chapter-6-trust-governance) | 레퍼런스 아키텍처와 가드레일 스택 |
| 도입을 계획하는 팀 리더 | [챕터 7](/ko/learn/aio/chapter-7-humans-on-the-loop), [챕터 9](/ko/learn/aio/chapter-9-roadmap) | 팀을 위한 새로운 운영 모델과 파일럿에서 확장까지의 로드맵 |
| 에이전트를 스택에 대응시키는 아키텍트 | [챕터 2](/ko/learn/aio/chapter-2-automation-to-autonomy), [챕터 5](/ko/learn/aio/chapter-5-agent-team) | 에이전트 플랫폼이 재사용하는 계층과, 인시던트 하나가 에이전트 팀을 거쳐 흐르는 방식 |
| 네이티브 클라우드 에이전트와 단일 플랫폼을 비교하는 구매자 | [챕터 10](/ko/learn/aio/chapter-10-road-ahead) | 클라우드별 네이티브 에이전트와 클라우드 전반의 단일 플랫폼 간 트레이드오프 |
| 지금 CloudThinker를 설정하는 플랫폼 엔지니어 | 제품 [빠른 시작](/ko/quickstart), 그다음 [2.5](/ko/learn/aio/chapter-2-automation-to-autonomy#25-cloudthinker의-위치) | 첫 연결, Signals로 들어오는 알림, 확인된 Approvals 설정 |

에이전트를 매일 구축하거나 운영할 엔지니어라면, [Engineer Edition](/learn/aio-engineer/introduction)이 같은 내용을 구현 수준으로 다룹니다.

## 논지 요약

1. **[위기](/ko/learn/aio/chapter-1-complexity-crisis).** 인프라 복잡성은 인력보다 빠르게 늘어나며, 더 많은 사람, 스크립트, 대시보드는 모두 실행 경로에 사람을 남겨 둡니다.
2. **[자동화에서 자율성으로](/ko/learn/aio/chapter-2-automation-to-autonomy).** 에이전트는 운영 도구의 네 번째 세대입니다. IaC, 알림, 스크립트를 재사용하며, 그 도구들이 열어 둔 루프를 닫습니다.
3. **[정의](/ko/learn/aio/chapter-3-what-is-aio).** 진짜 에이전트는 목표 지향적이고, 인식하고, 추론하고, 도구를 사용하고, 자체 검증합니다. 자율성은 작업 유형과 환경별로 설정하는 다이얼(L0~L4)입니다.
4. **[아키텍처](/ko/learn/aio/chapter-4-architecture).** 하나의 오케스트레이터, 범위가 정해진 소수의 전문가, 검증이 내장된 닫힌 루프, 비싼 추론 계층 앞의 저렴한 감지 계층, 그리고 모델 전에 마스킹되는 민감한 데이터.
5. **[에이전트 팀](/ko/learn/aio/chapter-5-agent-team).** 각 에이전트에 안정적인 범위와 최소 권한 액세스를 주고, 추론을 보여 주며 채팅에서 엔지니어와 만나세요.
6. **[신뢰와 거버넌스](/ko/learn/aio/chapter-6-trust-governance).** 에이전트가 프로덕션에 쓰기 전에 가드레일, 데이터 통제, 내보낼 수 있는 감사 기록을 갖추세요.
7. **[루프 위의 사람](/ko/learn/aio/chapter-7-humans-on-the-loop).** 엔지니어는 작업을 하는 사람에서 감독하는 사람으로 바뀌며, 입증된 단계마다 하나씩 자율성을 넘겨줍니다.
8. **[측정](/ko/learn/aio/chapter-8-measuring).** MTTR, 자율 해결률, 롤백률이 이끄는 여덟 가지 KPI가 프로그램이 더 많은 자율성을 얻을지 결정합니다.
9. **[로드맵](/ko/learn/aio/chapter-9-roadmap).** 다섯 가지 준비 기반을 점검하고, 종료 기준이 있는 90일 파일럿을 실행한 뒤, 12개월에 걸쳐 확장하세요.
10. **[앞으로의 길](/ko/learn/aio/chapter-10-road-ahead).** 다섯 가지 단기 변화에 대비하고, 클라우드별 네이티브 에이전트와 모든 클라우드를 아우르는 단일 플랫폼 중에서 결정하세요.

## 곳곳에서 보게 될 용어

| 용어 | 의미 |
|---|---|
| **AgenticOps**(에이전틱 인프라 운영) | 명시적인 정책 아래 전체 운영 루프를 실행하는 AI 에이전트: 문제를 감지하고, 분석하고, 해결하고, 수정을 검증합니다. 이 가이드는 이 루프를 DARV(Detect → Analyze → Resolve → Validate)라고 부릅니다. |
| **In the loop** | 사람이 모든 단계를 실행합니다. 에이전트가 있다면 제안만 합니다. |
| **On the loop** | 사람이 의도를 정하고, 중대한 작업을 승인하고, 결과를 검토합니다. 실행은 에이전트가 합니다. |
| **자율성 수준(L0~L4)** | 에이전트가 스스로 할 수 있는 범위를 관찰 전용(L0)부터 완전 위임(L4)까지 나타내는 이 가이드의 벤더 중립 척도. [챕터 3](/ko/learn/aio/chapter-3-what-is-aio)에 정의되어 있습니다. |
| **에이전트 워싱** | 챗봇, 스크립트 실행기, 알림 요약기를 자율 에이전트로 파는 것. [챕터 3](/ko/learn/aio/chapter-3-what-is-aio)이 이를 가려낼 다섯 가지 질문을 제공합니다. |
| **MCP**(Model Context Protocol) | 에이전트가 하나의 인터페이스로 다른 시스템의 도구를 호출하고 데이터를 읽을 수 있게 하는 개방형 표준. |
| **노동(Toil)** | 시스템 규모에 비례해 늘어나며 지속적인 가치를 더하지 않는 수동적이고 반복적인 운영 작업. |
| **오케스트레이터** | 작업을 나누고, 전문가에게 라우팅하고, 사람에게 에스컬레이션하는 조율 에이전트. CloudThinker에서는 임시 하위 에이전트를 생성하는 기본 제공 [CloudThinker](/ko/guide/agents/overview) 어시스턴트입니다. |
| **감지 계층** | 신호를 지켜보고 무엇이 전체 조사를 받을 가치가 있는지 결정하는 저렴하고 항상 켜진 계층. CloudThinker에서는 [Signals](/ko/guide/pulse/overview)입니다. |
| **작업 유형** | "파드 재시작"이나 "배포 롤백"처럼 에이전트가 할 수 있는 한 종류의 변경. 자율성은 작업 유형별로 설정됩니다. |
| **영향 범위** | 작업이 잘못되면 얼마나 많이 깨지는지. 영향 범위가 작은 작업이 먼저 더 많은 자율성을 얻습니다. |
| **BYOC**(bring your own cloud) | 벤더의 플랫폼을 자체 클라우드 계정 안에서 실행해 데이터가 경계 안에 머물게 하는 것. |
| **SLO**(service level objective) | "체크아웃 요청의 99.9%가 300ms 미만"처럼 서비스에 대한 목표. |
| **MTTR**(mean time to resolve) | 인시던트 시작(영향 발생)부터 해결까지의 평균 시간. Resolve Insights도 같은 방식으로 측정합니다. |

CloudThinker 자체의 제품 용어는 [용어집](/guide/glossary)을 참조하세요.
