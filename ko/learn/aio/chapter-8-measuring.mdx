*에이전틱 운영의 성패는 증거로 결정됩니다. 프로그램을 프로덕션 시스템처럼 계측하세요.*

이 챕터는 추적할 수치, 그 수치로 만들 비즈니스 케이스, 그리고 에이전트를 신뢰해도 안전한지 알려 주는 테스트 하네스를 제공합니다. 8.6절은 CloudThinker가 각 수치를 보고하는 위치를 보여 줍니다.

## 8.1 무엇이, 어떤 순서로 개선되나

개선은 예측 가능한 순서로 나타납니다. 둘째 주에 자율 수정을 기대하는 사람이 없도록 그 순서에 맞춰 보고를 계획하세요.

| 순서 | 메트릭 | 개선의 원천 |
| :---- | :---- | :---- |
| 첫째 | 알림 양 | 사람을 호출하기 전의 연관, 중복 제거, 증상 억제 |
| 둘째 | 근본 원인까지의 시간 | 에이전트가 로그, 메트릭, 변경 이력을 병렬로 수집해, 대부분 인시던트에서 가장 긴 단계인 진단을 단축 |
| 둘째 | 노동 | 분류, 증거 수집, 보고가 L1/L2 엔지니어에서 에이전트로 이동 |
| 지속 | 클라우드 비용 | 분기별 검토 대신 지속적인 적정 크기 조정과 유휴 리소스 정리 |
| 마지막 | 해결 시간(MTTR) | 이미 안전하다고 입증한 작업 유형에 대한 사전 승인된 수정 |

각 개선의 크기는 데이터 품질과 신뢰 사다리를 얼마나 올랐는지에 달려 있습니다([§7.3](/ko/learn/aio/chapter-7-humans-on-the-loop)).

공개된 가장 강력한 수치는 벤더의 수치입니다. [AWS는](https://aws.amazon.com/blogs/mt/announcing-general-availability-of-aws-devops-agent/) DevOps Agent 프리뷰 고객이 최대 75% 낮은 MTTR, 80% 빠른 조사, 94%의 근본 원인 정확도를 경험했다고 보고합니다. 같은 발표에서 Western Governors University(WGU)는 약 2시간으로 추정되던 해결 시간이 28분으로 줄었다고 설명합니다.

이를 계획의 기준이 되는 결과가 아니라, 자체 파일럿에서 검증할 주장으로 취급하세요.

## 8.2 운영 대시보드

여덟 가지 KPI로 프로그램을 운영하세요. 온콜 로테이션과 함께 매월 검토하세요.

| KPI | 알려 주는 것 | 읽는 방법 |
| :---- | :---- | :---- |
| **MTTD 및 MTTR** | 감지 시간, 그리고 평균 해결 시간(인시던트 시작부터 해결까지) | 심각도별 추세를 보세요. 에이전트가 처리한 인시던트와 사람이 처리한 인시던트를 분리하지 않으면 평균이 변화를 가립니다. |
| **자율 해결률** | 사람의 조치 없이 해결된 인시던트 비율 | 가장 좋은 단일 성숙도 지표입니다. 작업 유형이 졸업할수록 올라가야 합니다. |
| **권고 수락률** | 변경 없이 승인된 에이전트 제안 비율 | 세 가지 기준: 약 70% 미만이면 에이전트의 컨텍스트나 정책을 조정하세요. 전체 80%에서 파일럿의 Approve 단계를 종료할 수 있습니다([§9.2](/ko/learn/aio/chapter-9-roadmap)). 한 작업 유형에서 약 95%를 넘으면 승인 단계가 더하는 가치가 적으므로 그 유형을 졸업시키세요. |
| **롤백 및 개입률** | 되돌리거나 재정의해야 했던 에이전트 작업 | 안전 측면의 균형추입니다. 올라가면 자율성 확대를 늦추세요. |
| **반복 인시던트율** | 같은 문제가 계속 돌아오는지 여부 | 반복이 줄면 메모리와 문제 관리가 작동하고 있다는 뜻입니다. |
| **커버리지 비율** | 에이전트가 L2 이상에서 처리할 수 있는 인시던트 유형 비율 | 다음 런북을 작성하거나 다음 연결을 추가할 곳을 보여 줍니다. |
| **온콜 부담** | 엔지니어당 주간 호출 수, 업무 외 호출은 별도 | 엔지니어와 관리자가 가장 크게 체감하는 메트릭입니다. |
| **에이전트 단위 비용** | 해결된 인시던트당, 커버된 서비스당 모델 및 플랫폼 지출 | 첫날부터 추적하세요. §8.4를 참조하세요. |

자율성 수준(L0~L4)은 [§3.2](/ko/learn/aio/chapter-3-what-is-aio)에 정의되어 있습니다.

## 8.3 비즈니스 케이스 만들기

수익 쪽에는 세 줄이 있습니다. 각각 자체 입력값을 사용하세요.

| 항목 | 계산 방법 | 확보할 입력값 |
| :---- | :---- | :---- |
| **방지한 다운타임** | 연간 인시던트 수 × 다운타임 분당 비용 × 파일럿에서 측정한 MTTR 단축 분 | 재무팀의 분당 비용. 없다면 Global 2000 기업 기준 분당 약 $15,000인 [Splunk 및 Oxford Economics 2026 벤치마크](https://newsroom.cisco.com/c/r/newsroom/en/us/a/y2026/m05/the-600-billion-wake-up-call-new-splunk-research-reveals-downtime-is-a-systemic-business-crisis.html)를 사용하세요. 결제 및 거래 시스템은 더 높습니다. |
| **전환된 노동** | 에이전트가 흡수하는 L1/L2 작업 시간 × 시간당 엔지니어링 총비용 | 티켓 시스템이나 2주간의 시간 조사에서 얻은 시간. 엔지니어를 채용하기 어려운 곳에서는 대개 가장 큰 항목입니다. |
| **회수한 클라우드 낭비** | 구현된 비용 권고의 검증된 월 절감액 × 12 | 권고 시점에 표시된 추정치가 아니라, 각 변경 전후의 클라우드 청구서 |

비용 쪽에는 플랫폼 구독, 모델 사용량, 시스템을 통합하고 거버넌스하는 엔지니어링 시간이 포함됩니다. 자율성 정책 담당자의 시간도 포함하세요.

한 가지 규칙으로 케이스를 검증하세요. 다운타임 항목이 있어야만 성립한다면 파일럿 영역을 잘못 고른 것입니다. 노동 절감만으로 케이스가 성립하는 영역을 고르고, 방지한 다운타임은 추가 이익으로 취급하세요.

## 8.4 에이전트의 단위 경제학

에이전틱 프로그램 운영 비용의 대부분은 모델 추론입니다. 추론 비용의 대부분은 비싼 추론이 어디에서 실행되는지에 달려 있습니다. 따라서 저렴한 인식은 항상 켜 두고, 프론티어 추론은 그것이 필요한 소수의 신호에만 쓰세요.

[§4.3](/ko/learn/aio/chapter-4-architecture)은 이를 2계층 감지라고 부릅니다. 인시던트 하나를 비용 대상으로 읽어 보세요.

| 계층 | 실행되는 것 | 빈도 | 실행당 비용 |
| :---- | :---- | :---- | :---- |
| 감지 | 모든 신호에 대한 경량 인식 | 항상 | 가장 낮음 |
| 분류 | 살펴볼 가치가 있는 신호의 그룹화와 필터링 | 단순 노이즈가 아닌 모든 신호마다 | 더 높음 |
| 심층 해결 | 다단계 추론: 근본 원인, 수정, 검증 | 분류를 통과한 신호에만 | 압도적으로 가장 높음 |

심층 해결은 실행당 비용이 가장 높지만 드물게 실행되므로, 모든 신호가 커버되는 동안에도 비싼 계층은 대부분 유휴 상태입니다. 환경마다 차이가 너무 커서 일반적인 비율은 공개하지 않습니다. 자체 환경에서 세 가지 수치를 측정하세요. 일일 신호 수, 심층 해결로 에스컬레이션되는 비율, 심층 실행 한 번의 비용입니다. 이를 곱하면 일일 심층 해결 지출이 나옵니다.

그래서 해결된 인시던트당 비용과 커버된 서비스당 비용이 대시보드에 있습니다. 노이즈가 많은 모든 신호에 프론티어 추론을 실행하는 아키텍처는 첫 갱신 전에 자체 수익을 지워 버립니다. 처음부터 인시던트별 수치를 추적하지 않으면 그 일이 일어나는 것을 보지 못합니다.

벤더를 비교할 때는 가격이 가치를 어떻게 따라가는지 물어보세요. 검증된 절감액에 연동된 수수료 같은 성과 기반 옵션은 벤더가 추론을 위한 추론을 늘릴 유인을 없앱니다. 구조가 무엇이든, 비즈니스 케이스의 수치는 자체 90일 기준선([§9.2](/ko/learn/aio/chapter-9-roadmap))에 대해 측정한 것이어야 합니다.

## 8.5 신뢰하기 전에 에이전트 테스트하기

앞 챕터들은 에이전틱 운영을 자체 검증하는 것으로 설명합니다. 이 절은 그 검사가 어떻게 생겼는지, 그리고 확신에 찬 잘못된 수정이 프로덕션에 도달하기 전에 잡는 방법을 보여 줍니다.

평가 하네스에는 네 부분이 있습니다.

| 부분 | 하는 일 |
| :---- | :---- |
| **시나리오 라이브러리** | 기록된 실제 인시던트와 의도적으로 주입한 장애. 각각 알려진 정답(올바른 근본 원인, 안전한 작업, 깔끔한 롤백)이 있습니다 |
| **섀도 실행** | 에이전트가 프로덕션 자체가 아니라 프로덕션의 샌드박스 복사본에 대해 행동하므로, 결과 없이 제안된 작업을 지켜볼 수 있습니다 |
| **정답 대비 채점** | 올바른 근본 원인을 찾았나? 안전한 작업을 골랐나? 롤백이 작동했을까? |
| **회귀 게이트** | 새 에이전트 버전, 프롬프트, 스킬은 다른 프로덕션 코드처럼 출시 전에 라이브러리를 통과해야 합니다 |

에이전트는 결정론적이지 않습니다. 같은 시나리오도 실행마다 다른 동작을 낼 수 있습니다. 그러므로 각 시나리오를 여러 번 실행하고 결과의 분포를 채점하세요. 70% 확률로 맞는 수정과 99% 확률로 맞는 수정은 다른 위험이며, 어느 쪽인지는 반복 실행으로만 알 수 있습니다.

데이터베이스 연결 고갈 시나리오에 대한 구체적인 검사입니다. 하네스는 에이전트가 다음을 하는지 확인합니다.

1. 근본 원인으로 연결 풀 고갈을 지목합니다.
2. 서비스 재시작에 그치지 않고 올바른 연결 한도를 복원합니다.
3. 연결 수가 기준선으로 돌아와 유지되는지 확인합니다.

3단계는 에이전트가 프로덕션에서 실행하는 것과 같은 Validate 단계를, 여기서는 알려진 답에 대해 테스트한 것입니다. 에이전트가 하네스에서 자체 검증을 통과하지 못하면, 프로덕션에서 무인으로 실행되게 하지 마세요.

**CloudThinker에서:** [§7.3](/ko/learn/aio/chapter-7-humans-on-the-loop)처럼 워크스페이스를 **Manual**로 둔 채 해당 시간 범위의 조사를 요청해 종료된 인시던트를 재현하고, 답을 포스트모템과 비교할 수 있습니다. 이 문서는 기본 제공 시나리오 라이브러리, 샌드박스 섀도 실행, 회귀 게이트를 설명하지 않으므로, 이는 직접 구축할 계획을 세우세요.

## 8.6 CloudThinker에서 이 수치를 읽는 곳

CloudThinker로 파일럿을 운영한다면, 다음 페이지가 대시보드의 대부분을 보고합니다. 온콜 부담과 롤백률은 호출 및 변경 도구에서 추적하세요.

| KPI | 위치 |
| :---- | :---- |
| MTTD | 별도 수치로 보고되지 않습니다. **Where the time goes**는 첫 신호부터 시작하므로, 감지 시간은 모니터링 도구에서 가져오세요. |
| MTTR 및 추세 | **Resolve → Insights → Reliability**: **MTTR** 및 **MTTR over time**([Insights](/guide/incident/insights)) |
| 근본 원인까지의 시간 | **Resolve → Insights → Reliability**: **Alert → root cause**, 그리고 단계별 **Where the time goes** |
| 자율 해결률 | **Resolve → Insights → Reliability**: **Auto-resolved** |
| 권고 수락 | **Resolve → Insights → Accuracy and trust**: **Fix acceptance** 및 **Root-cause accuracy**, 둘 다 팀의 리뷰 기반 |
| 반복 인시던트 | **Resolve → Insights → Reliability**: **Recurrence trend** |
| 알림 노이즈(MTTD와 온콜 부담의 보조 메트릭) | **Resolve → Insights → Signal quality**: **Noise suppressed** 및 **Signals ingested**([Signal quality 메트릭](/ko/guide/pulse/analytics)) |
| 커버리지 비율 | Insights에 보고되지 않습니다. [런북](/ko/guide/incident/runbooks)이 다루는 인시던트 유형 수를 실제로 보는 유형과 비교해 세세요. |
| 클라우드 낭비 | **Optimize → Issues**는 실현된 절감액이 아니라 열린 발견 사항의 추정치를 보여 줍니다([절감액 계산 방식](/ko/guide/cost-optimization/savings)). 변경이 배포되면 발견 사항을 **Implemented**로 표시한 뒤, 클라우드 청구서로 절감액을 검증하세요. |
| 에이전트 단위 비용 | **Settings → Organization → Usage**는 인시던트별이 아니라 **By Feature**, **By User**, **By Workspace**로 크레딧을 보여 줍니다([사용량](/ko/guide/billing/usage)). 해결된 인시던트당 비용은 해당 월 Resolve 크레딧을 같은 달 Insights의 해결된 인시던트 수로 나누세요. 크레딧은 플랜의 [요금](/ko/guide/billing/pricing)으로 금액으로 환산하세요. |

**Root-cause accuracy**는 팀이 충분한 인시던트를 리뷰해야 의미가 있습니다. 보고하기 전에 같은 탭의 **Your review coverage**를 확인하세요.

<Tip>
**배포 전에 기준선을 잡으세요.** 비즈니스 케이스가 가장 흔히 실패하는 이유는 믿을 만한 "이전"이 없기 때문입니다. Insights는 CloudThinker가 처리한 인시던트만 다루므로, 첫 에이전트가 프로덕션에 닿기 전에 호출 및 티켓 도구에서 최근 90일의 MTTR, 알림 양, 호출 수를, 시간 조사에서 노동 시간을 가져오세요.
</Tip>
