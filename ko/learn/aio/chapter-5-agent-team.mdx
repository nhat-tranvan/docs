*에이전트 조직을 설계하는 것은 곧 조직 설계입니다. 같은 질문이 적용됩니다. 누가 무엇을 맡는가, 누가 누구에게 보고하는가, 작업을 어떻게 넘기는가.*

## 5.1 핵심 구성

대부분의 프로덕션 배포는 각각 명확한 범위를 가진 소수의 에이전트 팀으로 정착합니다. 안정적인 역할은 생각보다 중요합니다. 같은 범위와 메모리를 오래 유지하는 에이전트는 사람 팀원처럼 컨텍스트, 신뢰, 책임을 쌓아 갑니다. 다음은 대표적인 구성과 각 역할이 CloudThinker에서 어디에 해당하는지 보여 줍니다. CloudThinker에서는 기본 제공 [CloudThinker](/ko/guide/agents/overview) 어시스턴트가 오케스트레이터(SuperAgent 역할: 작업을 나누고, 라우팅하고, 사람에게 에스컬레이션하는 하나의 에이전트)를 맡습니다. 어시스턴트는 각 영역에 대해 임시 서브에이전트를 생성하며, 계속 유지하고 싶은 전문가는 [커스텀 에이전트](/guide/agents/quickstart)로 추가합니다.

| 역할 | 범위 | 책임 예시 | CloudThinker에서 |
| :---- | :---- | :---- | :---- |
| 오케스트레이터 / SuperAgent | 전 영역 | 목표 분해, 작업 라우팅, 다중 영역 인시던트, 사람에게 에스컬레이션, 보고 | 기본 제공 CloudThinker 어시스턴트(`@CloudThinker` 또는 멘션 없음) |
| 클라우드 엔지니어링 에이전트 | AWS / Azure / GCP / 로컬 클라우드 | 프로비저닝 문제, 네트워킹, 확장, 서비스 할당량, 비용 이상, IaC 드리프트 | 서브에이전트, 또는 클라우드 연결을 가진 커스텀 에이전트 |
| 보안 에이전트 | Cyber + CloudSec | 잘못된 구성, OWASP 유형의 애플리케이션 위험, CVE 트리아지, IAM 위생, 컴플라이언스 증거 | 서브에이전트, 또는 보안 연결을 가진 커스텀 에이전트 |
| 데이터베이스 에이전트 | 데이터 계층 | 느린 쿼리, 락, 복제 지연, 인덱스 전략, 스토리지 예측, 백업 검증 | 서브에이전트, 또는 데이터베이스 연결을 가진 커스텀 에이전트 |
| Kubernetes 에이전트 | 컨테이너 플랫폼 | Pod 크래시 루프, OOM kill, 노드 압박, HPA 튜닝, 업그레이드 준비 | 서브에이전트, 또는 Kubernetes 연결을 가진 커스텀 에이전트 |

핵심 구성 외에도 조직은 커스텀 에이전트를 추가합니다. 특정 사업부의 비용 최적화, 주력 애플리케이션의 성능, 플랫폼 팀의 생산성 워크플로처럼 자신의 영역과 목표에 맞게 구성한 전문가입니다. 커스텀 에이전트는 오케스트레이터가 이끄는 팀을 확장합니다. 모델에 더해질 뿐 결코 모델을 대체하지 않습니다.

<Tip>
기본 제공 어시스턴트로 시작하고, 반복되는 작업에 담당자, 명확한 범위, 성공 기준이 있을 때만 커스텀 에이전트를 추가하세요. 범위가 모호한 커스텀 에이전트는 모호한 발견 항목을 내놓습니다. **Settings → Workspace → Agents**에서 만들고, **Instructions**에 범위를 작성하고, **Connect** 단계에서 필요한 연결만 고르세요. 시크릿은 채팅이 아니라 [Credentials](/guide/credentials)에 넣으세요. [커스텀 에이전트 빠른 시작](/guide/agents/quickstart)을 참조하세요.
</Tip>

## 5.2 작업이 팀을 거쳐 가는 흐름

02:40에 발생한 대표적인 프로덕션 인시던트를 생각해 봅시다. 체크아웃 지연이 SLO를 위반합니다.

1. **감지.** 감지 레이어가 지연 알림, 데이터베이스 연결 오류 급증, 22분 전에 반영된 배포를 하나의 인시던트로 상관 분석하고, 하위 알림 41개를 억제합니다.

2. **분석.** 오케스트레이터가 데이터베이스 전문가와 Kubernetes 전문가를 병렬로 투입합니다. 데이터베이스 에이전트는 새로운 N+1 쿼리 패턴으로 인한 연결 풀 고갈을 찾고, Kubernetes 에이전트는 pod가 정상임을 확인하여 인프라를 원인에서 배제합니다. 오케스트레이터는 두 발견을 증거가 첨부된 근본 원인 가설로 통합합니다. 새 배포가 그 쿼리 패턴을 도입했다는 것입니다.

3. **해결.** 정책은 SLO 위반 중 60분 미만의 배포에 대한 자동 롤백을 허용합니다. 오케스트레이터는 롤백(L3 사전 승인 작업)을 실행하고, 전체 추론 과정을 팀의 인시던트 채널에 게시하여 온콜 엔지니어가 아침에 읽게 하며, 아무도 호출하지 않습니다.

4. **검증.** 지연이 4분 안에 기준선으로 돌아오고 오류율이 해소됩니다. 시스템은 SLO 복구를 확인하고, 문제가 된 쿼리를 명시한 문제 티켓을 엔지니어링 팀에 열고, 사후 보고서 초안을 작성하고, 패턴을 메모리에 저장합니다.

경과 시간: 10분 미만, 깨어난 사람 0명. 다음 날 아침 엔지니어가 보고서를 검토하고, 쿼리를 고치고, 재배포를 승인합니다. 이런 분담(기계는 02:40의 기계적인 작업을, 사람은 09:00의 엔지니어링 판단을 맡음)이 바로 의도대로 동작하는 모델입니다.

CloudThinker에서는 롤백 정책을 두 부분으로 표현합니다. **Allow** [Rule](/guide/approvals/rules)이 프로덕션 연결의 롤백 작업을 다루며, **Runs from**을 **Resolve**로 설정하면 **Auto** 모드에서 사람 없이 쓰기가 실행될 수 있습니다. [런북](/ko/guide/incident/runbooks)은 언제 사용할지 명시합니다. 60분 미만의 배포, SLO 위반입니다. **Manual**에서는 여전히 사람이 롤백을 승인하므로, 무인으로 실행하려면 **Auto** [Approval mode](/guide/approvals/approval-mode)를 고르세요.

## 5.3 에이전트와 사람의 인터페이스

에이전트는 엔지니어가 있는 곳에 있습니다. 지배적인 인터페이스 패턴은 대화와 증거의 결합입니다. 에이전트는 발견 항목, 계획, 승인 요청을 전체 추론 과정, 증거 링크, 원클릭 승인/거부 작업과 함께 Slack이나 Teams에 게시합니다. 대시보드는 추세와 감사를 위해 남고, 운영 대화는 채팅에서 일어납니다. 두 가지 인터페이스 규칙이 특히 중요합니다.

1. **작업 과정을 보여 주세요.** 모든 결론에는 검토한 데이터, 고려한 가설, 대안을 기각한 이유가 함께 제공됩니다. 투명한 추론은 엔지니어 신뢰의 가장 큰 동인이며, AIOps를 실패하게 만든 블랙박스 문제의 해결책입니다.

2. **승인은 쉽게, 거부는 유익하게 만드세요.** 승인은 전체 컨텍스트와 함께 원클릭이어야 하고, 거부는 이유를 기록해야 합니다. 모든 거부는 정책 조정을 위한 학습 신호이기 때문입니다.

## 5.4 증명: 네 가지 배포

익명화된 네 가지 배포와 각각의 시작 자율성, 범위, 측정한 것입니다. 세 가지는 결과가 있습니다. 네 번째는 진행 중입니다.

| 사례 | 산업 및 규모 | 범위 | 시작 | 종료 | 기간 | 결과 |
| :---- | :---- | :---- | :---- | :---- | :---- | :---- |
| 1 | 소비자 금융 대출 기관, 베트남, 800개 이상 지점 | 멀티 계정 AWS: 비용, 위생, 인시던트 | L1 | L2(핵심 대출 경로는 L1 유지) | 4주 기준선, 3개월 이내 결과 | 수동 운영 작업 감소, 몇 시간이 아닌 몇 분 만의 근본 원인 파악, 최적화 가능한 AWS 지출 회수 |
| 2 | 디지털 결제 플랫폼, 베트남, 시리즈 A | 프로덕션 Kubernetes 클러스터 3개, RDS 복제본 | L2 | 되돌릴 수 있는 작업에서 L3 | 3개월 이내 | 고객에게 보이는 다운타임 없는 업그레이드, 복제본 비용 절감, 월간 운영 비용 감소 |
| 3 | AI / SaaS 플랫폼, 미국, EU, APAC | 3개 리전 배포, 컴플라이언스 가드레일, 운영 | L2 | L2에서 L3 | 배포에 4주 | SOC 2, HIPAA, GDPR 준비, 운영 작업 부담 경감, 가용성 목표 유지 |
| 4 | 통신사 클라우드 제공자, 베트남, 수천 개 클러스터 | OpenStack 및 VMware의 구성 및 감사 자동화 | L1 | L3 계획 | 진행 중 | 아직 게시되지 않음 |

### 1. 소비자 금융 대출 기관

- **문제.** 여러 계정에 걸친 AWS 환경. 비용과 인시던트 작업이 수동이었고, 장애가 난 대출 앱의 원인을 찾는 데 계정 간 검색으로 몇 시간이 걸렸습니다.
- **부여한 자율성.** 4주 기준선 동안 모든 계정에 걸친 L1 조사를 운영자 자신의 근본 원인 분석과 대조했습니다. 그다음 비용 및 위생 작업에 L2를 적용하여, 원클릭 승인을 위한 수정을 준비했습니다.
- **사람의 관문으로 남은 것.** 핵심 대출 경로는 내내 권고 전용으로 유지했습니다.
- **결과.** 3개월 이내: 위 표의 결과에 더해, 중요한 앱에 대한 24시간 감시.

### 2. 디지털 결제 플랫폼

- **문제.** 프로덕션 Kubernetes 클러스터 3개를 다운타임 창 없이 버전 업그레이드해야 했고, RDS 복제본 지출이 늘고 있었습니다.
- **부여한 자율성.** Kubernetes 라이프사이클, 적정 크기 조정, 자가 복구, 복제본 확장에 사전 승인된 작업 유형으로 L2에서 L3.
- **사람의 관문으로 남은 것.** 업그레이드의 되돌릴 수 없는 단계.
- **결과.** 업그레이드가 세 클러스터 모두에서 고객에게 보이는 다운타임 없이 실행되었습니다. 복제본 및 운영 비용 절감은 3개월 안에 실현되었습니다.

### 3. AI / SaaS 플랫폼

- **문제.** 투자자들은 엄격한 가용성 목표 아래, GDPR이 적용되는 3개 리전에서 SOC 2와 HIPAA 준비를 원했습니다.
- **부여한 자율성.** 컴플라이언스 가드레일에 L2, 운영 해결 조치에 L2에서 L3를 적용했으며, 컴플라이언스 관련 모든 단계는 일어나는 즉시 기록되었습니다.
- **결과.** 4주 만의 3개 리전 배포. 여기서 준비란 완료된 감사가 아니라, 통제가 자동화되고 작업이 진행되는 대로 증거가 수집되는 것을 뜻합니다.

### 4. 통신사 클라우드 제공자(진행 중)

- **문제.** 수백 명의 운영자가 상태 점검, 드리프트 수정, 감사 증거 수집을 수동으로 하고 있었습니다. 도구와 인원이 늘어도 MTTR은 그대로였습니다.
- **계획한 자율성.** 전체 플릿에 걸친 L1 조사, 그다음 일상적인 클러스터 상태와 드리프트에 L2, 그다음 가장 안전한 반복 작업(클러스터 재시작, 용량 변경, 인증서 교체)에 L3.
- **사람의 관문으로 남는 것.** 모든 작업에 변경 불가능한 기록이 남는 규제 대상 통제 경로.
- **결과.** 측정이 진행 중입니다. 측정 기간이 끝나면 수치가 게시됩니다.

이 중 코어 뱅킹 배포는 없습니다. 규제 대상 은행 레퍼런스는 [문의](https://cloudthinker.io/contact)하세요.

<Info>
**하이퍼스케일러가 에이전트를 팀원으로 제공하는 방식**

- [AWS DevOps Agent](https://docs.aws.amazon.com/devopsagent/latest/userguide/about-aws-devops-agent.html)는 알림에서 조사를 시작하고 발견 항목과 완화 단계를 Slack과 ServiceNow로 라우팅합니다.
- [Azure SRE Agent](https://learn.microsoft.com/en-us/azure/sre-agent/overview)는 팀이 자체 서브에이전트를 추가하게 하고, MCP 서버를 통해 다른 도구에 연결합니다.

교훈: 엔지니어가 이미 사용하는 도구에서 만나고, 모든 발견 항목과 함께 추론을 보여 주세요. CloudThinker에서는 채팅용 [Slack](/ko/guide/slack-integration), [Microsoft Teams](/ko/guide/teams-integration), [Google Chat](/guide/google-chat-integration), ITSM용 [ServiceNow](/ko/guide/connections/servicenow), 그리고 [Signals 웹훅](/ko/guide/pulse/setup)을 통한 알림 소스로서의 PagerDuty를 뜻합니다.
</Info>
