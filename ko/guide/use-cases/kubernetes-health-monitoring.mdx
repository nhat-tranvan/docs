CloudThinker는 읽기 전용 서비스 계정으로 Kubernetes 클러스터를 읽고 채팅으로 답합니다. 이벤트, 재시작, 사용량을 맞춰 보려고 수십 개의 파드에 `kubectl get`, `describe`, `logs`를 실행할 필요가 없어집니다. 이 안내는 빈 워크스페이스에서 시작해 클러스터 상태 점검과 실패하는 파드 조사까지 약 15분이 걸립니다.

## 필요한 것

| 요구 사항 | 이유 |
|-------------|-----|
| CloudThinker가 인터넷으로 API 서버에 접근할 수 있는 클러스터 | 명령은 CloudThinker 클라우드에서 실행되므로, 비공개 전용 엔드포인트는 연결 테스트에 실패합니다. API 액세스를 제한한다면(EKS public access CIDRs, GKE authorized networks, AKS authorized IP ranges) `0.0.0.0/0`으로 여는 대신 CloudThinker의 송신 IP를 허용 목록에 추가하세요. 현재 목록은 CloudThinker 담당자에게 문의하세요. [비공개 서비스에 접근하기](/ko/guide/connections/overview#비공개-서비스-접근)를 참조하세요. |
| 네임스페이스, ClusterRole, ClusterRoleBinding을 만들 수 있는 `kubectl` 액세스 | CloudThinker가 로그인할 읽기 전용 계정을 만듭니다 |
| 선택: [Metrics Server](https://github.com/kubernetes-sigs/metrics-server) | 없어도 파드 상태, 이벤트, 노드 상태는 볼 수 있지만, 실시간 CPU와 메모리 수치는 볼 수 없습니다 |

<Info>
워크스페이스에는 Kubernetes 연결이 **하나**만 있으며, CloudThinker는 kubeconfig의 **current context**에서 작업합니다. 점검할 클러스터 하나를 고르세요. 여러 클러스터라면 클러스터마다 워크스페이스를 하나씩 사용하거나, Rancher가 관리하는 클러스터 전체의 인벤토리와 상태를 위해 [Rancher 연결](/guide/connections/rancher)을 추가하세요.
</Info>

## 1단계: 클러스터 연결

<Steps>
  <Step title="읽기 전용 서비스 계정 만들기">
    아래 매니페스트를 `cloudthinker-reader.yaml`로 저장하고 적용합니다.

    ```bash
    kubectl apply -f cloudthinker-reader.yaml
    ```

    `cloudthinker` 네임스페이스, `cloudthinker-reader` 서비스 계정, 여기에 바인딩된 ClusterRole, 장기 토큰 Secret이 만들어집니다. 역할은 `get`, `list`, `watch`만 부여하며, Secrets에는 절대 부여하지 않습니다.

    | API 그룹 | 리소스 |
    |---|---|
    | core (`""`) | pods, pods/log, nodes, namespaces, services, endpoints, events, configmaps, persistentvolumeclaims, persistentvolumes, resourcequotas, limitranges, serviceaccounts, replicationcontrollers |
    | `apps` | deployments, replicasets, statefulsets, daemonsets |
    | `batch` | jobs, cronjobs |
    | `autoscaling` | horizontalpodautoscalers |
    | `networking.k8s.io` | ingresses, networkpolicies |
    | `policy` | poddisruptionbudgets |
    | `storage.k8s.io` | storageclasses |
    | `rbac.authorization.k8s.io` | roles, rolebindings, clusterroles, clusterrolebindings |
    | `metrics.k8s.io` | pods, nodes (`get` 및 `list`) |

    <Accordion title="cloudthinker-reader.yaml">
      ```yaml
      apiVersion: v1
      kind: Namespace
      metadata:
        name: cloudthinker
      ---
      apiVersion: v1
      kind: ServiceAccount
      metadata:
        name: cloudthinker-reader
        namespace: cloudthinker
      ---
      apiVersion: rbac.authorization.k8s.io/v1
      kind: ClusterRole
      metadata:
        name: cloudthinker-reader
      rules:
      - apiGroups: [""]
        resources: ["pods", "pods/log", "nodes", "namespaces", "services", "endpoints", "events", "configmaps", "persistentvolumeclaims", "persistentvolumes", "resourcequotas", "limitranges", "serviceaccounts", "replicationcontrollers"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["apps"]
        resources: ["deployments", "replicasets", "statefulsets", "daemonsets"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["batch"]
        resources: ["jobs", "cronjobs"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["autoscaling"]
        resources: ["horizontalpodautoscalers"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["networking.k8s.io"]
        resources: ["ingresses", "networkpolicies"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["policy"]
        resources: ["poddisruptionbudgets"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["storage.k8s.io"]
        resources: ["storageclasses"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["rbac.authorization.k8s.io"]
        resources: ["roles", "rolebindings", "clusterroles", "clusterrolebindings"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["metrics.k8s.io"]
        resources: ["pods", "nodes"]
        verbs: ["get", "list"]
      ---
      apiVersion: rbac.authorization.k8s.io/v1
      kind: ClusterRoleBinding
      metadata:
        name: cloudthinker-reader
      roleRef:
        apiGroup: rbac.authorization.k8s.io
        kind: ClusterRole
        name: cloudthinker-reader
      subjects:
      - kind: ServiceAccount
        name: cloudthinker-reader
        namespace: cloudthinker
      ---
      apiVersion: v1
      kind: Secret
      metadata:
        name: cloudthinker-reader-token
        namespace: cloudthinker
        annotations:
          kubernetes.io/service-account.name: cloudthinker-reader
      type: kubernetes.io/service-account-token
      ```
    </Accordion>

    토큰 Secret은 스스로 만료되지 않습니다. 교체하려면 Secret을 삭제하고, 매니페스트를 다시 적용하고, kubeconfig를 다시 만든 뒤 CloudThinker에서 교체하세요. 명령과 액세스 취소 방법은 [보안](/ko/guide/connections/kubernetes#보안)을 참조하세요.
  </Step>
  <Step title="해당 계정용 kubeconfig 만들기">
    현재 `kubectl` 컨텍스트가 대상 클러스터인 셸에서 실행하세요. 해당 컨텍스트에서 서버 URL을, Secret에서 토큰과 CA 인증서를 읽으므로 채울 것이 없습니다. `cloudthinker-kubeconfig.yaml`을 작성합니다.

    ```bash
    SERVER=$(kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}')
    CA=$(kubectl get secret cloudthinker-reader-token -n cloudthinker -o jsonpath='{.data.ca\.crt}')
    TOKEN=$(kubectl get secret cloudthinker-reader-token -n cloudthinker -o jsonpath='{.data.token}' | base64 --decode)

    cat > cloudthinker-kubeconfig.yaml <<EOF
    apiVersion: v1
    kind: Config
    clusters:
    - name: target
      cluster:
        server: ${SERVER}
        certificate-authority-data: ${CA}
    users:
    - name: cloudthinker-reader
      user:
        token: ${TOKEN}
    contexts:
    - name: cloudthinker
      context:
        cluster: target
        user: cloudthinker-reader
    current-context: cloudthinker
    EOF
    ```

    이전 macOS 릴리스에서는 `base64 --decode`를 `base64 -D`로 바꾸세요. 그런 다음 파일을 테스트합니다.

    ```bash
    kubectl --kubeconfig cloudthinker-kubeconfig.yaml get nodes
    ```

    `STATUS`가 `Ready`인 노드가 나열되면 CloudThinker의 연결 테스트도 통과합니다. 같은 명령을 실행하기 때문입니다.
  </Step>
  <Step title="CloudThinker에 업로드">
    **Settings → Workspace → Connections**를 열고 **Kubernetes**를 선택한 뒤, **KUBECONFIG** 필드에 파일을 업로드하고 **Connect**를 클릭합니다.

    상태가 **Connecting**과 **Verifying**을 거쳐 **Connected**로 바뀝니다. 테스트가 실패하면 대화 상자에 클러스터의 오류와 함께 **Failed** 또는 **Timed out**이 표시됩니다. [문제 해결](#문제-해결)을 참조하세요.
  </Step>
</Steps>

<Warning>
평소 사용하는 kubeconfig를 업로드하지 마세요. 로컬 경로를 가리키거나 `exec` 플러그인(클라우드 CLI 등)으로 로그인하는 파일은 내 머신의 도구에 의존하므로 CloudThinker에서 실패합니다. **해당 계정용 kubeconfig 만들기**에서 만든 토큰 기반 파일은 둘 다 피합니다.
</Warning>

## 2단계: 클러스터 상태 확인

연결이 예상한 것을 보는지 빠르게 확인하는 것부터 시작하세요.

```text
Check the Kubernetes connection: list the namespaces, the node count, and any nodes that are not Ready
```

네임스페이스 목록, 노드 수, 각 노드의 상태를 받습니다. 사용량 수치가 없으면 Metrics Server가 설치되지 않았다고 답변이 알려 줍니다.

그런 다음 더 넓은 그림을 요청하세요. 각 프롬프트는 클러스터의 한 계층을 다룹니다.

| 목표 | 예시 프롬프트 | 받는 결과 |
|------|----------------|-------------------|
| 노드 압박 | `Which nodes are under memory or disk pressure, and what is using the most memory?` | 노드 상태, 용량과 할당 가능 리소스, 상위 사용자(Metrics Server 있을 때) |
| 크기 조정 | `Analyze pod resource utilization in the payments namespace` | 실제 사용량과 비교한 requests와 limits, 과다 또는 과소 프로비저닝된 파드 표시 |
| 유휴 용량 | `Show nodes with less than 30% CPU utilization` | 활용도가 낮은 노드와 파드가 분산된 방식 |
| 오토스케일링 | `Recommend HPA policies for the deployments in the payments namespace` | 오토스케일러가 없거나 레플리카가 너무 적은 디플로이먼트, 그리고 제안 정책 |

각 프롬프트에 네임스페이스나 `app.kubernetes.io/part-of=web` 같은 레이블을 지정하세요. "웹 디플로이먼트" 같은 느슨한 표현은 CloudThinker가 의미를 추측하게 만듭니다.

한 팀의 `payments` 네임스페이스에서, 크기 조정 프롬프트는 CPU 약 20%로 실행되는 서비스 두 개(과다 프로비저닝)와, CPU 80% 이상으로 실행되며 메모리 한도에 가까운 `payment-processor` 하나를 표시했습니다. 그 파드는 OOM(메모리 부족) 종료 위험이 있었습니다. 이어서 오토스케일링 프롬프트는 레플리카가 2개뿐이고 Horizontal Pod Autoscaler(HPA)가 없다는 것을 보여 주었습니다.

## 3단계: 실패하는 파드 조사

이미 무언가 고장 났다면 네임스페이스를 지정하고 증상을 설명하세요.

```text
Which pods in the payments namespace are crash-looping, and what do their logs say?
```

CloudThinker는 크래시 루프, 보류, 재시작 중인 파드를 찾아 로그와 경고 이벤트를 읽고, 가능한 원인을 하나의 답변으로 설명합니다. 같은 대화에서 후속 질문으로 범위를 좁히세요.

```text
Why can't the pending pods in payments be scheduled?
Compare the memory limit of payment-processor with its current usage
```

스케줄링 문제에 대해서는 답변이 파드 requests와 각 노드가 아직 할당할 수 있는 양을 비교합니다. 재시작에 대해서는 재시작을 로그, 이벤트, 리소스 한도와 연결합니다.

### 수정 적용

읽기 전용 역할에서는 `scale`, `rollout restart`, `cordon`, `drain`, `apply` 같은 변경 명령이 승인한 뒤에도 `403`으로 실패합니다. 변경을 허용하려면 먼저 필요한 동사만 있는 Role을 바인딩한 뒤, CloudThinker가 요청할 때 명령을 승인하세요. 이 Role은 CloudThinker가 `payments`에서만 디플로이먼트를 스케일하고 재시작할 수 있게 합니다.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: cloudthinker-scale
  namespace: payments
rules:
- apiGroups: ["apps"]
  resources: ["deployments", "deployments/scale"]
  verbs: ["patch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: cloudthinker-scale
  namespace: payments
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: cloudthinker-scale
subjects:
- kind: ServiceAccount
  name: cloudthinker-reader
  namespace: cloudthinker
```

Cordon과 drain은 노드에 작용하므로 ClusterRole이 필요합니다. [쓰기 액세스](/ko/guide/connections/kubernetes#쓰기-권한)와 [Approvals](/guide/approvals/overview)를 참조하세요.

## 일정에 따라 실행

프롬프트가 유용한 답을 주면, 누군가 호출되기 전에 상태 점검이 도착하도록 일정에 따라 다시 실행하세요. 사이드바에서 **Automations**를 열고 **New automation**을 선택합니다. **What should the agent do for you?** 상자에 작업을 설명합니다(또는 채팅에 `/creating-automation` 입력). 예:

```text
Every weekday at 08:00, check the payments namespace for crash-looping or pending pods and nodes under memory or disk pressure, and summarize what changed since yesterday
```

기본적으로 각 실행은 새 대화를 시작하며, 실행 기록은 해당 automation의 페이지에 표시됩니다. 결과나 실패를 Slack, Teams, Google Chat, 이메일로 받으려면 [알림](/ko/guide/notifications)을 설정하세요. [Automations](/guide/automation/automations)를 참조하세요.

## 문제 해결

<AccordionGroup>
  <Accordion title="연결 테스트가 클러스터에 접근할 수 없음">
    kubeconfig의 API 서버 주소에 인터넷에서 접근할 수 없습니다. VPN 전용이 아닌지 확인하세요. 허용 목록(EKS public access CIDRs, GKE authorized networks, AKS authorized IP ranges)을 사용한다면 CloudThinker의 송신 IP를 추가하세요. 현재 목록은 CloudThinker 담당자에게 문의하세요.
  </Accordion>
  <Accordion title="답변에 CPU나 메모리 수치가 없음">
    Metrics Server가 설치되지 않았거나 준비되지 않았습니다. `kubectl top nodes`를 실행해 확인하세요. 파드 상태, 이벤트, 노드 상태는 없어도 작동합니다.
  </Accordion>
  <Accordion title="답변에 일부 리소스의 403이 언급됨">
    ClusterRole이 해당 리소스를 다루지 않습니다. 오류에 리소스 이름이 나오므로 역할에 추가하세요(또는 Secrets처럼 의도적으로 제외하세요).
  </Accordion>
  <Accordion title="답변이 잘못된 클러스터에 관한 것임">
    CloudThinker는 kubeconfig의 current context를 사용합니다. 원하는 클러스터에서 파일을 다시 만드세요. 그런 다음 Connections에서 **Kubernetes**를 열고, 연결 행의 연필 아이콘을 클릭하고, **Edit Instance**에서 **Replace…**를 클릭해 새 파일을 업로드한 뒤 **Save and test**를 클릭하세요.
  </Accordion>
  <Accordion title="테스트가 exec 플러그인 또는 file not found 오류로 실패함">
    로컬 명령(`aws`, `gcloud`, `kubelogin` 등)으로 로그인하거나 로컬 파일을 가리키는 kubeconfig를 업로드했습니다. 1단계의 토큰 기반 kubeconfig를 만들어 대신 업로드하세요. `aws eks update-kubeconfig`와 `gcloud container clusters get-credentials`의 기본 kubeconfig는 모두 `exec` 플러그인을 사용하므로 업로드하지 마세요.
  </Accordion>
</AccordionGroup>
