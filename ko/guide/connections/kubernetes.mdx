Kubernetes 클러스터를 연결하면 CloudThinker가 크래시 루프 중이거나 대기 중인 파드를 찾고, 로그와 이벤트를 읽고, 노드 압박을 확인하고, RBAC와 네트워크 정책을 검토할 수 있습니다. 전용 읽기 전용 서비스 계정으로 로그인하는 **kubeconfig file**을 업로드합니다. 롤아웃 재시작 같은 변경은 워크스페이스의 Approvals를 거치며, 쓰기 RBAC를 부여한 경우에만 실행됩니다([쓰기 권한](#쓰기-권한) 참조).

## 사전 요구 사항

- CloudThinker가 인터넷으로 API 서버에 접근할 수 있는 클러스터. 명령은 CloudThinker 클라우드에서 실행되므로, 비공개 전용 엔드포인트는 연결 테스트에 실패합니다. API 접근을 제한한다면(EKS public access CIDRs, GKE authorized networks, AKS authorized IP ranges) `0.0.0.0/0`으로 여는 대신 CloudThinker의 egress IP를 추가하세요. 이 문서는 CloudThinker의 egress IP 목록을 공개하지 않습니다. CloudThinker 담당자에게 문의하거나 [문의하기](https://cloudthinker.io/contact)를 이용하세요. 다른 방법은 [비공개 서비스 접근](/ko/guide/connections/overview#비공개-서비스-접근)을 참조하세요.
- 네임스페이스, ClusterRole, ClusterRoleBinding을 만들 수 있는 권한으로 해당 클러스터에 대한 `kubectl` 접근.
- 관리형 클러스터(EKS, GKE, AKS)는 `aws`, `gcloud`, `az` exec 플러그인으로 로그인하는 kubeconfig를 제공하는데, 이는 CloudThinker에서 작동하지 않습니다. 2단계에서 작동하는 kubeconfig를 만듭니다. Kubernetes가 서비스 계정 토큰을 직접 확인하므로 클라우드 IAM에서 매핑할 필요가 없습니다(예: EKS access entry 불필요).
- 선택 사항: 클러스터의 [Metrics Server](https://github.com/kubernetes-sigs/metrics-server). 없어도 에이전트는 파드 상태와 노드 조건을 보고하지만, 실시간 CPU 및 메모리 사용량은 보고하지 못합니다.
- 연결을 추가하고 편집할 수 있는 CloudThinker 워크스페이스의 **Admin** 역할. [Roles](/guide/security/roles)를 참조하세요.

<Info>
워크스페이스당 Kubernetes 연결은 **하나**이며, 에이전트는 kubeconfig의 **current context**에서 작업합니다. 검사할 클러스터 하나에 대한 kubeconfig를 업로드하세요. 여러 클러스터의 경우 [클러스터마다 워크스페이스 하나](/ko/guide/workspaces#워크스페이스-만들기)를 사용하거나, Rancher가 관리하는 클러스터 전반의 인벤토리와 상태를 위해 [Rancher 연결](/guide/connections/rancher)을 추가하세요.
</Info>

## 설정

<Steps>
  <Step title="읽기 전용 서비스 계정 만들기">
    이 매니페스트를 `cloudthinker-reader.yaml`로 저장합니다. 서비스 계정의 토큰인 Secret 하나도 함께 만들며, 이 Secret은 2단계에서 사용자만 읽습니다. 역할이 허용하는 범위는 [필수 권한](#필수-권한)에서 다룹니다.

    <Accordion title="cloudthinker-reader.yaml">
      ```yaml
      apiVersion: v1
      kind: Namespace
      metadata:
        name: cloudthinker
      ---
      apiVersion: v1
      kind: ServiceAccount
      metadata:
        name: cloudthinker-reader
        namespace: cloudthinker
      ---
      apiVersion: rbac.authorization.k8s.io/v1
      kind: ClusterRole
      metadata:
        name: cloudthinker-reader
      rules:
      - apiGroups: [""]
        resources: ["pods", "pods/log", "nodes", "namespaces", "services", "endpoints", "events", "configmaps", "persistentvolumeclaims", "persistentvolumes", "resourcequotas", "limitranges", "serviceaccounts", "replicationcontrollers"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["apps"]
        resources: ["deployments", "replicasets", "statefulsets", "daemonsets"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["batch"]
        resources: ["jobs", "cronjobs"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["autoscaling"]
        resources: ["horizontalpodautoscalers"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["networking.k8s.io"]
        resources: ["ingresses", "networkpolicies"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["policy"]
        resources: ["poddisruptionbudgets"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["storage.k8s.io"]
        resources: ["storageclasses"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["rbac.authorization.k8s.io"]
        resources: ["roles", "rolebindings", "clusterroles", "clusterrolebindings"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["metrics.k8s.io"]
        resources: ["pods", "nodes"]
        verbs: ["get", "list"]
      ---
      apiVersion: rbac.authorization.k8s.io/v1
      kind: ClusterRoleBinding
      metadata:
        name: cloudthinker-reader
      roleRef:
        apiGroup: rbac.authorization.k8s.io
        kind: ClusterRole
        name: cloudthinker-reader
      subjects:
      - kind: ServiceAccount
        name: cloudthinker-reader
        namespace: cloudthinker
      ---
      apiVersion: v1
      kind: Secret
      metadata:
        name: cloudthinker-reader-token
        namespace: cloudthinker
        annotations:
          kubernetes.io/service-account.name: cloudthinker-reader
      type: kubernetes.io/service-account-token
      ```
    </Accordion>

    적용합니다.

    ```bash
    kubectl apply -f cloudthinker-reader.yaml
    ```

    `cloudthinker` 네임스페이스, `cloudthinker-reader` 서비스 계정, 그 계정에 바인딩된 읽기 전용 ClusterRole, 그리고 수명이 긴 토큰 Secret이 만들어집니다.

    **성공 상태:** `kubectl get secret cloudthinker-reader-token -n cloudthinker`가 `DATA` 개수 3인 Secret을 나열합니다. Kubernetes는 적용 후 몇 초 안에 토큰을 채우므로, `DATA`가 0으로 표시되면 잠시 기다렸다가 명령을 다시 실행하세요.
  </Step>
  <Step title="해당 계정용 kubeconfig 만들기">
    현재 `kubectl` 컨텍스트가 대상 클러스터인 셸에서 실행합니다. 먼저 API 서버 주소를 읽고 확인합니다.

    ```bash
    SERVER=$(kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}')
    echo $SERVER
    ```

    공개 호스트 이름이나 IP가 출력되어야 합니다. `127.0.0.1`, `localhost` 또는 `10.x`, `192.168.x` 같은 사설 주소(kind, minikube, k3d 또는 로컬 프록시 뒤에서 흔함)가 표시되면 CloudThinker가 접근할 수 없으므로, 멈추고 먼저 접근 문제를 해결하세요.

    그런 다음 같은 셸에서 토큰과 CA 인증서가 포함된 `cloudthinker-kubeconfig.yaml`을 작성합니다.

    ```bash
    CA=$(kubectl get secret cloudthinker-reader-token -n cloudthinker -o jsonpath='{.data.ca\.crt}')
    TOKEN=$(kubectl get secret cloudthinker-reader-token -n cloudthinker -o jsonpath='{.data.token}' | base64 --decode)

    cat > cloudthinker-kubeconfig.yaml <<EOF
    apiVersion: v1
    kind: Config
    clusters:
    - name: target
      cluster:
        server: ${SERVER}
        certificate-authority-data: ${CA}
    users:
    - name: cloudthinker-reader
      user:
        token: ${TOKEN}
    contexts:
    - name: cloudthinker
      context:
        cluster: target
        user: cloudthinker-reader
    current-context: cloudthinker
    EOF
    ```

    이전 macOS 릴리스에서는 `base64 --decode`를 `base64 -D`로 바꾸고, 닫는 `EOF`를 줄의 맨 앞에 두세요.

    **성공 상태:** `kubectl --kubeconfig cloudthinker-kubeconfig.yaml get nodes`가 노드를 나열합니다. CloudThinker가 연결을 테스트할 때 실행하는 것과 같은 명령입니다.
  </Step>
  <Step title="CloudThinker에서 kubeconfig 업로드">
    **Settings → Workspace → Connections**를 열고 **Kubernetes**를 선택한 다음, **KUBECONFIG** 필드에 `cloudthinker-kubeconfig.yaml`을 업로드합니다. **Connect**를 클릭합니다.

    **성공 상태:** 연결에 **Connecting**과 **Verifying**이 표시된 다음 **Connected** 상태가 표시됩니다.
  </Step>
</Steps>

## 연결 세부 정보

| 필드 | 필수 | 설명 | 예시 |
|-------|----------|-------------|---------|
| **KUBECONFIG** | 예 | kubeconfig 파일. 파일 선택기는 `.yaml` 확장자만 받으므로 `.yml` 파일은 선택할 수 없습니다. 먼저 `.yaml`로 이름을 바꾸세요. CloudThinker는 current context를 사용합니다 | `cloudthinker-kubeconfig.yaml` |

모든 것을 파일에 포함하세요. 로컬 인증서 파일을 가리키거나 `exec` 플러그인으로 로그인하는 kubeconfig에는 CloudThinker에 없는 파일과 도구가 필요합니다. 2단계의 토큰 기반 파일은 두 가지를 모두 피합니다.

## 필수 권한

[1단계](#설정)의 매니페스트는 에이전트가 검사하는 리소스와 파드 로그, 메트릭에 대한 읽기 권한(`get`, `list`, `watch`)을 부여합니다. Secret은 읽을 수 없습니다.

ClusterRoleBinding은 모든 네임스페이스에서 역할을 부여하므로, 읽기 권한은 `kube-system`을 포함해 클러스터 전체에 적용됩니다. 일부 네임스페이스만 다루려면 ClusterRoleBinding을 각 네임스페이스에서 같은 ClusterRole에 대한 RoleBinding으로 바꾸세요. 그러면 RoleBinding이 부여할 수 없는 노드, 네임스페이스, 퍼시스턴트 볼륨 같은 클러스터 범위 리소스는 답변에서 빠집니다.

사용자 지정 리소스는 포함되지 않으므로, 에이전트는 Argo CD 애플리케이션이나 Istio 가상 서비스 같은 CRD 기반 객체를 볼 수 없습니다. 보게 하려면 각 리소스의 API 그룹을 사용하는 규칙을 ClusterRole에 추가하세요.

<Tip>
역할을 필요한 범위로 줄이세요. ConfigMap에 민감한 값이 있다면 `configmaps`를 빼고, RBAC 검토가 필요 없다면 `rbac.authorization.k8s.io` 규칙을 빼세요. 답변에 나타나는 `403`은 역할에 빠진 리소스를 알려 줍니다.
</Tip>

## 쓰기 권한

에이전트는 대화에서 요청할 때만 `scale`, `rollout restart`, `cordon`, `drain`, `apply` 같은 변경을 실행하며, 위의 읽기 전용 역할에서는 `403`으로 실패합니다. 연결 상세 패널의 **Allow writes**가 두 번째 통제입니다. 기본적으로 켜져 있지만, 역할이 허용하는 범위를 넓힐 수는 없습니다.

| `cloudthinker-reader` 서비스 계정의 RBAC | Allow writes | 결과 |
|---|---|---|
| 읽기 전용 규칙만 | 켜짐 또는 꺼짐 | 읽기 전용. Kubernetes가 모든 변경을 `403`으로 거부합니다. |
| 쓰기 규칙 부여 | 꺼짐 | 읽기 전용. CloudThinker가 클러스터에 도달하기 전에 모든 변경을 거부합니다. |
| 쓰기 규칙 부여 | 켜짐 | 에이전트가 변경을 제안할 수 있습니다. [Rules와 Approval mode](/guide/approvals/overview)가 각 변경을 결정합니다. |

CloudThinker에서도 쓰기를 잠그려면 **Settings → Workspace → Connections**를 열고 **Kubernetes**를 선택한 다음, 상세 패널의 **Allow writes** 스위치를 끄세요.

<ApprovalDefault />

특정 변경을 허용하려면 그 변경에 필요한 것만 부여하세요.

- **Scale과 rollout restart**는 네임스페이스 범위 워크로드에 작용합니다. 관련된 각 네임스페이스에서 `deployments`에 대한 `patch`와 `deployments/scale`에 대한 `get` 및 `patch`를 가진 Role을 사용하세요. StatefulSet의 경우 `statefulsets`와 `statefulsets/scale`에 같은 권한을 추가하세요. DaemonSet의 경우 `daemonsets`를 추가하세요(확장되지 않으므로 재시작만 해당).
- **Apply**에는 적용하는 매니페스트의 각 리소스 유형에 대해, 대상 네임스페이스에서 `get`, `create`, `patch`가 필요합니다.
- **Cordon과 drain**은 클러스터 범위인 노드에 작용하므로 네임스페이스 Role로는 허용할 수 없습니다. `nodes`에 대한 `patch`와 `pods/eviction`에 대한 `create`를 가진 ClusterRole을 사용하세요. drain에 필요한 파드와 DaemonSet에 대한 `get`과 `list`는 읽기 역할이 이미 제공합니다.

쓰기 권한은 같은 `cloudthinker-reader` 서비스 계정에 바인딩되므로, 하나의 kubeconfig로 읽기와 변경을 모두 처리합니다. 처음부터 쓰기 권한을 계획한다면 두 매니페스트와 2단계에서 계정 이름을 바꾸세요(예: `cloudthinker-agent`).

이 예시는 한 네임스페이스에서 디플로이먼트 확장과 cordon, drain을 허용합니다. `payments`를 사용자의 네임스페이스로 바꾸고 `cloudthinker-write.yaml`로 저장한 다음 `kubectl apply -f cloudthinker-write.yaml`을 실행합니다.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: cloudthinker-scale
  namespace: payments
rules:
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["patch"]
- apiGroups: ["apps"]
  resources: ["deployments/scale"]
  verbs: ["get", "patch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: cloudthinker-scale
  namespace: payments
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: cloudthinker-scale
subjects:
- kind: ServiceAccount
  name: cloudthinker-reader
  namespace: cloudthinker
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: cloudthinker-node-ops
rules:
- apiGroups: [""]
  resources: ["nodes"]
  verbs: ["patch"]
- apiGroups: [""]
  resources: ["pods/eviction"]
  verbs: ["create"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: cloudthinker-node-ops
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: cloudthinker-node-ops
subjects:
- kind: ServiceAccount
  name: cloudthinker-reader
  namespace: cloudthinker
```

**성공 상태:** `kubectl auth can-i patch deployments/scale -n payments --as=system:serviceaccount:cloudthinker:cloudthinker-reader`가 `yes`를 출력합니다.

## 에이전트 기능

| 기능 | 에이전트가 하는 작업 |
|------------|----------------|
| **워크로드 분류** | 크래시 루프, 대기, 재시작 중인 파드와 저하된 디플로이먼트, 경고 이벤트를 찾은 다음 로그를 읽어 원인 설명 |
| **노드 압박** | 노드 조건, 용량, 할당 가능 리소스를 보고하고, Metrics Server가 설치된 경우 CPU와 메모리를 가장 많이 쓰는 대상 보고 |
| **용량과 스케줄링** | 요청과 제한을 사용량과 비교하고, 파드가 스케줄되지 않는 이유 설명 |
| **보안과 RBAC** | 역할 바인딩, 서비스 계정, 네트워크 정책, 권한 있는 워크로드 검토 |
| **구성** | 네임스페이스 전반의 인그레스, 서비스, 스토리지, 오토스케일러, 이미지 검사. 사용자 지정 리소스는 역할에 규칙을 추가해야 합니다 |
| **변경** | Scale, restart, cordon, drain 또는 apply. 각 변경은 Approvals를 거칩니다 |

### 연결 확인

```text
Check the Kubernetes connection: list the namespaces, the node count, and any nodes that are not Ready
```

네임스페이스 목록, 노드 수, 노드 상태가 표시됩니다. 사용량 숫자가 없으면 답변에 Metrics Server가 설치되지 않았다고 나옵니다.

### 예시 프롬프트

```text
Which pods in the payments namespace are crash-looping, and what do their logs say?
Which nodes are under memory or disk pressure, and what is using the most memory?
Which service accounts are bound to cluster-admin?
```

## 토큰 교체

Kubernetes는 연결을 하나만 가질 수 있는 서비스이므로, 정상 상태일 때는 연필 아이콘이나 **Edit Instance** 대화상자가 없습니다. 새 토큰을 먼저 만들고 이전 Secret은 마지막에 삭제하세요. 먼저 삭제하면 작동하는 대체 토큰이 생기기 전에 클러스터 연결이 끊깁니다.

<Steps>
  <Step title="두 번째 토큰 Secret 만들기">
    이것을 `cloudthinker-reader-token-2.yaml`로 저장합니다. 같은 서비스 계정의 두 번째 토큰이므로, 교체하는 동안 둘 다 작동합니다.

    ```yaml
    apiVersion: v1
    kind: Secret
    metadata:
      name: cloudthinker-reader-token-2
      namespace: cloudthinker
      annotations:
        kubernetes.io/service-account.name: cloudthinker-reader
    type: kubernetes.io/service-account-token
    ```

    적용합니다.

    ```bash
    kubectl apply -f cloudthinker-reader-token-2.yaml
    ```

    **성공 상태:** `kubectl get secret cloudthinker-reader-token-2 -n cloudthinker`가 `DATA` 개수 3인 Secret을 나열합니다.
  </Step>
  <Step title="새 토큰으로 kubeconfig 만들기">
    `cloudthinker-reader-token` 대신 `cloudthinker-reader-token-2`를 사용하여 [설정](#설정)의 2단계를 반복합니다.

    **성공 상태:** `kubectl --kubeconfig cloudthinker-kubeconfig.yaml get nodes`가 노드를 나열합니다.
  </Step>
  <Step title="CloudThinker에서 교체">
    연결에 **Connected**가 표시되는 동안에는 **Kubernetes** 상세 패널에서 **Disconnect**를 클릭한 다음, 다시 연결하고 새 kubeconfig를 업로드합니다. **Error**가 표시되는 동안에는 연결을 끊지 않고 상세 패널에서 **Replace credentials**를 클릭하여 새 kubeconfig를 업로드합니다.

    **성공 상태:** 연결에 **Connected**가 표시됩니다.
  </Step>
  <Step title="이전 Secret 삭제">
    이제서야 교체한 토큰을 제거합니다.

    ```bash
    kubectl delete secret cloudthinker-reader-token -n cloudthinker
    ```
  </Step>
</Steps>

연결을 끊고 다시 연결하면 새 연결이 시작됩니다.

- 끊은 시점부터 다시 연결할 때까지 에이전트와 예약된 [automation](/guide/automation/automations)은 클러스터를 사용할 수 없습니다.
- 첫 연결 시의 deep look 채팅이 다시 열리고 크레딧을 사용합니다.
- **Allow writes**가 켜짐으로 돌아갑니다. 꺼 두었다면 다시 끄세요.
- Kubernetes 연결을 지정한 [Rules](/guide/approvals/rules)가 여전히 그 연결을 나열하는지 확인하세요.

정책상 수명이 긴 자격 증명이 금지되어 있다면 Secret을 건너뛰고 `kubectl create token cloudthinker-reader -n cloudthinker --duration=<time>`으로 만든 수명이 짧은 토큰으로 kubeconfig를 만드세요. 그 토큰이 만료되면 연결이 끊기므로, 매번 kubeconfig를 다시 만들어 업로드해야 합니다.

## 문제 해결

테스트가 실패하면 `Failed to connect to Kubernetes:` 뒤에 `kubectl get nodes`의 첫 번째 오류 줄이 표시됩니다. 그 줄을 아래 항목과 대조하세요.

<Accordion title="Unable to connect to the server">
CloudThinker가 kubeconfig의 API 서버에 접근할 수 없었습니다. `server` 주소가 VPN에서만이 아니라 인터넷에서 접근 가능한지, API 서버 허용 목록이 외부 접근을 허용하는지 확인하세요. 네트워크 외부의 머신에서 `kubectl --kubeconfig cloudthinker-kubeconfig.yaml get nodes`를 실행하여 확인하세요.
</Accordion>

<Accordion title="error: You must be logged in to the server (Unauthorized)">
토큰이 잘못되었거나, 만료되었거나, 취소되었습니다. `cloudthinker-reader-token` Secret이 아직 있는지 확인한 다음, 2단계에서 kubeconfig를 다시 만들고 [토큰 교체](#토큰-교체)를 통해 업로드하세요.
</Accordion>

<Accordion title="답변에 Error from server (Forbidden)가 나타남">
ClusterRole이 해당 리소스를 다루지 않습니다. ClusterRoleBinding이 적용되었는지 확인한 다음, 역할에 리소스를 추가하세요.
</Accordion>

<Accordion title="getting credentials: exec 또는 no such file or directory">
kubeconfig가 로컬 명령이나 파일 경로에 의존합니다. 2단계의 토큰 기반 kubeconfig로 바꾸세요.
</Accordion>

<Accordion title="답변에 CPU 또는 메모리 사용량이 없음">
Metrics Server가 설치되지 않았거나 준비되지 않았습니다. `kubectl top nodes`를 실행하여 확인하세요. 파드 상태, 이벤트, 노드 조건은 이것 없이도 작동합니다.
</Accordion>

<Accordion title="Connection 'k8s' already exists. Only one instance is allowed.">
`k8s`는 Kubernetes 연결이며, 워크스페이스는 하나만 가질 수 있습니다. 편집할 연필 아이콘이 없으므로, CloudThinker가 다른 클러스터를 가리키게 하려면 **Kubernetes** 상세 패널에서 **Disconnect**를 클릭하고 다른 kubeconfig로 다시 연결하세요.
</Accordion>

## 보안

<ConnectionSecurity />

- **역할에서 Secret 제외.** 위의 매니페스트는 Secret 읽기를 부여하지 않으므로 에이전트는 Secret 객체를 읽을 수 없습니다. 파드 로그와 ConfigMap은 읽을 수 있으므로, 민감한 데이터가 있다면 역할에서 `pods/log`나 `configmaps`를 빼세요. 파드 스펙에 직접 설정한 env 값은 `pods`를 통해 읽을 수 있으므로, 민감한 값은 Secret으로 옮기세요.
- **토큰 교체.** 토큰 Secret은 스스로 만료되지 않으므로 평소 일정에 따라 교체하세요. [토큰 교체](#토큰-교체)를 참조하세요.
- **명령 하나로 취소.** 토큰 Secret을 삭제하면 즉시 접근이 끊기고, `cloudthinker` 네임스페이스와 ClusterRole 및 바인딩을 삭제하면 모든 것이 제거됩니다.
