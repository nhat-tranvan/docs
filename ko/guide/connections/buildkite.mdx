Buildkite를 연결하면 CloudThinker 에이전트가 파이프라인 상태를 측정하고, 로그와 주석으로 빌드 실패 원인을 찾고, 에이전트 용량을 확인할 수 있습니다. 이 연결은 Buildkite API 액세스 토큰을 사용하며, 토큰에 부여한 스코프가 에이전트가 할 수 있는 일의 실제 한계입니다.

## 사전 요구 사항

- 에이전트가 모니터링할 조직에 접근할 수 있는 Buildkite 계정.
- 해당 조직의 API 액세스 토큰을 만들 수 있는 권한.

## 설정

<Steps>
  <Step title="API 액세스 토큰 생성">
    Buildkite에서 **Personal Settings → API Access Tokens → New API Access Token**([buildkite.com/user/api-access-tokens/new](https://buildkite.com/user/api-access-tokens/new))으로 이동하여 다음을 설정합니다.
    - **Description**: `cloudthinker`
    - **Organization access**: CloudThinker가 접근할 조직
    - **REST API scopes**: `read_organizations`, `read_pipelines`, `read_builds`, `read_build_logs`, `read_artifacts`, `read_agents`, `read_clusters`, `read_user`. 에이전트가 재시도, 차단 해제, 재빌드, 취소를 하기를 원하는 경우에만 `write_builds`를 추가하세요.

    토큰을 즉시 복사하세요. Buildkite는 한 번만 표시합니다.
  </Step>
  <Step title="연결 추가">
    **Settings → Workspace → Connections**를 열고 **Discover** 탭에서 **Buildkite**를 선택합니다. **BUILDKITE_API_TOKEN**에 토큰을 붙여넣고 **Connect**를 클릭합니다.

    **성공 상태:** 다이얼로그가 닫히고 연결에 **Connected**가 표시됩니다.
  </Step>
  <Step title="토큰 작동 확인">
    [연결 확인](#연결-확인)의 프롬프트를 실행하세요. Buildkite는 잘못된 토큰으로도 연결을 받아들이고 에이전트가 첫 호출을 할 때만 거부하므로, **Connected** 상태만으로는 토큰이 유효하다는 것이 증명되지 않습니다.
  </Step>
</Steps>

## 연결 세부 정보

| 필드 | 설명 |
|-------|-------------|
| **BUILDKITE_API_TOKEN** | Buildkite API 액세스 토큰. 스코프가 어떤 작업이 성공할지 결정합니다 |

입력할 조직 slug는 없습니다. 에이전트가 토큰에서 알아냅니다. CloudThinker는 토큰을 `https://mcp.buildkite.com/direct`에 있는 Buildkite 호스팅 MCP 서버로 보내고, 서버가 이를 Buildkite REST API로 전달합니다. 이 서버는 CloudThinker가 아니라 Buildkite가 운영합니다.

## 필수 권한

| 스코프 | 필수 | 가능해지는 것 |
|-------|----------|---------|
| `read_organizations` | 예 | 토큰이 접근할 수 있는 조직 확인 |
| `read_pipelines` | 예 | 파이프라인 목록과 세부 정보 |
| `read_builds` | 예 | 빌드, 작업, 주석, 실패 요약 |
| `read_build_logs` | 예 | 작업 로그 읽기, 검색, 추적 |
| `read_artifacts` | 예 | 빌드 및 작업 아티팩트 |
| `read_agents` | 예 | 에이전트 연결 상태와 용량 |
| `read_clusters` | 예 | 클러스터와 클러스터 큐 |
| `read_user` | 예 | 토큰 자신의 사용자 조회 |
| `write_builds` | 아니요 | 작업 재시도, 작업 차단 해제, 재빌드, 취소 |

<Tip>
모니터링 전용 연결에서는 `write_builds`를 빼 두세요. 에이전트는 모든 읽기를 유지하고 Buildkite 자체가 모든 변경을 거부하므로, 승인에만 의존하지 않아도 됩니다.
</Tip>

## 에이전트 기능

| 기능 | 에이전트가 할 수 있는 일 |
|------------|--------------------|
| **Discovery** | 조직의 파이프라인, 최근 빌드, 에이전트, 클러스터 나열 |
| **Pipeline health** | 통과율, 연속 실패, 그리고 프롬프트에서 지정한 임계값(예: "30분 넘게 멈춤")보다 오래 멈춘 빌드 보고 |
| **Failed-build triage** | Buildkite의 실패 요약을 작업 로그, 주석, 실패한 테스트와 교차 확인 |
| **Logs and artifacts** | 작업 로그 읽기, 검색, 추적. 빌드 및 작업 아티팩트 나열과 가져오기 |
| **Capacity** | 에이전트 연결 상태, 클러스터, 클러스터 큐 표시 |
| **Build controls** | 작업 재시도, 작업 차단 해제, 빌드 재빌드, 빌드 취소. **각각 승인을 거칩니다** |

수동 block 단계에서 대기 중인 빌드는 Buildkite API에서 `passed`로 보고됩니다. 에이전트는 게이트를 확인하고 block 단계 이름을 밝히며 그 빌드를 통과율에서 제외하므로, 보류된 배포가 녹색 파이프라인으로 보이는 일이 없습니다. 차단을 해제하기 전에 에이전트는 block 단계의 라벨과 빌드의 주석을 인용하므로 어떤 게이트를 여는지 알 수 있습니다.

에이전트는 파이프라인, 클러스터, 큐, 일정을 만들거나 편집할 수 없으며, 작업 환경 변수를 읽지 않습니다. Buildkite Test Engine 데이터는 이 연결로 사용할 수 없습니다.

<ApprovalDefault />

매번 확인을 받으려면 사람이 모든 변경을 승인하도록 [Approval mode](/guide/approvals/approval-mode)를 **Manual**로 선택하세요. **Ask first** [Rule](/guide/approvals/rules)로 이를 이 연결에만 좁힐 수 있습니다.

### 연결 확인

```text
List my Buildkite pipelines and show the latest build status for each
```

각 파이프라인이 slug와 최신 빌드 상태와 함께 나와야 합니다. 여기서 401이 나오면 연결이 **Connected**로 표시되어도 토큰이 유효하지 않은 것입니다.

### 예시 프롬프트

```text
Which Buildkite pipelines are failing right now, and how long is each failure streak?
Build 42 of the web pipeline failed. Pull the logs and annotations and tell me the cause
Show Buildkite agent capacity and any builds stuck for more than an hour
```

## 문제 해결

<Accordion title="Connected 상태인데 모든 요청이 401을 반환합니다">
토큰이 유효하지 않거나 만료되었거나 폐기되었습니다. 새 API 액세스 토큰을 만들고 연결의 **BUILDKITE_API_TOKEN**을 업데이트하세요.
</Accordion>

<Accordion title="읽기에서 403이 발생합니다">
토큰에 읽기 스코프가 빠져 있습니다. [필수 권한](#필수-권한)과 대조하여 Buildkite에서 토큰의 스코프를 편집하세요. 새 토큰은 필요 없습니다.
</Accordion>

<Accordion title="재시도, 차단 해제, 재빌드 또는 취소가 권한 오류로 실패합니다">
토큰에 `write_builds`가 없습니다. Buildkite에서 스코프를 추가하거나, 연결을 읽기 전용으로 유지하고 Buildkite에서 직접 작업을 실행하세요.
</Accordion>

<Accordion title="게이트 상태가 unknown으로 표시됩니다">
수동 block 단계 확인이 보통 속도 제한 때문에 실패했습니다. 에이전트는 빌드를 미완료로 취급하고 통과율에서 제외합니다. unknown은 게이트가 없다는 뜻이 아닙니다. 1분 뒤 다시 요청하세요.
</Accordion>

<Accordion title="존재하는 파이프라인에서 404가 발생합니다">
Buildkite가 slug를 기대하는 곳에 파이프라인 이름이 사용되었습니다. 에이전트에게 파이프라인을 나열하라고 요청하고 그 목록의 slug를 사용하세요.
</Accordion>

<Accordion title="429 속도 제한">
요청이 너무 많은 파이프라인이나 빌드를 다뤘습니다. 질문을 파이프라인 하나로 좁히거나 최근 빌드를 더 적게 요청하세요.
</Accordion>

## 보안

<ConnectionSecurity />

- **승인만이 아니라 토큰의 스코프를 제한하세요**: Buildkite는 토큰 스코프를 강제합니다. `write_builds`가 없는 토큰은 CI 상태를 전혀 바꿀 수 없습니다.
- **차단 해제를 릴리스로 취급하세요**: block 단계는 보통 누군가 의도적으로 추가한 배포 게이트입니다. 에이전트가 인용한 라벨을 읽은 뒤에만 차단 해제를 승인하세요.
