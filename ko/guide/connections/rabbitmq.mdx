RabbitMQ 브로커를 연결하면 [CloudThinker](/ko/guide/agents/overview)가 어떤 큐가 쌓이고 있는지, 어떤 큐에 컨슈머가 없는지, dead-letter 큐에 무엇이 남아 있는지, 알람 상태인 노드가 있는지 알려 줄 수 있습니다. 이 연결은 RabbitMQ 관리 UI가 사용하는 것과 같은 Management HTTP API를 통해 브로커 **사용자 이름과 비밀번호**로 로그인합니다. 코드를 변경할 필요가 없습니다.

## 지원 플랫폼

| 플랫폼 | 지원 여부 | 참고 |
|----------|-----------|-------|
| **Self-hosted RabbitMQ** | 예 | `rabbitmq_management` 플러그인이 활성화되어 있어야 합니다 |
| **Managed RabbitMQ**(예: CloudAMQP) | 예 | 공급자가 Management HTTP API를 CloudThinker에 노출해야 합니다 |
| **Clusters** | 예 | 클러스터마다 연결을 하나씩 추가합니다. **RABBITMQ_HOST**가 로드 밸런서나 아무 노드를 가리키도록 합니다. 관리 API는 어느 노드에서든 클러스터 전체 상태를 보고합니다 |

## 사전 요구 사항

- 브로커에서 관리 플러그인이 활성화되어 있어야 합니다.
- 인터넷에서 접근할 수 있는 관리 포트: HTTP는 `15672`, HTTPS는 대개 `15671`. 이는 AMQP 포트(`5672`)와 다른 포트입니다. 연결은 CloudThinker Cloud에서 실행되므로, 비공개 네트워크의 브로커에는 [Reaching private services](/ko/guide/connections/overview#비공개-서비스-접근)의 옵션 중 하나가 필요합니다.
- 사용자를 만들기 위한 브로커 셸 접근(`rabbitmqctl`) 또는 공급자 콘솔.

## 설정

<Steps>
  <Step title="관리 플러그인 활성화">
    자체 호스팅 브로커에서 다음을 실행합니다:

    ```bash
    rabbitmq-plugins enable rabbitmq_management
    ```

    관리형 공급자는 대개 이미 켜져 있습니다. 공급자 콘솔에 관리 UI가 표시된다면 이 단계를 건너뜁니다.
  </Step>
  <Step title="CloudThinker용 모니터링 사용자 생성">
    전용 사용자를 만들고, `monitoring` 태그를 붙이고, 에이전트가 볼 각 가상 호스트(vhost)에 대한 읽기 권한을 부여합니다. vhost는 큐와 exchange를 위한 RabbitMQ의 네임스페이스이며, `/`가 기본값입니다.

    ```bash
    rabbitmqctl add_user cloudthinker '<strong-password>'
    rabbitmqctl set_user_tags cloudthinker monitoring
    rabbitmqctl set_permissions -p / cloudthinker "" "" ".*"
    ```

    세 권한 문자열은 configure, write, read입니다. configure와 write를 비우고 read를 `.*`로 하면 사용자가 vhost의 모든 것을 볼 수 있지만, 완전한 읽기 전용은 아닙니다. RabbitMQ에서는 read 권한으로 큐를 purge할 수 있으므로, 이 사용자는 여전히 큐를 비울 수 있습니다. 큐와 exchange 삭제에는 configure가 필요하며, 이 사용자에게는 없습니다. 추가 vhost마다 `set_permissions`를 반복합니다.

    에이전트가 아무것도 purge하지 못하게 하려면 다음 단계에서 **RABBITMQ_ALLOW_MUTATIONS**를 **Read-only**로 설정합니다.
  </Step>
  <Step title="네트워크 경로 열기">
    방화벽이나 보안 그룹에서 CloudThinker의 egress IP로부터 `<host>:15672`(또는 TLS 관리 포트)로 들어오는 트래픽을 허용합니다. 이 문서는 CloudThinker의 egress IP 목록을 게시하지 않습니다. CloudThinker 담당자에게 문의하거나 [문의](https://cloudthinker.io/contact)하세요. 자체 호스팅 브로커에서는 관리 리스너가 `127.0.0.1`에만 바인딩되어 있지 않은지 확인합니다.

    **성공 상태:** 브로커 네트워크 외부의 컴퓨터에서 다음을 실행합니다. `rabbitmq_version`과 `cluster_name`이 포함된 JSON을 반환하며, 이로써 새 사용자와 네트워크 경로가 모두 확인됩니다:

    ```bash
    curl -u cloudthinker:'<strong-password>' http://<host>:15672/api/overview
    ```

    TLS가 켜져 있다면 대신 `https://<host>:15671`을 사용합니다.
  </Step>
  <Step title="CloudThinker에 연결 추가">
    **Settings → Workspace → Connections**를 열고 **Discover** 탭을 연 다음 **RabbitMQ**를 선택합니다. 다음을 입력합니다:

    - **RABBITMQ_USERNAME**: `cloudthinker`
    - **RABBITMQ_PASSWORD**: 설정한 비밀번호
    - **RABBITMQ_HOST**: `rabbit.internal.example.com` 같은 호스트 이름 또는 IP만
    - **RABBITMQ_MANAGEMENT_PORT**: `15672` 또는 TLS 관리 포트
    - **RABBITMQ_USE_TLS**: 관리 API가 HTTPS를 제공한다면 **Enabled**
    - **RABBITMQ_ALLOW_MUTATIONS**: **Read-only**(권장). [쓰기 권한](#쓰기-권한)의 작업이 필요할 때만 **Allow writes**를 선택합니다
    - **LOG_LEVEL**: **Info**로 둡니다

    <Warning>
    **RABBITMQ_ALLOW_MUTATIONS**의 기본값은 **Allow writes**입니다. **Connect**를 클릭하기 전에 **Read-only**로 바꾸세요. 브로커 사용자만으로는 모든 쓰기를 막지 못합니다. read 권한만 있는 사용자도 큐를 purge할 수 있으며, purge는 메시지를 영구히 삭제합니다. **Read-only**는 purge와 delete 도구를 에이전트에게서 떼어 놓습니다.
    </Warning>

    **Connect**를 클릭합니다.

    **성공 상태:** 연결이 **Connecting**과 **Verifying**을 거쳐 **Connected**로 표시됩니다. 검증에 실패하면 **Failed**가 표시되고 오류 메시지가 나타납니다. 메시지를 [문제 해결](#문제-해결)과 대조합니다.
  </Step>
</Steps>

## 연결 세부 정보

| 필드 | 필수 | 기본값 | 설명 |
|-------|----------|---------|-------------|
| **RABBITMQ_USERNAME** | 예 | 없음 | `monitoring` 태그가 있는 브로커 사용자 |
| **RABBITMQ_PASSWORD** | 예 | 없음 | 해당 사용자의 비밀번호 |
| **RABBITMQ_HOST** | 예 | 없음 | 호스트 이름 또는 IP. `http://`, `https://`, 포트 없이 |
| **RABBITMQ_MANAGEMENT_PORT** | 예 | `15672` | Management HTTP API 포트. TLS를 켰다면 TLS 포트(대개 `15671`)를 사용합니다 |
| **RABBITMQ_USE_TLS** | 아니요 | **Disabled** | **Disabled**: 일반 HTTP 관리 API와 AMQP. **Enabled**: HTTPS 관리 API와 AMQPS |
| **RABBITMQ_ALLOW_MUTATIONS** | 아니요 | **Allow writes** | **Read-only**(권장): 모니터링과 문제 해결만. **Allow writes**: purge, delete, 일괄 정의 업데이트를 활성화하며, 각각 Approvals가 하나씩 확인합니다 |
| **LOG_LEVEL** | 아니요 | **Info** | 커넥터 로그 상세 수준: **Debug**, **Info**, **Warn**, **Error** |

## 필요 권한

| 목표 | 사용자 태그 | vhost 권한 |
|------|----------|-------------------|
| 모니터링과 문제 해결(권장, **Read-only** 설정) | `monitoring` | 에이전트가 볼 각 vhost의 read(`"" "" ".*"`). read는 큐 purge도 허용합니다 |
| 모니터링과 삭제 | `monitoring` | 에이전트가 변경할 수 있는 vhost의 configure와 read |
| 일괄 정의 업데이트 | `administrator` | configure, write, read. RabbitMQ는 관리자의 정의 가져오기만 허용하며, 이 태그는 브로커 전체의 사용자 및 정책 관리 권한도 부여합니다 |

<Tip>
`monitoring`, read 권한, **Read-only**로 설정한 **RABBITMQ_ALLOW_MUTATIONS**로 시작하세요. 아래의 모든 읽기 기능을 다룹니다. 에이전트가 purge나 삭제를 해야 한다고 결정했을 때만 **Allow writes**로 바꾸고, 에이전트가 삭제할 수 있는 vhost에만 configure 권한을 추가하세요. 일괄 정의 업데이트가 필요할 때만 `administrator`를 사용하세요.
</Tip>

## 에이전트 기능

| 기능 | 에이전트가 할 수 있는 일 |
|------------|--------------------|
| **Queue depth and rates** | 큐별 ready 및 unacknowledged 메시지 수를 게시 및 전달 속도와 함께 보고합니다 |
| **Consumer health** | 컨슈머가 없는 큐, 또는 컨슈머가 처리하는 것보다 메시지가 빨리 쌓이는 큐를 찾습니다 |
| **Dead-letter review** | dead-letter 큐 안에서 반복되는 실패와 그 원인이 된 메시지를 살펴봅니다 |
| **Cluster and node health** | 노드 상태, 메모리 및 디스크 알람, 쿼럼을 잃을 위험이 있는 quorum 큐를 확인합니다 |
| **Certificate checks** | 만료가 임박한 브로커 인증서를 표시합니다 |
| **Write actions** | **Allow writes**가 켜져 있고 각각 승인된 경우에만 큐와 exchange를 purge 또는 삭제하고, 일괄 정의 업데이트를 적용합니다 |

### 연결 검증

```text
Show the RabbitMQ cluster status and list every queue with its depth and consumer count
```

각 노드와 실행 상태에 이어, 큐별 ready 및 unacknowledged 수와 컨슈머 수가 담긴 큐 표가 표시됩니다.

### 예시 프롬프트

```text
Which RabbitMQ queues have messages but zero consumers right now?
The orders queue keeps growing. Find out why and check its dead-letter queue for poison messages
Is any RabbitMQ node in a memory or disk alarm, and do any certificates expire in the next 30 days?
```

## 쓰기 권한

**RABBITMQ_ALLOW_MUTATIONS**가 **Allow writes**로 설정되어 있고 사용자에게 적절한 vhost 권한이 있으면([필요 권한](#필요-권한) 참조), 에이전트는 다음을 할 수 있습니다:

- 큐 purge(큐의 모든 메시지 삭제)
- 큐 또는 exchange 삭제
- 브로커 정의에 일괄 업데이트 적용(`administrator` 필요)

각 작업은 개별적으로 [Approvals](/guide/approvals/overview)를 거치며, 읽기 작업에는 승인이 필요하지 않습니다.

<ApprovalDefault />

purge에는 큐에 대한 read 권한만 필요하므로 브로커 사용자가 이를 막지 못합니다. 쓰기를 켠다면 사람이 모든 변경을 승인하도록 **Manual**을 선택하세요. **Ask first** [Rule](/guide/approvals/rules)로 purge에만 대기를 걸 수도 있습니다.

<Warning>
큐를 purge하거나 삭제하면 메시지가 영구히 제거됩니다. RabbitMQ는 사본을 보관하지 않습니다. 승인하기 전에 승인 요청의 큐 이름과 vhost를 확인하세요.
</Warning>

## 문제 해결

<Accordion title="연결 거부 또는 시간 초과">
- CloudThinker가 `<host>:15672`(또는 TLS 관리 포트)에 접근할 수 있는지 확인합니다.
- AMQP 포트 `5672`가 아니라 관리 포트를 열었는지 확인합니다.
- 자체 호스팅 브로커에서는 관리 리스너가 `127.0.0.1`에만 바인딩되어 있지 않은지 확인합니다.
</Accordion>

<Accordion title="관리 API에서 404 Not Found">
관리 플러그인이 꺼져 있습니다. `rabbitmq-plugins enable rabbitmq_management`를 실행하고 다시 연결합니다. 관리형 브로커에서는 공급자가 해당 플랜에 Management HTTP API를 노출하는지 확인합니다.
</Accordion>

<Accordion title="401 Unauthorized">
- 사용자 이름과 비밀번호를 다시 확인합니다.
- 사용자에게 관리 태그가 있는지 확인합니다: `rabbitmqctl set_user_tags cloudthinker monitoring`. 태그가 없는 사용자는 AMQP로는 로그인할 수 있지만 관리 API는 거부합니다.
</Accordion>

<Accordion title="TLS 핸드셰이크 또는 인증서 오류">
**RABBITMQ_USE_TLS**와 **RABBITMQ_MANAGEMENT_PORT**가 일치해야 합니다. **Enabled**에는 HTTPS를 제공하는 포트(대개 `15671`)가, **Disabled**에는 일반 HTTP 포트(대개 `15672`)가 필요합니다.
</Accordion>

<Accordion title="호스트 필드 오류">
**RABBITMQ_HOST**에는 호스트 이름 또는 IP만 넣습니다. `http://`, `https://`, 경로, `:port`를 제거합니다. TLS와 포트에는 별도의 필드가 있습니다.
</Accordion>

<Accordion title="일부 큐 또는 vhost가 없음">
사용자에게 해당 vhost에 대한 read 권한이 없습니다. `rabbitmqctl set_permissions -p <vhost> cloudthinker "" "" ".*"`로 부여한 다음 다시 요청합니다.
</Accordion>

<Accordion title="purge 또는 delete가 거부됨">
**RABBITMQ_ALLOW_MUTATIONS**가 **Read-only**이거나, 브로커 사용자에게 작업에 필요한 vhost 권한(purge는 read, delete는 configure)이 없습니다. 허용하려던 쪽을 변경합니다. 작업은 여전히 Approvals를 거칩니다.
</Accordion>

## 보안

<ConnectionSecurity />

- **전용 사용자 사용**: 이 연결을 위해 `cloudthinker`를 만듭니다. `guest`나 개인 관리자 계정을 재사용하지 마세요.
- **TLS 켜기**: **RABBITMQ_USE_TLS**를 **Enabled**로 설정하면 CloudThinker와 브로커 사이에서 비밀번호와 브로커 데이터가 암호화됩니다.
