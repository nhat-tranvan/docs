CloudThinker는 계정에 대해 AWS CLI를 실행해 컴퓨팅, 스토리지, ID, 비용, 모니터링에 관한 질문에 답합니다. CloudThinker가 단기 자격 증명을 얻기 위해 맡는 IAM 역할로 연결하거나(권장), IAM 사용자의 액세스 키로 연결합니다.

## 사전 요구 사항

- IAM 역할(액세스 키 방식이라면 IAM 사용자)을 만들 수 있는 AWS 계정.
- 해당 계정의 [AWS CloudShell](https://console.aws.amazon.com/cloudshell/home) 접근 권한. 설정 스크립트가 그곳에서 실행되므로 아무것도 설치할 필요가 없습니다.
- 비용 질문과 [Optimize](/ko/guide/cost-optimization/overview)용: 계정에서 Cost Explorer가 켜져 있어야 합니다(**Billing and Cost Management → Cost Explorer → Launch Cost Explorer**, 조직이라면 관리 계정에서). 새 계정에서는 AWS가 활성화하는 데 최대 24시간이 걸릴 수 있습니다.
- AWS Organization에서는 서비스 제어 정책(SCP)을 확인하세요. 외부 주체의 `sts:AssumeRole`을 거부하는 SCP는 역할을 차단하고, 리전을 거부하는 SCP는 해당 리전을 에이전트에게 숨깁니다. 관리 계정에서 **AWS Organizations → AWS accounts → your account → Policies**에서 계정의 SCP를 나열하거나, `aws organizations list-policies-for-target --target-id <account-id> --filter SERVICE_CONTROL_POLICY`를 실행하세요.
- `ap-east-1`이나 `me-south-1` 같은 옵트인 리전은 AWS 콘솔의 **Account → AWS Regions**에서 활성화하기 전까지 에이전트에게 보이지 않습니다.

## 설정

먼저 연결 대화 상자를 여세요: **Settings → Workspace → Connections**로 이동해 **Amazon Web Services**를 선택하고 **Connect**를 클릭하세요. 그다음 대화 상자 상단에서 고른 방식의 탭을 따르세요.

<Tabs>
  <Tab title="Role-Based(권장)">
    대화 상자는 **External ID**(역할을 이 CloudThinker 워크스페이스에 묶어 confused-deputy 문제를 막는 고유 식별자. AWS는 이를 비밀 정보로 취급하지 않습니다)를 생성하고 그것을 바탕으로 설정 스크립트를 만듭니다.

    <Warning>
    **Connect**를 클릭할 때까지 대화 상자를 열어 두세요. 닫으면 External ID가 폐기되고, 새 대화 상자는 다른 ID를 생성하므로 이전 ID로 만든 역할은 일치하지 않습니다.
    </Warning>

    <Steps>
      <Step title="계정 이름 정하기">
        **Alias**(예: `production`)와 **Description**(예: `Production AWS account, main workloads`)을 입력하세요. 에이전트는 설명을 읽고 올바른 계정을 고릅니다. **Default AWS region**은 선택 사항이며 시작점일 뿐입니다: 에이전트는 역할이 접근할 수 있는 모든 리전을 사용할 수 있습니다.
      </Step>
      <Step title="CloudShell 열기">
        **Open CloudShell**을 클릭하고 연결할 AWS 계정에 로그인하세요.
      </Step>
      <Step title="설정 스크립트 실행하기">
        스크립트를 먼저 읽으려면 대화 상자에서 **View script**를 클릭하세요. 그다음 **Copy Script to Clipboard**를 클릭하고 CloudShell에 붙여 넣은 뒤 Enter를 누르세요. 스크립트는 다음을 수행합니다:

        1. `CloudThinkerAccessRole`이라는 역할이 이미 있으면 중지합니다.
        2. CloudThinker만, 그리고 External ID가 있을 때만 맡을 수 있는 신뢰 정책으로 `CloudThinkerAccessRole`을 만듭니다.
        3. AWS 관리형 `ReadOnlyAccess` 정책을 연결합니다.
        4. 역할의 ARN을 출력합니다.

        <Accordion title="실행 전에 검토할 전체 스크립트">
        대화 상자가 External ID와 CloudThinker 주체를 채워 넣습니다. 진행 메시지도 출력하지만 여기서는 생략했습니다.

        ```bash
        #!/bin/bash
        set -e
        ROLE_NAME="CloudThinkerAccessRole"

        # Stop if the role already exists
        if aws iam get-role --role-name "$ROLE_NAME" >/dev/null 2>&1; then
          echo "ERROR: Role '$ROLE_NAME' already exists!"
          exit 1
        fi

        # Trust policy: only the CloudThinker principal, only with your External ID
        cat > trust-policy.json <<'EOF'
        {
          "Version": "2012-10-17",
          "Statement": [
            {
              "Effect": "Allow",
              "Principal": { "AWS": "<CloudThinker principal shown in the dialog>" },
              "Action": "sts:AssumeRole",
              "Condition": { "StringEquals": { "sts:ExternalId": "<your External ID>" } }
            }
          ]
        }
        EOF

        aws iam create-role --role-name "$ROLE_NAME" \
          --assume-role-policy-document file://trust-policy.json \
          --description "Role for CloudThinker to access AWS resources"

        aws iam attach-role-policy --role-name "$ROLE_NAME" \
          --policy-arn arn:aws:iam::aws:policy/ReadOnlyAccess

        rm -f trust-policy.json
        aws iam get-role --role-name "$ROLE_NAME" --query 'Role.Arn' --output text
        ```
        </Accordion>

        출력의 끝은 다음과 같습니다:

        ```text
        ==========================================
          ✅ Setup Complete!
        ==========================================

        Copy this Role ARN and paste it in the connection form:

        arn:aws:iam::123456789012:role/CloudThinkerAccessRole
        ```
      </Step>
      <Step title="Role ARN을 붙여 넣고 연결하기">
        ARN을 **AWS Role ARN**에 붙여 넣으세요. **AWS External ID (Auto-generated)**는 그대로 두세요: 자동으로 채워지며 스크립트와 일치해야 합니다. **Connect**를 클릭하세요.

        **성공 상태:** 상태가 **Connecting**과 **Verifying**을 거쳐 계정에 **Connected** 상태가 표시됩니다. 이 계정에 Optimize가 아직 켜져 있지 않으면 CloudThinker는 deep look을 시작하는 대신 **Turn on Optimize?**를 묻습니다. **Turn on Optimize**를 클릭해 첫 비용 스캔을 시작하거나 **Not now**를 클릭합니다. 에이전트가 계정을 살펴보게 하려면 카드의 **More** 메뉴를 열고 **Try in chat**을 선택합니다. [연결 후 일어나는 일](/ko/guide/connections/overview#연결한-다음에-일어나는-일)을 참고하세요.
      </Step>
      <Step title="환경 설정하기">
        **Settings → Workspace → Connections**에서 **Amazon Web Services**를 열고, 계정 행의 연필 아이콘을 클릭한 뒤 **Edit Instance**에서 **Environment**를 설정하세요. 사람과 에이전트를 위해 계정에 라벨을 붙입니다. [환경 설정](/ko/guide/connections/overview#environment-설정)을 참고하세요.
      </Step>
      <Step title="확인 질문하기">
        채팅을 열고 [확인 질문](#연결-확인)을 하세요. 답변에 실제 12자리 계정 ID가 나와야 합니다.
      </Step>
    </Steps>

    Terraform이나 CloudFormation 등으로 역할을 직접 만들고 싶다면 대화 상자에서 **Manual steps**를 펼치세요. External ID와 CloudThinker 주체가 채워진 신뢰 정책이 표시됩니다. 주체는 모든 워크스페이스에서 같습니다. 대화 상자마다 바뀌는 것은 External ID뿐입니다. 수동 단계에서는 CloudThinker가 붙여 넣은 ARN을 사용하므로 어떤 역할 이름이든 쓸 수 있습니다. 형태는 다음과 같습니다:

    ```json
    {
      "Version": "2012-10-17",
      "Statement": [
        {
          "Effect": "Allow",
          "Principal": { "AWS": "<CloudThinker principal shown in the dialog>" },
          "Action": "sts:AssumeRole",
          "Condition": {
            "StringEquals": { "sts:ExternalId": "<your External ID>" }
          }
        }
      ]
    }
    ```

    두 값을 변수로 전달하는 Terraform의 같은 역할:

    ```hcl
    variable "cloudthinker_principal" {}
    variable "cloudthinker_external_id" {}

    resource "aws_iam_role" "cloudthinker" {
      name = "CloudThinkerAccessRole"
      assume_role_policy = jsonencode({
        Version = "2012-10-17"
        Statement = [{
          Effect    = "Allow"
          Principal = { AWS = var.cloudthinker_principal }
          Action    = "sts:AssumeRole"
          Condition = { StringEquals = { "sts:ExternalId" = var.cloudthinker_external_id } }
        }]
      })
    }

    resource "aws_iam_role_policy_attachment" "read_only" {
      role       = aws_iam_role.cloudthinker.name
      policy_arn = "arn:aws:iam::aws:policy/ReadOnlyAccess"
    }

    output "role_arn" {
      value = aws_iam_role.cloudthinker.arn
    }
    ```

    열린 대화 상자에서 두 값을 복사하고, `terraform apply`가 끝나 `role_arn` 출력을 **AWS Role ARN**에 붙여 넣을 때까지 대화 상자를 열어 두세요.

    대화 상자에 타이머는 없지만, External ID는 열린 브라우저 탭 안에만 존재합니다. 대화 상자를 닫거나 페이지를 새로 고치면 사라지며, External ID를 새 대화 상자로 되살릴 방법은 없습니다. 이는 `apply`가 몇 시간 뒤 CI에서 실행될 수 있는 풀 리퀘스트 리뷰 방식의 Terraform에 제약이 됩니다: 파이프라인이 끝날 때까지 대화 상자를 열어 두거나, 새 대화 상자를 시작하고 **Connect**를 클릭하기 전에 신뢰 정책의 External ID를 업데이트하세요.
  </Tab>
  <Tab title="Access Keys">
    조직이 교차 계정 역할을 허용하지 않을 때만 사용하세요. 액세스 키는 수명이 길어 직접 교체해야 합니다(예: 90일마다). [자격 증명 교체](/ko/guide/connections/overview#자격-증명-교체)를 참고하세요.

    <Steps>
      <Step title="계정 이름 정하기">
        대화 상자 상단에서 **Access Keys**를 선택하세요. **Alias**, **Description**, 그리고 선택적으로 **Default AWS region**을 입력하세요.
      </Step>
      <Step title="CloudShell에서 설정 스크립트 실행하기">
        **Open CloudShell**을 클릭한 다음 **Copy Script to Clipboard**를 클릭하고 CloudShell에서 실행하세요. 스크립트는 `CloudThinkerUser`라는 IAM 사용자를 만들고, `ReadOnlyAccess`를 연결하고, 액세스 키를 만든 뒤 `AWS_ACCESS_KEY_ID`와 `AWS_SECRET_ACCESS_KEY`를 출력합니다.

        AWS는 secret을 한 번만 보여주므로, 두 값을 대화 상자에 넣을 때까지 CloudShell을 열어 두세요. secret은 터미널 출력에 남으므로, 연결한 뒤 `clear`를 실행하고 CloudShell 세션을 닫으세요.
      </Step>
      <Step title="키를 입력하고 연결하기">
        `AWS_ACCESS_KEY_ID`를 **Access key ID**에, `AWS_SECRET_ACCESS_KEY`를 **Secret access key**에 붙여 넣고 **Connect**를 클릭하세요.

        **성공 상태:** 계정에 **Connected** 상태가 표시됩니다. 이 계정에 Optimize가 아직 켜져 있지 않으면 CloudThinker는 deep look을 시작하는 대신 **Turn on Optimize?**를 묻습니다. **Turn on Optimize**를 클릭해 첫 비용 스캔을 시작하거나 **Not now**를 클릭합니다. 에이전트가 계정을 살펴보게 하려면 카드의 **More** 메뉴를 열고 **Try in chat**을 선택합니다. [연결 후 일어나는 일](/ko/guide/connections/overview#연결한-다음에-일어나는-일)을 참고하세요.
      </Step>
      <Step title="환경 설정하기">
        **Settings → Workspace → Connections**에서 **Amazon Web Services**를 열고, 계정 행의 연필 아이콘을 클릭한 뒤 **Edit Instance**에서 **Environment**를 설정하세요. 사람과 에이전트를 위해 계정에 라벨을 붙입니다. [환경 설정](/ko/guide/connections/overview#environment-설정)을 참고하세요.
      </Step>
    </Steps>

    사용자는 `ReadOnlyAccess`를 받으므로 S3 객체도 읽을 수 있습니다. [필요한 권한](#필요한-권한)의 더 좁은 집합으로 바꾸려면 CloudShell에서 다음을 실행하세요:

    ```bash
    USER=CloudThinkerUser
    aws iam attach-user-policy --user-name $USER --policy-arn arn:aws:iam::aws:policy/job-function/ViewOnlyAccess
    aws iam attach-user-policy --user-name $USER --policy-arn arn:aws:iam::aws:policy/SecurityAudit
    aws iam put-user-policy --user-name $USER --policy-name CloudThinkerCostRead \
      --policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Action":"ce:Get*","Resource":"*"}]}'
    aws iam detach-user-policy --user-name $USER --policy-arn arn:aws:iam::aws:policy/ReadOnlyAccess
    ```

### 더 많은 계정 연결하기

각 AWS 계정은 별도의 연결입니다. **Amazon Web Services**에서 다시 **Connect**를 클릭하고, 계정에 고유한 별칭을 주고, 그 대화 상자의 스크립트를 새 계정의 CloudShell에서 실행하세요. 신뢰 정책이 해당 대화 상자에 표시된 External ID를 담도록 항상 완료하려는 대화 상자에서 스크립트를 복사하세요.

일괄 온보딩은 아직 지원되지 않습니다. 각 대화 상자가 자체 External ID를 생성하므로, StackSet이나 단일 Terraform apply로 여러 연결의 역할을 한 번에 만들 수 없습니다. 계정마다 자체 대화 상자와 자체 역할이 필요합니다. 계정이 많다면 위의 Terraform 모듈을 계정마다 한 번씩, 해당 계정의 열린 대화 상자 값으로 적용하는 것이 가장 빠릅니다.

AWS Organization 전체의 비용은 관리 계정을 연결하세요. 그러면 Optimize가 조직 전체 비용만 볼 수 있습니다. 에이전트는 멤버 계정의 리소스를 해당 계정의 자체 연결을 통해서만 봅니다.

## 연결 세부 정보

| 필드 | 방식 | 설명 | 예시 |
|---|---|---|---|
| **Alias** | 둘 다 | 이 계정의 짧은 이름. 비워 두면 자동으로 정해집니다. | `production` |
| **Description** | 둘 다 | 계정이 무엇인지. 에이전트가 계정을 고를 때 사용합니다. | `Production AWS account` |
| **Default AWS region** | 둘 다 | 선택적 시작 리전. 에이전트는 자격 증명이 허용하는 다른 리전도 사용할 수 있습니다. | `us-east-1` |
| **AWS Role ARN** | Role-Based | 설정 스크립트가 출력한 ARN | `arn:aws:iam::123456789012:role/CloudThinkerAccessRole` |
| **AWS External ID (Auto-generated)** | Role-Based | CloudThinker가 생성합니다. 읽기 전용이며 신뢰 정책과 일치해야 합니다. | 자동으로 채워짐 |
| **Access key ID** | Access Keys | IAM 사용자의 액세스 키 ID | `AKIA...` |
| **Secret access key** | Access Keys | IAM 사용자의 secret 키 | AWS가 한 번 표시 |

**Environment**(**Production**, **Staging**, **Development**, **Not set**)는 연결 대화 상자에 없습니다. 마지막 설정 단계처럼 연결한 뒤 설정하세요: 사람과 에이전트를 위해 계정에 라벨을 붙입니다. [승인 규칙](/guide/approvals/rules)은 이를 읽지 않으므로, 계정 하나를 다뤄야 하는 Rule은 해당 연결을 지정해야 합니다.

## 필요한 권한

설정 스크립트는 AWS 관리형 `ReadOnlyAccess` 정책을 연결합니다. 이 정책으로 에이전트는 여러 서비스의 리소스를 조회하고 나열하며, CloudWatch 지표와 Cost Explorer를 읽을 수 있습니다. 아무것도 생성, 변경, 삭제할 수 없습니다.

| 원하는 것 | 부여할 것 |
|---|---|
| 인벤토리, 상태, 보안 질문 | `ReadOnlyAccess`(스크립트가 연결하는 것) |
| Optimize 비용 데이터 | `ReadOnlyAccess`에 포함됩니다. 사용자 지정 정책이라면 `ce:Get*`를 추가하세요. |
| 에이전트가 특정 변경을 하게 하기 | 해당 작업만 역할에 추가한 다음 [쓰기 권한](#쓰기-권한)을 참고하세요 |

<Tip>
`ReadOnlyAccess`는 구성뿐 아니라 S3 객체 같은 데이터도 읽을 수 있습니다. 더 좁은 선택지는 AWS 관리형 `ViewOnlyAccess`와 `SecurityAudit`에 Optimize용 `ce:Get*` 읽기를 추가하는 것입니다. 리소스 나열과 조회는 다루지만, S3 객체 내용이나 로그 이벤트 같은 데이터 읽기는 다루지 않습니다. 권한이 없어도 계정 연결이 끊기지는 않습니다: 그 권한이 필요한 답변이 누락된 작업 이름과 함께 `AccessDenied`로 실패하므로, 그 작업만 인라인 정책에 추가하면 됩니다.
</Tip>

기존 역할을 더 좁은 집합으로 바꾸려면 CloudShell에서 다음을 실행하세요:

```bash
ROLE=CloudThinkerAccessRole
aws iam attach-role-policy --role-name $ROLE --policy-arn arn:aws:iam::aws:policy/job-function/ViewOnlyAccess
aws iam attach-role-policy --role-name $ROLE --policy-arn arn:aws:iam::aws:policy/SecurityAudit
aws iam put-role-policy --role-name $ROLE --policy-name CloudThinkerCostRead \
  --policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Action":"ce:Get*","Resource":"*"}]}'
aws iam detach-role-policy --role-name $ROLE --policy-arn arn:aws:iam::aws:policy/ReadOnlyAccess
```

Terraform에서는 `read_only` 연결을 그 두 정책 ARN의 연결과 `ce:Get*` 문을 담은 `aws_iam_role_policy`로 교체하세요.

## 에이전트 기능

| 영역 | CloudThinker가 하는 일 |
|---|---|
| **인벤토리** | 여러 리전의 컴퓨팅, 스토리지, 네트워킹, 관리형 서비스를 나열하고 조회합니다 |
| **ID** | 위험하거나 사용되지 않는 접근 권한이 있는지 IAM 역할, 사용자, 정책을 검토합니다 |
| **비용** | 서비스, 계정, 태그별로 지출을 분석하고 Reserved Instance와 Savings Plans 적용률을 확인합니다. [Optimize](/ko/guide/cost-optimization/overview)에 데이터를 제공합니다. |
| **모니터링** | CloudWatch 지표와 알람을 읽어 급증이나 장애를 설명합니다 |
| **변경** | **Allow writes**가 켜져 있고, 역할이 허용하고, 승인 설정이 허용할 때만 AWS CLI 쓰기를 실행합니다 |

## 쓰기 권한

연결 세부 정보 패널의 **Allow writes**는 에이전트가 AWS에서 무언가를 변경할 수 있는지 제어합니다. AWS에서는 기본적으로 켜져 있지만, 스크립트가 만드는 역할은 읽기 전용이므로 더 많은 권한을 부여하기 전까지 AWS 자체가 모든 쓰기를 거부합니다.

| IAM 권한 | Allow writes | 결과 |
|---|---|---|
| `ReadOnlyAccess`만 | 켜짐 또는 꺼짐 | 읽기 전용. AWS가 모든 변경을 거부합니다. |
| 추가 쓰기 작업 부여 | 꺼짐 | 읽기 전용. CloudThinker가 AWS에 도달하기 전에 모든 변경을 거부합니다. |
| 추가 쓰기 작업 부여 | 켜짐 | 에이전트가 변경을 제안할 수 있습니다. [Rules와 Approval mode](/guide/approvals/overview)가 각각을 결정합니다. |

CloudThinker에서도 쓰기를 잠그려면 **Settings → Workspace → Connections**에서 **Amazon Web Services**를 열고 세부 정보 패널의 **Allow writes** 스위치를 끄세요.

## 문제 해결

<Accordion title="스크립트에 CloudThinkerAccessRole이 이미 있다고 표시됩니다">
**원인:** 이 계정의 이전 설정이 역할을 만들었으며, 다른 External ID를 사용했을 가능성이 높습니다.

**해결:** 다른 CloudThinker 연결이 그 역할을 사용하지 않는다면 정책을 제거하고 역할을 삭제한 다음 새 스크립트를 실행하세요. 연결된 정책과 인라인 정책이 모두 없어지기 전까지 `delete-role`은 실패하므로 먼저 나열하세요:

```bash
ROLE=CloudThinkerAccessRole
aws iam list-attached-role-policies --role-name $ROLE
aws iam list-role-policies --role-name $ROLE
# For each attached policy ARN:
aws iam detach-role-policy --role-name $ROLE --policy-arn <policy-arn>
# For each inline policy name:
aws iam delete-role-policy --role-name $ROLE --policy-name <policy-name>
aws iam delete-role --role-name $ROLE
```

CloudThinker 연결이 아직 그 역할을 사용하는지 확인하려면 CloudTrail **Event history**를 열고 **Event name** = `AssumeRole`로 필터링한 뒤, 세션 이름이 `cloudthinker-`로 시작하는 `CloudThinkerAccessRole`의 최근 이벤트를 찾으세요. 있다면 External ID를 교체하지 마세요. 대신 **Manual steps**로 이 워크스페이스용으로 다른 이름의 두 번째 역할을 만드세요.
</Accordion>

<Accordion title="테스트가 sts:AssumeRole에서 AccessDenied로 실패합니다">
**원인:** 신뢰 정책이 CloudThinker가 제시하는 것과 일치하지 않습니다.

**확인:** 붙여 넣은 ARN이 스크립트가 출력한 것인지, 신뢰 정책의 `sts:ExternalId`가 대화 상자의 **AWS External ID (Auto-generated)**와 정확히 일치하는지 확인하세요.

**해결:** 테스트가 실패하면 연결은 저장되지 않습니다. 신뢰 정책을 고친 다음 External ID가 그대로 유지되도록 같은 대화 상자에서 다시 **Connect**를 클릭하세요. 대화 상자를 닫았다면 새 대화 상자에서 설정을 다시 실행하세요. **Retry**는 저장된 연결이 나중에 **Error**를 표시할 때만 나타납니다.
</Accordion>

<Accordion title="연결에 Error가 표시되고 예약된 작업이 멈췄습니다">
**원인:** 백그라운드 자격 증명 실패가 연속 세 번(삭제된 역할, 깨진 신뢰 정책, 취소된 키) 발생하면 연결이 **Error**로 바뀝니다. Optimize 비용 새로 고침, 예약된 automation, **Resolve → Signals**의 알림 폴링이 이 연결에 대해 일시 중지되며, 워크스페이스 관리자는 알림을 한 번 받습니다.

**해결:** AWS에서 역할이나 키를 복구한 다음 연결에서 **Retry**를 클릭하거나, **Replace credentials**로 새 키를 입력하세요. 상태가 **Connected**가 되면 예약된 작업은 다음 주기에 재개됩니다.
</Accordion>

<Accordion title="비용 질문에 데이터가 없습니다">
**확인:** AWS Billing 콘솔에서 Cost Explorer가 켜져 있고, 켠 지 24시간 이상 지났는지 확인하세요. AWS Organizations의 멤버 계정이라면 관리 계정이 멤버의 Cost Explorer 접근을 차단했을 수 있습니다.

**해결:** Cost Explorer를 켜거나, 관리 계정을 연결해 조직 전체의 비용을 보세요.
</Accordion>

<Accordion title="테스트에 Timed out이 표시됩니다">
**원인:** 테스트가 제시간에 끝나지 않았습니다. AWS 엔드포인트는 공개되어 있으므로 네트워크 문제인 경우는 드뭅니다.

**해결:** 다시 연결하세요. 계속 시간이 초과되면 [문의하세요](https://cloudthinker.io/contact).
</Accordion>

<Accordion title="리전이나 서비스가 명시적 거부와 함께 AccessDenied를 반환합니다">
**원인:** 서비스 제어 정책이 차단합니다. AWS 오류는 요청이 `with an explicit deny in a service control policy`로 거부되었다고 표시합니다. SCP가 `sts:AssumeRole`을 거부하면 테스트 자체가 실패합니다.

**확인:** [사전 요구 사항](#사전-요구-사항)에서처럼 계정의 SCP를 나열하세요.

**해결:** AWS Organizations 관리자에게 `CloudThinkerAccessRole`을 SCP에서 예외 처리해 달라고 요청하거나, 에이전트가 해당 리전이나 서비스를 볼 수 없다는 점을 받아들이세요.
</Accordion>


## 보안

<ConnectionSecurity />

- **역할을 우선 사용하세요.** CloudThinker는 AWS STS를 통해 역할을 맡아 단기 자격 증명을 받으므로 유출될 장기 비밀 정보가 없습니다. External ID는 다른 누구도 CloudThinker를 통해 역할을 사용하지 못하게 막습니다.
- **CloudTrail로 감사하세요.** 에이전트가 하는 모든 호출은 일반 AWS API 호출입니다. CloudThinker는 각 역할 세션의 이름을 `cloudthinker-<first 8 characters of your workspace ID>-<Unix timestamp>`로 지정하며, CloudTrail **Event history**는 그 세션 이름을 **User name**으로 표시합니다. 세션 전반의 모든 호출을 보려면 CloudTrail Lake나 Athena에서 `userIdentity.sessionContext.sessionIssuer.userName` = `CloudThinkerAccessRole`로 필터링하세요. 액세스 키라면 **Event history**를 **User name** = `CloudThinkerUser`로 필터링하세요.
