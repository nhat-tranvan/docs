HashiCorp Vault 클러스터를 연결하면 CloudThinker 에이전트가 봉인 상태와 클러스터 상태를 확인하고, 시크릿 경로에 무엇이 있는지 나열하고, 정책·인증 방법·감사 디바이스를 감사하고, [Approvals](/guide/approvals/overview)를 거쳐 단기 데이터베이스 또는 클라우드 자격 증명을 발급할 수 있습니다. 에이전트는 CloudThinker 관리형 샌드박스에서 공식 `vault` CLI를 실행하며, **token** 또는 **AppRole**(Vault가 단기 토큰으로 교환해 주는 role ID와 secret ID)로 로그인합니다.

## 사전 요구 사항

- 공개 DNS 이름이나 HCP Vault Dedicated 엔드포인트처럼 CloudThinker가 네트워크를 통해 접근할 수 있는 Vault 주소. `localhost`와 비공개 주소는 사용자의 네트워크가 아니라 CloudThinker가 명령을 실행하는 곳에서 해석됩니다. 방화벽 뒤의 Vault는 [Reaching private services](/ko/guide/connections/overview#비공개-서비스-접근)를 참조하세요.
- 정책을 작성하고 토큰 또는 AppRole을 만들 수 있는 권한.
- 연결을 추가하는 데 필요한 CloudThinker 워크스페이스의 **Admin** 역할. [역할](/guide/security/roles)을 참조하세요.
- Vault Enterprise 또는 HCP Vault Dedicated의 경우: 시크릿이 있는 네임스페이스. HCP는 기본적으로 `admin`을 사용합니다.

<Info>
워크스페이스에는 Vault 연결을 하나만 둘 수 있습니다. 에이전트가 접근할 수 있는 범위는 토큰 또는 AppRole에 연결된 정책이 허용하는 범위와 정확히 같습니다. 그 밖의 모든 것은 Vault가 기본적으로 거부합니다.
</Info>

## 인증 방법 선택

| 방법 | 사용하는 경우 | 장단점 |
|--------|-------------|-----------|
| **AppRole** | 프로덕션 클러스터 | 토큰을 다시 발급하지 않고 secret ID를 교체할 수 있습니다. 세션마다 로그인하여 새 단기 토큰을 받습니다 |
| **Token** | 체험 및 개발 클러스터 | 가장 빠르게 설정할 수 있습니다. 토큰은 TTL이 끝날 때까지 유효하므로 그 일정에 맞춰 교체합니다 |

## 설정

<Steps>
  <Step title="최소 권한 정책 작성">
    에이전트가 볼 경로에 대한 read와 list로 시작합니다. `secret`을 KV 마운트 이름으로 바꾸고 필요한 경로로 좁히세요. 이 예시는 KV v2 마운트를 가정합니다.

    ```bash
    vault policy write cloudthinker-read - <<EOF
    path "secret/data/*" {
      capabilities = ["read"]
    }
    path "secret/metadata/*" {
      capabilities = ["read", "list"]
    }
    path "sys/mounts" {
      capabilities = ["read"]
    }
    path "sys/auth" {
      capabilities = ["read"]
    }
    EOF
    ```

    `secret/data/*`에 대한 `read`는 토큰이 시크릿 값을 읽을 수 있게 합니다. CloudThinker는 값을 요청하지 않는 한 키 이름만 보여 주지만, 이는 Vault의 제한이 아니라 CloudThinker의 동작입니다. Vault가 이를 강제하게 하려면 `secret/data/*` 블록을 제거하세요. 에이전트는 여전히 경로를 나열하고 메타데이터를 읽을 수 있지만, 시크릿 안의 키는 나열할 수 없습니다.

    KV v1 마운트의 경우 두 `secret/` 블록을 `path "secret/*" { capabilities = ["read", "list"] }` 하나로 바꾸세요.

    정책 감사나 동적 자격 증명을 추가하려면 [필수 권한](#필수-권한)을 참조하세요.
  </Step>
  <Step title="자격 증명 만들기">
    <Tabs>
      <Tab title="AppRole">
        AppRole을 활성화하고(이미 켜져 있으면 건너뜀), 역할을 정책에 바인딩한 다음 role ID와 secret ID를 가져옵니다.

        ```bash
        vault auth enable approle

        vault write auth/approle/role/cloudthinker \
          token_policies=cloudthinker-read \
          token_ttl=1h \
          token_max_ttl=4h \
          secret_id_ttl=720h

        vault read auth/approle/role/cloudthinker/role-id
        vault write -f auth/approle/role/cloudthinker/secret-id
        ```

        출력에서 `role_id`와 `secret_id`를 복사합니다.
      </Tab>
      <Tab title="Token">
        정책에 바인딩된 토큰을 만듭니다.

        ```bash
        vault token create \
          -policy=cloudthinker-read \
          -ttl=720h \
          -display-name=cloudthinker
        ```

        출력에서 `token` 값을 복사합니다.
      </Tab>
    </Tabs>

    <Warning>
    두 예시 모두 30일(`720h`) 후에 만료됩니다. AppRole secret ID 또는 토큰이 작동을 멈추고 연결이 실패합니다. 알림을 설정한 다음, [보안](#보안)에 설명된 대로 새 값을 발급하고 연결을 업데이트하세요.
    </Warning>
  </Step>
  <Step title="CloudThinker에 연결 추가">
    **Settings → Workspace → Connections**를 열고 **HashiCorp Vault**를 선택합니다. **VAULT_ADDR**을 입력하고, Enterprise나 HCP를 사용하면 **Namespace**를 설정하고, **VAULT_AUTH_METHOD**에서 **AppRole** 또는 **Token**을 선택한 다음 나타나는 자격 증명 필드를 채웁니다. **Connect**를 클릭합니다.

    **성공 상태:** 연결에 **Connecting**과 **Verifying**이 표시된 다음 **Connected**가 표시됩니다. 토큰의 경우 CloudThinker가 `vault token lookup`을 실행합니다. AppRole의 경우 `auth/approle/login`으로 로그인하고 Vault가 토큰을 반환하는지 확인합니다.
  </Step>
</Steps>

## 연결 세부 정보

| 필드 | 필수 | 설명 | 예시 |
|-------|----------|-------------|---------|
| **VAULT_ADDR** | 예 | 스킴과 포트를 포함한 전체 Vault URL | `https://vault.example.com:8200` |
| **Namespace** | 아니요 | Enterprise 또는 HCP 네임스페이스. 오픈소스 Vault는 비워 둡니다 | `admin` |
| **VAULT_AUTH_METHOD** | 예 | **Token**(기본값) 또는 **AppRole** | **AppRole** |
| **VAULT_TOKEN** | Token 전용 | `vault token create`로 만든 토큰 | |
| **VAULT_ROLE_ID** | AppRole 전용 | AppRole `role_id` | |
| **VAULT_SECRET_ID** | AppRole 전용 | AppRole `secret_id` | |

## 필수 권한

필요한 행만 부여하세요. 각 행은 설정 단계의 정책에 경로를 추가합니다.

| 에이전트에게 원하는 작업 | 정책에 추가할 내용 |
|--------------------|-------------------|
| KV v2 시크릿의 키 나열 및 메타데이터 읽기 | `<mount>/data/*`에 `read`, `<mount>/metadata/*`에 `read`와 `list` |
| 시크릿 엔진과 인증 방법 나열 | `sys/mounts`와 `sys/auth`에 `read` |
| 정책 감사 | `sys/policies/acl`과 `sys/policies/acl/*`에 `read`와 `list` |
| AppRole 역할 나열 | `auth/approle/role`에 `list` |
| 감사 디바이스 나열 | `sys/audit`에 `read`와 `sudo` |
| 동적 자격 증명 발급 | `database/creds/readonly` 같은 `<engine>/creds/<role>`에 `read` |
| 리스 취소 또는 갱신 | `sys/leases/revoke`와 `sys/leases/renew`에 `update` |
| KV v2 시크릿 쓰기 또는 삭제 | 아래 예시 참조 |

`secret/myapp/` 아래의 KV v2 쓰기에는 다음을 추가합니다.

```hcl
path "secret/data/myapp/*" {
  capabilities = ["create", "update", "delete"]
}
path "secret/destroy/myapp/*" {
  capabilities = ["update"]
}
```

상태 확인(`sys/health`)과 호출자 자신의 토큰에 대한 `vault token lookup`은 Vault의 기본 제공 `default` 정책으로 작동하므로 추가할 필요가 없습니다.

<Tip>
읽기 전용으로 시작하세요. 필요한 워크플로가 있을 때만 쓰기 행을 추가하세요. 그 경우에도 모든 쓰기는 먼저 [Approvals](/guide/approvals/overview)를 거칩니다. **Manual**을 선택하면 모든 변경을 사람이 승인합니다. **Ask first** Rule을 사용하면 이를 Vault 연결에만 적용할 수 있습니다.
</Tip>

## 에이전트 기능

| 기능 | 에이전트가 할 수 있는 작업 | 승인 |
|------------|--------------------|----------|
| **Health** | 봉인 상태, 버전, 마운트된 시크릿 엔진, 인증 방법 확인 | 아니요 |
| **Secret discovery** | 경로와 시크릿이 가진 키를 나열하고 KV v1과 KV v2 구분 | 아니요 |
| **Policy audit** | 현재 토큰의 정책과 TTL 읽기, 정책 나열 및 읽기, 감사 디바이스와 AppRole 역할 나열 | 아니요 |
| **Dynamic credentials** | 시크릿 엔진에서 단기 데이터베이스 또는 클라우드 자격 증명 발급 | 예 |
| **Lease management** | 자격 증명 리스 취소 또는 갱신 | 예 |
| **Secret and config changes** | KV 버전 쓰기, 삭제, 파기, 정책 쓰기, 마운트·인증 방법·감사 디바이스 활성화 또는 비활성화 | 예 |

에이전트는 값을 요청하지 않는 한 시크릿 값이 아닌 키와 메타데이터를 보고하며, 토큰이나 secret ID를 출력하지 않습니다. 동적 자격 증명 발급은 Vault에서 읽기처럼 보이지만 리스를 만들기 때문에 CloudThinker는 이를 쓰기로 취급합니다. 쓰기는 실행되기 전에 [Approvals](/guide/approvals/overview)를 거칩니다.

### 연결 확인

```text
Check Vault health and seal status, and list the mounted secret engines and auth methods
```

봉인 상태, Vault 버전, `secret/`(KV v2) 같은 마운트 목록과 `approle/` 같은 인증 방법 목록이 표시됩니다.

### 예시 프롬프트

```text
Which keys does secret/myapp/config hold, and when was it last updated?
What policies and TTL does the current Vault token have?
Issue a database credential from the readonly role and tell me when the lease expires
```

## 문제 해결

<Accordion title="&quot;no such host&quot; 또는 connection refused로 연결 실패">
**VAULT_ADDR**이 CloudThinker가 접근할 수 없는 주소를 가리킵니다. `localhost`, `127.0.0.1`, 비공개 호스트 이름은 CloudThinker가 명령을 실행하는 곳에서 해석됩니다. 공개 DNS 이름이나 HCP 엔드포인트를 사용하세요. 방화벽이나 VPN 뒤의 Vault는 먼저 접근 가능한 엔드포인트나 허용 목록에 추가된 접근이 필요합니다.
</Accordion>

<Accordion title="unsupported protocol scheme">
주소에 스킴이 없습니다. `vault.example.com:8200`이 아니라 `https://vault.example.com:8200`을 사용하세요.
</Accordion>

<Accordion title="Invalid Vault token configuration 또는 Invalid Vault AppRole configuration">
선택한 인증 방법의 자격 증명 필드가 비어 있습니다. **Token**은 **VAULT_TOKEN**을, **AppRole**은 **VAULT_ROLE_ID**와 **VAULT_SECRET_ID**를 모두 채우세요.
</Accordion>

<Accordion title="403 permission denied">
Vault는 정책이 경로를 다루지 않을 때와 경로가 존재하지 않을 때 모두 403을 반환하므로, 403이 시크릿이 없다는 증거가 되지는 않습니다. 에이전트에게 토큰이 가진 정책을 물어본 다음 해당 경로에 `read` 또는 `list`를 추가하세요. KV v2에서 `secret/myapp`을 읽으려면 `secret/data/myapp`에 대한 정책이 필요합니다.

이전에 작동하던 요청이 이제 모두 403을 반환한다면 토큰이 만료되었을 가능성이 높습니다. 새 토큰을 발급하고 **VAULT_TOKEN**을 업데이트하세요.
</Accordion>

<Accordion title="HCP 또는 Enterprise에서 &quot;no handler for route&quot;">
**Namespace**가 비어 있거나 잘못되었습니다. 시크릿이 있는 네임스페이스로 설정하세요. HCP Vault Dedicated는 기본적으로 `admin`을 사용합니다.
</Accordion>

<Accordion title="invalid secret_id">
AppRole secret ID가 `secret_id_ttl`을 지났습니다. 새로 생성하여 [보안](#보안)에 설명된 대로 **VAULT_SECRET_ID**에 붙여 넣으세요.

```bash
vault write -f auth/approle/role/cloudthinker/secret-id
```
</Accordion>

<Accordion title="모든 요청이 실패하고 상태에 sealed: true가 표시됨">
클러스터가 봉인되어 있어 어떤 읽기나 쓰기도 성공할 수 없습니다. Vault 운영자가 `vault operator unseal`로 봉인을 해제해야 합니다.
</Accordion>

## 보안

<ConnectionSecurity />

- **자격 증명 교체**: Vault는 단일 연결 서비스이므로 연필 아이콘이 없습니다. 연결에 **Error**가 표시되는 동안 **Settings → Workspace → Connections**를 열고 **HashiCorp Vault**를 선택한 다음 **Replace credentials**와 **Replace…**를 클릭하고, 새 토큰 또는 secret ID를 붙여 넣고 **Save and test**를 클릭합니다. 테스트가 실패하면 연결은 이전 자격 증명을 유지합니다. 그 전에 교체하려면 연결을 끊고 새 값으로 다시 연결하세요. [Rotate a credential](/ko/guide/connections/overview#자격-증명-교체)을 참조하세요.
- **프로덕션에서는 AppRole 권장**: 각 세션은 설정한 TTL에 만료되는 토큰을 받고, 역할을 건드리지 않고 secret ID를 교체할 수 있습니다.
- **시크릿 값을 채팅에 두지 않기**: 에이전트는 기본적으로 키를 나열합니다. 값을 요청하면 대화에 표시되므로 필요할 때만 요청하세요.
- **더 이상 필요 없는 리스 취소**: 만료를 기다리지 말고 작업이 끝나면 에이전트에게 동적 자격 증명을 취소하도록 요청하세요.
