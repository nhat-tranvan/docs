Pulse는 보내 주는 것만 봅니다. 이 페이지에서는 하나의 알림 소스를 Pulse로 흐르게 하고, 그 소스에 의존하기 전에 제대로 동작하는지 확인하는 방법을 보여 줍니다.

## 사전 요구사항

- 워크스페이스 **Admin** 역할. Developer와 Viewer는 **Resolve → Triggers & Outcomes**를 볼 수 있지만 신호를 추가할 수는 없습니다. [Roles](/guide/security/roles)를 참조하세요.
- 웹훅을 추가하거나 테스트 알림을 보낼 수 있도록 알림을 생성하는 도구(예: CloudWatch, Datadog, Grafana)에 대한 접근 권한. 웹훅의 경우 도구가 HTTPS로 웹훅 URL에 도달할 수 있어야 합니다.
- AWS 폴링의 경우: 워크스페이스에 [AWS 연결](/ko/guide/connections/aws)이 있어야 합니다. 해당 AWS 계정의 최소 한 리전에서 AWS GuardDuty, AWS Config, AWS IAM Access Analyzer가 이미 켜져 있어야 합니다. CloudThinker는 이들을 읽기만 하며 켜지 않습니다.
- 채팅의 경우: CloudThinker에 연결된 Slack 또는 Microsoft Teams([Slack](/ko/guide/slack-integration), [Teams](/ko/guide/teams-integration)).

## 신호 경로 선택

알림은 세 가지 방법으로 Signals에 도달합니다. 웹훅과 폴링은 **Resolve → Triggers & Outcomes**에서, 채팅 채널은 **Resolve → On-call**에서 설정합니다. 도구가 지원하는 경로를 선택하세요.

| 신호 경로 | 표시 이름 | 적합한 경우 |
|---|---|---|
| 웹훅 | **Webhook** | 알림을 POST할 수 있는 모니터링 도구(EventBridge를 통한 CloudWatch, Datadog, Grafana, PagerDuty 등) 또는 **Custom source**를 통한 사내 시스템. |
| 폴링 | **Polling source** | CloudThinker가 대신 읽는 AWS 서비스: CloudTrail, AWS Health, AWS GuardDuty, AWS IAM Access Analyzer, AWS Config. |
| 채팅 | **Resolve → On-call**의 **Watch a channel** | 도구가 알림을 게시하거나 사람들이 이미 인시던트를 논의하는 Slack 또는 Teams 채널. |

[알림 소스 연결](/guide/incident/connect-alert-sources)은 도구를 이 경로 중 하나에 매칭하고, 설정 방법을 다루는 페이지를 알려 줍니다.

## 소스 연결

<Steps>
  <Step title="플랫폼 열기">
    **Resolve → Triggers & Outcomes**로 이동하여 플랫폼을 선택합니다. 목록이 길면 검색 필드를 사용하세요. 전용 카드가 없는 시스템이라면 **Custom source**를 선택합니다.
  </Step>
  <Step title="연결 확인">
    플랫폼에 계정이나 워크스페이스 연결이 필요하면 **Connection** 섹션에서 연결합니다. **Needs connection**으로 표시된 플랫폼은 연결이 끝날 때까지 신호를 추가할 수 없습니다.
  </Step>
  <Step title="신호 추가">
    **Signals to Resolve**에서 **Add signal**(또는 **Add another signal**)을 클릭하고 소스에 맞는 경로를 따릅니다.

    <Tabs>
      <Tab title="Webhook">
        1. **Custom source**의 경우 먼저 **Source name**을 입력하고 **Create endpoint**를 클릭합니다. **Webhook URL**과 **Secret Key**를 복사합니다. **Secret Key**는 한 번만 표시됩니다. 잃어버린 경우 행의 **⋯** 메뉴를 열고 **Regenerate credentials**를 클릭합니다. 그러면 **Webhook URL**과 **Secret Key**가 모두 교체되고 이전 쌍은 즉시 동작을 멈추므로, 도구에서 둘 다 업데이트하세요.
        2. 둘 다 모니터링 도구에 붙여 넣습니다. 시크릿은 도구가 지원하는 방식으로 각 호출을 인증합니다. 대화상자는 **Auth Method**에 따라 레이블을 붙입니다. **Bearer Token**은 **Secret Key**, **HMAC Signature**는 **HMAC Secret**, **API Key**는 **API Secret**입니다.

           | 방식 | 사용하는 곳 |
           |---|---|
           | Bearer 토큰 헤더 | **Custom source** 및 `Authorization: Bearer` 헤더를 보내는 도구 |
           | HMAC 서명 | PagerDuty처럼 웹훅에 서명하는 도구 |
           | API 키 헤더 | EventBridge를 통한 CloudWatch |

           [인증 선택](/ko/guide/incident/webhook-integrations/overview#인증-선택)에서 각 방식을 설명합니다. CloudWatch의 경우 EventBridge를 사용하는 [CloudWatch 연동 가이드](/ko/guide/incident/webhook-integrations/cloudwatch)를 따르세요.
        3. 도구에서 알림을 하나 보냅니다.
        4. 벤더 플랫폼의 경우 필드 매핑과 심각도 매핑이 미리 설정되어 있지만, 실제 페이로드와 비교해 확인하세요. 일부 프리셋은 도구가 보내는 값을 놓칩니다. [필드 매핑](/ko/guide/incident/webhook-integrations/overview#필드-매핑)의 Datadog 참고 사항을 확인하세요. **Custom source**의 경우 **Incident title**(필수), **Severity**, **Service**, **Resource**, **Description**을 담은 페이로드 필드를 클릭합니다. 경로는 `event.data.title`처럼 점으로 구분합니다. 앞의 `$.`는 선택 사항이며 제거됩니다.

        전체 가이드: [CloudWatch](/ko/guide/incident/webhook-integrations/cloudwatch) 및 [custom source](/guide/incident/webhook-integrations/custom-source).
      </Tab>
      <Tab title="AWS polling">
        각 AWS 서비스는 스위치가 있는 행으로 표시됩니다. Pulse가 읽을 서비스를 켭니다. AWS 연결이 둘 이상이면 각 행에 읽는 연결의 이름이 표시됩니다.

        | 서비스 | 폴링 주기(대략) |
        |---|---|
        | CloudTrail, AWS Health, AWS GuardDuty | 5분 |
        | AWS IAM Access Analyzer, AWS Config | 30분 |

        AWS 연결에는 켠 각 서비스에 대한 읽기 권한이 필요합니다. 권한은 [AWS 연결](/ko/guide/connections/aws)을 참조하세요.
      </Tab>
      <Tab title="Chat channel">
        채팅 채널은 여기서 추가하지 않습니다. **Resolve → On-call**로 이동하여 **Alert path**의 **Hears** 행에서 **Watch a channel**을 클릭합니다. 플랫폼과 채널을 고르고, **What gets posted there**(**Alerts from tools**, **Team chat** 또는 **Both**)를 선택한 다음 **Start watching**을 클릭합니다. 그 채널의 새 메시지는 각각 신호가 되며, 분류가 실행 가능 여부를 결정합니다. 예를 들어 `checkout-api is returning 502s since the 14:05 deploy`는 실행 가능할 가능성이 높지만, 점심 약속은 그렇지 않습니다.

        Slack에서는 메시지가 Resolve에 도달하도록 `@CloudThinker`를 채널에 초대하세요. Teams에서는 먼저 CloudThinker를 팀에 추가하세요. Resolve는 자신의 메시지를 건너뜁니다.
      </Tab>
    </Tabs>
  </Step>
  <Step title="테스트 알림 보내기">
    소스 도구에서 실제 알림이나 테스트 알림을 발생시킨 다음 **Resolve → Signals**를 열고 레인을 **History**로 설정합니다. 폴링되는 AWS 소스는 다음 폴링 이후에만 표시됩니다(AWS polling 탭 참조). 테스트를 다시 보낼 때는 제목을 바꾸거나 1분 기다리세요. Pulse는 이전 이벤트와 같은 분(minute)에 타임스탬프가 있는 정확한 사본을 버립니다. 웹훅의 경우 타임스탬프는 **Timestamp Path**가 가리키는 필드이며, 경로가 없으면 최상위 `timestamp` 키, 둘 다 없으면 Pulse가 받은 시간입니다. 따라서 도구가 원래 타임스탬프로 같은 이벤트를 다시 보낸다면 기다려도 소용없으니 제목을 바꾸세요.

    **성공 상태:** 알림이 클러스터로 나타나고, **Resolve → Triggers & Outcomes**에서 플랫폼에 **Ready**가 표시됩니다. Slack, Teams, Google Chat에서 **Ready**가 되려면 **Post incident updates**용 채널도 있거나, 그 아웃컴이 꺼져 있어야 합니다.
  </Step>
</Steps>

<Tip>
계정이 연결되었다고 해서 이벤트가 도착한다는 것이 증명되지는 않습니다. 소스에 의존하기 전에 항상 **Resolve → Signals**에서 신호 하나를 확인하세요.
</Tip>

## 동작을 바꾸는 웹훅 옵션

이 옵션을 편집하려면 플랫폼의 **Signals to Resolve** 섹션에서 웹훅을 엽니다.

| 설정 | 기본값 | 기능 |
|---|---|---|
| **Auto-investigate** | 켜짐 | 이 웹훅의 클러스터가 자동으로 트리아지와 조사로 넘어갑니다. 끄면 알림은 여전히 Signals에서 클러스터링되지만, 사람이 클러스터에서 **Open incident**와 **Send to triage**를 클릭할 때까지 아무것도 시작되지 않습니다. |
| **Only from a minimum severity** | 꺼짐 | 낮은 심각도의 알림도 클러스터로 묶이지만, 스스로 트리아지를 시작하지 않습니다. 켜면 **High and above**부터 시작합니다. **Critical only**, **High and above**, **Medium and above**, **Low and above**, **Info and above** 중에서 고를 수 있습니다. |
| **Send directly to CloudThinker** | 꺼짐 | Signals의 필터링과 그룹화를 건너뜁니다. 각 이벤트가 자체 트리아지 실행을 받고, 그 실행이 인시던트나 응답자가 필요한지 결정합니다. **AI auto-investigate**가 꺼져 있는 동안에도 각 이벤트는 상태가 **Open**인 인시던트를 생성하지만, 누군가 **Investigate**를 클릭할 때까지 트리아지 실행은 시작되지 않습니다. 모든 실행은 [크레딧](/ko/guide/billing/usage)을 사용하므로, 모든 이벤트가 중요한 저용량 소스에만 사용하세요. |

이 옵션은 **Resolve → Issues** 제목 행의 워크스페이스 **AI auto-investigate** 스위치와 조합됩니다. [조사를 시작하는 조건](/guide/incident/settings#what-starts-an-investigation)에서 모든 조합을 하나의 표로 보여 줍니다. 어느 경우든 사람이 클러스터에서 **Open incident**를, 인시던트에서 **Investigate**를 클릭할 수 있습니다.

## 준비 상태 배지 읽기

**Resolve → Triggers & Outcomes**의 각 플랫폼에는 연결부터 신호 행, 아웃컴까지 전체 설정을 요약하는 배지가 하나 있습니다. [준비 상태 읽기](/guide/incident/triggers-and-outcomes#read-readiness)에 모든 배지와 그 의미, 해야 할 일이 나열되어 있습니다.

신호 소스의 경우 **Ready**는 모든 연결과 소스 행이 설정되고 활성 상태라는 뜻입니다. 이벤트가 도착했다는 증거는 아니므로 **Resolve → Signals**에서 신호 하나를 확인하세요.

## 문제 해결

<AccordionGroup>
  <Accordion title="Signals에 여전히 No signals yet이 표시됨">
    **원인:** 소스가 보내지 않았거나 잘못된 URL로 보냈습니다. **확인:** 모니터링 도구의 전송 로그. **해결:** 웹훅 URL을 다시 붙여 넣고 테스트 알림을 보냅니다.
  </Accordion>
  <Accordion title="알림은 도착했지만 클러스터가 나타나지 않음">
    **원인:** 억제가 알림을 버렸습니다. 흔히 중복으로 처리된 경우입니다. 제목, 심각도, 리소스가 같고 이전 알림과 같은 분(minute)에 타임스탬프가 있는 경우입니다. **확인:** **Resolve → Signals** 상단의 퍼널. 원시 이벤트 수는 늘었지만 **History** 레인에 클러스터가 나타나지 않았다면 억제가 이벤트를 버린 것입니다. **해결:** 다른 알림을 보내거나 [노이즈 억제](/ko/guide/pulse/clusters#노이즈-억제)를 참조하세요.
  </Accordion>
  <Accordion title="Custom source 클러스터에 쓸모 있는 제목이 없음">
    **원인:** 필드 매핑이 잘못된 경로를 가리킵니다. **해결:** 웹훅을 편집하고 새 페이로드를 보낸 다음 필드를 다시 선택합니다.
  </Accordion>
  <Accordion title="AWS 폴링 행에 배지가 표시되고 켜지지 않음">
    **원인:** 그 뒤의 AWS 연결이 비정상이거나 권한이 부족합니다. **해결:** [AWS 연결](/ko/guide/connections/aws)을 확인하세요.
  </Accordion>
</AccordionGroup>
