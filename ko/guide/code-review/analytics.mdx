Review Insights는 머지된 풀 리퀘스트(PR)와 머지 리퀘스트(MR)를 팀 단위 수치로 바꿉니다. 누가 무엇을 출시했는지, 머지 시점에 얼마나 깔끔했는지, 어떤 종류의 발견 사항이 계속 돌아오는지 보여 줍니다. 주간 팀 리뷰나 1:1에서 코칭할 한 가지를 고르고, 각 수치 뒤에 있는 발견 사항으로 클릭해 들어가세요.

## 사전 요구 사항

- 최소 하나의 저장소에 Review가 연결되어 있고, 머지된 PR 또는 MR이 있어야 합니다. [Review 설정](/ko/guide/code-review/setup)을 참고하세요.
- Insights를 보려면 아무 워크스페이스 역할(Admin, Developer 또는 Viewer)이면 됩니다. 리포트 일정을 변경하려면 워크스페이스 **Admin** 역할이 필요합니다. [역할](/guide/security/roles)을 참고하세요.
- **Review Patterns** 탭의 경우: 이 탭은 Advanced Review만 세므로 리뷰 모드가 **Advanced** 또는 **Auto**로 설정되어 있어야 합니다. **Auto**에서는 Auto가 Advanced Review로 보낸 변경만 셉니다. [리뷰 모드](/ko/guide/code-review/setup#리뷰-모드-선택)를 참고하세요.

<Note>
Viewer를 포함하여 워크스페이스 역할이 있는 모든 사람이 개발자 이름이 포함된 리더보드를 볼 수 있으며, 이를 숨기는 설정은 없습니다. Review를 도입하기 전에 팀과 확인하세요.
</Note>

## Insights 열기

<Steps>
  <Step title="Insights로 이동">
    왼쪽 탐색에서 **Review**를 클릭한 다음 **Insights**를 클릭합니다. 페이지 헤더에 **Quality trends, patterns and contributions**가 표시됩니다.
  </Step>
  <Step title="기간 선택">
    오른쪽 상단의 **Date range** 메뉴를 엽니다. 기간은 세 그룹으로 나뉩니다.

    | 그룹 | 기간 | 추세 차트 단위 |
    |---|---|---|
    | **Daily** | Last 7 days(기본값), Last 14 days | 일 |
    | **Weekly** | This week, Last 4 weeks, Last 8 weeks, Last 12 weeks | 주 |
    | **Monthly** | Last 3 months, Last 6 months, Last 12 months | 월 |

    주는 월요일 00:00 UTC에 시작합니다. **This week**에는 추세가 없으므로 **Details**와 **Review Patterns** 탭이 숨겨집니다. 더 긴 기간을 고르면 다시 나타납니다.

    기간이 유일한 필터입니다. Insights는 항상 워크스페이스의 모든 저장소를 다룹니다. 저장소 하나만 보려면 **Reports** 탭의 PDF를 사용하세요.
  </Step>
  <Step title="탭 선택">
    | 탭 | 답하는 질문 |
    |---|---|
    | **Leaderboard** (기본값) | 누가 얼마나 출시했고, 머지 시점에 얼마나 깔끔했는가 |
    | **Details** | 기간 동안 지표 하나가 개발자별로 어떻게 움직였는가 |
    | **Review Patterns** | 개발자별로 어떤 발견 사항 영역이 리뷰된 변경에 가장 많이 영향을 주는가 |
    | **Reports** | 저장소별 PDF 리포트와 리포트가 추적하는 조치 |

    **성공 상태:** **Leaderboard**와 **Details** 상단에 요약 카드가 로드되고, 선택한 탭에 해당 기간의 데이터가 표시됩니다.
  </Step>
</Steps>

탭, 기간, 지표는 페이지 URL에 담기므로, 보기를 북마크하거나 팀 채널에 붙여넣으면 다른 사람도 같은 화면을 봅니다. Insights에는 CSV나 API 내보내기가 없습니다. URL이나 **Reports** 탭의 리포트 PDF를 공유하세요.

## 요약 카드

**Leaderboard**와 **Details**는 선택한 기간에 대한 카드 네 개로 시작합니다.

| 카드 | 세는 것 |
|---|---|
| **Active authors** | 기간 내 머지된 변경이 있는 개발자 |
| **Change requests** | 머지된 변경 |
| **Found in &lt;range&gt;**, 예: **Found in last 7 days** (기간에 이름이 없으면 **Found in period**) | 선택한 기간에 제기된 발견 사항 |
| **Team quality score** | CloudThinker가 머지된 각 변경에 매긴 리뷰 점수(1~10)의 평균. 높을수록 깔끔합니다 |

카드 아래 띠에는 최대 세 가지 신호가 추가되며, 각각 데이터가 있을 때만 표시됩니다.

| 신호 | 의미 |
|---|---|
| **avg to merge** | 변경을 연 시점부터 머지까지의 평균 시간 |
| **accurate findings** | 발견 사항에 대한 모든 좋아요와 싫어요 투표 중 좋아요의 비율 |
| **review rating** | 리뷰에 매겨진 평균 별점(5점 만점) |

기간 내 투표가 없으면 **accurate findings** 신호는 0%가 아니라 표시되지 않습니다. 이 수치를 원한다면 팀에 발견 사항 투표를 요청하세요.

## Leaderboard

**Developer Leaderboard**는 머지 시점에 매겨진 기여도와 품질로 개발자 순위를 정합니다. 점수는 변경이 머지될 때 고정되므로, 이후 발견 사항을 수정해도 과거 순위는 바뀌지 않습니다.

| 열 | 의미 |
|---|---|
| **Rank** | 선택한 기간에서의 순위 |
| **Move** | 이전 기간 대비 오르거나 내린 순위. 마우스를 올리면 어떤 기간과 비교하는지 표시됩니다 |
| **Developer** | 변경 작성자 |
| **Contribution score** | 팀 대비 Quality와 Impact의 평균. **1.00**이 팀 평균입니다 |
| **Change requests** | 머지된 PR 또는 MR |
| **Quality score** | 머지 시점 개발자 변경들의 평균 리뷰 점수(1~10) |
| **Impact** | 변경된 파일과 줄로 계산한 출시 변경의 총 규모 |
| **Findings** | 전체 발견 사항. 마우스를 올리면 Critical, High, Medium, Low 분포가 표시됩니다 |

봇 작성자는 모든 Insights 수치에서 제외됩니다. Review는 사용자 이름으로 봇을 식별합니다. GitHub `[bot]` 접미사, 끝에 붙은 `-bot`, `_bot` 또는 `.bot`, 또는 GitLab 프로젝트나 그룹 액세스 토큰 사용자입니다. 다른 이름을 가진 서비스 계정은 집계되며, 워크스페이스에서 계정을 제외할 수 없습니다.

### 점수 계산 방식

- **Impact**는 변경이 얼마나 많이 건드리는지를 반영합니다. 변경하는 파일과 추가 및 삭제하는 줄입니다.
- **Contribution score**는 개발자의 Quality score와 총 Impact를 팀 평균과 비교합니다. 약 1이면 팀과 비슷한 수준이고, 1보다 크면 팀보다 높습니다.

리더보드는 누구를 지원하고 무엇을 코칭할지 찾는 데 사용하세요. 성과 평가로 사용하지 마세요. Impact는 가치가 아니라 규모를 측정합니다.

## Details

**Details**는 기간 동안 개발자별 지표 하나를 차트로 보여 주고, 각 주 또는 월을 표로 나열합니다.

1. **Metric** 메뉴에서 지표를 선택합니다: **Contribution score**, **Quality score**, **Change requests** 또는 **Total impact**.
2. 예를 들어 **Quality score by Developer**라는 제목의 차트를 읽습니다.
3. 표로 스크롤하여 일, 주 또는 월별 팀 합계를 봅니다: **Change requests**, **Team quality**, **Total impact**, **Findings**, **Authors**.

하락이 한 기간의 일인지 추세인지 확인할 때 사용하세요.

## Review Patterns

**Review Patterns**는 코칭용 보기입니다. 개발자마다 리뷰된 변경이 네 가지 영역 각각에서 발견 사항 없이 머지된 빈도를 보여 줍니다.

| 영역 | 대상 |
|---|---|
| **Security** | 보안 취약점과 안전하지 않은 동작 |
| **Performance** | 느린 경로, 과도한 작업, 확장성 위험 |
| **Correctness** | 로직 오류와 놓친 엣지 케이스 |
| **Patterns** | 코드베이스 규칙과 유지보수 가능한 구조 |

### 집계 대상

결과가 기록된 변경에 대한, 완료되고 초안이 아닌 Advanced Review만 집계됩니다. Fast Review, 완료되지 않은 리뷰, 파이프라인 발견 사항, 봇 작성자는 제외됩니다. 해당하는 것이 없으면 탭에 **No confirmed Advanced Reviews in this period**가 표시됩니다.

영역 비율은 다음과 같습니다.

```text
changes with no finding in that domain / reviewed changes
```

변경은 여러 번 리뷰되었더라도 기간당 한 번만 집계됩니다. 한 영역에 발견 사항이 여러 개 있어도 그 변경은 한 번만 집계됩니다. 해결된 발견 사항과 열린 발견 사항은 똑같이 집계되며, 심각도는 비율에 가중치를 주지 않습니다.

### 주요 코칭 우선순위

탭 상단에는 팀 전체에서 영향을 받은 변경의 비율이 가장 높은 영역이 표시됩니다. 정확히 동률이면 Critical과 High 발견 사항 수로 결정합니다. 그것도 동률이면 동률인 모든 영역이 나열됩니다.

### 근거 살펴보기

<Steps>
  <Step title="셀 선택">
    영역 열에서 개발자의 셀을 클릭합니다.
  </Step>
  <Step title="추세 읽기">
    추세 차트가 해당 개발자를 합산된 **Team** 선과 비교하여 보여 줍니다.
  </Step>
  <Step title="발견 사항 열기">
    근거 목록에는 각 발견 사항이 최신순으로 심각도, 제목, 파일 위치, 변경 링크, **Open** 또는 **Resolved**와 함께 표시됩니다. 이전 항목은 **Load more evidence**를 클릭하고, 링크를 따라 변경으로 이동하세요.

    **성공 상태:** 개발자와 이야기하기 전에 비율 뒤에 있는 구체적인 발견 사항을 짚을 수 있습니다.
  </Step>
</Steps>

해결된 발견 사항도 근거에 남습니다. 리뷰가 무엇을 잡아냈는지 여전히 보여 주기 때문입니다.

### 데이터가 적을 때

| 표시 | 이유 |
|---|---|
| **Not enough data** | 개발자의 리뷰된 변경이 기간 내 3개 미만입니다. 그 변경도 **Team** 비율에는 집계됩니다 |
| **No data** | 해당 구간에 리뷰된 변경이 없습니다. 차트에 빈 구간이 표시됩니다 |
| **No findings in this period** | 선택한 모든 리뷰가 해당 영역에서 깔끔했습니다 |

## Reports

**Reports**는 매주 저장소마다 PDF 두 개를 제공합니다. 엔지니어와 기술 리드를 위한 **Technical PDF**와 제품 및 엔지니어링 리더를 위한 **Product PDF**입니다. 행은 기간별로 묶이며, 저장소당 한 행에 **Repository**, **Trends**, **Actions**, **Status**, **Generated**가 표시됩니다. 이 탭에서는 기간 컨트롤이 숨겨집니다.

<Steps>
  <Step title="리포트 실행 방식 선택">
    **Scheduled reports**를 켜면 매주 월요일 09:00 UTC부터 리포트가 생성됩니다(각 워크스페이스는 그 시각부터 30분 안에 시작). 오늘 실행하려면 **Generate now**를 클릭하세요. 일정을 변경하려면 워크스페이스 Admin 역할이 필요합니다.
  </Step>
  <Step title="리포트 읽기">
    행을 열면 **Repository report** 패널이 표시됩니다. "Findings down" 같은 **Trends**와 **Tracked actions**가 표시됩니다. Tracked actions는 이번 리포트와 이전 리포트의 조치이며, 각각 open, improved, resolved, regressed 또는 stale로 표시됩니다. 행에는 저장소의 상태도 표시됩니다: 10점 만점 점수와 함께 **Healthy**, **Watch** 또는 **At risk**, 또는 **Not rated yet**.
  </Step>
  <Step title="PDF 다운로드">
    패널에서 **Technical PDF** 또는 **Product PDF**를 다운로드합니다. 실패한 행에는 **Retry**가 있습니다.
  </Step>
</Steps>

첫 실행 전까지 탭에는 **No reports yet**이 표시됩니다. 예약 실행 후 워크스페이스 Admin은 **Reports ready** 알림을 받습니다. 일정을 꺼도 기존 리포트는 유지됩니다. Review는 그 주의 리뷰 활동을 담은 별도의 **Weekly Review digest** 이메일도 보냅니다. 둘 다 [알림 설정](/ko/guide/notifications)의 Review에서 관리하세요.

## 문제 해결

<AccordionGroup>
  <Accordion title="Details와 Review Patterns 탭이 없습니다">
    **This week**가 선택되어 있으며, 이 기간에는 추세가 없습니다. **Date range**에서 다른 기간을 고르세요.
  </Accordion>
  <Accordion title="Review Patterns에 No confirmed Advanced Reviews in this period가 표시됩니다">
    변경이 **Fast** 모드로 리뷰되었거나, 기간 내 완료된 리뷰가 없습니다. **Review → Settings**로 이동하여 **General** 섹션에서 **Review mode**를 **Advanced** 또는 **Auto**로 설정하세요. 그런 다음 새 변경이 머지되면 다시 확인하세요. 이전 Fast Review는 여기에 나타나지 않습니다.
  </Accordion>
  <Accordion title="개발자에게 Not enough data가 표시됩니다">
    기간 내 리뷰된 변경이 3개 미만입니다. 기간을 넓히거나 대신 **Team** 비율을 읽으세요.
  </Accordion>
  <Accordion title="리더보드가 비어 있거나 누군가 빠져 있습니다">
    Insights는 머지된 변경만 집계합니다. 열린 PR과 머지 없이 닫힌 PR은 나타나지 않으며, 봇 작성자도 마찬가지입니다. PR이 선택한 기간 안에 머지되었는지 확인하세요.
  </Accordion>
  <Accordion title="Review Patterns unavailable">
    계정에 이 워크스페이스의 Review 보기 권한이 없습니다. 워크스페이스 Admin에게 역할과 멤버십 확인을 요청하세요. [역할](/guide/security/roles)을 참고하세요.
  </Accordion>
  <Accordion title="패널에 Could not load가 표시됩니다">
    해당 패널에서 **Retry**를 클릭하세요. 기간과 탭은 선택된 상태로 유지됩니다.
  </Accordion>
</AccordionGroup>
