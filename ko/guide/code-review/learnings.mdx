Review는 모든 풀 리퀘스트(PR) 또는 머지 리퀘스트(MR)를 팀이 문서로 정한 기준과, 팀이 해결한 발견 사항에서 CloudThinker가 추출한 규칙에 비추어 확인합니다. 이 페이지에서는 각 소스를 켜는 방법, `BUSINESS.md`에 제품 고유의 규칙을 설명하는 방법, Review가 학습한 내용을 확인하는 방법, 더 이상 맞지 않는 규칙을 폐기하는 방법을 보여 줍니다.

<LearningsScene />

| 용어 | 작성자 | 설명 |
|---|---|---|
| **Learnings** | CloudThinker | 팀이 이미 해결한 리뷰 발견 사항에서 추출한 규칙 |
| **Learning sources** | 팀 | `AGENTS.md`처럼 저장소에 보관하는 규칙 파일 |
| **`BUSINESS.md`** | 팀 | 제품의 모듈과 그 모듈이 지켜야 하는 규칙(불변 조건)을 정리한 지도 |

## 사전 요구 사항

- [Review 설정](/ko/guide/code-review/setup)에서 연결되고 활성화되었으며 클론이 완료된 저장소.
- 일정, 소스, 규칙을 변경하려면 워크스페이스 **Admin** 역할. Developer와 Viewer는 Learnings를 읽을 수 있지만 변경할 수는 없습니다. [역할](/guide/security/roles)을 참고하세요.
- Learnings를 위해서는 해당 저장소의 해결된 발견 사항. 첫 실행은 최근 30일 동안 해결된 발견 사항을 돌아봅니다. 이후 실행은 이전 실행 이후 해결된 발견 사항을 읽습니다. Learning sources는 첫날부터 작동합니다.

## 소스 선택

| | Learnings (CloudThinker 작성) | Learning sources (직접 작성) |
|---|---|---|
| 규칙의 출처 | 팀이 해결한 발견 사항의 반복 패턴 | `AGENTS.md` 또는 `.cursorrules`처럼 팀이 작성한 파일 |
| 설정 | 저장소마다 Weekly 또는 Monthly 일정 켜기 | 없음. 자동으로 감지됩니다 |
| 적용 시점 | 실행이 충분한 근거를 찾은 뒤 | 다음 리뷰부터 |
| 적합한 경우 | 팀이 계속 손으로 고치는 실수 | 이미 문서로 정한 기준 |

둘은 독립적으로 작동합니다. 문서화된 기준과 실제 수정에서 Review가 잡아내는 패턴을 모두 원하면 둘 다 사용하세요. Learnings와 Learning sources는 Review 고유의 컨텍스트입니다. [CloudThinker 가르치기](/guide/teach-cloudthinker)에서 워크스페이스 메모리 및 스킬과 비교합니다.

## 저장소에 Learnings 켜기

<Steps>
  <Step title="저장소 목록 열기">
    **Review → Settings**로 이동하여 저장소 표에서 저장소를 찾습니다.
  </Step>
  <Step title="일정 선택">
    **Learnings** 열에서 **Weekly** 또는 **Monthly**를 선택합니다. **Off**는 해당 저장소의 새 Learnings를 중지합니다.

    **Review → Learnings**에서 시작할 수도 있습니다. 아직 일정이 있는 저장소가 없으면 페이지에서 **Enable weekly learning**을 제안합니다.
  </Step>
  <Step title="지금 실행 (선택 사항)">
    **Review → Learnings**로 이동하여 **Run now**를 클릭하고, 저장소를 고른 뒤 **Update review rules now** 다이얼로그에서 **Run now**를 클릭합니다. 일정이 있는 저장소만 선택기에 나타납니다.

    **성공 상태:** 페이지의 요약 줄에 **Running**이 표시되고, 실행이 끝나면 **Last run**이 표시됩니다.
  </Step>
</Steps>

예약 실행은 토요일에 진행되므로, 근무 주가 시작되기 전에 새 규칙이 적용됩니다. Weekly는 매주 토요일, Monthly는 매월 첫째 토요일에 실행됩니다. 각 저장소는 00:00 또는 12:00 UTC의 고정 슬롯을 받습니다. CloudThinker가 지정하며 변경할 수 없지만, **Run now**로 언제든 실행을 시작할 수 있습니다. **Review → Learnings**의 **Next run** 줄에 예정 시각이 표시됩니다. 실행은 보통 10분 안에 끝납니다.

각 Learning은 이 워크스페이스에서 한 저장소의 해결된 리뷰 발견 사항에서 나오며, 그 저장소에만 적용됩니다.

<Note>
실행이 새 Learnings 없이 끝날 수 있습니다. 신생 저장소에서는 정상입니다. CloudThinker는 같은 종류의 수정이 반복되는 것을 봐야 규칙을 작성합니다. 도달해야 할 고정 개수는 없으므로 발견 사항을 계속 해결하고 다음 실행 후 확인하세요.
</Note>

## CloudThinker가 학습한 내용 검토

**Review → Learnings**를 엽니다. 각 행은 하나의 Learning이며, 그 Learning을 만든 리뷰의 저장소로 범위가 정해집니다.

| 부분 | 표시 내용 |
|---|---|
| Learning | 평이한 말로 쓴 규칙과 그 아래의 카테고리: Security, Performance, Patterns 또는 Correctness |
| Repository | 규칙이 적용되는 저장소 |
| Signal | 최근 리뷰가 이 규칙에 얼마나 의존하는지(아래 참고) |
| Created | CloudThinker가 규칙을 작성한 시점 |

**Search learning name...**, **All categories**, **All signals**, **All repositories**로 필터링합니다.

| Signal | 의미 |
|---|---|
| Strong | 이 저장소의 리뷰에서 최근에 자주 인용됨 |
| Quiet | 켜져 있지만 Strong보다 덜 인용됨 |
| Weak | 최근에 인용되지 않음. 리뷰가 인용하지 않으면 곧 폐기됩니다 |
| Retired | 꺼짐. 리뷰가 더 이상 사용하지 않습니다 |

리뷰 발견 사항이 Learning을 참조하면 인용된 것입니다. 리뷰가 인용을 멈춘 Learning은 Weak가 되었다가 스스로 폐기되므로 규칙이 최신 상태로 유지됩니다.

행을 클릭하면 Learning이 열립니다. 규칙, **Citation trend**, 그리고 이를 참조한 리뷰 발견 사항으로 연결되는 **Recent citations**가 표시됩니다. 인용이 많은 Learning은 공용 헬퍼나 린트 규칙처럼 근본에서 고칠 가치가 있는 문제를 가리킵니다.

PR에서 Learning에 의존하는 발견 사항에는 `Cites Learning:`으로 시작하며 규칙 이름을 담은 줄이 붙습니다(여러 개이면 `Cites Learnings:`). **Review → Learnings**에서 그 이름을 검색하여 규칙을 확인하고, 잘못되었다면 폐기하세요.

Learning의 문구를 편집하거나 직접 만들 수는 없습니다. 규칙을 직접 추가하려면 규칙 파일에 작성하세요([자체 규칙 파일 추가](#자체-규칙-파일-추가) 참고).

## Learning 폐기 또는 복원

워크스페이스 Admin이라면, Review가 규칙을 적용하지 않기를 원할 때 행의 작업 메뉴에서 **Retire**를 선택합니다. 되돌리려면 **Restore**를 선택합니다. 폐기해도 규칙과 인용은 유지되므로 잃는 것이 없습니다.

CloudThinker는 30일 동안 어떤 리뷰도 인용하거나 다듬지 않은 Learning도 스스로 폐기합니다. Learning 세부 정보에 어느 쪽인지 표시됩니다: "Retired automatically" 또는 팀원 이름과 함께 "Retired by".

## 자체 규칙 파일 추가

Review는 팀이 이미 저장소에 보관하는 가이드라인 파일을 설정 없이 읽어 리뷰에 적용합니다. 인식하는 모든 경로는 다음과 같습니다.

| 도구 또는 범위 | 파일과 폴더 |
|---|---|
| 저장소의 모든 폴더 | `AGENTS.md`, `AGENTS.override.md`, `CLAUDE.md`, `GEMINI.md` |
| 저장소 루트 | `CONVENTIONS.md`, `.rules` |
| Cursor | `.cursorrules`, `.cursor/rules/*.mdc` |
| GitHub Copilot | `.github/copilot-instructions.md`, `.github/instructions/**/*.instructions.md` |
| Windsurf | `.windsurfrules`, `.windsurf/rules/**/*.md` |
| Cline | `.clinerules`, `.clinerules/**/*.md` |
| Roo | `.roorules`, `.roo/rules/**/*.md` |
| Continue | `.continuerules`, `.continue/rules/*.md` |
| Augment | `.augment-guidelines`, `.augment/rules/*.md` |
| Junie | `.junie/AGENTS.md`, `.junie/guidelines.md`, `.junie/guidelines/` |
| Amazon Q | `.amazonq/rules/*.md` |
| Kiro | `.kiro/steering/` |
| Trae | `.trae/rules/` |

변경이 파일을 건드리면 그 파일에 가장 가까운 규칙 파일이 우선하고, 그다음 저장소 루트의 파일이 적용됩니다. `services/payments/AGENTS.md`의 가이드라인은 결제 코드에 해당하고, 루트의 가이드라인은 모든 것에 해당합니다. 한 폴더 안에서는 `AGENTS.override.md`가 먼저 오고, 그다음 `AGENTS.md`, `CLAUDE.md`, `GEMINI.md` 순입니다.

Review는 이 파일들을 지침이 아니라 규칙의 근거로 다룹니다. 파일 안의 텍스트가 리뷰어에게 발견 사항을 건너뛰거나, 기준을 바꾸거나, 변경을 승인하라고 지시할 수 없습니다.

Review가 읽는 것을 보거나 확장하려면:

<Steps>
  <Step title="Learning sources 열기">
    **Review → Settings**에서 저장소의 작업 메뉴를 열고 **Learning sources**를 선택합니다.
  </Step>
  <Step title="찾은 항목 확인">
    **Detected sources**에 Review가 찾은 파일이 나열됩니다. Review가 매 리뷰 전에 새 파일을 확인하도록 **Detect sources automatically**를 켜 두세요. 꺼져 있으면 Review는 현재 목록을 그대로 유지하고 새 파일 추가를 멈춥니다. 사용자 지정 경로는 계속 적용됩니다.
  </Step>
  <Step title="사용자 지정 경로 추가">
    **Custom convention paths** 아래에 저장소 기준 상대 경로를 최대 10개 추가합니다. 예: `docs/style-guide.md`. 경로는 파일이나 `docs/standards/` 같은 폴더를 지정할 수 있고, `docs/**/*.md` 같은 glob 패턴을 사용할 수 있습니다. 경로는 `/`로 시작하거나, `..`를 포함하거나, `.claude/rules/`를 가리킬 수 없습니다. Review는 브랜치가 자체 규칙 파일을 리뷰어 정책으로 바꿀 수 없도록 이 폴더를 차단합니다. **Save**를 클릭하세요.

    **성공 상태:** **Save** 후 경로가 **Custom convention paths** 아래에 나열되고, 해당 저장소의 다음 리뷰가 이를 따릅니다.
  </Step>
</Steps>

## 비즈니스 규칙 설명

`BUSINESS.md`는 제품의 모듈과 그 모듈이 지켜야 하는 규칙(불변 조건)을 설명합니다. 예를 들어 어떤 플랜이 어떤 기능을 여는지입니다. Review는 Learnings 설정과 관계없이 이 파일을 읽습니다. 대상 브랜치의 저장소 루트에 두면 모든 리뷰가 변경을 이에 비추어 확인합니다. 파일 형식, 예시, 문제 해결은 [Business flow checks](/guide/code-review/business-flow)를 참고하세요.

## 문제 해결

<AccordionGroup>
  <Accordion title="Review → Learnings가 비어 있습니다">
    **Review → Settings**에서 저장소에 **Weekly** 또는 **Monthly** 일정이 있고 클론이 완료되었는지 확인하세요. **Last run**에 완료된 실행이 표시된다면, 저장소에 아직 패턴을 만들 만큼 해결된 발견 사항이 없는 것입니다. 발견 사항을 계속 해결하고 다음 예약 실행을 기다리세요.
  </Accordion>
  <Accordion title="Run now에 No scheduled repositories가 표시됩니다">
    **Run now**는 일정이 있는 저장소만 나열합니다. **Review → Settings**의 **Learnings** 열에서 일정을 설정한 뒤 다시 시도하세요.
  </Accordion>
  <Accordion title="Review가 꺼져 있는 동안 일정에 Paused가 표시됩니다">
    해당 저장소에서 Review가 꺼지면 Learnings가 일시 중지됩니다. 저장소에서 Review를 다시 켜면 일정이 재개됩니다.
  </Accordion>
  <Accordion title="Review가 가이드라인 파일을 무시합니다">
    **Learning sources**를 열고 파일이 **Detected sources** 아래에 있는지 확인하세요. 없다면 **Custom convention paths** 아래에 경로를 추가하세요.
  </Accordion>
  <Accordion title="Learning이 우리 코드베이스에 맞지 않습니다">
    행의 작업 메뉴에서 폐기하세요. Review는 다음 리뷰부터 적용을 멈추며, 나중에 복원할 수 있습니다.
  </Accordion>
</AccordionGroup>
