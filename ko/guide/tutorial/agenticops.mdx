이 튜토리얼을 마치면 CloudThinker가 Kubernetes 클러스터의 실제 증상 하나를 클라우드 계정과 최근 코드 변경을 거쳐 추적하고, 증거와 함께 근본 원인을 지목하고, 승인을 기다리는 수정을 제안하게 됩니다. **약 15분**이 걸립니다.

<Info>
**준비물:** 세 연결이 **Connected**로 표시된 워크스페이스([빠른 시작](/ko/quickstart)에서 하나를 만듭니다). [Kubernetes](/ko/guide/connections/kubernetes), [AWS](/ko/guide/connections/aws), [Google Cloud](/ko/guide/connections/gcp), [Azure](/ko/guide/connections/azure) 같은 클라우드 계정, 그리고 [GitHub](/guide/connections/github)나 [GitLab](/guide/connections/gitlab) 같은 코드 호스트입니다. 모든 단계에 읽기 전용 접근이면 충분합니다.

**Kubernetes만 연결되어 있나요?** 클라우드와 코드 단계를 건너뛰고 근본 원인 단계에서 클러스터 전용 프롬프트를 사용하세요. 프로덕션을 연결할 준비가 되지 않았나요? 읽기 전용 kubeconfig로 스테이징 클러스터를 연결하고([Kubernetes 단계](/ko/guide/connections/kubernetes)), 첫 프롬프트에서 *in the production namespace*를 빼고, 나열된 아무 pod나 따라가세요.
</Info>

아래의 모든 프롬프트는 일반 언어입니다. 전체 프롬프트 문법은 [CloudThinker Language](/guide/commands)를 참조하세요. 각 메시지는 [크레딧](/ko/guide/billing/usage)을 사용하며, 근본 원인 단계는 여러 서브에이전트를 실행하므로 더 많이 사용합니다.

## 조사 따라가기

아래 프롬프트는 `production` 네임스페이스의 `checkout`이라는 서비스를 사용합니다. 최근에 재시작했거나, 느렸거나, 오류를 낸 자신의 서비스로 바꾸세요. 실제 증상이 실제 답을 줍니다.

<Steps>
  <Step title="연결 확인">
    **Settings → Workspace → Connections**로 이동하여 Kubernetes, 클라우드, 코드 연결이 나열되어 있는지 확인합니다.

    **성공 상태:** 각 연결에 **Connected**가 표시됩니다. **Connection error**가 표시되면 계속하기 전에 그 연결 페이지에서 고치세요. 그렇지 않으면 CloudThinker가 그 레이어를 건너뜁니다.
  </Step>

  <Step title="이 채팅을 Manual로 전환">
    사이드바에서 **New chat**을 클릭합니다(또는 Home의 채팅 상자를 사용합니다). 무엇이든 보내기 전에, 프롬프트 상자 아래쪽 행에서 전송 버튼 바로 왼쪽에 있는 승인 컨트롤을 클릭합니다. **Approval for this chat**에서 **Manual**을 선택합니다. 이제 이 채팅의 모든 쓰기 작업은 **Approve**를 기다립니다.

    **성공 상태:** 승인 컨트롤에 **Manual**이 표시됩니다.
  </Step>

  <Step title="증상부터 시작">
    같은 채팅에서 다음을 보냅니다.

    ```text
    Which pods in the production namespace restarted in the last 24 hours? For each, show the restart count, the last termination reason, and the node it ran on.
    ```

    CloudThinker가 클러스터를 조회하고 pod 목록으로 답합니다. `OOMKilled`나 `CrashLoopBackOff` 같은 종료 사유를 찾고, 어떤 노드를 공유하는지 확인하세요.

    **성공 상태:** 답변에 일반적인 예시가 아니라 자신의 클러스터의 pod와 노드 이름이 나옵니다.
  </Step>

  <Step title="클라우드 레이어 추가">
    같은 대화를 이어갑니다. pod 이름을 반복할 필요는 없습니다.

    ```text
    For the nodes those pods ran on, check the cloud instance metrics and events over the same window: CPU, memory, disk, and any maintenance or scaling events.
    ```

    CloudThinker는 Kubernetes 노드를 클라우드 인스턴스에 매핑하고 해당 메트릭과 이벤트를 가져옵니다. 이는 EKS, GKE, AKS 클러스터처럼 노드가 연결한 클라우드 계정에서 실행될 때 동작합니다. 온프레미스 노드처럼 그렇지 않은 경우 CloudThinker는 인스턴스에 매핑할 수 없습니다. 코드 단계로 건너뛰세요.

    **성공 상태:** 답변이 최소 하나의 노드를 클라우드 계정의 특정 인스턴스와 연결하고, 요청한 시간 범위의 수치를 보여 줍니다.
  </Step>

  <Step title="코드에서 바뀐 것 확인">
    ```text
    What changed in acme/checkout in the last 3 days? List merged pull requests and commits that touch resource limits, memory use, or the deployment config.
    ```

    위처럼 저장소를 `owner/name` 형식으로 바꾸세요. 이것이 확실한 방법입니다. 코드 연결이 여러 개라면 `#`를 입력하고 올바른 연결도 고르세요. 모노레포라면 *under services/checkout* 같은 경로를 추가하세요.

    CloudThinker는 코드 연결을 통해 저장소를 읽고, 작성자, 시간, 한 줄 요약과 함께 변경 사항을 나열합니다.

    **성공 상태:** 알아볼 수 있는 풀 리퀘스트나 커밋이 보이며, 각각 첫 재시작과 맞춰 볼 수 있는 타임스탬프가 있습니다.
  </Step>

  <Step title="하나의 근본 원인 요청">
    이제 CloudThinker에게 세 레이어를 종합하도록 요청합니다.

    ```text
    Combine what you found across the cluster, the cloud metrics, and the code changes. Give me the most likely root cause, the evidence for it, and anything that rules out the alternatives.
    ```

    Kubernetes 전용 경로라면 대신 다음을 보냅니다. *Using the pod events, logs, resource limits, and recent rollouts, give me the most likely root cause, the evidence for it, and anything that rules out the alternatives.*

    이런 요청에서 CloudThinker는 각 레이어를 병렬로 확인하기 위해 [서브에이전트](/ko/guide/agents/overview#서브에이전트)를 생성하는 경우가 많습니다. 채팅에 **Spawn Subagents**가 표시되며, 사이드 패널의 **Agents** 탭에서 각 서브에이전트를 따라갈 수 있습니다.

    **성공 상태:** 원인을 지목하고(예: 최근 병합에서 낮아진 메모리 한도와 이어진 같은 pod의 `OOMKilled` 재시작), 각 레이어의 증거를 인용하고, 무엇을 배제했는지 말하는 하나의 답변.
  </Step>

  <Step title="제안된 수정 검토">
    ```text
    Propose a fix for this root cause. Show the exact change and what it will affect before you do anything.
    ```

    CloudThinker가 배포 패치나 한도를 복원하는 풀 리퀘스트 같은 변경을 설명합니다. Manual에서는 모든 쓰기 작업이 작업 카드에서 기다립니다. 웹 앱에서는 **Approve**, **Approve and draft rule**, **Decline**이 표시됩니다. Google Chat은 자체 버튼 **Approve**, **Approve with reason**, **Reject**를 표시합니다. Slack과 Microsoft Teams는 Resolve 인시던트 채널에서만 **Approve**와 **Reject**를 표시합니다. 다른 곳에서는 **View in CloudThinker** 링크를 게시하며, 웹 앱에서 결정합니다.

    보이는 것은 연결에 따라 다릅니다.

    - **읽기 전용 역할, Allow writes 켜짐:** 카드가 나타납니다. 승인하면 제공자가 쓰기를 거부하고 채팅에 오류가 표시됩니다. 아무것도 바뀌지 않습니다.
    - **Allow writes 꺼짐:** 카드가 나타나지 않습니다. CloudThinker가 제공자를 호출하기 전에 쓰기를 거부합니다.

    수정을 실행하려면 연결의 권한을 넓히고 상세 패널에서 **Allow writes**를 켜세요. [접근 방식](/ko/guide/connections/overview#접근-권한이-작동하는-방식)을 참조하세요.

    <Warning>
    승인하면 실제 시스템에 변경이 실행됩니다. 프로덕션 클러스터에서는 지금은 **Decline**을 클릭하세요. CloudThinker에게 평소 리뷰를 통해 적용할 수 있는 diff로 변경을 요청하거나, 코드 연결에 쓰기 권한이 있다면 풀 리퀘스트를 열도록 요청하세요.
    </Warning>

    **성공 상태:** 정확한 변경을 확인하고 결정을 내렸습니다. 승인했다면 대화에 결과가 표시됩니다. 거부했다면 아무것도 바뀌지 않았습니다.
  </Step>

  <Step title="정리하기">
    ```text
    Summarize this investigation as an incident write-up: timeline, root cause, evidence, fix, and follow-up actions.
    ```

    **성공 상태:** 사실을 고치지 않고 티켓이나 포스트모템에 붙여 넣을 수 있는 보고서. 이 채팅에 남아 있습니다. 팀원에게 보내려면 [공유](/guide/sharing)를 참조하세요. [Jira가 연결](/ko/guide/connections/atlassian)되어 있다면 CloudThinker에게 Jira 이슈로 등록하도록 요청할 수 있습니다. 이것은 쓰기 작업이므로 승인을 기다립니다.
  </Step>
</Steps>

## 완료 기준

- [x] CloudThinker가 자신의 환경에서 pod, 노드, 인스턴스, 커밋의 이름을 댔습니다
- [x] 하나의 답변이 증거와 함께 단일 근본 원인을 지목했습니다(세 레이어 모두에서, 또는 Kubernetes 전용 경로에서는 클러스터만으로)
- [x] 제안된 변경을 보고 승인하거나 거부했습니다
- [x] 조사의 서면 요약이 있습니다

## 문제 해결

<AccordionGroup>
  <Accordion title="CloudThinker가 클러스터, 계정 또는 저장소에 도달할 수 없다고 함">
    연결이 없거나, 오류 상태이거나, 읽기 권한이 없습니다. **Settings → Workspace → Connections**를 열고 상태를 확인한 다음, 그 연결 페이지의 문제 해결 섹션을 따르세요.
  </Accordion>
  <Accordion title="답변이 내 환경이 아닌 일반적인 내용임">
    프롬프트에 대상(네임스페이스, 리전 또는 저장소)을 명시하거나 `#`를 입력하고 연결을 고르세요. 클러스터나 계정이 여러 개라면 CloudThinker가 다른 것을 봤을 수 있습니다.
  </Accordion>
  <Accordion title="최근 24시간 동안 재시작한 것이 없음">
    범위를 넓히거나("in the last 7 days") 느린 응답이나 5xx 오류 급증 같은 다른 증상에서 시작하세요. 나머지 단계는 같은 방식으로 동작합니다.
  </Accordion>
  <Accordion title="승인 카드가 나타나지 않았는데 변경이 실행됨">
    먼저 프롬프트 상자의 승인 컨트롤이 여전히 **Manual**인지 확인하세요. 이 설정은 하나의 채팅에만 적용되므로, 새 채팅은 **Chat** 실행 유형의 모드로 시작합니다(관리자가 [Approval mode](/guide/approvals/approval-mode#set-a-mode-for-a-run-type)에서 **Chat**에 재정의를 설정하지 않았다면 워크스페이스 모드). **Auto** 모드가 표시되면 워크스페이스의 Approvals가 묻지 않고 그 작업을 실행하도록 허용한 것입니다. 프로덕션에서 수정을 실행하기 전에 [Approval mode](/guide/approvals/approval-mode)와 [규칙](/guide/approvals/rules)을 검토하세요.
  </Accordion>
</AccordionGroup>
