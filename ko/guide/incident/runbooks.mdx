**runbook**은 "checkout 파드 재시작"이나 "데이터베이스 페일오버"처럼 알려진 문제를 고치기 위한 작성된 절차입니다. runbook을 Resolve에 연결하면 CloudThinker가 근본 원인 분석(RCA) 중에 이를 읽고, 즉흥적으로 만들어 내는 대신 일치하는 수정을 제안합니다.

<Note>
**Legacy.** Runbooks에는 사이드바의 이름 옆과 페이지 상단에 **Legacy** 레이블이 붙어 있습니다. 여기 설명된 대로 작동하며, 대체 기능이나 제거 일정은 발표되지 않았습니다. 연결된 소스는 Confluence, GitHub 또는 GitLab에 그대로 남으므로, 이 페이지가 어떻게 되든 절차는 계속 사용할 수 있습니다. 여기에 얼마나 투자할지 결정 중이라면 [support@cloudthinker.io](mailto:support@cloudthinker.io)에 문의하세요.
</Note>

## 작동 방식

1. **runbook source**를 추가합니다: Confluence 스페이스, GitHub 또는 GitLab 저장소, 또는 업로드한 Markdown 파일.
2. [근본 원인 분석](/ko/guide/incident/root-cause-analysis) 중에 CloudThinker가 활성화된 소스에서 발견한 문제에 맞는 절차를 검색합니다.
3. 절차에 무언가를 변경하는 명령이 포함되어 있으면, 모든 에이전트 쓰기와 마찬가지로 각 변경이 워크스페이스의 [Approvals](/guide/approvals/overview)를 거칩니다. 사람이 결정해야 하면 실행이 승인을 기다리며, 인시던트는 **Resolve → Issues**의 **Approval needed** 필터에 해당합니다.
4. 모든 시도는 정책 결정, 승인, 결과와 함께 **Execution history** 탭에 기록됩니다.

<ApprovalDefault />

읽기 전용 명령(`kubectl get pods`처럼 보기만 하는 명령)은 업로드든 연결된 소스든 runbook 승인을 기다리지 않습니다. `kubectl rollout restart`처럼 인프라를 변경하는 명령은 Approvals를 거칩니다. runbook 자체의 효과가 어떻게 적용되는지는 [명령 효과 제어](#명령-효과-제어)에서 설명합니다.

## CloudThinker가 runbook을 찾는 방법

CloudThinker는 발견한 문제의 설명으로 활성화된 각 소스를 검색합니다.

| 소스 | 검색 방식 |
|---|---|
| **Confluence** | 설정한 스페이스와 레이블의 페이지를 전문 검색합니다. 영향받는 서비스를 언급하는 페이지가 먼저 정렬됩니다. |
| **GitHub**, **GitLab** | 브랜치(기본값 `main`)에서 **Path Prefix** 아래의 **File Patterns**와 일치하는 파일을 나열하고, 읽고, 각 파일의 관련성을 판단합니다. 영향받는 서비스를 언급하는 파일이 먼저 정렬됩니다. |
| **Upload** | 하나를 고를 때 각 업로드의 처음 200자를 봅니다 |

CloudThinker는 활성화된 모든 소스에서 후보를 모은 다음, 수정을 계획하기 전에 가장 잘 맞는 후보를 읽습니다.

따라서 runbook은 알림이 읽히는 방식대로 작성하세요. 제목과 첫 줄에 증상과 서비스 이름을 넣으세요. 예를 들어 `# Procedure 7`이 아니라 `# checkout-api pods in CrashLoopBackOff`처럼 씁니다. 업로드의 경우 CloudThinker가 고를 때 보는 내용은 대부분 그 첫 줄입니다. 페이지나 파일 하나에 절차 하나를 쓰세요.

## 명령이 실행되는 곳

runbook 명령은 다른 에이전트 명령과 마찬가지로 대상 시스템의 [connection](/ko/guide/connections/overview)을 통해 그 연결의 자격 증명과 권한으로 실행됩니다. 자격 증명이 범위를 정합니다. 읽기 전용 자격 증명은 runbook에 무엇이 적혀 있든 쓸 수 없으며, **Allow writes**가 꺼진 연결도 쓰기를 거부합니다. 모든 쓰기는 절대 실행되지 않는 호출 목록을 포함하여 [Approvals](/guide/approvals/overview#how-a-write-is-decided)도 거칩니다. 명령이 실행되는 머신에 대해서는 [Where agents run](/ko/guide/security/overview#에이전트가-실행되는-곳)을 참조하세요.

## 사전 요구 사항

- 소스를 추가, 편집, 게시, 삭제하려면 워크스페이스 **Admin** 역할. Developer와 Viewer는 소스와 **Execution history**를 볼 수 있습니다. [역할](/guide/security/roles)을 참조하세요.
- runbook 작업의 승인자는 Admin 역할이 아니라 Approvals 설정을 따릅니다. [approvers](/guide/approvals/approvers)를 참조하세요.
- Confluence, GitHub, GitLab의 경우: runbook을 읽을 수 있는 작동 중인 연결. 연결이 없으면 소스 양식을 저장할 수 없습니다.
  - Confluence: [Atlassian connection](/ko/guide/connections/atlassian#필수-권한)을 승인한 계정이 해당 스페이스를 열 수 있어야 합니다.
  - GitHub: CloudThinker 앱이 [저장소에 설치](/guide/connections/github#required-permissions)되어 있어야 합니다.
  - GitLab: 로그인한 사용자나 액세스 토큰이 프로젝트를 읽을 수 있어야 합니다. [GitLab permissions](/guide/connections/gitlab#required-permissions)를 참조하세요.
- 업로드의 경우: 명령이 펜스 코드 블록에 들어 있는 `.md` 파일 형식의 절차.

## 소스 유형 선택

| 소스 유형 | 적합한 경우 | 좁힐 수 있는 항목 |
|---|---|---|
| **Confluence** | runbook이 위키 스페이스에 있을 때. | **Confluence Space Key**(비우면 모든 스페이스 검색)와 **Labels** |
| **GitHub** | runbook이 저장소의 파일일 때. | **Repository**, **Branch**, **Path Prefix**, **File Patterns** |
| **GitLab** | GitHub와 같으며, GitLab에 있을 때. | **Repository**, **Branch**, **Path Prefix**, **File Patterns** |
| **Upload a runbook** | 절차가 몇 개뿐이고 이를 위한 위키나 저장소가 없을 때. | 좁힐 것이 없습니다. CloudThinker가 파일을 워크스페이스에 저장합니다 |

연결된 소스는 원래 시스템에 그대로 있습니다. CloudThinker는 RCA 시점에 이를 읽으므로, Confluence의 편집이나 Git에 병합된 변경은 다시 동기화하지 않아도 다음 조사에 반영됩니다.

소스를 추가하기 전에 runbook source가 그 절차를 두기에 적절한 곳인지 확인하세요. [Teach CloudThinker](/guide/teach-cloudthinker)에서 runbook source를 CloudThinker를 가르치는 다른 방법과 비교합니다.

## Confluence, GitHub 또는 GitLab 소스 연결

<Steps>
  <Step title="Runbooks 열기">
    사이드바에서 **Resolve → Runbooks**(**Configuration** 아래)를 엽니다. 페이지에는 **Runbook sources**와 **Execution history** 두 탭이 있습니다. 아직 소스가 없으면 페이지에 각 소스 유형이 나열됩니다. 연결된 유형은 연결 이름을, 연결되지 않은 유형은 **Connect first**를 표시합니다.
  </Step>
  <Step title="소스 추가">
    **Add source**(또는 빈 상태의 소스 유형)를 클릭합니다. **Add Runbook Source**에서 `SRE Runbooks` 같은 **Source Name**을 입력하고, **Source Type**을 고르고, 연결을 선택합니다.
  </Step>
  <Step title="CloudThinker가 검색할 범위 좁히기">
    Confluence는 `SRE` 같은 **Confluence Space Key**와 필요한 **Labels**를 설정합니다. GitHub나 GitLab은 **Repository**를 고른 다음, 선택적으로 **Branch**, `docs/runbooks` 같은 **Path Prefix**, `*.md` 같은 **File Patterns**를 설정합니다. **Add Source**를 클릭합니다.
  </Step>
</Steps>

**성공 상태:** 소스가 `GitHub · acme/runbooks · docs/runbooks`처럼 유형과 범위와 함께 목록에 나타나고, 토글이 켜져 있습니다.

CloudThinker는 연결된 페이지에서는 업로드처럼 명령을 추출하거나 분류하지 않습니다. 양식의 안내에는 소스의 모든 명령에 승인이 필요하다고 적혀 있습니다. 실제로는 변경을 만드는 모든 명령을 의미합니다. 읽기 전용 명령은 runbook 승인 없이 실행되고, 변경은 워크스페이스의 Approvals를 거칩니다. 이 소스들에는 명령별로 설정할 효과가 없습니다.

## Markdown runbook 업로드

<Steps>
  <Step title="업로드 대화 상자 열기">
    **Resolve → Runbooks**에서 **Upload runbook**(또는 빈 상태의 **Upload a runbook**)을 클릭합니다.
  </Step>
  <Step title="파일 추가">
    각각 최대 5 MB인 `.md` 파일을 최대 20개까지 끌어다 놓습니다. 각 파일에는 업로드 전에 편집할 수 있는 **Runbook name**이 지정됩니다.
  </Step>
  <Step title="업로드">
    **Upload**를 클릭합니다. CloudThinker가 코드 블록에서 명령을 추출하는 동안 각 파일에 **Uploading...**에 이어 **Extracting commands...**가 표시됩니다.
  </Step>
</Steps>

**성공 상태:** 각 파일이 목록에 별도의 소스로 나타나며, 바로 게시되고 검색할 수 있습니다. 업로드는 초안으로 만들어지지 않습니다. 행의 책 아이콘을 클릭하면 원본 Markdown을 받을 수 있는 **Download** 버튼과 함께 읽기 전용 미리 보기가 열립니다.

다음과 같이 작성된 runbook은 CloudThinker에게 명확하고 분리 가능한 명령을 제공합니다.

````md
# Checkout pods in CrashLoopBackOff

## Check
```bash
kubectl get pods -n checkout
kubectl logs deploy/checkout-api -n checkout --tail=200
```

## Fix
```bash
kubectl rollout restart deploy/checkout-api -n checkout
```
````

이 파일에서 CloudThinker는 `kubectl rollout restart`를 승인이 필요한 변경 명령으로 기록합니다. 두 읽기 전용 명령은 기록되지 않으며, CloudThinker는 RCA 중에 runbook 승인 없이 이를 실행할 수 있습니다.

업로드 시 CloudThinker 백엔드가 호출하는 AI 모델이 펜스 코드 블록을 읽고 무언가를 변경하는 명령만 남깁니다. 파이프라인은 어느 부분이든 쓰기를 하면 변경 명령으로 간주됩니다. 남긴 각 명령은 코드 블록에 있어야 하므로 일반 문장에서는 아무것도 기록되지 않습니다. 모델 단계가 실패하면 고정된 보기 전용 명령 목록(`kubectl get`, `kubectl logs`, `cat`, `grep` 등)이 대신 결정하며, 그 목록에 없는 것은 모두 변경 명령으로 간주됩니다. 모델 호출이 어디로 가는지는 [Data CloudThinker handles](/ko/guide/security/overview#cloudthinker가-처리하는-데이터)를 참조하세요.

잘못 분류된 명령이 승인을 건너뛸 수는 없습니다. 모델이 놓친 쓰기도 모든 에이전트 쓰기와 마찬가지로 연결의 자격 증명과 **Allow writes** 설정, 그리고 [Approvals](/guide/approvals/overview)를 거쳐 실행됩니다([명령이 실행되는 곳](#명령이-실행되는-곳) 참조). 워크스페이스에서 runbook 명령 효과가 활성화되어 있다면 기록된 명령을 검토할 수 있습니다. [명령 효과 제어](#명령-효과-제어)를 참조하세요.

업로드한 runbook을 변경하려면 소스를 삭제하고 새 버전을 업로드하세요. 업로드는 그 자리에서 편집할 수 없습니다. 이전 **Execution history** 행은 runbook 제목을 유지하지만, 삭제된 소스와 더 이상 연결되지 않습니다.

<Warning>
새 업로드는 새 정책을 받으므로 모든 명령이 다시 **Require Approval**에서 시작합니다. 이전 업로드에 설정한 **Allow** 또는 **Deny**는 사라집니다.
</Warning>

## 명령 효과 제어

**effect**는 변경 명령에 대한 runbook 자체의 규칙입니다. 워크스페이스의 [Approvals](/guide/approvals/overview) 모드도 모든 변경에 적용됩니다. runbook 명령 효과가 꺼져 있는 곳(대부분의 배포)에서는 효과가 적용되지 않고 Approvals만 결정합니다. 기본 **Auto · Rules + AI · Ask me** 모드에서는 AI 판단이 묻지 않고 변경을 실행하게 할 수 있으며, Allow [Rule](/guide/approvals/rules)도 그렇게 할 수 있습니다. 모든 runbook 변경이 사람을 기다리게 하려면 **Manual**을 선택하세요. 사용할 수 있는 효과는 소스 유형에 따라 다릅니다.

| 소스 유형 | 효과 | 기본값 |
|---|---|---|
| Confluence, GitHub, GitLab | 항상 **Require Approval** | Require Approval |
| Upload | runbook 명령 효과가 활성화된 곳에서만 명령별로 **Allow**, **Require Approval**, 또는 **Deny**. 대부분의 배포: **Require Approval**만. | Require Approval |

| 효과 | 동작 |
|---|---|
| **Allow** | 묻지 않고 실행 |
| **Require Approval** | 사람이 승인하거나 거절할 때까지 대기 |
| **Deny** | 절대 실행되지 않음 |

각 업로드는 추출된 명령마다 구문 하나씩을 가진 `Manual Runbook: <runbook name>`이라는 자체 정책을 받습니다. runbook 명령 효과는 대부분의 배포에서 꺼져 있습니다. 켜져 있는 곳에서는 **Settings → Workspace → Autonomy → Runbooks** 아래에 있으며, 거기서 정책을 열고 명령의 효과를 바꿀 수 있습니다. 예를 들어 자주 실행하는 안전한 재시작은 **Allow**로 바꿀 수 있습니다. 이 기능이 없으면 모든 명령이 정책에서 **Require Approval**을 유지하며, Approvals 모드가 변경을 기다릴지 결정합니다. 배포에서 이 기능을 켤 수 있는지 문의하려면 [support@cloudthinker.io](mailto:support@cloudthinker.io)로 이메일을 보내세요.

## runbook 작업 승인

인시던트 중에 CloudThinker가 변경 명령을 실행하려 하면 인시던트가 승인을 기다리며 **Resolve → Issues**의 **Approval needed** 필터에 해당합니다.

<Steps>
  <Step title="대화 열기">
    인시던트에서 **More actions**를 열고 **Open AI Conversation**을 클릭합니다.
  </Step>
  <Step title="결정">
    승인 카드에서 제안된 명령을 읽고 **Approve** 또는 **Decline**을 클릭합니다. 승인하면 실행이 계속됩니다. 거절하면 해당 작업이 중단됩니다. 카드에는 명령을 편집하는 필드가 없습니다. 다른 것을 실행하려면 거절하고 대화에서 원하는 내용을 말하세요.
  </Step>
</Steps>

**성공 상태:** 인시던트가 더 이상 **Approval needed**에 해당하지 않으며, **Execution history** 탭에서 실행에 **Approved**가 표시됩니다. 거절된 작업은 그곳에 **Rejected**로 표시됩니다.

실행은 누군가 결정할 때까지 그 단계에서 기다립니다. 누가 승인할 수 있는지는 워크스페이스의 승인 설정을 따릅니다. [approvers](/guide/approvals/approvers)를 참조하세요. 승인할 수 없다면 카드에 승인자를 기다리는 중이라고 표시됩니다. 대화를 시작한 사람에게는 카드에 **Notify approvers** 버튼도 표시됩니다. 승인 요청을 이메일이나 채팅으로 받으려면 [Notifications](/ko/guide/notifications)에서 **Agent approvals**를 켜세요.

## 실행된 내용 검토

**Resolve → Runbooks**의 **Execution history** 탭을 엽니다. 각 행은 runbook 작업 하나입니다.

| 열 | 값 | 알려 주는 내용 |
|---|---|---|
| **Runbook** | 소스에 연결된 runbook 제목 | CloudThinker가 사용한 절차 |
| **Policy** | Auto Execute, Requires Approval, Denied, Per Command | 누군가에게 묻기 전에 정책이 결정한 내용: **Auto Execute**는 작업을 허용했고, **Requires Approval**은 사람에게 보냈고, **Denied**는 차단했습니다. **Per Command**는 업로드한 runbook을 표시하며, 각 명령이 실행될 때 자체 효과와 대조됩니다. |
| **Approval** | Pending, Approved, Rejected | 사람에게 물었다면 그 사람의 결정 |
| **Status** | 아래 표 참조 | 실행되었을 때 일어난 일 |
| **Created** | 타임스탬프 | CloudThinker가 제안한 시점 |

| 상태 | 의미 |
|---|---|
| 비어 있음 | 아무것도 실행되지 않음: 작업이 사람을 기다리거나, 거절되었거나, 정책에 의해 거부됨 |
| **Not Started** | 승인되었거나 정책이 허용함. 별도의 실행 중 상태가 없으므로 대기 중이거나 아직 실행 중일 수 있습니다. 새로 고침하면 **Completed** 또는 **Failed**를 볼 수 있습니다. 이 상태에 계속 머문다면 인시던트를 열고 **More actions** → **Open AI Conversation**에서 명령이 아직 실행 중인지 확인하세요. |
| **Completed** | 명령이 실행되어 완료됨 |
| **Failed** | 명령이 실행되어 오류를 반환함. 다시 시도하기 전에 결과를 읽으세요. |

인시던트를 종료하기 전에 **Status**를 확인하세요. **Approved**는 사람이 승인했다는 뜻입니다. **Completed**만 명령이 실행되었다는 뜻입니다.

## 소스 관리

소스 행에 마우스를 올리면 작업이 표시됩니다.

| 작업 | 동작 |
|---|---|
| Toggle | 소스를 삭제하지 않고 끕니다. CloudThinker는 비활성화된 소스를 검색하지 않습니다. |
| Edit | 연결된 소스의 이름이나 범위를 변경합니다. |
| Preview (책 아이콘) | 업로드한 runbook의 내용을 보여 줍니다. |
| Publish | 아직 **Draft**로 표시된 오래된 업로드 소스에만 나타납니다. 새 업로드는 항상 게시됩니다. CloudThinker는 Admin이 게시하기 전까지 초안을 검색하지 않습니다. |
| Delete | 확인 후 소스를 제거합니다. |

## 문제 해결

<AccordionGroup>
  <Accordion title="소스 유형이 회색으로 비활성화되었거나 Connect first가 표시됨">
    소스 양식에는 해당 플랫폼의 연결이 필요합니다. 행을 클릭하여 연결하거나 [Connections](/ko/guide/connections/overview)에서 추가한 다음, 돌아와서 **Add source**를 클릭하세요.
  </Accordion>
  <Accordion title="CloudThinker가 RCA 중에 내 runbook을 사용하지 않음">
    소스의 토글이 켜져 있고 **Draft**로 표시되어 있지 않은지 확인하세요. 그런 다음 범위를 확인하세요. 잘못된 **Confluence Space Key**, **Path Prefix**, **File Patterns** 값은 파일을 숨깁니다. runbook 제목에 증상과 서비스를 넣으세요. [CloudThinker가 runbook을 찾는 방법](#cloudthinker가-runbook을-찾는-방법)을 참조하세요.
  </Accordion>
  <Accordion title="업로드가 거부됨">
    최대 5 MB의 `.md` 파일만, 업로드당 최대 20개까지 허용됩니다. 큰 runbook은 절차 하나당 파일 하나로 나누세요.
  </Accordion>
  <Accordion title="업로드에서 명령이 추출되지 않음">
    명령은 펜스 코드 블록 안에 있어야 합니다. 일반 문단의 명령이나 읽기 전용 명령만 있으면 승인할 것이 생기지 않습니다.
  </Accordion>
  <Accordion title="인시던트가 대기 상태에서 멈춤">
    runbook 작업이 보류 중입니다. 인시던트를 열고 **More actions** → **Open AI Conversation**을 클릭한 다음 **Approve** 또는 **Decline**을 클릭하세요.
  </Accordion>
</AccordionGroup>
