웹훅은 알림이 발생할 때마다 모니터링 도구가 호출하는 URL로, Resolve가 몇 초 안에 알림을 볼 수 있게 합니다. 도구마다 웹훅을 하나씩 만들고, 도구의 JSON 필드를 제목, 심각도, 서비스에 매핑하고, CloudThinker가 스스로 근본 원인 분석(RCA)을 시작할지 결정합니다.

## 알림의 흐름

웹훅에 도달한 알림은 바로 인시던트가 되지 않습니다. 먼저 [Pulse](/ko/guide/pulse/overview)를 거칩니다.

<Frame caption="Pulse drops noise and groups signals into clusters; only a cluster with an actionable signal reaches triage.">
  <img src="/images/pulse/diagram-pulse-flow-light.svg" alt="A raw event passes suppression, joins a cluster, and is classified; a cluster with an actionable signal goes to Resolve triage and becomes an incident." className="block dark:hidden" style={{width: '100%'}} />
  <img src="/images/pulse/diagram-pulse-flow-dark.svg" alt="A raw event passes suppression, joins a cluster, and is classified; a cluster with an actionable signal goes to Resolve triage and becomes an incident." className="hidden dark:block" style={{width: '100%'}} />
</Frame>

**signal**은 노이즈 억제를 통과한 이벤트입니다. **cluster**는 Pulse가 하나의 문제로 취급하는 관련 신호 묶음입니다. 조치 가능한 신호를 담은 클러스터만 분류(triage)로 넘어가며, 분류 단계에서 인시던트가 될지 결정합니다.

웹훅은 알림이 Resolve에 도달하는 세 가지 방법 중 하나입니다. 소스가 폴링되거나 채팅 채널로 들어온다면 [Connect alert sources](/guide/incident/connect-alert-sources)를 참조하세요.

## 시작하기 전에

- 워크스페이스 **Admin** 역할.
- 웹훅을 추가할 수 있는 모니터링 도구의 관리자 접근 권한.
- 필요할 때 발생시킬 수 있는 실제 알림 페이로드 하나 또는 그 JSON 샘플.

## 웹훅 만들기

<Steps>
  <Step title="플랫폼 열기">
    **Resolve → Triggers & Outcomes**로 이동하여 Datadog, Grafana, PagerDuty 같은 도구를 선택합니다.
  </Step>
  <Step title="신호 추가">
    **Signals to Resolve** 아래에서 **Add signal**(또는 **Add another signal**)을 클릭합니다. 세 단계로 된 **Create Webhook** 대화 상자가 열립니다.
  </Step>
  <Step title="Basic Info">
    **Webhook Name**(기본값은 `<Tool> Webhook`)을 그대로 두거나 바꾸고, 선택적으로 **Description**을 추가합니다. **Next**를 클릭합니다.
  </Step>
  <Step title="Configure">
    **Field Mapping**과 **Severity Mapping**을 확인합니다. 둘 다 선택한 도구에 맞게 미리 채워져 있습니다. **Send directly to CloudThinker**는 꺼 둡니다([이유](#rca-시작-시점-결정)). **Next**를 클릭합니다.
  </Step>
  <Step title="Advanced">
    **Auth Method**를 고르고 **Auto-investigate**를 설정합니다(둘 다 아래에서 설명). **Create**를 클릭합니다.
  </Step>
</Steps>

**성공 상태:** 대화 상자에 **Webhook URL**, **Authentication Setup** 아래의 **Secret Key**, 그리고 **cURL**, **JavaScript**, **Python**, **Node.js** 탭이 있는 **Integration Examples**가 표시됩니다. URL과 **Secret Key**를 지금 복사하세요. 키는 한 번만 표시됩니다. 같은 대화 상자에 도구별 **Setup Guide**가 표시되므로, 이를 따라 붙여 넣으세요. **cURL** 탭이 테스트를 보내는 가장 빠른 방법입니다.

<Tip>
**Done**을 클릭하기 전에 **Secret Key**를 복사하세요. 잃어버렸다면 **Resolve → Triggers & Outcomes**로 이동하여 도구를 열고, **Signals to Resolve** 아래에서 웹훅 행의 **Manage** 메뉴(**⋯**) → **Regenerate credentials**를 여세요. 이렇게 하면 **Webhook URL**과 **Secret Key**가 모두 교체되며, 이전 쌍은 즉시 작동을 멈춥니다. 웹훅을 사용하는 모든 도구에 새 URL과 키가 필요합니다.
</Tip>

## 필드 매핑

각 매핑 필드는 알림 JSON 안의 경로를 받습니다. **Title Path**만 필수입니다.

- `event.data.title`처럼 점으로 구분된 키를, 목록 항목에는 `alerts[0].labels.severity`처럼 `[n]`을 사용합니다. 앞의 `$.`는 허용되며 제거됩니다.
- 경로는 최대 8개 세그먼트까지 가질 수 있습니다. 점이 포함된 키는 지정할 수 없으며, 대체 경로도 없습니다.
- 경로는 하나의 텍스트 또는 숫자 값에서 끝나야 합니다. 목록이나 객체에서 끝나는 경로는 아무것에도 매핑되지 않습니다.

| 필드 | 채우는 내용 |
|---|---|
| **Title Path** | 인시던트 제목. 필수입니다. |
| **Severity Path** | **Severity Mapping**으로 변환되는 심각도 수준. |
| **Description Path** | 인시던트 설명. |
| **Service Path** | 영향받는 서비스. 같은 서비스를 가리키는 신호는 한 클러스터에 합쳐질 수 있으므로 `prod` 같은 넓은 값이 아닌 서비스 이름 하나를 사용하세요. |
| **Resource ID Path** | 영향받는 리소스의 식별자. 같은 리소스 ID로 반복되는 신호는 한 클러스터에 합쳐집니다. 비워 두면 CloudThinker가 최상위 `resource_id` 키를 읽습니다. [How signals join a cluster](/ko/guide/pulse/clusters#신호가-클러스터에-합류하는-방식)를 참조하세요. |
| **Resource Name Path** | 영향받는 리소스의 이름. |
| **Timestamp Path** | 이벤트가 시작된 시점(ISO 8601 시간). 비워 두면 CloudThinker가 최상위 `timestamp` 키를 읽습니다. 둘 다 없거나 구문 분석할 수 없는 값이면 전송이 도착한 시간을 사용합니다. |

페이로드 형태는 도구가 정합니다. 예를 들어 Datadog에서는 Datadog의 템플릿 변수를 사용하여 웹훅의 **Payload** 필드에 JSON을 직접 작성합니다. Datadog 프리셋은 `title`, `body`, `alert_type`을 읽습니다. 프리셋의 기본 **Service Path**(`tags`)는 목록을 가리켜 아무것에도 매핑되지 않으므로, 서비스 이름 하나를 담은 `service` 키를 추가하세요.

```json
{
  "title": "$EVENT_TITLE",
  "body": "$EVENT_MSG",
  "alert_type": "$ALERT_TYPE",
  "service": "web-api"
}
```

| 필드 | 경로 | 예시 값 |
|---|---|---|
| **Title Path** | `title` | High CPU on web-server-01 |
| **Description Path** | `body` | CPU usage exceeded 90% for 5 minutes |
| **Severity Path** | `alert_type` | error |
| **Service Path** | `service`(`tags`에서 변경) | web-api |

고정된 `service` 값은 이 웹훅에 알리는 모든 모니터에 적용됩니다. Datadog의 `$ALERT_TYPE`은 `error`, `warning`, `info`, `success`를 보내지만, Datadog 프리셋의 **Severity Mapping**은 `alert`, `warn`, `ok`, `no data`를 다룹니다. **Severity Mapping** 아래에서 **Customize**를 클릭한 다음, 다음 각 행에 대해 **Add Mapping**을 클릭하세요(수준은 팀에 맞게 바꾸세요). 나중에 웹훅 행의 **Manage** 메뉴(**⋯**) → **Edit**에서 추가할 수도 있습니다.

| 소스 값 | 심각도 |
|---|---|
| `error` | high |
| `warning` | medium |
| `info` | info |
| `success` | info |

`success`(복구) 이벤트는 아무것도 닫지 않습니다. 일반 신호로 도착하며, 클러스터는 여전히 12시간 동안 조용하거나 사람이 해결할 때 닫힙니다. CloudThinker의 분류기는 복구나 정상 상태를 조치 불필요로 취급하므로, 그 클러스터는 스스로 분류로 넘어가지 않습니다. 이 확인은 모델의 판단이므로 복구가 여전히 통과할 수 있습니다. 사람은 언제든지 **Open incident**(또는 클러스터 **⋯** 메뉴의 **Escalate**)로 클러스터를 분류로 보낼 수 있습니다.

**Severity Mapping**은 도구 자체의 용어를 CloudThinker의 다섯 수준인 critical, high, medium, low, info로 변환합니다. 예를 들어 일반 프리셋은 `warning`을 medium으로, `error`를 high로 매핑합니다. 일치 여부는 대소문자와 앞뒤 공백을 무시하므로 `ERROR`와 `error`는 같은 행에 해당합니다.

| **Severity Path**의 값 | 결과 |
|---|---|
| 다섯 수준 중 하나 | 그대로 사용됩니다. 행이 필요 없습니다. |
| 매핑 행이 있음 | 해당 행의 수준 |
| 그 밖의 값 | **medium** |
| **Severity Path**가 비어 있거나 아무것도 찾지 못함 | CloudThinker가 대신 최상위 `severity` 또는 `priority` 키를 읽음 |
| `severity`나 `priority` 키도 없음 | **medium** |

도구가 목록에 없으면 대신 [Custom source](/guide/incident/webhook-integrations/custom-source)를 사용하세요. 실제 페이로드 하나를 캡처하여 매핑할 필드를 클릭으로 지정할 수 있습니다.

## 인증 선택

| Auth Method | 도구가 보내는 내용 | 사용하는 경우 |
|---|---|---|
| **Bearer Token** | `Authorization: Bearer <secret>` | 도구가 사용자 지정 헤더를 추가할 수 있을 때. 대부분의 도구의 기본값입니다. Datadog에서는 웹훅의 **Custom Headers** 필드에 JSON을 입력합니다: `{"Authorization": "Bearer <secret>"}`. |
| **HMAC Signature** | 원시 요청 본문의 HMAC-SHA256을 16진수로 인코딩하여 지정한 헤더에 `sha256=<hex digest>`로 보냄. PagerDuty의 `X-PagerDuty-Signature`(`v1=<hex digest>`)도 허용됩니다. | PagerDuty처럼 도구가 웹훅에 서명할 때. **HMAC Signature Header**에 헤더 이름을 설정합니다. 도구가 자체 서명 시크릿을 생성한다면 **Provider signing secret**에 붙여 넣습니다. |
| **API Key** | 지정한 헤더에 담긴 키 | EventBridge를 통한 CloudWatch처럼 도구가 API 키 헤더만 지원할 때. **API Key Header**와 선택적으로 **Key Prefix**를 설정합니다. |
| **No Authentication** | 없음 | 빠른 테스트용으로만. URL을 가진 누구나 알림을 보낼 수 있습니다. |

대화 상자는 선택한 방법에 따라 자격 증명의 이름을 붙입니다. **Bearer Token**은 **Secret Key**, **HMAC Signature**는 **HMAC Secret**, **API Key**는 **API Secret**입니다. 어느 경우든 같은 자격 증명이며 한 번만 표시됩니다.

## RCA 시작 시점 결정

**Auto-investigate**는 기본적으로 켜져 있습니다. 이 웹훅의 조치 가능한 클러스터는 분류로 넘어가 인시던트를 열고 조사합니다. 끄면 누군가 클러스터에서 **Open incident**와 **Send to triage**를 클릭할 때까지 알림이 Signals에 남습니다. **Only from a minimum severity**를 사용하면 하한을 고릅니다: **Info and above**, **Low and above**, **Medium and above**, **High and above**, **Critical only**. 하한보다 낮은 알림은 여전히 관련 알림과 묶이지만, 스스로 분류를 시작하지 않습니다.

[What starts an investigation](/guide/incident/settings#what-starts-an-investigation)에서 이 옵션들이 **AI auto-investigate** 및 수동 시작과 어떻게 결합되는지 보여 줍니다.

<Note>
각 자동 조사는 크레딧으로 청구됩니다. 노이즈가 많은 도구를 연결하기 전에 최소 심각도나 [Credit limit](/guide/billing/credit-limits)을 설정하세요.
</Note>

**Send directly to CloudThinker**(**Configure** 단계에 있으며 기본적으로 꺼져 있음)는 Pulse의 필터링과 그룹화를 건너뜁니다. 그러면 CloudThinker가 각 이벤트를 개별적으로 판단합니다. 도구가 이미 알림의 중복을 제거하지 않는 한 꺼 두세요.

## 전체 경로 테스트

<Steps>
  <Step title="실제 알림 하나 발생시키기">
    도구에서 대표적인 알림을 발생시키거나, **Integration Examples**의 **cURL** 탭에서 요청을 보냅니다. **Bearer Token**의 경우 테스트는 다음과 같습니다.

    ```bash
    curl -X POST "https://YOUR_WEBHOOK_URL" \
      -H "Content-Type: application/json" \
      -H "Authorization: Bearer YOUR_SECRET_KEY" \
      -d '{"title": "Test: high CPU on web-01", "alert_type": "error", "service": "web-api"}'
    ```

    전송에 성공하면 `"success": true`와 `request_id`가 포함된 본문과 함께 `200`이 반환됩니다. 아직 Datadog 행을 추가하지 않았다면 `error`는 medium으로 매핑됩니다.
  </Step>
  <Step title="Pulse 확인">
    **Resolve → Signals**를 열고 매핑한 제목의 신호를 찾습니다.
  </Step>
  <Step title="인시던트 확인">
    **Resolve → Signals**에서 분류로 넘어간 클러스터는 인시던트에 연결되면 **Handled** 레인으로 이동합니다. 그런 다음 **Resolve → Issues**를 엽니다. **Auto-investigate**와 **AI auto-investigate**가 모두 켜져 있으면 인시던트에 **AI is handling**이 표시됩니다. 클러스터가 **Handled**에 도달하지 않는다면 분류 단계에서 조치 불필요로 판단했을 수 있습니다. [Clusters troubleshooting](/ko/guide/pulse/clusters#문제-해결)을 참조하세요.
  </Step>
</Steps>

**성공 상태:** 신호가 올바른 제목, 심각도, 서비스와 함께 Pulse에 나타나고, 해당하는 인시던트에 **AI is handling**이 표시됩니다. `200`만으로는 전송만 증명됩니다.

의존하는 심각도 행마다 알림을 하나씩 테스트하세요. 위 Datadog 예시라면 `error`(high로 매핑) 하나와 `warning`(medium으로 매핑) 하나를 보내세요.

## 제한과 응답

| 응답 | 시점 |
|---|---|
| `200`과 `"success": true` | 전송이 수락되었습니다. |
| `400` | 웹훅이 일시 중지되었거나 비활성화되었습니다. **Signals to Resolve** 아래의 해당 행에 **Paused**가 표시됩니다. 이를 재개하는 Resolve 화면은 없습니다. 소스 이름과 워크스페이스를 적어 [support@cloudthinker.io](mailto:support@cloudthinker.io)로 이메일을 보내 다시 활성화를 요청하세요. |
| `401` | 인증 헤더가 없거나, URL이 현재 **Webhook URL**이 아닙니다(오타이거나 **Regenerate credentials**로 교체됨). |
| `403` | 시크릿이나 서명이 잘못되었습니다. |
| `413` | 본문이 1 MB보다 큽니다. |
| `422` | 본문이 JSON 객체가 아닙니다. 배열이나 일반 텍스트가 아닌 `{...}`를 보내세요. |
| `429` | 요청이 너무 많거나 인증 실패가 너무 많습니다. 15분 안에 10번 실패하면 그 15분 창이 끝날 때까지 웹훅이 요청을 거부합니다. `Retry-After` 헤더가 있으면 그 시간이 지난 후 다시 시도하세요. |

<Warning>
각 웹훅은 기본적으로 시간당 최대 1,000건의 전송을 받습니다. 제한은 응답 후에 확인되므로 이를 넘는 전송도 `"success": true`와 함께 `200`을 받지만, 조용히 버려집니다. 이 전송은 신호가 되지 않으며 [Pulse analytics](/ko/guide/pulse/analytics)의 **Signals ingested**에도 집계되지 않습니다. Resolve는 버려진 개수를 표시하지 않으므로, 유일한 징후는 급증 시 **Resolve → Signals**에서 누락된 알림입니다.

이를 피하려면 다음을 하세요.

- 제한 높이기: 웹훅 행의 **Manage** 메뉴(**⋯**) → **Edit**을 열고 **Rate limit (requests per hour)**를 변경합니다. 최대 10,000까지 올릴 수 있으며, `0`은 제한 없음을 뜻합니다.
- 대량 모니터를 여러 웹훅으로 나누기.
- 알림을 보내기 전에 도구에서 중복을 제거하거나 그룹화하기.
</Warning>

Pulse는 전송의 소스, 리소스, 제목, 심각도, 이벤트 시간(분 단위, 출처는 **Timestamp Path** 참조)이 지난 1시간 내의 신호와 일치하면 중복으로 취급합니다. 중복은 새 신호를 만들지 않고 해당 신호의 개수를 늘립니다. 클러스터는 새 신호 없이 12시간이 지나거나 사람이 해결하면 닫힙니다. [Cluster lifecycle](/ko/guide/pulse/clusters#클러스터-라이프사이클)을 참조하세요.

## 문제 해결

<AccordionGroup>
  <Accordion title="도구가 401 또는 403을 보고함">
    **원인:** 인증 헤더가 **Auth Method**와 일치하지 않거나, (`401`의 경우) 도구가 여전히 이전 **Webhook URL**로 보내고 있습니다. **확인:** 도구의 URL, 헤더 이름, 시크릿을 **Authentication Setup**과 비교하세요. **해결:** 시크릿을 다시 붙여 넣거나, **Resolve → Triggers & Outcomes**에서 웹훅 행의 **Manage** 메뉴에 있는 **Regenerate credentials**를 사용하세요.
  </Accordion>
  <Accordion title="전송은 성공했지만 Pulse에 아무것도 나타나지 않음">
    **원인:** Pulse가 알림을 노이즈로 억제했거나, 이전 신호의 중복으로 집계했거나, 시간 창 때문에 보이지 않습니다. **확인:** **Resolve → Signals**에서 창을 넓힌 다음, 상단의 퍼널에 마우스를 올려 억제된 이벤트 수를 확인하세요. 같은 알림을 1분 안에 두 번 보냈다면 이전 신호를 찾아보세요. 대신 그 개수가 올라갔을 것입니다([제한과 응답](#제한과-응답) 참조). **해결:** 각 확인 항목은 [Noise suppression](/ko/guide/pulse/clusters#노이즈-억제)을 참조하세요.
  </Accordion>
  <Accordion title="신호의 제목이 비어 있거나 심각도가 잘못됨">
    **원인:** 경로가 페이로드와 일치하지 않거나, 도구의 심각도 값에 매핑 행이 없습니다. **해결:** 경로를 실제 페이로드와 비교한 다음, 누락된 값을 **Severity Mapping**에 추가하세요.
  </Accordion>
  <Accordion title="알림이 Pulse에 도달했지만 RCA가 시작되지 않음">
    **원인:** **Auto-investigate**가 꺼져 있거나, 심각도가 하한보다 낮거나, **AI auto-investigate**가 꺼져 있습니다. **해결:** 세 가지 모두를 [What starts an investigation](/guide/incident/settings#what-starts-an-investigation)과 대조하거나, 클러스터에서 **Open incident**와 **Send to triage**를 클릭하세요. 인시던트가 이미 열려 있다면 그 인시던트에서 **Investigate**를 클릭하세요.
  </Accordion>
</AccordionGroup>
