この章では、エージェントをすでに運用しているツールと並べて位置づけ、AIOps がどこで止まったのかを説明し、エージェントを実用的にした3つの技術的変化を取り上げます。現在のスタックのどの部分をエージェントプラットフォームが再利用し、どのギャップを埋める必要があるのかを判断する材料にしてください。

## 2.1 運用の4つの世代

| 世代 | 中心となる考え方 | 自動化したもの | 手作業のまま残ったもの |
| :---- | :---- | :---- | :---- |
| 第1世代：手作業とスクリプト | 人がシステムを運用し、シェルスクリプトが繰り返しの手順を処理する | 単一の既知のタスク | 何をいつ実行するかの判断。知識は人の頭の中にありました。 |
| 第2世代：Infrastructure as Code（IaC） | あるべき状態をコードで宣言し、CI/CD パイプラインがそれを適用する | プロビジョニングとデプロイ | Day-2 の作業：ドリフト、インシデント、チューニング、クリーンアップ |
| 第3世代：AIOps | 機械学習（ML）が異常を見つけ、イベントを相関させ、ノイズを減らす | 問題の発見とグループ化 | 原因の特定、修正方法の選択、その適用 |
| 第4世代：エージェント型運用 | 目標を持ったエージェントが観察し、推論し、行動し、結果を確認する | あなたが設定したポリシーのもとでのループ全体 | ポリシーの設定、リスクの高い変更の承認、未知の障害への対応 |

各世代は前の世代を置き換えるのではなく、その上に積み重なります。エージェントは変更をコードとして表現し（第2世代）、相関されたアラートを入力として受け取り（第3世代）、今もスクリプトを書いて実行します（第1世代）。変わるのは、誰がループを閉じるかです。

これには実務上の帰結があります。エージェントの質は、その下にあるスタックの質で決まります。始める前に、次の4点を確認してください。

- **インフラがコード化されている。** エージェントが触れるシステムが、少なくとも部分的に Terraform などの IaC ツールで定義されています。
- **アラートをルーティングできる。** 監視ツールが Webhook でアラートを送信できます。[アラートソースを接続する](/ja/guide/pulse/setup)を参照してください。
- **ランブックが文書化されている。** 既知の修正方法が Confluence、Git リポジトリ、または Markdown ファイルにまとまっています。[ランブック](/ja/guide/incident/runbooks)を参照してください。
- **読み取り専用の認証情報がある。** クラウドアカウントやクラスターごとに、スコープを絞った読み取り専用の認証情報を発行できます。[Connections](/ja/guide/connections/overview)を参照してください。

完全な準備状況チェックは[第9章](/ja/learn/aio/chapter-9-roadmap)にあります。

## 2.2 AIOps が届かなかった理由

AIOps には確かな価値がありました。イベントの相関と重複排除は機能し、アラート量を減らします。しかし、これらのツールは「関連するアラートのグループはこれです」で止まり、残りは人がやる必要がありました。

3つのギャップが上限を決めていました。

1. **因果なき相関。** 50件のアラートを1つのインシデントにまとめるのは役に立ちます。それでも、根本原因や取るべき対応は分かりません。
2. **推論なき答え。** 説明のない ML スコアは信頼しにくいものです。エンジニアは出力を手作業で再確認し、節約できたはずの時間の大半が失われました。
3. **手がない。** AIOps はチケットを起票したり Webhook を呼び出したりはできました。しかし、調査し、仮説を検証し、修正を選び、適用し、効果を確認することはできませんでした。行動するのは依然としてエンジニアでした。

## 2.3 何が変わったか：推論モデル、ツール、プロトコル

3つの変化によって、エージェントが運用業務で実用的になりました。

1. **推論モデル。** 大規模言語モデル（LLM）は、適切にスコープが絞られた領域であれば、ログ、設定、コードを読み、原因について仮説を立て、複数ステップの修正を計画できるようになりました。
2. **ツールの使用。** モデルは関数を確実に呼び出せるようになりました。CLI コマンドの実行、API へのクエリ、`kubectl` や Terraform の実行、ダッシュボードの読み取りなどです。これにより推論が行動に変わります。
3. **ツールを接続する標準的な方法。** Model Context Protocol（MCP）は、AI エージェントにツールを公開するためのオープン標準です。チームが社内システムの前に MCP サーバーを1つ置けば、互換性のあるどのエージェントもそれを使えます。

運用がエージェントに向いている理由はもう1つあります。結果を確認しやすいことです。修正によってレイテンシが目標値以下に戻るか戻らないか。Terraform のプランがきれいに適用されるか失敗するか。ヘルスチェックが通るか通らないか。フィードバックがこれほど明確なら、エージェントは自分の作業を検証でき、あなたもそれが実際に行われたかを確認できます。

## 2.4 業界はエージェントをどう展開しているか

主要なクラウドプロバイダーは、独自の運用エージェントを提供しています。AWS DevOps Agent、Azure SRE Agent、Google Cloud の Gemini Cloud Assist です（それぞれが自律性をどう扱うかは [3.2](/ja/learn/aio/chapter-3-what-is-aio#32-自律性のスペクトル) で説明します）。いずれも同じやり方でリリースされました。まず調査から始め、変更はすべて顧客の承認の後ろに置くというものです。

このパターンが、自社での展開に向けた教訓です。まずは読み取って説明するエージェントから始め、その分析をエンジニアの調査結果と照らし合わせ、そのうえで初めて行動を許可します。それも1種類のアクションずつです。[第7章](/ja/learn/aio/chapter-7-humans-on-the-loop)と[第9章](/ja/learn/aio/chapter-9-roadmap)で、これを段階的な計画にまとめます。

## 2.5 CloudThinker の位置づけ

CloudThinker の Frontier Investigation Agents は、すでにあるスタックの上で検出・分析・解決・検証のループを実行し、各レイヤーを置き換えるのではなく再利用します。

| 既存のレイヤー | CloudThinker での使い方 |
| :---- | :---- |
| 監視とアラート（第3世代） | [Signals](/ja/guide/pulse/overview) は、ツールがすでに送信しているアラートを受け取り、既知のノイズを除外し、関連するアラートをクラスターにまとめます。 |
| クラウド、Kubernetes、IaC（第2世代） | エージェントは [AWS](/ja/guide/connections/aws)、[Kubernetes](/ja/guide/connections/kubernetes)、[Terraform](/guide/connections/terraform) などの [connections](/ja/guide/connections/overview) を通じて読み取り、行動します。 |
| 社内ツール | 独自の MCP サーバーを [MCP connection](/ja/guide/connections/mcp) として追加すると、エージェントがそのツールを呼び出せます。 |
| スクリプトとランブック（第1世代） | [ランブック](/ja/guide/incident/runbooks)に既知の修正方法を保持します。すべての変更は [Approvals](/guide/approvals/overview) を通り、あなたが設定したポリシーに基づいて、実行されるか、人を待つか、拒否されます。新しいワークスペースは **Auto · Rules + AI · Ask me** で始まります。読み取りは常に実行され、Rules が許可する書き込みは実行され、AI の判断で安全な書き込みを許可でき、それ以外は人を待ちます。これは **Settings → Workspace → Autonomy → Rules** の **When no Rule matches** で変更します。 |

新しいワークスペースでの最初の1時間：

1. 読み取り専用のクラウドまたは Kubernetes の [connection](/ja/guide/connections/overview) を追加します。手順は[クイックスタート](/ja/quickstart)で説明しています。
2. 1つのアラートソースを [Signals](/ja/guide/pulse/setup) に向けます。
3. [Approvals](/guide/approvals/overview) のデフォルトを確認します。評価中にすべての書き込みを人が承認するようにしたい場合は **Manual** に切り替え、[run type rows](/guide/approvals/approval-mode#set-a-mode-for-a-run-type) で **Automations** も **Manual** に上書きしてください。この行はワークスペースの設定に従わないためです。チャットごとに独自のモードを選ぶこともできます。
4. [Resolve クイックスタート](/guide/incident/quickstart)でテストアラートを送り、CloudThinker が [Resolve](/ja/guide/incident/overview) で調査する様子を確認します。

<Info>
**重要なポイント**

AIOps はシステムを可視化しました。エージェント型運用はシステムを操作可能にします。違いは閉じたループにあります。観察し、推論し、行動し、結果を確認する。人はすべての手順を自分で行うのではなく、監督します。
</Info>
