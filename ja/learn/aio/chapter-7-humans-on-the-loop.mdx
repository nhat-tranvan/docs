*エージェント型オペレーションは、テクノロジーの衣装をまとった人の変革です。*

この章では、運用作業を行うことから監督することへの移行、各運用の役割がどう変わるか、そしてエージェントに作業を引き渡すための 4 段階の信頼のはしごを説明します。7.5 節では、はしごの各段階を CloudThinker の設定に対応付けています。

## 7.1 実行者から監督者へ

「Human in the loop」は、人が実行の経路の中にいることを意味します。すべてのステップがその人を待ちます。「Human on the loop」は、人が監督することを意味します。意図とポリシーを設定し、重大な操作を承認し、成果を監査し、例外のときに介入します。

| | Human in the loop | Human on the loop |
| :---- | :---- | :---- |
| 各ステップを実行するのは | エンジニア | エージェント |
| エンジニアがすること | トリアージ、コマンドの実行、修正の作成 | ポリシーの設定、影響の大きい書き込みの承認、成果の確認 |
| エンジニアが必要になるとき | すべてのステップ | 新しい障害と重大な判断 |
| スループットを制限するもの | エンジニアの時間 | ポリシーが許す自律性の量 |

飛行機を手動で操縦するパイロットと、オートパイロットを管理するパイロットを考えてください。2 人目のパイロットの重要性が低いわけではありません。少ない手作業で機体のより多くに責任を持ち、判断が最も重要なときに操縦を引き継ぎます。

うまくいくチームは、意図的に役割を再設計します。そうしないチームでは、エンジニアがもはや理解していない承認を、形式的に押すだけになってしまいます。

## 7.2 役割がどう変わるか

| 現在の役割 | 縮小するもの | 拡大するもの |
| :---- | :---- | :---- |
| SRE またはオンコールのエンジニア | 手作業のトリアージ、ログの掘り起こし、午前 3 時の機械的な修正 | ポリシーの設計、エージェントの監督、新しい障害のためのエンジニアリング、信頼性のアーキテクチャ |
| DevOps またはプラットフォームのエンジニア | チケット駆動のプロビジョニング、繰り返しのパイプラインの修正 | エージェントの環境整備: 接続、コンテキストと runbook、ゴールデンパス、評価 |
| 運用マネージャーまたは IT 運用のリーダー | 人員数に基づくキャパシティの計画、ウォールームの調整 | 自律性のガバナンス、エージェントが担う作業の管理、成果に基づくベンダーの管理 |
| セキュリティのエンジニア | 設定ミスの手作業での探索、コンプライアンスのスクリーンショットの収集 | ガードレールの設計、エージェントの権限の設計、継続的なコンプライアンスのチェック |

2 つの新しい職務が生まれます。どちらも、片手間の仕事ではなくキャリアパスとして扱ってください。

- **エージェントオペレーションのエンジニア。** エージェント自体の健全性を担います: 指示、接続、スキル、メモリ、評価、コスト。
- **自律性のポリシーのオーナー。** 多くの場合、シニアの SRE かエンジニアリングマネージャーです。どの種類の操作を信頼のはしごで上げるかを決め、エージェントと人の意見が分かれたときに決着をつけます。

## 7.3 信頼は少しずつ築かれる

エンジニアは、予測できる順序でエージェントを信頼するようになります。段階を飛ばすと逆効果になります。

| 段階 | エージェントがすること | 人がすること | 次に進む条件 |
| :---- | :---- | :---- | :---- |
| **1. 調査するのを見る** | 調査して推奨します。変更はしません。 | エージェントの根本原因分析を自分のものと比較します。 | 根本原因分析の少なくとも 70% が、オンコールによって正しいと評価される。 |
| **2. 操作を承認する** | 完全な修正を提案して待ちます。 | 各書き込みを承認または却下します。すべての判断が、エージェントの判断力についてのラベル付きのデータになります。 | 提案の少なくとも 80% が受け入れられ、有害な操作がゼロ。変更なしで約 95% 承認され、ロールバックがなくなったら、操作のクラスを 1 つずつ卒業させます（[§8.2](/ja/learn/aio/chapter-8-measuring)）。 |
| **3. 日常的なものを事前承認する** | 実証済みの操作を単独で実行します。 | 通知を受け、事後に記録を確認します。 | 領域全体のロールバックと介入の率が横ばいか低下する。 |
| **4. 領域を委任する** | アイドルなリソースのクリーンアップ、キャッシュの管理、証明書のローテーションなど、範囲が限定された領域をエンドツーエンドで担います。 | 各操作を承認する代わりに、スケジュールに沿って成果を監査します。 | 最終段階。インシデントの後と、予定された監査のたびに見直します。 |

70% と 80% の基準は、[§9.2](/ja/learn/aio/chapter-9-roadmap) のパイロットの終了基準と一致します。CloudThinker では、オンコールがインシデントの **Was Resolve's diagnosis right?** で各根本原因分析を評価し、その評価を記録できるのはワークスペースの Developer と Admin のロールだけです。評価者には少なくとも Developer のロールを与えるか、Developer か Admin にオンコールの判定を記録してもらってください。

失敗の形は一貫しています。段階を飛ばすと、午前 3 時に自信満々で誤るエージェントを出荷することになります。そのようなインシデントが 1 つあるだけで、エージェント型のプログラムは数か月後退することがあります。段階を順に踏めば、自律性は積み重なっていきます。

段階 1 の実用的なテスト: チームがすでにクローズしたインシデントをエージェントに与え、答えを比較します。

```text
Investigate why checkout-api returned 5xx errors between 14:00 and 14:20 UTC yesterday. Give the root cause, the evidence for it, and the fix you would propose. Don't change anything.
```

このように、クローズ済みのインシデントをいくつか再現してください。そのうち少なくとも 70% で、ポストモーテムと一致する証拠とともに根本原因を正しく特定できれば、段階 2 に進みます。

## 7.4 取り戻した時間を測る

監督者のモデルの見返りは、シニアの時間が労力から予防の作業へと移ることです。測らなければ、ビジネスケースには現れません。

- **オンコールの負荷:** ページングのツールから得る、エンジニアあたり週ごとのページ数。時間外のページは別に数えます（[§8.2](/ja/learn/aio/chapter-8-measuring)）。
- **労力の時間:** チケットのシステム、または 2 週間の時間調査から得る、週あたりのトリアージと証拠集めの時間（[§8.3](/ja/learn/aio/chapter-8-measuring)）。

両方を、パイロットの前と、はしごの各段階で記録してください。

## 7.5 CloudThinker での信頼のはしご

CloudThinker では、読み取りは常に実行され、すべての書き込みは [Approvals](/guide/approvals/overview) を通ります。はしごの各段階は、確認して変更できる設定です。

| 段階 | Approval mode | セットアップの方法 | 場所 |
| :---- | :---- | :---- | :---- |
| **1. 調査するのを見る** | **Manual** | 何かを接続する前に **Workspace mode** を **Manual** に設定し、すべての書き込みが人を待つようにします。Automations を実行する場合は、その行がワークスペースに従わないため、**When no Rule matches** の **Automations** の行で **Override** をクリックし、**Manual** も選びます。チャットもコンポーザーで独自のモードを選べるため、ワークスペースのモードのままにしておきます。調査を依頼し、「don't change anything」と伝えます。 | **Settings → Workspace → Autonomy → Rules** の **When no Rule matches** |
| **2. 操作を承認する** | **Manual** のまま | チャットまたは [Google Chat](/guide/google-chat-integration) で各承認のカードに答えます。[Slack](/ja/guide/slack-integration) と [Microsoft Teams](/ja/guide/teams-integration) は、答えるために Web アプリにリンクします。メールやチャットでリクエストを受け取るには、[通知](/ja/guide/notifications)で **Agent approvals** をオンにします。[Approvers](/guide/approvals/approvers) のグループで答えられる人を選び、最もリスクの高い書き込みには 2 人ルールをオンにします。 | **Settings → Workspace → Autonomy → Approvers** |
| **3. 日常的なものを事前承認する** | **Auto · Rules · Ask me** に切り替える | 段階 2 の基準を満たした、1 つの接続での 1 つの操作について、**Allow** の [Rule](/guide/approvals/rules) を受け入れます。エージェントは作業しながら Rule を提案します。**Rules** のページで **Find rules** をクリックすると、さらに得られます。提案は **Needs your review** で待機し、待機中のものがあると **Review** 付きのバナーが表示されます。Admin が受け入れるまで何も変わりません。その後、モードを切り替えます。Allow の Rule が書き込みを単独で実行するのは **Auto** の下だけです。AI の判断がオフなら、どの Rule も許可しない書き込みは引き続き人に確認します。 | **Settings → Workspace → Autonomy → Rules** |
| **4. 領域を委任する** | Automation には **Auto · Rules + AI · Refuse** | 領域を [Automation](/guide/automation/automations) として実行します。日常的な書き込みごとに、**Runs from** で **Automations** に範囲を限定した **Allow** の Rule を受け入れます。どの Rule も許可せず、AI の判断も通さない書き込みは、いない人を待つのではなく拒否されます。毎週、**Rules** のページで **Activity** をクリックし、**Refused** の件数と **No Rule matched** の行を確認して、拒否された日常的な書き込みには Rule を追加します。 | **Settings → Workspace → Autonomy → Rules** の **Activity** ダイアログ |

新しいワークスペースは **Auto · Rules + AI · Ask me** で始まります。そこでは受け入れられた Rule が実行され、さらに AI の判断が、どの Rule もカバーしない書き込みを、安全で依頼の範囲内だと判断したときに単独で実行させることがあります。これにより、それらの書き込みについては、デフォルトが段階 3 を超えた状態になるため、段階 1 では **Manual** に切り替えてください。**Auto · Rules + AI · Ask me** に移るのは、チームがあなたのシステムでのエージェントの判断を信頼してからにしてください。

**次へ:** [第 8 章 · 重要なものを測る](/ja/learn/aio/chapter-8-measuring)では、はしごの各段階を上がることを正当化する KPI と証拠とともに、エージェントが機能していることをどう証明するかを示します。
