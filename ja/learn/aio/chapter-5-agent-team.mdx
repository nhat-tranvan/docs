*エージェントの組織を設計することは、組織設計そのものです。同じ問いが当てはまります。誰が何を担い、誰が誰に報告し、どう作業を引き渡すか。*

## 5.1 中心となる顔ぶれ

ほとんどの本番のデプロイは、それぞれが明確な範囲を持つ小さなエージェントのチームに落ち着きます。安定した役割は、聞こえる以上に重要です。同じ範囲とメモリを長く保つエージェントは、人のチームメイトと同じように、コンテキスト、信頼、説明責任を積み上げていきます。代表的な顔ぶれと、それぞれの役割が CloudThinker でどこにあるかを示します。CloudThinker では、組み込みの [CloudThinker](/ja/guide/agents/overview) アシスタントがオーケストレーター（SuperAgent の役割: 作業を分割し、振り分け、人にエスカレーションする 1 つのエージェント）を務めます。領域ごとに一時的なサブエージェントを起動し、常に置いておきたい専門家には[カスタムエージェント](/guide/agents/quickstart)を追加します。

| 役割 | 範囲 | 責任の例 | CloudThinker では |
| :---- | :---- | :---- | :---- |
| オーケストレーター / SuperAgent | 横断的 | 目標の分解、タスクの振り分け、複数の領域にまたがるインシデント、人へのエスカレーション、レポート | 組み込みの CloudThinker アシスタント（`@CloudThinker`、またはメンションなし） |
| クラウドエンジニアリングのエージェント | AWS / Azure / GCP / ローカルクラウド | プロビジョニングの問題、ネットワーク、スケーリング、サービスのクォータ、コストの異常、IaC のドリフト | サブエージェント、またはクラウドの接続を持つカスタムエージェント |
| セキュリティのエージェント | Cyber + CloudSec | 設定ミス、OWASP クラスのアプリケーションのリスク、CVE のトリアージ、IAM の衛生管理、コンプライアンスの証拠 | サブエージェント、またはセキュリティの接続を持つカスタムエージェント |
| データベースのエージェント | データ層 | 遅いクエリ、ロック、レプリケーションの遅延、インデックスの戦略、ストレージの予測、バックアップの検証 | サブエージェント、またはデータベースの接続を持つカスタムエージェント |
| Kubernetes のエージェント | コンテナのプラットフォーム | Pod のクラッシュループ、OOM による強制終了、ノードの逼迫、HPA の調整、アップグレードの準備 | サブエージェント、または Kubernetes の接続を持つカスタムエージェント |

中心となる顔ぶれに加えて、組織はカスタムエージェントを追加します。特定の事業部のコスト最適化、主力アプリケーションの性能、プラットフォームチームの生産性のワークフローなど、独自の対象と目的のために設定された専門家です。カスタムエージェントは、オーケストレーターが率いるチームを拡張します。モデルに加わるものであり、決して置き換えるものではありません。

<Tip>
組み込みのアシスタントから始め、繰り返されるタスクにオーナー、明確な範囲、成功の基準があるときにだけ、カスタムエージェントを追加してください。範囲が曖昧なカスタムエージェントは、曖昧な検出事項を生みます。**Settings → Workspace → Agents** で作成し、**Instructions** にその範囲を書き、**Connect** のステップで必要な接続だけを選びます。シークレットはチャットではなく [Credentials](/guide/credentials) に入れてください。[カスタムエージェントのクイックスタート](/guide/agents/quickstart)を参照してください。
</Tip>

## 5.2 チームの中を作業がどう流れるか

02:40 に起きる代表的な本番のインシデントを考えます。checkout のレイテンシが SLO を超えました。

1. **検出。** 検知の層が、レイテンシのアラート、データベースの接続エラーの急増、22 分前に反映されたデプロイを相関させて 1 つのインシデントにまとめ、下流の 41 のアラートを抑制します。

2. **分析。** オーケストレーターが、データベースと Kubernetes の専門家を並行して投入します。データベースのエージェントは、新しい N+1 のクエリのパターンによる接続プールの枯渇を見つけます。Kubernetes のエージェントは Pod が正常であることを確認し、インフラを除外します。オーケストレーターは両方の検出事項を、証拠を添えた根本原因の仮説にまとめます: 新しいデプロイがそのクエリのパターンを持ち込んだ、というものです。

3. **解決。** ポリシーは、SLO の違反中に、60 分未満のデプロイの自動ロールバックを許可しています。オーケストレーターはロールバック（L3 の事前承認された操作）を実行し、推論の連鎖全体をチームのインシデントのチャネルに投稿します。オンコールのエンジニアはそれを朝に読み、誰も呼び出されません。

4. **検証。** レイテンシは 4 分以内にベースラインに戻り、エラー率も解消します。システムは SLO の回復を確認し、問題のクエリを特定したうえでエンジニアリングチームの問題チケットを開き、インシデント後のレポートの下書きを作り、パターンをメモリに保存します。

経過時間: 10 分未満、起こされた人はゼロ。翌朝、エンジニアがレポートを確認し、クエリを修正し、再デプロイを承認します。この分担（02:40 の機械的な作業は機械が、09:00 のエンジニアリングの判断は人が担う）こそが、意図どおりに機能しているモデルです。

CloudThinker では、ロールバックのポリシーを 2 つの部分で表現します。**Allow** の [Rule](/guide/approvals/rules) が本番の接続でのロールバックの操作をカバーし、**Runs from** を **Resolve** に設定するため、**Auto** のモードの下で、その書き込みは人なしで実行できます。[runbook](/ja/guide/incident/runbooks) は、それを使うタイミングを示します: 60 分未満のデプロイで、SLO が違反しているときです。**Manual** の下では引き続き人がロールバックを承認するため、無人で実行させるには **Auto** の [Approval mode](/guide/approvals/approval-mode) を選んでください。

## 5.3 エージェントと人のインターフェース

エージェントは、エンジニアがいる場所にいます。主流のインターフェースのパターンは、会話と証拠の組み合わせです。エージェントは、検出事項、計画、承認のリクエストを、推論の連鎖全体、証拠へのリンク、ワンクリックの承認/却下の操作とともに、Slack や Teams に投稿します。ダッシュボードは傾向と監査のために残り、運用の会話はチャットで行われます。インターフェースの 2 つのルールが、特に大きな意味を持ちます。

1. **作業を見せる。** すべての結論には、調べたデータ、検討した仮説、代替案を退けた理由が付きます。透明な推論は、エンジニアの信頼を生む最大の要因であり、AIOps を沈めたブラックボックスの失敗への対策です。

2. **承認を手軽に、拒否を有益にする。** 承認は完全なコンテキスト付きのワンクリックであるべきです。却下はその理由を記録すべきです。すべての却下は、ポリシーの調整のための学習のシグナルだからです。

## 5.4 証拠: 4 つのデプロイ

匿名化した 4 つのデプロイと、それぞれが開始した自律性、範囲、測定したものを示します。3 つには結果があります。4 つ目は進行中です。

| 事例 | 業界と規模 | 範囲 | 開始 | 終了 | 期間 | 結果 |
| :---- | :---- | :---- | :---- | :---- | :---- | :---- |
| 1 | 消費者金融の貸し手、ベトナム、800 以上の支店 | 複数アカウントの AWS: コスト、衛生管理、インシデント | L1 | L2（中心の融資の経路は L1 のまま） | 4 週間のベースライン、3 か月以内に結果 | 手作業の運用作業の削減、数時間ではなく数分での根本原因、最適化可能な AWS の支出の回収 |
| 2 | デジタル決済のプラットフォーム、ベトナム、シリーズ A | 3 つの本番の Kubernetes クラスター、RDS のレプリカ | L2 | 元に戻せる操作で L3 | 3 か月以内 | 顧客から見えるダウンタイムゼロでのアップグレード、レプリカのコストの削減、月次の運用コストの縮小 |
| 3 | AI / SaaS のプラットフォーム、米国、EU、APAC | 3 リージョンのデプロイ、コンプライアンスのガードレール、運用 | L2 | L2〜L3 | デプロイまで 4 週間 | SOC 2、HIPAA、GDPR への準備、運用タスクの負荷の軽減、可用性の目標の維持 |
| 4 | 通信事業者のクラウドプロバイダー、ベトナム、数千のクラスター | OpenStack と VMware での設定と監査の自動化 | L1 | L3 を計画 | 進行中 | まだ公開していません |

### 1. 消費者金融の貸し手

- **課題。** AWS の環境が多数のアカウントに分散していました。コストとインシデントの作業は手作業で、障害を起こしている融資のアプリの原因を見つけるには、数時間のアカウントをまたいだ検索が必要でした。
- **与えた自律性。** 4 週間のベースラインのために、すべてのアカウントにわたる L1 の調査を行い、運用担当者自身の根本原因分析と照合しました。その後、コストと衛生管理の操作で L2 とし、修正をワンクリックの承認のために準備しました。
- **人の承認のまま残したもの。** 中心の融資の経路は、終始助言のみにとどめました。
- **結果。** 3 か月以内に: 上の表の結果に加え、重要なアプリの 24 時間体制の監視。

### 2. デジタル決済のプラットフォーム

- **課題。** 3 つの本番の Kubernetes クラスターで、ダウンタイムの時間枠なしにバージョンのアップグレードが必要で、同時に RDS のレプリカの支出が増えていました。
- **与えた自律性。** Kubernetes のライフサイクル、ライトサイジング、自己修復、レプリカのスケーリングで、事前承認された操作のクラスとして L2〜L3。
- **人の承認のまま残したもの。** アップグレードの元に戻せないステップ。
- **結果。** アップグレードは、顧客から見えるダウンタイムゼロで 3 つのクラスターすべてで実行されました。レプリカと運用コストの削減は 3 か月以内に実現しました。

### 3. AI / SaaS のプラットフォーム

- **課題。** 投資家が、厳しい可用性の目標を守りつつ、GDPR の下の 3 つのリージョンにわたって SOC 2 と HIPAA への準備を求めていました。
- **与えた自律性。** コンプライアンスのガードレールで L2、運用の修復で L2〜L3 とし、コンプライアンスに関わるすべてのステップをその場で記録しました。
- **結果。** 4 週間で 3 リージョンのデプロイ。ここでの準備とは、完了した監査ではなく、制御が自動化され、作業の進行に合わせて証拠が集められていることを意味します。

### 4. 通信事業者のクラウドプロバイダー（進行中）

- **課題。** 数百人の運用担当者が、ヘルスチェック、ドリフトの修正、監査の証拠を手作業で行っていました。ツールと人員が増えても、MTTR は横ばいのままでした。
- **計画している自律性。** フリート全体で L1 の調査、次に日常的なクラスターの健全性とドリフトで L2、そして最も安全な繰り返しの操作（クラスターの再起動、キャパシティの変更、証明書のローテーション）で L3。
- **人の承認のまま残すもの。** すべての操作に変更不能な記録を持つ、規制下の制御の経路。
- **結果。** 測定を進めています。数値は期間が終わり次第公開します。

これらのいずれも、勘定系の銀行のデプロイではありません。規制下の銀行の事例については、[お問い合わせ](https://cloudthinker.io/contact)ください。

<Info>
**ハイパースケーラーがエージェントをチームメイトとしてどう提供しているか**

- [AWS DevOps Agent](https://docs.aws.amazon.com/devopsagent/latest/userguide/about-aws-devops-agent.html) はアラートから調査を開始し、検出事項と緩和のステップを Slack と ServiceNow に送ります。
- [Azure SRE Agent](https://learn.microsoft.com/en-us/azure/sre-agent/overview) では、チームが独自のサブエージェントを追加でき、MCP サーバーを通じて他のツールに接続します。

教訓: エンジニアがすでに使っているツールで出会い、すべての検出事項とともに推論を見せることです。CloudThinker では、チャットには [Slack](/ja/guide/slack-integration)、[Microsoft Teams](/ja/guide/teams-integration)、[Google Chat](/guide/google-chat-integration) を、ITSM には [ServiceNow](/ja/guide/connections/servicenow) を、アラートのソースとしての PagerDuty には [Signals の Webhook](/ja/guide/pulse/setup) を使います。
</Info>
