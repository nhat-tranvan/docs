*エージェント型運用の成否は証拠で決まります。プログラムを、本番システムと同じように計測してください。*

この章では、追跡すべき数値、それをもとに組み立てるビジネスケース、そしてエージェントを信頼してよいかを判断するテストハーネスを紹介します。8.6節では、CloudThinker が各数値をどこで報告しているかを示します。

## 8.1 何が、どの順番で改善するか

改善は予測可能な順番で現れます。2週目に自律的な修正を期待する人が出ないよう、その順番に沿ってレポートを計画してください。

| 順番 | メトリクス | 改善の源泉 |
| :---- | :---- | :---- |
| 最初 | アラート量 | 人が呼び出される前の相関、重複排除、症状の抑制 |
| 2番目 | 根本原因までの時間 | エージェントがログ、メトリクス、変更履歴を並列に収集するため、ほとんどのインシデントで最も長い段階である診断が短くなる |
| 2番目 | トイル | トリアージ、証拠の収集、レポート作成が L1/L2 エンジニアからエージェントへ移る |
| 継続的 | クラウドコスト | 四半期ごとのレビューではなく、継続的なライトサイジングと未使用リソースのクリーンアップ |
| 最後 | 解決までの時間（MTTR） | 安全性がすでに証明されたアクションクラスに対する事前承認済みの修正 |

それぞれの改善の大きさは、データの品質と、信頼のはしご（[§7.3](/ja/learn/aio/chapter-7-humans-on-the-loop)）をどこまで登ったかによって決まります。

公開されている最も強力な数値はベンダーのものです。[AWS の報告](https://aws.amazon.com/blogs/mt/announcing-general-availability-of-aws-devops-agent/)によると、DevOps Agent のプレビュー顧客では、MTTR が最大75%短縮、調査が80%高速化、根本原因の正確性が94%でした。同じ発表の中で、Western Governors University（WGU）は、推定2時間かかっていた解決が28分に短縮されたと述べています。

これらは計画の前提にする結果ではなく、自社のパイロットで検証すべき主張として扱ってください。

## 8.2 運用ダッシュボード

プログラムは8つの KPI で運営します。オンコールのローテーションと一緒に毎月レビューしてください。

| KPI | 何が分かるか | 読み方 |
| :---- | :---- | :---- |
| **MTTD と MTTR** | 検出までの時間と、平均解決時間（インシデントの開始から解決まで） | 重大度別に傾向を見ます。エージェントが対応したインシデントと人が対応したインシデントを分けてください。そうしないと平均値が変化を隠してしまいます。 |
| **自律解決率** | 人のアクションなしで解決したインシデントの割合 | 成熟度を示す最良の単一指標です。アクションクラスが卒業するにつれて上昇するはずです。 |
| **推奨の受け入れ率** | 変更なしで承認されたエージェントの提案の割合 | 3つの基準があります。約70%未満なら、エージェントのコンテキストかポリシーを調整します。全体で80%に達したら、パイロットの Approve フェーズを終了できます（[§9.2](/ja/learn/aio/chapter-9-roadmap)）。1つのアクションクラスで約95%を超えたら、承認ステップの付加価値はほとんどないため、そのクラスを卒業させます。 |
| **ロールバックと介入の率** | 元に戻すか上書きする必要があったエージェントのアクション | 安全性の重しです。上昇したら、自律性の拡大を遅らせます。 |
| **再発インシデント率** | 同じ問題が繰り返し起きていないか | 再発が減っていれば、メモリと問題管理が機能しています。 |
| **カバレッジ率** | エージェントが L2 以上で対応できるインシデントクラスの割合 | 次にどのランブックを書き、どの接続を追加すべきかが分かります。 |
| **オンコール負荷** | エンジニア1人あたりの週ごとの呼び出し数（時間外の呼び出しは別に集計） | エンジニアとそのマネージャーが最も実感するメトリクスです。 |
| **エージェントの単位コスト** | 解決したインシデントあたり、カバーするサービスあたりのモデルとプラットフォームの支出 | 初日から追跡します。§8.4 を参照してください。 |

自律性のレベル（L0〜L4）は [§3.2](/ja/learn/aio/chapter-3-what-is-aio) で定義しています。

## 8.3 ビジネスケースを組み立てる

リターン側は3行です。それぞれに自社のインプットを使ってください。

| 項目 | 計算方法 | 用意するインプット |
| :---- | :---- | :---- |
| **回避したダウンタイム** | 年間インシデント数 × ダウンタイム1分あたりのコスト × パイロットで測定した MTTR の短縮分（分） | 1分あたりのコストは財務チームから入手します。ない場合は、Global 2000 企業で1分あたり約 $15,000 という [Splunk と Oxford Economics の2026年のベンチマーク](https://newsroom.cisco.com/c/r/newsroom/en/us/a/y2026/m05/the-600-billion-wake-up-call-new-splunk-research-reveals-downtime-is-a-systemic-business-crisis.html)を使います。決済やトレーディングのシステムではさらに高くなります。 |
| **転換したトイル** | エージェントが引き受けた L1/L2 の作業時間 × 1時間あたりのエンジニアリングの総コスト | 時間はチケットシステムか2週間の時間調査から得ます。エンジニアの採用が難しい組織では、多くの場合これが最大の項目になります。 |
| **回収したクラウドの無駄** | 実施したコスト推奨による検証済みの月間削減額 × 12 | 推奨が作成されたときに表示された見積もりではなく、各変更の前後のクラウドの請求額 |

コスト側には、プラットフォームのサブスクリプション、モデルの使用量、そしてシステムを統合し統治するためのエンジニアリング時間が含まれます。自律性ポリシーの責任者の時間も含めてください。

ケースは1つのルールで検証します。ダウンタイムの項目がなければ成り立たないなら、パイロットの領域の選択を誤っています。トイルの削減でケースが成り立つ領域を選び、回避したダウンタイムは上乗せとして扱ってください。

## 8.4 エージェントのユニットエコノミクス

エージェント型プログラムの運用コストの大半はモデルの推論です。推論コストの大半は、高コストな推論をどこで実行するかで決まります。だからこそ、低コストな知覚は常時稼働させ、フロンティアレベルの推論はそれを必要とする少数のシグナルのために取っておきます。

[§4.3](/ja/learn/aio/chapter-4-architecture) ではこれを二層の検知と呼んでいます。1件のインシデントをコストの対象として見てみましょう。

| 層 | 何を実行するか | 頻度 | 1回あたりのコスト |
| :---- | :---- | :---- | :---- |
| 検知 | すべてのシグナルに対する軽量な知覚 | 常時 | 最も低い |
| トリアージ | 確認する価値のあるシグナルのグループ化とフィルタリング | 単なるノイズではないすべてのシグナルに対して | より高い |
| 深い解決 | 複数ステップの推論：根本原因、修正、検証 | トリアージを通過したシグナルに対してのみ | 群を抜いて最も高い |

深い解決は1回あたりのコストが最も高いものの、実行される頻度は低いため、すべてのシグナルをカバーしながらも高コストな層はほとんど待機したままです。典型的な比率は環境によって差が大きすぎるため公開していません。自社の環境で3つの数値を測定してください。1日あたりのシグナル数、深い解決にエスカレーションされる割合、そして1回の深い実行のコストです。これらを掛け合わせれば、1日あたりの深い解決の支出が分かります。

だからこそ、解決したインシデントあたりのコストとカバーするサービスあたりのコストがダッシュボードに含まれています。ノイズの多いシグナルのすべてでフロンティアレベルの推論を実行するアーキテクチャは、最初の契約更新の前に自らのリターンを食いつぶします。最初からインシデントあたりの数値を追跡していなければ、それが起きていることに気づきません。

ベンダーを比較するときは、価格が価値にどう連動しているかを確認してください。検証済みの削減額に連動する料金のような成果ベースのオプションは、ベンダーが推論を無駄に増やす動機をなくします。どのような体系であっても、ビジネスケースに使う数値は、自社の90日間のベースライン（[§9.2](/ja/learn/aio/chapter-9-roadmap)）と比べて測定したものにしてください。

## 8.5 信頼する前にエージェントをテストする

前の章では、エージェント型運用を自己検証するものとして説明しました。この節では、そのチェックが実際にどのようなものか、そして自信満々に間違った修正を本番環境に届く前にどう捉えるかを示します。

評価ハーネスには4つの要素があります。

| 要素 | 役割 |
| :---- | :---- |
| **シナリオライブラリ** | 記録した実際のインシデントと意図的に注入した障害。それぞれに既知の正しい結果（正しい根本原因、安全なアクション、きれいなロールバック）があります |
| **シャドー実行** | エージェントは本番環境そのものではなく、本番環境のサンドボックスのコピーに対して行動します。そのため、提案されたアクションを影響なく観察できます |
| **正解に対する採点** | 正しい根本原因を見つけたか。安全なアクションを選んだか。そのロールバックは機能したはずか |
| **リグレッションゲート** | 新しいエージェントのバージョン、プロンプト、スキルは、ほかの本番コードと同じように、リリース前にライブラリを通過しなければなりません |

エージェントは決定論的ではありません。同じシナリオでも、実行ごとに異なる振る舞いをすることがあります。そのため、各シナリオを何度も実行し、結果のばらつきを採点してください。70%の確率で正しい修正と99%の確率で正しい修正は異なるリスクであり、どちらなのかは繰り返し実行して初めて分かります。

データベースの接続枯渇シナリオを例に、具体的なチェックを示します。ハーネスは、エージェントが次のことを行うかを検証します。

1. 根本原因としてコネクションプールの枯渇を挙げる。
2. サービスを再起動するだけでなく、正しい接続数の上限を復元する。
3. 接続数がベースラインに戻り、その状態を維持していることを確認する。

ステップ3は、エージェントが本番環境で実行するのと同じ Validate ステップを、既知の答えに対してテストするものです。ハーネスの中で自分自身の検証チェックを通過できないエージェントを、本番環境で無人で実行させてはいけません。

**CloudThinker では：** [§7.3](/ja/learn/aio/chapter-7-humans-on-the-loop) のように、ワークスペースを **Manual** にした状態でその時間帯の調査を依頼すれば、クローズしたインシデントを再現でき、その答えをポストモーテムと比べられます。このドキュメントでは組み込みのシナリオライブラリ、サンドボックスでのシャドー実行、リグレッションゲートについては説明していないため、それらは自分で構築する計画を立ててください。

## 8.6 CloudThinker でこれらの数値を確認する場所

CloudThinker でパイロットを実施している場合、ダッシュボードの大部分は次のページで報告されます。オンコール負荷とロールバック率は、ページングツールと変更管理ツールで追跡してください。

| KPI | 場所 |
| :---- | :---- |
| MTTD | 単独の数値としては報告されません。**Where the time goes** は最初のシグナルから始まるため、検出時間は監視ツールから取得してください。 |
| MTTR とその傾向 | **Resolve → Insights → Reliability**：**MTTR** と **MTTR over time**（[Insights](/guide/incident/insights)） |
| 根本原因までの時間 | **Resolve → Insights → Reliability**：**Alert → root cause**、および各段階の **Where the time goes** |
| 自律解決率 | **Resolve → Insights → Reliability**：**Auto-resolved** |
| 推奨の受け入れ | **Resolve → Insights → Accuracy and trust**：**Fix acceptance** と **Root-cause accuracy**。どちらもチームのレビューに基づきます |
| 再発インシデント | **Resolve → Insights → Reliability**：**Recurrence trend** |
| アラートのノイズ（MTTD とオンコール負荷の補助メトリクス） | **Resolve → Insights → Signal quality**：**Noise suppressed** と **Signals ingested**（[Signal quality のメトリクス](/ja/guide/pulse/analytics)） |
| カバレッジ率 | Insights では報告されません。[ランブック](/ja/guide/incident/runbooks)がカバーするインシデントの種類を、実際に発生している種類と比べて数えてください。 |
| クラウドの無駄 | **Optimize → Issues** には、実現した削減額ではなく、未対応の検出結果の見積もりが表示されます（[削減額の数え方](/ja/guide/cost-optimization/savings)）。変更をリリースしたら検出結果を **Implemented** にし、その削減額をクラウドの請求額で検証してください。 |
| エージェントの単位コスト | **Settings → Organization → Usage** には、インシデントごとではなく、**By Feature**、**By User**、**By Workspace** でクレジットが表示されます（[使用量](/ja/guide/billing/usage)）。解決したインシデントあたりのコストは、その月の Resolve のクレジットを、同じ月に Insights で解決したインシデント数で割って求めます。クレジットは、プランの[料金](/ja/guide/billing/pricing)で金額に換算します。 |

**Root-cause accuracy** は、チームが十分な数のインシデントをレビューして初めて意味を持ちます。報告する前に、同じタブの **Your review coverage** を確認してください。

<Tip>
**デプロイ前にベースラインを取る。** ビジネスケースで最もよくある失敗は、信頼できる「導入前」の数値がないことです。Insights は CloudThinker が対応したインシデントしかカバーしないため、最初のエージェントが本番環境に触れる前に、ページングツールとチケットツールから直近90日間の MTTR、アラート量、呼び出し数を、時間調査からトイルの時間を取得してください。
</Tip>
