プロダクション環境のデプロイが収束しつつあるリファレンスアーキテクチャは、オーケストレーター、スペシャリストのチーム、閉じた運用ループ、そしてコンテキストレイヤーで構成されます。

## 4.1 単一エージェントではなくマルチエージェントである理由

この章ではベンダーに依存しないパターンを説明します。4.2〜4.4節では各要素が CloudThinker のどこにあるかを示し、[第10.3節](/ja/learn/aio/chapter-10-road-ahead#103-ハイパースケーラーのエージェントかクラウドをまたぐ-1-つのプラットフォームか)ではハイパースケーラー独自のエージェントと比較します。

プロダクションシステムでは、万能なエージェント1つではなく、オーケストレーションされたスペシャリストのチームを使います。理由は実務的なものです。

1. **広さより深さ。** 厳選された K8s ツール、プロンプト、学習済みのパターンを持つ Kubernetes スペシャリストは、K8s の問題においてジェネラリストを上回ります。人間のチームが専門分化するのと同じです。

2. **影響範囲の限定。** 各スペシャリストは、自分の領域に必要な認証情報だけを持ちます。データベースエージェントはセキュリティグループを変更できず、コストエージェントはテーブルを削除できません。

3. **独立した進化。** スペシャリストは個別にアップグレード、評価、ロールバックできます。マイクロサービスの教訓をエージェントに適用したものです。

4. **監査可能な引き継ぎ。** エージェント間の委任によって、誰が何を決めたのかの明確な記録が残ります。モノリシックな推論ではこれが隠れてしまいます。

設計上の帰結として、オーケストレーションレイヤー（タスクのルーティング、コンテキストの管理、エラー処理）には、エージェントそのものと同じだけのエンジニアリングが必要です。

公開されている2つの事例が限界を示しています。

- **専門化を支持する事例。** Anthropic の[マルチエージェント・リサーチシステム](https://www.anthropic.com/engineering/multi-agent-research-system)は、リードエージェントが作業を並列の環境に分割します。単一エージェントと比べて品質が大きく向上した一方、トークンコストは大幅に高くなったと報告しています。そのコストこそが、[4.3](#43-検知と解決の二層構造) の二層設計が重要な理由です。
- **やりすぎを戒める事例。** Microsoft の Azure SRE Agent チームは、100以上のツールと50以上の細分化されたエージェントから始め、最終的に5つのコアツールと少数のジェネラリストに落ち着いたと[書いています](https://techcommunity.microsoft.com/blog/appsonazureblog/-/4481200)。専門化は領域と認証情報の境界で行い、数十のマイクロエージェントに分けないでください。エージェントやツールを1つ追加するたびに、コンテキスト、トークン、調整のコストがかかります。

## 4.2 リファレンスアーキテクチャ

プロダクションのエージェント型運用プラットフォームには5つのレイヤーがあります。プラットフォームを評価するときや自社で設計するときのチェックリストとして使ってください。

| レイヤー | 役割 | 評価時に確認すること | CloudThinker では |
| :---- | :---- | :---- | :---- |
| **オーケストレーター** | 目標やインシデントを受け取り、タスクに分割し、スペシャリストに作業を振り分け、結果をまとめ、人にエスカレーションする | 1つのエージェントが会話とエスカレーション経路を担っているか | 組み込みの [CloudThinker](/ja/guide/agents/overview) アシスタント |
| **スペシャリストエージェント** | 厳選されたツールとスコープを絞った認証情報を持つ領域の専門家（クラウド、セキュリティ、データベース、Kubernetes） | 独自のスペシャリストを追加し、それぞれの接続を制限できるか | CloudThinker が生成する一時的なサブエージェントと、あなたが作成する[カスタムエージェント](/guide/agents/quickstart) |
| **運用ループ** | 検出、分析、解決、検証。検証の段階こそがエージェントと自動化を分けるもので、システムが自分の作業を確認します。 | プラットフォームは行動後に結果を確認し、失敗時にロールバックするか | [Signals](/ja/guide/pulse/overview) が検出し、[Resolve](/ja/guide/incident/overview) が調査・修正し、[Approvals](/guide/approvals/overview) がどの書き込みを実行するかを決める |
| **ツールと連携** | クラウド API、オブザーバビリティ、CI/CD、ITSM、チャット。エージェントごとに最小権限の認証情報を使う | 認証情報はシステムごとにスコープが絞られているか、独自のツールを接続できるか | 独自の [MCP サーバー](/ja/guide/connections/mcp)を含む [Connections](/ja/guide/connections/overview) |
| **コンテキストとメモリ** | トポロジー、ランブック、過去のインシデント、チームの慣習、環境のメタデータ。エージェントが積み重ねで強くなる場所です。 | システムは学んだことを記憶しているか、それを確認・編集できるか | [Memory](/guide/memory)、[ランブック](/ja/guide/incident/runbooks)、[インシデントメモリ](/ja/guide/incident/incident-memory) |

## 4.3 検知と解決の二層構造

素朴なエージェント設計はアラートごとに1回モデルを呼び出し、プロダクション規模では破綻します。成熟したプラットフォームは2つの層を分けます。すべてのシグナルを監視する低コストで常時稼働の検知層と、検知層が価値のあるものを見つけたときにだけ複数ステップの本格的な調査を行う高コストな推論層です。これによって 24 時間 365 日のカバーが手頃なコストで可能になります。プラットフォームを評価するときは、何が高コストな層に届くのかをどう決めているかを確認してください。その判断がモデルの請求額を左右します。

CloudThinker では、[Signals](/ja/guide/pulse/overview) が検知層です。重複とノイズを除外し、関連するアラートをクラスターにまとめ、対応が必要なシグナルを持つクラスターだけをトリアージに送ります。トリアージでは CloudThinker がインシデントを作成するか既存のものと照合し、調査します。何がエスカレーションされるかは3か所で調整します。

- [ノイズ抑制](/ja/guide/pulse/clusters#ノイズ抑制)の **Snoozes** で、既知のイベントを除外します。
- **Resolve → Issues** の **AI auto-investigate** スイッチで、CloudThinker が自ら調査するか、誰かが **Investigate** をクリックするのを待つかを決めます。[Resolve](/ja/guide/incident/overview#誰が調査を開始するかを選ぶ) を参照してください。
- [Signals のセットアップ](/ja/guide/pulse/setup)でどのソースを接続するかによって、そもそも何が Signals に届くかが決まります。

## 4.4 パイプライン内のデータ保護

規制業界では、テレメトリは機密情報です。ログやクエリから顧客の個人情報（PII）、認証情報、アカウントデータが漏れます。新たなベストプラクティスはトークン化の境界です。データがモデルに届く前に、機密性の高い値をトークンに置き換える PII 対応のレイヤーです。プライベートなデプロイと組み合わせれば、銀行などの規制対象企業も、生のテレメトリを境界の外に出さずにエージェント型運用を導入できます。データの所在と管理については[第6章](/ja/learn/aio/chapter-6-trust-governance#63-データの所在と管理)で詳しく扱います。

### CloudThinker では

- **マスキング。** [Guardrails](/guide/security/custom-guardrails) は、エージェントが読み取る前に機密性の高い値をプレースホルダーに置き換えます。メールアドレス、電話番号、クレジットカード、IBAN、MAC アドレス、API キー、クラウドの認証情報はデフォルトで有効です。IP アドレス、公開鍵、クラウドアカウント ID はデフォルトで無効です。独自の ID パターンは **Settings → Organization → Guardrails** で追加できます。
- **デプロイ。** CloudThinker Cloud、自社のマシン上の [Environments](/guide/workers) と組み合わせた Cloud、そしてアーリーアクセスプログラムを通じた専用・セルフホスト・エアギャップのデプロイがあります。[デプロイオプション](/ja/guide/deployment/overview)を参照してください。
- **自社アカウントでのモデル呼び出し。** [BYOK](/ja/guide/byok) を使うと、モデル呼び出しを自社のモデルプロバイダーアカウントで実行できます。

## アーキテクチャチェックリスト

どのベンダーにも、あるいは自社のチームにも、次のことを確認してください。

1. 1つのオーケストレーターが、領域横断の推論と人へのエスカレーションを担っているか。
2. 各スペシャリストは、自分の領域に必要な認証情報だけを持っているか。
3. すべての作業が検出、分析、解決、検証を通り、行動後に結果が確認されているか。
4. 高コストな推論層の前に低コストな検知層があり、何がエスカレーションされるかを調整できるか。
5. モデルを呼び出す前に、個人の識別情報やシークレットがマスクされているか。
6. 規制対象のワークロード向けに、プライベートまたはセルフホストのデプロイオプションがあるか。
7. システムはインシデント間でメモリを保持し、毎回ゼロから始めずに済むか。
