*段階的で証拠に基づく導入の道筋: 最初の価値まで 90 日、新しい運用モデルまで 12 か月。*

この章では、始める前に何を直すか、最初の 90 日をどう進めるか、どう拡大するか、そしていつ待つべきかを説明します。9.6 節では、パイロットの各フェーズを CloudThinker の設定に対応付けています。

## 9.1 準備: エージェントがあなたに求めるもの

エージェントは、受け継いだ環境を増幅します。最初のデプロイの前に、5 つの基盤を確認してください。

| 基盤 | 「準備ができている」状態 | 欠けている場合 |
| :---- | :---- | :---- |
| **オブザーバビリティ** | 対象の領域を十分にカバーする、一元化されたログ、メトリクス、トレース | エージェントは存在しないシグナルについて推論できません。まずこれを直してください。 |
| **アクセスのアーキテクチャ** | エージェントごとに発行できる、範囲が限定された短期の認証情報 | すべてが 1 つの管理者のキーで動いているなら、エージェントが行動できるようになる前に直してください。CloudThinker では、認証情報は接続ごとです。[AWS](/ja/guide/connections/aws#必要な権限)、[Azure](/ja/guide/connections/azure)、[Google Cloud](/ja/guide/connections/gcp) のセットアップのように、パイロットの各接続に独自の読み取り専用のロールを与えてください。 |
| **信頼できる情報源** | エージェントが触れるシステムの Infrastructure as Code（IaC）。部分的でも構いません | エージェントには安全な変更の仕組みがなく、差分を取れる監査証跡も失われます。 |
| **文書化された意図** | SLO、runbook、アーキテクチャのメモ。不完全でも構いません。 | エージェントには、システムがどう振る舞うべきかのコンテキストがありません。 |
| **説明責任を持つオーナー** | 自律性のポリシーを設定し、オンコールのローテーションを巻き込む立場を持つ、名前のあるシニアのエンジニア | プログラムが助言のみで停滞するか、統制のない行動へと流れていきます。 |

## 9.2 90 日間のパイロット

この表の自律性のレベルは [§3.2](/ja/learn/aio/chapter-3-what-is-aio) から来ています: **L0** は観察して報告し、**L1** は調査して推奨し、**L2** は修正を準備して承認を待ち、**L3** は事前承認された操作のクラスを実行して事後に人に知らせます。

| フェーズ | 週 | すること | 終了基準 |
| :---- | :---- | :---- | :---- |
| **ベースラインと範囲** | 1–2 | MTTR、アラートの件数、ページ数、労力の時間を記録します。1 つの製品のインシデント対応や 1 つのアカウントのクラウドのコストなど、範囲が限定された領域を 1 つ選びます。 | 署名されたベースライン、範囲を決めた領域、合意した成功の指標 |
| **観察（L0–L1）** | 3–6 | 読み取りアクセスでテレメトリーとツールを接続します。エージェントはエンジニアと並行してすべてのインシデントを調査し、オンコールが各分析を評価します。 | 根本原因分析の少なくとも 70% が、オンコールによって正しいとされる |
| **承認（L2）** | 7–10 | エージェントは証拠とともに完全な修正を提案します。人がそれぞれを承認します。受け入れ率とロールバック率を追跡します。 | 少なくとも 80% の受け入れ、有害な操作ゼロ、MTTR の目に見える改善 |
| **卒業（L3）** | 11–13 | 最も安全で最も繰り返される 5〜10 の操作のクラスを事前承認します。エージェントが行動し、その後通知します。すべての操作を毎週確認します。 | 本番での最初の自律的な解決と、ベースラインに対する MTTR の変化の記録 |

最も難しい問題から始めないでください。パイロットの役割は、証拠と信頼を生むことです。頻繁で繰り返し起きるインシデントのある退屈な領域が、最も早く統計的な確信を築きます。良い候補: Kubernetes の Pod の再起動、ディスクの逼迫、証明書の期限切れ、コストの異常。

ハイパースケーラーも同じ形を勧めています。AWS の [DevOps Agent のベストプラクティス](https://aws.amazon.com/blogs/devops/best-practices-for-deploying-aws-devops-agent-in-production/)は、絞り込んだ範囲から始め、調査の結果に基づいて広げるよう述べています。ベンダーがこれらのフェーズを飛ばすよう言うなら、その理由を尋ねてください。

## 9.3 拡大: 4 か月目から 12 か月目

| 動き | 意味 |
| :---- | :---- |
| **自律性だけでなく領域を広げる** | データベース、セキュリティ、コストなど、一度に 1 つの領域を追加します。それぞれが、同じ観察、承認、卒業の順序をたどります。 |
| **ガバナンスを強制可能にする** | 自律性のポリシーを、文書から強制される設定へと移します。監督の層を加え、エージェントの操作を自動の証拠とともに変更管理に流し込みます。 |
| **メモリの層を築く** | エージェントが知っていることを整えます: トポロジー、規約、過去のインシデント、チームの知識。時間とともに、これがあなたのデプロイを真似しにくくするものになります。 |
| **オンコールを再編する** | 自律的な解決が増えるにつれて、ローテーションを統合し、取り戻したシニアの時間を予防の作業に移し、[§7.2](/ja/learn/aio/chapter-7-humans-on-the-loop) のエージェントオペレーションと自律性のポリシーの役割を正式にします。 |
| **毎月報告する** | [§8.2](/ja/learn/aio/chapter-8-measuring) のダッシュボードを、エンジニアリングとビジネスに公開します: MTTR の傾向、自律的な解決の率、避けられたページ、節約した金額。予算が付くプログラムは、測定されているプログラムです。 |

## 9.4 中止される 40% はどう失敗するか

[Gartner は、2027 年末までにエージェント型 AI のプロジェクトの 40% 以上が中止されると予測しています](https://www.gartner.com/en/newsroom/press-releases/2025-06-25-gartner-predicts-over-40-percent-of-agentic-ai-projects-will-be-canceled-by-end-of-2027)。3 つの原因を挙げています: 増大するコスト、不明確なビジネス価値、不十分なリスクの制御。運用では、それらが 5 つの具体的な失敗として現れます。

| 失敗 | Gartner の原因 | 起こること | 対策 |
| :---- | :---- | :---- | :---- |
| **卒業しないパイロット** | 不明確な価値 | 永遠に助言のみは安全に感じられますが、何も証明しません。更新の時期が来ても、示せる MTTR の変化がありません。 | 初日に卒業の基準に署名し、予定どおりにそれを守ります。 |
| **証拠より先の自律性** | 不十分なリスクの制御 | 午前 3 時の自信満々で誤った操作 1 つは、100 の良い操作が得る以上の信頼を失わせます。 | フェーズを決して飛ばしません。受け入れ率とロールバック率にペースを決めさせます。 |
| **オーケストレーションのないツールの乱立** | 増大するコスト、不明確な価値 | 互いにつながらない 5 つの単機能のエージェントが、余分なライセンスとともに回転椅子の問題を呼び戻します。[§10.3](/ja/learn/aio/chapter-10-road-ahead) は、同じ問題を単一のクラウドのエージェントにまたがってたどっています。 | 1 つのオーケストレーター、1 つの監査証跡、1 つのダッシュボード。 |
| **際限のないモデルの支出** | 増大するコスト | ノイズの多いすべてのシグナルに最先端の推論を使うと、最初の更新の前にリターンが消えます。 | 初日からの 2 層の検知と、インシデントごとのコストの追跡（[§8.4](/ja/learn/aio/chapter-8-measuring)）。 |
| **ツールの購入として扱う** | 3 つすべて | [第 1 章](/ja/learn/aio/chapter-1-complexity-crisis)の実験と本番の間のギャップは、テクノロジーのギャップではなく、運用モデルのギャップです。 | ライセンスだけでなく、役割の変更、ポリシーの作業、信頼のはしごに予算を割きます。 |

## 9.5 デプロイすべきでないとき

待つべき場合もあります。以下のそれぞれは、永続的な判定ではなく、先に直すべきものです。そのいずれかを抱えたままデプロイすると、高くつく失望を買うことになります。

| 失格の要因 | 妨げになる理由 | 先に直すこと |
| :---- | :---- | :---- |
| **推論の材料となるシグナルがない** | オブザーバビリティがまばらか断片的だと、エージェントはノイズから自信満々に推論します。盲点を増幅すると、自信満々の盲点が生まれます。 | 対象の領域のログ、メトリクス、トレースを一元化します。 |
| **1 つの共有の管理者の認証情報** | エージェントの影響範囲を限定したり、侵害されたエージェントを封じ込めたりできません。 | 自律的な操作を許可する前に、エージェントごと（CloudThinker では接続ごと）に、範囲が限定された短期の認証情報を発行します。 |
| **自律性のポリシーのオーナーがいない** | プログラムが助言のみで停滞するか、統制のない行動へとよろめきます。 | パイロットを始める前にオーナーを決めます。後で埋める役割ではありません。 |
| **変更管理に機械が起こす変更の経路がない** | エージェントの操作がガバナンスを迂回する（規制下の環境では受け入れられません）か、完全にブロックされます。 | 監査証跡付きの、機械が提案し人が承認する変更の経路を追加します。 |
| **最初の対象が、最も重要で最も元に戻しにくいシステム** | 誤った操作が壊滅的な場所から始めると、信頼のはしごが逆さまになります。 | 範囲が限定され元に戻せる領域を待つか、意図的に切り出します。 |

もう 1 つの失格の要因は、インフラとは関係がありません。組織がライセンスだけを買い、役割の再設計、ポリシーの作業、信頼のはしごに予算を割けないなら、システムの準備がどれほど整っていても、中止される 40% に入ることになります。

## 9.6 CloudThinker でパイロットを実行する

CloudThinker でパイロットを実行する場合、各フェーズは確認できる設定に対応します。

| フェーズ | CloudThinker では |
| :---- | :---- |
| **ベースラインと範囲** | まず [Approval mode](/guide/approvals/approval-mode) を **Manual** に設定し（**Settings → Workspace → Autonomy → Rules** の **When no Rule matches**）、その行はワークスペースに従わないため、[**Automations** もオーバーライド](/guide/approvals/approval-mode#set-a-mode-for-a-run-type)して **Manual** にします。次に、1 つの AWS アカウントやステージングの Kubernetes クラスターなど、範囲が限定された 1 つの領域だけの[接続](/ja/guide/connections/overview)を、読み取り専用の認証情報で追加します。ベースラインのために、ページングのツールから過去 90 日分の MTTR とページ数をエクスポートします。CloudThinker は接続する前の期間を測定できません（[§8.2](/ja/learn/aio/chapter-8-measuring)）。 |
| **観察** | **Manual** のままにします。実行タイプ、Automation、チャットが独自により緩いモードを選んでいない限り、読み取りは常に実行され、すべての書き込みは人を待ちます。オンコールに、インシデントの **Was Resolve's diagnosis right?** で各診断の正誤をマークしてもらいます。評価にはワークスペースの Developer または Admin のロールが必要なため、評価者には少なくとも Developer のロールを与えるか、Developer か Admin にオンコールの判定を記録してもらいます。 |
| **承認** | **Manual** のままにし、提案された修正が適切な人に届くよう、**Settings → Workspace → Autonomy → Approvers** で [Approvers](/guide/approvals/approvers) のグループを追加します。承認のカードはチャットに表示され、Google Chat でも機能します。Slack と Microsoft Teams は、承認のために Web アプリにリンクします。メールやチャットでリクエストを送るには、[通知](/ja/guide/notifications)で **Agent approvals** をオンにします。**Resolve → Insights → Accuracy and trust** で **Fix acceptance** を追跡します。 |
| **卒業** | 変更なしで約 95% の承認とロールバックなしを達成した特定の操作を、特定の接続で **Allow** する [Approval Rules](/guide/approvals/rules) を受け入れます（[§8.2](/ja/learn/aio/chapter-8-measuring)）。その後、**Workspace mode** を **Auto · Rules · Ask me** に切り替えます。Allow の Rule が書き込みを単独で実行するのは **Auto** の下だけで、AI の判断がオフなら、どの Rule も許可しない書き込みは引き続き人を待ちます。 |
| **報告** | [Resolve Insights](/guide/incident/insights) から、MTTR、自動解決の割合、ノイズの数値を取得します。各 KPI がどこにあるかは [§8.6](/ja/learn/aio/chapter-8-measuring) に一覧があります。 |

[CloudThinker について](/ja/learn/aio/about-cloudthinker)では、このフィールドガイドの残りをプロダクトの機能に対応付けています。
