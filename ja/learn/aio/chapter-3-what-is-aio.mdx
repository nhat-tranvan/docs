*定義は重要です。「エージェント」は、エンタープライズソフトウェアで最も乱用されている言葉だからです。*

この章では 4 つの道具を提供します。引用できる定義、エージェントが単独で何をしてよいかを決める 5 段階の自律性のスケール、エージェント型オペレーションではないものの一覧、そしてベンダーのための 5 つの質問のテストです。

## 3.1 実用的な定義

<Info>
**定義**

エージェント型インフラ運用（AgenticOps）とは、AI エージェントが、クラウドとオンプレミスのインフラにわたって、運用作業の中心となるループ（状態を検出し、原因を分析し、問題を解決し、結果を検証する）を実行する運用モデルです。エージェントは、人が定義する明示的なポリシーの下で作業します。人はループの *中* で実行するのではなく、ループの *上* で監督します。
</Info>

この意味でのエージェントは、runbook を持つチャットボットでも、LLM を後付けしたスクリプトでもありません。本物のオペレーションのエージェントには 5 つの特性があります。どのツールを評価するときも、チェックリストとして使ってください。

| 特性 | 意味 | 確認すべきこと |
| :---- | :---- | :---- |
| **目標指向** | 一歩ずつの指示ではなく、成果を受け取る | 「checkout のレイテンシを 300ms 未満に保つ」や「月次のクラウドの支出を予算内に保つ」と言える |
| **知覚的** | プロンプトを待つのではなく、テレメトリーを継続的に読む | メトリクス、ログ、トレース、イベント、設定の状態、コストデータを取り込む |
| **推論** | 因果の仮説を立てて検証し、代替の修正を比較する | エンジニアが監査できる言葉で考えを説明する |
| **ツールの使用** | エンジニアがすでに使っているインターフェースを通じて行動する | 範囲が限定され監査可能な認証情報で、クラウドの API、kubectl、Terraform、SQL、CI/CD を扱う |
| **自己検証** | 行動した後、成果が達成されたかを確認する | 修正が機能しなかった場合にエスカレーションまたはロールバックする |

ツールにこれらのいずれか 1 つでも欠けている場合は、エージェントではなくアシスタントとして扱ってください。

## 3.2 自律性のスペクトル

自律性はオンかオフかではありません。成熟したエージェント型のプラットフォームは、それをポリシーのダイヤルとして提供し、通常は操作のクラス（例:「Pod を再起動する」）ごと、環境（例: 本番とステージング）ごとに設定します。

| レベル | 名前 | エージェントの振る舞い | 人の役割 |
| :---- | :---- | :---- | :---- |
| L0 | 観察 | 監視して報告する。行動はしない | すべてを実行する |
| L1 | 助言 | 調査し、証拠とともに推奨する | 判断して実行する |
| L2 | 承認付きで行動 | 修復を完全に準備し、承認を待つ | ワンクリックで承認/却下 |
| L3 | 通知付きで行動 | 事前承認された操作のクラスを実行し、人に知らせる | 事後に確認する |
| L4 | 領域内で自律 | ポリシーの範囲内で、限定された領域をエンドツーエンドで担う | ポリシーを設定し、成果を監査する |

ほとんどの組織は、複数のレベルを同時に運用しています。すべての操作のクラスは低いレベルから始まり、実績で上がっていきます。証拠がそろった後の一般的な上限:

| 操作の種類 | 例 | 一般的な上限 |
| :---- | :---- | :---- |
| 元に戻せて、影響範囲が小さい | Pod の再起動、キャッシュのクリア、レプリカセットのスケール | L3〜L4 |
| 重大な変更 | スキーマのマイグレーション、セキュリティグループの変更、フェイルオーバー、認証情報のローテーション（認証情報を使うすべてのものが壊れる可能性があります） | L2 |
| 新しいもの | この環境でエージェントがこれまでに行ったことのない修復 | L1 |

操作のクラスを 1 段階上げるのは、現在のレベルで機能するという証拠がある場合だけにしてください。[第 8 章の KPI](/ja/learn/aio/chapter-8-measuring#82-運用ダッシュボード) を関門として使います: その操作のクラスの受け入れ率が約 95% を超え、ロールバックと介入の率が横ばいか低下していることです。それより速くしてはいけません。[第 7 章](/ja/learn/aio/chapter-7-humans-on-the-loop#73-信頼は少しずつ築かれる)では、これを段階的な信頼のはしごにしています。

### CloudThinker では

CloudThinker は L0 から L4 のラベルを使いません。読み取りは常に実行され、すべての書き込みは [Approvals](/guide/approvals/overview) を通ります。これは **Settings → Workspace → Autonomy → Rules** の **When no Rule matches** で設定します。各レベルは次の設定に対応します。

| レベル | CloudThinker での実現方法 |
| :---- | :---- |
| L0〜L1 | 調査だけを依頼し、エージェントが決して変更してはならない接続では **Allow writes** をオフにしておきます。**Deny** の [Rule](/guide/approvals/rules) が 2 つ目の層を加えます。 |
| L2 | [Approval mode](/guide/approvals/approval-mode) を **Manual** に設定し、すべての書き込みを人が承認するようにします。**Ask first** の Rule で、1 種類の書き込みに絞り込めます。 |
| L3 | **Auto** のモードを設定した状態で、受け入れられた **Allow** の Rule が、指定した接続で 1 つの操作を単独で実行します。 |
| L4 | 1 つのスイッチはありません。範囲が限定された領域を [Automation](/guide/automation/automations) として実行し、その書き込みには **Allow** の Rule を使います。 |

新しいワークスペースは **Auto · Rules + AI · Ask me** で始まります。これは、AI の判断で安全な書き込みを許可し、残りは人に確認します。受け入れられた [Rule](/guide/approvals/rules) が最初に判断し、どの Rule にも一致しない書き込みは Approval mode が扱います。

<Info>
**ハイパースケーラーがダイヤルをどう提供しているか**

- [Gemini Cloud Assist investigations](https://docs.cloud.google.com/cloud-assist/investigations) は根本原因分析を実行し、観察を報告します。リソースは変更しません（L1）。
- [AWS DevOps Agent](https://docs.aws.amazon.com/devopsagent/latest/userguide/about-aws-devops-agent.html) はインシデントを調査し、実行すべき緩和計画を渡します（L1〜L2）。
- [Azure SRE Agent](https://learn.microsoft.com/en-us/azure/sre-agent/overview) には、操作があなたの承認を待つ Review モードと、許可した操作のためのより自律的なモードがあります（L2〜L3）。

3 つとも、エージェントを少ない信頼から始め、より多くの信頼を獲得させます。
</Info>

## 3.3 エージェント型オペレーションではないもの

「エージェントウォッシング」は、Gartner が名前を付けるほど一般的です。本物のエージェントの能力なしに、アシスタント、チャットボット、RPA を「エージェント」として再ブランド化するベンダーのことです。[2025 年 6 月のプレスリリース](https://www.gartner.com/en/newsroom/press-releases/2025-06-25-gartner-predicts-over-40-percent-of-agentic-ai-projects-will-be-canceled-by-end-of-2027)で、Gartner は、エージェント型 AI を主張する数千のベンダーのうち、本物は約 130 社にすぎないと推定しました。エージェント型オペレーションが何で *ない* かを知ることが、購入者にとって最善の防御です。

1. **ダッシュボードの上のチャットボットではありません。** テレメトリーとのチャットは機能であって、運用モデルではありません。人が答えを読んでから作業をしに行かなければならないなら、マーケティングが何と言おうと、まだ第 3 世代（[第 2 章](/ja/learn/aio/chapter-2-automation-to-autonomy)を参照）にいます。

2. **無人のオペレーションではありません。** 信頼できる実務家で、人を取り除くことを主張する人はいません。目指すのは人のレバレッジです。かつてチームを要した作業を、1 人のエンジニアが監督することです。

3. **エンジニアリングの規律の代わりではありません。** エージェントは与えられた環境を増幅します。弱いオブザーバビリティ、IaC の欠如、文書化されていないシステムは、弱いエージェントを生みます。ゴミのようなコンテキストを入れれば、ゴミのような自律性が出てきます。

4. **何でもこなす 1 つの巨大なモデルではありません。** 次の章で示すように、本番のシステムは、単一の超大型モデルではなく、オーケストレーションされた専門家のチームに収束しつつあります。

<Warning>
**ベンダーのための 5 つの質問のテスト**

「エージェント型」を名乗るベンダーに尋ねてください。

1. システムは修復をエンドツーエンドで実行できるのか、それとも推奨だけか?
2. 自身の成果を検証し、失敗したらロールバックするか?
3. 自律性を操作のクラスごと、環境ごとに設定できるか?
4. すべての操作に、完全で変更不能な推論の記録が付いているか?
5. 直近の 3 つの本番のデプロイでの、ロールバックと介入の率はどうだったか?

本物のプラットフォームは、ロードマップのスライドではなく、証拠で 5 つすべてに答えます。エージェントウォッシングは、たいてい 2 つ目の質問で失格になります。
</Warning>

## 3.4 現在エージェントが担える運用作業の範囲

最初の領域を選ぶには、この表を使ってください。一般的な自律性が最も高く、操作を最も元に戻しやすいところから始めます。通常はクラウドのコストか Kubernetes の運用で、その後広げていきます。最後の列は、CloudThinker でどこから始めるかを示します。

| 領域 | 代表的なエージェントのタスク | 一般的な自律性（2026 年） | CloudThinker では |
| :---- | :---- | :---- | :---- |
| インシデント対応 | トリアージ、相関分析、根本原因分析、修復、インシデント後のレポート | L1〜L3 | [Resolve](/ja/guide/incident/overview) |
| クラウドのコスト（FinOps） | ライトサイジング、アイドルなリソースのクリーンアップ、コミットメントの計画、異常検出 | L2〜L4 | [Optimize](/ja/guide/cost-optimization/overview) |
| Kubernetes の運用 | Pod とノードの健全性、リソースの調整、アップグレードの支援、キャパシティの計画 | L2〜L3 | [Kubernetes 接続](/ja/guide/connections/kubernetes) |
| データベースの運用 | 遅いクエリの分析、インデックスの助言、レプリケーションの健全性、ストレージの予測 | L1〜L3 | [PostgreSQL](/ja/guide/connections/postgresql) などのデータベースの接続 |
| セキュリティの運用 | 設定ミスの検出、CVE のトリアージ、IAM の衛生管理、コンプライアンスの証拠 | L1〜L2 | [Cyber](/guide/security/cyber-overview) |
| 変更とリリース | デプロイ前のリスク分析、カナリアの監視、自動のロールバック | L2〜L3 | デプロイ前のリスクには [Review](/ja/guide/code-review/overview) |
| Infrastructure as Code | ドリフトの検出、モジュールの生成、プランのレビュー、ステートの衛生管理 | L1〜L3 | [Terraform 接続](/guide/connections/terraform) |

ここでの自律性の範囲は、2026 年の業界で一般的なものであり、固定の上限ではありません。自社のレベルは、オブザーバビリティ、IaC、runbook の質によって決まります。
