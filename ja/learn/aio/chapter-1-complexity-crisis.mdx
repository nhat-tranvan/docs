現代のインフラは、人間のチームが頭の中で把握できる範囲を超えました。複雑さはマシンの速度で複利的に増大する一方、チームのキャパシティは採用1人分ずつしか増えません。この章では、そのギャップがどこから生まれるのか、よくある対策がなぜ行き詰まるのか、そしてそれが運用の進め方にどう影響するのかを示します。

## 1.1 複雑さは複利的に増大するが、ヘッドカウントは増えない

3つの力が掛け合わさって危機が生まれました。

| 力 | 何を変えたか |
|---|---|
| マイクロサービス | モノリスが、独立してデプロイされ独立して障害を起こす数百のサービスに分割されました。 |
| クラウド | インフラがプログラマブルでエラスティックになり、常に変化するようになりました。 |
| AI ワークロード | GPU フリート、ベクターデータベース、推論パイプラインが、コストと信頼性の新たな問題をもたらしました。 |

それぞれの力は単独なら管理できます。しかし組み合わさると、人間のチームでは完全に観察することすらできず、ましてや制御などできないシステムが生まれます。

その結果は、あらゆる運用チームの日常と損益計算書に表れます。

1. **アラート疲れ。** 多くの運用チームは1日に数百件のアラートを処理しています。その大半はノイズ、重複、または1つの原因から派生した下流の症状です。エンジニアは読むのをやめ、本当に重要な1件のアラートが埋もれてしまいます。

2. **調査のトイル。** インシデント対応の時間を奪うのは修復ではなく診断です。エンジニアは仮説を立てる前に、十数個のダッシュボードを行き来し、ギガバイト単位のログを grep し、最近のデプロイをたどり直します。

3. **高コストなダウンタイム。** Splunk と Oxford Economics が2026年5月に Global 2000 企業のエグゼクティブ2,000名を対象に実施した調査 [The Hidden Costs of Downtime 2026](https://newsroom.cisco.com/c/r/newsroom/en/us/a/y2026/m05/the-600-billion-wake-up-call-new-splunk-research-reveals-downtime-is-a-systemic-business-crisis.html) によると、計画外ダウンタイムの損失は年間総額 \$6,000億に達し、2年で50%増加しています。この調査では、ダウンタイム1分あたりの平均損失は \$15,000、1回のインシデント後の株主価値の平均下落率は3.4%と報告されています。

4. **人材不足。** シニア SRE は高価で採用が難しく、今いる人材も午前3時の呼び出しで燃え尽きていきます。

5. **ツールを増やしても増えるトイル。** 監視への支出は増えても、トイルは減りません。シグナルと人間の間にインテリジェントな仕組みがない限り、ツールが増えればシグナルが増え、シグナルが増えれば作業が増えます。

## 1.2 なぜ旧来の答えが通用しなくなったか

運用はこれまで3つの方法でスケールしようとしてきましたが、いずれも限界に達しています。

| アプローチ | 行き詰まる理由 |
|---|---|
| **人を増やす** | 複雑さが指数関数的に増大するのに対し、コストは線形に増大します。労働市場はエンジニアを供給できず、チームの規模とともに調整のオーバーヘッドも増えます。 |
| **自動化を増やす** | スクリプトとランブックは既知の障害しかカバーしません。すべてのランブックは昨日の障害パターンをコード化したものであり、カタログ自体がメンテナンスの負担になります。本当に痛手となる未知の障害はすり抜けてしまいます。 |
| **ダッシュボードを増やす** | オブザーバビリティはシステムを可視化しましたが、操作可能にはしませんでした。アクションを伴わない可視性は、ボトルネックをダッシュボードを読む人へと戻すだけです。 |

共通する欠陥は、3つとも人間を実行パスに置き続けることです。すべての検出、診断、修正は人を待ちます。人間の注意はシステムの中で最も希少なリソースであり、旧来の答えはどれもそれをさらに多く消費します。

<Warning>
来年の成長に向けた計画が「人を増やし、ランブックを増やし、ダッシュボードを増やす」であれば、同じアラート量と同じ午前3時の呼び出しが、より高いコストで続くと考えてください。
</Warning>

## 1.3 このガイドの主張

運用の複雑さは今やマシンの速度で増大しています。それについていけるのは、マシンのキャパシティで動作するシステム、つまり検出し、分析し、解決し、検証するエージェントだけです。人間の役割は実行者から監督者へと移ります。意図を設定し、影響の大きい変更を承認し、結果に責任を持つ立場です。

<Info>
**ハイパースケーラーからの証拠**

Microsoft は、社内に1,300以上の Azure SRE Agent を展開し、35,000件以上のインシデントを緩和し、20,000時間以上のエンジニアリング工数を削減したと[報告しています](https://github.com/microsoft/sre-agent)。Google の SRE の実践では、各 SRE の時間に占める[トイルの割合を50%に制限しています](https://sre.google/sre-book/eliminating-toil/)。際限のない運用負荷は、人員配置の問題ではなくエンジニアリングの失敗だからです。
</Info>

これは遠い未来の予測ではなく、異論がないわけでもありません。同じ調査会社による2つの予測が並んでいます。

- Gartner の2025年12月のリサーチ *Predicts 2026: AI Agents Will Transform IT Infrastructure and Operations*（購読者限定）は、今後5年で AI エージェントが I&O のチーム、役割、運用モデルを作り変え、エージェントの自律性と信頼が高まるにつれて企業が human-in-the-loop の関与を着実に減らしていくと予測しています。
- 一方で Gartner は、2027年末までにエージェント型 AI プロジェクトの40%以上が、コストの増大、ビジネス価値の不明確さ、または不十分なリスク管理を理由に中止されるとも[予測しています](https://www.gartner.com/en/newsroom/press-releases/2025-06-25-gartner-predicts-over-40-percent-of-agentic-ai-projects-will-be-canceled-by-end-of-2027)（2025年6月）。

どちらも正しく、同じ分かれ道を描いています。技術の方向性はすでに決まっています。あなたのプログラムが変革を遂げる多数派に入るか、中止される40%に入るかは、実行で決まります。つまり、このガイドの残りで扱うアーキテクチャ、ガバナンス、計測の規律です。

## 1.4 この章から持ち帰ること

先に進む前に、1.1節の5つの症状に照らして自分のチームを確認してください。

| 当てはまる状況 | 自問すること | 測り方 |
|---|---|---|
| 1日に数百件のアラートがあり、大半が無視されている | そのうち何件が1つの根本原因を共有しているか | ページングツールまたはアラートツールから直近30日分をエクスポートし、インシデントごとのアラート数を数えます。 |
| 修正よりも診断に時間がかかるインシデント | インシデントの最初の1時間、エンジニアはどこに時間を使っているか | 直近5件のポストモーテムで、原因の特定にかかった時間と修正の適用にかかった時間を比べます。 |
| 売上に影響する障害 | 直近の大規模障害のコストはいくらだったか | 障害の継続時間に影響を受けたサービスの1分あたりの売上を掛け、費やしたエンジニアの工数を加えます。 |
| 呼び出しが同じ数人に集中している | 時間外の負荷を誰が担っているか | オンコールツールから、エンジニア1人あたりの週ごとの時間外呼び出し数を数えます。 |
| 新しいツールの購入後にトイルが増えた | そのツールはシグナルを増やしたのか、作業を減らしたのか | 購入前後の四半期で、アラート量とオンコール時間を比べます。 |

2つ以上の行があなたのチームに当てはまるなら、この章で説明したギャップはすでにコストを生んでいます。CloudThinker で自分たちのアラートからインシデントへのファネルを確認するには、[アラートソースを Signals に接続](/ja/guide/pulse/setup)してください。第2章では、自動化から自律へ移行することがこのギャップを埋める方法である理由を説明します。
