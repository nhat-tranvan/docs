Cassandra リングを接続すると、[Tony](/ja/guide/agents/tony)（データベースエンジニア）がキースペースとテーブルを一覧し、レプリケーションと TTL の設定を監査し、ドライバから見えるノードの状態を確認し、プライマリキーで行を読み取れるようになります。CloudThinker はログインロールを使って CQL ネイティブトランスポート経由で認証し、変更はすべてツール呼び出しの時点で停止してあなたの承認を待ちます。

## 前提条件

- CloudThinker から CQL ネイティブトランスポートのポート（既定は `9042`）に到達できる Cassandra クラスタ。
- ログインロールを作成する権限、または誰かが用意したロール。
- 同一データセンター内のノードアドレス 2 つか 3 つ。ドライバはそこからリングの残りを検出します。

<Info>
この接続が話すのは CQL だけです。`nodetool` は別ポートの JMX 上で動作するため、リペアの状況、コンパクションの滞留、ディスク使用量はここでエージェントが読める範囲の外に留まります。
</Info>

## セットアップ

<Steps>
  <Step title="ログインロールを作成する">
    既存のスーパーユーザーで接続し、専用のロールを作成します。
    ```sql
    CREATE ROLE ct_agent WITH LOGIN = true AND PASSWORD = 'your-secure-password';
    ```
    既定の `cassandra` スーパーユーザーを使い回さないでください。
  </Step>
  <Step title="読み取り権限を付与する">
    `system` と `system_schema` の読み取りに権限付与は不要です。そのため、ロールがログインできた時点でキースペース一覧、スキーマ監査、リング状態は動作します。行の読み取りは、エージェントに触れさせたいキースペースにだけ追加してください。
    ```sql
    GRANT SELECT ON KEYSPACE your_keyspace TO ct_agent;
    ```
  </Step>
  <Step title="変更権限を付与する（任意）">
    読み取り専用の接続にする場合はこの手順を飛ばしてください。エージェントに変更を提案させたいときは、キースペース単位で付与します。
    ```sql
    GRANT MODIFY ON KEYSPACE your_keyspace TO ct_agent;  -- 単一行の insert、update、delete
    GRANT ALTER  ON KEYSPACE your_keyspace TO ct_agent;  -- テーブルの TTL、gc_grace、セカンダリインデックス
    ```
  </Step>
  <Step title="ネットワークを開放する">
    入力する予定のコンタクトポイントに対して、CloudThinker からの `9042` 受信を許可します。Amazon Keyspaces は `9142` を使い、TLS が必須です。
  </Step>
  <Step title="CloudThinker で接続を追加する">
    **Connections → Cassandra** を開き、次を入力します。
    - **Contact points**: カンマ区切りのホスト名または IP。ポートは含めません。例: `10.0.1.10,10.0.1.11`
    - **Native transport port**: 多くのクラスタでは `9042`、Amazon Keyspaces では `9142`
    - **Role name**: `ct_agent`
    - **Password**: 上で設定したパスワード
    - **Local datacenter**: 任意。マルチ DC リングで読み取りを 1 つのデータセンター内に留めたい場合に設定します
    - **Use TLS**: クラスタで `client_encryption_options` を無効にしていない限り `Yes` のままにします
    - **Verify the TLS certificate**: `Yes` のままにします。自己署名証明書または内部 CA 証明書の場合だけオフにしてください

    **Connect** をクリックします。CloudThinker がリングに到達すると、接続は **Connected** 状態になります。
  </Step>
</Steps>

## 接続情報

| 項目 | 説明 | 既定値 |
|------|------|--------|
| **Contact points** | 1 つ以上のノードアドレス。カンマ区切りで、ホスト名か IP のみ | — |
| **Native transport port** | JMX ポートではなく CQL ポート | `9042` |
| **Role name** | 専用のログインロール。例: `ct_agent` | — |
| **Password** | そのロールに設定したパスワード | — |
| **Local datacenter** | 読み取りを 1 つのデータセンターに固定します。空欄なら応答したデータセンターを使います | 空欄 |
| **Use TLS** | ロールのパスワードを含めセッションを暗号化します | `Yes` |
| **Verify the TLS certificate** | どのサーバーが応答したかを証明します。TLS がオフのときは表示されません | `Yes` |

<Warning>
標準の `cassandra.yaml` はクライアントとノード間の暗号化を無効にした状態で出荷されます。**Use TLS** を `No` にするのはその既定に合わせることであり、ロール名とパスワードが平文で通信路に乗ります。CloudThinker とコンタクトポイントの間にあるものはすべてそれを読めます。
</Warning>

## 必要な権限

### 最小構成

権限付与は一切不要です。ログインできるロールは `system` と `system_schema` を読めるため、キースペース一覧、レプリケーションファクタ、TTL、コンパクション、インデックス、プライマリキーの構成、ドライバから見えるノード状態がそれだけで揃います。

### 行の読み取り

```sql
GRANT SELECT ON KEYSPACE your_keyspace TO ct_agent;
```

### 変更

```sql
GRANT MODIFY ON KEYSPACE your_keyspace TO ct_agent;
GRANT ALTER  ON KEYSPACE your_keyspace TO ct_agent;
```

<Tip>
エージェントに触れさせたいキースペースだけに付与し、`ON ALL KEYSPACES` は決して使わないでください。永続的な境界は権限付与のほうです。承認は CloudThinker が変更を求めるかどうかを決め、権限付与は Cassandra が変更を許すかどうかを決めます。
</Tip>

## エージェントができること

接続後、Tony は次を実行できます。

| 機能 | 説明 |
|------|------|
| **キースペースとテーブルの一覧** | キースペースとテーブルを、レプリケーション戦略とキー構成とともに一覧します |
| **スキーマ監査** | レプリケーションファクタ、`default_time_to_live`、`gc_grace_seconds`、コンパクション設定、セカンダリインデックスを報告します |
| **リング状態** | データセンター、ラック、リリース、スキーマ合意状況をドライバから見えるまま報告します |
| **行の読み取り** | キーで 1 パーティションを読み取ります。名前で明示的に依頼すればパーティションをまたいで走査します |
| **承認付き変更** | 1 行、テーブルの TTL か `gc_grace_seconds`、またはセカンダリインデックスを変更します |

### 接続を確認する

```text
@tony #report list the Cassandra keyspaces and the tables in each one
```

### プロンプト例

```text
@tony #report audit replication factor and TTL for the events keyspace
@tony #report show the row in ct_demo.sessions where session_id = 'abc-123'
@tony #recommend which tables in the events keyspace have no automatic expiry configured
```

## 承認付き変更

変更は任意の CQL ではありません。接続が持つ操作は固定されており、その外側はすべて承認ではなく拒否になります。

| 操作 | 範囲 |
|------|------|
| `insert`、`update`、`delete` | ちょうど 1 行。対象はプライマリキーの全カラムを指定する必要があるため、パーティション全体や範囲の削除は表現できません。 |
| テーブル設定 | `default_time_to_live` と `gc_grace_seconds` のみ。 |
| セカンダリインデックス | インデックスを 1 つ作成または削除します。 |

承認する前に知っておくべきことが 4 つあります。

- **すべての変更は測定した内容を報告します。** エージェントは変更前に読み取った値、結果、そしてそれを元に戻す正確なコマンドを提示します。その取り消しコマンドを実行することは 2 回目の変更であり、独自の承認が必要です。
- **`TRUNCATE`、`DROP TABLE`、`DROP KEYSPACE`、`ALTER KEYSPACE`、`GRANT`、`ALTER ROLE` は存在しません。** これらは拒否であって、承認を待っている操作ではありません。エージェントに尋ねれば、操作名と、運用担当者なら代わりに何を実行するかを答えます。
- **テーブル設定の変更は条件付きにできません。** Cassandra には条件付きの `ALTER TABLE` がないため、エージェントは現在値を読み、変更し、再度読み直して自分の値が残ったかどうかを報告します。その隙間に入った書き込みは検知されずに上書きしますが、出力にはそのことが記されます。
- **ロールバックはありません。** Cassandra にトランザクションはありません。削除はトゥームストーンを書くため、行は直ちに存在しないものとして読まれ、容量が戻るのは `gc_grace_seconds` とコンパクションの後です。新しい TTL は変更後に書かれた行に適用され、すでに保存されている行には適用されません。

<Warning>
同じワークスペースに 2 つ目の Cassandra 接続があると、両方が読み取り専用になります。変更は個々のインスタンスではなく接続の種類を指定するため、ステージングのつもりで与えた承認が本番に届く可能性があるからです。変更が必要な間は、ワークスペースごとに Cassandra 接続を 1 つに保ってください。
</Warning>

## トラブルシューティング

<Accordion title="接続がすぐに失敗する">
- **Contact points** にポートやスキームが含まれていないか確認してください。ポートには専用の項目があります。
- **Native transport port** が CQL ポートであることを確認してください。`7199` は JMX、`7000` はノード間通信で、どちらもここでは応答しません。
</Accordion>

<Accordion title="認証に失敗する">
- ロールが存在し、ログインできることを確認してください: `LIST ROLES;`
- `WITH LOGIN = true` なしで作成されたロールはどこにも認証できません。作り直すか、`ALTER ROLE ct_agent WITH LOGIN = true;` を実行してください。
</Accordion>

<Accordion title="接続できたが、キースペースが空に見える">
必ずしもエラーではありません。キースペースとテーブルのメタデータは `system_schema` から来ており権限付与を必要としないため、テーブル一覧が空ならそのキースペースにテーブルがないということです。**行**の読み取りが空の場合は、ロールにそのキースペースの `SELECT` がないか、パーティションに本当に何もないかのどちらかです。
</Accordion>

<Accordion title="TLS ハンドシェイクが失敗する">
- Amazon Keyspaces はポート `9142` で TLS を必須とします。両方をまとめて設定してください。
- 自己署名証明書または内部 CA 証明書の場合は、**Use TLS** を `Yes` のままにし、**Verify the TLS certificate** を `No` にします。セッションは暗号化されたままですが、どのサーバーが応答したかは証明されなくなります。
</Accordion>

<Accordion title="変更がタイムアウトした">
Cassandra は書き込みがコミットされる前でも後でもタイムアウトを返すため、結果は本当に不明であり、自動的な再試行は行われません。エージェントにその行または設定を読み直させ、その読み取りが報告する内容から判断してください。適用されたかどうかを確かめるために変更を再実行してはいけません。
</Accordion>

<Accordion title="インデックスを作成したのにクエリが失敗する">
新しいセカンダリインデックスがクエリに応答するのは、すべてのノードで構築が完了した後です。構築の時間を置いてから、もう一度尋ねてください。
</Accordion>

## セキュリティ

<ConnectionSecurity />

- **TLS がパスワードを運ぶ** — この接続はロール名とパスワードをクエリと同じソケットで送ります。プライベートネットワークの外に出るものには **Use TLS** をオンのままにしてください。
- **最小権限のロール** — 権限付与のないログインロールでも、一覧、スキーマ、状態の質問には答えられます。`SELECT`、`MODIFY`、`ALTER` は必要になったときにキースペース単位でのみ追加し、既定の `cassandra` スーパーユーザーには決して付与しないでください。
