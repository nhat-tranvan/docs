RabbitMQ ブローカーを接続すると、[CloudThinker](/ja/guide/agents/overview) は、どのキューが滞留しているか、どのキューにコンシューマーがいないか、デッドレターキューに何が溜まっているか、アラーム状態のノードがあるかを教えてくれます。この接続は、Management HTTP API 経由でブローカーの**ユーザー名とパスワード**を使ってサインインします。これは RabbitMQ 管理 UI が使うのと同じ API です。コードの変更は必要ありません。

## 対応プラットフォーム

| プラットフォーム | 対応 | 備考 |
|----------|-----------|-------|
| **Self-hosted RabbitMQ** | はい | `rabbitmq_management` プラグインを有効にする必要があります |
| **Managed RabbitMQ**（例: CloudAMQP） | はい | プロバイダーが Management HTTP API を CloudThinker に公開している必要があります |
| **Clusters** | はい | クラスターごとに接続を 1 つ追加します。**RABBITMQ_HOST** にはロードバランサーまたは任意のノードを指定します。管理 API はどのノードからでもクラスター全体の状態を返します |

## 前提条件

- ブローカーで management プラグインが有効になっていること。
- 管理ポートにインターネットから到達できること: HTTP は `15672`、HTTPS は通常 `15671` です。これは AMQP（`5672`）とは別のポートです。接続は CloudThinker Cloud から実行されるため、プライベートネットワーク上のブローカーには [Reaching private services](/ja/guide/connections/overview#プライベートサービスへの到達) のいずれかの方法が必要です。
- ユーザーを作成するための、ブローカーへのシェルアクセス（`rabbitmqctl`）またはプロバイダーのコンソール。

## セットアップ

<Steps>
  <Step title="management プラグインを有効にする">
    セルフホストのブローカーでは、次を実行します:

    ```bash
    rabbitmq-plugins enable rabbitmq_management
    ```

    マネージドプロバイダーでは通常すでに有効になっています。プロバイダーのコンソールに管理 UI が表示される場合は、このステップを飛ばしてください。
  </Step>
  <Step title="CloudThinker 用の監視ユーザーを作成する">
    専用ユーザーを作成して `monitoring` タグを付け、エージェントに見せたい各仮想ホスト（vhost）で読み取り権限を与えます。vhost は RabbitMQ におけるキューとエクスチェンジの名前空間で、`/` がデフォルトです。

    ```bash
    rabbitmqctl add_user cloudthinker '<strong-password>'
    rabbitmqctl set_user_tags cloudthinker monitoring
    rabbitmqctl set_permissions -p / cloudthinker "" "" ".*"
    ```

    3 つの権限文字列は、configure、write、read の順です。configure と write を空にして read を `.*` にすると、ユーザーは vhost 内のすべてを見られますが、完全な読み取り専用ではありません。RabbitMQ では読み取り権限でキューをパージできるため、このユーザーでもキューを空にできます。キューやエクスチェンジの削除には configure が必要で、このユーザーにはありません。追加の vhost ごとに `set_permissions` を繰り返してください。

    エージェントに何もパージさせたくない場合は、次のステップで **RABBITMQ_ALLOW_MUTATIONS** を **Read-only** に設定します。
  </Step>
  <Step title="ネットワーク経路を開く">
    ファイアウォールまたはセキュリティグループで、CloudThinker の送信元 IP から `<host>:15672`（または TLS 用の管理ポート）への受信トラフィックを許可します。このドキュメントでは CloudThinker の送信元 IP 一覧を公開していません。CloudThinker の担当者に問い合わせるか、[お問い合わせ](https://cloudthinker.io/contact)ください。セルフホストのブローカーでは、管理リスナーが `127.0.0.1` だけにバインドされていないことを確認してください。

    **成功の状態:** ブローカーのネットワーク外のマシンから次を実行します。`rabbitmq_version` と `cluster_name` を含む JSON が返れば、新しいユーザーとネットワーク経路の両方が確認できています:

    ```bash
    curl -u cloudthinker:'<strong-password>' http://<host>:15672/api/overview
    ```

    TLS を有効にしている場合は、代わりに `https://<host>:15671` を使います。
  </Step>
  <Step title="CloudThinker で接続を追加する">
    **Settings → Workspace → Connections** を開き、**Discover** タブを開いて **RabbitMQ** を選択します。次を入力します:

    - **RABBITMQ_USERNAME**: `cloudthinker`
    - **RABBITMQ_PASSWORD**: 設定したパスワード
    - **RABBITMQ_HOST**: ホスト名または IP のみ（例: `rabbit.internal.example.com`）
    - **RABBITMQ_MANAGEMENT_PORT**: `15672`、または TLS 用の管理ポート
    - **RABBITMQ_USE_TLS**: 管理 API が HTTPS を提供している場合は **Enabled**
    - **RABBITMQ_ALLOW_MUTATIONS**: **Read-only**（推奨）。[書き込みアクセス](#書き込みアクセス)の操作が必要な場合にのみ **Allow writes** を選びます
    - **LOG_LEVEL**: **Info** のままにします

    <Warning>
    **RABBITMQ_ALLOW_MUTATIONS** のデフォルトは **Allow writes** です。**Connect** をクリックする前に **Read-only** に切り替えてください。ブローカーユーザーだけではすべての書き込みを止められません。読み取り権限しかないユーザーでもキューをパージでき、パージするとメッセージは完全に削除されます。**Read-only** にすると、パージと削除のツールがエージェントから外れます。
    </Warning>

    **Connect** をクリックします。

    **成功の状態:** 接続は **Connecting**、**Verifying** を経て **Connected** になります。検証に失敗すると **Failed** と表示され、エラーメッセージが出ます。メッセージを[トラブルシューティング](#トラブルシューティング)と照らし合わせてください。
  </Step>
</Steps>

## 接続の詳細

| フィールド | 必須 | デフォルト | 説明 |
|-------|----------|---------|-------------|
| **RABBITMQ_USERNAME** | はい | なし | `monitoring` タグを持つブローカーユーザー |
| **RABBITMQ_PASSWORD** | はい | なし | そのユーザーのパスワード |
| **RABBITMQ_HOST** | はい | なし | ホスト名または IP。`http://`、`https://`、ポートは含めません |
| **RABBITMQ_MANAGEMENT_PORT** | はい | `15672` | Management HTTP API のポート。TLS を有効にする場合は TLS 用のポート（通常 `15671`）を使います |
| **RABBITMQ_USE_TLS** | いいえ | **Disabled** | **Disabled**: 平文 HTTP の管理 API と AMQP。**Enabled**: HTTPS の管理 API と AMQPS |
| **RABBITMQ_ALLOW_MUTATIONS** | いいえ | **Allow writes** | **Read-only**（推奨）: 監視とトラブルシューティングのみ。**Allow writes**: パージ、削除、定義の一括更新を有効にし、それぞれを Approvals が 1 件ずつ確認します |
| **LOG_LEVEL** | いいえ | **Info** | コネクターのログの詳しさ: **Debug**、**Info**、**Warn**、**Error** |

## 必要な権限

| 目的 | ユーザータグ | vhost の権限 |
|------|----------|-------------------|
| 監視とトラブルシューティング（推奨、**Read-only** 設定時） | `monitoring` | エージェントに見せる各 vhost で read（`"" "" ".*"`）。read でもキューのパージは可能です |
| 監視と削除 | `monitoring` | エージェントが変更してよい vhost で configure と read |
| 定義の一括更新 | `administrator` | configure、write、read。RabbitMQ は管理者からの定義インポートしか受け付けず、このタグはブローカー全体のユーザーとポリシーの管理権限も与えます |

<Tip>
まずは `monitoring`、read 権限、**RABBITMQ_ALLOW_MUTATIONS** を **Read-only** にした状態で始めてください。これで下記の読み取り機能はすべてカバーできます。エージェントにパージや削除をさせると決めたときだけ **Allow writes** に切り替え、configure 権限はエージェントが削除してよい vhost にだけ追加します。`administrator` は定義の一括更新が必要な場合にのみ使ってください。
</Tip>

## エージェントの機能

| 機能 | エージェントができること |
|------------|--------------------|
| **キューの深さとレート** | キューごとの ready と unacknowledged のメッセージ数を、パブリッシュとデリバーのレートとともに報告します |
| **コンシューマーの健全性** | コンシューマーがいないキューや、消費より速くメッセージが溜まるキューを見つけます |
| **デッドレターの確認** | デッドレターキューの中を見て、繰り返される失敗とその原因のメッセージを調べます |
| **クラスターとノードの健全性** | ノードの状態、メモリとディスクのアラーム、クォーラムを失うおそれのあるクォーラムキューを確認します |
| **証明書の確認** | 期限切れが近いブローカー証明書を指摘します |
| **書き込み操作** | キューとエクスチェンジのパージや削除、定義の一括更新を行います。**Allow writes** が有効で、かつ 1 件ずつ承認された場合に限ります |

### 接続を確認する

```text
Show the RabbitMQ cluster status and list every queue with its depth and consumer count
```

各ノードとその稼働状態に続き、キューごとの ready と unacknowledged の件数、コンシューマー数の表が返ります。

### プロンプト例

```text
Which RabbitMQ queues have messages but zero consumers right now?
The orders queue keeps growing. Find out why and check its dead-letter queue for poison messages
Is any RabbitMQ node in a memory or disk alarm, and do any certificates expire in the next 30 days?
```

## 書き込みアクセス

**RABBITMQ_ALLOW_MUTATIONS** を **Allow writes** にし、ユーザーに適切な vhost 権限がある場合（[必要な権限](#必要な権限)を参照）、エージェントは次のことができます:

- キューをパージする（キュー内のメッセージをすべて削除する）
- キューまたはエクスチェンジを削除する
- ブローカー定義の一括更新を適用する（`administrator` が必要）

それぞれが個別に [Approvals](/guide/approvals/overview) を通り、読み取りには承認は不要です。

<ApprovalDefault />

パージに必要なのはキューの読み取り権限だけなので、ブローカーユーザーではパージを防げません。書き込みを有効にする場合は **Manual** を選び、すべての変更を人が承認するようにしてください。**Ask first** の [Rule](/guide/approvals/rules) を使うと、承認待ちをパージだけに絞れます。

<Warning>
キューをパージまたは削除すると、そのメッセージは完全に失われます。RabbitMQ はコピーを残しません。承認する前に、承認リクエストのキュー名と vhost を確認してください。
</Warning>

## トラブルシューティング

<Accordion title="接続が拒否される、またはタイムアウトする">
- CloudThinker が `<host>:15672`（または TLS 用の管理ポート）に到達できることを確認してください。
- AMQP ポート `5672` ではなく、管理ポートを開けたことを確認してください。
- セルフホストのブローカーでは、管理リスナーが `127.0.0.1` だけにバインドされていないことを確認してください。
</Accordion>

<Accordion title="管理 API から 404 Not Found が返る">
management プラグインが無効です。`rabbitmq-plugins enable rabbitmq_management` を実行して、もう一度接続してください。マネージドブローカーの場合は、プロバイダーがご利用のプランで Management HTTP API を公開しているか確認してください。
</Accordion>

<Accordion title="401 Unauthorized">
- ユーザー名とパスワードを確認し直してください。
- ユーザーに管理タグがあることを確認してください: `rabbitmqctl set_user_tags cloudthinker monitoring`。タグのないユーザーは AMQP ではサインインできますが、管理 API には拒否されます。
</Accordion>

<Accordion title="TLS ハンドシェイクまたは証明書のエラー">
**RABBITMQ_USE_TLS** と **RABBITMQ_MANAGEMENT_PORT** を一致させる必要があります。**Enabled** には HTTPS を提供するポート（通常 `15671`）、**Disabled** には平文 HTTP のポート（通常 `15672`）が必要です。
</Accordion>

<Accordion title="ホストフィールドのエラー">
**RABBITMQ_HOST** にはホスト名または IP だけを入力してください。`http://`、`https://`、パス、`:port` は削除します。TLS とポートにはそれぞれ専用のフィールドがあります。
</Accordion>

<Accordion title="一部のキューや vhost が表示されない">
ユーザーにそれらの vhost の読み取り権限がありません。`rabbitmqctl set_permissions -p <vhost> cloudthinker "" "" ".*"` で付与してから、もう一度質問してください。
</Accordion>

<Accordion title="パージまたは削除が拒否された">
**RABBITMQ_ALLOW_MUTATIONS** が **Read-only** になっているか、ブローカーユーザーにその操作に必要な vhost 権限（パージには read、削除には configure）がありません。許可するつもりだった方を変更してください。操作は引き続き Approvals を通ります。
</Accordion>

## セキュリティ

<ConnectionSecurity />

- **専用ユーザーを使う**: この接続用に `cloudthinker` を作成してください。`guest` や個人の管理者アカウントは決して再利用しないでください。
- **TLS を有効にする**: **RABBITMQ_USE_TLS** を **Enabled** にすると、CloudThinker とブローカー間のパスワードとブローカーデータが暗号化されます。
