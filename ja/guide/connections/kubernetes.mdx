Kubernetes クラスターを接続すると、CloudThinker がクラッシュループや Pending の Pod を見つけ、ログとイベントを読み、ノードの逼迫を確認し、RBAC とネットワークポリシーを確認できるようになります。専用の読み取り専用サービスアカウントとしてサインインする **kubeconfig ファイル** をアップロードします。ロールアウトの再起動などの変更はワークスペースの Approvals を経由し、書き込みの RBAC を付与した場合にのみ実行されます（[書き込みアクセス](#書き込みアクセス)を参照）。

## 前提条件

- CloudThinker がインターネット経由で API サーバーに到達できるクラスター。コマンドは CloudThinker のクラウドで実行されるため、プライベートのみのエンドポイントでは接続テストが失敗します。API へのアクセスを制限している場合（EKS の public access CIDR、GKE の authorized networks、AKS の authorized IP ranges）は、`0.0.0.0/0` に開放する代わりに CloudThinker の送信元 IP を追加してください。このドキュメントでは CloudThinker の送信元 IP の一覧を公開していません。CloudThinker の担当者に問い合わせるか、[お問い合わせ](https://cloudthinker.io/contact)ください。その他の選択肢は [Reaching private services](/ja/guide/connections/overview#プライベートサービスへの到達) を参照してください。
- そのクラスターへの `kubectl` アクセスと、Namespace、ClusterRole、ClusterRoleBinding を作成する権限。
- マネージドクラスター（EKS、GKE、AKS）が発行する kubeconfig は `aws`、`gcloud`、`az` の exec プラグインでサインインするため、CloudThinker では機能しません。ステップ 2 で機能するものを作成します。サービスアカウントのトークンは Kubernetes 自体が確認するため、クラウドの IAM でマッピングする必要はありません（たとえば EKS のアクセスエントリは不要です）。
- 任意: クラスター内の [Metrics Server](https://github.com/kubernetes-sigs/metrics-server)。これがなくても、エージェントは Pod のステータスとノードの状態を報告しますが、CPU とメモリのライブの使用量は報告できません。
- 接続を追加・編集できる、CloudThinker ワークスペースの **Admin** ロール。[Roles](/guide/security/roles) を参照してください。

<Info>
Kubernetes 接続はワークスペースごとに **1 つ** で、エージェントは kubeconfig の **current context** で作業します。調べたい 1 つのクラスターの kubeconfig をアップロードしてください。複数のクラスターには、[クラスターごとに 1 つのワークスペース](/ja/guide/workspaces#ワークスペースを作成する)を使うか、Rancher が管理するクラスター全体のインベントリとヘルスのために [Rancher 接続](/guide/connections/rancher)を追加してください。
</Info>

## セットアップ

<Steps>
  <Step title="読み取り専用のサービスアカウントを作成する">
    このマニフェストを `cloudthinker-reader.yaml` として保存します。サービスアカウントのトークンである Secret も 1 つ作成されますが、それを読むのはステップ 2 のあなただけです。ロールが許可する内容は[必要な権限](#必要な権限)で説明しています。

    <Accordion title="cloudthinker-reader.yaml">
      ```yaml
      apiVersion: v1
      kind: Namespace
      metadata:
        name: cloudthinker
      ---
      apiVersion: v1
      kind: ServiceAccount
      metadata:
        name: cloudthinker-reader
        namespace: cloudthinker
      ---
      apiVersion: rbac.authorization.k8s.io/v1
      kind: ClusterRole
      metadata:
        name: cloudthinker-reader
      rules:
      - apiGroups: [""]
        resources: ["pods", "pods/log", "nodes", "namespaces", "services", "endpoints", "events", "configmaps", "persistentvolumeclaims", "persistentvolumes", "resourcequotas", "limitranges", "serviceaccounts", "replicationcontrollers"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["apps"]
        resources: ["deployments", "replicasets", "statefulsets", "daemonsets"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["batch"]
        resources: ["jobs", "cronjobs"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["autoscaling"]
        resources: ["horizontalpodautoscalers"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["networking.k8s.io"]
        resources: ["ingresses", "networkpolicies"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["policy"]
        resources: ["poddisruptionbudgets"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["storage.k8s.io"]
        resources: ["storageclasses"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["rbac.authorization.k8s.io"]
        resources: ["roles", "rolebindings", "clusterroles", "clusterrolebindings"]
        verbs: ["get", "list", "watch"]
      - apiGroups: ["metrics.k8s.io"]
        resources: ["pods", "nodes"]
        verbs: ["get", "list"]
      ---
      apiVersion: rbac.authorization.k8s.io/v1
      kind: ClusterRoleBinding
      metadata:
        name: cloudthinker-reader
      roleRef:
        apiGroup: rbac.authorization.k8s.io
        kind: ClusterRole
        name: cloudthinker-reader
      subjects:
      - kind: ServiceAccount
        name: cloudthinker-reader
        namespace: cloudthinker
      ---
      apiVersion: v1
      kind: Secret
      metadata:
        name: cloudthinker-reader-token
        namespace: cloudthinker
        annotations:
          kubernetes.io/service-account.name: cloudthinker-reader
      type: kubernetes.io/service-account-token
      ```
    </Accordion>

    適用します。

    ```bash
    kubectl apply -f cloudthinker-reader.yaml
    ```

    `cloudthinker` 名前空間、`cloudthinker-reader` サービスアカウント、それにバインドされた読み取り専用の ClusterRole、長期間有効なトークンの Secret が作成されます。

    **成功時の状態:** `kubectl get secret cloudthinker-reader-token -n cloudthinker` で、`DATA` の数が 3 の Secret が表示されます。Kubernetes は適用後数秒でトークンを埋めるため、`DATA` が 0 の場合は少し待ってからコマンドを再実行してください。
  </Step>
  <Step title="そのアカウント用の kubeconfig を作成する">
    現在の `kubectl` コンテキストが対象クラスターになっているシェルで実行します。まず、API サーバーのアドレスを読み取って確認します。

    ```bash
    SERVER=$(kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}')
    echo $SERVER
    ```

    公開ホスト名または IP が表示される必要があります。`127.0.0.1`、`localhost`、または `10.x` や `192.168.x` などのプライベートアドレス（kind、minikube、k3d、ローカルプロキシの背後でよく見られます）が表示される場合、CloudThinker は到達できないため、作業を止めて先にアクセスを修正してください。

    次に、同じシェルで、トークンと CA 証明書を埋め込んだ `cloudthinker-kubeconfig.yaml` を書き出します。

    ```bash
    CA=$(kubectl get secret cloudthinker-reader-token -n cloudthinker -o jsonpath='{.data.ca\.crt}')
    TOKEN=$(kubectl get secret cloudthinker-reader-token -n cloudthinker -o jsonpath='{.data.token}' | base64 --decode)

    cat > cloudthinker-kubeconfig.yaml <<EOF
    apiVersion: v1
    kind: Config
    clusters:
    - name: target
      cluster:
        server: ${SERVER}
        certificate-authority-data: ${CA}
    users:
    - name: cloudthinker-reader
      user:
        token: ${TOKEN}
    contexts:
    - name: cloudthinker
      context:
        cluster: target
        user: cloudthinker-reader
    current-context: cloudthinker
    EOF
    ```

    古い macOS のリリースでは、`base64 --decode` を `base64 -D` に置き換え、最後の `EOF` は行の先頭に置いてください。

    **成功時の状態:** `kubectl --kubeconfig cloudthinker-kubeconfig.yaml get nodes` でノードが一覧表示されます。これは CloudThinker が接続のテストで実行するのと同じコマンドです。
  </Step>
  <Step title="CloudThinker で kubeconfig をアップロードする">
    **Settings → Workspace → Connections** を開き、**Kubernetes** を選んで、**KUBECONFIG** フィールドに `cloudthinker-kubeconfig.yaml` をアップロードします。**Connect** をクリックします。

    **成功時の状態:** 接続に **Connecting** と **Verifying** が表示され、その後 **Connected** のステータスになります。
  </Step>
</Steps>

## 接続の詳細

| フィールド | 必須 | 説明 | 例 |
|-------|----------|-------------|---------|
| **KUBECONFIG** | はい | kubeconfig ファイル。ファイルピッカーは `.yaml` 拡張子だけを受け付けるため、`.yml` のファイルは選べません。先に `.yaml` に名前を変更してください。CloudThinker はその current context を使います | `cloudthinker-kubeconfig.yaml` |

すべてをファイルに埋め込んでください。ローカルの証明書ファイルを参照する kubeconfig や、`exec` プラグインでサインインする kubeconfig には、CloudThinker にないファイルやツールが必要です。ステップ 2 のトークンベースのファイルなら、そのどちらも避けられます。

## 必要な権限

[ステップ 1](#セットアップ) のマニフェストは、エージェントが調べるリソースへの読み取りアクセス（`get`、`list`、`watch`）と、Pod のログおよびメトリクスを付与します。Secret は読めません。

ClusterRoleBinding はすべての名前空間でロールを付与するため、読み取りアクセスは `kube-system` を含むクラスター全体に及びます。一部の名前空間だけを対象にするには、ClusterRoleBinding を、各名前空間で同じ ClusterRole への RoleBinding に置き換えます。その場合、RoleBinding では付与できないため、ノード、名前空間、永続ボリュームなどのクラスタースコープのリソースは回答から外れます。

カスタムリソースは対象外のため、エージェントは Argo CD のアプリケーションや Istio の仮想サービスなど、CRD ベースのオブジェクトを見られません。見られるようにするには、各リソースの API グループを含むルールを ClusterRole に追加します。

<Tip>
ロールは必要なものに絞ってください。ConfigMap に機密の値がある場合は `configmaps` を、RBAC の確認が不要な場合は `rbac.authorization.k8s.io` のルールを削除します。回答に `403` が出た場合、ロールに不足しているリソースが示されます。
</Tip>

## 書き込みアクセス

エージェントが `scale`、`rollout restart`、`cordon`、`drain`、`apply` などの変更を実行するのは、あなたが会話で依頼した場合だけで、上記の読み取り専用のロールでは `403` で失敗します。接続の詳細パネルにある **Allow writes** が 2 つ目の制御です。デフォルトでオンですが、ロールが許可する範囲を広げることはできません。

| `cloudthinker-reader` サービスアカウントの RBAC | Allow writes | 結果 |
|---|---|---|
| 読み取りのルールのみ | オンまたはオフ | 読み取り専用。Kubernetes がすべての変更を `403` で拒否します。 |
| 書き込みのルールを付与 | オフ | 読み取り専用。CloudThinker がクラスターに届く前にすべての変更を拒否します。 |
| 書き込みのルールを付与 | オン | エージェントが変更を提案できます。各変更は [Rules と Approval mode](/guide/approvals/overview) が判断します。 |

CloudThinker 側でも書き込みをロックするには、**Settings → Workspace → Connections** を開き、**Kubernetes** を選んで、詳細パネルの **Allow writes** スイッチをオフにします。

<ApprovalDefault />

特定の変更を許可するには、それに必要なものだけを付与します。

- **Scale と rollout restart** は名前空間のワークロードに作用します。関係する各名前空間で、`deployments` への `patch` と、`deployments/scale` への `get` と `patch` を持つ Role を使います。StatefulSet には、`statefulsets` と `statefulsets/scale` に同じものを追加します。DaemonSet には `daemonsets` を追加します（スケールしないため、再起動のみ）。
- **Apply** には、適用するマニフェスト内の各リソースの種類について、対象の名前空間で `get`、`create`、`patch` が必要です。
- **Cordon と drain** はクラスタースコープのノードに作用するため、名前空間の Role では許可できません。`nodes` への `patch` と `pods/eviction` への `create` を持つ ClusterRole を使います。drain に必要な Pod と DaemonSet への `get` と `list` は、読み取りロールがすでに提供しています。

書き込みの付与は同じ `cloudthinker-reader` サービスアカウントにバインドされるため、1 つの kubeconfig で読み取りと変更の両方をカバーできます。最初から書き込みアクセスを計画している場合は、両方のマニフェストとステップ 2 で、アカウント名を変更してください（例: `cloudthinker-agent`）。

この例では、1 つの名前空間でのデプロイメントのスケールと、cordon および drain を許可します。`payments` を自分の名前空間に置き換えて `cloudthinker-write.yaml` として保存し、`kubectl apply -f cloudthinker-write.yaml` を実行します。

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: cloudthinker-scale
  namespace: payments
rules:
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["patch"]
- apiGroups: ["apps"]
  resources: ["deployments/scale"]
  verbs: ["get", "patch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: cloudthinker-scale
  namespace: payments
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: cloudthinker-scale
subjects:
- kind: ServiceAccount
  name: cloudthinker-reader
  namespace: cloudthinker
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: cloudthinker-node-ops
rules:
- apiGroups: [""]
  resources: ["nodes"]
  verbs: ["patch"]
- apiGroups: [""]
  resources: ["pods/eviction"]
  verbs: ["create"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: cloudthinker-node-ops
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: cloudthinker-node-ops
subjects:
- kind: ServiceAccount
  name: cloudthinker-reader
  namespace: cloudthinker
```

**成功時の状態:** `kubectl auth can-i patch deployments/scale -n payments --as=system:serviceaccount:cloudthinker:cloudthinker-reader` が `yes` を出力します。

## エージェントの機能

| 機能 | エージェントが行うこと |
|------------|----------------|
| **Workload triage** | クラッシュループ、Pending、再起動中の Pod、劣化したデプロイメント、警告イベントを見つけ、ログを読んで理由を説明します |
| **Node pressure** | ノードの状態、容量、割り当て可能なリソースを報告し、Metrics Server がインストールされていれば CPU とメモリの上位の消費者を示します |
| **Capacity and scheduling** | リクエストとリミットを使用量と比較し、Pod がスケジュールできない理由を説明します |
| **Security and RBAC** | ロールバインディング、サービスアカウント、ネットワークポリシー、特権ワークロードを確認します |
| **Configuration** | 名前空間をまたいで Ingress、サービス、ストレージ、オートスケーラー、イメージを調べます。カスタムリソースにはロールへのルールの追加が必要です |
| **Changes** | scale、restart、cordon、drain、apply。各変更は Approvals を経由します |

### 接続を確認する

```text
Check the Kubernetes connection: list the namespaces, the node count, and any nodes that are not Ready
```

名前空間の一覧、ノード数、ノードのステータスが返されます。使用量の数値がない場合、回答には Metrics Server がインストールされていないと示されます。

### プロンプトの例

```text
Which pods in the payments namespace are crash-looping, and what do their logs say?
Which nodes are under memory or disk pressure, and what is using the most memory?
Which service accounts are bound to cluster-admin?
```

## トークンをローテーションする

Kubernetes は単一接続のサービスのため、正常な状態では鉛筆アイコンや **Edit Instance** ダイアログはありません。新しいトークンを先に作成し、古い Secret は最後に削除してください。先に削除すると、機能する代わりのものができる前にクラスターから切り離されます。

<Steps>
  <Step title="2 つ目のトークンの Secret を作成する">
    これを `cloudthinker-reader-token-2.yaml` として保存します。同じサービスアカウントの 2 つ目のトークンで、切り替えの間は両方が機能します。

    ```yaml
    apiVersion: v1
    kind: Secret
    metadata:
      name: cloudthinker-reader-token-2
      namespace: cloudthinker
      annotations:
        kubernetes.io/service-account.name: cloudthinker-reader
    type: kubernetes.io/service-account-token
    ```

    適用します。

    ```bash
    kubectl apply -f cloudthinker-reader-token-2.yaml
    ```

    **成功時の状態:** `kubectl get secret cloudthinker-reader-token-2 -n cloudthinker` で、`DATA` の数が 3 の Secret が表示されます。
  </Step>
  <Step title="新しいトークンから kubeconfig を作成する">
    `cloudthinker-reader-token` の代わりに `cloudthinker-reader-token-2` を使って、[セットアップ](#セットアップ)のステップ 2 を繰り返します。

    **成功時の状態:** `kubectl --kubeconfig cloudthinker-kubeconfig.yaml get nodes` でノードが一覧表示されます。
  </Step>
  <Step title="CloudThinker で切り替える">
    接続に **Connected** と表示されている間は、**Kubernetes** の詳細パネルで **Disconnect** をクリックしてから、再度接続して新しい kubeconfig をアップロードします。**Error** と表示されている間は、切断せずに、詳細パネルで **Replace credentials** をクリックして新しい kubeconfig をアップロードします。

    **成功時の状態:** 接続に **Connected** と表示されます。
  </Step>
  <Step title="古い Secret を削除する">
    この段階で初めて、置き換えたトークンを削除します。

    ```bash
    kubectl delete secret cloudthinker-reader-token -n cloudthinker
    ```
  </Step>
</Steps>

切断して再接続すると、新しい接続が開始されます。

- 切断から再接続までの間、エージェントとスケジュールされた[オートメーション](/guide/automation/automations)はクラスターを使えません。
- 初回接続時の詳細調査のチャットが再度開き、クレジットを消費します。
- **Allow writes** はオンに戻ります。オフにしていた場合は、もう一度オフにしてください。
- Kubernetes 接続を指定している [Rules](/guide/approvals/rules) が、引き続きその接続を含んでいることを確認してください。

ポリシーで長期間有効な認証情報が禁止されている場合は、Secret を使わず、`kubectl create token cloudthinker-reader -n cloudthinker --duration=<time>` による短期のトークンで kubeconfig を作成します。そのトークンが期限切れになると接続が壊れるため、そのたびに kubeconfig を作り直してアップロードします。

## トラブルシューティング

テストが失敗すると、`Failed to connect to Kubernetes:` に続いて `kubectl get nodes` の最初のエラー行が表示されます。その行を下の項目と照合してください。

<Accordion title="Unable to connect to the server">
CloudThinker が kubeconfig の API サーバーに到達できませんでした。`server` のアドレスが VPN からだけでなくインターネットから到達できること、API サーバーの許可リストが外部からのアクセスを許可していることを確認してください。ネットワーク外のマシンから `kubectl --kubeconfig cloudthinker-kubeconfig.yaml get nodes` を実行して確認します。
</Accordion>

<Accordion title="error: You must be logged in to the server (Unauthorized)">
トークンが誤っている、期限切れ、または取り消されています。`cloudthinker-reader-token` の Secret がまだ存在することを確認してから、ステップ 2 から kubeconfig を作り直し、[トークンをローテーションする](#トークンをローテーションする)の手順でアップロードしてください。
</Accordion>

<Accordion title="回答に Error from server (Forbidden) が出る">
ClusterRole がそのリソースをカバーしていません。ClusterRoleBinding が適用されていることを確認してから、ロールにリソースを追加してください。
</Accordion>

<Accordion title="getting credentials: exec、または no such file or directory">
kubeconfig がローカルのコマンドやファイルパスに依存しています。ステップ 2 のトークンベースの kubeconfig に置き換えてください。
</Accordion>

<Accordion title="回答に CPU やメモリの使用量がない">
Metrics Server がインストールされていないか、準備ができていません。`kubectl top nodes` を実行して確認してください。Pod のステータス、イベント、ノードの状態はそれがなくても機能します。
</Accordion>

<Accordion title="Connection 'k8s' already exists. Only one instance is allowed.">
`k8s` は Kubernetes 接続で、ワークスペースが持てるのは 1 つです。編集するための鉛筆アイコンはないため、CloudThinker を別のクラスターに向けるには、**Kubernetes** の詳細パネルで **Disconnect** をクリックし、別の kubeconfig で再度接続してください。
</Accordion>

## セキュリティ

<ConnectionSecurity />

- **Secret をロールに含めない。** 上記のマニフェストは Secret の読み取りを一切付与しないため、エージェントは Secret オブジェクトを読めません。Pod のログと ConfigMap は読めるため、機密データが含まれる場合は `pods/log` や `configmaps` をロールから削除してください。Pod の spec に直接設定された環境変数の値は `pods` を通じて読めるため、機密の値は Secret に移してください。
- **トークンをローテーションする。** トークンの Secret は自動では期限切れにならないため、通常のスケジュールでローテーションしてください。[トークンをローテーションする](#トークンをローテーションする)を参照してください。
- **1 つのコマンドで取り消す。** トークンの Secret を削除するとすぐにアクセスを遮断でき、`cloudthinker` 名前空間と ClusterRole およびバインディングを削除するとすべてを取り除けます。
