Snowflake を接続すると、CloudThinker がどのウェアハウスが最も多くのクレジットを消費しているかを示し、遅いクエリと失敗するクエリをランク付けし、タイムトラベルとフェイルセーフのストレージを測定できるようになります。CloudThinker はサービスユーザーの **programmatic access token**（PAT）で Snowflake SQL REST API を呼び出し、新しい接続は **Allow writes** をオンにするまで読み取りのみを行います。

---

## 前提条件

- ロール、サービスユーザー、ネットワークポリシー、トークンを作成するための `ACCOUNTADMIN` または同等のロール。
- ロールが使用できるウェアハウス。接続テストにはコンピュートが不要なため、ウェアハウスがなくてもテストは合格しますが、実際の分析は失敗します。セットアップのステップ 1 で上限付きのものを作成します。
- アカウントに認証ポリシーがある場合、その `AUTHENTICATION_METHODS` に `PROGRAMMATIC_ACCESS_TOKEN` が含まれている必要があります。含まれていないと、サインイン時にトークンが拒否されます。
- 接続の追加に必要な、CloudThinker ワークスペースの **Admin** ロール。[Roles](/guide/security/roles) を参照してください。

---

## セットアップ

リソースモニターの作成に必要なため、以下の SQL はすべて `ACCOUNTADMIN` として実行してください（`USE ROLE ACCOUNTADMIN;` から始めます）。SQL ではウェアハウスとして `CT_WH` を使います。既存のウェアハウスを使う場合は、すべての箇所でその名前に置き換えてください。

<Steps>
  <Step title="上限付きのウェアハウスを作成する（推奨）">
    分析クエリは、このウェアハウスにクレジットを課金します。自動停止の時間が短く、リソースモニターを持つ専用の X-Small のウェアハウスなら、コストの上限を保てます。
    ```sql
    USE ROLE ACCOUNTADMIN;

    CREATE WAREHOUSE IF NOT EXISTS CT_WH WAREHOUSE_SIZE = XSMALL AUTO_SUSPEND = 60 AUTO_RESUME = TRUE INITIALLY_SUSPENDED = TRUE;
    CREATE RESOURCE MONITOR IF NOT EXISTS CT_MONITOR WITH CREDIT_QUOTA = 10 FREQUENCY = MONTHLY START_TIMESTAMP = IMMEDIATELY TRIGGERS ON 100 PERCENT DO SUSPEND;
    ALTER WAREHOUSE CT_WH SET RESOURCE_MONITOR = CT_MONITOR;
    ```
    `CREDIT_QUOTA` の決め方: X-Small のウェアハウスは稼働 1 時間あたり 1 クレジットを使い、秒単位で課金され、再開のたびに最低 60 秒が課金されます。10 のクォータは月 10 時間の稼働をカバーします。クォータを使い切るとウェアハウスが停止し、翌月になるか管理者が引き上げるまで分析クエリは失敗します。
  </Step>
  <Step title="読み取り専用のロールを作成する">
    ```sql
    USE ROLE ACCOUNTADMIN;

    CREATE ROLE IF NOT EXISTS CT_READONLY;
    GRANT DATABASE ROLE SNOWFLAKE.USAGE_VIEWER      TO ROLE CT_READONLY;
    GRANT DATABASE ROLE SNOWFLAKE.OBJECT_VIEWER     TO ROLE CT_READONLY;
    GRANT DATABASE ROLE SNOWFLAKE.GOVERNANCE_VIEWER TO ROLE CT_READONLY;
    GRANT MONITOR USAGE ON ACCOUNT                  TO ROLE CT_READONLY;
    GRANT USAGE ON WAREHOUSE CT_WH                  TO ROLE CT_READONLY;
    ```
  </Step>
  <Step title="サービスユーザーを作成する">
    `SERVICE` ユーザーにはパスワード、MFA、SSO がないため、トークンが唯一の入り口です。
    ```sql
    CREATE USER IF NOT EXISTS SVC_CLOUDTHINKER
      TYPE = SERVICE
      DEFAULT_ROLE = CT_READONLY
      DEFAULT_WAREHOUSE = CT_WH
      COMMENT = 'CloudThinker connection';
    GRANT ROLE CT_READONLY TO USER SVC_CLOUDTHINKER;
    ```
  </Step>
  <Step title="ネットワークポリシーを付与する">
    Snowflake は、ユーザーにネットワークポリシーが設定されるまでトークンによるサインインを拒否します。このドキュメントでは CloudThinker の送信元 IP の一覧を公開していません。CloudThinker の担当者に問い合わせるか、[お問い合わせ](https://cloudthinker.io/contact)ください。それらを `ALLOWED_IP_LIST` に入れます。
    ```sql
    CREATE NETWORK POLICY IF NOT EXISTS CT_POLICY ALLOWED_IP_LIST = ('<cloudthinker-egress-ip-1>', '<cloudthinker-egress-ip-2>');
    ALTER USER SVC_CLOUDTHINKER SET NETWORK_POLICY = CT_POLICY;
    ```
    使い捨てのテストアカウントに限り、`('0.0.0.0/0')` を使えば一覧が手に入る前に接続を試せます。本番のアカウントでは決して残さないでください。
  </Step>
  <Step title="programmatic access token を作成する">
    ```sql
    ALTER USER SVC_CLOUDTHINKER ADD PROGRAMMATIC ACCESS TOKEN CT_TOKEN
      ROLE_RESTRICTION = 'CT_READONLY'
      DAYS_TO_EXPIRY = 90;
    ```
    結果の `token_secret` 列の値をコピーします。Snowflake は一度しか表示せず、有効期限の日に機能しなくなります。アカウントでより低い上限が設定されていない限り、`DAYS_TO_EXPIRY` は最大 365 です。CloudThinker はトークンの期限切れの前に警告しないため、その 1 週間前にカレンダーのリマインダーを設定して[ローテーション](#トークンをローテーションする)してください。後で有効期限を確認するには、`SHOW USER PROGRAMMATIC ACCESS TOKENS FOR USER SVC_CLOUDTHINKER;` を実行し、`expires_at` 列を読みます。
  </Step>
  <Step title="CloudThinker で接続を追加する">
    **Settings → Workspace → Connections** をクリックし、**Discover** タブで **Snowflake** を検索して **Connect** をクリックします。[接続の詳細](#接続の詳細)のフィールドに入力し、**Connect** をクリックします。

    **成功時の状態:** Snowflake に **Connected** のステータスが表示され、メッセージにトークンが解決した内容が示されます（例: `Connected to MYORG-MYACCOUNT (AWS_US_WEST_2), role CT_READONLY, warehouse CT_WH`）。
  </Step>
</Steps>

## 接続の詳細

| フィールド | 必須 | 説明 | デフォルト |
|-------|----------|-------------|---------|
| **Account identifier** | はい | `MYORG-MYACCOUNT`。完全な URL ではありません。見つけ方は下記を参照 | |
| **Programmatic access token** | はい | セットアップのステップ 5 のトークン。アカウントのパスワードではありません | |
| **Role** | いいえ | 接続が使うロール。トークンの `ROLE_RESTRICTION` の範囲内でなければなりません | ユーザーのデフォルトのロール |
| **Warehouse** | いいえ | この接続が使うクレジットを課金するウェアハウス | ユーザーのデフォルトのウェアハウス |

**Account identifier** を見つけるには、Snowsight の左メニューの下部にあるアカウントセレクターを開き、**View account details** をクリックします。または次を実行します。

```sql
SELECT CURRENT_ORGANIZATION_NAME() || '-' || CURRENT_ACCOUNT_NAME();
```

アンダースコアで書いた識別子（`MYORG_MYACCOUNT`）も機能します。

## 必要な権限

| 付与 | 利用可能になるもの |
|-------|-----------------|
| `SNOWFLAKE.USAGE_VIEWER` | クレジットの計測とストレージの履歴 |
| `SNOWFLAKE.OBJECT_VIEWER` | データベース、スキーマ、テーブルのインベントリ |
| `SNOWFLAKE.GOVERNANCE_VIEWER` | 遅いクエリとエラーの回答に必要な `QUERY_HISTORY` |
| `MONITOR USAGE ON ACCOUNT` | アカウントレベルの使用量のビュー |
| `USAGE ON WAREHOUSE` | 分析クエリを実行するためのコンピュート |

<Tip>
`GOVERNANCE_VIEWER` は見落とされがちな付与です。これがないと、クレジットとストレージの回答は機能しますが、遅いクエリとエラーの回答はすべて失敗します。接続が他の何にも到達できないよう、トークンの `ROLE_RESTRICTION` はこの読み取り専用のロールにしておいてください。
</Tip>

## エージェントの機能

| 機能 | 説明 |
|------------|-------------|
| **Account discovery** | ID、ウェアハウス、データベース、ロールが読める `ACCOUNT_USAGE` のビュー |
| **Credit analysis** | 指定した期間（デフォルトは 30 日）における、ウェアハウスごと・日ごとの計測されたクレジット |
| **Query health** | 最も遅いクエリ、繰り返し発生するエラーの種類、リモートストレージにスピルするクエリ |
| **Storage review** | 最大のテーブル、タイムトラベルとフェイルセーフのオーバーヘッド、データベースごとの増加 |
| **Inventory** | スキーマ、ロール、この接続自身の付与 |
| **Warehouse control** | **Allow writes** がオンの場合: 名前を指定した 1 つのウェアハウスの停止または再開 |

CloudThinker は Snowflake の支出を金額ではなく、常にクレジットで報告します。クレジットあたりの価格は、この接続では読み取れません。

### 接続を確認する

```text
List my Snowflake warehouses and which ACCOUNT_USAGE views this connection can read
```

**成功時の状態:** CloudThinker がウェアハウスを一覧表示し、各 `ACCOUNT_USAGE` のビューを読み取り可能かブロックされているかでマークし、ブロックされているものにはそれを修正する `GRANT` を示します。

### プロンプトの例

```text
Which Snowflake warehouses burned the most credits in the last 30 days?
Show the slowest Snowflake queries this week and any errors that keep recurring
Where are time travel and failsafe adding the most storage?
```

## 書き込みアクセス

新しい Snowflake の接続では、**Allow writes** はオフです。

<ApprovalDefault />

スイッチをオンにすると、AI は人を介さずにウェアハウスの停止を承認できます。本番のアカウントでは、書き込みをオンにする前に **Manual** を選び、すべての変更を人が承認するようにしてください。**Ask first** の Rule を使えば、待機を Snowflake の接続だけに絞り込めます。チャットで `Propose an Ask first Rule for every write on the Snowflake connection` と依頼し、**Settings → Workspace → Autonomy → Rules** の **Needs review** で受け入れます。提案の確認方法は [Cassandra のガイド](/guide/connections/cassandra#write-access)で説明しています。

書き込みとは、任意の SQL ではなく、正確に 2 つの操作を意味します。

- 名前を指定した 1 つのウェアハウスの停止または再開。
- 依頼した場合に、測定した検出事項を `CT_FINDINGS` テーブルに保存すること。最初の保存時に、ロールが `CREATE TABLE` を持つ 1 つのスキーマにテーブルを作成します。ロールが複数のスキーマに書き込める場合は、どれにするかを尋ねます。プロンプトで指定することもできます（例: `MONITORING.ALERTS`）。

`CT_FINDINGS` には 6 つの列があります: `RECORDED_AT_UTC`、`CATEGORY`、`SEVERITY`、`SUBJECT`、`DETAIL`、`SOURCE`。検出事項の保存と古いものの削除はどちらも書き込みのため、それぞれが承認を経由します。自動では何も削除されません。指定した日数より古い行を削除するよう CloudThinker に依頼するか、自分で削除するまで、行は残ります。

ウェアハウスのサイズ変更、リソースモニターの変更、`DATA_RETENTION_TIME_IN_DAYS` の引き下げは、引き続き Snowsight で実行するステートメントとしてあなたに渡されます。

**Allow writes** は CloudThinker が依頼できるようにするだけです。ロールには引き続き付与が必要で、読み取り専用のトークンでは Snowflake がすべての書き込みを拒否します。書き込みをオンにするには:

<Steps>
  <Step title="書き込み用のロールとトークンを作成する">
    `DEV_WH` はエージェントが停止してよいウェアハウスに、`MONITORING.ALERTS` は `CT_FINDINGS` 用のスキーマに置き換えてください。`OPERATE` は、エージェントが停止してよいウェアハウスにだけ付与し、共有の本番のウェアハウスには決して付与しないでください。
    ```sql
    USE ROLE ACCOUNTADMIN;

    CREATE ROLE IF NOT EXISTS CT_READWRITE;
    GRANT DATABASE ROLE SNOWFLAKE.USAGE_VIEWER      TO ROLE CT_READWRITE;
    GRANT DATABASE ROLE SNOWFLAKE.OBJECT_VIEWER     TO ROLE CT_READWRITE;
    GRANT DATABASE ROLE SNOWFLAKE.GOVERNANCE_VIEWER TO ROLE CT_READWRITE;
    GRANT MONITOR USAGE ON ACCOUNT                  TO ROLE CT_READWRITE;
    GRANT USAGE ON WAREHOUSE CT_WH                  TO ROLE CT_READWRITE;

    GRANT USAGE, OPERATE, MONITOR ON WAREHOUSE DEV_WH     TO ROLE CT_READWRITE;
    GRANT USAGE ON DATABASE MONITORING                    TO ROLE CT_READWRITE;
    GRANT USAGE, CREATE TABLE ON SCHEMA MONITORING.ALERTS TO ROLE CT_READWRITE;

    GRANT ROLE CT_READWRITE TO USER SVC_CLOUDTHINKER;
    ALTER USER SVC_CLOUDTHINKER ADD PROGRAMMATIC ACCESS TOKEN CT_TOKEN_RW
      ROLE_RESTRICTION = 'CT_READWRITE'
      DAYS_TO_EXPIRY = 90;
    ```
    `token_secret` 列の値をコピーします。
  </Step>
  <Step title="接続を更新する">
    **Settings → Workspace → Connections** を開き、Snowflake を選んで、アカウントの行の鉛筆アイコンをクリックし、**Edit Instance** で **Replace…** をクリックします。新しいトークンを **Programmatic access token** に貼り付け、**Role** を `CT_READWRITE` に設定して、**Save and test** をクリックします。
  </Step>
  <Step title="Allow writes をオンにする">
    **Edit Instance** を閉じます。Snowflake の接続の詳細パネルで、**Allow writes** スイッチをオンにします。
  </Step>
  <Step title="読み取り専用のトークンを削除する">
    **Save and test** に合格すると、古いトークンは使われなくなります。`ALTER USER SVC_CLOUDTHINKER REMOVE PROGRAMMATIC ACCESS TOKEN CT_TOKEN;` を実行します。
  </Step>
</Steps>

読み取り専用に戻すには:

<Steps>
  <Step title="Allow writes をオフにする">
    Snowflake の接続の詳細パネルで、**Allow writes** スイッチをオフにします。CloudThinker はすぐに書き込みの提案をやめます。
  </Step>
  <Step title="読み取り専用のトークンに戻す">
    新しい読み取り専用のトークンを作成します。
    ```sql
    ALTER USER SVC_CLOUDTHINKER ADD PROGRAMMATIC ACCESS TOKEN CT_TOKEN_RO
      ROLE_RESTRICTION = 'CT_READONLY'
      DAYS_TO_EXPIRY = 90;
    ```
    **Settings → Workspace → Connections** を開き、**Snowflake** を選んで、アカウントの行の鉛筆アイコンをクリックし、**Edit Instance** で **Replace…** をクリックします。それを **Programmatic access token** に貼り付け、**Role** を `CT_READONLY` に設定して、**Save and test** をクリックします。
  </Step>
  <Step title="書き込み用のトークンとロールを削除する">
    ```sql
    ALTER USER SVC_CLOUDTHINKER REMOVE PROGRAMMATIC ACCESS TOKEN CT_TOKEN_RW;
    REVOKE ROLE CT_READWRITE FROM USER SVC_CLOUDTHINKER;
    DROP ROLE CT_READWRITE;
    ```
  </Step>
</Steps>

<Warning>
1 つのワークスペースに Snowflake の接続が 2 つ以上あると、承認された書き込みがどのアカウントを対象にするかを特定できないため、すべての接続で書き込みがオフになります。
</Warning>

<Warning>
停止を条件付きにすることはできません。CloudThinker が使用中かを確認してから停止するまでの間にクエリが開始され、そのコンピュートを失う可能性があります。
</Warning>

## トークンをローテーションする

<Steps>
  <Step title="新しいトークンを作成する">
    切り替えが完了するまで、古いトークンは残しておきます。読み取り専用の接続の場合:
    ```sql
    ALTER USER SVC_CLOUDTHINKER ADD PROGRAMMATIC ACCESS TOKEN CT_TOKEN_2
      ROLE_RESTRICTION = 'CT_READONLY'
      DAYS_TO_EXPIRY = 90;
    ```
    書き込みがオンの場合:
    ```sql
    ALTER USER SVC_CLOUDTHINKER ADD PROGRAMMATIC ACCESS TOKEN CT_TOKEN_RW_2
      ROLE_RESTRICTION = 'CT_READWRITE'
      DAYS_TO_EXPIRY = 90;
    ```
    `token_secret` 列の値をコピーします。
  </Step>
  <Step title="CloudThinker で置き換える">
    **Settings → Workspace → Connections** を開き、Snowflake を選んで、アカウントの行の鉛筆アイコンをクリックし、**Edit Instance** で **Replace…** をクリックします。新しいトークンを貼り付けて **Save and test** をクリックします。

    **成功時の状態:** テストに合格し、接続は **Connected** のままです。失敗した場合、CloudThinker は以前のトークンを保持します。
  </Step>
  <Step title="古いトークンを削除する">
    `ALTER USER SVC_CLOUDTHINKER REMOVE PROGRAMMATIC ACCESS TOKEN <old_token_name>;` を実行します（例: `CT_TOKEN` または `CT_TOKEN_RW`）。
  </Step>
</Steps>

## トラブルシューティング

<Accordion title="認証がすぐに失敗する（390403）">
サービスユーザーにネットワークポリシーがありません。`ALTER USER SVC_CLOUDTHINKER SET NETWORK_POLICY = CT_POLICY;` を実行してください。
</Accordion>

<Accordion title="昨日は機能していたのに今日は失敗する（390318）">
トークンが期限切れになったか、取り消されました。新しいトークンを作成し（セットアップのステップ 5）、接続に[ローテーション](#トークンをローテーションする)してください。
</Accordion>

<Accordion title="Object does not exist or not authorized（002003）">
ロールにデータベースロールが不足しています。確認用のプロンプトを実行してください。CloudThinker が、読めないすべての `ACCOUNT_USAGE` のビューと、それぞれに対する正確な `GRANT` を一覧表示します。
</Accordion>

<Accordion title="Connected なのに、すべてのクエリが失敗する（090073）">
リソースモニターがクォータを超えているか、ウェアハウスが停止していて再開できません。これは `GRANT` では修正できません。アカウントの管理者がリソースモニターを引き上げるかリセットします。トークンは有効でテストにはコンピュートが不要なため、ステータスは **Connected** のままです。
</Accordion>

<Accordion title="No active warehouse selected（000606）">
サービスユーザーに `DEFAULT_WAREHOUSE` がなく、接続にも設定がありません。**Warehouse** を設定するか、ユーザーにデフォルトを与えてください。
</Accordion>

<Accordion title="Role not authorized（090105）">
ロールがトークンの `ROLE_RESTRICTION` の範囲外です。トークンが許可するロールを使うか、**Role** を空にしてユーザーのデフォルトを使ってください。
</Accordion>

<Accordion title="セクションが空で返る">
エラーではありません。`ACCOUNT_USAGE` は最大数時間遅れ、365 日分の履歴を保持するため、静かなアカウントで短い期間を指定すると行が返らないことがあります。
</Accordion>

## セキュリティ

<ConnectionSecurity />

- **専用のサービスユーザー**: `TYPE = SERVICE` のユーザーにはパスワード、MFA、SSO がないため、トークンが唯一の入り口で、そのアクティビティを監査しやすくなります。
- **トークンを制限し、期限を設ける**: `ROLE_RESTRICTION` は接続が到達できる範囲を制限し、`DAYS_TO_EXPIRY` はローテーションを強制します。
