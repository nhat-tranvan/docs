HashiCorp Vault クラスターを接続すると、CloudThinker エージェントはシール状態とヘルスの確認、シークレットパスの中身の一覧表示、ポリシー・認証方式・監査デバイスの監査を行い、[Approvals](/guide/approvals/overview) を通じて短期間有効なデータベースやクラウドのクレデンシャルを発行できます。エージェントは CloudThinker のマネージドサンドボックスで公式の `vault` CLI を実行し、**token** または **AppRole**（Vault が短期間有効なトークンと交換する role ID と secret ID の組）でサインインします。

## 前提条件

- パブリック DNS 名や HCP Vault Dedicated のエンドポイントなど、CloudThinker がネットワーク経由で到達できる Vault のアドレス。`localhost` やプライベートアドレスは、お客様のネットワークではなく CloudThinker がコマンドを実行する場所で解決されます。ファイアウォールの内側にある Vault については、[Reaching private services](/ja/guide/connections/overview#プライベートサービスへの到達) を参照してください。
- ポリシーを書き込み、トークンまたは AppRole を作成する権限。
- 接続を追加するために必要な、CloudThinker ワークスペースの **Admin** ロール。[Roles](/guide/security/roles) を参照してください。
- Vault Enterprise または HCP Vault Dedicated の場合: シークレットがある namespace。HCP のデフォルトは `admin` です。

<Info>
1 つのワークスペースが持てる Vault 接続は 1 つです。エージェントがアクセスできる範囲は、トークンまたは AppRole のポリシーが許可する範囲とまったく同じです。それ以外はすべて Vault がデフォルトで拒否します。
</Info>

## 認証方式を選ぶ

| 方式 | 使う場面 | トレードオフ |
|--------|-------------|-----------|
| **AppRole** | 本番クラスター | トークンを再発行せずに secret ID をローテーションできます。各セッションがログインして、新しい短期間有効なトークンを取得します |
| **Token** | 試用や開発用のクラスター | 最も早くセットアップできます。トークンは TTL が切れるまで有効なので、そのスケジュールで置き換えます |

## セットアップ

<Steps>
  <Step title="最小権限のポリシーを書く">
    エージェントに見せたいパスの read と list から始めます。`secret` を KV のマウント名に置き換え、パスを必要な範囲に絞ってください。この例は KV v2 マウントを前提としています:

    ```bash
    vault policy write cloudthinker-read - <<EOF
    path "secret/data/*" {
      capabilities = ["read"]
    }
    path "secret/metadata/*" {
      capabilities = ["read", "list"]
    }
    path "sys/mounts" {
      capabilities = ["read"]
    }
    path "sys/auth" {
      capabilities = ["read"]
    }
    EOF
    ```

    `secret/data/*` の `read` があると、トークンはシークレットの値を読めます。CloudThinker は値を求められない限りキー名だけを表示しますが、これは CloudThinker の動作であって Vault の制限ではありません。Vault 側で強制したい場合は `secret/data/*` のブロックを削除してください。エージェントは引き続きパスの一覧とメタデータを読めますが、シークレット内のキーは一覧できなくなります。

    KV v1 マウントの場合は、2 つの `secret/` ブロックを 1 つに置き換えます: `path "secret/*" { capabilities = ["read", "list"] }`。

    ポリシーの監査や動的クレデンシャルを追加するには、[必要な権限](#必要な権限)を参照してください。
  </Step>
  <Step title="クレデンシャルを作成する">
    <Tabs>
      <Tab title="AppRole">
        AppRole を有効にし（すでに有効なら飛ばします）、ロールをポリシーに紐付けてから、role ID と secret ID を取得します:

        ```bash
        vault auth enable approle

        vault write auth/approle/role/cloudthinker \
          token_policies=cloudthinker-read \
          token_ttl=1h \
          token_max_ttl=4h \
          secret_id_ttl=720h

        vault read auth/approle/role/cloudthinker/role-id
        vault write -f auth/approle/role/cloudthinker/secret-id
        ```

        出力から `role_id` と `secret_id` をコピーします。
      </Tab>
      <Tab title="Token">
        ポリシーに紐付いたトークンを作成します:

        ```bash
        vault token create \
          -policy=cloudthinker-read \
          -ttl=720h \
          -display-name=cloudthinker
        ```

        出力から `token` の値をコピーします。
      </Tab>
    </Tabs>

    <Warning>
    どちらの例も 30 日（`720h`）で期限切れになります。AppRole の secret ID またはトークンが使えなくなり、接続が失敗します。リマインダーを設定し、期限が来たら新しいものを発行して、[セキュリティ](#セキュリティ)の説明どおりに接続を更新してください。
    </Warning>
  </Step>
  <Step title="CloudThinker で接続を追加する">
    **Settings → Workspace → Connections** を開き、**HashiCorp Vault** を選択します。**VAULT_ADDR** を入力し、Enterprise または HCP を使う場合は **Namespace** を設定し、**VAULT_AUTH_METHOD** で **AppRole** か **Token** を選んで、表示されるクレデンシャルのフィールドを入力します。**Connect** をクリックします。

    **成功の状態:** 接続は **Connecting**、**Verifying** を経て **Connected** になります。トークンの場合、CloudThinker は `vault token lookup` を実行します。AppRole の場合は `auth/approle/login` でログインし、Vault がトークンを返すことを確認します。
  </Step>
</Steps>

## 接続の詳細

| フィールド | 必須 | 説明 | 例 |
|-------|----------|-------------|---------|
| **VAULT_ADDR** | はい | スキームとポートを含む Vault の完全な URL | `https://vault.example.com:8200` |
| **Namespace** | いいえ | Enterprise または HCP の namespace。オープンソース版の Vault では空欄にします | `admin` |
| **VAULT_AUTH_METHOD** | はい | **Token**（デフォルト）または **AppRole** | **AppRole** |
| **VAULT_TOKEN** | Token のみ | `vault token create` で得たトークン | |
| **VAULT_ROLE_ID** | AppRole のみ | AppRole の `role_id` | |
| **VAULT_SECRET_ID** | AppRole のみ | AppRole の `secret_id` | |

## 必要な権限

必要な行だけを付与してください。各行は、セットアップで作ったポリシーにパスを追加します。

| エージェントにさせたいこと | ポリシーに追加するもの |
|--------------------|-------------------|
| KV v2 シークレットのキーの一覧表示とメタデータの読み取り | `<mount>/data/*` に `read`、`<mount>/metadata/*` に `read` と `list` |
| シークレットエンジンと認証方式の一覧表示 | `sys/mounts` と `sys/auth` に `read` |
| ポリシーの監査 | `sys/policies/acl` と `sys/policies/acl/*` に `read` と `list` |
| AppRole のロールの一覧表示 | `auth/approle/role` に `list` |
| 監査デバイスの一覧表示 | `sys/audit` に `read` と `sudo` |
| 動的クレデンシャルの発行 | `<engine>/creds/<role>`（例: `database/creds/readonly`）に `read` |
| リースの取り消しまたは更新 | `sys/leases/revoke` と `sys/leases/renew` に `update` |
| KV v2 シークレットの書き込みまたは削除 | 下の例を参照 |

`secret/myapp/` 配下への KV v2 の書き込みには、次を追加します:

```hcl
path "secret/data/myapp/*" {
  capabilities = ["create", "update", "delete"]
}
path "secret/destroy/myapp/*" {
  capabilities = ["update"]
}
```

ヘルスチェック（`sys/health`）と、呼び出し元自身のトークンに対する `vault token lookup` は Vault 組み込みの `default` ポリシーで動作するため、追加する必要はありません。

<Tip>
読み取り専用で始めてください。書き込みの行は、それが必要なワークフローがあるときにだけ追加します。その場合でも、すべての書き込みはまず [Approvals](/guide/approvals/overview) を通ります。**Manual** を選んで、すべての変更を人が承認するようにしてください。**Ask first** の Rule を使うと、それを Vault の接続だけに絞れます。
</Tip>

## エージェントの機能

| 機能 | エージェントができること | 承認 |
|------------|--------------------|----------|
| **ヘルス** | シール状態、バージョン、マウントされたシークレットエンジン、認証方式を確認します | 不要 |
| **シークレットの検出** | パスとシークレットが持つキーを一覧表示し、KV v1 と KV v2 を見分けます | 不要 |
| **ポリシーの監査** | 現在のトークンのポリシーと TTL を読み、ポリシーを一覧表示して読み、監査デバイスと AppRole のロールを一覧表示します | 不要 |
| **動的クレデンシャル** | シークレットエンジンから短期間有効なデータベースやクラウドのクレデンシャルを発行します | 必要 |
| **リースの管理** | クレデンシャルのリースを取り消すか更新します | 必要 |
| **シークレットと設定の変更** | KV のバージョンの書き込み、削除、破棄、ポリシーの書き込み、マウント・認証方式・監査デバイスの有効化と無効化を行います | 必要 |

エージェントは値を求められない限りシークレットの値ではなくキーとメタデータを報告し、トークンや secret ID を表示することは決してありません。動的クレデンシャルの発行は Vault では読み取りに見えますが、リースを作成するため、CloudThinker は書き込みとして扱います。書き込みは実行前に [Approvals](/guide/approvals/overview) を通ります。

### 接続を確認する

```text
Check Vault health and seal status, and list the mounted secret engines and auth methods
```

シール状態、Vault のバージョン、`secret/`（KV v2）などのマウントと `approle/` などの認証方式の一覧が返るはずです。

### プロンプト例

```text
Which keys does secret/myapp/config hold, and when was it last updated?
What policies and TTL does the current Vault token have?
Issue a database credential from the readonly role and tell me when the lease expires
```

## トラブルシューティング

<Accordion title="&quot;no such host&quot; や connection refused で接続が失敗する">
**VAULT_ADDR** が CloudThinker から到達できないアドレスを指しています。`localhost`、`127.0.0.1`、プライベートなホスト名は、CloudThinker がコマンドを実行する場所で解決されます。パブリック DNS 名か HCP のエンドポイントを使ってください。ファイアウォールや VPN の内側にある Vault には、まず到達可能なエンドポイントか許可リストによるアクセスが必要です。
</Accordion>

<Accordion title="unsupported protocol scheme">
アドレスにスキームがありません。`vault.example.com:8200` ではなく `https://vault.example.com:8200` を使ってください。
</Accordion>

<Accordion title="Invalid Vault token configuration、または Invalid Vault AppRole configuration">
選択した認証方式のクレデンシャルのフィールドが空です。**Token** の場合は **VAULT_TOKEN** を、**AppRole** の場合は **VAULT_ROLE_ID** と **VAULT_SECRET_ID** の両方を入力してください。
</Accordion>

<Accordion title="403 permission denied">
Vault は、ポリシーがパスをカバーしていない場合と、パスが存在しない場合の両方で 403 を返すため、403 はシークレットが存在しないことの証明にはなりません。エージェントにトークンが持つポリシーを尋ね、そのパスに `read` または `list` を追加してください。KV v2 では、`secret/myapp` を読むには `secret/data/myapp` に対するポリシーが必要です。

以前は動いていたリクエストがすべて 403 を返すようになった場合は、トークンが期限切れになった可能性が高いです。新しいトークンを発行して **VAULT_TOKEN** を更新してください。
</Accordion>

<Accordion title="HCP または Enterprise で &quot;no handler for route&quot; が出る">
**Namespace** が空か間違っています。シークレットがある namespace に設定してください。HCP Vault Dedicated のデフォルトは `admin` です。
</Accordion>

<Accordion title="invalid secret_id">
AppRole の secret ID が `secret_id_ttl` を過ぎました。新しいものを生成し、[セキュリティ](#セキュリティ)の説明どおりに **VAULT_SECRET_ID** に貼り付けてください:

```bash
vault write -f auth/approle/role/cloudthinker/secret-id
```
</Accordion>

<Accordion title="すべてのリクエストが失敗し、ヘルスに sealed: true と表示される">
クラスターがシールされているため、読み取りも書き込みも成功しません。Vault のオペレーターが `vault operator unseal` でアンシールする必要があります。
</Accordion>

## セキュリティ

<ConnectionSecurity />

- **クレデンシャルを置き換える**: Vault は単一接続のサービスなので、鉛筆アイコンはありません。接続が **Error** と表示されている間に、**Settings → Workspace → Connections** を開いて **HashiCorp Vault** を選択し、**Replace credentials** をクリックしてから **Replace…** をクリックし、新しいトークンまたは secret ID を貼り付けて **Save and test** をクリックします。テストが失敗した場合、接続は以前のクレデンシャルを保持します。それより前にローテーションするには、接続を切断し、新しい値でもう一度接続してください。[Rotate a credential](/ja/guide/connections/overview#認証情報をローテーションする) を参照してください。
- **本番では AppRole を優先する**: 各セッションは設定した TTL で期限切れになるトークンを取得し、ロールに触れずに secret ID をローテーションできます。
- **シークレットの値をチャットに出さない**: エージェントはデフォルトでキーを一覧表示します。値を求めると会話に表示されるため、必要なときにだけ求めてください。
- **不要になったリースを取り消す**: 期限切れを待つのではなく、タスクが終わったら動的クレデンシャルを取り消すようエージェントに依頼してください。
