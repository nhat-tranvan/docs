組織は、CloudThinker の最上位のアカウントです。請求とメンバーの一覧を所有し、実際の作業が行われる 1 つ以上の[ワークスペース](/ja/guide/workspaces)を含みます。

## 前提条件

- このページのほとんどのタスクには、組織の **Owner** または **Admin** が必要です。Developer と Viewer は、オーバーライドによってワークスペースの Admin になっている場合でも、**Settings → Organization** を開けません。そのようなワークスペースの Admin は、直接リンクから **Guardrails** と **BYOK** の 2 ページを開けます。ワークスペースの Admin は、自身の BYOK キーを含め、**Settings → Workspace** でそのワークスペースを管理します。
- Owner 以外は誰でも[組織を離れる](#組織を離れる)ことができます。

## 組織とワークスペースの関係

サインアップすると、CloudThinker はあなたの名前を付けた組織（例: "Jane's Organization"）を作成し、あなたをその Owner にします。その後、オンボーディングでその中に最初のワークスペースが作成されます。

| 組織にあるもの | 各ワークスペースにあるもの |
|---|---|
| プランと請求 | [接続](/ja/guide/connections/overview)と[認証情報](/guide/credentials) |
| メンバーの一覧と組織のロール | [カスタムエージェント](/ja/guide/agents/customize)、[スキル](/ja/guide/skills/overview)、[メモリ](/guide/memory) |
| [BYOK](/ja/guide/byok)、[SSO とプロビジョニング](/ja/guide/security/sso)、[監査ログ](/guide/security/audit-logs) | 会話、アーティファクト、モジュールのデータ（Optimize、Review、Cyber、Resolve） |
| [使用量](/ja/guide/billing/usage)と[クレジット上限](/guide/billing/credit-limits)（ここで設定し、ワークスペースごとに 1 つの上限） | [Approvals](/guide/approvals/overview)、[通知](/ja/guide/notifications)、ワークスペースのメンバー |

Approvals は各ワークスペース内で設定します。クレジット上限は、Owner または Admin が **Settings → Organization → Billing** で、ワークスペースごとに 1 つずつ設定します。一方により厳しい承認やより厳しい予算が必要な場合は、本番と非本番を別々のワークスペースに分けてください。[レイアウトを選ぶ](/ja/guide/workspaces#レイアウトを選ぶ)を参照してください。

## 組織の設定を開く

組織の制御は **Settings → Organization** にあり、一度に 1 つのワークスペースを扱う **Settings → Workspace** とは別です。

<Steps>
  <Step title="Settings を開く">
    サイドバー上部のワークスペースメニューをクリックし、**Settings** をクリックします。⌘⇧,（Windows と Linux では Ctrl+Shift+,）を押しても開けます。
  </Step>
  <Step title="Organization タブを選ぶ">
    Settings の上部にある **Organization** をクリックします。

    **成功時の状態:** サイドの一覧に、**General**、**Workspaces**、**Members** から始まる組織のページが表示されます。
  </Step>
</Steps>

[Organization settings](/guide/admin-settings) には、そこにあるすべてのページ、それぞれが設定する内容、各ページのガイドが一覧されています。表示されるページは、組織のロールと、組織で何が有効になっているかによって異なります。各ロールが何を変更できるかは、[下のロールの表](#組織のロール)に示しています。ワークスペースを削除できるのは **Workspaces** だけです。

## メンバーを招待する

<Steps>
  <Step title="Members を開く">
    **Settings → Organization → Members** に移動し、**Invite people** をクリックします。
  </Step>
  <Step title="メールアドレスを追加する">
    **Enter an email** にアドレスを入力し、Enter キーを押して追加します。このバッチに必要なだけ追加します。
  </Step>
  <Step title="ロールを選ぶ">
    ロールのメニューで **Admin**、**Developer**、**Viewer** のいずれかを選びます。デフォルトは Developer です。Owner として招待することはできません。

    このバッチのすべてのアドレスに 1 つのロールが適用されます。異なるロールで招待するには、別々のバッチで送ってください。
  </Step>
  <Step title="送信する">
    **Invite** をクリックします。

    **成功時の状態:** 招待された人がそれぞれ、**Invited** と有効期限とともにメンバーの一覧の上部に表示され、招待メールを受け取ります。招待は 7 日後に期限切れになります。
  </Step>
</Steps>

Developer と Viewer を招待する際にワークスペースを選ぶには、代わりにサイドバー上部のワークスペースメニューにある **Invite members** を使います。そのダイアログには **Select workspaces** があります。Admin はすべてのワークスペースを自動的に得るため、これは不要です。

<Warning>
ワークスペースを選ばずに Developer や Viewer を招待すると、組織には参加しますが、アクセスを付与するまでどのワークスペースも開けません。[ワークスペースのメンバー](/ja/guide/workspace-users)を参照してください。
</Warning>

**招待された人がすること:** メールのリンクを開き、招待されたアドレスでサインインまたはサインアップします。別のアドレスは拒否されます。すでに別の組織に所属している人はその組織を保持し、両方がワークスペースメニューに表示されます。

## 組織のロール

すべてのメンバーは 1 つの組織のロールを持ちます。組織の **Owner** は最も高いロールで、組織の料金を支払います。組織の **Admin** は、[Roles](/guide/security/roles#organization-permissions) の Owner 専用の行を除き、組織内のすべてを設定できます。Owner と Admin は、すべてのワークスペースで Admin です。Developer と Viewer には、組織の名前と割り当てられたワークスペースが表示されます。組織のメンバーの一覧は表示されず、各ワークスペースの **Members** ページでそのワークスペースのメンバーだけが表示されます。

| 権限 | Owner | Admin | Developer | Viewer |
|---|:---:|:---:|:---:|:---:|
| 組織の名前と説明の編集 | ✓ | ✓ | | |
| メンバーの招待と削除、ロールの変更 | ✓ | ✓† | | |
| ワークスペースの作成と削除 | ✓ | ✓ | | |
| すべてのワークスペースへの Admin アクセス | ✓ | ✓ | | |
| 使用量の閲覧、クレジット上限の設定 | ✓ | ✓ | | |
| プランと請求の管理 | ✓ | | | |
| BYOK と SSO の設定 | ✓ | | | |
| すべてのワークスペースの[ケイパビリティ](/guide/capabilities)の変更 | ✓ | | | |
| オーナーシップの移譲の依頼 | ✓ | | | |
| 割り当てられたワークスペースでの作業 | ✓ | ✓ | ✓ | 閲覧のみ* |

\*Viewer は会話、検出事項、ダッシュボードを開けますが、エージェントとのチャット、スキルの実行、変更はできません。

†Admin がロールを変更・削除できるのは、Developer と Viewer だけです。Admin は新しいメンバーを Admin として招待できますが、既存のメンバーを Admin に昇格させること、Admin のロールを変更すること、Admin を削除することができるのは Owner だけです。

SSO のジャストインタイムのサインインや SCIM で追加された人には、接続で設定した **Auto-assigned organization role**（デフォルトは Viewer）が付与されます。SCIM では、IdP のグループごとにロールを設定することもできます。[SSO](/ja/guide/security/sso) と [SCIM group mapping](/ja/guide/security/scim#グループをワークスペースに対応付ける) を参照してください。

Developer や Viewer のロールは、1 つのワークスペース内で上げたり下げたりできます。[ワークスペースのロール](/ja/guide/workspace-users#ワークスペースロール)を参照してください。"Member" は旧来のロール名で、Developer と同様に機能します。

## メンバーと招待を管理する

組織の名前は **Settings → Organization → General** で変更します。**Organization name** の横の **Edit** をクリックし、**Organization Name**（必要に応じて **Description** も）を変更して、**Save Changes** をクリックします。それ以外はすべて **Settings → Organization → Members** にあり、各人が操作メニュー（**...**）付きの 1 行になっています。

| タスク | 方法 |
|---|---|
| メンバーのロールを変更する | その行のロールのメニューで新しい値を選びます |
| Developer や Viewer が開けるワークスペースを変更する | 行の操作メニューで **Edit workspace access** をクリックします |
| メンバーを削除する | 行の操作メニューで **Remove** をクリックして確定します。組織内のすべてのワークスペースへのアクセスを失います |
| メンバーを有効化する | **Inactive** と表示された行の操作メニューで **Activate member** をクリックします |
| 招待を再送または取り消す | 招待の行の操作メニューを開き、**Resend invitation** または **Revoke invitation** をクリックします |

旧来のシート単位のサブスクリプションでは、組織に空きシートがない状態で（たとえば SSO 経由で）プロビジョニングされたメンバーは **Inactive** と表示されます。Inactive のメンバーはシートを使いません。有効化すると 1 シートを使います。

### 誰かを削除したときに起こること

| 項目 | 起こること |
|---|---|
| ワークスペースへのアクセス | 組織内のすべてのワークスペースから削除されます。そのメールアドレスへの保留中のワークスペースの招待はキャンセルされます |
| その人が所有する [Automations](/guide/automation/automations) | オフになります。それぞれに "Its owner no longer has access to this workspace." と表示されます。ワークスペースの Admin が **Take ownership** をクリックしてから、再度オンにします。その後は新しいオーナーとして、そのアクセス権で実行されます |
| Approvals | すべての承認者グループから外されるため、保留中のリクエストは残りの承認者に回ります |
| その人が作成したワークスペース | 中身すべてとともに組織に残ります。Owner と Admin はアクセスを保持します |
| その人のシート（旧来のシート単位のサブスクリプション） | 解放されます |

<Warning>
スケジュールされた Automations を所有する人を削除する前に、誰が引き継ぐかを決めてください。そうしないと、ワークスペースの Admin がオーナーシップを引き継ぐまで、それらの実行は何の通知もなく止まります。
</Warning>

## シート

Team、Scale、Enterprise には無制限のメンバーが含まれます。メンバーを追加しても、プランの料金や月間クレジットは増えません。Team には 3 つ、Scale には 10 のワークスペースが含まれます。[プランと料金](/ja/guide/billing/pricing)を参照してください。

<Note>
  シートの管理は、シート単位で請求される旧来のサブスクリプションにのみ適用されます。それらのサブスクリプションでは、有効なメンバーと保留中の招待がシートを占有します。招待は 7 日後に期限切れになります。Owner は **Settings → Organization → General** の **Seats → Manage** からシートを管理します。新しい有料プランではシートの購入は不要です。
</Note>

## 支出を制御する

クレジットは組織のレベルでプールされ、**Settings → Organization → Billing** の **Credit limits** のセクションで、各ワークスペースの取り分に上限を設定します。このセクションは、組織でクレジット上限が有効になっている場合にのみ表示されます。

| 設定 | 動作 |
|---|---|
| **Default monthly limit per workspace** | 独自のオーバーライドを持たないすべてのワークスペースのクレジットの上限、または **Unlimited** |
| **Per-workspace limits** | 1 つのワークスペースのための異なる上限や適用モード |
| **When a workspace hits its monthly limit** | **Throttle** はそのワークスペースでの有料クレジットの支出を止めます。Light モデルでのチャットは、1 日 100 の無料クレジットで続きます。[使用量](/ja/guide/billing/usage)を参照してください。**Notify only** は何もブロックしません |
| **Alert the owner at 80%** と **Alert the owner at 100%** | 2 つのスイッチがあり、どちらか、または両方をオンにできます。アラートは、アプリ内とメールで Owner にだけ届きます |

<Warning>
**Throttle** では、上限に達したワークスペースは、インシデントの最中であっても、有料クレジットでのエージェントの実行を止めます。本番は **Notify only** にするか高い上限を与え、**Throttle** はサンドボックスに使ってください。
</Warning>

消費量は **Settings → Organization → Usage** で追跡します。[クレジット上限](/guide/billing/credit-limits)と[使用量](/ja/guide/billing/usage)を参照してください。

## オーナーシップを移譲する

各組織には 1 人の Owner がいます。アプリには移譲のボタンはありません。オーナーシップを移すには、現在の Owner から [support@cloudthinker.io](mailto:support@cloudthinker.io) に、組織の名前と新しい Owner のメールアドレスを記載してメールを送ってもらいます。

- 新しい Owner は、すでに組織の有効なメンバーである必要があります。
- 元の Owner は Admin になります。

<Tip>
Owner が退職する前、まだメールを送れるうちに移譲を依頼してください。
</Tip>

## 組織を離れる

Admin、Developer、Viewer は組織を離れられます。サイドバー上部のワークスペースメニューをクリックし、組織のワークスペースの下にある **Leave organization** をクリックして確定します。

離れると、削除された場合と同じ影響があります。[誰かを削除したときに起こること](#誰かを削除したときに起こること)を参照してください。

Owner は離れられません。まず[オーナーシップを移譲](#オーナーシップを移譲する)してください。SCIM でプロビジョニングされたメンバーは、代わりに ID プロバイダーで削除されます。

## トラブルシューティング

<AccordionGroup>
  <Accordion title="Settings → Organization に Organization admin access required と表示される">
    **原因:** 組織のロールが Developer または Viewer です。オーバーライドによってワークスペースの Admin になっていても、組織の設定は開けません。

    **対処:** 組織の Owner または Admin にロールの変更を依頼してください。ワークスペースの BYOK キーなどのワークスペースの設定には、代わりに **Settings → Workspace** を使います。
  </Accordion>
  <Accordion title="招待のボタンに Seats full と表示される">
    **原因:** 旧来のシート単位のサブスクリプションで、有効なメンバーと保留中の招待がすべてのシートを使い切っています。新しい有料プランには無制限のメンバーが含まれます。

    **対処:** 誰も受け入れない招待をキャンセルするか、退職したメンバーを削除するか、**Settings → Organization → General** の **Seats → Manage** からシートを追加するよう Owner に依頼してください。
  </Accordion>
  <Accordion title="メンバーを削除できない">
    **原因:** 次のいずれかのルールが当てはまります。

    - Admin は他の Admin や Owner を削除できません。
    - 組織の Owner は削除できません。
    - SCIM でプロビジョニングされたメンバーは、ID プロバイダーで削除する必要があります。エラーには "This member was provisioned via SCIM." と表示されます。

    **対処:** Owner に依頼するか、ID プロバイダーでユーザーのプロビジョニングを解除してください。[SCIM](/ja/guide/security/scim) を参照してください。
  </Accordion>
  <Accordion title="新しいチームメイトがサインインしたが、ワークスペースが表示されない">
    **原因:** ワークスペースが割り当てられていない Developer または Viewer です。

    **対処:** **Settings → Organization → Members** に移動し、その人の行の操作メニューで **Edit workspace access** をクリックし、ワークスペースを選んで、**Save Changes** をクリックします。
  </Accordion>
</AccordionGroup>
