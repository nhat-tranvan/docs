アラートより先に問題が届いたときに、インシデントを記録します。顧客からのメール、チャットでのチームメイトからの連絡、様子がおかしいダッシュボードなどです。何が起きているかを説明し、手元にあるものを添付すると、送信した時点で CloudThinker が根本原因の調査を開始します。調査を開始せずにインシデントを記録する方法はないため、すでに修正済みのものを記録する手段ではありません。アラートのソースを接続している必要はありません。

## 始める前に

- ワークスペースの **Admin** ロール。Developer と Viewer はインシデントを読めますが、記録はできません。ロールは固定のため、この権限だけを付与する方法はありません。[Roles](/guide/security/roles) を参照してください。
- 調査が実際のデータを確認できるよう、関係するシステムへの[接続](/ja/guide/connections/overview)。
- 任意: 添付するスクリーンショット、ログのエクスポート、エラーの出力。`.log` ファイルは受け付けられないため、ログは `.txt` として保存してください。
- クレジット。記録した各インシデントは、**AI auto-investigate** がオフでも送信した瞬間に調査を開始し、他の実行と同様にクレジットで課金されます。[使用量](/ja/guide/billing/usage)と [What starts an investigation](/guide/incident/settings#what-starts-an-investigation) を参照してください。

<Warning>
記録したインシデントは本物のインシデントです。テストの場合は、まず[安全にテストする](#安全にテストする)を読んでください。
</Warning>

## インシデントを記録する

<Steps>
  <Step title="フォームを開く">
    **Resolve → Issues** に移動し、**Log Incident** をクリックします。
  </Step>
  <Step title="テンプレートを選ぶ（任意）">
    **Quick Start Template** は、タイトルのプレフィックス、説明の骨子、重大度を入力します。入力された内容はすべて編集できます。5 つのテンプレートは固定のため、独自のものは追加できません。たとえば **API Outage** は、タイトルを `[API Outage] ` に、コンテキストを次のように設定します。

    ```text
    Affected API:
    Error Type: (5xx, timeout, connection refused)
    First Detected:
    Impact: (users affected, dependent services)
    Error Rate:
    ```

    | テンプレート | タイトルのプレフィックス | 骨子が求める内容 | 入力される重大度 |
    |---|---|---|---|
    | API Outage | `[API Outage]` | 影響を受ける API、エラーの種類、最初の検出、影響、エラー率 | High |
    | Database Issue | `[Database]` | データベース、問題の種類、最初の検出、影響、現在のメトリクス | High |
    | Deployment Failure | `[Deployment]` | サービス、環境、デプロイの ID またはバージョン、失敗の理由、ロールバックの状況 | Medium |
    | Service Degradation | `[Degradation]` | サービス、劣化の種類、最初の検出、現在の性能と期待される性能 | Medium |
    | Infrastructure Alert | `[Infrastructure]` | リソース、アラートの種類、インスタンスまたはノード、現在の値、しきい値 | Medium |
  </Step>
  <Step title="問題を説明する">
    | フィールド | 必須 | 入力する内容 |
    |---|---|---|
    | **What's happening?** | はい | 1 行の要約。これがインシデントのタイトルになります。 |
    | **Context** | いいえ | 症状、影響、タイミング、すでに試したこと |
    | **Attach** | いいえ | **Attach** をクリックするか、ドラッグ＆ドロップするか、貼り付けます。最大 5 ファイル、それぞれ 25 MB までですが、`.csv`、`.tsv`、`.xlsx` は最大 100 MB です。ファイルピッカーは、画像（PNG、JPG、GIF、WebP）、`.pdf`、`.txt`、`.md`、`.json`、`.yaml`、`.yml`、`.xml`、`.csv`、`.tsv`、`.docx`、`.xlsx`、`.pptx`、`.zip`、`.tar`、`.gz` を受け付けます。アーカイブは直接読まれず、調査ではまず展開する必要があるため、可能であればログファイル自体を添付してください。 |
    | **Severity** | はい | **Critical**、**High**、**Medium**、**Low**、**Info**。**Medium** から始まります。 |
    | **Occurred At** | いいえ | 始まった時刻（ブラウザのローカル時刻）。デフォルトは現在です。最大 30 日前まで遡れますが、未来の時刻は指定できません。 |

    <Note>
    重大度は、Slack のウォールームを開くかどうかを決めます。開くのは、[Resolve Triggers & Outcomes](/guide/incident/triggers-and-outcomes#outcomes) で設定した下限（デフォルトは **High & critical**）を満たす場合だけです。誰かを呼び出すかどうかは、重大度ではなくトリアージ（インシデントに今すぐ対応者が必要かを CloudThinker が確認すること）で決まります。[How Resolve decides an incident needs people](/guide/incident/oncall#how-resolve-decides-an-incident-needs-people) を参照してください。
    </Note>

    具体的なコンテキストがあれば、調査はより良い出発点を得られます。例:

    ```text
    What's happening?
    Checkout API returning 502s for EU customers

    Context
    Service: checkout-api (EKS cluster prod-eu)
    First reported: 14:05 UTC by support, three customer tickets
    Impact: roughly 1 in 5 checkout requests fail, EU only
    Recent change: payment-client v2.3 deployed at 13:50 UTC
    Already tried: restarted two pods, no change
    ```
  </Step>
  <Step title="送信する">
    **Log Incident** をクリックします。

    **成功時の状態:** 新しいインシデントが **Resolve → Issues** で選択された状態で開き、**AI auto-investigate** がオフでも RCA がすでに開始されています。ステータスは **AI is handling** で、インシデントのページに **Watch live** ボタンが表示されます。
  </Step>
</Steps>

## 次に起こること

1. CloudThinker が説明と添付ファイルを読み、接続されたシステムを確認して説明を検証します。
2. 検出事項は保存されるたびにインシデントのページに表示されます。**Watch live** をクリックすると、会話を追えます。
3. 完了すると、インシデントは文章の判定、因果グラフ、修復の提案とともに **Needs you** に移ります。

結果の読み方と各提案の決着のさせ方は、[調査と RCA](/ja/guide/incident/root-cause-analysis) で説明しています。

## 安全にテストする

記録したインシデントは本物のインシデントで、クレジットを使います。テストを記録する前に:

- [Resolve Triggers & Outcomes](/guide/incident/triggers-and-outcomes#outcomes) で **Post incident updates** をオフにするか、テスト用のチャネルに向けてください。そうしないと、インシデントの開始、ステータスの変更、解決のたびに、そのチャネルにメッセージが届きます。
- 重大度に **Info** を選んでください。下限が **All severities** に設定されていない限り、Slack のウォールームは開きません。
- 誰かが呼び出されるかどうかは、重大度ではなく、[On-call](/guide/incident/oncall) の設定とトリアージの判断によって決まります。
- テストも [Resolve insights](/guide/incident/insights) にカウントされます。たとえば **Event → incident reduction** の背後にあるインシデントの合計です。**False alarm** としてクローズしても除外されません。
- テストのインシデントをクローズするには、インシデントのヘッダーのステータスバッジをクリックし、**False alarm** を選んで、**Change Status** で確定します。

## 記録するか、Pulse に捉えさせるか

| 状況 | すること |
|---|---|
| 顧客やチームメイトが問題を報告した | インシデントを記録する |
| モニターが発火する前に調査したい | インシデントを記録する |
| アラートツールが Webhook を送信できる | [Pulse のソース](/ja/guide/pulse/setup)として接続し、今後のアラートが自動でインシデントになるようにする |
| Signals がすでにアラートをまとめている | 重複して記録せず、既存のインシデントから作業する。まず確認してください: **Resolve → Issues** の **Search issues**、または **Resolve → Signals** の **History** レーンの **Search signals...** で、アラートのタイトルの単語を検索します。[Clusters](/ja/guide/pulse/clusters) を参照してください。 |

## トラブルシューティング

| 問題 | 対処 |
|---|---|
| **Log Incident** ボタンがない | インシデントを記録できるのはワークスペースの Admin だけです。ワークスペースの Admin に依頼してください。 |
| **Log Incident** がグレー表示になっている | ファイルがまだアップロード中か、検証に失敗しています（種類が誤っているか、大きすぎます）。ファイルを削除するか、アップロードを待ってください。 |
| 日付を選べない | **Occurred At** は過去 30 日間だけを受け付け、未来は受け付けません。 |
| 判定が **Possible**、またはステータスが **Not found** | 調査が適切なシステムを読めませんでした。不足している[接続](/ja/guide/connections/overview)を追加してください。**Not found** の場合は、まずステータスバッジをクリックして **Investigating** を選びます（[the Not found warning](/ja/guide/incident/root-cause-analysis#調査の結果) を参照）。その後、**More actions → Open AI Conversation** を開き、より詳しく再度依頼します。[Re-investigation](/ja/guide/incident/root-cause-analysis#再調査) を参照してください。 |
