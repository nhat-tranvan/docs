インシデントメモリとは、CloudThinker が [根本原因の調査](/ja/guide/incident/root-cause-analysis) の最後に書き込み、次の調査の最初に読み込むメモの集まりです。同じサービスが同じ形で再び障害を起こしたとき、CloudThinker はゼロからではなく、チームがすでに学んだことから調査を始めます。

## 前提条件

- Resolve が少なくとも 1 つのソースからアラートを受信していること。[Pulse ソースの接続](/ja/guide/pulse/setup) を参照してください。
- 有効にする設定はなく、無効にするワークスペースのスイッチもありません。処置 (disposition) に到達したすべての調査がメモリを書き込みます。調査を始めたのが **AI auto-investigate** でも、Admin が **Investigate** をクリックした場合でも同じです。調査結果はすべてのロールが閲覧できます。[Roles](/guide/security/roles) を参照してください。

## CloudThinker が記録する内容

メモリは CloudThinker が自分で書き込みます。フォームに入力する必要はなく、すべてのインシデントがエントリーを生むわけではありません。各エントリーは次の 3 種類のいずれかです。

| 種類 | 用途 |
|---|---|
| **Recollection** | 1 件のインシデントの経緯: 症状、根本原因、何が変わったか、修正、そして修正を証明するチェック |
| **Observation** | 進行中の調査から得た発見。対応者が何をすべきかを示す `Action:` 行を含みます |
| **Lesson** | 少なくとも 2 件の過去のインシデントに裏付けられたパターン。1 件の珍しいインシデントがルールになることを防ぎます |

CloudThinker は、実際に調査を行い処置に到達した実行 (評価、重大度、クローズの判断を保存した実行) のあとに recollection を書き込むか更新します。単純な質問、中断された実行、処置に到達しなかった実行では何も書き込みません。インシデントが再オープンされると、CloudThinker は 2 件目を追加せず、そのインシデントの既存の recollection を更新します。

すべての recollection は同じ 5 行の形式に従います。次の例はその一例です。

```text
Symptom: checkout-api 5xx rate above 20% on target group tg-checkout at 14:02 (CloudWatch)
Root cause: Probable. Connection pool exhausted after max connections was lowered
Origin changed: unknown
Fix: operator-applied. Pool size restored to its previous value
Verify-with: 5xx rate on tg-checkout over 15 minutes; expected below 1%
```

CloudThinker は、観測された事実、推論、不明な経緯を区別して記録します。裏付けのない項目には推測ではなく `unknown` と書きます。

## 想起の仕組み

新しい調査が始まると、CloudThinker は仮説を立てる前にメモリを読み込みます。

1. ワークスペース内で最近更新された 20 件のエントリーを、3 種類すべてから、サービスで絞り込まずに読み込みます。インシデントの多いワークスペースでは、古い recollection は、CloudThinker がこの 20 件を超えてワークスペースの recollection の全一覧を調べた場合にのみ見つかります。
2. 一致する recollection、つまり同じサービスまたはコンポーネントで同じ症状のものを探します。
3. 一致したインシデントが以前に解決されている場合、その recollection に記録された、修正を証明する手軽なチェックを 1 つ実行します。
   - **チェックが成功した場合:** 以前の修正はまだ有効です。CloudThinker は現在の証拠を読んで処置を決めます。同じ事象の重複した報告は新たな発生として数えません。
   - **チェックが失敗した場合:** CloudThinker は現在の障害をそれ自体として調査します。以前の原因が再発したとは仮定しません。
4. 想起したエントリーはすべて証拠ではなく手がかりとして扱います。判定は引き続きお使いのシステムのデータに基づき、メモリが **Probable** の原因を **Strong evidence** に格上げすることはありません。

<Tip>
新しいアラートを過去のインシデントと照合できるよう、すべてのソースで **Service** と **Resource ID Path** の名前をそろえてください。
</Tip>

インシデントメモリは **Settings → Workspace → Memory** には表示されません。そこに表示されるのは [ワークスペースメモリ](/guide/memory) の項目です。CloudThinker が何を確認したかを見るには、実行中に **Watch live** をクリックするか、終了後に **More actions → Open AI Conversation** を開きます。過去の修正が再チェックされた場合、会話には CloudThinker が実行した `Verify-with:` チェックが表示されます。想起したエントリーを一覧表示する別のステップはありません。

## 修正が維持されたかを確認する

適用済みの修正を記録した recollection は、最初は **Unverified** です。フォローアップのチェックによって **Verified** または **Failed** になり、以降の調査がそれを信頼するかどうかが決まります。

<Steps>
  <Step title="調査の会話を開く">
    **Resolve → Issues** に移動してインシデントを選択し、**More actions → Open AI Conversation** を開きます。
  </Step>
  <Step title="フォローアップカードを有効にする">
    CloudThinker が自分で修正を適用し、`Verify-with:` チェックを記録した場合、会話内のカードとしてフォローアップを提案します。カードには実行タイミングと監視内容が表示されます。**Enable** と **Dismiss** にはワークスペースの Admin ロールが必要です。Admin が **Enable** をクリックするまで何もスケジュールされません。他のメンバーにはボタンのないカードと、**Only members who can create automations may enable this.** という注記が表示されます。会話のリンクを Admin に送るか、自分でチェックを依頼してください (次のステップ)。

    チームが手作業で適用した修正にはカードが表示されず、カードには時刻の選択欄もありません。いずれの場合も、自分でチェックを依頼してください (次のステップ)。

    **成功時の状態:** カードに **Scheduled** と表示され、フォローアップは提案された時刻に実行される [automation](/guide/automation/automations) になります。
  </Step>
  <Step title="または自分で依頼する">
    カードが表示されなかった場合は、同じ会話で次のように依頼します。

    ```text
    Tomorrow at 09:00 UTC, re-run the check that proves this incident's fix and update its recollection with the result.
    ```

    実行時刻があいまいにならないよう、依頼にはタイムゾーンを明記してください。**成功時の状態:** フォローアップが、依頼した時刻とともに [automations](/guide/automation/automations) の一覧に表示されます。
  </Step>
  <Step title="結果を読む">
    フォローアップが実行されると、会話内でチェック結果を報告し、recollection の結果を設定します。
  </Step>
</Steps>

### 検証結果

結果は、会話内のフォローアップの報告でのみ確認できます。他の画面には表示されません。

| 結果 | エントリーの種類 | 意味 | 以降の調査への影響 |
|---|---|---|---|
| **Unverified** | すべて | まだ決定的なチェックがありません。結果のないエントリーの既定値です。 | 手がかりとして使われます。CloudThinker がこれを標準手順にすることはありません。 |
| **Verified** | すべて | フォローアップのチェックが期待どおりの結果を確認しました | 維持された修正というラベル付きで、手がかりとして使われます |
| **Failed** | Lesson | パターンが当てはまりませんでした | ガイダンスとして表示されなくなります |
| **Failed** | Recollection または observation | 記録された修正が維持されませんでした | 同じ修正が再び前提とされないよう、反例として保持されます |

## メモリの正確さを保つ仕組み

インシデントメモリを表示、エクスポート、編集、削除する画面はありません。メモリはワークスペースごとに保持され、他のワークスペースと共有されることはありません。CloudThinker がワークスペースのデータをどのように保存し保護するかは、[セキュリティの概要](/ja/guide/security/overview) を参照してください。エントリーが誤っている場合や、含まれるべきでないデータが含まれている場合は、ワークスペース名とインシデント ID を添えて [support@cloudthinker.io](mailto:support@cloudthinker.io) にメールしてください。CloudThinker は作業しながらメモリを維持します。

- 新しい証拠が過去の recollection の一文と矛盾した場合、CloudThinker はその一文を編集し、訂正の根拠となる観測を記載します。
- 裏付けのない過去の主張は削除されず、未検証としてマークされます。今日の障害が異なっていても、裏付けのある過去のインシデントは消されません。
- 互いに矛盾する 2 つの lesson は、1 つの訂正済み lesson に統合されるか、古いほうが削除されます。
- 古くなったエントリーは複製されず、その場で編集されます。

調査を最後まで実行させること、インシデントの **Actions** セクション (**Resolve → Issues** の結果の下) で各提案を **Mark as Done** または **Dismiss** で確定し、実際に行ったことをメモに残すこと、そしてフォローアップのチェックを有効にすることが、メモリの精度向上に役立ちます。[各修復提案を確定する](/ja/guide/incident/root-cause-analysis#修復の各提案を決着させる) を参照してください。

## トラブルシューティング

<AccordionGroup>
  <Accordion title="再発したインシデントの調査がゼロから始まった">
    **原因:** 以前の実行が処置に到達しなかったため、recollection が書き込まれませんでした。または、新しいインシデントの症状、サービス、コンポーネントが異なります。インシデントの多いワークスペースでは、古い recollection が最近の 20 件のエントリーの外にある場合もあります。[想起の仕組み](#想起の仕組み) を参照してください。**確認:** 以前のインシデントを開き、判定とクローズ済みの結果が表示されていることを確認します。**対処:** 調査を判定まで実行させてください。カスタム Webhook の場合は、インシデントがコンポーネントを一貫して指すよう、**Service** と **Resource ID Path** をマッピングします (ソースの編集画面で設定)。[カスタムソース](/guide/incident/webhook-integrations/custom-source) を参照してください。
  </Accordion>
  <Accordion title="前回失敗した修正を CloudThinker が提案した">
    **原因:** 以前の修正が一度もチェックされなかったため、その recollection が **Unverified** のままでした。**対処:** 次回はフォローアップカードを有効にするか、上記のように会話内でフォローアップのチェックを依頼してください。
  </Accordion>
  <Accordion title="フォローアップのチェックが実行されなかった">
    **原因:** カードが有効にされませんでした。提案されたフォローアップは、有効にするまで automation になりません。**確認:** [automations](/guide/automation/automations) の一覧でフォローアップを探します。**対処:** 会話内でカードを有効にするか、CloudThinker にチェックのスケジュールを依頼してください。
  </Accordion>
</AccordionGroup>
