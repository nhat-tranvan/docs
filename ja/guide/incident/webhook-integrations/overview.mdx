Webhook とは、アラートが発生するたびに監視ツールが呼び出す URL で、Resolve は数秒以内にアラートを受け取ります。ツールごとに 1 つ作成し、ツールの JSON フィールドをタイトル、重大度、サービスにマッピングして、CloudThinker が根本原因分析 (RCA) を自動で開始するかどうかを決めます。

## アラートの流れ

Webhook に届いたアラートは、そのままインシデントになるわけではありません。まず [Pulse](/ja/guide/pulse/overview) を通ります。

**シグナル** とは、ノイズ抑制を通過したイベントです。**クラスター** とは、Pulse が 1 つの問題として扱う、関連するシグナルのグループです。トリアージに進むのは対応が必要なシグナルを含むクラスターだけで、トリアージがインシデントにするかどうかを決めます。

Webhook は、アラートが Resolve に届く 3 つの経路の 1 つです。ソースがポーリングされる場合やチャットチャンネルに届く場合は、[アラートソースの接続](/guide/incident/connect-alert-sources) を参照してください。

## 始める前に

- ワークスペースの **Admin** ロール。
- Webhook を追加できる、監視ツールの管理者権限。
- 必要なときに発生させられる実際のアラートのペイロード 1 件、またはその JSON のサンプル。

## Webhook を作成する

<Steps>
  <Step title="プラットフォームを開く">
    **Resolve → Triggers & Outcomes** に移動し、Datadog、Grafana、PagerDuty などのツールを選択します。
  </Step>
  <Step title="シグナルを追加する">
    **Signals to Resolve** の下で **Add signal** (または **Add another signal**) をクリックします。3 つのステップからなる **Create Webhook** ダイアログが開きます。
  </Step>
  <Step title="Basic Info">
    **Webhook Name** (既定値は `<Tool> Webhook`) はそのままにするか変更し、必要に応じて **Description** を追加します。**Next** をクリックします。
  </Step>
  <Step title="Configure">
    **Field Mapping** と **Severity Mapping** を確認します。どちらも選んだツールに合わせて事前に入力されています。**Send directly to CloudThinker** はオフのままにします ([理由](#rca-の開始タイミングを決める))。**Next** をクリックします。
  </Step>
  <Step title="Advanced">
    **Auth Method** を選び、**Auto-investigate** を設定します (どちらも下記で説明します)。**Create** をクリックします。
  </Step>
</Steps>

**成功時の状態:** ダイアログに **Webhook URL**、**Authentication Setup** の下の **Secret Key**、そして **cURL**、**JavaScript**、**Python**、**Node.js** タブのある **Integration Examples** が表示されます。URL と **Secret Key** を今すぐコピーしてください。キーは一度しか表示されません。同じダイアログに、お使いのツール向けの **Setup Guide** が表示されるので、それに従って貼り付けます。テストを送るには **cURL** タブが最も手早い方法です。

<Tip>
**Done** をクリックする前に **Secret Key** をコピーしてください。紛失した場合は、**Resolve → Triggers & Outcomes** に移動してツールを開き、**Signals to Resolve** の下で Webhook の行の **Manage** メニュー (**⋯**) → **Regenerate credentials** を開きます。これにより **Webhook URL** と **Secret Key** の両方が置き換えられ、古い組み合わせはすぐに使えなくなります。この Webhook を使うすべてのツールに、新しい URL とキーが必要です。
</Tip>

## フィールドをマッピングする

各マッピングフィールドには、アラートの JSON 内のパスを指定します。必須なのは **Title Path** だけです。

- `event.data.title` のようにドット区切りのキーを使い、リストの項目には `alerts[0].labels.severity` のように `[n]` を使います。先頭の `$.` は受け付けられ、取り除かれます。
- パスは最大 8 セグメントです。ドットを含むキーは指定できず、代替パスもありません。
- パスは 1 つのテキストまたは数値で終わる必要があります。リストやオブジェクトで終わるパスは何にもマッピングされません。

| フィールド | 入力される内容 |
|---|---|
| **Title Path** | インシデントのタイトル。必須です。 |
| **Severity Path** | 重大度レベル。**Severity Mapping** によって変換されます。 |
| **Description Path** | インシデントの説明。 |
| **Service Path** | 影響を受けたサービス。同じサービスを示すシグナルは 1 つのクラスターにまとまることがあるため、`prod` のような広い値ではなく、1 つのサービス名を使ってください。 |
| **Resource ID Path** | 影響を受けたリソースの識別子。同じリソース ID の繰り返しは 1 つのクラスターにまとまります。空の場合、CloudThinker は最上位の `resource_id` キーを読み取ります。[シグナルがクラスターにまとまる仕組み](/ja/guide/pulse/clusters#シグナルがクラスターに合流する仕組み) を参照してください。 |
| **Resource Name Path** | 影響を受けたリソースの名前。 |
| **Timestamp Path** | イベントの開始時刻 (ISO 8601 形式)。空の場合、CloudThinker は最上位の `timestamp` キーを読み取ります。どちらもない場合、または解析できない値の場合は、配信が届いた時刻を使います。 |

ペイロードの形はお使いのツールが決めます。たとえば Datadog では、Datadog のテンプレート変数を使って、Webhook の **Payload** フィールドに JSON を自分で書きます。Datadog のプリセットは `title`、`body`、`alert_type` を読み取ります。プリセットの既定の **Service Path** (`tags`) はリストを指していて何にもマッピングされないため、1 つのサービス名を持つ `service` キーを追加してください。

```json
{
  "title": "$EVENT_TITLE",
  "body": "$EVENT_MSG",
  "alert_type": "$ALERT_TYPE",
  "service": "web-api"
}
```

| フィールド | パス | 値の例 |
|---|---|---|
| **Title Path** | `title` | High CPU on web-server-01 |
| **Description Path** | `body` | CPU usage exceeded 90% for 5 minutes |
| **Severity Path** | `alert_type` | error |
| **Service Path** | `service` (`tags` から変更) | web-api |

固定の `service` 値は、この Webhook に通知するすべてのモニターに適用されます。Datadog の `$ALERT_TYPE` は `error`、`warning`、`info`、`success` を送りますが、Datadog プリセットの **Severity Mapping** が対応しているのは `alert`、`warn`、`ok`、`no data` です。**Severity Mapping** の下で **Customize** をクリックし、次の各行について **Add Mapping** をクリックしてください (レベルはチームに合わせて変更してください)。後から Webhook の行の **Manage** メニュー (**⋯**) → **Edit** で追加することもできます。

| ソースの値 | 重大度 |
|---|---|
| `error` | high |
| `warning` | medium |
| `info` | info |
| `success` | info |

`success` (復旧) イベントは何もクローズしません。通常のシグナルとして届き、クラスターは引き続き 12 時間新しいシグナルがないか、人が解決したときにクローズします。CloudThinker の分類器は復旧や正常な状態を対応不要として扱うため、そのクラスターが自動でトリアージに進むことはありません。このチェックはモデルの判断なので、復旧が通り抜けることもあります。人はいつでも **Open incident** (またはクラスターの **⋯** メニューの **Escalate**) でクラスターをトリアージに送れます。

**Severity Mapping** は、ツール独自の語を CloudThinker の 5 つのレベル (critical、high、medium、low、info) に変換します。たとえば汎用プリセットは、`warning` を medium に、`error` を high にマッピングします。照合では大文字と小文字、前後の空白は区別しないため、`ERROR` と `error` は同じ行に一致します。

| **Severity Path** の値 | 結果 |
|---|---|
| 5 つのレベルのいずれか | そのまま使われます。行は不要です。 |
| マッピングの行がある | その行のレベル |
| その他 | **medium** |
| **Severity Path** が空、または何も見つからない | CloudThinker は代わりに最上位の `severity` または `priority` キーを読み取ります |
| `severity` キーも `priority` キーもない | **medium** |

お使いのツールが一覧にない場合は、代わりに [カスタムソース](/guide/incident/webhook-integrations/custom-source) を使ってください。実際のペイロードを 1 件取り込み、フィールドをクリックしてマッピングできます。

## 認証を選ぶ

| Auth Method | ツールが送るもの | 使う場面 |
|---|---|---|
| **Bearer Token** | `Authorization: Bearer <secret>` | ツールでカスタムヘッダーを追加できる場合。ほとんどのツールの既定値です。Datadog では、Webhook の **Custom Headers** フィールドに JSON を指定します: `{"Authorization": "Bearer <secret>"}`。 |
| **HMAC Signature** | 生のリクエストボディの HMAC-SHA256 を 16 進数でエンコードし、指定したヘッダーで `sha256=<hex digest>` として送ります。PagerDuty の `X-PagerDuty-Signature` (`v1=<hex digest>`) も受け付けます。 | PagerDuty のように、ツールが Webhook に署名する場合。ヘッダー名は **HMAC Signature Header** に設定します。ツールが独自の署名シークレットを生成する場合は、それを **Provider signing secret** に貼り付けます。 |
| **API Key** | 指定したヘッダーに入れたキー | EventBridge 経由の CloudWatch のように、ツールが API キーのヘッダーにしか対応していない場合。**API Key Header** と、必要に応じて **Key Prefix** を設定します。 |
| **No Authentication** | なし | 簡単なテスト専用です。URL を知っている人なら誰でもアラートを送れてしまいます。 |

ダイアログでは、選んだ方法に応じて認証情報の名前が変わります。**Bearer Token** では **Secret Key**、**HMAC Signature** では **HMAC Secret**、**API Key** では **API Secret** です。どれも同じ認証情報で、いずれの場合も一度しか表示されません。

## RCA の開始タイミングを決める

**Auto-investigate** は既定でオンです。この Webhook の対応が必要なクラスターはトリアージに進み、トリアージがインシデントをオープンして調査します。オフにすると、誰かがクラスターで **Open incident** と **Send to triage** をクリックするまで、アラートは Signals に残ります。**Only from a minimum severity** では下限を選びます: **Info and above**、**Low and above**、**Medium and above**、**High and above**、**Critical only**。下限未満のアラートも関連するアラートとまとめられますが、それだけでトリアージを開始することはありません。

これらのオプションが **AI auto-investigate** や手動の開始とどう組み合わさるかは、[調査を開始するもの](/guide/incident/settings#what-starts-an-investigation) を参照してください。

<Note>
自動調査はそれぞれクレジットで課金されます。ノイズの多いツールを接続する前に、最低重大度または [Credit limit](/guide/billing/credit-limits) を設定してください。
</Note>

**Send directly to CloudThinker** (**Configure** ステップにあり、既定でオフ) は、Pulse によるフィルタリングとグループ化をスキップします。その場合、CloudThinker は各イベントを個別に判断します。ツールがすでにアラートの重複排除を行っている場合を除き、オフのままにしてください。

## 経路全体をテストする

<Steps>
  <Step title="実際のアラートを 1 件発生させる">
    ツールから代表的なアラートを発生させるか、**Integration Examples** の **cURL** タブからリクエストを送ります。**Bearer Token** の場合、テストは次のようになります。

    ```bash
    curl -X POST "https://YOUR_WEBHOOK_URL" \
      -H "Content-Type: application/json" \
      -H "Authorization: Bearer YOUR_SECRET_KEY" \
      -d '{"title": "Test: high CPU on web-01", "alert_type": "error", "service": "web-api"}'
    ```

    配信が成功すると、`"success": true` と `request_id` を含むボディとともに `200` が返ります。Datadog の行をまだ追加していない場合、`error` は medium にマッピングされます。
  </Step>
  <Step title="Pulse を確認する">
    **Resolve → Signals** を開き、マッピングしたタイトルのシグナルを探します。
  </Step>
  <Step title="インシデントを確認する">
    **Resolve → Signals** では、トリアージに進んだクラスターは、インシデントにリンクされると **Handled** レーンに移ります。次に **Resolve → Issues** を開きます。**Auto-investigate** と **AI auto-investigate** の両方がオンの場合、インシデントに **AI is handling** と表示されます。クラスターが **Handled** に到達しない場合は、分類で対応不要と判断された可能性があります。[クラスターのトラブルシューティング](/ja/guide/pulse/clusters#トラブルシューティング) を参照してください。
  </Step>
</Steps>

**成功時の状態:** シグナルが正しいタイトル、重大度、サービスで Pulse に表示され、対象となるインシデントに **AI is handling** と表示されます。`200` だけでは配信が成功したことしか証明されません。

利用する重大度の行ごとに、アラートを 1 件ずつテストしてください。上記の Datadog の例では、`error` (high にマッピング) と `warning` (medium にマッピング) を 1 件ずつ送ります。

## 制限とレスポンス

| レスポンス | 条件 |
|---|---|
| `"success": true` を含む `200` | 配信が受け付けられました。 |
| `400` | Webhook が一時停止または無効になっています。**Signals to Resolve** の下の行に **Paused** と表示されます。Resolve の画面から再開することはできません。ソース名とワークスペースを添えて [support@cloudthinker.io](mailto:support@cloudthinker.io) にメールし、再有効化を依頼してください。 |
| `401` | 認証ヘッダーがないか、URL が現在の **Webhook URL** ではありません (入力ミス、または **Regenerate credentials** で置き換えられた)。 |
| `403` | シークレットまたは署名が誤っています。 |
| `413` | ボディが 1 MB を超えています。 |
| `422` | ボディが JSON オブジェクトではありません。配列やプレーンテキストではなく `{...}` を送ってください。 |
| `429` | リクエストが多すぎるか、認証の失敗が多すぎます。15 分以内に 10 回失敗すると、その 15 分間が終わるまで Webhook はリクエストを拒否します。`Retry-After` ヘッダーがある場合は、その時間が経過してから再試行してください。 |

<Warning>
各 Webhook は既定で 1 時間あたり最大 1,000 件の配信を受け付けます。制限はレスポンスのあとにチェックされるため、それを超えた配信にも `"success": true` を含む `200` が返りますが、何も通知されずに破棄されます。シグナルにはならず、[Pulse analytics](/ja/guide/pulse/analytics) の **Signals ingested** にも数えられません。Resolve は破棄された件数を表示しないため、唯一の兆候は、急増時に **Resolve → Signals** からアラートが欠けていることです。

回避するには:

- 制限を引き上げます。Webhook の行の **Manage** メニュー (**⋯**) → **Edit** を開き、**Rate limit (requests per hour)** を変更します。最大 10,000 まで設定でき、`0` は無制限を意味します。
- 大量のアラートを送るモニターを複数の Webhook に分けます。
- 送信前にツール側でアラートの重複排除やグループ化を行います。
</Warning>

Pulse は、配信のソース、リソース、タイトル、重大度、イベント時刻 (分単位。取得元は **Timestamp Path** を参照) が過去 1 時間のシグナルと一致する場合、その配信を重複として扱います。重複は新しいシグナルを作らず、そのシグナルのカウントを増やします。クラスターは、12 時間新しいシグナルがないか、人が解決したときにクローズします。[クラスターのライフサイクル](/ja/guide/pulse/clusters#クラスターのライフサイクル) を参照してください。

## トラブルシューティング

<AccordionGroup>
  <Accordion title="ツールが 401 または 403 を報告する">
    **原因:** 認証ヘッダーが **Auth Method** と一致していないか、(`401` の場合) ツールがまだ古い **Webhook URL** に送っています。**確認:** URL と、ツール側のヘッダー名とシークレットを **Authentication Setup** と照合します。**対処:** シークレットを貼り付け直すか、**Resolve → Triggers & Outcomes** の Webhook の行の **Manage** メニューで **Regenerate credentials** を使います。
  </Accordion>
  <Accordion title="配信は成功したが Pulse に何も表示されない">
    **原因:** Pulse がアラートをノイズとして抑制したか、以前のシグナルの重複として数えたか、時間枠のせいで表示されていません。**確認:** **Resolve → Signals** で時間枠を広げ、上部のファネルにカーソルを合わせて抑制されたイベントの数を確認します。同じアラートを 1 分以内に 2 回送った場合は、以前のシグナルを探してください。代わりにそのカウントが増えています ([制限とレスポンス](#制限とレスポンス) を参照)。**対処:** 各チェックについては [ノイズ抑制](/ja/guide/pulse/clusters#ノイズ抑制) を参照してください。
  </Accordion>
  <Accordion title="シグナルのタイトルが空、または重大度が誤っている">
    **原因:** パスがペイロードと一致していないか、ツールの重大度の値にマッピングの行がありません。**対処:** パスを実際のペイロードと比較し、足りない値を **Severity Mapping** に追加します。
  </Accordion>
  <Accordion title="アラートは Pulse に届いたが RCA が開始されなかった">
    **原因:** **Auto-investigate** がオフ、重大度が下限未満、または **AI auto-investigate** がオフです。**対処:** 3 つすべてを [調査を開始するもの](/guide/incident/settings#what-starts-an-investigation) と照らし合わせて確認するか、クラスターで **Open incident** と **Send to triage** をクリックします。インシデントがすでにオープンしている場合は、そのインシデントで **Investigate** をクリックします。
  </Accordion>
</AccordionGroup>
