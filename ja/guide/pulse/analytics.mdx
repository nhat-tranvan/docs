Pulse アナリティクスは、アラートのパイプラインが有用な仕事をしているかどうかを示します。1 つのタブで、届いた生のイベントの数、Pulse がノイズとして抑えた数、インシデントに到達したか解決された数、そしてどのソースが最も多くの量を送っているかを確認できます。

このページで使う用語は次のとおりです。

- **Raw event (生のイベント)**: Pulse が受信した 1 件の通知。1 件の Datadog アラートや CloudWatch アラームなどです。
- **Signal**: ノイズ抑制を通過したイベント。
- **Suppressed event (抑制されたイベント)**: Pulse がノイズと判断したものの、数えられるように保持しているイベント (Rate limit、Snooze、Verdict)。破棄された重複は保持されません。
- **Stored events (保存されたイベント)**: シグナルと抑制されたイベントの合計。
- **Cluster**: Pulse が 1 つの問題として扱う、関連するシグナルのグループ。
- **Reached an outcome (結果に到達した)**: Cluster がインシデントにリンクされたか解決された Signal。**Correlation yield** と **Clusters routed** 列はどちらもこれを数えます (自動クローズを含みます。[自動解決された Cluster](#自動解決された-cluster) を参照)。

ライフサイクル全体については [Clusters](/ja/guide/pulse/clusters) を参照してください。

## Signal quality を開く

<Steps>
  <Step title="Insights に移動する">
    サイドバーの **Live Operations** の下で **Resolve → Insights** を開きます。ワークスペースの Admin、Developer、Viewer のどのロールでも開けます。
  </Step>
  <Step title="Signal quality タブを選ぶ">
    **Signal quality** タブをクリックします。他のタブ (**Reliability** と **Accuracy and trust**) は [Resolve insights](/guide/incident/insights) で説明しています。
  </Step>
  <Step title="時間枠を設定する">
    右上の時間枠の選択欄を使います。選択肢は **Last 1 hour** から **Last 30 days** までです。既定値は **Last 7 days** です。カードごとに異なる時刻で絞り込みます (下の **時間枠の基準** 列を参照)。8 日前に形成されて昨日解決した Cluster は、**Last 7 days** の **Cluster MTTR** には含まれませんが、過去 7 日間のその Signal は **Correlation yield** に引き続き数えられます。

    **成功時の状態:** 4 つの指標カードが表示され、その下に **Top noisy sources** の表が表示されます。時間枠内にイベントが届いていない場合、表には「No signals ingested in this period」と表示されます。
  </Step>
</Steps>

数値はタブの読み込み時に計算されます。更新するには再読み込みしてください。エクスポートはありません。

## 各指標の意味

| カード | 測定するもの | 計算方法 | 時間枠の基準 |
|---|---|---|---|
| **Correlation yield** | アラート量のうち、どれだけが結果に到達したか | 結果に到達した Signal を、保存されたすべてのイベントで割った値。クラスターではなくイベントを数え、(上位 10 件だけでなく) すべてのソースを対象とします。 | Signal の時刻 |
| **Cluster MTTR** | 問題がどれだけ長くオープンのままか | Cluster の最初の Signal から、解決済みとマークされた時点までの時間の中央値 (自動クローズを含みます。[自動解決された Cluster](#自動解決された-cluster) を参照)。 | Cluster が最初に形成された時刻 |
| **Signals ingested** | 生の量 | Pulse が受信したすべての配信。保存せずに破棄した重複も含みます。Webhook のレート制限を超えた配信は数えられません (下の警告を参照)。 | 配信が届いた時間帯 |
| **Noise suppressed** | Pulse がどれだけ取り除いたか | 抑制されたイベントを、保存されたイベントで割った値。破棄された重複は保存されないため、**Signals ingested** には数えられますが、ここには数えられません。サブタイトルには、シグナルがクラスターにまとまる様子が `1,240 signals → 38 clusters` のように表示されます。 | Signal の時刻 |

破棄された重複があるため、**Signals ingested** は通常、他のカードの基になっている保存イベント数より大きくなります。

**Cluster MTTR** は Cluster の中央値です。**Reliability** タブの **MTTR** はインシデントの平均値です。両者は異なる値になります。

<Warning>
Webhook のレート制限 (既定で 1 時間あたり 1,000 件) を超えた配信は、何も通知されずに破棄されます。それでも `200` が返り、このタブのどこにも表示されません。Resolve は破棄された件数を表示しません。急増時のアラートが欠けている場合は、その時間帯にツールが送った数と **Signals ingested** を比較し、Webhook の制限を引き上げるかモニターを分けてください。[制限とレスポンス](/ja/guide/incident/webhook-integrations/overview#制限とレスポンス) を参照してください。
</Warning>

### 自動解決された Cluster

12 時間新しい Signal がない Cluster は自動でクローズし、解決済みとして数えられます。これは 3 つの数値に影響します。

- **Correlation yield** と **Clusters routed** は、誰も見ていなくても、それを結果に到達したものとして数えます。yield が高いということは、アラートが終了した Cluster にまとまったことを意味し、すべてのアラートが重要だったことを意味するわけではありません。**Resolve → Signals** の **Handled** レーンと合わせて読んでください。このレーンには、インシデント、人、またはエージェントが保持しているオープンな Cluster が表示されます。
- **Cluster MTTR** は、最後の Signal ではなく、自動クローズの時刻までを測定します。

<Warning>
誰も触れていない Cluster は解決までに少なくとも 12 時間かかるため、**Cluster MTTR** に 12 時間以上が加わります。ほとんどの Cluster が自動でクローズする場合、中央値は主にそのタイマーを反映します。MTTR を実際の復旧に合わせるには、問題が終わったときに Cluster のパネルで **Resolve** をクリックしてください。[アクションのリファレンス](/ja/guide/pulse/clusters#操作のリファレンス) を参照してください。
</Warning>

<Note>
**Noise suppressed** は、**Reliability** タブの **Event → incident reduction** とは別の数値です。Reliability は、生のイベントがインシデントにまとまる度合いを測定します。Signal quality は、保存されたイベントに対する抑制されたイベントの割合を測定します。それぞれの数値は、その数値自体の推移とだけ比較してください。
</Note>

## Top noisy sources

この表は、時間枠内で最も多くのイベントを送った 10 のソースを順位付けします。

| 列 | 意味 |
|---|---|
| **Source** | `webhook.datadog` や、アカウントとリージョン付きの CloudTrail ストリームなどの生のソース名。長い名前はカーソルを合わせると全体が表示されます。 |
| **Signals** | 名前に反して、時間枠内のそのソースからの保存されたすべてのイベントです。シグナルだけでなく、Pulse が保持した抑制されたイベントも含みます。破棄された重複は数えられません。 |
| **Suppressed** | そのソースの保存されたイベントのうち、Pulse が抑制したものの割合 |
| **Clusters routed** | 名前に反して、そのソースの保存されたイベントのうち、クラスターがインシデントにリンクされた **か** 解決されたものの割合です (自動クローズを含みます。[自動解決された Cluster](#自動解決された-cluster) を参照)。誰かが保持しているオープンな Cluster については、**Resolve → Signals** の **Handled** レーンを使ってください。 |

1 つの連携が複数の行として表示されることがあります。たとえば 1 つの AWS 接続から、アカウントとリージョンごとに別々のストリームが生まれることがあります。

## 結果を読む

数値を使って、調整に時間をかける場所を決めます。健全な割合の基準値はありません。ソースによって異なるためです。それぞれの数値を、週ごとの自身の推移と比較してください。

| 見えているもの | 通常の意味 | 対応 |
|---|---|---|
| **Signals** が多く、**Clusters routed** がほぼ 0% のソース | 大量に送っているのに、インシデントや解決にほとんど到達していない | **Resolve → Signals** を開き、ソースフィルターでそのソースを選びます (選ぶまでは **All sources** と表示されます)。ソース側でアラートを厳しくします。アラートを直す間ミュートするには、クラスターの行で **Snooze** をクリックします。[ノイズ抑制](/ja/guide/pulse/clusters#ノイズ抑制) を参照してください |
| 全体の **Correlation yield** が低い | ほとんどのイベントがインシデントや解決に到達していない | まず上位のソースがノイズかどうかを確認します。ノイズでない場合は、同じ障害の繰り返しがまとまるよう各 Webhook が **Resource ID Path** をマッピングしているか、1 つのサービスに関する異なるアラートがまとまるよう **Service Path** を 1 つのサービス名にマッピングしているかを確認します。[シグナルがクラスターにまとまる仕組み](/ja/guide/pulse/clusters#シグナルがクラスターに合流する仕組み) を参照してください。 |
| **Cluster MTTR** が週ごとに上昇している | 問題がオープンのままの時間が長くなっている | [On-call](/guide/incident/oncall) で担当とルーティングを確認し、誰も引き受けていない Cluster を探します |
| 1 つのソースで **Noise suppressed** が急増した | 新しいイベントのパターン、または一致範囲が広がりすぎた Snooze (表の下のチェックを参照) | **Resolve → Signals** の **History** レーンを開き、ソースフィルターでそのソースを選び、いくつかの Signal を開きます。Signal の詳細パネルに、Pulse が抑制したかどうかとその理由が表示されます。Snooze が原因の場合は、一致する Signal で **Unsnooze** をクリックします。[ノイズ抑制](/ja/guide/pulse/clusters#ノイズ抑制) を参照してください |

Pulse は 4 つのチェックでイベントを抑制します。

- 繰り返しの配信の重複排除
- ソースごとのレート制限
- 誰かが設定した **Snooze**
- 学習したノイズのパターン

それぞれの詳細は [ノイズ抑制](/ja/guide/pulse/clusters#ノイズ抑制) にあります。

たとえば、`webhook.datadog`、**Signals** 4,800、**Suppressed** 92%、**Clusters routed** 1% という行は、Datadog が大量の繰り返しを送っていて、そのほとんどがどこにもつながっていないことを示します。**Resolve → Signals** でいくつかの Signal を開いて元になっているモニターを見つけ、Datadog でそのしきい値を上げるかオフにしてください。

これらは判定ではなく手がかりとして扱ってください。ソースや Snooze を変更する前に、実際のクラスターとシグナルを確認してください。

## トラブルシューティング

| 問題 | 対処 |
|---|---|
| すべてのカードがゼロまたは空 | 時間枠内にイベントが届いていません。時間枠を広げるか、[Pulse ソースの接続](/ja/guide/pulse/setup) でソースが送信していることを確認してください。 |
| **Cluster MTTR** が空 | 時間枠内に解決された Cluster がありません。Cluster が解決されると表示されます。 |
| 「Failed to Load Signals Analysis」 | **Retry** をクリックします。失敗が続く場合は、ページを再読み込みしてください。それでも失敗する場合は、ワークスペース名、選んだ時間枠、エラーの発生時刻、エラーの文面を添えて [support@cloudthinker.io](mailto:support@cloudthinker.io) にメールしてください。 |
| **Insights** の代わりにセットアップ画面が表示される | ワークスペースにまだインシデントがなく、誰も Resolve のセットアップを完了していません。**Connect monitoring** をクリックするか ([Pulse ソースの接続](/ja/guide/pulse/setup) を参照)、Admin が **Skip for now** をクリックします。 |
