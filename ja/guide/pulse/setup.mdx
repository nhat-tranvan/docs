Pulse が見るのは、あなたが送ったものだけです。このページでは、1 つのアラートのソースから Pulse にアラートが流れるようにし、頼る前にそれが機能することを確認する方法を説明します。

## 前提条件

- ワークスペースの **Admin** ロール。Developer と Viewer は **Resolve → Triggers & Outcomes** を閲覧できますが、シグナルを追加できません。[Roles](/guide/security/roles) を参照してください。
- Webhook を追加したりテストのアラートを発火したりできるよう、アラートを生成するツール（CloudWatch、Datadog、Grafana など）へのアクセス。Webhook の場合、ツールが HTTPS で Webhook URL に到達できる必要があります。
- AWS のポーリングの場合: ワークスペースの [AWS 接続](/ja/guide/connections/aws)。その AWS アカウントの少なくとも 1 つのリージョンで、AWS GuardDuty、AWS Config、AWS IAM Access Analyzer がすでに有効になっている必要があります。CloudThinker はそれらを読みますが、有効にはしません。
- チャットの場合: CloudThinker に接続された Slack または Microsoft Teams（[Slack](/ja/guide/slack-integration)、[Teams](/ja/guide/teams-integration)）。

## シグナルの経路を選ぶ

アラートは 3 つの方法で Signals に届きます。Webhook とポーリングは **Resolve → Triggers & Outcomes** で、チャットのチャネルは **Resolve → On-call** でセットアップします。ツールが対応しているものを選んでください。

| シグナルの経路 | 表示名 | 最適な用途 |
|---|---|---|
| Webhook | **Webhook** | アラートを POST できるモニタリングツール（EventBridge 経由の CloudWatch、Datadog、Grafana、PagerDuty など）、または **Custom source** を通じた任意の社内システム。 |
| ポーリング | **Polling source** | CloudThinker があなたのために読む AWS のサービス: CloudTrail、AWS Health、AWS GuardDuty、AWS IAM Access Analyzer、AWS Config。 |
| チャット | **Resolve → On-call** の **Watch a channel** | ツールがアラートを投稿したり、人がすでにインシデントについて話したりしている Slack や Teams のチャネル。 |

[Connect alert sources](/guide/incident/connect-alert-sources) は、ツールをこれらの経路のいずれかに対応付け、それをセットアップするページを示します。

## ソースを接続する

<Steps>
  <Step title="プラットフォームを開く">
    **Resolve → Triggers & Outcomes** に移動し、プラットフォームを選びます。一覧が長い場合は検索フィールドを使います。独自のカードがないシステムの場合は、**Custom source** を選びます。
  </Step>
  <Step title="接続を確認する">
    プラットフォームが必要とする場合は、**Connection** のセクションでアカウントやワークスペースを接続します。**Needs connection** と表示されたプラットフォームは、これが完了するまでシグナルを追加できません。
  </Step>
  <Step title="シグナルを追加する">
    **Signals to Resolve** で **Add signal**（または **Add another signal**）をクリックし、ソースに応じた手順に従います。

    <Tabs>
      <Tab title="Webhook">
        1. **Custom source** の場合は、まず **Source name** を入力し、**Create endpoint** をクリックします。**Webhook URL** と **Secret Key** をコピーします。**Secret Key** は一度しか表示されません。紛失した場合は、行の **⋯** メニューを開き、**Regenerate credentials** をクリックします。これにより **Webhook URL** と **Secret Key** の両方が置き換わり、古い組はすぐに機能しなくなるため、ツールで両方を更新してください。
        2. 両方をモニタリングツールに貼り付けます。シークレットは、ツールが対応する方法で各呼び出しを認証します。ダイアログでは **Auth Method** に応じたラベルが付きます: **Bearer Token** では **Secret Key**、**HMAC Signature** では **HMAC Secret**、**API Key** では **API Secret**。

           | 方法 | 使うもの |
           |---|---|
           | Bearer トークンのヘッダー | **Custom source** と、`Authorization: Bearer` ヘッダーを送るツール |
           | HMAC 署名 | PagerDuty のように Webhook に署名するツール |
           | API キーのヘッダー | EventBridge 経由の CloudWatch |

           各方法は [Choose authentication](/ja/guide/incident/webhook-integrations/overview#認証を選ぶ) で説明しています。CloudWatch の場合は、EventBridge を使う [CloudWatch の手順](/ja/guide/incident/webhook-integrations/cloudwatch)に従ってください。
        3. ツールからアラートを 1 つ送ります。
        4. ベンダーのプラットフォームでは、フィールドの対応付けと重大度の対応付けはプリセットされていますが、実際のペイロードと照合してください。プリセットの中には、ツールが送る値を取りこぼすものがあります。[Map the fields](/ja/guide/incident/webhook-integrations/overview#フィールドをマッピングする) の Datadog に関する注記を参照してください。**Custom source** では、**Incident title**（必須）、**Severity**、**Service**、**Resource**、**Description** を持つペイロードのフィールドをクリックします。パスは `event.data.title` のようにドットで区切ります。先頭の `$.` は任意で、取り除かれます。

        完全な手順: [CloudWatch](/ja/guide/incident/webhook-integrations/cloudwatch) と [custom source](/guide/incident/webhook-integrations/custom-source)。
      </Tab>
      <Tab title="AWS のポーリング">
        各 AWS のサービスは、スイッチ付きの行として表示されます。Pulse に読ませたいサービスをオンにします。複数の AWS 接続がある場合、各行には読み取る接続の名前が表示されます。

        | サービス | ポーリングの間隔（目安） |
        |---|---|
        | CloudTrail、AWS Health、AWS GuardDuty | 5 分 |
        | AWS IAM Access Analyzer、AWS Config | 30 分 |

        AWS 接続には、オンにした各サービスへの読み取りアクセスが必要です。その権限は [AWS 接続](/ja/guide/connections/aws)を参照してください。
      </Tab>
      <Tab title="チャットのチャネル">
        チャットのチャネルはここでは追加しません。**Resolve → On-call** に移動し、**Alert path** の **Hears** の行で **Watch a channel** をクリックします。プラットフォームとチャネルを選び、**What gets posted there**（**Alerts from tools**、**Team chat**、**Both**）を選んで、**Start watching** をクリックします。そこに投稿された新しいメッセージはそれぞれシグナルになり、分類によって対応が必要かどうかが判断されます。たとえば、`checkout-api is returning 502s since the 14:05 deploy` は対応が必要である可能性が高く、ランチの予定はそうではありません。

        Slack では、メッセージが Resolve に届くよう、`@CloudThinker` をチャネルに招待します。Teams では、まず CloudThinker をチームに追加します。Resolve は自身のメッセージをスキップします。
      </Tab>
    </Tabs>
  </Step>
  <Step title="テストのアラートを送る">
    ソースのツールで実際のアラートまたはテストのアラートを発生させ、**Resolve → Signals** を開いて、レーンを **History** に設定します。ポーリングする AWS のソースは、次のポーリングの後にだけ表示されます（AWS のポーリングのタブを参照）。テストを再送する場合は、タイトルを変えるか 1 分待ってください。Pulse は、タイムスタンプが以前のものと同じ分にある完全なコピーを破棄します。Webhook の場合、タイムスタンプは **Timestamp Path** が指すフィールド、パスが設定されていない場合は最上位の `timestamp` キー、どちらもない場合は Pulse が受け取った時刻です。そのため、ツールが同じイベントを元のタイムスタンプで再送する場合、待っても効果はありません。タイトルを変えてください。

    **成功時の状態:** アラートがクラスターとして表示され、**Resolve → Triggers & Outcomes** でプラットフォームに **Ready** と表示されます。Slack、Teams、Google Chat では、**Ready** には **Post incident updates** のチャネルも必要です（またはその結果をオフにします）。
  </Step>
</Steps>

<Tip>
アカウントを接続しただけでは、イベントが届くことの証明にはなりません。ソースに頼る前に、必ず **Resolve → Signals** で 1 つのシグナルを確認してください。
</Tip>

## 動作を変える Webhook のオプション

これらを編集するには、プラットフォームの **Signals to Resolve** のセクションから Webhook を開きます。

| 設定 | デフォルト | 動作 |
|---|---|---|
| **Auto-investigate** | オン | この Webhook のクラスターは、自動でトリアージと調査に進みます。オフの場合、アラートは引き続き Signals でクラスターにまとめられますが、人がクラスターで **Open incident** と **Send to triage** をクリックするまで何も開始されません。 |
| **Only from a minimum severity** | オフ | 重大度の低いアラートも引き続きクラスターにまとめられますが、自動でトリアージを開始しません。オンにすると **High and above** から始まります。**Critical only**、**High and above**、**Medium and above**、**Low and above**、**Info and above** から選べます。 |
| **Send directly to CloudThinker** | オフ | Signals のフィルタリングとグループ化をスキップします。各イベントが独自のトリアージの実行を受け、インシデントや対応者が必要かが判断されます。**AI auto-investigate** がオフの間も、各イベントはステータス **Open** のインシデントを作成しますが、誰かが **Investigate** をクリックするまで、トリアージの実行は自動では開始されません。すべての実行で[クレジット](/ja/guide/billing/usage)を使うため、すべてのイベントが重要な、件数の少ないソースにだけ使ってください。 |

これらのオプションは、**Resolve → Issues** のタイトルの行にあるワークスペースの **AI auto-investigate** スイッチと組み合わされます。[What starts an investigation](/guide/incident/settings#what-starts-an-investigation) は、すべての組み合わせを 1 つの表に示しています。どの場合でも、人はクラスターで **Open incident** を、インシデントで **Investigate** をクリックできます。

## 準備状況のバッジを読む

**Resolve → Triggers & Outcomes** の各プラットフォームには、接続からシグナルの行、結果まで、セットアップ全体をまとめた 1 つのバッジが付いています。[Read readiness](/guide/incident/triggers-and-outcomes#read-readiness) には、すべてのバッジ、その意味、対処方法が一覧されています。

シグナルのソースでは、**Ready** はすべての接続とソースの行がセットアップされ有効であることを意味します。イベントが届いたことの証明ではないため、**Resolve → Signals** で 1 つのシグナルを確認してください。

## トラブルシューティング

<AccordionGroup>
  <Accordion title="Signals に No signals yet と表示されたまま">
    **原因:** ソースが一度も送信していないか、誤った URL に送信しました。**確認:** モニタリングツールの配信ログ。**対処:** Webhook URL を再度貼り付け、テストのアラートを発火します。
  </Accordion>
  <Accordion title="アラートは届いたが、クラスターが表示されない">
    **原因:** 抑制によって破棄されました。多くの場合は重複としてです: 同じタイトル、重大度、リソースで、タイムスタンプが以前のアラートと同じ分にあるもの。**確認:** **Resolve → Signals** の上部のファネル。生のイベントの件数が増えたのに **History** レーンにクラスターが表示されない場合、抑制がイベントを破棄しています。**対処:** 別のアラートを送るか、[ノイズ抑制](/ja/guide/pulse/clusters#ノイズ抑制)を参照してください。
  </Accordion>
  <Accordion title="Custom source のクラスターに役立つタイトルがない">
    **原因:** フィールドの対応付けが誤ったパスを指しています。**対処:** Webhook を編集し、新しいペイロードを送って、フィールドを選び直します。
  </Accordion>
  <Accordion title="AWS のポーリングの行にバッジが表示され、オンにできない">
    **原因:** その背後の AWS 接続が正常でないか、権限が不足しています。**対処:** [AWS 接続](/ja/guide/connections/aws)を確認してください。
  </Accordion>
</AccordionGroup>
