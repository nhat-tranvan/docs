Review Insights は、マージされたプルリクエスト（PR）とマージリクエスト（MR）を、チーム単位の数値に変えます。誰が何をリリースしたか、マージ時点でどれだけクリーンだったか、どの種類の検出が繰り返し発生しているかがわかります。週次のチームレビューや 1on1 でコーチングすることを 1 つ選び、各数値の裏にある検出事項をクリックして確認するのに使ってください。

## 前提条件

- Review が少なくとも 1 つのリポジトリに接続され、マージ済みの PR または MR があること。[Review のセットアップ](/ja/guide/code-review/setup)を参照してください。
- Insights を表示するには、いずれかのワークスペースロール（Admin、Developer、Viewer）が必要です。レポートのスケジュールを変更するには、ワークスペースの **Admin** ロールが必要です。[ロール](/guide/security/roles)を参照してください。
- **Review Patterns** タブを使うには、レビューモードを **Advanced** または **Auto** に設定する必要があります。このタブは Advanced Review だけを数えるためです。**Auto** では、Auto が Advanced Review に送った変更だけが数えられます。[レビューモード](/ja/guide/code-review/setup#レビューモードを選ぶ)を参照してください。

<Note>
Viewer を含め、ワークスペースロールを持つ全員が開発者名入りのリーダーボードを見られます。これを非表示にする設定はありません。Review を展開する前に、チームと確認してください。
</Note>

## Insights を開く

<Steps>
  <Step title="Insights に移動する">
    左のナビゲーションで **Review** をクリックし、次に **Insights** をクリックします。ページのヘッダーには **Quality trends, patterns and contributions** と表示されます。
  </Step>
  <Step title="期間を選ぶ">
    右上の **Date range** メニューを開きます。期間は 3 つのグループに分かれています。

    | グループ | 期間 | 傾向グラフの区切り |
    |---|---|---|
    | **Daily** | Last 7 days（デフォルト）、Last 14 days | 日 |
    | **Weekly** | This week、Last 4 weeks、Last 8 weeks、Last 12 weeks | 週 |
    | **Monthly** | Last 3 months、Last 6 months、Last 12 months | 月 |

    週は月曜日の 00:00 UTC に始まります。**This week** には傾向がないため、**Details** タブと **Review Patterns** タブが非表示になります。これらを再表示するには、より長い期間を選んでください。

    フィルターは期間だけです。Insights は常にワークスペース内のすべてのリポジトリを対象とします。1 つのリポジトリについて見るには、**Reports** タブのそのリポジトリの PDF を使います。
  </Step>
  <Step title="タブを選ぶ">
    | タブ | 答える問い |
    |---|---|
    | **Leaderboard**（デフォルト） | 誰がどれだけリリースし、マージ時点でどれだけクリーンだったか |
    | **Details** | 期間中に 1 つの指標が開発者ごとにどう推移したか |
    | **Review Patterns** | 開発者ごとに、どの検出ドメインがレビュー済みの変更に最も多く影響しているか |
    | **Reports** | リポジトリごとの PDF レポートと、それが追跡するアクション |

    **完了の状態:** **Leaderboard** と **Details** の上部にサマリーカードが読み込まれ、選んだタブに期間のデータが表示されます。
  </Step>
</Steps>

タブ、期間、指標はページの URL に含まれるため、ビューをブックマークしたり、チームのチャンネルに貼り付けたりすると、他の人にも同じ内容が表示されます。Insights には CSV や API でのエクスポートはありません。URL か、**Reports** タブのレポート PDF を共有してください。

## サマリーカード

**Leaderboard** と **Details** は、選択した期間の 4 つのカードから始まります。

| カード | 数える内容 |
|---|---|
| **Active authors** | 期間中にマージされた変更がある開発者 |
| **Change requests** | マージされた変更 |
| **Found in &lt;range&gt;**（例：**Found in last 7 days**。期間に名前がない場合は **Found in period**） | 選択した期間に挙がった検出 |
| **Team quality score** | CloudThinker がマージされた各変更に付けるレビュースコア（1〜10）の平均。高いほどクリーンです |

カードの下の帯には最大 3 つのシグナルが表示され、それぞれデータがある場合にのみ表示されます。

| シグナル | 意味 |
|---|---|
| **avg to merge** | 変更を開いてからマージするまでの平均時間 |
| **accurate findings** | 検出に対するすべての高評価と低評価の投票のうち、高評価の割合 |
| **review rating** | レビューに付けられた星評価の平均（5 点満点） |

期間中に投票がない場合、**accurate findings** は 0% ではなく表示されません。この数値が必要な場合は、チームに検出への投票を依頼してください。

## Leaderboard

**Developer Leaderboard** は、マージ時点のスコアに基づいて、貢献と品質で開発者を順位付けします。スコアは変更がマージされた時点で固定されるため、あとで検出を編集しても過去の順位は動きません。

| 列 | 意味 |
|---|---|
| **Rank** | 選択した期間での順位 |
| **Move** | 前の期間と比べて上がった、または下がった順位の数。ホバーすると、どの期間と比較しているかが表示されます |
| **Developer** | 変更の作成者 |
| **Contribution score** | チームと比べた Quality と Impact の平均。**1.00** がチームの平均です |
| **Change requests** | マージされた PR または MR |
| **Quality score** | 開発者の変更のマージ時点でのレビュースコアの平均（1〜10） |
| **Impact** | 変更されたファイルと行から算出した、リリースした変更の合計サイズ |
| **Findings** | 検出の合計。ホバーすると Critical、High、Medium、Low の内訳が表示されます |

ボットの作成者は、Insights のすべての数値から除外されます。Review はユーザー名でボットを見分けます。GitHub の `[bot]` サフィックス、末尾の `-bot`、`_bot`、`.bot`、または GitLab のプロジェクトやグループのアクセストークンユーザーです。それ以外の名前のサービスアカウントは数えられ、ワークスペースからアカウントを除外することはできません。

### スコアの算出方法

- **Impact** は、変更がどれだけの範囲に及ぶかを表します。変更するファイルと、追加・削除する行です。
- **Contribution score** は、開発者の Quality score と Impact の合計をチームの平均と比較します。1 前後はチームと同程度、1 を超えるとチームを上回ることを意味します。

リーダーボードは、誰を支援し何をコーチングするかを見つけるために使い、パフォーマンス評価には使わないでください。Impact が測るのは大きさであり、価値ではありません。

## Details

**Details** は、期間中の 1 つの指標を開発者ごとにグラフ化し、各週または各月を表にまとめます。

1. **Metric** メニューから指標を選びます：**Contribution score**、**Quality score**、**Change requests**、**Total impact**。
2. **Quality score by Developer** などのタイトルのグラフを読みます。
3. 表までスクロールして、日、週、月ごとのチームの合計を確認します：**Change requests**、**Team quality**、**Total impact**、**Findings**、**Authors**。

落ち込みが一時的なものか傾向なのかを確認するのに使います。

## Review Patterns

**Review Patterns** はコーチング用のビューです。開発者ごとに、レビューされた変更が 4 つの各ドメインで検出なしにマージされた頻度を表示します。

| ドメイン | 対象 |
|---|---|
| **Security** | セキュリティの脆弱性と安全でない動作 |
| **Performance** | 遅い処理経路、余分な処理、スケーリングのリスク |
| **Correctness** | ロジックの誤りと見落とされたエッジケース |
| **Patterns** | コードベースの規約と保守しやすい構造 |

### 数えられるもの

結果が記録された変更に対する、完了済みで下書きでない Advanced Review だけが数えられます。Fast Review、未完了のレビュー、パイプラインの検出、ボットの作成者は除外されます。対象がない場合、タブには **No confirmed Advanced Reviews in this period** と表示されます。

ドメインの割合は次のとおりです。

```text
changes with no finding in that domain / reviewed changes
```

1 つの変更は、複数回レビューされても期間中に 1 回だけ数えられます。1 つのドメインに複数の検出があっても、その変更は 1 回だけ数えられます。解決済みと未解決の検出は同じように数え、重大度で割合に重み付けすることはありません。

### 主なコーチング優先度

タブの上部には、チーム全体で影響を受けた変更の割合が最も高いドメインが示されます。完全に同点の場合は、Critical と High の検出件数で決まります。それも同点の場合は、同点のドメインがすべて表示されます。

### 証拠を確認する

<Steps>
  <Step title="セルを選ぶ">
    ドメインの列で、開発者のセルをクリックします。
  </Step>
  <Step title="傾向を読む">
    傾向グラフに、その開発者と、全体をまとめた **Team** の線が表示されます。
  </Step>
  <Step title="検出を開く">
    証拠の一覧には、各検出が新しい順に、重大度、タイトル、ファイルの場所、変更へのリンク、**Open** または **Resolved** とともに表示されます。古いものを見るには **Load more evidence** をクリックし、リンクから変更を開きます。

    **完了の状態:** 開発者と話す前に、割合の裏にある具体的な検出を挙げられるようになります。
  </Step>
</Steps>

解決済みの検出も証拠に残ります。レビューが何を見つけたかを示し続けるためです。

### データが少ない場合

| 表示 | 理由 |
|---|---|
| **Not enough data** | 期間中にレビューされた変更が 3 件未満の開発者です。その変更も **Team** の割合には数えられます |
| **No data** | その区間にレビューされた変更がありません。グラフには空白が表示されます |
| **No findings in this period** | 選択したすべてのレビューが、そのドメインでクリーンでした |

## Reports

**Reports** は、各リポジトリについて毎週 2 つの PDF を提供します。エンジニアと技術リード向けの **Technical PDF** と、プロダクトとエンジニアリングのリーダー向けの **Product PDF** です。行は期間ごとにまとめられ、リポジトリごとに 1 行で **Repository**、**Trends**、**Actions**、**Status**、**Generated** が表示されます。このタブでは期間の操作は非表示になります。

<Steps>
  <Step title="レポートの実行方法を選ぶ">
    **Scheduled reports** をオンにすると、毎週月曜日の 09:00 UTC からレポートが生成されます（各ワークスペースはその 30 分以内に開始します）。今日実行するには **Generate now** をクリックします。スケジュールの変更には、ワークスペースの Admin ロールが必要です。
  </Step>
  <Step title="レポートを読む">
    行を開くと **Repository report** パネルが表示されます。「Findings down」などの **Trends** と、**Tracked actions**（今回と以前のレポートのアクションで、それぞれ open、improved、resolved、regressed、stale のいずれかが付きます）が表示されます。行にはリポジトリの健全性も表示されます：**Healthy**、**Watch**、**At risk** と 10 点満点のスコア、または **Not rated yet** です。
  </Step>
  <Step title="PDF をダウンロードする">
    パネルから **Technical PDF** または **Product PDF** をダウンロードします。失敗した行には **Retry** が表示されます。
  </Step>
</Steps>

最初の実行までは、タブに **No reports yet** と表示されます。スケジュール実行のあと、ワークスペースの Admin に **Reports ready** 通知が届きます。スケジュールをオフにしても、既存のレポートは残ります。Review は、その週のレビュー活動をまとめた **Weekly Review digest** メールも別途送信します。どちらも[通知設定](/ja/guide/notifications)の Review で管理します。

## トラブルシューティング

<AccordionGroup>
  <Accordion title="Details タブと Review Patterns タブが表示されない">
    **This week** が選択されていて、傾向がありません。**Date range** で別の期間を選んでください。
  </Accordion>
  <Accordion title="Review Patterns に No confirmed Advanced Reviews in this period と表示される">
    変更が **Fast** モードでレビューされたか、期間中に完了したレビューがありません。**Review → Settings** に移動し、**General** セクションで **Review mode** を **Advanced** または **Auto** に設定します。その後、新しい変更がマージされてから確認してください。以前の Fast Review はここには表示されません。
  </Accordion>
  <Accordion title="開発者に Not enough data と表示される">
    期間中にレビューされた変更が 3 件未満です。期間を広げるか、代わりに **Team** の割合を見てください。
  </Accordion>
  <Accordion title="リーダーボードが空、または誰かが表示されない">
    Insights はマージされた変更だけを数えます。オープン中の PR、マージされずにクローズされた PR、ボットの作成者は表示されません。PR が選択した期間内にマージされたことを確認してください。
  </Accordion>
  <Accordion title="Review Patterns unavailable">
    あなたのアカウントには、このワークスペースで Review を表示する権限がありません。ワークスペースの Admin に、ロールとメンバーシップの確認を依頼してください。[ロール](/guide/security/roles)を参照してください。
  </Accordion>
  <Accordion title="パネルに Could not load と表示される">
    そのパネルで **Retry** をクリックしてください。期間とタブの選択はそのまま残ります。
  </Accordion>
</AccordionGroup>
