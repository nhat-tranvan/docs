このチュートリアルを終えるまでに、CloudThinker は Kubernetes クラスターの 1 つの実際の症状を、クラウドアカウントと最近のコード変更までたどり、証拠とともに根本原因を特定し、あなたの承認を待つ修正を提案します。所要時間は **約 15 分** です。

<Info>
**必要なもの:** **Connected** と表示される 3 つの接続を持つワークスペース（[クイックスタート](/ja/quickstart)で作成されます）。[Kubernetes](/ja/guide/connections/kubernetes)、[AWS](/ja/guide/connections/aws)、[Google Cloud](/ja/guide/connections/gcp)、[Azure](/ja/guide/connections/azure) などのクラウドアカウント、[GitHub](/guide/connections/github) や [GitLab](/guide/connections/gitlab) などのコードホストです。すべてのステップで読み取り専用のアクセスで十分です。

**Kubernetes だけを接続している場合は?** クラウドとコードのステップをスキップし、根本原因のステップでクラスターのみのプロンプトを使ってください。本番を接続する準備ができていない場合は、読み取り専用の kubeconfig でステージングのクラスターを接続し（[Kubernetes の手順](/ja/guide/connections/kubernetes)）、最初のプロンプトから *in the production namespace* を外して、表示された Pod のいずれかを追ってください。
</Info>

以下のプロンプトはすべて平易な言葉です。プロンプトの構文の全体は、[CloudThinker Language](/guide/commands) を参照してください。各メッセージは[クレジット](/ja/guide/billing/usage)を使い、根本原因のステップは複数のサブエージェントを実行するため、より多くのクレジットを使います。

## 調査を進める

以下のプロンプトは、`production` 名前空間の `checkout` というサービスを使います。最近再起動した、遅くなった、またはエラーを出したあなたのサービスに置き換えてください。実際の症状からは実際の答えが得られます。

<Steps>
  <Step title="接続を確認する">
    **Settings → Workspace → Connections** に移動し、Kubernetes、クラウド、コードの接続が一覧にあることを確認します。

    **成功時の状態:** それぞれに **Connected** と表示されます。**Connection error** と表示されるものがあれば、続ける前にその接続のページから修正してください。そうしないと、CloudThinker はその層をスキップします。
  </Step>

  <Step title="このチャットを Manual に切り替える">
    サイドバーの **New chat** をクリックします（または Home のチャットボックスを使います）。何かを送信する前に、プロンプトボックスの下の行、送信ボタンのすぐ左にある承認の制御をクリックします。**Approval for this chat** で **Manual** を選びます。これで、このチャットのすべての書き込みがあなたの **Approve** を待つようになります。

    **成功時の状態:** 承認の制御に **Manual** と表示されます。
  </Step>

  <Step title="症状から始める">
    同じチャットで、次を送信します。

    ```text
    Which pods in the production namespace restarted in the last 24 hours? For each, show the restart count, the last termination reason, and the node it ran on.
    ```

    CloudThinker がクラスターに照会し、Pod の一覧を返します。`OOMKilled` や `CrashLoopBackOff` などの終了理由を探し、それらが共有するノードに注目してください。

    **成功時の状態:** 回答に、一般的な例ではなく、あなたのクラスターの Pod とノードの名前が示されます。
  </Step>

  <Step title="クラウドの層を取り入れる">
    同じ会話の上に積み上げます。Pod の名前を繰り返す必要はありません。

    ```text
    For the nodes those pods ran on, check the cloud instance metrics and events over the same window: CPU, memory, disk, and any maintenance or scaling events.
    ```

    CloudThinker は Kubernetes のノードをクラウドのインスタンスに対応付け、そのメトリクスとイベントを取得します。これは、EKS、GKE、AKS のクラスターのように、ノードが接続したクラウドアカウントで動作している場合に機能します。オンプレミスのノードなど、そうでない場合、CloudThinker はインスタンスに対応付けられません。コードのステップに進んでください。

    **成功時の状態:** 返信で、少なくとも 1 つのノードがクラウドアカウントの特定のインスタンスに結び付けられ、尋ねた期間の数値が示されます。
  </Step>

  <Step title="コードで何が変わったかを確認する">
    ```text
    What changed in acme/checkout in the last 3 days? List merged pull requests and commits that touch resource limits, memory use, or the deployment config.
    ```

    上と同様に、あなたのリポジトリを `owner/name` として置き換えてください。それが確実な方法です。複数のコードの接続がある場合は、`#` を入力して正しいものも選んでください。モノレポでは、*under services/checkout* のようにパスを追加します。

    CloudThinker はコードの接続を通じてリポジトリを読み、変更を作成者、時刻、それぞれの 1 行の要約とともに一覧します。

    **成功時の状態:** 見覚えのあるプルリクエストやコミットが表示され、それぞれに最初の再起動と照らし合わせられるタイムスタンプがあります。
  </Step>

  <Step title="1 つの根本原因を求める">
    次に、3 つの層をまとめるよう CloudThinker に依頼します。

    ```text
    Combine what you found across the cluster, the cloud metrics, and the code changes. Give me the most likely root cause, the evidence for it, and anything that rules out the alternatives.
    ```

    Kubernetes のみの場合は、代わりに次を送信します: *Using the pod events, logs, resource limits, and recent rollouts, give me the most likely root cause, the evidence for it, and anything that rules out the alternatives.*

    このようなリクエストでは、CloudThinker は多くの場合、各層を並行して確認するために[サブエージェント](/ja/guide/agents/overview#サブエージェント)を起動します。チャットに **Spawn Subagents** と表示され、サイドパネルの **Agents** タブでそれぞれを追えます。

    **成功時の状態:** 原因（たとえば、最近のマージで下げられたメモリの上限と、それに続く同じ Pod での `OOMKilled` の再起動）を特定し、各層からの証拠を示し、何を除外したかを述べる 1 つの回答。
  </Step>

  <Step title="提案された修正を確認する">
    ```text
    Propose a fix for this root cause. Show the exact change and what it will affect before you do anything.
    ```

    CloudThinker は、デプロイへのパッチや、上限を元に戻すプルリクエストなどの変更を説明します。Manual では、すべての書き込みがアクションカードであなたを待ちます。Web アプリでは **Approve**、**Approve and draft rule**、**Decline** が表示されます。Google Chat は独自のボタン（**Approve**、**Approve with reason**、**Reject**）を表示します。Slack と Microsoft Teams が **Approve** と **Reject** を表示するのは、Resolve のインシデントのチャネルだけです。それ以外では **View in CloudThinker** のリンクを投稿し、Web アプリで判断します。

    表示される内容は接続によって異なります。

    - **読み取り専用のロールで、Allow writes がオン:** カードが表示されます。承認すると、プロバイダーが書き込みを拒否し、チャットにエラーが表示されます。何も変わりません。
    - **Allow writes がオフ:** カードは表示されません。CloudThinker はプロバイダーを呼び出す前に書き込みを拒否します。

    修正を実行させるには、接続の権限を広げ、その詳細パネルで **Allow writes** をオンにします。[How access works](/ja/guide/connections/overview#アクセスの仕組み) を参照してください。

    <Warning>
    承認すると、実際のシステムに対して変更が実行されます。本番のクラスターでは、今は **Decline** をクリックしてください。通常のレビューで適用できる差分として変更を出すよう CloudThinker に依頼するか、コードの接続に書き込みアクセスがある場合は、プルリクエストを開くよう依頼してください。
    </Warning>

    **成功時の状態:** 正確な変更を確認し、判断しました。承認した場合は会話に結果が表示されます。却下した場合は何も変わっていません。
  </Step>

  <Step title="まとめる">
    ```text
    Summarize this investigation as an incident write-up: timeline, root cause, evidence, fix, and follow-up actions.
    ```

    **成功時の状態:** 事実を編集せずにチケットやポストモーテムに貼り付けられるまとめ。これはこのチャットにあります。チームメイトに送るには、[Sharing](/guide/sharing) を参照してください。[Jira を接続](/ja/guide/connections/atlassian)している場合は、Jira の課題として登録するよう CloudThinker に依頼できます。これは書き込みのため、あなたの承認を待ちます。
  </Step>
</Steps>

## 完了の目安

- [x] CloudThinker が、あなた自身の環境の Pod、ノード、インスタンス、コミットの名前を示した
- [x] 1 つの回答が、証拠とともに 1 つの根本原因を特定した（3 つの層すべてから、または Kubernetes のみの場合はクラスターだけから）
- [x] 提案された変更を確認し、承認か却下かを選んだ
- [x] 調査の文章のまとめがある

## トラブルシューティング

<AccordionGroup>
  <Accordion title="CloudThinker がクラスター、アカウント、リポジトリに到達できないと言う">
    接続がない、エラーになっている、または読み取りアクセスがありません。**Settings → Workspace → Connections** を開いてステータスを確認し、その接続のページのトラブルシューティングのセクションに従ってください。
  </Accordion>
  <Accordion title="回答が一般的で、自分の環境についてではない">
    プロンプトで対象（名前空間、リージョン、リポジトリ）を指定するか、`#` を入力して接続を選んでください。複数のクラスターやアカウントがある場合、CloudThinker が別のものを見ていた可能性があります。
  </Accordion>
  <Accordion title="過去 24 時間に何も再起動していない">
    期間を広げる（"in the last 7 days"）か、応答の遅さや 5xx エラーの急増など、別の症状から始めてください。残りのステップは同じように機能します。
  </Accordion>
  <Accordion title="承認のカードが表示されなかったのに、変更が実行された">
    まず、プロンプトボックスの承認の制御にまだ **Manual** と表示されていることを確認してください。これは 1 つのチャットにだけ適用されるため、新しいチャットは **Chat** の実行タイプのモード（Admin が [Approval mode](/guide/approvals/approval-mode#set-a-mode-for-a-run-type) で **Chat** のオーバーライドを設定していない限り、ワークスペースのモード）で始まります。**Auto** のモードが表示されている場合は、ワークスペースの Approvals が、その操作を確認なしで実行することを許可しました。本番で修正を実行する前に、[Approval mode](/guide/approvals/approval-mode) と [rules](/guide/approvals/rules) を見直してください。
  </Accordion>
</AccordionGroup>
