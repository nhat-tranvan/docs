すべてのスキルは `SKILL.md` ファイルです。スキルの名前と使う場面を示す短い YAML ヘッダー（フロントマター）の後に、Markdown の指示が続きます。このページでは、ファイルが読み込まれるために満たすべきルールと、エージェントが従いやすくなる書き方のパターンを説明します。

## 最小限の有効なスキル

これをコピーし、名前、説明、ルールを変更すれば読み込まれます:

```markdown
---
name: security-review-checklist
description: Enforce our SQL and secrets rules when reviewing code. Use for any pull request review or security question about code.
---

## SQL injection

- Flag SQL built with string concatenation or f-strings.
- Require parameterized queries or ORM methods.

## Secrets

- Flag hardcoded credentials, tokens, and API keys.
- Require secrets to come from a secrets manager or environment variables.
```

| パーツ | 必須 | 目的 |
|---|---|---|
| フロントマター（`---` の行の間） | はい | `name` と `description` を保持します。有効な YAML である必要があります。 |
| 指示本文 | はい | エージェントがスキルを使うときに読む Markdown のルールです。 |
| ルールグループごとに 1 つの `##` 見出し | 推奨 | あなたとエージェントの両方がルールを把握しやすくなります。 |
| 良い例と悪い例 | 推奨 | 各ルールを具体的なものに結び付けます。 |

## フロントマターのフィールド

| フィールド | 必須 | ルール |
|---|---|---|
| `name` | はい | 英字または数字で始まり、その後は英字、数字、`_`、`-` を使います。大文字も使えます。スペースは使えません。最大 255 文字です。名前は大文字と小文字を区別し、`/` コマンドは名前をそのまま使います。`pdf`、`docx`、`deep-research` など、CloudThinker の組み込みスキルと同じ名前は使えません。 |
| `description` | はい | スキルが何をするか、いつ使うかを示す空でない文です。エージェントは説明を読んでタスクに合うスキルを判断するため、説明があいまいだとスキルはほとんど選ばれません。コロンを含む場合は引用符で囲みます: `description: "Use when: reviewing PRs"`。最大 2,000 文字です。 |
| `argument-hint` | いいえ | チャットの `/` メニューからスキルを実行する場合にのみ適用されます。そのメニューでスキルの横に表示されるテキスト（`<service-name>` など）で、コマンドの後に何を入力すればよいかを示します。動作は変わりません。`/skill-name` の後に入力した内容は、メッセージの一部としてエージェントに届きます。 |

他のツール向けに書かれた SKILL.md ファイルにある `license` や `allowed-tools` などの他のフィールドはアップロードを妨げませんが、CloudThinker はそれらを使いません。他のツールから移植したスキルも、`name` と `description` があれば読み込まれます。

名前の例:

| 名前 | 有効? |
|---|---|
| `security-checklist` | はい |
| `security_checklist` | はい |
| `Security-Checklist` | はい |
| `Security Checklist` | いいえ（スペース） |
| `-checklist` | いいえ（英字または数字で始める必要があります） |

<Note>
**Write skill instructions** でスキルを作成すると、CloudThinker が **Skill name** と **Description** のフィールドからフロントマターを作成します。フロントマターを自分で書くのは、`.zip` をアップロードする場合か、`SKILL.md` を手動で編集する場合だけです。
</Note>

## zip パッケージの構成

スキルに補助ファイルが必要な場合や、スキルをワークスペース間で移動する場合は `.zip` を使います。**Settings → Workspace → Skills → +**（**Search skills** の横）**→ Upload zip file** からアップロードします。

```text
security-review-checklist.zip
└── security-review-checklist/
    ├── SKILL.md            required
    ├── references/         optional: longer docs the skill points to
    ├── scripts/            optional: scripts the skill runs
    └── schemas/            optional: schemas the skill validates against
```

- `SKILL.md` は zip のルートか、1 つのトップレベルフォルダーの中に置きます。スキルの名前はフロントマターの `name` から取られるため、フォルダー名を合わせる必要はありません。
- zip ファイルの名前は、大文字と小文字も含めてフロントマターの `name` と完全に一致させます（例: `security-review-checklist.zip`）。CloudThinker は zip のファイル名を使って既存のスキルを見つけ、**Replace** を提示します。両者が異なると、**Replace** によって zip 名に一致するスキルが削除され、別の名前のスキルがアップロードされることがあります。一致するものがない場合、フロントマターの `name` がすでに使われていると、アップロードは **This skill name is already in use.** で失敗します。
- 保持されるのは `scripts/`、`schemas/`、`references/` だけです。その他のファイルとフォルダーは無視されます。
- 補助ファイルは `SKILL.md` から相対パスで参照します。エージェントはそれらを自動では読みません。指示がファイルを指している場合にそのファイルを開きます。例:

  ```markdown
  For the escalation order, read references/escalation-matrix.md.
  ```

- スクリプトの場合は、名前と実行するタイミングを書きます。例: 「Run `scripts/check_tags.sh` with the account ID.」スクリプトは Bash または TypeScript（`bun` で実行）で書けます。エージェントは他のコマンドと同じコマンドツールでスクリプトを実行するため、スクリプトによる書き込みは他のコマンドと同様に [Approvals](/guide/approvals/overview) を通ります。
- スクリプトは、ワークスペースの [Credentials](/guide/credentials) を環境変数として受け取ります。変数名は各クレデンシャルの **Key** です。キーが `DATADOG_API_KEY` のクレデンシャルは、スクリプト内では `$DATADOG_API_KEY` になります。

<Note>
クレデンシャルはスキルのスクリプトに限りません。エージェントが実行するすべてのコマンドは、スキルやプロンプトが使うかどうかに関係なく、ワークスペースのすべてのクレデンシャルを受け取ります。クレデンシャルを 1 つのスキルやエージェントに限定することはできません。スキルに必要なキーだけを保存し、読み取り専用のベンダーキーを優先してください。[エージェントがクレデンシャルを使う方法](/guide/credentials#how-agents-use-credentials)を参照してください。
</Note>

## 上限

| 項目 | 上限 |
|---|---|
| アプリで作成または編集する `SKILL.md` | 50,000 文字 |
| zip でアップロードする `SKILL.md` | 以下の zip の上限以外に制限はありません。50,000 文字を超えるファイルはアプリ内エディターから保存できません。 |
| 説明 | 2,000 文字 |
| スキル名 | 255 文字 |
| zip アップロードサイズ | 5 MB |
| zip 内のファイル数 | 1,024 |
| 展開後の zip サイズ | 50 MB。`references/`、`scripts/`、`schemas/` 内のファイルに対する唯一の上限です |

## アップロード前のチェック

- `SKILL.md` のファイル名が大文字で、zip のルートか 1 階層下にある。
- ファイルの 1 行目が `---` で始まり、フロントマターが `---` で閉じている。
- `name` が英字または数字で始まり、英字、数字、`_`、`-` だけを使っている。
- `name` が `pdf` や `deep-research` などの組み込みスキル名ではない。
- `description` が入力されており、コロンを含む場合は引用符で囲まれている。
- zip ファイル名が `name` と完全に一致している。
- 補助ファイルが `references/`、`scripts/`、`schemas/` にある。

## エージェントが従う指示を書く

**エージェントがまだ知らないことだけを書きます。** エージェントは SQL インジェクションをすでに理解しています。知らないのは、それに関するあなたのルールです。

```markdown
<!-- Too general: the agent already knows this -->
SQL injection is a vulnerability where attackers run arbitrary SQL
through unsanitized input, so always be careful with queries...

<!-- Useful: your specific rules -->
## SQL injection
- Flag `execute()` calls that take f-strings or `.format()`.
- Require the `db.query(sql, params)` helper for every new query.
```

**どれだけ自由度を持たせたいかに合わせてルールのスタイルを選びます:**

| 自由度 | スタイル | 用途 |
|---|---|---|
| 高 | 原則とガイドライン | アーキテクチャのアドバイス、探索的なレビュー |
| 中 | 例付きのチェックリスト | 標準的なレビュー、セキュリティチェック |
| 低 | 厳密なテンプレートと固定フィールド | 出力形式、必須セクション |

**説明するより、見せます。** 1 組の例は 1 段落の説明に勝ります:

```markdown
## Naming
- `remaining_retries`, not `r`
- `is_authenticated`, not `auth`
- Booleans start with `is_`, `has_`, or `should_`.
```

**1 つのスキルには 1 つのトピックにします。** セキュリティのルールとパフォーマンスのルールを分けると、それぞれを別の場所で使えるようにできます。スキルが約 300 行を超える場合は分割するか、長い参照用の表を `references/` に移してそこを指すようにします。これはエージェントを脱線させないための目安で、50,000 文字の厳密な上限よりずっと小さい値です。

## 完全な例

そのまま応用できるプルリクエスト標準のスキル:

````markdown
---
name: pr-review-standards
description: Enforce our pull request standards for size, tests, and docs. Use when reviewing any merge request or pull request.
argument-hint: <pull request link>
---

## Size

- Flag pull requests over 500 changed lines as "needs splitting" and suggest split points.
- Generated files (migrations, lockfiles) don't count toward the limit.

## Tests

- Require tests for every new public function.
- Flag deleted tests that have no matching feature removal.

## Docs

- Flag breaking API changes without a migration note.
- Require a README update when a new environment variable is added.

## Comment format

```text
**[severity]** Short title

What is wrong and why it matters.

**Suggestion:** How to fix it.
```

Severity is one of `critical`, `warning`, `suggestion`, `nitpick`. For example:

```text
**[warning]** New endpoint has no tests

`create_invoice()` is public and has no test, so a regression would reach production unnoticed.

**Suggestion:** Add a test in `tests/test_invoices.py` that covers the happy path and an invalid amount.
```
````

保存したら、**Available in** の下にある **Review** にチェックを入れて、プルリクエストのレビューに適用されるようにします。レビューでは `argument-hint` は使われません。これはチャットの `/` メニューからスキルを実行する人にだけ役立ちます。[カスタムスキル](/ja/guide/skills/custom-skills#スキルを適用する場所を選ぶ)を参照してください。

## トラブルシューティング

<AccordionGroup>
  <Accordion title="This skill file could not be saved">
    - **フロントマター。** フロントマターがない、YAML エラーがある、または `name` か `description` が空です。`SKILL.md` が `---` で始まり、ヘッダーが `---` で閉じていて、両方のフィールドに値があることを確認してください。コロンを含む説明は引用符で囲みます。また、`name` が上記の命名ルールに従っていることも確認してください。
    - **CloudThinker が探す場所に `SKILL.md` がない。** zip のルートか 1 階層下にある必要があり、ファイル名は大文字と小文字を区別します。`skill.md` を `SKILL.md` に名前変更し、もう一度 zip にしてください。
  </Accordion>
  <Accordion title="SKILL.md name must match the selected skill">
    既存のスキルを手動で編集する場合、フロントマターの `name` はまったく同じままにする必要があります。スキルの名前を変更するには、スキルをダウンロードして名前を変更し、新しいスキルとしてアップロードします。その後、古いスキルを削除し、新しいスキルの **Available in** にもう一度チェックを入れます。新しいスキルは **Chat** のみで始まるためです。
  </Accordion>
  <Accordion title="アップロード後にスクリプトやドキュメントがない">
    保持されるのは、`SKILL.md` と同じ場所にある `scripts/`、`schemas/`、`references/` 内のファイルだけです。他のファイルはこれらのフォルダーのいずれかに移動してください。
  </Accordion>
  <Accordion title="スキルは読み込まれるが、エージェントがほとんど使わない">
    `description` を書き直し、ユーザーが実際に入力する言葉でスキルを使う場面を示します（「Use when reviewing a pull request」）。その後、ルールを具体的にし、例を追加します。
  </Accordion>
