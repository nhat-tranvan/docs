**Potential monthly savings** は、1 つのクラウドアカウントにあるすべての未決定の finding（スキャンが見つけた 1 つの節約機会）の月間見積もりを合計したものです。目の前にある作業の規模を測るために使い、請求額が減ることの約束としては使わないでください。

## 数値が表示される場所

Optimize のどのページも、一度に 1 つのアカウントを表示します。切り替えるには、ページタイトルの横にあるアカウントメニュー（現在のアカウント名が表示されています）を開き、別のアカウントを選びます。合計はアカウントの請求通貨で表示されます。AWS と GCP では USD、Azure では請求スコープの通貨です。

| 場所 | 対象 |
|---|---|
| **Optimize**（Overview）の **At a glance** にある **Savings potential** タイル | 選択したアカウントの、未決定で対応可能なすべての finding。タイルをクリックすると、そのアカウントの **Issues** が開きます。 |
| **Optimize → Issues** のサマリーカード | **Potential monthly savings** と同じ合計に加え、別々の **Quick wins** と **Needs review** のカード。それぞれに件数と `/mo potential` の金額があります。 |

アカウントをまたいだ節約額の合計はありません。並べて比較するには、[Reports](/ja/guide/cost-optimization/reports) で **All accounts** スコープの **Savings opportunities** レポートを生成してください。

**Issues** では、サマリーは **Service** フィルターに従うため、1 つのサービスを選ぶとそのサービスの分が表示されます。**Quick wins** と **Needs review** のカード、検索、手間とリスクのフィルター、ページ送りはサマリーを変えないので、閲覧中もヘッダーは安定しています。

**Issues** の各サマリーカードは、現在の合計を、前回のスキャン完了時に記録された合計とも比較します。この行での「actions」は集計対象の finding を意味します:

| 行 | 意味 |
|---|---|
| `+2 actions, +$X/mo vs last scan` | 集計対象の finding が 2 件増え、合計が上がった |
| `-1 action, -$X/mo vs last scan` | 集計対象の finding が 1 件減り、合計が下がった |
| **No change since last scan** | 件数も金額も同じ |
| **No previous scan baseline** | アカウントに完了したスキャンが 1 回しかない |

差分は、合計が動くあらゆる理由で動きます。新しい finding、移動またはマークした finding、編集した見積もり、期限切れになったスヌーズなどです。

チームが変更を反映した後や、finding に異議を唱えた後には、新しいスキャンを実行してください。エージェントはそのときに disputed の finding を再確認します。**Overview** と **Issues** の **More Optimize actions**（⋯）メニューにある **Re-scan** は同じアカウントのスキャンを開始し、その後の比較は、そのスキャンが記録した合計に対して行われます。[finding を更新する](/ja/guide/cost-optimization/recommendations#finding-を更新する)を参照してください。

## 見積もりの計算方法

スキャン中、CloudThinker はアカウントのサービスごとの請求済み支出を読み、その背後にあるリソースを読み取り専用のコマンドで調べます。使用する権限はプロバイダーごとに記載されています: [AWS](/ja/guide/connections/aws#必要な権限)、[GCP](/ja/guide/connections/gcp#必要な権限)、[Azure](/ja/guide/connections/azure#必要な権限)。各見積もりは固定の料金表ではなくそれらの測定値から算出され、各 finding の説明に計算が示されます。

たとえば、それぞれ月 $33 で請求されているアイドル状態の NAT ゲートウェイが 2 つあれば、ゲートウェイ ID と測定したトラフィックを証拠として、月 $66 の見積もりになります。数値は説明のためのものです。

| 項目 | 詳細 |
|---|---|
| 単位 | 月単位。年間や期間の節約額は 12 で割ります |
| 支出の基準 | 実際に請求される額。AWS では net unblended cost なので、割引や既存の RI や Savings Plans の適用はすでに反映されています |
| 請求ソースと通貨 | プロバイダーによって異なります。[Provider differences](/ja/guide/cost-optimization/overview#プロバイダーごとの違い) を参照してください |
| 計算を確認する場所 | finding を開きます。詳細パネルの **Overview** タブに証拠、見積もり、影響を受けるリソースが表示されます。**Open analysis** には、スキャンが実行した読み取り専用のコマンドが表示されます |

finding の数値を財務に伝える前に、その証拠バッジを確認してください。伝えてよいのは **Verified** です。**Inferred** と **Assumed** にはスキャンが読んでいない部分が残っているので、その部分を自分で確認してください。[finding の読み方](/ja/guide/cost-optimization/recommendations#finding-の読み方)を参照してください。

## どの finding が集計されるか

finding が合計に含まれるのは、3 つの条件をすべて満たす場合だけです。

| 条件 | 集計される | 集計されない |
|---|---|---|
| クラス | **Quick win**、**Needs review** | **No action**（スキャンが支出を確認し、変更を提案しないもの） |
| 状態 | **Pending**、**In progress** | **Implemented**、**Ignored** |
| マーク | マークなし、日付を過ぎたスヌーズ、または有効期限を過ぎた expected のマーク | 有効期限なし、または有効期限がまだ先の **Hide as expected**、有効な **Snooze until…**、**Dispute…** |

スキャンがクラスと証拠バッジをどう選ぶかについては、[finding の読み方](/ja/guide/cost-optimization/recommendations#finding-の読み方)を参照してください。

<Note>
disputed の finding は表示されたままでフラグが付きますが、その節約額は合計から外れます。CloudThinker は次のスキャンで最初にそれらを再確認します。異議が正しかった場合、エージェントは finding をアーカイブします。finding は状態の列に移ることなく、ボードと合計から完全に外れます。そうでない場合は証拠が更新され、**Clear mark** を選ぶまで **Disputed** のマークが残ります。
</Note>

## 上限である理由

2 つの finding が同じ支出に対して節約額を見積もることがあります。たとえば、ライトサイジングの finding が月 $200 を節約し、同じコンピューティングに対する Savings Plan の finding が月 $150 を節約するとします。ライトサイジングした後は、プランがカバーする範囲が小さくなるため、両方を行っても節約額は $350 未満になります。Optimize は重複する finding を指摘しません。

実際には:

- Overview の **Monthly forecast** タイルにある月末の予測から合計を差し引かないでください。予測は請求額がどこに向かっているかを示し、節約額の合計は未決定の作業にどれだけの価値がありうるかを示します。
- 合計を実現した節約額や ROI として報告しないでください。Optimize は変更後の節約額を測定しません。
- 2 つの見積もりを足し合わせる前に、両方の finding を開き、同じリソースに関係していないか確認してください。
- 金額だけでなく、クラス、手間、リスクで優先順位を付けてください。

## 合計を正確に保つ

チームが判断するたびに、finding を合計から外していきます。変更のたびに全員の合計が更新されるため、数値の正確さは一覧の正確さで決まります。

| チームが | **Issues** で行うこと | 合計への影響 |
|---|---|---|
| finding の作業を始める | **In progress** に移す | 変わりません。finding は引き続き集計されます |
| 変更を反映する | **Implemented** に移す | finding の見積もり分だけ下がります |
| 変更しないと決める | **Ignored** に移す | finding の見積もり分だけ下がります |
| 支出が意図的だと分かっている、または後で見直したい | **Hide as expected**、または日付を指定して **Snooze until…** | 下がり、有効期限や再開日を過ぎると再び集計されます |
| finding が間違っていると考える | **Dispute…** する | 下がり、finding は次のスキャンで再確認されるまで表示されたままです |
| 実際の数値を知っている | finding を **Edit** して **Potential savings ($/mo)** を変更する | それ以降はあなたの数値に従います |

finding の移動、マーク、編集の方法と、各マークで求められる内容は [Issues](/ja/guide/cost-optimization/recommendations) で説明しています。移動と編集にはワークスペースの Developer ロール以上が必要で、finding を expected、snoozed、disputed としてマークするには Admin が必要です。組織の Owner と Admin は、すべてのワークスペースでワークスペースの Admin を持ちます。

<Tip>
Optimize は実現した節約額の記録を残しません。finding を **Implemented** に移す前に、チケットに見積もりを書き留めるか、**Issues** の **More Optimize actions**（⋯）メニューから **Download PDF** を選んでください。その後、[変更後に節約を証明する](#変更後に節約を証明する)の手順で実際の削減を確認します。
</Tip>

## finding をワークフローに送る

レビューに添付するファイルが必要な場合は、**Issues** または [Cost Health](/ja/guide/cost-optimization/overview#主な概念) の **More Optimize actions**（⋯）メニューから **Download PDF** を選びます。今すぐ、またはスケジュールで書面のレポートを作るには [Reports](/ja/guide/cost-optimization/reports) を使います。定期的なまとめには、2 つの Optimize ダイジェストのいずれかを使います。

| ダイジェスト | 送信日 | 内容 | 送信先 | デフォルトのメール |
|---|---|---|---|---|
| **Optimize weekly digest** | 毎週月曜日 | Cost Health、新しい finding、期限が近いコミットメント、まだ確認されていない異常 | [ワークスペースのオーナー](/guide/security/roles)。組織が所有するワークスペースにはオーナーがいないことがあります | オフ |
| **Optimize monthly digest** | 毎月 2 日 | 前月の支出、新しい finding、まだ確認されていない異常、Cost Health | 組織の Owner と Admin を含む、ワークスペースの Admin | オン |

メール、Slack、Microsoft Teams、Google Chat のオンとオフは、ダイジェストごとに [Notifications](/ja/guide/notifications) で切り替えます。

Optimize には、finding からチケットやプルリクエストを開く組み込みのボタンはなく、finding の CSV エクスポートもありません。

## 変更後に節約を証明する

Optimize が報告するのは節約見込み額だけです。実際の削減を示すには:

1. 変更後、請求月が 1 か月まるごと終わるのを待ちます。途中の月では結果が小さく出ますし、プロバイダーの請求データは遅れることがあります（AWS Cost Explorer では 24 から 48 時間）。
2. **Optimize → [Cost Explorer](/ja/guide/cost-optimization/analytics)** で、変更前の最後の丸 1 か月と、変更後の最初の丸 1 か月を比較します。**Group by** は一度に 1 つのディメンションを使います。まず **Service** で下がったサービスを見つけ、次に **Region** に切り替えてどこで下がったかを確認します。

Optimize の Cost Explorer は、支出をリソースやタグ別には分解しません。1 つのリソースを切り分けるには、プロバイダー自身のツールを使ってください: リソースレベルの AWS Cost Explorer や Cost and Usage Report、GCP の BigQuery 請求エクスポート、または Azure Cost Management です。

## トラブルシューティング

[Optimize troubleshooting](/guide/cost-optimization/troubleshooting#findings-and-the-savings-total) には、節約額の合計に関するすべての症状が、原因、確認、対処とともに載っています。次の 2 つはさらに詳しい説明が必要です。

<AccordionGroup>
  <Accordion title="誰もスキャンを実行していないのに合計が変わった">
    **原因:** 合計はワークスペース全体で共有されているため、誰の判断でも動きます。スヌーズの日付が過ぎたとき、チームメイトがマークを解除したとき、チームメイトが finding を **Implemented** や **Ignored** から **Pending** や **In progress** に戻したとき、チームメイトが編集した見積もりを引き上げたときに上がります。チームメイトが finding を **Implemented** や **Ignored** に移したとき、マークしたとき、見積もりを引き下げたとき、そしてスキャンが異議を認めたときに下がります。

    **確認:** finding を開きます。**Activity** タブに状態の変更と編集が一覧表示され、マーク済みの finding には誰がいつマークしたかが表示されます。**Issues** のツールバーにある **hidden** トグルを選ぶと、マーク済みの finding が表示されます。

    **対処:** 変更が誤りだった場合は、もう一度移動、編集、またはマークの解除を行います。
  </Accordion>
  <Accordion title="合計が $0、高すぎる、または Overview と一致しない">
    **原因:** $0 の場合、[どの finding が集計されるか](#どの-finding-が集計されるか)の 3 つの条件をすべて満たす finding がないため、一覧はおそらくすべて **No action**、マーク済み、またはすでに **Implemented** か **Ignored** です。高すぎるように見える合計には、たいてい同じ支出に対して節約額を見積もる finding が含まれています。**Issues** の合計が **Overview** より低い場合は、**Service** フィルターが設定されています。

    **確認:** **Quick wins** と **Needs review** のカード、**Open** と **Decided** のタブ、一覧の上のフィルターバー。

    **対処:** **Service** フィルターを解除して 2 つの合計を一致させ、大きな finding を足し合わせる前にリソースを比較します。[上限である理由](#上限である理由)を参照してください。
  </Accordion>
</AccordionGroup>
