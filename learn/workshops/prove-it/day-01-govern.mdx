Day 01 of [Prove It](/learn/workshops/prove-it/overview). By the end you'll have connected a read-only agent to your own AWS account, asked it what to optimize, labelled every claim by how well it's backed, and handed in one report per team. The live session ran on Sep 5, 2026. You can repeat the lab on your own on any AWS account you control.

The idea behind the day: a code repo is a folder you can undo. A cloud account is a live system. An agent can pass every test in your repo and still be wrong about your account, so you set the controls and demand the evidence first.

## Rules of the room

- **150 minutes.** Learn 35, Practice 95 with a 10-minute break, Share 20.
- **Your AWS account is connected read-only.** Use a staging or sandbox account if you can. The agent can inspect. It can't change anything.
- **Credentials stay with the owner.** The account owner connects it on their own screen with a read-only IAM role, and turns off **Allow writes**.
- **The agent recommends. People decide.** No fix is applied today, in your account or anywhere else.
- **Redact.** Account IDs, ARNs, endpoints, hostnames and customer data come out of the report before it's shared or shown on screen.
- **One report file per team**, submitted before Share starts.

## Learn: 35 minutes

Five ideas. Each one becomes a rule you use in the lab.

### 1. An agent is a model plus an environment

An agent has a goal, context, a model, tools and an environment. The model picks the next action. The environment is where that action lands. The loop: act, observe the result, act again, check, stop.

| The model chooses | The environment decides |
|---|---|
| Which tool to call next, and with what input | Which tools exist at all |
| How to read the result | What each call may do, and to what |
| When the job is done | Whether the action can be undone |

A better model makes better choices. It can't do anything you didn't give it.

### 2. The cloud has no single workspace boundary

The same agent with the same skill plays by different rules for being wrong.

| | In a repo | In the cloud |
|---|---|---|
| The boundary | One folder on your machine | Many accounts, regions and roles |
| Who else is affected | Only you, until you push | Live users and other teams, right now |
| What the agent can see | Every file | Only what its role may call |
| If it's wrong | Cheap to spot, cheap to undo | Expensive to spot, sometimes impossible to undo |

The visibility row is the one people miss. When an agent says nothing about a resource, that doesn't mean the resource isn't there. Its role may not be allowed to look.

In CloudThinker, the boundary sits outside the agent in two places: the IAM role your [AWS connection](/guide/connections/aws) uses decides which calls can succeed, and your [Approvals](/guide/approvals/overview) settings decide which actions wait for a person. You set both. Today's connection uses a read-only role with **Allow writes** off, so nothing can change.

### 3. Auto-approve needs a stated intent

Some coding agents offer an auto mode: instead of asking you before each action, a second model reviews the action and blocks the dangerous ones. That works while you're there.

- **When you're prompting**, the reviewer has something to check against. You said "don't touch production", so matching actions are blocked.
- **When nobody is prompting**, for example an alert starts the run at 3am, no goal or boundary was stated. The reviewer has only its defaults, and when it pauses to ask a person, nobody answers.

When the human leaves, the intent has to be written down:

| What carries the intent | What it answers |
|---|---|
| Runbook | What to do |
| Boundary | How far |
| Permission | What is possible at all |
| Human approval | Who signs off before the irreversible step |
| Audit log | What happened |

In CloudThinker, this is the job of [Approvals](/guide/approvals/overview): the Rules you write decide first, then the workspace's **Manual** or **Auto** mode decides what still needs a person. **Manual** is the exception: it asks a person even for a write an Allow Rule covers. Rules decide only once CloudThinker turns on [Rule enforcement](/guide/approvals/rules#troubleshooting) for your workspace; until then they record the verdict they would give and the mode alone decides, so **Manual** is the control you can prove today.

### 4. One tool call passes through many layers

Between the agent deciding to act and a cloud resource changing, a call passes through several layers. Each layer can say no, and each is blind to something.

| Layer | In CloudThinker | What it can refuse | What it can't see |
|---|---|---|---|
| Agent, guided by your intent | CloudThinker, following your prompt | Nothing on its own. It proposes. | Whether the call is safe |
| Sandbox | Applies to coding agents on your laptop. A CloudThinker chat doesn't run on your machine. | Access to your laptop's files and network | Your account. It can still read any keys left inside it. |
| Permission mode | [Approvals](/guide/approvals/overview): your rules, then **Manual** or **Auto** | Actions you haven't allowed, or that a rule or reviewer flags | Anything the rules didn't anticipate |
| IAM role | The role your AWS connection uses | Any call the role isn't allowed to make | Everything above. It sees one signed call. |
| Resource | The AWS resource itself | Nothing. It does what it's told. | Many actions have no undo |

A sandbox protects a laptop. Only IAM protects your account. That's why today's role is read-only at the IAM layer, not just by instruction.

### 5. Every cloud claim needs source, scope and time

Ask three questions about every line the agent gives you:

| Question | Example answer |
|---|---|
| **Source:** which call produced it? | The bucket policy status call, raw output attached. |
| **Scope:** which account, region and role? | Your read-only account, one region, the read-only role. |
| **Time:** when was it true? | Checked at 10:14 today. The cloud can change after that. |

Then give every claim one label:

| Label | Meaning | Example | What you do |
|---|---|---|---|
| **Verified** | Raw output proves it | "Bucket X blocks public access, checked at 10:14." | Act on it |
| **Inferred** | Reasoned from a verified fact | "So this data is probably not exposed." | Check it before you use it |
| **Assumed** | Nothing backs it yet | "This bucket is a security issue." | Test it, or leave it out |
| **Blocked** | The role couldn't look | "Couldn't list the bucket's objects." | Write it down. A blocked check is a valid result. |

CloudThinker's incident verdicts use three labels: **Verified** and **Inferred** mean the same as here, and **Cause unproven** matches **Assumed**. **Blocked** has no product label, so you add it yourself.

A finding is only as strong as its weakest step. One unchecked step in the middle makes the whole finding inferred. If you can't show the source, "not enough evidence" is the honest answer, and it's a valid one.

## Practice: 95 minutes

**The task:** what would you optimize in this AWS account? One team, one read-only agent, one report.

| Time | Length | Step | Done when |
|---|---|---|---|
| T+0 | 10 min | Sign in, invite your team, set your scope | Everyone is in one workspace and you've written a bounded task: the question and where the agent must stop |
| T+10 | 10 min | Connect your AWS account | The account shows **Connected**, **Allow writes** is off, and a chat is open |
| T+20 | 25 min | Explore with the agent | You have raw output for cost, security, reliability and performance |
| T+45 | 10 min | Break | The chat keeps the output |
| T+55 | 40 min | Label every claim, then write the report | Every claim has a label and a source; the file is submitted |

Write the scope at the top of your report draft. Two lines are enough:

```text
Question: what would we optimize in this account for cost and security?
Stop: before proposing any change that deletes data.
```

### Connect your AWS account

Use your own AWS account, ideally a staging or sandbox account, through a read-only IAM role. The account owner connects it on their own screen, and adding a connection needs the workspace **Admin** role. The full reference is [Connect AWS](/guide/connections/aws).

<Steps>
  <Step title="Open Connections">
    Sign in at [app.cloudthinker.io](https://app.cloudthinker.io). In the sidebar, click **More → Workspace settings** and select **Connections**.

    **Success state:** the **Connections** list opens.
  </Step>
  <Step title="Create the read-only role and connect">
    Select **Amazon Web Services** and follow the **Role-Based (recommended)** steps in [Connect AWS](/guide/connections/aws): name the account, run the setup script in CloudShell, paste the Role ARN, and click **Connect**. The script attaches only the AWS managed `ReadOnlyAccess` policy.

    **Success state:** the account shows a **Connected** status.
  </Step>
  <Step title="Turn off Allow writes">
    Open **Amazon Web Services** in Connections and turn off the **Allow writes** switch on its detail panel. The role already makes AWS refuse every change. With the switch off, CloudThinker refuses them too, before they reach AWS.

    **Success state:** **Allow writes** shows as off.
  </Step>
  <Step title="Open a chat">
    Start a new chat and send "Give me an overview of this AWS account."

    **Success state:** the agent answers with the regions and services it can see.
  </Step>
</Steps>

<Warning>
**Can't add the connection?** Adding a connection needs connector edit permission, which only the workspace **Admin** role has. Ask a workspace Admin to connect the account, or to change your role. See [Workspace roles](/guide/workspace-users#workspace-roles).
</Warning>

Nobody types credentials into a slide, a chat or a shared document. The account owner connects it on their own screen.

### What to ask the agent

Most teams ask for a list. Push for evidence instead: which resource, which region, when. Plain language works; you don't need any special syntax. Start with these:

```text
Give me an overview of this AWS account: regions in use, main services, and what your role could not read.
```

A useful answer names regions and services you can check, and includes a short list of things it was denied. That denied list is the start of your **01: What you looked at** block.

Working alone, compare your answer with this sample. It shows the shape, not a real result: your regions, counts and gaps will differ.

```text
Regions in use: us-east-1 (most resources), ap-southeast-1 (one S3 bucket)
Main services: EC2 (4 instances), EBS (6 volumes, 1 not attached), RDS (1 instance), S3 (3 buckets)
Could not read: Cost Explorer data (not turned on for this account)
```

If your answer has no "could not read" line, ask for one. If it lists services without counts or regions, ask which resources it saw.

```text
What would you optimize in this account for cost? For each item, show the call you made and the raw output.
```

A useful answer ties each item to a named resource and the output that shows the problem. An item with no resource or no output is assumed until proven.

```text
Which of these findings can you prove from the output you already have, and which are inferences?
```

Use the answer as a first pass at your labels, then check it yourself. The agent labelling its own work is not the same as you verifying it.

Keep the raw output. You need it for every claim in the report.

### Find the raw output

Each call the agent makes shows as a row in the chat. Click the row to expand it: **Input** shows what the agent asked for and **Output** shows what came back. Click **Copy** on the **Output** section and paste it into your report's appendix, with the time you copied it.

### Stuck?

| Problem | What to do |
|---|---|
| Sign-up or the AWS connection isn't working | Pair with a neighbouring team and keep going. Don't spend the block debugging one laptop. |
| The agent answers with generic best practices | Ask for the specific resource, region and call behind each line. |
| The agent says it can't read something | Good. Label it blocked and put it in your scope statement. |

## Your output: one report

PDF, doc or markdown. There's no template; working out what a good optimization report looks like is part of the task. These three blocks are the minimum.

| Block | What it contains |
|---|---|
| **01: What you looked at** | Account, regions, role. What the role couldn't see. |
| **02: What you'd optimize** | Each finding with source, scope and time, labelled verified, inferred, assumed or blocked. Biggest impact first. |
| **03: What happens next** | Which changes need a person to approve. What you dropped, and why. |

One finding, written well (an illustration of the format, not a real result):

```text
Finding: unattached EBS volume in one region (Verified)
Source: describe-volumes, raw output in appendix A
Scope: staging account, one region, read-only role
Time: checked 2026-09-05 10:42 ICT
Next: owner approves deletion after confirming no snapshot is needed
```

A dropped finding is a good result. A blocked check is a good result if it's written down. Only an unsupported claim kept as true is a bad result.

Submit one file per team before Share starts. Redact account IDs, ARNs, endpoints, hostnames and customer data first.

### When you're done

The connection stays in your workspace until you remove it, and lab chats spend credits like any other chat. To remove it, open **More → Workspace settings → Connections**, select **Amazon Web Services**, and click **Disconnect**. That needs the workspace Admin role.

## Share: 20 minutes

The organizers read the reports during the last part of the lab and pick the best ones, usually three. At the event, a team that ran the task on its own AWS account got extra credit. Each chosen team presents for five minutes from the report file and the raw agent output. No slides.

| Minutes | Show |
|---|---|
| 2 | **Scope and top finding.** What you looked at, what the role couldn't see, and the one finding you'd fix first. |
| 2 | **Evidence and what you dropped.** The evidence and its label. What you dropped, and why. |
| 1 | **What needs approval.** Which change needs a person before it happens. |

Then the room compares: same account, different scopes, different findings. For each finding, the room votes on what the evidence supports:

- **Observe:** keep watching. The evidence isn't strong enough to act on.
- **Recommend:** propose the change to its owner.
- **Request approval:** the change is ready, and a person signs off before it happens.
- **Stop:** drop it. The evidence doesn't hold up.

## Glossary

| Term | Meaning on Day 01 |
|---|---|
| Bounded task | A task with a stated goal, scope, allowed tools, and a point where the agent must stop. |
| Read-only | The agent can inspect resources and configuration. It can't create, change or delete anything. |
| Scope | Which account, region and role an answer came from. Part of every claim. |
| Least privilege | The role has only the permissions the task needs. Today that's read access. |
| Verified, inferred, assumed, blocked | The four labels for every claim in the report. |
| Human approval | A person signs off before a change happens. Today nothing changes at all: the role is read-only and **Allow writes** is off, so every fix stays a recommendation. |
| Audit trail | The raw output and the calls the agent made, kept so the run can be checked later. |
