The reference architecture production deployments are converging on: an orchestrator, a team of specialists, a closed operational loop, and a context layer.

## 4.1 Why multi-agent, not mono-agent

This chapter describes the vendor-neutral pattern. Sections 4.2 to 4.4 show where each part lives in CloudThinker, and [Chapter 10.3](/learn/aio/chapter-10-road-ahead#103-hyperscaler-agents-or-one-platform-across-clouds) compares it with the hyperscalers' own agents.

Production systems use orchestrated teams of specialists instead of one all-purpose agent. The reasons are practical:

1. **Depth beats breadth.** A Kubernetes specialist with curated K8s tools, prompts, and learned patterns outperforms a generalist on K8s problems, the same way human teams specialize.

2. **Bounded blast radius.** Each specialist holds only the credentials its domain requires. A database agent cannot modify security groups; a cost agent cannot drop tables.

3. **Independent evolution.** Specialists can be upgraded, evaluated, and rolled back independently. It's the microservices lesson applied to agents.

4. **Auditable handoffs.** Inter-agent delegation produces an explicit trail of who decided what, which monolithic reasoning hides.

The design consequence: the orchestration layer (routing tasks, managing context, handling errors) needs as much engineering as the agents themselves.

Two published accounts set the limits:

- **For specialization.** Anthropic's [multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) uses a lead agent that splits work across parallel workers. It reports large quality gains over a single agent, at much higher token cost. That cost is why the two-tier design in [4.3](#43-two-tier-sensing-and-resolving) matters.
- **Against overdoing it.** Microsoft's Azure SRE Agent team [wrote](https://techcommunity.microsoft.com/blog/appsonazureblog/-/4481200) that they started with 100+ tools and 50+ narrow agents, and ended with five core tools and a handful of generalists. Specialize by domain and credential boundary, not into dozens of micro-agents. Every agent and tool you add costs context, tokens, and coordination.

## 4.2 The reference architecture

A production agentic operations platform has five layers. Use them as a checklist when you evaluate any platform or design your own.

| Layer | Job | What to check when evaluating | In CloudThinker |
| :---- | :---- | :---- | :---- |
| **Orchestrator** | Receives goals and incidents, splits them into tasks, routes work to specialists, combines their findings, and escalates to people | Does one agent own the conversation and the escalation path? | The built-in [CloudThinker](/guide/agents/overview) assistant |
| **Specialist agents** | Domain experts (cloud, security, database, Kubernetes) with curated tools and scoped credentials | Can you add your own specialists, and limit each one's connections? | Temporary subagents that CloudThinker spawns, plus [custom agents](/guide/agents/quickstart) you create |
| **Operational loop** | Detect, analyze, resolve, validate. The validate stage is what separates agents from automation: the system checks its own work. | Does the platform confirm the outcome after acting, and roll back on failure? | [Pulse](/guide/pulse/overview) detects, [Resolve](/guide/incident/overview) investigates and fixes, [Approvals](/guide/approvals/overview) decides which writes run |
| **Tools and integrations** | Cloud APIs, observability, CI/CD, ITSM, and chat, with least-privilege credentials per agent | Are credentials scoped per system, and can you plug in your own tools? | [Connections](/guide/connections/overview), including your own [MCP servers](/guide/connections/mcp) |
| **Context and memory** | Topology, runbooks, past incidents, team conventions, environment metadata. This is where agents compound. | Does the system remember what it learned, and can you see and edit it? | [Memory](/guide/memory), [Runbooks](/guide/incident/runbooks), [Incident memory](/guide/incident/incident-memory), and [Knowledge](/guide/knowledge) |

## 4.3 Two-tier sensing and resolving

Naive agent designs run one model call per alert and fall over at production scale. Mature platforms separate two tiers: a cheap, always-on sensing tier that watches every signal, and an expensive reasoning tier that runs a full multi-step investigation only when the sensing tier finds something worth it. This is what makes 24/7 coverage affordable. When you evaluate a platform, ask how it decides what reaches the expensive tier, because that decision drives your model bill.

In CloudThinker, [Pulse](/guide/pulse/overview) is the sensing tier. It drops duplicates and noise, groups related alerts into clusters, and sends only clusters with an actionable signal to triage, where CloudThinker opens or matches an incident and investigates. You tune what escalates in three places:

- **Snoozes** in [noise suppression](/guide/pulse/clusters#noise-suppression) drop events you already know about.
- The **On duty** switch in **Resolve → Investigation** decides whether CloudThinker investigates on its own or waits for someone to click **Investigate**. See [Resolve](/guide/incident/overview#choose-who-starts-investigations).
- Which sources you connect in [Pulse setup](/guide/pulse/setup) decides what reaches Pulse at all.

## 4.4 Data protection inside the pipeline

In regulated industries, telemetry is sensitive: logs and queries leak customer PII, credentials, and account data. The emerging best practice is a tokenization boundary: a PII-aware layer that replaces sensitive values with tokens before any data reaches a model. Combined with a private deployment, it lets banks and other regulated firms adopt agentic operations without raw telemetry leaving their perimeter. [Chapter 6](/learn/aio/chapter-6-trust-governance#63-data-residency-and-control) covers data residency and control in depth.

### In CloudThinker

- **Masking.** [Guardrails](/guide/security/custom-guardrails) replace sensitive values with placeholders before an agent reads them. Email, phone, credit card, IBAN, MAC address, API keys, and cloud credentials are on by default. IP addresses, public keys, and cloud account IDs are off by default. You can add your own ID patterns in **Admin Settings → Guardrails**.
- **Deployment.** CloudThinker Cloud, Cloud plus [Workers](/guide/workers) on your own machines, and dedicated, self-hosted, or air-gapped deployments through an early-access program. See [Deployment options](/guide/deployment/overview).
- **Model calls on your account.** [BYOK](/guide/byok) runs model calls on your own model provider account.

## Architecture checklist

Ask any vendor, or your own team:

1. Does one orchestrator own cross-cutting reasoning and escalation to people?
2. Does each specialist hold only the credentials its domain needs?
3. Does every piece of work go through detect, analyze, resolve, validate, with the outcome checked after acting?
4. Is there a cheap sensing tier in front of the expensive reasoning tier, and can you tune what escalates?
5. Are personal identifiers and secrets masked before any model call?
6. Is there a private or self-hosted deployment option for regulated workloads?
7. Does the system keep memory between incidents, so it doesn't start cold each time?
