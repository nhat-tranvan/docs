*Definitions matter, because "agent" is the most abused word in enterprise software.*

This chapter gives you four tools: a definition you can quote, a five-level autonomy scale for deciding what an agent may do on its own, a list of what agentic operations is not, and a five-question test for vendors.

## 3.1 A working definition

<Info>
**Definition**

Agentic infrastructure operations (AgenticOps) is an operating model in which AI agents run the core loop of operational work (detect a condition, analyze the cause, resolve the issue, validate the outcome) across cloud and on-premise infrastructure. They work under explicit policy that humans define. Humans supervise *on* the loop instead of executing *in* it.
</Info>

An agent in this sense is not a chatbot with a runbook, and not a script with an LLM bolted on. A real operations agent has five properties. Use them as a checklist when you evaluate any tool:

| Property | What it means | What to look for |
| :---- | :---- | :---- |
| **Goal-directed** | It takes outcomes, not step-by-step instructions | You can say "keep checkout latency under 300ms" or "keep monthly cloud spend within budget" |
| **Perceptive** | It reads telemetry continuously instead of waiting for a prompt | It consumes metrics, logs, traces, events, configuration state and cost data |
| **Reasoning** | It forms and tests causal hypotheses and weighs alternative fixes | It explains its thinking in language an engineer can audit |
| **Tool-using** | It acts through the interfaces engineers already use | It works with cloud APIs, kubectl, Terraform, SQL and CI/CD using scoped, auditable credentials |
| **Self-verifying** | After acting, it checks whether the outcome was achieved | It escalates or rolls back when the fix didn't work |

If a tool is missing any one of these, treat it as an assistant, not an agent.

## 3.2 The autonomy spectrum

Autonomy is not on or off. Mature agentic platforms expose it as a policy dial, usually set per action class (for example "restart a pod") and per environment (for example production versus staging):

| Level | Name | Agent behavior | Human role |
| :---- | :---- | :---- | :---- |
| L0 | Observe | Monitors and reports; takes no action | Executes everything |
| L1 | Advise | Investigates and recommends with evidence | Decides and executes |
| L2 | Act with approval | Prepares full remediation; waits for sign-off | One-click approve/reject |
| L3 | Act with notification | Executes pre-approved action classes; informs humans | Reviews after the fact |
| L4 | Autonomous in domain | Owns a bounded domain end-to-end within policy | Sets policy; audits outcomes |

Most organizations run several levels at once. Every action class starts low and earns its way up. A typical ceiling once the evidence is in:

| Action type | Examples | Typical ceiling |
| :---- | :---- | :---- |
| Reversible, small blast radius | Restart a pod, clear a cache, scale a replica set | L3 to L4 |
| Consequential changes | Schema migrations, security group changes, failovers, credential rotation (every consumer of the credential can break) | L2 |
| Anything novel | A remediation the agent hasn't performed before in this environment | L1 |

Move an action class up one level only when you have evidence it works at the current one. Use the [Chapter 8 KPIs](/learn/aio/chapter-8-measuring#82-the-operating-dashboard) as the gate: an acceptance rate above about 95% for that action class and a flat or falling rollback and intervention rate. Never faster. [Chapter 7](/learn/aio/chapter-7-humans-on-the-loop#73-trust-is-built-in-increments) turns this into a step-by-step trust ladder.

### In CloudThinker

CloudThinker doesn't use L0 to L4 labels. Reads always run, and every write passes through [Approvals](/guide/approvals/overview) in **Approvals** in the sidebar, **Approval mode** tab. Each level maps to a setting:

| Level | How to get it in CloudThinker |
| :---- | :---- |
| L0 to L1 | Ask for investigations only, and add a **Deny** [Rule](/guide/approvals/rules) for writes the agent must never make. |
| L2 | Set the [Approval mode](/guide/approvals/approval-mode) to **Manual**, or add an **Ask first** Rule for one kind of write. |
| L3 | Accept an **Allow** Rule for one operation on named connections, under an **Auto** mode. |
| L4 | No single switch. Run a bounded domain as an [Automation](/guide/automation/automations) with **Allow** Rules for its writes. |

New workspaces start on **Auto · Rules + AI · Ask me**, which runs accepted Rules, lets AI judgment allow a safe write, and asks a person about the rest.

<Info>
**How the hyperscalers ship the dial**

- [Gemini Cloud Assist investigations](https://docs.cloud.google.com/cloud-assist/investigations) run root-cause analysis and report observations. They don't change your resources (L1).
- [AWS DevOps Agent](https://docs.aws.amazon.com/devopsagent/latest/userguide/about-aws-devops-agent.html) investigates incidents and hands you a mitigation plan to carry out (L1 to L2).
- [Azure SRE Agent](https://learn.microsoft.com/en-us/azure/sre-agent/overview) has a Review mode where actions wait for your approval, and a more autonomous mode for actions you allow (L2 to L3).

All three start an agent with little trust and let it earn more.
</Info>

## 3.3 What agentic operations is not

"Agent washing" is common enough that Gartner has named it: vendors rebranding assistants, chatbots and RPA as "agents" without real agentic capability. In a [June 2025 press release](https://www.gartner.com/en/newsroom/press-releases/2025-06-25-gartner-predicts-over-40-percent-of-agentic-ai-projects-will-be-canceled-by-end-of-2027), Gartner estimated that of the thousands of vendors claiming agentic AI, only about 130 were real. Knowing what agentic operations is *not* is your best defense as a buyer:

1. **Not a chatbot over your dashboards.** Chatting with your telemetry is a feature, not the operating model. If a human has to read the answer and then go do the work, you are still in Gen 3 (see [Chapter 2](/learn/aio/chapter-2-automation-to-autonomy)), whatever the marketing says.

2. **Not lights-out operations.** No credible practitioner advocates removing humans. The target is human leverage: one engineer supervising work that used to take a team.

3. **Not a replacement for engineering discipline.** Agents amplify the environment they are given. Weak observability, absent IaC, and undocumented systems produce weak agents. Garbage context in, garbage autonomy out.

4. **Not one giant model that does everything.** As the next chapter shows, production systems are converging on orchestrated teams of specialists, not monolithic super-models.

<Warning>
**The five-question vendor test**

Ask any "agentic" vendor:

1. Can the system execute a remediation end-to-end, or only recommend?
2. Does it verify its own outcomes and roll back on failure?
3. Can autonomy be set per action class and per environment?
4. Does every action carry a full, immutable reasoning trail?
5. What were its rollback and intervention rates in its last three production deployments?

A real platform answers all five with evidence, not a roadmap slide. Agent washing usually fails by question two.
</Warning>

## 3.4 The scope of operational work agents can own today

Use this table to pick a first domain. Start where typical autonomy is highest and actions are easiest to reverse, which usually means cloud cost or Kubernetes operations, then expand. The last column shows where to start in CloudThinker.

| Domain | Representative agent tasks | Typical autonomy (2026) | In CloudThinker |
| :---- | :---- | :---- | :---- |
| Incident response | Triage, correlation, root-cause analysis, remediation, post-incident reports | L1 to L3 | [Resolve](/guide/incident/overview) |
| Cloud cost (FinOps) | Rightsizing, idle-resource cleanup, commitment planning, anomaly detection | L2 to L4 | [Optimize](/guide/cost-optimization/overview) |
| Kubernetes operations | Pod/node health, resource tuning, upgrade assistance, capacity planning | L2 to L3 | [Kubernetes connection](/guide/connections/kubernetes) |
| Database operations | Slow-query analysis, index advice, replication health, storage forecasting | L1 to L3 | Database connections such as [PostgreSQL](/guide/connections/postgresql) |
| Security operations | Misconfiguration detection, CVE triage, IAM hygiene, compliance evidence | L1 to L2 | [Cyber](/guide/security/cyber-overview) |
| Change & release | Pre-deploy risk analysis, canary monitoring, automated rollback | L2 to L3 | [Review](/guide/code-review/overview), for pre-deploy risk |
| Infrastructure as Code | Drift detection, module generation, plan review, state hygiene | L1 to L3 | [Terraform connection](/guide/connections/terraform) |

Autonomy ranges here are typical for the industry in 2026, not fixed limits. Your own levels depend on how good your observability, IaC and runbooks are.
