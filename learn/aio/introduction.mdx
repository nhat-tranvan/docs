This is the CloudThinker field guide to AgenticOps, *Agentic Infrastructure Operations, Leadership Edition* (June 2026, last reviewed October 2026). Use it to decide whether, where, and how fast to let AI agents do operational work in your environment.

## Who this guide is for

It's written for the people who carry the pager and the people who set the budget: SREs, DevOps and platform engineers, infrastructure leaders, CTOs, and CIOs. Regulated industries get extra attention, because there autonomy has to be earned, evidenced, and audited: see [4.4](/learn/aio/chapter-4-architecture#44-data-protection-inside-the-pipeline) on masking data before the model, and [Chapter 6](/learn/aio/chapter-6-trust-governance) on data residency and audit trails.

Each chapter hands you something to use: a definition to hold vendors to, an architecture checklist, a governance model, a set of KPIs, or a 90-day plan.

## The argument in brief

1. **[The crisis](/learn/aio/chapter-1-complexity-crisis).** Infrastructure complexity grows faster than headcount, and more people, scripts, and dashboards all keep a human in the execution path.
2. **[Automation to autonomy](/learn/aio/chapter-2-automation-to-autonomy).** Agents are the fourth generation of operations tooling. They reuse your IaC, alerts, and scripts, and close the loop those tools left open.
3. **[The definition](/learn/aio/chapter-3-what-is-aio).** A real agent is goal-directed, perceptive, reasoning, tool-using, and self-verifying. Autonomy is a dial (L0 to L4) set per action class and environment.
4. **[The architecture](/learn/aio/chapter-4-architecture).** One orchestrator, a few scoped specialists, a closed loop with validation built in, a cheap sensing tier in front of an expensive reasoning tier, and sensitive data masked before the model.
5. **[The agent team](/learn/aio/chapter-5-agent-team).** Give each agent a stable scope and least-privilege access, and meet engineers in chat with the reasoning shown.
6. **[Trust and governance](/learn/aio/chapter-6-trust-governance).** Put guardrails, data controls, and an exportable audit trail in place before any agent writes to production.
7. **[Humans on the loop](/learn/aio/chapter-7-humans-on-the-loop).** Engineers move from doing the work to supervising it, and hand over autonomy one proven step at a time.
8. **[Measuring](/learn/aio/chapter-8-measuring).** Eight KPIs, led by MTTR, autonomous resolution rate, and rollback rate, decide whether the program earns more autonomy.
9. **[The roadmap](/learn/aio/chapter-9-roadmap).** Check five readiness foundations, run a 90-day pilot with exit criteria, then scale over twelve months.
10. **[The road ahead](/learn/aio/chapter-10-road-ahead).** Plan for five near-term shifts and decide between a native agent per cloud and one platform across all of them.

## Terms you'll see everywhere

| Term | Meaning |
|---|---|
| **AgenticOps** (agentic infrastructure operations) | AI agents that run the whole operational loop under explicit policy: detect a problem, analyze it, resolve it, and validate the fix. The guide calls this loop DARV (Detect → Analyze → Resolve → Validate). |
| **In the loop** | A person executes every step. The agent, if there is one, only suggests. |
| **On the loop** | A person sets intent, approves consequential actions, and reviews outcomes. Agents do the execution. |
| **Autonomy level (L0 to L4)** | The guide's vendor-neutral scale for how much an agent may do on its own, from observe-only (L0) to fully delegated (L4). Defined in [Chapter 3](/learn/aio/chapter-3-what-is-aio). |
| **Agent washing** | Selling a chatbot, a script runner, or an alert summarizer as an autonomous agent. [Chapter 3](/learn/aio/chapter-3-what-is-aio) gives you five questions to catch it. |
| **MCP** (Model Context Protocol) | An open standard that lets an agent call tools and read data from other systems through one interface. |
| **Toil** | Manual, repetitive operational work that scales with system size and adds no lasting value. |
| **Orchestrator** | The coordinating agent that splits work, routes it to specialists, and escalates to people. In CloudThinker this is the built-in [CloudThinker](/guide/agents/overview) assistant, which spawns temporary subagents. |
| **Sensing tier** | The cheap, always-on layer that watches signals and decides what deserves a full investigation. In CloudThinker this is [Pulse](/guide/pulse/overview). |
| **Action class** | One kind of change an agent can make, such as "restart a pod" or "roll back a deploy". Autonomy is set per action class. |
| **Blast radius** | How much breaks if an action goes wrong. Small-blast-radius actions are the first to get more autonomy. |
| **BYOC** (bring your own cloud) | Running the vendor's platform inside your own cloud account, so data stays in your perimeter. |
| **SLO** (service level objective) | A target for a service, such as "99.9% of checkout requests under 300ms". |
| **MTTR** (mean time to resolve) | Average time from an incident starting (impact onset) to it being resolved. Resolve Insights measures it the same way. |

For CloudThinker's own product terms, see the [Glossary](/guide/glossary).
