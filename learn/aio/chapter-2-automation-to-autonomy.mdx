*Agentic operations is the fourth generation of operations tooling. Knowing what came before tells you what it needs from you.*

This chapter places agents next to the tools you already run, explains where AIOps stopped short, and covers the three technical changes that made agents practical. Use it to judge which parts of your current stack an agent platform will reuse and which gaps it has to fill.

## 2.1 Four generations of operations

| Generation | Core idea | What it automated | What stayed manual |
| :---- | :---- | :---- | :---- |
| Gen 1: Manual work and scripts | People operate systems; shell scripts handle repeated steps | Single, known tasks | Deciding what to run, and when. Knowledge lived in people's heads. |
| Gen 2: Infrastructure as Code (IaC) | Declare the desired state in code; CI/CD pipelines apply it | Provisioning and deployment | Day-2 work: drift, incidents, tuning, cleanup |
| Gen 3: AIOps | Machine learning (ML) finds anomalies, correlates events, and cuts noise | Spotting and grouping problems | Finding the cause, choosing a fix, and applying it |
| Gen 4: Agentic operations | Goal-directed agents that observe, reason, act, and check the result | The full loop, under policy you set | Setting policy, approving risky changes, handling novel failures |

Each generation builds on the one before it instead of replacing it. Agents express changes as code (Gen 2), take correlated alerts as input (Gen 3), and still write and run scripts (Gen 1). What changes is who closes the loop.

That has a practical consequence: an agent is only as good as the stack under it. If your infrastructure isn't in code or your alerts are pure noise, fix that first or expect weaker results.

## 2.2 Why AIOps fell short

AIOps earned its place. Event correlation and deduplication work, and they cut alert volume a lot. But the tools stopped at "here is a group of alerts," and a person still had to do the rest.

Three gaps set the ceiling:

1. **Correlation without causation.** Grouping fifty alerts into one incident helps. It still doesn't tell you the root cause or what to do about it.
2. **Answers without reasoning.** An ML score with no explanation is hard to trust. Engineers re-checked the output by hand, which removed most of the time saved.
3. **No hands.** AIOps could open a ticket or call a webhook. It couldn't investigate, test a hypothesis, pick a fix, apply it, and confirm it worked. The engineer stayed the one who acted.

## 2.3 What changed: reasoning models, tools, and protocols

Three changes made agents practical for operations work.

1. **Reasoning models.** Large language models (LLMs) can now read logs, configuration, and code, form a hypothesis about the cause, and plan a multi-step fix in a well-scoped domain.
2. **Tool use.** Models can reliably call functions: run CLI commands, query APIs, run `kubectl` or Terraform, and read dashboards. That turns reasoning into action.
3. **A standard way to plug in tools.** The Model Context Protocol (MCP) is an open standard for exposing tools to AI agents. A team can put one MCP server in front of an internal system and any compatible agent can use it.

Operations suits agents for one more reason: results are easy to check. A fix either brings latency back under target or it doesn't. A Terraform plan applies cleanly or it fails. A health check passes or it doesn't. When the feedback is that clear, an agent can test its own work, and you can see whether it did.

## 2.4 How the industry is rolling agents out

The major cloud providers now ship their own operations agents. They launched them the same way: investigate first, and keep any change behind the customer's approval.

That pattern is the lesson for your own rollout. Start with agents that read and explain, check their analyses against what your engineers find, and only then let them act, one kind of action at a time.
