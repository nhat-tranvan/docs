*One harness, three domains. The loop, context, tools, and policy from Parts 01 to 03 only create value once you point them at real work, and each domain bends the engineering in its own way.*

Teams usually deploy an operations agent into three domains: complexity, cloud cost, and security. This book calls reliability and incident response "complexity", because that's where the size and tangle of your estate shows up as outages. Treat them as one loop with different settings, not three products. This chapter gives you those settings per domain, the traps in each, and the order in which each one can safely earn more autonomy.

## 10.1 One loop, five dials

Five parameters decide how an agent behaves in a domain. They're part of the harness, which [Chapter 7](/learn/aio-engineer/chapter-7-evaluating-agents) showed does more for production results than the bare model does. The last row is what they add up to.

| Dial | Complexity (reliability) | Cost | Security |
|---|---|---|---|
| Trigger | Alerts and events, in real time | Schedules; billing data often lags a day or two | Scanner and pentest findings, vulnerability feeds, config drift |
| Tempo | Minutes; latency matters | Hours to daily; batch is fine | Minutes for a live exposure; daily for posture |
| Context that decides quality | Topology, recent changes, runbooks, incident memory | Usage over time, pricing and commitment data, ownership tags | Asset inventory, infrastructure-as-code (IaC) state, identities, the controls you track |
| Action risk | Mostly reversible; rollback exists | Mostly reversible, except multi-year commitments | Enforcement can break production; a quarantine has blast radius |
| Verification | A health or SLO probe after the fix | Billing change, plus a check that performance didn't regress | A rescan or retest shows the finding is gone |
| Where autonomy starts | Investigate freely; act through approvals (Ch. 6) | Report freely; gate rightsizing; commitments always need a person | Detect and gather evidence freely; remediate with approval first |

Use this table as a design review checklist. If you can't fill in a cell for your environment, the agent can't either.

## 10.2 Complexity: the pillar the pager answers to

Incident response is the hardest case in this book. The question is open-ended ("why is checkout slow?"), the system is failing while you investigate, and proving a fix means probing a live service, not reading a bill. That's why benchmark results in [Chapter 7](/learn/aio-engineer/chapter-7-evaluating-agents) are weakest here, and why this pillar earns autonomy slowly.

Four rules follow from that.

- **Diagnosis is the product.** Track how often on-call engineers accept the agent's root cause. That number unlocks everything else.
- **Fix the cause, not the symptom.** Chapter 7 showed agents passing mitigation tests with restart loops. In production, escalate any fix that doesn't cite a diagnosed cause, or that repeats inside its own cooldown window.
- **Act through runbooks.** A runbook with pre-checks, typed steps, and a post-check turns an open-ended action into a bounded, auditable one.
- **Measure against your own baseline.** Track MTTR change, diagnosis acceptance rate, escalation rate, and repeat-incident rate. The last one tells you whether incident memory ([Chapter 2](/learn/aio-engineer/chapter-2-context-engineering)) is learning.

## 10.3 Cost: where autonomy is earned fastest

Cost flips the profile. Verification is nearly free, since the bill either moved or it didn't. Most actions reverse cleanly: you can resize an instance back, restore a volume from a snapshot, or re-enable a schedule. Cheap proof plus reversible action is the promotion test [Chapter 12](/learn/aio-engineer/chapter-12-autonomous-mission-loop) formalizes, so cost is usually the first domain where an agent acts on its own and tells you afterward.

Three traps still need engineering.

| Trap | What goes wrong | What to do |
|---|---|---|
| Counterfactual savings | "Savings" is a claim about spend that would have happened. Summing recommendations inflates it. | Report realized change against a frozen baseline: spend recorded before the agent started and never revised afterward ([Appendix A](/learn/aio-engineer/appendix-a-poc-test-plan)). |
| Moving the bill | A rightsizing that causes latency incidents shifts cost to the reliability team. | Verify with the billing change and a performance guard. If the guard trips, roll back and record the case in memory. |
| Irreversible commitments | Reserved instances and savings plans lock you in for one to three years. | Keep them approval-only for good. The agent's job is the evidence: usage history, coverage math, break-even point. |

## 10.4 Security: highest stakes, clearest split

Security has the sharpest gap between reading and writing. The read side is large, recurring work with cheap verification: triaging findings, checking whether a vulnerability is actually reachable in your environment, and gathering evidence. Automate it first. The write side (patching, quarantining workloads, revoking credentials, changing IAM) has the worst blast radius in this book. An over-broad quarantine is a self-inflicted outage, and a bad IAM change can lock out your responders.

Run the [Chapter 6](/learn/aio-engineer/chapter-6-policy-approvals) approval machinery at its strictest here. Enforcement actions need approval by default, and you loosen that one narrow action class at a time.

Two habits matter most in this domain.

- **Fix in code, not in the console.** If IaC manages the resource, a console fix is undone by the next apply and the finding comes back. Propose the change to the IaC source and let CI be the verification gate.
- **Keep evidence current, not reconstructed.** Configuration snapshots, access reviews, and change records are read-only and easy to verify. Collecting them continuously saves the scramble before an audit, and it's often the easiest deployment to get approved.

Useful measures: time to remediate by severity, how long internet-facing findings stay exposed, how fresh your evidence is, and zero enforcement actions that skipped approval.

## 10.5 One harness, three packs

Per domain, you change four things: the tool pack, the context pack, the policy defaults, and the evaluation set. Keep the harness itself shared: one policy engine, one approval surface, one trace store, one evaluation method.

The anti-pattern is a separate product per domain, each with its own console, permissions, and audit trail. It rebuilds the swivel-chair problem one layer up and triples the attack surface from [Chapter 5](/learn/aio-engineer/chapter-5-threat-model). Worse, it hides the cases that cross domains, such as a cost change that causes an incident, or a security finding caused by a change the reliability agent made.

<Info>
**In practice: one platform, three modules**

CloudThinker maps these pillars to modules that share one set of [connections](/guide/connections/overview), one [Approvals](/guide/approvals/overview) system, and one [audit log](/guide/security/audit-logs).

| Pillar | Module | What it does today |
|---|---|---|
| Complexity | [Resolve](/guide/incident/overview) | Runs [root cause analysis](/guide/incident/root-cause-analysis) on incidents, reads your [runbooks](/guide/incident/runbooks), and learns from past incidents through [incident memory](/guide/incident/incident-memory). |
| Cost | [Optimize](/guide/cost-optimization/overview) | Scans AWS, GCP, or Azure billing read-only and ranks savings findings with estimates. It needs read access to billing data: AWS Cost Explorer, a GCP billing export in BigQuery, or an Azure Cost Management scope. The first scan pulls up to 13 months of history, and AWS Cost Explorer can lag usage by 24 to 48 hours. On a finding, **Implement** asks CloudThinker to make the change, and that write goes through Approvals. To let one kind of change run without asking, accept an **Allow** Rule for that exact operation and connection. |
| Security | [Cyber](/guide/security/cyber-overview) | Pentests a web app or API on a domain you've verified, and keeps the request and response that prove each finding. [Code Audit](/guide/security/code-audit) checks a repository revision. On a finding, **Create PR with agent** prepares the fix as a pull request in a repository attached to the app, so you need a [Git provider connection](/guide/connections/github) first. Then you retest. Cyber doesn't assess cloud configuration or IAM posture. |

Every write, in any module, passes the same Rules and the same **Manual** or **Auto** Approval mode, so you set the policy once.
</Info>

<Tip>
**Key takeaways**

1. **The domain doesn't change the loop, it changes the dials.** Set trigger, tempo, context, action risk, and verification cost per domain instead of buying a product per domain.
2. **Autonomy arrives at the speed of verification.** Cost usually graduates first, bounded incident actions next, security enforcement last. Evidence collection is the quiet early win.
3. **One harness, three packs.** Separate stacks per domain multiply the audit surface and hide the cross-domain failures that hurt most.
</Tip>
