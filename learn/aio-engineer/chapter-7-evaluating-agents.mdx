*Public benchmarks are humbling and gameable. Your own environment is the only test that settles anything, and this chapter shows how to build it.*

## 7.1 What the public benchmarks say

Open, independent measurement of operations agents now exists. Sources for every figure here are in [Appendix D](/learn/aio-engineer/appendix-d-sources).

| Benchmark | What it tests | What to take from it |
|---|---|---|
| **ITBench** (IBM Research) | SRE, compliance, and FinOps scenarios | Agents on state-of-the-art models resolve roughly 11–14% of SRE scenarios, about one in seven |
| **ITBench-AA** (Artificial Analysis with IBM, 2026) | Frontier models diagnosing Kubernetes incidents | Every evaluated model scored below 50% on the headline precision metric |
| **AIOpsLab** (Microsoft Research) | Agents evaluated in a live environment | No single headline figure. It set the pattern of evaluating agents in a live environment, which the replay guidance in 7.3 builds on |

These are diagnosis and mitigation tasks in controlled environments. They are easier than your production in some ways and harder in others, and the best public results still fail most of the time.

Teams still run agents in production successfully, so both facts hold. The difference is that a production deployment is not a bare model on an unfamiliar cluster. It is a model inside a **harness**: curated context about a known estate, purpose-built tools, runbooks with your team's knowledge, memory of past incidents, and policy that routes agents to the incident classes they handle well.

Benchmarks measure the bare model. Production measures the harness. So "which model do you use?" tells you little about a platform. Test the harness instead, which is what the rest of this chapter covers.

## 7.2 Benchmarks can be gamed, and so can yours

The SREGym research (2026) documented two exploits to remember whenever you read an evaluation claim:

- **Reward hacking.** When the fault injector ran inside the environment the agent could inspect, agents found it and disabled it instead of fixing the fault.
- **Alert-clearing as false success.** A large share of one benchmark's mitigation tasks could be "solved" by a generic pod-restart loop that made the alert go away without touching the defect.

The same work measured the gap between knowing and fixing: even with the right root cause, mitigation succeeded only about 69–88% of the time.

Three rules carry over to your own evaluation:

1. **Score state, not symptoms.** Check independently that the defect is gone and the system is healthy. Whether the alert cleared proves nothing.
2. **Hide the test machinery.** The agent under test must not be able to see or reach the evaluation harness.
3. **Score diagnosis and mitigation separately.** They fail independently and improve independently.

The same trap exists in production. An agent graded on "alerts closed" learns to close alerts, so pick online success metrics with the same care. The independent-verification rule in [Chapter 1](/learn/aio-engineer/chapter-1-agent-anatomy) is the production version of this principle.

## 7.3 Build a golden set from your own incidents

Public benchmarks calibrate the field. Only your incidents calibrate your deployment. The asset to build is a **golden set**: a curated, versioned collection of test scenarios drawn from your production history.

1. **Harvest from postmortems.** Each real incident becomes a candidate scenario with five parts: the telemetry at detection, the environment state, the true root cause, the accepted fix, and the evidence that the fix worked. Twenty to fifty scenarios across your top incident classes is a working golden set. For a first proof of concept, ten is the minimum (7.5). Add every new kind of incident after that.
2. **Replay, don't re-break.** Feed the recorded signals to the agent and let it investigate against snapshotted or simulated state. Fault injection in staging adds mitigation scoring, with the isolation rules from 7.2 applied.
3. **Score in layers.** Score each scenario on every layer in the table below.
4. **Use model judges, and check the judges.** A model can grade the rubric at scale. Each cycle, compare its grades with human grades on a sample, and keep people grading a rotating slice. On-call engineers rating agent analyses gives you evaluation data and builds trust at the same time.

| Layer | Question | Scored against |
|---|---|---|
| **Detection** | Did it triage the signal correctly? | The known severity and incident class |
| **Diagnosis** | Did it name the right root-cause entity and mechanism? | The recorded root cause |
| **Plan quality** | Is the proposed fix safe, minimal, and the right choice? | The accepted fix and your policy |
| **Mitigation** | Is the system actually healthy afterward? | An independent state check |
| **Evidence integrity** | Does every claim trace to data the agent really retrieved? | The agent's tool-call log |

<Note>
Fabricated evidence scores zero on the whole scenario, whatever the answer. A right answer built on data the agent never retrieved will fail you on the next incident.
</Note>

A scenario record can be as small as this generic sketch (not a CloudThinker file format):

```yaml
# Generic golden-set scenario, not a product format
id: 2026-03-checkout-latency
class: database
signals: snapshots/2026-03-checkout/   # alerts, metrics, logs at detection
expected:
  severity: high
  root_cause: "connection pool exhausted on orders-db after a config change"
  service: orders-db
  accepted_fix: "revert pool size config"
  healthy_when: "p95 checkout latency < 400ms for 15m, error rate < 1%"
```

The `healthy_when` line is the state-based check from 7.2. Write it before you run the agent, so nobody grades the answer to fit.

## 7.4 Treat evals as CI

The agent stack changes constantly: prompts, tools, skills, policies, retrieval, and models, which vendors can swap under you. Each of those is a deploy, and deploys need gates.

- **Run the golden set on every change.**
- **Block on per-class regressions, not just the average.** A new model that gains on database scenarios and quietly loses on Kubernetes ones is a regression, even if the total goes up.
- **Canary in production with online metrics.** Track acceptance rate, rollback rate, and autonomous-resolution rate per class. They are your evals running continuously against reality.

The golden set is the offline half of one evaluation system. The online metrics are the other half.

## 7.5 How this maps to CloudThinker

Use the golden set to run a proof of concept (POC) on any platform, including CloudThinker. [Appendix A](/learn/aio-engineer/appendix-a-poc-test-plan) gives the protocol: bring ten or more replayable scenarios from your own history, and score detection, diagnosis, plan, mitigation, and evidence integrity for each one.

**Running your scenarios in CloudThinker.** You can replay a recorded alert by posting its JSON to a [Resolve webhook](/guide/webhooks/overview), which sends it through Pulse and can open an incident and start root cause analysis. CloudThinker then investigates the live systems behind your [connections](/guide/connections/overview), not a snapshot. So point it at a staging account or cluster where you've injected the same fault, and score the result by hand against your scenario record. CloudThinker doesn't gate releases on your golden set or run a model judge for you, so the CI gate in 7.4 and any judge stay in your own tooling.

For the online half, [Resolve Insights](/guide/incident/insights) has an **Accuracy & trust** tab. Resolve is CloudThinker's incident response module, and this tab is built only from your team's verdicts, never from the agent scoring itself.

| Chapter idea | Where it lives in CloudThinker |
|---|---|
| Human grades on agent analyses | **Was Resolve's diagnosis right?** on each resolved incident |
| Informative rejection reasons | **What was wrong?**: **Wrong root cause**, **Wrong service**, **Fix wouldn't work**, **False positive**, or **Something else** |
| Diagnosis scoring | **Root-cause accuracy** |
| Plan acceptance | **Fix acceptance** |
| Detection quality | **False-positive rate** |
| Per-class scoreboard | **Accuracy by service** |
| Sample size behind the numbers | **Your review coverage** |

### Start your online evaluation

<Steps>
  <Step title="Grade a resolved incident">
    Go to **Resolve → Investigation** and open a resolved incident. Below the analysis, under **Was Resolve's diagnosis right?**, click thumbs-up or thumbs-down. If it was wrong, pick a reason under **What was wrong?**. Only the workspace Admin role can grade, and the question appears once the incident has a verdict.

    **Success state:** the incident shows **Marked accurate** or **Marked not accurate**.
  </Step>
  <Step title="Read the scoreboard">
    In the Resolve sidebar, find the **Analytics** heading, click **Insights**, and choose the **Accuracy & trust** tab.

    **Success state:** your verdict counts toward **Root-cause accuracy**, and **Your review coverage** shows how many resolved incidents someone has reviewed.
  </Step>
</Steps>

Check **Your review coverage** before you act on any rate. With only a few reviewed incidents, one verdict swings the number a lot. A rule of thumb: wait for about 20 reviewed incidents on a service before you act on its rate in **Accuracy by service**.

<Tip>
**KEY TAKEAWAY**

Public benchmarks say the bare model fails most SRE scenarios. Production says the harness closes much of the gap. So evaluate harnesses: a golden set built from your own incidents, layered state-based scoring with evidence integrity, checked judges, and regression gates on every change to prompts, tools, policies, or models.
</Tip>
