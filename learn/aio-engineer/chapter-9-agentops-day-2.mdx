*The pilot ends and the fleet stays. Day 2 is version management, model migrations, memory upkeep, and postmortems for a new kind of teammate, and this chapter gives you a working routine for each.*

## 9.1 Everything is an artifact, and every change is a deploy

The unit you operate is a versioned bundle:

| Part of the bundle | Example |
|---|---|
| Prompts and agent instructions | The system prompt, a custom agent's instructions |
| Tool schemas | Tool names, argument types, and descriptions the model reads |
| Skills | Step-by-step procedures the agent can load |
| Policy files | Approval rules, approver groups, autonomy settings |
| Retrieval configuration | What gets indexed, chunking, ranking |
| Judge rubrics | The scoring prompts from [Chapter 7](/learn/aio-engineer/chapter-7-evaluating-agents) |
| Model pins | The exact model version each agent uses |

Ship the bundle like a service release. Review it in a pull request, run it through the Chapter 7 eval gates, roll it out progressively, and roll it back as one unit.

Hunt down **invisible change**: a prompt edited in a console, a model updated on the vendor's side, a tool description tweaked in place. If a change can't be diffed, gated, and reverted, it will eventually be the root cause you can't find, in a system whose whole job is finding root causes.

## 9.2 The model migration playbook

Models change on someone else's schedule: deprecations, upgrades, price moves. A model swap is the highest-variance change in the stack, so run it as a project:

1. **Pin versions explicitly.** Never point production at "latest".
2. **Run the full golden set on the candidate** and diff results per incident class, not just the average.
3. **Canary on low-risk classes** and watch online metrics: acceptance, rollback, step counts, and cost. A shift in step counts is the classic tell of changed behavior.
4. **Keep dual-run capability** so sensitive classes can run old and new side by side and compare.
5. **Agree deprecation windows with vendors in advance**, so a migration is planned work, not an emergency.

Some fleets mix models: small tuned models on routine classes, frontier models on novel investigations. Apply the same playbook per lane. You also gain resilience, because a price shock or regression in one model becomes a problem for one lane, not the whole fleet.

## 9.3 Memory and knowledge upkeep

[Chapter 2](/learn/aio-engineer/chapter-2-context-engineering) designed memory. On day 2 you maintain it. A monthly cycle that works:

1. **Review new memories** written since the last cycle. Sample them, starting with high-impact incident classes.
2. **Settle contradictions** where fresh evidence disputed a stored conclusion.
3. **Prune or expire memories** that reference decommissioned systems.
4. **Re-index the knowledge layer** after major changes to your estate.

Give the knowledge layer a named owner. It's a production dependency, not a wiki with good intentions. And close the loop: every resolved incident's postmortem should end with one explicit line, "What did we teach the system?"

## 9.4 Postmortems for agents

Agents will be wrong. The reflex you want is the one SRE culture already has: blameless postmortems that focus on mechanism, now applied to software teammates.

When an agent makes a consequential mistake, rebuild the event from the trace and the audit record with four questions:

| Audit | Question |
|---|---|
| Context | What did the agent know? |
| Reasoning | What did it conclude, and from which evidence? |
| Governance | What did policy allow it to do? |
| Safety | What did verification catch or miss? |

Then name the mechanism, because each one has a different fix:

| Mechanism | Typical fix |
|---|---|
| Context gap | Add the missing source or connection |
| Retrieval miss | Fix indexing or ranking for that class |
| Prompt injection | Tighten input handling and egress ([Chapter 5](/learn/aio-engineer/chapter-5-threat-model)) |
| Tool defect | Fix the tool or its description |
| Policy gap | Add or narrow an approval rule ([Chapter 6](/learn/aio-engineer/chapter-6-policy-approvals)) |
| Judge blind spot | Update the rubric and recheck the judge |
| Model regression | Roll back the pin and rerun the migration playbook |

"The AI made a mistake" isn't a mechanism. Add every event to the golden set as a new scenario, so the same failure can't ship twice.

Hold the same line in public for people and agents: errors get engineered away with the same discipline, and neither gets a witch hunt. Nothing kills an agentic program faster than one bad incident treated as a betrayal instead of a defect.

## 9.5 The role, made concrete

The Field Guide names the **agent operations engineer** ([§7](/learn/aio/chapter-7-humans-on-the-loop)): the person who runs the system that runs your estate. Here is a typical week:

| Day | Work |
|---|---|
| Monday | Review the weekend's autonomous actions and any human interventions. Triage drift alerts. |
| Tuesday | Run the golden set on the pending bundle release. Review the per-class diff. |
| Wednesday | Memory upkeep block. Spot-check retrieval quality. |
| Thursday | Policy review with the autonomy owner: which classes are ready to graduate (high acceptance, clean rollbacks) and which should drop back. Send the approval-latency report to on-call leads. |
| Friday | Check red-team seeds ([Chapter 5](/learn/aio-engineer/chapter-5-threat-model)). Review cost at the boundary between the sensing and resolver engines. Publish the monthly business dashboard when it's due. |

It's a real engineering role with real leverage, and it's the career path this category creates.

**IN PRACTICE: DAY 2 IN CLOUDTHINKER**

CloudThinker runs as a fleet by design: one built-in assistant, **CloudThinker**, spawns temporary subagents for specialist work, and they share the same workspace skills and memory. A skill fix therefore reaches every agent at once. Here is where each Day-2 habit lives:

| Habit | Where it lives |
|---|---|
| Keep bundle parts as files you can diff | Download any skill as a `.zip` and edit its `SKILL.md` ([Custom skills](/guide/skills/custom-skills)). **Export active Rules** saves Rules, approver groups, and Approval modes as YAML you can keep in Git ([Rules](/guide/approvals/rules)) |
| Control model cost per agent | A custom agent's **Model Tier** field (**Light**, **Pro**, or **Ultra**) sets its tier. A tier is not a pinned model version, so treat a tier change as a deploy and rerun your golden set ([Custom agents](/guide/agents/customize)) |
| Memory upkeep | **Dreaming**, on by default, runs nightly. It merges duplicates and removes memory and custom skills that newer conversations contradict. Check **Run history** in workspace **Settings → Memory** ([Dreaming](/guide/memory-dreaming)) |
| Review and correct memory by hand | Workspace **Settings → Memory**: browse, edit, or delete items ([Memory](/guide/memory)) |
| Close the loop on incidents | Settle each remediation suggestion with **Mark as Done** or **Dismiss** plus a note on what you did. A recorded fix stays **Unverified** until a follow-up check marks it **Verified** or **Failed** ([Incident memory](/guide/incident/incident-memory)) |
| Review scheduled work | **Automations → Runs** lists every run with its status and conversation ([Automations](/guide/automation/automations)) |
</Info>

<Tip>
**KEY TAKEAWAY**

Day 2 is a discipline. Ship versioned bundles through eval gates, run model migrations as projects with per-class diffs, maintain memory on a schedule with a named owner, and run blameless postmortems that name the mechanism and grow the golden set. Give one engineer a week that makes all of it routine. Fleets that do this improve over time; fleets that don't decay into the toil they replaced.
</Tip>
