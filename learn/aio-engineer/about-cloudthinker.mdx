CloudThinker builds Frontier Investigation Agents: agents that investigate problems across your cloud and propose fixes your engineers approve. This page maps each harness layer in the book to the product control behind it, so you can test every claim during a proof of concept.

## What you're evaluating

Every workspace has one built-in assistant, also called **CloudThinker**. It splits large tasks across temporary subagents that work in parallel, and your team can add [custom agents](/guide/agents/customize) for its own systems. The [agents overview](/guide/agents/overview) explains how they fit together.

Agents reach your systems through [connections](/guide/connections/overview), the saved credentials CloudThinker uses for one service: AWS, Azure, Google Cloud, Kubernetes, databases, observability tools, and more. A [Worker](/guide/workers) (beta) runs file and shell work in a folder on a machine you control, over an outbound connection with no inbound port.

All six products share the same connections, the same [Approvals](/guide/approvals/overview) system, and the same [audit log](/guide/security/audit-logs).

| Product | What it does | Start here |
| :---- | :---- | :---- |
| **Resolve** | Groups alerts with Pulse, then investigates incidents and finds the root cause | [Resolve overview](/guide/incident/overview) |
| **Review** | Reviews every pull or merge request and posts findings as comments | [Review overview](/guide/code-review/overview) |
| **Cyber** | Tests your running web apps and APIs and proves each finding with evidence | [Cyber overview](/guide/security/cyber-overview) |
| **Optimize** | Scans cloud billing read-only and ranks savings findings | [Optimize overview](/guide/cost-optimization/overview) |
| **Customize** | Shapes how agents work: custom agents, skills, knowledge, credentials, and approvals | [Customize](/guide/agents/customize) |
| **Automation** | Runs saved instructions on a schedule, a webhook call, a repository event, or a probe | [Automations](/guide/automation/automations) |

## Where each harness layer lives

Each row points to the chapter that explains the pattern and the control you can open in the product.

| Harness layer | Chapter | CloudThinker control |
| :---- | :---- | :---- |
| Read-only versus change-making commands | [1](/learn/aio-engineer/chapter-1-agent-anatomy) | Reads run freely. Every write goes through [Approvals](/guide/approvals/overview). |
| Context before action | [2](/learn/aio-engineer/chapter-2-context-engineering) | **Discovery** runs one background investigation when a [connection](/guide/connections/overview) first reaches **Connected**, and cites the read behind each fact. Results fill the **Discovery** section of the connection's detail panel. |
| Structured memory | [2](/learn/aio-engineer/chapter-2-context-engineering) | [Incident memory](/guide/incident/incident-memory) records symptom, cause, and fix. Admins can edit or delete any [memory](/guide/memory) item. |
| Skills and tool risk | [3](/learn/aio-engineer/chapter-3-tools-skills-protocol) | A [skill](/guide/skills/overview) is a `SKILL.md` file. Risk is decided at the call by the always-blocked list, then [Rules](/guide/approvals/rules), then the Approval mode. |
| Protocol layer | [3](/learn/aio-engineer/chapter-3-tools-skills-protocol) | Your own [MCP server](/guide/connections/mcp) becomes a connection, with its tools sorted into reads and writes. |
| Two engines: sense, then resolve | [4](/learn/aio-engineer/chapter-4-orchestration-economics) | [Pulse](/guide/pulse/overview) suppresses noise and clusters alerts. [Investigations](/guide/incident/root-cause-analysis) run only on incidents. |
| Sensitive data kept from models | [5](/learn/aio-engineer/chapter-5-threat-model) | [Guardrails](/guide/security/custom-guardrails) show agents a placeholder instead of secrets, emails, card numbers, and your own ID patterns. |
| Sandboxed execution | [5](/learn/aio-engineer/chapter-5-threat-model) | Commands run in an isolated, CloudThinker-managed sandbox. Shell commands on a Worker run on your machine (see the warning below). See the [security overview](/guide/security/overview). |
| Policy as code | [6](/learn/aio-engineer/chapter-6-policy-approvals) | **Export active Rules** on the [Rules](/guide/approvals/rules) page downloads Rules, approver groups, and Approval modes as YAML. |
| Autonomy levels | [6](/learn/aio-engineer/chapter-6-policy-approvals) | Two [Approval modes](/guide/approvals/approval-mode): **Manual** (a person approves every write) or **Auto** (Rules first, optional AI judgment, then ask a person or refuse). |
| Evaluation | [7](/learn/aio-engineer/chapter-7-evaluating-agents) | There's no built-in golden-set replay harness. Run your evaluation outside the product with the [Appendix A](/learn/aio-engineer/appendix-a-poc-test-plan) method. |
| Observing the agents | [8](/learn/aio-engineer/chapter-8-observing-the-observer) | Tool calls and **Show reasoning** in each conversation. Agent actions in **Admin Settings → Audit Logs**. Spend in **Admin Settings → Usage**. |
| Day 2 budgets | [9](/learn/aio-engineer/chapter-9-agentops-day-2) | [Credit limits](/guide/billing/credit-limits) set a monthly budget per workspace, with **Throttle** or **Notify only**. |
| Kill switch | [6](/learn/aio-engineer/chapter-6-policy-approvals) | No single halt-all switch. The control that works today is **Allow writes**: turn it off on a connection and every change on that connection is refused. Setting each run type to **Manual** sends its writes to a person, but that alone isn't a halt, because a chat can pick its own mode in the composer. Turn off **On duty** in Resolve to stop automatic investigations, and switch off an automation's triggers to stop its runs. Once CloudThinker turns on [Rule enforcement](/guide/approvals/rules#troubleshooting) for your workspace, Rules add a broader halt. A **Deny** [Rule](/guide/approvals/rules) for every operation, on every connection, with **Never allow break-glass** on, refuses every agent write in every mode while reads keep running. |
| Standing missions | [12](/learn/aio-engineer/chapter-12-autonomous-mission-loop) | [Automations](/guide/automation/automations), with limits for unattended work set under [autonomous agents](/guide/automation/autonomous-agents). |
| Model calls on your own account | | [BYOK](/guide/byok) lets you bring your own LLM credentials. |
| Data residency | | [Deployment options](/guide/deployment/overview): Workers today, plus dedicated and self-hosted deployments through an early-access program. |

<Warning>
Shell commands on a [Worker](/guide/workers) aren't sandboxed. They can read `~/.ssh`, write outside the folder, and reach your network. Run the Worker under a dedicated, non-admin account, keep SSH keys and cloud credentials out of its home folder, and use [Approvals](/guide/approvals/overview) to decide which writes need a person.
</Warning>

<Note>
Audit Logs and Credit limits need a Scale, Scale Plus, or Enterprise plan. See [Pricing](/guide/billing/pricing).
</Note>
