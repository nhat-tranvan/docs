Autonomous operations are agent runs that start without anyone typing a prompt: automations firing on a trigger, and Pulse sorting your monitoring alerts. Set three things before you rely on them: the Approval mode for unattended runs, Rules for routine writes, and notifications for anything that needs a person.

## What runs without a live prompt

| Surface | What it does on its own | Configure it in |
|---------|-------------------------|-----------------|
| **Automations** | Runs saved instructions on a schedule, a webhook call, a repository event, or a probe script the agent wrote | [Automations](/guide/automation/automations) |
| **Pulse** | Groups incoming alerts into clusters, drops noise, and hands actionable ones to triage | [Pulse](/guide/pulse/overview) |

Every automation run keeps its conversation, so you can open any run and read what the agent checked and did. A chat reply can also end with a proposed automation, but nothing runs until an Admin selects **Enable**.

## Prerequisites

- The workspace Admin role. Only admins can change Approval modes, Rules, and automations.
- At least one automation (see the [Automation quickstart](/guide/automation/quickstart))

## How a write is decided

Reads always run. Every write goes through [Approvals](/guide/approvals/overview), whichever surface started it:

| The agent wants to | What decides |
|--------------------|--------------|
| Read data | Nothing. It runs. |
| Make a write a Rule covers | The Rule: **Allow** runs it, **Ask first** waits for a person, **Deny** refuses it |
| Make a write no Rule covers | The run's Approval mode |
| Make a call that is **Always blocked** | Nothing. It never runs. [Always blocked](/guide/approvals/overview#how-a-write-is-decided) is CloudThinker's built-in list of calls that no Rule or person can allow. |

When several Rules match one write, **Deny** beats **Ask first**, and **Ask first** beats **Allow**.

There are two modes, **Manual** and **Auto**. Auto ends in one of two fallbacks for a write nothing else allowed: **Refuse** or **Ask me**. So an automation's picker offers choices such as **Auto · Rules + AI · Refuse**, **Auto · Rules + AI · Ask me**, and **Manual**.

<AutonomyModes />

Automations use **Auto · Rules + AI · Refuse** by default. No one may be online to answer, so a write that AI judgment won't allow is refused instead of left waiting.

## Set the limits

<Steps>
  <Step title="Choose the mode for all automations">
    Open **Approvals** in the sidebar, then the **Approval mode** tab. Under **Run types**, find **Automations**. Keep the built-in default, or select **Override** and pick another mode. Select **Reset** to undo an override.

    Pick **Auto · Rules + AI · Ask me** if someone watches notifications and you'd rather a write wait than fail.

    **Success state:** the **Automations** row shows the mode you picked.
  </Step>
  <Step title="Allow the writes your automations make every time">
    On the **Rules** tab, accept an **Allow** Rule for each routine write, with **Runs from** set to **Automations**. A Rule decides the same way in every Auto choice, so a nightly run doesn't depend on AI judgment. See [Rules](/guide/approvals/rules).
  </Step>
  <Step title="Set one automation's mode if it needs it">
    Open the automation and use the **Approval** picker beside the model picker under its instructions. **Default** follows the **Automations** run type.

    <Warning>
    A mode set here wins over the run type and the workspace, even when it's looser. Only Admins can change it, and the edit is recorded in [audit logs](/guide/security/audit-logs) as an automation update.
    </Warning>
  </Step>
  <Step title="Route the notifications that need a person">
    Open **Notifications**. Under **What to notify me about**, open **Agents & Tasks** and turn on a channel for the events below. Alerts an agent raises are a separate row, **Agent alerts** under **Alerts**. See [Notifications](/guide/notifications).

    **Success state:** each event shows at least one channel turned on.
  </Step>
</Steps>

| Notification | Sent when |
|--------------|-----------|
| **Agent approvals** | A write is waiting for a person, and when it's approved or rejected |
| **Automation run failed** | A run fails for the first time after a success |
| **Automation turned off** | An automation stops after 10 failed runs in a row, or after a plan change |
| **Automation resource missing** | A run can't start because something it needs was deleted |
| **Watched condition met** | An automation reports the condition it was set to watch for is met. **Agent alerts** is different: any alert an agent raises, filtered by severity. |
| **Agent reduced its monitoring** | An unattended run paused or removed one of its own triggers, or made a probe check less often |

<Note>
**Automation run failed** fires once, on the first failure after a success. Later failures in a row send nothing until **Automation turned off** at the tenth.
</Note>

## What an unattended run can change about itself

An agent running an automation can manage that automation's triggers, for example removing a probe once an incident is closed. The limits:

- **Only its own automation.** An unattended run can't edit any other automation.
- **Loosening is reported.** Turning the automation off, pausing or removing a trigger, or making a probe check less often sends the owner **Automation turned off** or **Agent reduced its monitoring**. A stop shows the reason on the automation, such as "Stopped by the agent: the incident is closed".
- **Every change is recorded** in [audit logs](/guide/security/audit-logs) with the agent as the actor.

The owner is the person who created the automation. If the owner loses access to the workspace, their automations turn off and show "Its owner no longer has access to this workspace." A workspace admin can then select **Take ownership** in that notice on the automation's page. Ownership can't be moved ahead of time, only after the owner loses access. The automation stays off until someone turns it back on.

## Examples

- **Read-only daily report.** An automation summarizes cost every morning. It only reads, so no approval is involved and nobody is woken. The report waits in the run's conversation.
- **A comment on every new pull request.** A repository trigger fires on **Opened**, and the run needs to post a comment. Add an **Allow** Rule for that comment on the repository's connection, with **Runs from** set to **Automations**, and it posts every time. Without a Rule it depends on AI judgment, and anything AI judgment doesn't allow is refused, so don't rely on it for a write you want every run.

## Troubleshooting

<AccordionGroup>
  <Accordion title="A scheduled run refused a write instead of asking">
    The default for automations is **Auto · Rules + AI · Refuse**. Accept an **Allow** Rule for that write, or set the automation or the **Automations** run type to an **Ask me** choice.
  </Accordion>
  <Accordion title="A run sits on Required Approval">
    A write is waiting for a person. Open the run's conversation from **Runs** and select **Approve** or **Decline**. Turn on **Agent approvals** so the next one reaches you.
  </Accordion>
  <Accordion title="An Allow Rule didn't let the write run">
    Check the mode first: **Manual** asks before every write, even one an Allow Rule covers. Then check that **Runs from** includes **Automations** and that the Rule names the right connection. Last, look for a **Deny** or **Ask first** Rule that matches the same write: it beats the Allow.
  </Accordion>
  <Accordion title="An automation turned itself off">
    Open it to read the reason. Ten failed runs in a row, an agent stop, or an owner losing access each turn it off. Fix the cause, use **Run now** to confirm, then turn it back on.
  </Accordion>
</AccordionGroup>
