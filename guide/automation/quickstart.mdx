In about 10 minutes you'll have an automation that checks yesterday's cloud spend every morning and alerts a Slack channel when a service jumps. It only reads billing data, and any write it attempts later still goes through your approvals.

## Prerequisites

- The workspace Admin role. Only admins can create and edit automations.
- A cloud connection with billing access, such as [AWS](/guide/connections/aws), [Google Cloud](/guide/connections/gcp), or [Azure](/guide/connections/azure)
- Slack connected to CloudThinker. See [Slack integration](/guide/slack-integration).

## Send agent alerts to Slack

The automation reports through an agent alert. Route those alerts to a channel first, so the first test reaches you.

<Steps>
  <Step title="Pick a Slack channel">
    Open **Notifications**. Under **Delivery channels**, select the Slack card (it reads **Pick a channel** until one is set) and choose the channel your team watches.

    If the card says **Upgrade to enable**, Slack delivery needs a Team plan or above. See [Pricing](/guide/billing/pricing).
  </Step>
  <Step title="Turn on agent alerts for Slack">
    Under **What to notify me about**, open **Alerts** and turn on Slack for **Agent alerts**.

    **Success state:** the Slack toggle on the **Agent alerts** row is on.
  </Step>
</Steps>

## Create the automation

<Steps>
  <Step title="Open the template">
    Open **Automations** in the sidebar and select **New automation**. Under **Or start from a template**, select **Daily cost anomaly alert**.

    The form opens with the name, the instructions, and a **Schedule** trigger for every day at 08:00 already filled in.
  </Step>
  <Step title="Tell it to alert">
    In **What should the agent do?**, add the last sentence below so a spike becomes a Slack alert. Type `#` to pick your cloud connection if the workspace has more than one.

    ```text
    Compare yesterday's spend per service against its trailing 14-day average. Report only the services more than 20% above it, with the most likely cause for each. If any service is above, raise a high-severity alert that names the service, the increase, and the cause.
    ```
  </Step>
  <Step title="Check the schedule">
    On the **Schedule** card, confirm **Daily** at 08:00, or change the time. Times are in your local time zone.
  </Step>
  <Step title="Leave the approval picker on its default">
    The **Approval** picker sits beside the model picker under the instructions. Its default follows the **Automations** run type, which is **Auto · Rules + AI · Refuse** unless an admin changed it. The section below explains what that means.
  </Step>
  <Step title="Create it">
    Select **Create automation**.

    **Success state:** the automation opens on its own page and appears in the **Automations** list with its next run time.
  </Step>
</Steps>

## Test it now

Don't wait for 08:00. Select **Run now** on the automation.

**Success state:** a run appears in **Runs** as **Running**, then **Succeeded**. Open it to read the agent's comparison in the run's conversation. If any service was more than 20% above its average, an alert also posts in your Slack channel.

A quiet day produces no Slack message, which is the point. To check the Slack path anyway, edit the instructions once to "Raise a low-severity test alert with yesterday's total spend", select **Run now**, and change them back.

## What happens if the agent tries a write

This automation only reads, so no write ever reaches approvals. If you later extend it, for example "tag the resource that caused the spike", approvals decide each write before it runs:

| Approval choice for this automation | A write no Rule covers |
|--------------------------------------|------------------------|
| **Auto · Rules + AI · Refuse** (default) | AI judgment can allow a safe, in-scope write. Anything else is refused and the run continues. |
| **Auto · Rules + AI · Ask me** | Same, but the rest waits. The run shows **Required Approval** until someone selects **Approve** or **Decline** in its conversation. |
| **Manual** | Every write waits for a person, even one an Allow Rule covers |

For a write the automation makes every day, accept an **Allow** [Rule](/guide/approvals/rules) scoped to **Automations** under **Runs from**. Then the run never depends on AI judgment or on someone being online.

## Troubleshooting

<AccordionGroup>
  <Accordion title="The run succeeded but nothing posted in Slack">
    Either no service crossed 20%, or alerts aren't routed. Read the run's conversation first. If it says it raised an alert, check that Slack is on for **Agent alerts** in **Notifications**, that the alert's severity meets the channel's threshold, and that the CloudThinker bot is in the channel.
  </Accordion>
  <Accordion title="The run failed or says it has no cost data">
    Open the run's conversation for the error. Most often the cloud connection lacks billing permissions. Check the required permissions on your connection's page, such as [AWS](/guide/connections/aws).
  </Accordion>
  <Accordion title="The run shows Required Approval">
    The agent attempted a write and your approval choice asks a person. Open the run's conversation and select **Approve** or **Decline**. If you didn't expect a write, tighten the instructions.
  </Accordion>
  <Accordion title="The automation turned itself off">
    Ten runs in a row failed. Fix the cause using **Run now**, which still works, then turn the automation back on.
  </Accordion>
</AccordionGroup>
