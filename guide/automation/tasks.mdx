Automations run a stored agent prompt from a schedule, webhook, repository event, or **Run now**. Create and manage them from **Automations**, then choose where each run executes.

## Prerequisites

- Permission to create Automations in the workspace
- Connections are optional; add a [connection](/guide/connections/overview) only when the Automation needs that service
- `@agent` mentions are optional; use one only when you want to choose an agent in the prompt. See [CloudThinker Language](/guide/language)

<Info>
Create Automations from **Automations → New automation**. The composer calendar control shown in older screens is not part of the current creation flow.
</Info>

## Create an Automation

<Steps>
  <Step title="Open Automations">
    Open **Automations** from the workspace navigation.
  </Step>
  <Step title="Select New automation">
    Select **New automation**, then choose **Create manually** to open the form. You can also start from a template or choose **Create with CloudThinker**.
  </Step>
  <Step title="Add the Automation details">
    Enter an Automation name and instructions. Connections and agent mentions are optional; include them only when the Automation needs them.

    ```text
    @kai #alert Check error logs from the last 24 hours and alert on high or critical issues
    ```
  </Step>
  <Step title="Add a trigger">
    Add a schedule when the Automation should run at a time you choose. You can also add a webhook or repository trigger, or leave the trigger empty and use **Run now**.

    For a schedule, choose **Daily**, **Weekly**, **Monthly**, **No Repeat** (a single future run), or **Custom** (a cron expression). A recurring schedule can also take an optional **Expiration** date.
  </Step>
  <Step title="Create the Automation">
    Select **Create automation**.

    **Success state:** the Automation appears in **Automations** with its trigger and next run time when it has a schedule.
  </Step>
</Steps>

## Choose how an Automation starts

An Automation can have more than one trigger. Any enabled trigger starts one run, so you can combine a schedule with an event trigger.

| Start method | When it starts a run |
|--------|----------------------|
| Schedule | At a recurring or future one-time time you choose |
| Webhook | When an authenticated external request reaches its webhook URL |
| Repository | When a matching event arrives from a connected repository |
| Run now | When you start an existing Automation manually; it does not add a trigger |

A webhook or repository trigger does not need a schedule. An Automation with no trigger starts only through **Run now**.

## Timing examples

| Timing | Prompt |
|--------|--------|
| Future one-time | `@anna #report Generate an executive infrastructure summary before the next planning meeting` |
| Daily | `@alex #report Analyze EC2 spending trends and flag anomalies over $100` |
| Every 6 hours | `@kai #alert Monitor Kubernetes pod health and alert on CrashLoopBackOff` |
| Weekly | `@oliver #report Run a security audit across all connected AWS accounts` |
| Monthly | `@anna #report Generate an executive infrastructure summary with cost, security, and performance highlights` |

<Tip>
Start with a recurring Automation that replaces work your team already does. Scope the instructions to the accounts, regions, and thresholds you need.
</Tip>

## Custom cron expressions

**Custom** takes a 5-field cron expression (`minute hour day month weekday`). The minute and hour fields accept a single value, `*`, or a step such as `*/15`; a list or range in those two fields is rejected with "This schedule format is not supported." Day, month, and weekday accept ranges and lists. `MON`–`SUN` names and `?` are converted for you.

```text
*/15 * * * *     Every 15 minutes
0 */6 * * *      Every 6 hours
0 9 * * MON-FRI  09:00 on weekdays
```

## Times and time zones

You pick schedule times in your local time zone, and CloudThinker stores them in UTC and displays each run back in your zone.

<Warning>
A recurring schedule keeps its local clock time and does not shift for daylight saving, so a run can land an hour off across a DST change.
</Warning>

## Choose where an Automation runs

Use **Run in** in the Automation form to choose **CloudThinker-managed** or an available shared outpost. The managed option is the default, and an unavailable shared outpost stays selected instead of silently falling back. See [Outpost Worker](/guide/automation/outpost-worker) to set up the worker.

## Manage Automations

Open **Automations** to manage the Automations in your workspace.

| Action | What it does |
|--------|--------------|
| View | See the triggers, next run, and status for each Automation |
| Run now | Run an existing Automation immediately; this does not create a separate trigger |
| Pause | Temporarily disable an Automation without deleting its configuration. Past run history is kept |
| Edit | Update the instructions, triggers, or agent assignment |
| Delete | Remove an Automation that is no longer needed |
| View history | Review past runs, including status, start and end time, duration, and any error message. Each run links to its conversation, where the full output lives |

## Run status

| Status | What it means |
|--------|---------------|
| **Pending** | The Automation is waiting for its next scheduled run |
| **Running** | The run is in progress |
| **Succeeded** | The last run finished successfully |
| **Failed** | The last run ended with an error |
| **Required Approval** | The run paused because an action needs a person to approve it. See [Approval](/guide/approval) |

Pair Automations with [notifications](/guide/notifications) so results reach the right people by email or Slack. Review run history periodically to tune instructions and timing.
