title: Review Workspace
description: Triage reviewed changes, settle findings, apply fixes, and merge from the Reviews page without opening your Git provider.

---

Review posts its findings on your merge requests and pull requests (MR/PRs) and keeps a copy of every review at **Review → Reviews** in CloudThinker. From there you can see what needs you, settle each finding, commit fixes, and on GitHub or GitLab merge, all in one place.

## Prerequisites

- At least one repository connected in [Review setup](/guide/code-review/setup), with one MR/PR reviewed.
- A workspace role that fits what you want to do (see [Roles](/guide/security/roles)):

| Role | What you can do here |
|---|---|
| Viewer | Browse reviews, read findings, vote on accuracy, rate reviews, ask questions, copy fix prompts |
| Developer | Everything above, plus resolve and reopen findings, apply fixes, fix all findings, re-run or stop a review, and merge |
| Admin | Everything above, plus change Review settings |

Your provider's branch protection and approval rules still apply to everything you do here. A push or merge your provider refuses fails in CloudThinker too.

## Triage the Reviews list

<Steps>
  <Step title="Open the list">
    Go to **Review → Reviews**. Every MR/PR that CloudThinker tracks sits in one of four tabs, each with a live count.

    | Tab | What it lists |
    |---|---|
    | **Needs attention** | Open MR/PRs that aren't clean yet: still in review, failed, or carrying unresolved findings |
    | **Ready to merge** | Open MR/PRs that were reviewed clean |
    | **Merged** | Merged MR/PRs, kept as history |
    | **All** | Every MR/PR in the workspace |
  </Step>
  <Step title="Narrow it down">
    Filter with **Search title or number...**, repository, author, or verdict. Use the density toggle to switch between **Comfortable** and **Compact** rows. Your filters stay applied when you switch tabs.

    **Success state:** the tab counts match your filters, and each row shows the title, author, repository, verdict, and how many findings are still unresolved.
  </Step>
</Steps>

A **verdict** is the review's overall call on the MR/PR. A **finding** is one issue the review flagged for a human to look at.

| Verdict | Meaning | Tab while open | What to do |
|---|---|---|---|
| **Approved** | Reviewed clean | Ready to merge | Merge when you're ready |
| **Review suggested** | Findings worth a look, nothing blocking | Needs attention | Skim the findings, then decide |
| **Changes requested** | At least one finding should be fixed before merge | Needs attention | Open it and work the findings |
| **In review** | A review is running | Needs attention | Wait, or open it to follow along |
| **Failed** or **Stopped** | The run ended without a complete review | Needs attention | Re-run the review (see [Re-run, fix, and merge](#re-run-fix-and-merge)) |
| **Ignored** | Skipped by a repository filter or the `@cloudthinker:ignore` marker | All only | Nothing. See [Skip a review](/guide/code-review/mention-commands#skip-a-review) |

A red **Conflict** badge next to a title means your provider reports that the MR/PR can't merge because its branches conflict. When CloudThinker has opened a fix for it, the row also links to the **Resolution MR** (or **Resolution PR**). See [Auto-resolve conflicts](/guide/code-review/conflict-resolution).

## Read a review

Click a row to open the review. The page has these tabs:

| Tab | What you get |
|---|---|
| **Overview** | The **Walkthrough**, the reviewing agent's account of what the change does and how the parts fit, followed by the MR/PR description |
| **Findings** | Every finding as an expandable card, split into **Unresolved** and **Resolved** |
| **Commits** | The commit history. Select a commit to see only its changes |
| **Pipelines** | CI runs for this MR/PR (GitHub and GitLab only). On Bitbucket and Azure DevOps, see failed runs on **Review → Pipelines** |
| **Changes** | The full diff with a file tree and search. Large files open collapsed; click the file header to expand |
| **Layers** | The diff grouped by purpose: **Core change**, **Verification**, **Records and docs**, and **Generated files**. Shown only when the review grouped the change. Use **Mark viewed** to track your progress |

The rail beside the tabs shows the **Review summary**: the verdict, unresolved findings by severity and category, and any Learnings the review cited. Below it, **Rate this review** takes 1 to 5 stars.

If an [extension](/guide/code-review/extensions) found a linked ticket, a **Ticket compliance** card rates the change **Fully compliant**, **Partially compliant**, or **Not compliant** against the ticket, with the agent's notes.

## Work the findings

<Steps>
  <Step title="Open a finding">
    On the **Findings** tab, expand a card. You see the severity, file and line, the agent's explanation, the original code and suggested fix, and a chip for any [Learning](/guide/code-review/convention-rules) it relied on.
  </Step>
  <Step title="Vote on accuracy">
    Click thumbs-up if the finding is right. Click thumbs-down if it's wrong, and describe what it got wrong in the **Inaccurate finding** note. Later reviews of the repository get your recent notes, so they don't raise the same issue again on unchanged code. This is separate from [Learnings](/guide/code-review/convention-rules).
  </Step>
  <Step title="Fix it">
    Pick the path that fits:

    | Action | What happens |
    |---|---|
    | **Apply fix** | Commits the exact suggested change to the MR/PR source branch and resolves the finding. The commit is made by the connected provider identity, with you as co-author. Available on GitHub, GitLab, and Azure DevOps, and only when the finding has a literal code change |
    | **Copy prompt** | Copies a fix instruction to paste into your own coding agent. Works on every provider |
    | **Ask** | Opens a chat scoped to this finding so you can ask why it was flagged or how else to fix it |
  </Step>
  <Step title="Settle it">
    Click **Mark resolved** once it's handled, or **Reopen** to undo. Resolving also resolves the finding's comment thread on your provider, where the provider has threads.

    **Success state:** the card moves to the **Resolved** group, and the unresolved count on the Reviews list drops.
  </Step>
</Steps>

## Ask about the whole review

Click **Ask CloudThinker** in the header. A chat drawer opens beside the review, scoped to this MR/PR and separate from the agent's own review run. Try:

```text
Summarize the riskiest change in this MR and what I should test before merging.
Which of these findings would break existing callers?
```

The drawer keeps the repository and any finding you asked from as locked context, so answers stay on this review.

## Re-run, fix, and merge

Header buttons cover the actions that change the MR/PR. Less frequent ones sit in the **More actions** (⋯) menu.

| Action | Where | What it does | Comment equivalent |
|---|---|---|---|
| **Fix all findings** | Header | CloudThinker fixes every unresolved finding and commits to the source branch. Not available on AWS CodeCommit | [`@cloudthinker-ai autofix`](/guide/code-review/mention-commands#fix-findings-with-autofix) |
| **Merge** | Header | Merges as you, through your linked GitHub or GitLab account, so the provider shows you as the merger. GitHub and GitLab only | None |
| **Re-run review** | ⋯ menu | Reviews again from the last reviewed commit. When it's unavailable, the reason shows under it | [`@cloudthinker-ai review`](/guide/code-review/mention-commands#commands) |
| **Stop review** | ⋯ menu | Stops a running review. Takes the place of **Re-run review** while a run is live | None |
| **Run Ultra review** | ⋯ menu | One deeper, slower review of the latest commit. Shown only when Ultra review is turned on for your CloudThinker instance. It isn't a workspace setting | [`@cloudthinker-ai review ultra`](/guide/code-review/mention-commands#run-an-ultra-review) |
| **View review conversation** | ⋯ menu | Opens the agent's own review run, read-only | None |
| **View in** your provider | ⋯ menu | Opens the MR/PR on GitHub, GitLab, or your provider | None |

The first time you click **Merge**, CloudThinker asks you to link your provider account. You can also do it ahead of time in **Account Settings → Linked accounts**: click **Link GitHub account** or **Link GitLab account**.

When you click **Merge**, pick a merge method (**Create a merge commit**, **Squash and merge**, or **Rebase and merge**, as your repository allows) and choose whether to **Delete source branch**. If the review requested changes, a review is still running, or the newest commits aren't reviewed yet, a **Check before you merge** warning appears and the button reads **Merge anyway**.

<Warning>
  **Fix all findings** pushes commits to the source branch without a separate approval step. On GitHub or GitLab, comment `@cloudthinker-ai autofix stacked` instead to get the fixes in their own MR/PR first.
</Warning>

## Troubleshooting

<AccordionGroup>
  <Accordion title="Apply fix is disabled">
    **Cause:** your provider is Bitbucket or AWS CodeCommit. **Apply fix** commits through the provider's file API, which CloudThinker doesn't support on those two yet. **Fix:** use **Copy prompt** and apply the change in your own tools. On Bitbucket, **Fix all findings** also works, because it pushes with Git instead.
  </Accordion>
  <Accordion title="Apply fix fails">
    **Cause:** the code changed after the review, so the original lines are gone or appear more than once, or the source branch is protected or in a fork. **Fix:** re-run the review to get a fix against the current code, or apply the change through your Git provider.
  </Accordion>
  <Accordion title="I don't see Fix all findings, Re-run review, or Mark resolved">
    **Cause:** your workspace role is Viewer. **Fix:** ask a workspace Admin for the Developer role.
  </Accordion>
  <Accordion title="Fix all findings is missing but I'm a Developer">
    **Cause:** the MR/PR has no unresolved findings left to fix. **Fix:** nothing to do. Check the **Findings** tab to confirm everything is resolved.
  </Accordion>
  <Accordion title="Re-run review is greyed out">
    **Check:** the reason under the menu item. A running review must finish or be stopped first. Merged MR/PRs keep the item visible but disabled.
  </Accordion>
  <Accordion title="An MR/PR I expected isn't listed">
    **Check:** the **All** tab with filters cleared. If it's still missing, confirm the repository is enabled and the webhook is set up in [Review setup](/guide/code-review/setup). Draft MR/PRs aren't reviewed.
  </Accordion>
</AccordionGroup>
