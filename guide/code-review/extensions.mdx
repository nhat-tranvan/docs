title: Review Extensions
description: "Connect Jira, Confluence, Linear, Backlog or your Git provider's issues so Review checks each change against the ticket it implements."
icon: puzzle-piece
---

Extensions let Review read the ticket behind a pull request (PR) or merge request (MR): when the description links a Jira issue, a Confluence page, a Linear or Backlog issue, or a GitHub or GitLab issue, the reviewer fetches it and checks whether the code does what the ticket asks. Without an extension, Review judges the diff on its own and can't tell you that an acceptance criterion was missed.

## Available extensions

| Extension | Reads | Needs |
|---|---|---|
| **Jira / Confluence** | The linked ticket (summary, acceptance criteria, linked pages) and Confluence spec pages | An [Atlassian connection](/guide/connections/atlassian) |
| **Linear** | Issue title, description, status, labels and the issue's git branch name. PR branch names aren't scanned | A [Linear connection](/guide/connections/linear) |
| **Backlog** | Issue summary, description and status | A [Backlog connection](/guide/connections/backlog) |
| **GitHub Issues** | Issues the PR references: title, body, labels and comments | Review set up on GitHub. Uses that same connection |
| **GitLab Issues** | Issues the MR references: title, description, labels and comments | Review set up on GitLab. Uses that same connection |

GitHub Issues appears only when your Review provider is GitHub, and GitLab Issues only when it's GitLab.

**Not supported:** Jira and Confluence Data Center or Server (the Atlassian connection works with Atlassian Cloud only), and Azure Boards, which has no extension. For those, paste the acceptance criteria into the PR description: Review reads the description along with the change.

## Prerequisites

- Review connected to at least one repository. See [Review setup](/guide/code-review/setup).
- To connect a tracker: the workspace **Admin** role and access to **More → Workspace settings → Connections**. Other roles see **View** instead of **Connect** on tiles. See [roles](/guide/security/roles).
- An account on the tracker that can read the projects your tickets live in.

## Turn on an extension

<Steps>
  <Step title="Open the Extensions section">
    Go to **Review → Settings** and scroll to **Extensions** ("Link tickets and specs so Review can check changes against them"). Each tracker has a tile with its status.

    | Tile status | Meaning |
    |---|---|
    | **Connected** | Review already fetches tickets from it |
    | **Not connected** | No connection yet. Click **Connect** |
    | **Uses your GitHub connection** (or GitLab) | Works through your Review provider. Nothing to set up |
    | **Status unavailable** | The connection list didn't load. Refresh the page |
  </Step>
  <Step title="Connect the tracker">
    Click **Connect** on the tile. CloudThinker opens **More → Workspace settings → Connections** with that connection's form ready. Fill it in using the connection guide for [Atlassian](/guide/connections/atlassian), [Linear](/guide/connections/linear) or [Backlog](/guide/connections/backlog), then save.

    **Success state:** back in **Review → Settings → Extensions**, the tile shows **Connected**.
  </Step>
  <Step title="Reference the ticket in the PR description">
    Put the ticket link or key in the PR or MR description. No command or setting is needed.

    | Tracker | Write this in the description |
    |---|---|
    | Jira | `https://myorg.atlassian.net/browse/OPS-1234` or `OPS-1234` |
    | Confluence | `https://myorg.atlassian.net/wiki/spaces/ENG/pages/123456/API-contract`. Confluence has no short key, so use the page URL |
    | Linear | `https://linear.app/myorg/issue/ENG-123/slug` or `ENG-123` |
    | Backlog | `https://myspace.backlog.com/view/PROJ-123` or `PROJ-123` |
    | GitHub or GitLab issues | `Closes #123`, `Fixes #456` or `#123` for the PR's own repository. `org/repo#123` or the issue URL for another repository |

    Jira, Linear and Backlog keys look alike. With one of them connected, a bare key such as `OPS-1234` goes to that tracker. With more than one connected, the reviewer has to try each, and a key that exists in two trackers can match the wrong ticket.

    <Tip>
    With more than one key-based tracker connected, always use full ticket URLs.
    </Tip>
  </Step>
  <Step title="Open the PR and read the review">
    The review runs as usual. Findings now cover gaps against the ticket as well as the code itself.

    **Success state:** when the change misses part of the ticket, the review findings say which part.
  </Step>
</Steps>

Click **Manage** on a connected tile, or **View** on any other, to see what that extension reads and the patterns it recognizes.

An extension is on whenever the workspace has that connection, including one first made for chat or another agent. It applies to every repository Review covers. There's no separate switch or per-repository setting.

<Warning>
To stop Review reading a tracker, you have to disconnect it in **More → Workspace settings → Connections**. That removes the connection for every agent and chat in the workspace, not only Review.
</Warning>

## Example

A PR description like this:

```markdown
Add rate limiting to the login endpoint.

Implements OPS-1234. Spec: https://myorg.atlassian.net/wiki/spaces/ENG/pages/123456
```

Say OPS-1234 lists "return 429 with a Retry-After header" as an acceptance criterion, and the diff returns 429 without the header. With the Jira extension, the reviewer has that criterion in front of it and can flag the missing header against the ticket, for example: "The login endpoint returns 429 without the Retry-After header that OPS-1234 requires." Without it, the same diff looks correct.

In the [review workspace](/guide/code-review/review-workspace), a **Ticket compliance** card also rates the change **Fully compliant**, **Partially compliant** or **Not compliant** against the ticket. It works in any review mode. The card shows when exactly one Jira or Linear ticket was checked. With several tickets, or a Backlog ticket or Git issue, the review summary comment has a table instead, with one verdict per ticket.

## What gets read

- **The description only.** Review scans the PR or MR description for links and keys.
- **Not code.** A key inside a code block or inline code (`` `OPS-1234` ``) is ignored, so example IDs in snippets don't trigger lookups.
- **Up to 20 references per PR**, taken from the first 65,535 characters of the description. Put the ticket that matters most first.
- **Tickets your connection can see.** Review reads with the connected account's access, so a ticket in a project that account can't open isn't available to the review.
- **Shown to your workspace.** What the reviewer takes from a ticket can appear in findings. Those show in the review comments on the PR and to anyone with access to Review in the workspace. On a public repository, anyone who can see the PR can read those comments, so keep confidential detail out of tickets you link there. See [data protection](/guide/security/data-protection).

## Write tickets that help the review

- **List acceptance criteria as separate lines.** Each one becomes something the reviewer can check. "Works well" can't be checked; "returns 429 after 5 failed attempts in 1 minute" can.
- **Link the spec, not just the ticket.** A Confluence page with the API contract gives the reviewer the exact field names and status codes.
- **Reference every ticket the PR closes.** A PR that fixes two bugs should name both.

## Troubleshooting

<AccordionGroup>
  <Accordion title="The review doesn't mention the ticket">
    **Check:** the reference is in the description, not only the branch name or commit message, and not inside backticks or a code block. Confirm the tile shows **Connected**.

    **Fix:** edit the description, then comment `@cloudthinker-ai review` on the PR so the review runs again and reads the new description. On AWS CodeCommit, push a new commit to the PR's source branch instead. See [mention commands](/guide/code-review/mention-commands).
  </Accordion>
  <Accordion title="I don't see GitHub Issues or GitLab Issues">
    Those tiles appear only for the matching Review provider. On Bitbucket, Azure DevOps or AWS CodeCommit, use Jira, Linear or Backlog instead.
  </Accordion>
  <Accordion title="Tiles show View instead of Connect">
    Only workspace Admins can connect trackers. Ask a workspace Admin to connect it, or to change your role. See [roles](/guide/security/roles).
  </Accordion>
  <Accordion title="The tile says Connected but a ticket isn't read">
    The connected account can't open that ticket's project. Grant it access in the tracker, or reconnect with an account that has it.
  </Accordion>
</AccordionGroup>
