Review checks every pull request (PR) or merge request (MR) against two sets of team standards: **Learnings**, which are rules CloudThinker distills from review findings your team has already resolved, and **Learning sources**, which are convention files your team writes and keeps in the repository. This page shows how to turn on both, check what Review learned, and retire a rule that no longer fits.

## Prerequisites

- A repository connected and enabled in [Review setup](/guide/code-review/setup), with cloning finished.
- Edit permission on Review to change schedules, sources or rules. With view-only access you can read Learnings but not change them.
- For Learnings, a history of resolved findings on that repository. Learning sources work from day one.

## Choose your source

| | Learnings | Learning sources |
|---|---|---|
| Where the rules come from | Recurring patterns in findings your team resolved | Files your team writes, such as `AGENTS.md` or `.cursorrules` |
| Setup | Turn on a Weekly or Monthly schedule per repository | None. Detected automatically |
| When they apply | After a run finds enough evidence | On the next review |
| Best for | Mistakes your team keeps fixing by hand | Standards you've already written down |

The two work independently. Use both when you want written standards plus the patterns Review picks up from real fixes.

## Turn on Learnings for a repository

<Steps>
  <Step title="Open the repository list">
    Go to **Review → Settings** and find the repository in the repositories table.
  </Step>
  <Step title="Pick a schedule">
    In the **Learnings** column, choose **Weekly** or **Monthly**. **Off** stops new Learnings for that repository.

    You can also start from **Review → Learnings**: when no repository is scheduled yet, the page offers **Enable weekly learning**.
  </Step>
  <Step title="Run it now (optional)">
    Go to **Review → Learnings**, click **Run now**, pick the repository and click **Run now** in the **Run Learnings now** dialog. Only repositories with a schedule appear in the picker.

    **Success state:** the **Running** card counts the repository, and **Last run** updates when the run finishes.
  </Step>
</Steps>

Scheduled runs happen on Saturdays, so new rules are in place before the work week starts. Weekly runs every Saturday, Monthly on the first Saturday of the month. The **Next run** card on **Review → Learnings** shows when the next one is due.

<Note>
A run can finish with no new Learnings. That's expected on a young repository: CloudThinker only writes a rule once the same kind of fix shows up often enough to count as a pattern.
</Note>

## Review what CloudThinker learned

Open **Review → Learnings**. Each row is one Learning, scoped to the repository whose reviews produced it.

| Column | What it shows |
|---|---|
| Learning | The rule in plain words, plus its short identifier |
| Signal | How much recent reviews rely on it (see below) |
| Category | Security, Performance, Patterns or Correctness |
| Repository | The repository the rule applies to |
| Created | When CloudThinker wrote the rule |

Filter with **Search learnings**, the repository picker, **Any category** and **Any signal**.

| Signal | Meaning |
|---|---|
| Strong | Cited often in recent reviews |
| Quiet | On, but cited rarely |
| Weak | Going stale. Retires soon unless a review cites it |
| Retired | Off. Reviews no longer use it |

Click a row to open the Learning. It shows the rule, a **Citation trend**, and **Recent citations** linking to the review findings that referenced it. A Learning with many citations points at a problem worth fixing at the source, for example with a shared helper or a lint rule.

## Retire or restore a Learning

Use the row's actions menu and choose **Retire** when you don't want Review to apply a rule. Choose **Restore** to bring it back. Retiring keeps the rule and its citations, so you lose nothing.

CloudThinker also retires a Learning on its own when no review cites or refines it for a while. The Learning's detail tells you which happened: "Retired automatically" or "Retired by" a teammate's name.

## Add your own convention files

Review reads the guideline files your team already keeps in the repository and applies them during reviews, with no setup. Recognized files include:

- `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `CONVENTIONS.md`
- `.cursorrules` and `.cursor/rules/`
- `.github/copilot-instructions.md` and `.github/instructions/`
- `.windsurfrules`, `.clinerules`, `.roorules`, `.continuerules`, and similar rule folders such as `.kiro/steering/` and `.amazonq/rules/`

When a change touches a file, the convention files nearest to it take priority, then the files at the repository root. A guideline in `services/payments/AGENTS.md` speaks to payments code; one at the root speaks to everything.

To see or extend what Review reads:

<Steps>
  <Step title="Open Learning sources">
    In **Review → Settings**, open the repository's actions menu and select **Learning sources**.
  </Step>
  <Step title="Check what was found">
    **Detected sources** lists the files Review found. Keep **Detect sources automatically** on so Review checks for new files before every review.
  </Step>
  <Step title="Add custom paths">
    Under **Custom convention paths**, add up to 10 repository-relative paths, for example `docs/style-guide.md`. Paths can't start with `/` or contain `..`. Click **Save**.

    **Success state:** the next review on that repository follows the added file.
  </Step>
</Steps>

## Troubleshooting

<AccordionGroup>
  <Accordion title="Review → Learnings is empty">
    Check that the repository has a **Weekly** or **Monthly** schedule in **Review → Settings** and has finished cloning. If **Last run** shows a finished run, the repository doesn't yet have enough resolved findings to form a pattern. Keep resolving findings and wait for the next scheduled run.
  </Accordion>
  <Accordion title="Run now shows No scheduled repositories">
    **Run now** only lists repositories with a schedule. Set one in the **Learnings** column of **Review → Settings**, then try again.
  </Accordion>
  <Accordion title="The schedule shows Paused while Review is off">
    Learnings pause when Review is turned off for that repository. Turn Review back on for the repository and the schedule resumes.
  </Accordion>
  <Accordion title="Review ignores a guideline file">
    Open **Learning sources** and check whether the file appears under **Detected sources**. If it doesn't, add its path under **Custom convention paths**.
  </Accordion>
  <Accordion title="A Learning is wrong for our codebase">
    Retire it from the row's actions menu. Review stops applying it on the next review, and you can restore it later.
  </Accordion>
</AccordionGroup>
