A pipeline is your CI system's build-and-test run for a commit. With pipeline analysis on, Review picks up each failed run, reads the failed jobs, and writes findings that explain why it broke and how to fix it.

## Prerequisites

- A repository connected through [Review setup](/guide/code-review/setup) with webhooks configured, so your provider sends pipeline events.
- A supported provider: GitHub, GitLab, Bitbucket or Azure DevOps. AWS CodeCommit repositories don't support pipeline analysis.
- Edit permission on Review to turn analysis on or start one by hand.

## Turn on pipeline analysis

Pipeline analysis is a workspace-wide setting and is off by default.

<Steps>
  <Step title="Open Review settings">
    Go to **Review → Settings**.
  </Step>
  <Step title="Switch it on">
    In the **General** section, turn on **Pipeline analysis**. You can also click **Turn on** in the banner at the top of **Review → Pipelines**.

    **Success state:** the toast reads "Pipeline analysis enabled", and new CI runs from your connected repositories start to appear on **Review → Pipelines**.
  </Step>
</Steps>

## How a failed run becomes findings

1. Your provider sends a pipeline event, and Review records the run with its status and commit.
2. Only failed runs are analyzed. Successful, running, pending and cancelled runs are listed but never analyzed, and a run is never analyzed twice.
3. Review fetches the failed jobs and, when the run belongs to a reviewed MR or PR, links it so the analysis can use that change's review context.
4. CloudThinker analyzes the failed jobs in its own conversation and writes root-cause findings with a suggested fix.

## Check a failed run

<Steps>
  <Step title="Open the run list">
    Go to **Review → Pipelines**. Each row shows the run **Status**, the **Pipeline** (repository, number and commit), and the **Analysis** state. Narrow the list with **Search runs**, **Any status** and **Any analysis**.
  </Step>
  <Step title="Start an analysis if one hasn't run">
    A failed run marked **Not analyzed** shows an **Analyze** button. Click it to start without waiting.

    **Success state:** the toast reads "Pipeline analysis started" and the row moves to **Analyzing**.
  </Step>
  <Step title="Read the findings">
    Open the run. **Pipeline jobs** shows each stage and job with its status. **Findings** lists the root causes with **Severity**, **Issue**, **Location** and **Status**. Open a finding for its **Description** and **Suggested Fix**.
  </Step>
  <Step title="Hand the fix off">
    On a finding, click **Copy prompt** to copy a ready-made fix request for your coding agent, or **View file** to jump to the failing code on your provider. On the run list, click an **Analyzed** badge to open the full analysis in Chat.
  </Step>
</Steps>

The list uses two kinds of status:

| Run status | Meaning |
|---|---|
| Pending, Running | The pipeline hasn't finished on your provider |
| Success | It passed. No analysis |
| Failed | It failed and can be analyzed |
| Cancelled | It was cancelled. No analysis |

| Analysis | Meaning |
|---|---|
| Not analyzed | A failed run waiting for analysis |
| Analyzing | CloudThinker is reading the failed jobs |
| Analyzed | Findings are ready |
| Analysis failed | Fetching the jobs or starting the analysis failed |

## Repository reports

For a weekly view of each repository, rather than one run at a time, Review generates two PDFs per repository: a **Technical PDF** for engineers and a **Product PDF** for leaders.

<Steps>
  <Step title="Open the Reports tab">
    Go to **Review → Insights** and select **Reports**. Reports are grouped by period, with each row showing **Repository**, **Generated**, **Trends**, **Actions**, **Status** and **PDFs**.
  </Step>
  <Step title="Choose how reports run">
    Turn on **Scheduled reports** to generate them every week, or click **Generate now** for a run today.
  </Step>
  <Step title="Download the PDFs">
    Open a completed row to see the **Repository report** panel, then download the **Technical PDF** or **Product PDF**. A failed row offers **Retry**.
  </Step>
</Steps>

After a scheduled run, workspace admins get a **Reports ready** notification. Turning the schedule off keeps existing reports. Review also sends a separate **Weekly Review digest** email summarizing the week's review activity. Manage both under Review in [notification settings](/guide/notifications).

## Troubleshooting

<AccordionGroup>
  <Accordion title="Review → Pipelines says No pipeline runs yet">
    Check that **Pipeline analysis** is on and that your provider's webhook is set up to send pipeline events. Then push a commit that runs a pipeline.
  </Accordion>
  <Accordion title="The page says Pipeline analysis unavailable">
    Pipeline analysis is off for this workspace and you don't have permission to turn it on. Ask a workspace admin.
  </Accordion>
  <Accordion title="A failed run shows Analysis failed">
    Review couldn't fetch the failed jobs from your provider or couldn't start the analysis. Check that your Git connection is healthy in [Review setup](/guide/code-review/setup), then rerun the pipeline on your provider.
  </Accordion>
  <Accordion title="I don't see the Analyze button">
    The button only shows on failed runs that haven't been analyzed, and only to people with edit permission on Review.
  </Accordion>
</AccordionGroup>
