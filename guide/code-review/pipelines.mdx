A pipeline is your CI system's build-and-test run for a commit. With pipeline analysis on, Review picks up each failed run, reads the failed jobs, and writes findings that explain why it broke and how to fix it.

## Prerequisites

- A repository connected through [Review setup](/guide/code-review/setup), with its provider sending pipeline events:

  | Provider | What sends pipeline events | CI analyzed |
  |---|---|---|
  | GitHub | The CloudThinker GitHub App | GitHub Actions workflow runs |
  | Bitbucket | Registered for you during setup | Bitbucket Pipelines |
  | GitLab | The **Pipeline events** trigger on your webhook | GitLab CI/CD pipelines |
  | Azure DevOps | A **Build completed** service hook | Azure Pipelines builds |

  Review fetches jobs and logs from these CI systems only, so runs from other CI tools, such as check runs another tool posts on GitHub, aren't analyzed. See [Configure webhooks](/guide/code-review/provider-auth#configure-webhooks). AWS CodeCommit repositories don't support pipeline analysis.
- The workspace **Admin** role to turn analysis on or start one by hand. Everyone else can read runs and findings. See [roles](/guide/security/roles).

## Turn on pipeline analysis

Pipeline analysis is a workspace-wide setting and is off by default. There's no per-repository switch: once it's on, every failed run from a connected repository that sends pipeline events is analyzed.

<Steps>
  <Step title="Open Review settings">
    Go to **Review → Settings**.
  </Step>
  <Step title="Switch it on">
    In the **Review** section, turn on **Pipeline analysis**. You can also click **Turn on** in the banner at the top of **Review → Pipelines**.

    **Success state:** the toast reads "Pipeline analysis enabled", and new CI runs from your connected repositories start to appear on **Review → Pipelines**.
  </Step>
</Steps>

## How a failed run becomes findings

1. Your provider sends a pipeline event, and Review records the run with its status and commit.
2. Only failed runs are analyzed. Successful, running, pending and cancelled runs are listed but never analyzed, and a run is never analyzed twice.
3. Review fetches the failed jobs and the last 50 KB of each job's log through your Git connection. When the run belongs to a reviewed MR or PR, Review links it so the analysis can use that change's review context.
4. CloudThinker analyzes the failed jobs in a Chat conversation and writes root-cause findings with a suggested fix. Workspace admins get a **Pipeline analysis** notification when it finds issues. Choose where it goes in [notification settings](/guide/notifications).

<Note>
Only the last 50 KB of each failed job's log is read. If the real error comes earlier, for example a compile error followed by a long test dump, the analysis can miss it. Fail fast, or trim verbose output from the job, so the error lands near the end of the log.
</Note>

The analysis is an agent conversation, so the [data protection](/guide/security/data-protection) rules for tool output apply to the logs it reads.

## Check a failed run

<Steps>
  <Step title="Open the run list">
    Go to **Review → Pipelines**. Each row shows the run **Status**, the **Pipeline** (repository, number and commit), and the **Analysis** state. Narrow the list with **Search runs**, **Any status** and **Any analysis**.
  </Step>
  <Step title="Start an analysis if one hasn't run">
    A failed run marked **Not analyzed** shows an **Analyze** button. Click it to start without waiting.

    **Success state:** the toast reads "Pipeline analysis started" and the row moves to **Analyzing**.
  </Step>
  <Step title="Read the findings">
    Open the run. **Pipeline jobs** shows each stage and job with its status. **Findings** lists the root causes with **Severity**, **Issue**, **Location** and **Status**. Status reads **Open** until someone settles the finding, then **Resolved**, **Acknowledged** or **Withdrawn**. Open a finding for its **Description** and **Suggested Fix**.
  </Step>
  <Step title="Hand the fix off">
    On a finding, click **Copy prompt** to copy a ready-made fix request for your coding agent, or **View file** to jump to the failing code on your provider. On the run list, click an **Analyzed** badge to open the full analysis in Chat.
  </Step>
</Steps>

The list uses two kinds of status:

| Run status | Meaning |
|---|---|
| Pending, Running | The pipeline hasn't finished on your provider |
| Success | It passed. No analysis |
| Failed | It failed and can be analyzed |
| Cancelled | It was cancelled. No analysis |

| Analysis | Meaning |
|---|---|
| Not analyzed | A failed run waiting for analysis |
| Analyzing | CloudThinker is reading the failed jobs |
| Analyzed | Findings are ready |
| Analysis failed | Fetching the jobs or starting the analysis failed. There's no retry button: rerun the pipeline on your provider to get a new run |

## Troubleshooting

<AccordionGroup>
  <Accordion title="Review → Pipelines says No pipeline runs yet">
    Check that **Pipeline analysis** is on and that your provider's webhook is set up to send pipeline events. Then push a commit that runs a pipeline.
  </Accordion>
  <Accordion title="The page says Pipeline analysis unavailable">
    Pipeline analysis is off for this workspace and you don't have the workspace Admin role. Ask a workspace Admin to turn it on.
  </Accordion>
  <Accordion title="A failed run shows Analysis failed">
    Review couldn't fetch the failed jobs from your provider or couldn't start the analysis. A run is analyzed only once, so check that your Git connection is healthy in [Review setup](/guide/code-review/setup), then rerun the pipeline on your provider to get a new run.
  </Accordion>
  <Accordion title="I don't see the Analyze button">
    The button only shows on failed runs marked **Not analyzed**, and only to workspace Admins.
  </Accordion>
</AccordionGroup>
