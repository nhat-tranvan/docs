Review is CloudThinker's code review product: when someone opens a pull request (PR) or merge request (MR), CloudThinker reads the change, posts a summary comment and inline findings on it, and checks the fix when you push again. You connect your Git provider once and pick repositories, and it runs without anyone starting it.

<ReviewScene />

A linter matches patterns. Review reads what the change is trying to do: the diff, the linked ticket, your team's convention files and, if you keep one, a `BUSINESS.md` that describes the rules your product must keep. That lets it flag a broken business rule or a risky migration, not only a style slip.

## How it works

1. **A PR or MR opens.** Your provider sends an event to CloudThinker. Draft PRs and MRs are skipped until they're marked ready for review.
2. **CloudThinker gathers context.** It checks out the change and reads the diff, a ticket linked from the description (Jira, Linear, Backlog or a provider issue, when that connection exists), and the convention files in the repository.
3. **The review runs.** Depth depends on the workspace [review mode](/guide/code-review/setup#choose-a-review-mode): **Fast**, **Auto** or **Advanced**.
4. **Findings land on the PR.** You get one summary comment plus inline comments. Each finding has a severity (Critical, High, Medium or Low) and a suggested fix.
5. **New pushes get an incremental review.** Only the commits pushed since the last review are read, and the review checks whether earlier findings were fixed.

Tests, fixtures, snapshots, generated code and Storybook stories are left out of every review automatically.

## What it checks

Each finding carries one category, so you can tell at a glance what kind of problem it is.

| Category | What it catches | Example |
|---|---|---|
| Security | Injection, exposed secrets, unsafe auth or permissions | A query built from request input without parameters |
| Correctness | Logic errors, null handling, race conditions | A lost update when two requests write the same row |
| Performance | Slow queries, N+1 loops, blocking calls | A full table scan inside a request handler |
| Pattern | Breaks a convention your repository already follows | A new handler that skips the shared error wrapper |
| Deploy, migration, backward compatibility | Changes that break a rollout or existing clients | A migration that drops a column the current release still reads |
| Test gap | A test that mocks the wrong thing | A patch that targets a symbol the code no longer calls |
| Business flow | A change that breaks a rule in your `BUSINESS.md` | A path that reports a recommendation as an executed change |

## What you can do

| Capability | What you get | Learn more |
|---|---|---|
| Automatic review | A summary and inline findings on every new PR or MR | [Set up Review](/guide/code-review/setup) |
| Review workspace | Every reviewed change, its findings and status, in CloudThinker | [Review workspace](/guide/code-review/review-workspace) |
| Mention commands | Ask a question, re-run a review or fix findings with `@cloudthinker-ai` in a PR comment | [Mention commands](/guide/code-review/mention-commands) |

| Pipeline analysis | An explanation and suggested fix for each failed CI run | [Pipelines](/guide/code-review/pipelines) |
| Conflict resolution | A follow-up MR that resolves merge conflicts on an open MR | [Conflict resolution](/guide/code-review/conflict-resolution) |
| Releases | A risk report when a release tag is pushed | [Releases](/guide/code-review/releases) |
| Insights | Which finding categories hit your team, and how fast they get fixed | [Insights](/guide/code-review/analytics) |

## Supported providers

GitHub, GitLab (GitLab.com or self-hosted), Bitbucket Cloud, Azure DevOps and AWS CodeCommit. Each workspace connects one provider. See [provider authentication](/guide/code-review/provider-auth) for what each one needs.
