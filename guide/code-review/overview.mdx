Review is the Frontier Investigation Agent for code changes: an AI reviewer for your pull requests (PRs) and merge requests (MRs). When someone opens one, CloudThinker reads the change, posts a summary comment and inline findings on it, and checks the fix when you push again. You connect your Git provider once and pick repositories, and it runs without anyone starting it.

<ReviewScene />

A linter matches patterns. Review reads what the change is trying to do: the diff, the linked ticket, your team's convention files and, if you keep one, a `BUSINESS.md` that describes the rules your product must keep. That lets it flag a broken business rule or a risky migration, not only a style slip.

## How it works

1. **A PR or MR opens.** Your provider sends an event to CloudThinker. Draft PRs and MRs are skipped until they're marked ready for review.
2. **CloudThinker gathers context.** It checks out the change and reads the diff, a ticket linked from the description (Jira, Linear, Backlog or a provider issue, once you add an [extension](/guide/code-review/extensions)), and the files listed in [What Review reads](#what-review-reads).
3. **The review runs.** Depth depends on the workspace [review mode](/guide/code-review/setup#choose-a-review-mode): **Fast**, **Auto** or **Advanced**. Each review uses credits; see [usage and credits](/guide/billing/usage).
4. **Findings land on the PR.** You get one summary comment plus inline comments. Each finding has a severity (Critical, High, Medium or Low) and a suggested fix.
5. **New pushes get an incremental review.** Only the commits pushed since the last review are read, and the review checks whether earlier findings were fixed.

The unresolved findings set the review's verdict:

| Unresolved findings | Verdict |
|---|---|
| Any Critical or High | **Changes requested** |
| Only Medium or Low | **Review suggested** |
| None | **Approved** |

The verdict is CloudThinker's label on the change. Your provider's branch rules still decide whether it can merge. While a review runs, or when it doesn't complete or is skipped, the change shows **In review**, **Failed**, **Stopped** or **Ignored** instead. See [verdicts](/guide/code-review/review-workspace#triage-the-reviews-list).

<Note>
  CloudThinker clones each selected repository into a sandbox to read it. **Remove setup** tears that sandbox down. Secrets in tool output are replaced with placeholders before the model sees them; see [data protection](/guide/security/data-protection).
</Note>

Changed test files, fixtures, snapshots, generated code and Storybook stories aren't reviewed: no finding is ever placed in one. Matching is by file path only. The common patterns:

| Kind of file | Example path patterns |
|---|---|
| Tests | `test_*.py`, `*_test.py`, `conftest.py`, `*_test.go`, `*.test.ts`, `*.spec.tsx`, `*_spec.rb`, `*Test.java`, `__tests__/` |
| Fixtures and test data | `fixtures/`, `testdata/` |
| Snapshots | `__snapshots__/`, `*.snap` |
| Generated code | `*.generated.*`, `*.gen.go`, `*.pb.go` |
| Storybook stories | `*.stories.tsx`, `*.stories.mdx` |
| Other | `prototypes/`, HTML under `docs/`, vendored `*.jsonnet` and `*.libsonnet`, and every Solidity file under a top-level `lib/` folder (`lib/**/*.sol`) |

The list is built in, so you can't add your own patterns. If your own Solidity contracts live in a top-level `lib/` folder, they won't be reviewed. File headers such as "generated, do not edit" aren't checked. Review still knows these files are part of the change, so it won't report a missing test that the PR adds.

## What Review reads

Besides the diff, Review reads these files from your repository. All of them are optional.

| File | Where it goes | What it does |
|---|---|---|
| `BUSINESS.md` | Repository root, on the target branch | Describes your product's modules and the rules (invariants) they must keep. Business flow findings come from it. Read whenever it exists: it doesn't depend on **Repository conventions** |
| `AGENTS.md`, `CLAUDE.md`, `GEMINI.md` | Repository root or any folder | Coding conventions Review follows, when **Repository conventions** is on |
| `CONVENTIONS.md` | Repository root | Same as above |
| Coding agent rule files | Their usual paths, such as `.cursor/rules/`, `.github/copilot-instructions.md`, `.windsurf/rules/`, `.clinerules`, `.amazonq/rules/` or `.kiro/steering/` | Same as above |

You write `BUSINESS.md` by hand, and it must follow a fixed format. A file that doesn't parse, or is larger than 200 KB, is skipped for that review, and the rest of the review still runs.

<Accordion title="BUSINESS.md format and example">
  `BUSINESS.md` has a fixed structure: a `# Business map: <owner>/<repo>` title, a `## Product` section and a `## Modules` section, with an optional `## Flows` section, in that order. Each entry is a `###` heading in the form `### <id>: <title>`, followed by a short description and these optional lines:

  | Line | Format | What it's for |
  |---|---|---|
  | `Sources:` | Free text, items separated by `; ` | Where the description comes from, such as `README.md` |
  | `Code roots:` | Paths in backticks, separated by commas | The code that belongs to this entry |
  | `Depends on:` | Entry IDs, separated by commas | Other entries this one relies on. Each ID must exist in the file |
  | `Invariant <id>: <rule>` | One line per rule | A rule the code must keep. Review cites its ID in Business flow findings |

  IDs are lowercase and dot-separated, and the first part names the section: `product.`, `modules.` or `flows.` for entries, and `invariants.` for rules. After the first dot, use lowercase letters, digits and hyphens, for example `invariants.plans.trial-fast-only`. Every ID must be unique.

  ```markdown
  # Business map: acme/meterly

  ## Product

  ### product.meterly: Meterly
  Usage billing.

  ## Modules

  ### modules.plans: Plans
  Decides which run types each plan can start.
  Sources: README.md
  Code roots: `src/plans.py`
  Invariant invariants.plans.trial-fast-only: A Trial workspace starts only Fast runs.

  ## Flows

  ### flows.upgrade: Upgrade a trial
  A Trial workspace moves to a paid plan and unlocks Advanced runs.
  Code roots: `src/billing/upgrade.py`
  Depends on: modules.plans
  Invariant invariants.upgrade.paid-before-advanced: Advanced runs unlock only after the first payment succeeds.
  ```
</Accordion>

## What it checks

Each finding carries one category, so you can tell at a glance what kind of problem it is.

| Category | What it catches | Example |
|---|---|---|
| Security | Injection, exposed secrets, unsafe auth or permissions | A query built from request input without parameters |
| Correctness | Logic errors, null handling, race conditions | A lost update when two requests write the same row |
| Performance | Slow queries, N+1 loops, blocking calls | A full table scan inside a request handler |
| Pattern | Breaks a convention your repository already follows | A new handler that skips the shared error wrapper |
| Deploy, migration, backward compatibility | Changes that break a rollout or existing clients | A migration that drops a column the current release still reads |
| Test gap | Changed behavior that no test covers | A new error path with no test, in a PR that adds none |
| Business flow | A change that breaks a rule in your `BUSINESS.md` | In the `BUSINESS.md` example above, a change that lets a Trial workspace start an Advanced run, breaking `invariants.plans.trial-fast-only` |

## Supported providers

GitHub, GitLab (GitLab.com or self-hosted), Bitbucket Cloud, Azure DevOps and AWS CodeCommit. See [provider authentication](/guide/code-review/provider-auth) for what each one needs. Check these limits before you plan a rollout:

- **One provider per workspace.** If your team uses two, set up Review in a separate workspace for each.
- **No GitHub Enterprise Server or Bitbucket Data Center.** The GitHub connection goes to github.com and the Bitbucket connection to bitbucket.org. Self-hosted GitLab is the only instance URL you can enter.
- **One Azure DevOps project per workspace.** Repositories in another project need their own workspace.
- **One AWS account and region per CodeCommit connection.**

Some actions work on only some providers:

| Action | GitHub | GitLab | Bitbucket | Azure DevOps | CodeCommit |
|---|---|---|---|---|---|
| Automatic reviews | Yes | Yes | Yes | Yes | Yes |
| Questions to `@cloudthinker-ai` | Yes | Yes | Yes | Yes | Top-level comments only |
| Re-run with `@cloudthinker-ai review` | Yes | Yes | Yes | Yes | No |
| **Fix all findings** | Yes | Yes | Yes | Yes | No |
| `@cloudthinker-ai autofix` | Yes | Yes | Top-level comments only | Top-level comments only | No |
| `autofix stacked` | Yes | Yes | No | No | No |
| **Apply fix** | Yes | Yes | No | Yes | No |
| **Merge** from CloudThinker | Yes | Yes | No | No | No |
| Auto-resolve conflicts | Yes | Yes | Yes | No | Yes |

[Mention commands](/guide/code-review/mention-commands#provider-support) has the full comment command matrix.

Two pieces of text look alike but go in different places. Type them exactly as shown:

| Purpose | Exact text | Where to put it |
|---|---|---|
| Talk to the bot: ask, re-run, fix | `@cloudthinker-ai` | A PR or MR comment |
| Skip review on one PR | `@cloudthinker:ignore` | The PR or MR description |

Type `@cloudthinker-ai` as plain text even if your comments come from a bot user with another name. See [mention commands](/guide/code-review/mention-commands) and [Skip a review](/guide/code-review/mention-commands#skip-a-review).
