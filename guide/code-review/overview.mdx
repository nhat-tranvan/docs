**Nothing breaks in production.**

Review is the Frontier Investigation Agent for code changes: an AI reviewer for your pull requests (PRs) and merge requests (MRs). When someone opens one, CloudThinker reads the change, posts a summary comment and inline findings on it, and checks the fix when you push again.

<ReviewScene />

A linter matches patterns. Review reads what the change is trying to do: the diff, the linked ticket, your team's convention files and, if you keep one, a `BUSINESS.md` that describes the rules your product must keep. That lets it flag a broken business rule or a risky migration, not only a style slip.

## How it works

1. **A PR or MR opens.** You connect your Git provider and pick repositories once, and after that your provider sends CloudThinker an event whenever a PR or MR opens, with nobody starting a review. Draft PRs and MRs are skipped until they're marked ready for review.
2. **CloudThinker gathers context.** It checks out the change and reads the diff, a ticket linked from the description (Jira, Linear, Backlog or a provider issue, once you add an [extension](/guide/code-review/extensions)), and the files listed in [What Review reads](#what-review-reads).
3. **The review runs.** Depth depends on the workspace [review mode](/guide/code-review/setup#choose-a-review-mode): **Fast**, **Auto** or **Advanced**. Each review uses credits; see [usage and credits](/guide/billing/usage).
4. **Findings land on the PR.** You get one summary comment plus inline comments. Each finding has a severity (Critical, High, Medium or Low) and a suggested fix.
5. **New pushes get an incremental review.** Only the commits pushed since the last review are read, and the review checks whether earlier findings were fixed.

The most severe unresolved finding sets the review's verdict, and a run that never finished or was skipped gets a status of its own instead. The verdict is CloudThinker's label on the change, and your provider's branch rules still decide whether it can merge. See [verdicts](/guide/code-review/review-workspace#triage-the-reviews-list) for all seven and what each one asks of you.

<Note>
  CloudThinker keeps its own copy of each selected repository to read it, and deletes those copies when you click **Remove setup**. Secrets in tool output are replaced with placeholders before the model sees them; see [data protection](/guide/security/data-protection).
</Note>

Changed test files, fixtures and test data, snapshots, generated code, Storybook stories, prototypes, HTML under `docs/` and vendored Jsonnet aren't reviewed: no finding is ever placed in one.

## What Review reads

Besides the diff, Review reads these files from your repository. All of them are optional.

| File | Where it goes | What it does |
|---|---|---|
| `BUSINESS.md` | Repository root, on the target branch | Describes your product's modules and the rules (invariants) they must keep. Business flow findings come from it. Read whenever it exists: it doesn't depend on **Repository conventions** |
| Convention files | `AGENTS.md`, `CLAUDE.md`, `CONVENTIONS.md` and the rule files of coding agents such as Cursor or Copilot, in the repository root or any folder | Coding conventions Review follows, when **Repository conventions** is on. [Every path it recognizes](/guide/code-review/convention-rules#add-your-own-convention-files) |

You write `BUSINESS.md` by hand, and it must follow a fixed format: see [describe your business rules](/guide/code-review/convention-rules#describe-your-business-rules). A file that doesn't parse, or is larger than 200 KB, is skipped for that review, and the rest of the review still runs.

## What it checks

Each finding carries one category.

| Category | What it catches | Example |
|---|---|---|
| Security | Injection, exposed secrets, unsafe auth or permissions | A query built from request input without parameters |
| Correctness | Logic errors, null handling, race conditions | A lost update when two requests write the same row |
| Performance | Slow queries, N+1 loops, blocking calls | A full table scan inside a request handler |
| Pattern | Breaks a convention your repository already follows | A new handler that skips the shared error wrapper |
| Deploy, migration, backward compatibility | Changes that break a rollout or existing clients | A migration that drops a column the current release still reads |
| Test gap | Changed behavior that no test covers | A new error path with no test, in a PR that adds none |
| Business flow | A change that breaks a rule in your `BUSINESS.md` | Code that lets a trial account use a feature an invariant reserves for paid plans |

## Supported providers

GitHub, GitLab (GitLab.com or self-hosted), Bitbucket Cloud, Azure DevOps and AWS CodeCommit. See [provider authentication](/guide/code-review/provider-auth) for what each one needs. Check these limits before you plan a rollout:

- **One provider and one Azure DevOps project per workspace.** A second provider, or repositories in a second Azure DevOps project, need their own workspace.
- **Self-hosted GitLab is the only instance URL you can enter.** GitHub Enterprise Server and Bitbucket Data Center aren't options, and a CodeCommit connection covers one AWS account and region.

Automatic reviews run on all five providers. The actions on top of them don't:

- Comment commands with `@cloudthinker-ai` differ by provider, and AWS CodeCommit takes top-level questions only. See [provider support](/guide/code-review/mention-commands#provider-support).
- **Apply fix** is listed per provider in [Work the findings](/guide/code-review/review-workspace#work-the-findings); **Fix all findings** and **Merge** in [Re-run, fix, and merge](/guide/code-review/review-workspace#re-run-fix-and-merge).
- [Auto-resolve conflicts](/guide/code-review/conflict-resolution) works on every provider except Azure DevOps.

Two pieces of text look alike but go in different places: `@cloudthinker-ai` in a comment asks a question, a re-review or a fix, while `@cloudthinker:ignore` in the description [skips the review](/guide/code-review/mention-commands#skip-a-review) on that one change. See [mention commands](/guide/code-review/mention-commands).
