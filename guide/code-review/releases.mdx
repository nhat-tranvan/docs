A release report answers one question: is this set of changes safe to ship? You pick a release in a connected repository, CloudThinker reads the actual diff against the previous release, and you get the risks, the steps to take, and a place to record **Approve** or **Hold**.

## Prerequisites

- A repository connected through [Review setup](/guide/code-review/setup) on GitHub, GitLab, Bitbucket, Azure DevOps or AWS CodeCommit.
- The right workspace role for what you want to do. See [roles](/guide/security/roles).

  | Action | Who can do it |
  |---|---|
  | Read reports and download the PDF | Admin, Developer, Viewer |
  | Analyze a release, record a decision, settle steps, use **Fix with CloudThinker** | Admin |

## Analyze a release

<Steps>
  <Step title="Open Analyze release">
    Go to **Review → Releases** and click **Analyze release**.
  </Step>
  <Step title="Pick the repository and release">
    Choose the **Repository**. A release is a Git tag. CloudThinker lists the tags newest first and preselects **Not released yet** when the default branch has changes since the last release. The analyze button calls the same thing **unreleased changes**. Use the search box to find a branch or tag, or paste a commit ID.

    AWS CodeCommit has no tag support, so on CodeCommit the picker offers branches only.
  </Step>
  <Step title="Check what it compares with">
    CloudThinker picks the base for you: the previous release on the same line. A release line is a chain of tags that build on each other in Git history. Tags on your default branch form one line, and a tag on a branch that forked off it, such as a hotfix branch, starts its own. To compare with something else, click **Change** next to the base and pick another release, branch or commit.
  </Step>
  <Step title="Start the analysis">
    Click **Analyze** (the button names the release, for example **Analyze unreleased changes**). It takes about 5 minutes, and you can leave the page. No notification is sent when it's ready, so check the **Needs decision** tab.

    **Success state:** the release shows **Analyzing**, then lands in the **Needs decision** tab once the report is ready.
  </Step>
</Steps>

If a release already has a report, the dialog offers **Open report** and **Analyze again** instead. Analyzing again creates a new report; the older one is marked **Replaced** and stays readable, but only the newest one takes a decision.

<Tip>
By default, an analysis only starts when someone clicks **Analyze release**. To start a report for every pushed tag, turn on **Analyze new release tags** in the **Review** section of **Review → Settings**. The setting shows only when release reports are turned on for your workspace. If you don't see it, contact support. Each report is one agent run, so leave it off if you tag often.
</Tip>

## Read the report

The top card gives the verdict:

| Field | What it tells you |
|---|---|
| Status | **Hold recommended** when a blocking risk is open, otherwise **Ready to approve** |
| Review Quality | The review score (out of 10) of the release's PRs and MRs, weighted by how much each one changes. **Not scored** when none of them were reviewed |
| Impact at risk | The share of the release's size ([Impact](/guide/code-review/analytics#how-the-scores-are-built)) in PRs or MRs that are at risk (see below) |

A PR or MR counts as at risk when any of these is true:

- A blocking risk cites it.
- It has a high or critical finding open.
- Review never reviewed it.

For example, a release of three PRs with Impact 50, 30 and 20, where only the 30 one has a high finding open, shows 30% at risk.

Below it, tiles show **Commits**, **Lines**, **Reviewed by CloudThinker** and **Pipeline on head**. **Pipeline on head** is the CI status of the release's head commit and links to that run in [Pipelines](/guide/code-review/pipelines). It reads **No pipeline seen** when Review has no run for that commit. Then come three sections that never repeat each other:

| Section | What it answers |
|---|---|
| Risks | Why this release might not be safe. Each risk is **Blocking** or **Watch**, with **Evidence** and a **Mitigation** |
| Steps | What to do about it, grouped as **Before you ship**, **Recommended** and **After rollout** |
| What changed | What ships, each change tagged Feature, Fix, Breaking change, Data change, Dependency change, Infrastructure change or Internal change |

A risk is **Blocking** when someone should fix it, or explicitly accept it, before shipping. It's **Watch** when the rollout needs attention but the evidence doesn't justify a hold. CloudThinker checks nine risk areas on every release and lists only the ones that matter for it:

| Risk area | The question it asks |
|---|---|
| Security and access | Can access, identity, secret or trust boundaries change? |
| Payment and entitlements | Can money, credits, quotas or entitlements change? |
| Data and migrations | Can data be lost, locked, misread or become incompatible? |
| Review assurance | Are important commits, tests or findings unresolved? |
| Rollback safety | Can the change be stopped, rolled back or forward-fixed safely? |
| Blast radius | How many users, services, regions or tenants can one failure reach? |
| Public API contract | Can a client, event consumer or stored contract break? |
| Infrastructure and deployment | Can rollout order, capacity, config or health checks fail? |
| Dependency change | Does a dependency add supply-chain, compatibility or runtime risk? |

The report also lists the release's PRs or MRs with their review status, and a **Quality map** that highlights changes with low quality, no review, or a blocking risk. If CloudThinker couldn't read part of the range, an **Assessment limits** note says so rather than guessing.

<Note>
Counts are a snapshot. If you fix an open finding after the report, the report still shows it. Analyze the release again for current numbers.
</Note>

## Work through the steps

Each open step has **Mark resolved** and **Dismiss**. Dismissing asks for a reason, and **Re-open** undoes either. When you analyze the same release again, steps you already settled are **Carried over** if the instruction hasn't changed, so you don't redo work. Marking a step resolved is your claim; only a new analysis confirms the risk is gone.

To get help with the open steps, click **Fix with CloudThinker**:

| Option | What happens |
|---|---|
| Fix all findings | Despite the name, this works on the report's open steps. It opens a Chat conversation where CloudThinker works on a branch started from the release's head commit. It makes each change, runs the relevant tests, and reports what it changed. Check its work in the conversation before you ship |
| Analyze in Chat | Opens Chat with this report as context, so you can ask questions first |

Click **Download PDF** to share the report outside CloudThinker.

## Approve or hold

<Steps>
  <Step title="Make the call">
    On the report, click **Approve** or **Hold**. When a blocking risk is still open, the button reads **Approve anyway**.
  </Step>
  <Step title="Add a note">
    The note is optional, with two exceptions. Approving with a blocking risk open asks **Why is it safe to ship?** Holding a release with no blocking risk asks **Why are you holding it?**

    **Success state:** the report shows "Approved by" or "Held by" with your name and note, and the release moves to the **Approved** or **On hold** tab.
  </Step>
</Steps>

A decision is a record in CloudThinker. It doesn't merge, tag or deploy, and nothing is sent to your Git provider, so it never blocks your pipeline. To change it later, click **Change decision**. Replaced reports keep the decision they had.

<Warning>
The report keeps only the latest decision and note. **Change decision** overwrites the earlier one, and there's no decision history. If you need an audit record, click **Download PDF** right after you decide: the PDF includes the decision and its note.
</Warning>

The **Releases** list works as a decision queue:

| Tab | What it holds |
|---|---|
| Needs decision | The newest report for each release line with no decision yet |
| On hold | Releases someone held |
| Approved | Releases someone approved |
| All | Everything. Use the status chips for **Analyzing**, **Failed** and **Replaced** |

## Troubleshooting

<AccordionGroup>
  <Accordion title="The dialog says This repository has no releases or unreleased changes to analyze yet">
    There's no tag to analyze and the default branch has nothing new since the last release. Push a tag, or pick a branch or commit with the search box.
  </Accordion>
  <Accordion title="That base was not found">
    The base you chose doesn't exist or isn't an ancestor of the release. Click **Change** and pick another base.
  </Accordion>
  <Accordion title="The release shows Analysis failed">
    The analysis stopped before it finished, and no score was published. Start a new analysis from **Analyze release**.
  </Accordion>
  <Accordion title="Merge request counts are missing">
    AWS CodeCommit can't link commits to PRs, so the report marks those counts as not available. The risk analysis still reads the full diff.
  </Accordion>
  <Accordion title="Two analyses of the same release disagree">
    The report is CloudThinker's judgment on the diff, so details can shift between runs. Treat the status and the blocking risks as the signal, not small changes in numbers.
  </Accordion>
</AccordionGroup>
