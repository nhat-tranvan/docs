**Resolve → Insights** shows how Resolve, CloudThinker's incident response module, performed over a time window you pick, and whether you can trust its diagnoses. Use it to decide what to fix next: a noisy alert source, a service with slow recovery, or an incident type with no runbook.

## Prerequisites

- A workspace with some [Resolve](/guide/incident/overview) incidents, from alerts or [logged by hand](/guide/incident/manual-logging). Insights reads past incidents, so it stays empty until some exist.
- Any workspace role. Admin, Developer, and Viewer can all open Insights. See [Roles](/guide/security/roles).
- For the accuracy numbers: workspace Admins marking diagnoses right or wrong (see [Mark a diagnosis](#mark-a-diagnosis-right-or-wrong)).

## Open Insights and pick a window

<Steps>
  <Step title="Open the page">
    In the sidebar, open **Resolve → Insights**, under **Analytics**.
  </Step>
  <Step title="Pick a time window">
    Use the selector in the page header. Options run from **Last 1 hour** to **Last 30 days**, and the default is **Last 7 days**. The window stays the same when you switch tabs.

    On **Overview** and **Accuracy & trust**, the window selects incidents by when Resolve recorded them, not when they resolved or were marked. An incident recorded last week and resolved today stays in last week's numbers. Runbook figures use when the runbook execution was created. **Pulse analysis** has its own rules, listed in [Pulse analytics](/guide/pulse/analytics#what-each-metric-means).
  </Step>
  <Step title="Pick a tab">
    Choose **Overview**, **Accuracy & trust**, **Pulse analysis**, or **Runbook analytics**.
  </Step>
</Steps>

**Success state:** the tab fills with cards for the window you chose. A card that says something like "No runbook executions in this period" means there's no data yet, not an error.

Numbers are computed from live data when the tab loads, so reload the page to refresh them. The page has no export button.

## Choose the right tab

| Tab | Question it answers | Start here when |
|---|---|---|
| **Overview** | How fast does Resolve get from alert to fix, and which services hurt most? | Your on-call lead asks why last week felt slow. |
| **Accuracy & trust** | How often did people confirm Resolve's root cause was correct? | You're deciding how much to rely on automatic investigation. |
| **Pulse analysis** | How much alert noise does Pulse absorb, and which sources make the most? | Responders complain about alert volume. |
| **Runbook analytics** | Which runbooks run, succeed, and which services have none? | You're planning which runbook to write next. |

## Read the Overview tab

| Card | What it shows |
|---|---|
| **Mean time to resolve** | Average time from when the incident occurred (its **Occurred At** time, or when it was recorded if that's missing) to when it was resolved, across resolved incidents. It's a mean, so one long incident pulls it up. Compare it with **Alert → root cause**, which is a median. |
| **Alert → root cause** | Median time from the incident starting to a root cause being found. It covers detection, correlation, and analysis together, not only how long the agent ran. |
| **Auto-resolved** | Share of resolved incidents CloudThinker closed with no human touch. |
| **Noise reduced** | Raw events that didn't become an incident, out of all raw events: (raw events − incidents) ÷ raw events. The help icon shows the funnel: raw events → signals that weren't suppressed → clusters → incidents. |
| **Where the time goes** | Average time spent in each stage. See [Stages](#stages-in-where-the-time-goes). |
| **MTTR over time** | Mean time to resolve (MTTR), plotted across the window. |
| **Recurrence trend** | Share of incidents that came back within 72 hours of a matching incident resolving. Two incidents match when they share a dedup key, an identifier set on incidents created from webhooks. Manually logged incidents have none, so they aren't counted. |
| **Reliability by service** | Per service: **Incidents**, **MTTR**, **Auto** (share closed as **Auto-resolved**), and **Manual takeover** (share where a person fixed and closed the incident without running a runbook they approved). |

### Stages in Where the time goes

| Stage | Starts | Ends |
|---|---|---|
| **Detect** | The incident occurred | Resolve recorded it |
| **Correlate** | A cluster first formed in Pulse | The cluster was routed |
| **Root cause** | The first RCA session started | A root cause was identified |
| **Fix staged** | A runbook execution was created | It started running. This is mostly approval wait time, not how long the fix took. If it's long, check pending requests in [Approvals](/guide/approvals/overview). |
| **Validate** | The last runbook finished | The incident was closed |

When total response time goes up, check this card first. A slower **Detect** stage points at your alert sources, not at root cause analysis (RCA).

## Read the Accuracy & trust tab

Every number on this tab comes from people on your team marking a diagnosis as right or wrong. Nothing comes from the agent scoring itself.

| Card | What it shows |
|---|---|
| **Root-cause accuracy** | Diagnoses marked accurate, out of all reviewed diagnoses. Reviewed means someone marked it, either way. |
| **Fix acceptance** | Runbook executions a person approved, out of executions that needed approval. Runbooks that ran without approval aren't counted. |
| **False-positive rate** | Diagnoses marked wrong with the reason **False positive**, out of all reviewed diagnoses (the same set as **Root-cause accuracy**). |
| **Your review coverage** | Resolved incidents anyone in the workspace reviewed, out of all resolved incidents. It's a team number, not a personal one. |
| **When Resolve was off, why?** | The reasons people gave when they marked a diagnosis wrong. |
| **Review more incidents** | How many resolved incidents are still unmarked. |
| **Accuracy by service** | **Reviewed**, **Accurate**, and **Rate** per service. Services come from each incident's **Affected services** list, which the investigation fills in. |

Use the reasons to decide what to change:

| Reason | What it usually points at |
|---|---|
| **Wrong root cause** | Missing evidence. Connect the logs, metrics, or traces the investigation needed. |
| **Wrong service** | Missing context about how your services depend on each other. |
| **Fix wouldn't work** | Remediation quality. Add or update a [runbook](/guide/incident/runbooks). |
| **False positive** | A noisy alert. Tune it at the source or in [Pulse](/guide/pulse/clusters). |
| **Something else** | Read the comments on those incidents. |

<Warning>
Check **Your review coverage** before you act on **Root-cause accuracy**. With only a handful of reviewed incidents, one verdict swings the rate a lot. Read the underlying incidents before you change a connection, runbook, or process.
</Warning>

### Mark a diagnosis right or wrong

<Steps>
  <Step title="Open the incident">
    Go to **Resolve → Investigation** and open the incident. It doesn't have to be resolved.
  </Step>
  <Step title="Answer the question">
    Below the analysis, under **Was Resolve's diagnosis right?**, click the thumbs-up (**Accurate**) or thumbs-down (**Inaccurate**) button. The question appears as soon as the incident has a verdict. Only the workspace Admin role can answer.
  </Step>
  <Step title="Say what was wrong">
    If you click **Inaccurate**, pick the closest reason under **What was wrong?** and add an optional note. The mark only saves once you pick a reason.
  </Step>
</Steps>

**Success state:** the incident shows **Marked accurate** or **Marked not accurate**, and the verdict counts on the **Accuracy & trust** tab. Any mark counts toward **Root-cause accuracy** and **False-positive rate**. Only marks on resolved incidents count toward **Your review coverage**. Each Admin has their own mark on an incident and can change it later. Two Admins marking the same incident count as two reviews in **Root-cause accuracy**.

## Read the Pulse analysis tab

This tab shows how much alert noise [Pulse](/guide/pulse/overview) absorbs and which sources send the most. Every card and column is defined in [Pulse analytics](/guide/pulse/analytics). Its **Noise suppressed** card uses a different denominator from **Noise reduced** on Overview, so don't compare the two.

## Read the Runbook analytics tab

| Card | What it shows |
|---|---|
| **Runbook coverage** | Closed incidents that used a runbook, out of all closed incidents. |
| **Executions** | Runbook runs in the window. |
| **Completion rate** | Runs that finished successfully, out of runs that started. It doesn't tell you whether the fix held later. |
| **Runbook effectiveness** | Per runbook: **Mode** (auto, approval, or mixed when it ran both ways), **Runs** (every execution recorded, including ones still waiting for approval), **Executed** (runs that actually ran), and **Success** (completed, out of executed). See [Runbooks](/guide/incident/runbooks). |
| **Coverage gaps** | Services whose incidents closed without any runbook running, sorted by **Incidents with no runbook**, highest first. |

**Coverage gaps** is your runbook to-do list: the service at the top is where a new runbook helps most. The full list of individual runs stays on **Resolve → Runbooks**.

## Troubleshooting

<AccordionGroup>
  <Accordion title="Every tab is empty">
    **Cause:** no incidents fall inside the window. **Check:** widen the selector to **Last 30 days**. **Fix:** if it's still empty, confirm alerts are arriving on **Resolve → Pulse**, then follow [Pulse setup](/guide/pulse/setup).
  </Accordion>
  <Accordion title="Accuracy shows no percentage">
    **Cause:** nobody has marked a diagnosis in this window. **Fix:** mark a few resolved incidents under **Was Resolve's diagnosis right?**. The **Review more incidents** card shows how many are waiting.
  </Accordion>
  <Accordion title="A service is missing from Accuracy by service">
    **Cause:** services on this table come from each incident's **Affected services** list. An incident counts only when it was marked and its investigation named the service. **Check:** open a marked incident for that service and look at **Affected services**. **Fix:** if it's empty, the investigation couldn't place the service. Add the connection it needed, so later investigations can.
  </Accordion>
  <Accordion title="A tab shows a load error">
    Click **Retry**. If it keeps failing, see [Resolve troubleshooting](/guide/incident/troubleshooting).
  </Accordion>
</AccordionGroup>
