A **runbook** is a written procedure for fixing a known problem, such as "restart the checkout pods" or "fail over the database". When you connect your runbooks to Resolve, CloudThinker reads them during a root cause analysis (RCA) and proposes the matching fix instead of improvising one.

## How it works

1. You add a **runbook source**: a Confluence space, a GitHub or GitLab repository, or Markdown files you upload.
2. During [root cause analysis](/guide/incident/root-cause-analysis), CloudThinker searches your enabled sources for a procedure that fits the problem it found.
3. If the procedure includes commands that change something, the run stops at **Action requires approval** until a person decides.
4. Every attempt is recorded on the **Execution history** tab with its policy decision, approval, and outcome.

Read-only commands (ones that only look, like `kubectl get pods`) never wait for approval. Commands that change infrastructure, like `kubectl rollout restart`, do.

## Prerequisites

- Access to Resolve in your workspace.
- For Confluence, GitHub, or GitLab: a working [Atlassian](/guide/connections/atlassian), [GitHub](/guide/connections/github), or [GitLab](/guide/connections/gitlab) connection. The source form can't be saved without one.
- For uploads: your procedures as `.md` files, with commands in fenced code blocks.

## Choose a source type

| Source type | Best when | What you can narrow |
|---|---|---|
| **Confluence** | Your runbooks live in a wiki space. | **Confluence Space Key** (empty searches all spaces) and **Labels** |
| **GitHub** | Runbooks are files in a repository. | **Repository**, **Branch**, **Path Prefix**, **File Patterns** |
| **GitLab** | Same as GitHub, on GitLab. | **Repository**, **Branch**, **Path Prefix**, **File Patterns** |
| **Upload a runbook** | You have a few procedures and no wiki or repo for them. | Nothing to narrow: CloudThinker stores the files in your workspace |

Connected sources stay in their own system. CloudThinker reads them at RCA time, so an edit in Confluence or a merged change in Git is picked up on the next investigation without a re-sync.

## Connect a Confluence, GitHub, or GitLab source

<Steps>
  <Step title="Open Runbooks">
    In the sidebar, open **Resolve → Runbooks** (under **Configuration**). If you have no sources yet, the page lists each source type: a connected one shows the connection name, an unconnected one shows **Connect first**.
  </Step>
  <Step title="Add the source">
    Click **Add source** (or the source type in the empty state). In **Add Runbook Source**, enter a **Source Name**, for example `SRE Runbooks`, pick the **Source Type**, and select the connection.
  </Step>
  <Step title="Narrow what CloudThinker searches">
    For Confluence, set a **Confluence Space Key** such as `SRE` and any **Labels**. For GitHub or GitLab, pick the **Repository**, then optionally a **Branch**, a **Path Prefix** such as `docs/runbooks`, and **File Patterns** such as `*.md`. Click **Add Source**.
  </Step>
</Steps>

**Success state:** the source appears in the list with its type and scope, for example `GitHub · acme/runbooks · docs/runbooks`, and its toggle is on.

Every change-making command that CloudThinker takes from a connected source requires approval before it runs. The form shows this as a notice, and there's no per-command setting for connected sources.

## Upload Markdown runbooks

<Steps>
  <Step title="Open the upload dialog">
    On **Resolve → Runbooks**, click **Upload runbook** (or **Upload a runbook** in the empty state).
  </Step>
  <Step title="Add your files">
    Drag in up to 20 `.md` files, up to 5 MB each. Each file gets a **Runbook name**, which you can edit before uploading.
  </Step>
  <Step title="Upload">
    Click **Upload**. Each file shows **Uploading...** and then **Extracting commands...** while CloudThinker pulls the commands out of its code blocks.
  </Step>
</Steps>

**Success state:** each file appears as its own source in the list. Click the book icon on its row to open a read-only preview, with a **Download** button for the original Markdown.

A runbook written like this gives CloudThinker clear, separable commands:

````md
# Checkout pods in CrashLoopBackOff

## Check
```bash
kubectl get pods -n checkout
kubectl logs deploy/checkout-api -n checkout --tail=200
```

## Fix
```bash
kubectl rollout restart deploy/checkout-api -n checkout
```
````

From this file, CloudThinker skips the two read-only commands and records `kubectl rollout restart` as a change-making command that requires approval.

## Approve a runbook action

When CloudThinker wants to run a change-making command during an incident, the incident's analysis shows **Action requires approval** with the runbook it came from.

<Steps>
  <Step title="Open the conversation">
    On the incident, click **Go to conversation**.
  </Step>
  <Step title="Decide">
    Read the proposed command and approve or reject it there. Approving lets the run continue. Rejecting stops that action.
  </Step>
</Steps>

**Success state:** the banner disappears, and the execution shows **Approved** or **Rejected** on the **Execution history** tab.

Who can approve follows your workspace's approval setup. See [Approvals](/guide/approvals/overview) and [approvers](/guide/approvals/approvers).

## Review what ran

Open the **Execution history** tab on **Resolve → Runbooks**. Each row is one runbook action:

| Column | Values | What it tells you |
|---|---|---|
| **Runbook** | The runbook title, linked to its source | Which procedure CloudThinker used |
| **Policy** | Auto Execute, Requires Approval, Denied, Per Command | What the policy decided before anyone was asked |
| **Approval** | Pending, Approved, Rejected | What a person decided, if one was asked |
| **Status** | Not Started, Completed, Skipped, Failed | What happened when it ran |
| **Created** | Timestamp | When CloudThinker proposed it |

Check **Status** before you close an incident. **Approved** means a person said yes. Only **Completed** means the command ran.

For trends across incidents, open the **Runbook analytics** tab in [Resolve Insights](/guide/incident/insights).

## Manage sources

Hover a source row to see its actions:

| Action | What it does |
|---|---|
| Toggle | Turns the source off without deleting it. CloudThinker doesn't search a disabled source. |
| Edit | Changes the name or scope of a connected source. |
| Preview (book icon) | Shows an uploaded runbook's content. |
| Publish | Appears on a source marked **Draft**. CloudThinker doesn't search drafts until they're published. |
| Delete | Removes the source after a confirmation. |

<Note>
In the sidebar, **Runbooks** carries a **Legacy** label. The page and its sources still work as described here.
</Note>

## Troubleshooting

<AccordionGroup>
  <Accordion title="A source type is greyed out or says Connect first">
    The source form needs a connection for that platform. Click the row to connect it, or add it from [Connections](/guide/connections/overview), then come back and click **Add source**.
  </Accordion>
  <Accordion title="CloudThinker didn't use my runbook during RCA">
    Check that the source's toggle is on and that it isn't marked **Draft**. Then check the scope: a wrong **Confluence Space Key**, **Path Prefix**, or **File Patterns** value hides the file. Give the runbook a title that names the symptom, such as "Checkout pods in CrashLoopBackOff", so it matches what RCA finds.
  </Accordion>
  <Accordion title="An upload was rejected">
    Only `.md` files up to 5 MB are accepted, and at most 20 per upload. Split a large runbook into one file per procedure.
  </Accordion>
  <Accordion title="No commands were picked up from my upload">
    Commands must sit in fenced code blocks. Commands in plain paragraphs, or read-only commands only, produce nothing to approve.
  </Accordion>
  <Accordion title="The incident is stuck waiting">
    A runbook action is pending. Open the incident, click **Go to conversation**, and approve or reject it.
  </Accordion>
</AccordionGroup>
