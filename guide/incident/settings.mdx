Resolve has no settings page of its own. Each control sits on the page it affects: **AI auto-investigate** in the title row of **Resolve → Issues**, webhook options on **Resolve → Triggers & Outcomes**, paging on **Resolve → On-call**, and Detectors in a sheet on **Resolve → Detectors**.

## Prerequisites

- The workspace **Admin** role to change any setting. Developers and Viewers can see the values but can't change them. See [Roles](/guide/security/roles).
- Resolve set up with at least one alert source. See [Connect Pulse sources](/guide/pulse/setup).

## Where each setting lives

Use this table to find the control you need. An old **Resolve → Settings** link now opens **Settings → Workspace → Autonomy → Rules**.

| Setting | Where | Default | What it controls |
|---|---|---|---|
| **AI auto-investigate** | **Resolve → Issues**, title row | On | Whether CloudThinker triages and investigates on its own. See [What starts an investigation](#what-starts-an-investigation). |
| **Auto-investigate** | Each webhook, under **Resolve → Triggers & Outcomes** | On | Whether that webhook's clusters go to triage and investigation on their own |
| **Only from a minimum severity** | Each webhook | Off | The lowest signal severity that starts triage on its own |
| **Send directly to CloudThinker** | Each webhook | Off | Whether alerts skip Signals filtering and grouping. Use only for low-volume sources where every event matters. |
| Watched chat channels | **Resolve → On-call** › **Alert path** › **Hears** | None | Which Slack or Teams channels Resolve listens to. Click **Manage**, then **Watch a channel** to add one. |
| Paging | **Resolve → On-call** › **Alert path** › **Pages** | Off | Whether a qualifying incident opens an Incident Room with your responders. The switch appears once you add responders. See [On-call](/guide/incident/oncall). |
| **Detectors**, **Review**, **Fire limit** | **Resolve → Detectors**, **Settings** icon | Off | Whether Detectors runs, how often it reviews your Monitors, and the read-only fire cap. See [Detectors](/guide/incident/detectors#settings). |
| Runbook command effects | **Settings → Workspace → Autonomy → Runbooks**, only where enabled | Not shown | The effect of each command from an uploaded runbook. See [Runbooks](/guide/incident/runbooks#control-command-effects). |
| Approval mode | **Settings → Workspace → Autonomy → Rules**, section **When no Rule matches** | **Auto** | What happens to a fix no Rule covers. See [Approvals](/guide/approvals/overview). |

Every switch saves as soon as you flip it. There's no **Save** button.

## What starts an investigation

This table is the one place Resolve's start rules are written down. Other Resolve pages link here.

**Triage** is CloudThinker's first look at a cluster. It attaches the cluster to an open incident, reopens a closed incident when the same fault comes back, or opens a new one, and then investigates it (root-cause analysis, or RCA). A **signal** is an event that survived noise suppression, and a **cluster** is a group of related signals treated as one problem. See [Signals](/guide/pulse/overview).

| Situation | What happens |
|---|---|
| **AI auto-investigate** on, webhook with **Auto-investigate** on | A cluster that holds an actionable signal goes to triage on its own. Triage opens or reopens an incident and investigates it. |
| **AI auto-investigate** on, webhook with **Only from a minimum severity** set | The same, but only signals at or above the floor start triage. Signals below it still group into clusters, and if their cluster already belongs to an open incident, they're added to that incident. |
| **AI auto-investigate** on, webhook with **Auto-investigate** off | Alerts still land in Signals and group into clusters. Nothing starts on its own until a person clicks **Open incident** on the cluster and then **Send to triage**. |
| **AI auto-investigate** on, webhook with **Send directly to CloudThinker** | Each event skips Signals filtering and grouping and gets its own triage run. |
| **AI auto-investigate** on, polled AWS services and Slack or Teams channels | These sources have no **Auto-investigate** or severity option. Their actionable clusters always go to triage. |
| **AI auto-investigate** off, any source | CloudThinker keeps detecting and grouping alerts, and an actionable cluster is still filed as an incident with status **Open**. CloudThinker doesn't triage, investigate, or page responders on its own — each incident waits until someone clicks **Investigate**. Incidents a person logs or escalates still investigate right away. |
| A person clicks **Open incident** (or **Escalate** in the **⋯** menu), then **Send to triage**, on a cluster | Triage runs right away, whichever way **AI auto-investigate** is set. |
| A person clicks **Investigate** on an incident (Admins only) | The investigation starts right away, whichever way **AI auto-investigate** is set. |
| A person [logs an incident](/guide/incident/manual-logging) | The investigation starts the moment the form is submitted, even while **AI auto-investigate** is off. Nobody needs to click **Investigate**. |
| The same fault had an automatic investigation in the last 24 hours | CloudThinker starts at most one automatic investigation per fault in 24 hours. A person can still start one. |

**Auto-investigate** and **Only from a minimum severity** are set on each webhook under **Resolve → Triggers & Outcomes**. See [Webhook options](/guide/pulse/setup#webhook-options-that-change-behavior).

## Turn off automatic investigation

**AI auto-investigate** is CloudThinker's autonomy switch, not your on-call rotation. Turn it off during a planned maintenance window, or while you tune a noisy source. [What starts an investigation](#what-starts-an-investigation) shows what still runs while it's off.

<Steps>
  <Step title="Open the issue queue">
    Go to **Resolve → Issues**.
  </Step>
  <Step title="Flip the switch">
    In the title row, turn off the **AI auto-investigate** switch.

    **Success state:** the switch shows off. CloudThinker keeps detecting and files incidents as **Open** for you to review.
  </Step>
  <Step title="Work by hand while it's off">
    On **Resolve → Signals**, click **Open incident** on a cluster and then **Send to triage**, or click **Investigate** on an incident in **Resolve → Issues**. Both work whichever way the switch is set.
  </Step>
  <Step title="Turn it back on">
    Flip the switch back on. New actionable clusters are triaged on their own from that point. Incidents filed while it was off are not started later — each one stays **Open** until someone clicks **Investigate**.
  </Step>
</Steps>

<Tip>
There's no timer or auto-resume. **AI auto-investigate** stays off until someone turns it back on, so check the title row after every maintenance window. The page doesn't show who turned it off or when. Each change is recorded in [Audit Logs](/guide/security/audit-logs): filter **Category** to **Incident** and look for the raw action `incidents.settings_updated`. The entry shows who made the change, when, and which setting changed with its new value (not the old one).
</Tip>

## Troubleshooting

<AccordionGroup>
  <Accordion title="The switches are greyed out">
    **Cause:** you don't have the workspace Admin role. **Resolve → On-call** says "You can view these settings, but only editors can change them." There, "editors" means workspace Admins. **Fix:** ask a workspace Admin to change the setting or your role.
  </Accordion>
  <Accordion title="AI auto-investigate is on, but an alert wasn't investigated">
    **Cause:** that webhook has **Auto-investigate** off, **Only from a minimum severity** is set above the alert's severity, or the same fault already had an automatic investigation in the last 24 hours. **Check:** open the webhook under **Resolve → Triggers & Outcomes**, and see [What starts an investigation](#what-starts-an-investigation). **Fix:** adjust the option, then click **Open incident** and **Send to triage** on the waiting cluster in **Resolve → Signals**. More causes are in [Resolve troubleshooting](/guide/incident/troubleshooting).
  </Accordion>
</AccordionGroup>
