Root-cause analysis (RCA) is the step where CloudThinker works out why an incident happened. It reads the incident, the alerts behind it, and your connected systems, tests possible explanations, and hands you a written verdict, a diagram of how the failure unfolded, and a list of suggested fixes. You review it and decide what happens next.

RCA is the Investigate stage of [Resolve](/guide/incident/overview). It reads logs, metrics, traces, recent changes, and dependencies through the [connections](/guide/connections/overview) you've already set up, and it can only reach what those connections can. Investigation only reads. Any change goes through a [runbook](/guide/incident/runbooks) and your [Approvals](/guide/approvals/overview) settings. For what the model sees and how secrets are handled, see [Data protection](/guide/security/data-protection).

## Before you start

- At least one [connection](/guide/connections/overview) to the systems involved, such as your cloud account, Kubernetes cluster, or monitoring tool. RCA can only check what it can read.
- The workspace **Admin** role to start investigations, settle suggestions, and change an incident's status (including closing it). Developers and Viewers can read results. See [Roles](/guide/security/roles).
- Credits. Each investigation is agent work, billed in credits like any other run, including ones that start automatically. Watch spend on [Usage](/guide/billing/usage), and cap a workspace with [Credit limits](/guide/billing/credit-limits). To stop automatic runs, turn **Auto-investigate** off on a webhook or turn off **AI auto-investigate**. See [What starts an investigation](/guide/incident/settings#what-starts-an-investigation).

## How an investigation starts

| Incident came from | When RCA starts |
|---|---|
| [Signals](/guide/pulse/overview) (an alert source) | Automatically when triage opens or reopens the incident, while **AI auto-investigate** is on and the webhook's options allow it. [What starts an investigation](/guide/incident/settings#what-starts-an-investigation) has the full rules. |
| [Log Incident](/guide/incident/manual-logging) (a person) | Right away, as soon as you submit the form, even while **AI auto-investigate** is off. |
| An incident with no investigation yet. It waits in **Not started**. | When you click **Investigate**. |
| An incident set to **Investigating** that has never had an investigation, for example because someone picked **Investigating** from the status badge. It waits in **Not started**. | When you click **Investigate**. |

## Run an investigation

<Steps>
  <Step title="Open the incident">
    Go to **Resolve → Issues** and select the incident from the queue.
  </Step>
  <Step title="Start RCA if it hasn't started">
    If the incident has never been investigated, click **Investigate** in the incident header.

    **Success state:** the incident moves to **AI is handling**, and the incident page reads **CloudThinker is investigating** with a **Watch live** button.
  </Step>
  <Step title="Follow along (optional)">
    Click **Watch live** to open the conversation where CloudThinker is working. You'll see each check it runs as it runs. Findings also appear on the incident page as they are saved.
  </Step>
  <Step title="Read the verdict">
    When analysis finishes, the incident moves to **Needs you**. For an incident with status **Identified**, the result's heading reads **Root cause**. [Investigation outcomes](#investigation-outcomes) lists every status and where it lands. [Read the result](#read-the-result) explains each section of the page.

    If no new findings appear and **Watch live** shows no activity, see [Investigation stuck](/guide/incident/troubleshooting#investigation-stuck).
  </Step>
  <Step title="Settle each suggestion">
    Mark each item under **Actions** as done or dismissed. See [Settle each remediation suggestion](#settle-each-remediation-suggestion).
  </Step>
  <Step title="Close the incident">
    Click the status badge in the incident header, pick **Resolved** or **False alarm**, and confirm with **Change Status**. Only workspace Admins can change status. Other roles see the badge without a menu.

    | Current status | Closing options in the menu |
    |---|---|
    | **Open**, **Acknowledged**, **Investigating**, **Identified** | **Resolved** or **False alarm** |
    | **On hold** | **Resolved** only. To mark it **False alarm**, move it to **Investigating** first. |
    | **Not found** | Neither. The menu offers **Investigating** only. To close it, pick **Investigating**, then open the badge again and choose **Resolved** or **False alarm**. |

    **Success state:** the incident moves to the **Resolved** or **Dismissed** group.
  </Step>
</Steps>

## The investigation queue

**Resolve → Issues** groups incidents by what they need from you:

| Group | What's in it |
|---|---|
| **AI is handling** | An investigation is running |
| **Needs you** | A verdict is ready, the investigation paused for input, or the checks were inconclusive |
| **Not started** | No investigation has run yet, or one is queued. Click **Investigate** to start one. |
| **Resolved** | Closed as **Resolved** or **Auto-resolved** |
| **Dismissed** | Closed as **False alarm** |
| **Triaged** | Triage looked at the alert and no response was started, for example because it judged the alert needs no action |

## Read the result

The incident page puts the answer first and the supporting material below it.

The answer's heading names where the investigation stands: **Triage**, **Working theory**, **Root cause**, **On hold**, **No root cause found**, **False alarm**, or **Resolution**. Next to it, an evidence label (below) says how strong the evidence is, and **Running** shows while a session is running. Under the verdict, short rows such as **Impact**, **Cause**, **Fix**, **Risk and undo**, and **Confidence** sum it up, with how long it took to find the root cause.

Below the answer, each section opens on click:

| Section | What it tells you |
|---|---|
| **How it happened** | A causal graph from the first failure to the visible impact |
| **Actions** | Suggested fixes, each with a risk level: **Low risk**, **Medium risk**, or **High risk** |
| **What happened** | The timeline of the incident |
| **Evidence** | The findings the verdict rests on |
| **Full analysis** | The complete written analysis, when there are no findings to list |
| **Investigation trail** | Every step CloudThinker took, when there are no findings to list |
| **Affected services** | Services and dependencies involved |
| **Duplicate webhooks** | Repeat deliveries of the same alert, when there were any. Many duplicates point at a source that retries: check the tool's retry setting, or the fields Pulse uses to spot duplicates in [Limits and responses](/guide/incident/webhook-integrations/overview#limits-and-responses). |
| **Was Resolve's diagnosis right?** | Thumbs up or down on the verdict, or **Confirm cause** / **Not the cause** when it names a root cause. These answers feed the **Accuracy and trust** tab. See [Mark a diagnosis right or wrong](/guide/incident/insights#mark-a-diagnosis-right-or-wrong). |

When CloudThinker thinks the severity is wrong, the incident's **More actions** menu shows **AI suggests** with the suggested level. Click it to see the current and suggested levels, then click **Apply** the suggested level or **Keep** the current one.

Here's what a short result can look like:

```text
Root cause                                     Strong evidence
checkout-api pods ran out of memory after payment-client v2.3 doubled
its connection pool. Restarts cleared it for minutes at a time.

Actions
High    Roll back payment-client to v2.2 on prod-eu
Medium  Set a pool size limit in the payment-client config
```

### Evidence labels

The label next to the heading says how strong CloudThinker rates its evidence:

| Label | Meaning | How to treat it |
|---|---|---|
| **Strong evidence** | Confirmed against data from your systems, shown under **Evidence** | Review the findings it rests on, then act. Any change still runs through a runbook and your Approvals settings. |
| **Probable** | Reasoned from the evidence, not directly confirmed | Check the evidence before acting |
| **Possible** | The verdict rests on an assumption | Treat it as a lead. Add access or context and [investigate again](#re-investigation). |

**Possible** is a verdict with weak support. **Not found** is a status that means no verdict at all.

### Settle each remediation suggestion

Hover a suggestion in **Actions**, open its **More remediation actions** menu, and choose:

| Action | Use it when | Add a note about |
|---|---|---|
| **Mark as Done** | Your team did the work | What you actually did |
| **Dismiss** | It doesn't apply or isn't worth doing | Why |

The note is optional and stays on the suggestion for anyone reviewing the incident. Settling is final: the menu disappears once a suggestion is marked, and there's no undo. A later investigation session doesn't overwrite it either.

## Investigation outcomes

Each status maps to a queue group:

| Status | Meaning | Queue group |
|---|---|---|
| **Open**, **Acknowledged** | No outcome yet. **Acknowledged** means a responder owns it. | **Not started** before any investigation, **Needs you** after one finishes |
| **Identified** | A root cause was found | **Needs you** |
| **On hold** | Waiting for information, access, or a decision from a person | **Needs you** |
| **Not found** | The available evidence didn't support a root cause | None. The queue doesn't list it. |
| **False alarm** | The alert wasn't a real problem | **Dismissed** |
| **Resolved** | Fixed and closed with a person involved | **Resolved** |
| **Auto-resolved** | Fixed and closed by the agent with nobody involved | **Resolved** |

An incident can also sit in **Needs you** for one of these reasons:

| What you see | Meaning | What to do |
|---|---|---|
| A result, but the status is still **Open**, **Acknowledged**, or **Investigating** | The investigation finished without moving the status | Read the result, then set the status yourself |
| The row shows **Failed**, and the incident page says the investigation stopped | The session failed or was cancelled | Click **Retry investigation** |
| A triage note, but no verdict | Triage couldn't decide whether the alert needs action | Read the source alerts with **View origin**, then set the status yourself |

<Warning>
Known limitation: a **Not found** incident drops out of the queue. No queue group or filter lists it. Before you leave its page, either move it on or copy its URL:

- To keep working on it, add the missing [connection](/guide/connections/overview), click the status badge, and choose **Investigating**. An incident that was investigated before returns to **Needs you**, not **Not started**, where you can [investigate again](#re-investigation).
- To drop it, choose **Investigating**, then open the badge again and pick **Resolved** or **False alarm**.
- To come back later, bookmark the incident's URL. That's the only way back to it.
</Warning>

## Re-investigation

An incident has one investigation record. A session is one investigation conversation. Asking again in that conversation stays in the same session. A later session can start when triage matches a new alert to the incident.

The **Investigate** button only appears before the first investigation. To investigate again with new access or context:

<Steps>
  <Step title="Add what was missing">
    Add the missing [connection](/guide/connections/overview), or note the context you want CloudThinker to use.
  </Step>
  <Step title="Open the conversation">
    In the incident header, open **More actions → Open AI Conversation**.
  </Step>
  <Step title="Ask it to look again">
    Say what changed. For example: `I've connected the prod-eu Datadog account. Re-check the root cause.`

    **Success state:** the findings it records appear on the incident page, and the answer at the top updates if the root cause changes. If nothing changes, the reply didn't change the incident.
  </Step>
</Steps>

If the session failed (the queue row shows **Failed**), the incident page says the investigation stopped. Click **Retry investigation** there. Admin only.

## Correlated incidents

When several alerts share a likely cause, Resolve groups them under one parent incident and runs a single RCA there. Opening a grouped alert shows a **Part of a Correlated Group** card:

| Option | What it does |
|---|---|
| **View Parent Analysis** | Opens the parent incident that owns the investigation |
| **Promote to Standalone** | Detaches the alert into its own incident. After you confirm, choose whether to start RCA on it now or leave it for later. Admin only. |

Grouping starts in Pulse. To make related alerts group correctly, map **Resource ID Path** on each webhook so repeats of one fault group, and **Service Path** to a single service name so different alerts about one service can join. See [How signals join a cluster](/guide/pulse/clusters#how-signals-join-a-cluster).

## Share or export the result

From the incident's **More actions** menu:

- **Download analysis PDF** saves the analysis as a PDF.
- **Open AI Conversation** opens the full investigation conversation, where you can ask follow-up questions.
- **View origin** shows the alerts and Pulse data the incident came from.

## Troubleshooting

| Problem | Fix |
|---|---|
| No **Investigate** button | The incident already has an investigation (see [Re-investigation](#re-investigation)), a session is running, or it's part of a correlated group (use **View Parent Analysis**). It also needs the Admin role. |
| An alert never became an investigated incident | Check **AI auto-investigate**, the webhook's **Auto-investigate** and minimum severity against [What starts an investigation](/guide/incident/settings#what-starts-an-investigation). To start one now, click **Open incident** and **Send to triage** on its cluster in **Resolve → Signals**. |
| An incident stays in **Not started** | Click **Investigate**. |
| Verdict is **Possible** or status is **Not found** | RCA couldn't read enough. Add the missing [connection](/guide/connections/overview), then ask again in the conversation. A **Not found** incident must be moved back to **Investigating** first. See [the Not found warning](#investigation-outcomes) and [Re-investigation](#re-investigation). |
| Stuck in **On hold** | Open the conversation with **Open AI Conversation** and answer what CloudThinker asked for. |
