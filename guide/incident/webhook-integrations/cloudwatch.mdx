This guide sends every CloudWatch alarm state change to Resolve, so CloudThinker sees the alarm within seconds and can open an incident and start a root cause analysis (RCA). Amazon EventBridge does the delivery: no Lambda function and no code to maintain.

## How it works

```text
CloudWatch alarm → EventBridge rule → API destination → CloudThinker webhook URL → Pulse
```

When an alarm changes state, EventBridge forwards the event to your CloudThinker webhook URL. Resolve turns it into a **signal** (one alert that passed noise filtering) in [Pulse](/guide/pulse/overview). Pulse groups related signals, and an actionable group becomes an incident.

## Prerequisites

- Permission to manage Resolve integrations in your CloudThinker workspace.
- An AWS account where you can create EventBridge connections, API destinations, and rules.
- At least one CloudWatch alarm in the region you're setting up.
- The AWS CLI, if you want to test with a simulated alarm (recommended).

## Create the webhook in CloudThinker

<Steps>
  <Step title="Open the AWS platform">
    Go to **Resolve → Integrations** and select **Amazon Web Services**. Under **Signals to Resolve**, click **Add signal**. The **Create Webhook** dialog opens with the AWS CloudWatch preset.
  </Step>
  <Step title="Basic Info">
    Keep the default **Webhook Name** or rename it, for example `Production CloudWatch`. Click **Next**.
  </Step>
  <Step title="Configure">
    **Field Mapping** and **Severity Mapping** are pre-filled for EventBridge events (see the tables below). Leave them as they are for a first setup. Click **Next**.
  </Step>
  <Step title="Advanced">
    **Auth Method** is already **API Key** with the header `x-api-key`. That's what EventBridge sends, so don't change it. Set **Auto-investigate** (on by default) and click **Create**.
  </Step>
  <Step title="Copy the URL and secret">
    Copy the **Webhook URL** and the secret key from the dialog that opens. You'll paste both into AWS next.
  </Step>
</Steps>

**Success state:** the webhook appears under **Signals to Resolve** on the Amazon Web Services platform.

<Warning>
The secret key is shown only once. If you close the dialog without copying it, you have to regenerate the credentials, and every sender using the old secret stops working.
</Warning>

You don't need an AWS connection to receive alarms. Add an [AWS connection](/guide/connections/aws) as well if you want CloudThinker to query the affected resources during RCA.

## Set up EventBridge in AWS

Do these steps in the AWS console, in the same region as your alarms.

<Steps>
  <Step title="Create a connection">
    Open **Amazon EventBridge → Integration → Connections** and click **Create connection**. Set:

    | Field | Value |
    |---|---|
    | Name | `cloudthinker-webhook` |
    | Authorization type | API Key |
    | API key name | `x-api-key` |
    | Value | The secret key from CloudThinker |
  </Step>
  <Step title="Create an API destination">
    Open **Integration → API destinations** and click **Create API destination**. Set:

    | Field | Value |
    |---|---|
    | Name | `cloudthinker-resolve` |
    | API destination endpoint | The **Webhook URL** from CloudThinker |
    | HTTP method | `POST` |
    | Connection | `cloudthinker-webhook` |
  </Step>
  <Step title="Create a rule">
    Open **Rules**, select the **default** event bus, and click **Create rule**. Choose **Rule with an event pattern** and paste this pattern:

    ```json
    {
      "source": ["aws.cloudwatch"],
      "detail-type": ["CloudWatch Alarm State Change"]
    }
    ```

    For the target, choose **EventBridge API destination**, select `cloudthinker-resolve`, and let AWS create an execution role (it needs `events:InvokeApiDestination`). Click **Create rule**.
  </Step>
</Steps>

**Success state:** the rule shows as **Enabled** with your API destination as its target.

## Test the integration

<Steps>
  <Step title="Force an alarm">
    Replace `YourAlarmName` with a real alarm in the same region:

    ```bash
    aws cloudwatch set-alarm-state \
      --alarm-name "YourAlarmName" \
      --state-value ALARM \
      --state-reason "Testing CloudThinker integration"
    ```
  </Step>
  <Step title="Check Pulse">
    Open **Resolve → Pulse**. Within a few seconds a signal appears, titled with the alarm name and marked **High** severity.
  </Step>
  <Step title="Reset the alarm">
    Run the same command with `--state-value OK`. CloudWatch then evaluates the alarm normally again.
  </Step>
</Steps>

**Success state:** the signal shows the alarm name as its title, the state reason as its description, and the metric namespace (for example `AWS/EC2`) as its service.

## Field and severity mapping

The preset reads these fields from the EventBridge event:

| Field | Path | Example value |
|---|---|---|
| **Title Path** | `detail.alarmName` | `HighCPUUtilization` |
| **Description Path** | `detail.state.reason` | `Threshold Crossed: 1 out of the last 1 datapoints [85.0] was greater than the threshold (80.0)` |
| **Severity Path** | `detail.state.value` | `ALARM` |
| **Service Path** | `detail.configuration.metrics[0].metricStat.metric.namespace` | `AWS/EC2` |

| CloudWatch state | CloudThinker severity |
|---|---|
| `ALARM` | High |
| `INSUFFICIENT_DATA` | Medium |
| `OK` | Info |

Want production alarms to be critical? Edit the webhook and change the `ALARM` row in **Severity Mapping**. A state with no mapping row falls back to Medium.

## Send only the alarms you care about

Narrow the EventBridge rule's event pattern instead of filtering in CloudThinker. Add a `detail` block to the base pattern:

| Goal | Add to the pattern |
|---|---|
| Only alarms named `prod-*` | `"detail": { "alarmName": [{ "prefix": "prod-" }] }` |
| Skip recoveries | `"detail": { "state": { "value": ["ALARM", "INSUFFICIENT_DATA"] } }` |

## More than one region

CloudWatch only sends alarm events to EventBridge in the alarm's own region. To cover several regions, either repeat the connection, API destination, and rule in each region (all pointing to the same webhook URL), or forward events from each region to one central event bus and route from there.

<Note>
CloudThinker also accepts Amazon SNS HTTPS subscriptions: it confirms the subscription and verifies each notification. The CloudWatch preset is built for the EventBridge event shape, so use EventBridge unless you have a reason not to.
</Note>

## Troubleshooting

<AccordionGroup>
  <Accordion title="No signal appears in Pulse">
    **Check the rule:** in EventBridge, open the rule's **Monitoring** tab. If `Invocations` stays at 0, the pattern isn't matching (see the next item).
    **Check the destination:** the API destination endpoint must be the exact **Webhook URL** from CloudThinker.
    **Check Pulse:** widen the time window on **Resolve → Pulse**. Pulse can also suppress an alert as noise, see [Pulse clusters](/guide/pulse/clusters).
  </Accordion>
  <Accordion title="The rule never matches">
    The rule must be on the **default** event bus, in the same region as the alarm. The `detail-type` value is case-sensitive: `CloudWatch Alarm State Change`.
  </Accordion>
  <Accordion title="EventBridge reports 401 or 403">
    The connection's API key name must be `x-api-key` and its value must be the CloudThinker secret key. If you lost the secret, regenerate it from the webhook's details and update the EventBridge connection.
  </Accordion>
  <Accordion title="Signals arrive but the title or severity is empty">
    The field paths must start with `detail.`, because that's where EventBridge puts the alarm. Paths like `AlarmName` or `NewStateValue` come from the older SNS format and won't match.
  </Accordion>
  <Accordion title="EventBridge reports 429">
    The webhook's rate limit was reached. Edit the webhook and raise **Rate limit (requests per hour)**, or narrow the rule's event pattern.
  </Accordion>
  <Accordion title="An incident opened but no RCA started">
    **Auto-investigate** is off, the severity is below its minimum, or **On duty** is paused. See [Resolve settings](/guide/incident/settings).
  </Accordion>
</AccordionGroup>
