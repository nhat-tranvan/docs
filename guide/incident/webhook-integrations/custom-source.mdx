description: "Connect any system that can POST JSON to Resolve, capture one real event, and map its fields by clicking them."

A custom source connects a system that has no preset in Resolve: an in-house uptime checker, a cron job, a deploy script, or a vendor CloudThinker doesn't list yet. If it can send an HTTP POST with a JSON body, its events can open incidents and trigger a root cause analysis (RCA).

## How it works

You create an endpoint, send it one real event, then click the fields in that event to tell Resolve which one is the title, severity, and so on. Because you pick from a payload your system really sent, every mapping you save points at a field that exists.

Each event becomes a **signal** in [Pulse](/guide/pulse/overview), where it's filtered, grouped with related signals, and routed into an incident when it's actionable.

<Note>
A custom source isn't the same as a conversation webhook. A custom source feeds Pulse and opens incidents. If you want an event to start a chat with CloudThinker instead, use [webhooks](/guide/webhooks/overview).
</Note>

## Prerequisites

- The workspace **Admin** role. Developers and Viewers can see sources but can't add or change them. See [Roles](/guide/security/roles).
- A system that can send `POST` requests with a JSON object body. A new source expects an `Authorization` header. If your system can't set headers, see [Authentication options](#authentication-options).
- A way to fire one representative event on demand, such as a test button or a `curl` command.

## Create the source

Go to **Resolve → Integrations**, open the **Custom source** card, and click **Add signal**. Every custom source you create is listed on this one card.

<Steps>
  <Step title="Name the source">
    Enter a **Source name** your team will recognize, for example `Acme uptime`, and click **Create endpoint**.
  </Step>
  <Step title="Copy the URL and secret">
    The dialog shows the **Webhook URL** and the **Secret Key**. Copy both into your system now.

    The **Secret Key** is shown only once. If you lose it, see [Rotate or replace credentials](#rotate-or-replace-credentials).
  </Step>
  <Step title="Send one real event">
    <Warning>
    The capture event goes through Pulse like any other event, and **Auto-investigate** is already on. If Pulse judges it actionable, it opens an incident and starts an investigation. To make that unlikely, add a top-level `"title": "Test notification, ignore"` and `"severity": "info"` to the capture body, next to your real fields. Until you save a mapping, Resolve reads those two keys, and Pulse treats a test notification as not actionable. It isn't guaranteed: if an incident opens anyway, close it.

    Those two keys show up in the picker. Don't map them. Pick your real fields instead, such as `event.data.title`.
    </Warning>

    Trigger the event from your system. The dialog waits and updates itself when the event arrives. If it doesn't update after you send, resend and click **Check again**.

    Send a representative event, not an empty test body. You can only map fields that this event contains.
  </Step>
  <Step title="Map the fields">
    When the dialog says **Payload received**, click **Map the fields**. Every field in the captured JSON is listed with its value. Pick the one for **Incident title**, then any of **Severity**, **Service**, **Resource**, and **Description**. Click **Save mapping**. The dialog closes.

    Fields inside a list show with their index, such as `alerts[0].labels.severity`, for the first three items. Here you can only pick from the captured event. To use a path the event doesn't contain, type it into the matching field in **Edit**, where every path is a text field.

    **Resource** here is a display name only (the Edit view calls it **Resource Name Path**). Grouping uses **Resource ID Path**, which you set in the next step.

    If a later event lacks a mapped field, Resolve falls back: the title to a top-level `title` key or `Webhook signal`, severity to Medium, service to `unknown`, and the timestamp to the receive time.
  </Step>
  <Step title="Finish in Edit">
    Open the source's **...** menu under **Signals to Resolve** and choose **Edit**. Setup isn't finished until you set these three fields, which the setup dialog doesn't have:

    - **Resource ID Path**: a stable identifier, such as a host ID or check ID. Pulse uses it to group repeats of the same fault. Without it, every event can open its own cluster.
    - **Severity Mapping**: a row for each severity value your system sends that isn't `critical`, `high`, `medium`, `low` or `info`. Without one, those events arrive as Medium.
    - **Rate limit (requests per hour)**: raise it from 1,000 if your system can send more in an hour.

    This is also where you turn **Auto-investigate** off, or set **Only from a minimum severity**.
  </Step>
</Steps>

**Success state:** the source appears under **Signals to Resolve** on the Custom source card. The next event arrives in Pulse with the title and severity you mapped, and repeats of the same fault join one cluster.

## Edit a source

Open **Resolve → Integrations → Custom source**, find the source under **Signals to Resolve**, and choose **Edit** from its **...** menu. The edit view has every mapping field (including **Resource ID Path** and **Timestamp Path**), **Severity Mapping**, **Auto-investigate** with **Only from a minimum severity**, and **Rate limit (requests per hour)**.

**Severity Mapping** matching ignores case. For example:

| Your value | CloudThinker severity |
|---|---|
| `P1` | critical |
| `P2` | high |
| `P3` | medium |

## Send events

A new custom source expects `Authorization: Bearer <secret>`, with the **Secret Key** as the token. It doesn't accept `x-api-key` until you change the method (see [Authentication options](#authentication-options)). Here's a complete example:

```bash
curl -X POST "<your-webhook-url>" \
  -H "Authorization: Bearer <your-secret-key>" \
  -H "Content-Type: application/json" \
  -d '{
    "event": {
      "data": {
        "title": "Checkout latency above 2s",
        "priority": "critical",
        "service": "checkout-api",
        "host": "web-03",
        "summary": "p95 latency 2.4s for 5 minutes"
      }
    }
  }'
```

Mapped to this payload, the fields look like this:

| Field | Where you set it | Path you'd pick | What it does |
|---|---|---|---|
| **Incident title** (required) | Setup or Edit | `event.data.title` | Names the signal and the incident. |
| **Severity** | Setup or Edit | `event.data.priority` | Feeds routing and the automatic RCA threshold ([Only from a minimum severity](/guide/pulse/setup#webhook-options-that-change-behavior)). |
| **Service** | Setup or Edit | `event.data.service` | Names the affected service on the signal. Shows `unknown` when unmapped. |
| **Resource** | Setup or Edit (**Resource Name Path**) | `event.data.host` | Display name of the affected host, cluster, or component. |
| **Resource ID** | Edit only (**Resource ID Path**) | `event.data.host` | Stable key for grouping. Pulse joins a repeat to the open cluster when the source, alert type, and resource ID match. Map it, or every event can open its own cluster. |
| **Description** | Setup or Edit | `event.data.summary` | Gives responders and CloudThinker the symptom in your system's words. |
| **Timestamp** | Edit only (**Timestamp Path**) | none here | When the event started. Must be ISO 8601, like `2026-10-25T14:02:00Z`. A value without a time zone is read as UTC. Unmapped, or in another format such as epoch seconds, the receive time is used. |

With the mapping from the table above, this event arrives in Pulse as a signal titled `Checkout latency above 2s`, severity **Critical**, service `checkout-api`, resource `web-03`.

## Authentication options

Change the method in the source's edit view under **Auth Method**. Changing it breaks current senders at once.

| Auth Method | What the sender sends | Risk |
|---|---|---|
| **Bearer Token** (default) | `Authorization: Bearer <secret>` | The secret travels in a header. Fine over HTTPS for most senders. |
| **HMAC Signature** | `X-Webhook-Signature: sha256=<hex digest>` of the raw body (the header name is configurable) | The strongest option: the secret never leaves the sender, and a changed body fails the check. |
| **API Key** | The secret in a header you name, such as `X-Api-Key`, with an optional prefix | Same as Bearer. Use it when the sender only supports a named key header. |
| **No Authentication** | Nothing | The URL is the only credential. Anyone who has it can post events. Use it only when the sender can't set any header. |

## Responses

Write your sender's retry logic against these responses:

| Status | Meaning | What to do |
|---|---|---|
| `2xx` | Accepted and queued. It doesn't yet mean a signal was created. | Check Pulse (see [Verify the whole path](#verify-the-whole-path)). |
| `400` | CloudThinker has paused or disabled the source. No Resolve screen does this, and your sender didn't cause it. | Don't retry. Email [support@cloudthinker.io](mailto:support@cloudthinker.io) with the source name and workspace, and ask for the source to be re-enabled. |
| `401` | The `Authorization` header is missing, or the URL isn't a current **Webhook URL** (wrong, or replaced by **Regenerate credentials**). | Fix the header or the URL. Don't retry unchanged. |
| `403` | The secret is wrong, or the header isn't in the form `Bearer <secret>`. | Fix the header. Don't retry with the same secret. |
| `413` | The body is larger than 1 MB. | Send a smaller body. |
| `422` | The body isn't a JSON object: invalid JSON, an array, or a plain value. | Fix the body. Don't retry unchanged. |
| `429` | Over 10 times the hourly rate limit, 10 failed authentication attempts within 15 minutes, or CloudThinker briefly busy. | Retry with backoff, after the `Retry-After` header when present. For an auth lockout, fix the secret, then wait: the window starts at the first failure and clears 15 minutes later. **Regenerate credentials** doesn't clear it. |
| `5xx` | A temporary problem on CloudThinker's side. | Retry with backoff. |

Each source allows 1,000 requests per hour by default. Change it in the edit view under **Rate limit (requests per hour)**: up to 10,000, or `0` for no limit. A `429` comes back only at 10 times the limit: at the default 1,000, after 10,000 requests within the same hour.

<Warning>
Events over the hourly limit still get a `2xx`, then are dropped before Pulse, whatever their severity. The sender sees no error, and no Resolve screen lists the dropped events. Raise the limit before a planned burst.

To check for drops after a burst, set the **Resolve → Pulse** time window to **Last 1 hour** and read the **raw events** count in the header. Compare it with what your sender reports sending in the same hour. Raw events counts every source in the workspace, so a lower number means events were dropped.
</Warning>

## Rules for payloads and paths

| Rule | What it means for you |
|---|---|
| Send a JSON object | A JSON array or a plain value is rejected with `422`. `{}` is accepted but has nothing to map, and the dialog tells you so. |
| Paths are dotted | `event.data.title` reads `title` inside `data` inside `event`. A list index is `[0]`, as in `alerts[0].labels.severity`. |
| At most 8 segments | A path deeper than 8 levels is rejected. Send a flatter body if your value is nested deeper. |
| JSONPath prefix is optional | A leading `$.` is accepted and removed, so `$.event.data.title` works too. |
| Severity values | Only `critical`, `high`, `medium`, `low`, and `info` are understood as-is (any case). Everything else, including `warning`, `error`, `sev1` and `P1`, becomes Medium unless you map it in **Severity Mapping**. |
| Repeats are dropped | Pulse drops an exact repeat: same title, severity and resource ID, with an event timestamp in the same minute as an event it saw in the last hour. Without **Timestamp Path**, the timestamp is the receive time, so only two sends within the same minute match. With it, a resend carrying the original timestamp is dropped for up to an hour. When you resend a test, change the title. See [noise suppression](/guide/pulse/clusters#noise-suppression). |

## Verify the whole path

A successful HTTP response only proves delivery. Open **Resolve → Pulse**: the signal should appear within a few seconds. Confirm its title and severity. If **Auto-investigate** is on and the severity clears its minimum, the incident shows **AI is handling** on **Resolve → Investigation**.

A test event is treated like a real one, so with **Auto-investigate** on it can start a real investigation. To test delivery only, turn **Auto-investigate** off in the edit view first, and back on after. Avoid pausing **On duty** for this: it affects every source in the workspace.

## Rotate or replace credentials

**Regenerate credentials** (the source's **...** menu under **Signals to Resolve**) replaces both the **Webhook URL** and the **Secret Key**. The old pair stops working at once, with no overlap, so senders fail until you update them. Each regeneration is recorded in [Audit Logs](/guide/security/audit-logs).

To rotate without a gap:

1. Create a second custom source and map it from one real event, as in [Create the source](#create-the-source).
2. In the new source's edit view, copy over what the setup dialog doesn't carry: **Resource ID Path**, **Timestamp Path**, **Severity Mapping**, **Rate limit (requests per hour)**, **Auto-investigate** and **Only from a minimum severity**, and **Auth Method** if you changed it.
3. Point each sender at the new URL and secret.
4. When the old source's events stop arriving in Pulse, delete the old source.

If a short gap is fine, regenerate and update every sender right after.

## Security and data

| Topic | What to know |
|---|---|
| URL | Each source gets its own **Webhook URL** with a long random token, so one source's URL can't be guessed from another's. |
| Authentication | By default, every request needs the **Secret Key** as `Authorization: Bearer <secret>`. After 10 failed attempts within 15 minutes, the source answers `429` until the window clears (see [Responses](#responses)). |
| Payload signing | With **HMAC Signature**, the sender signs the raw body with HMAC-SHA256. Paste your own secret into **Provider signing secret** in the edit view, which keeps the **Webhook URL**. Or click **Regenerate credentials** after saving to get a new secret, which also changes the **Webhook URL**. See the example below. |
| Stored payloads | Stored event bodies expire after 90 days. |

To send a signed event, set **Auth Method** to **HMAC Signature** in the edit view and save. Then put the signing secret (your **Provider signing secret**, or the secret from **Regenerate credentials**) in `SECRET` and sign the exact bytes you send. The example uses the default header name:

```bash
read -rs SECRET   # paste the signing secret, then press Enter
BODY='{"title":"Checkout latency above 2s","severity":"high"}'
SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$SECRET" -hex | sed 's/^.* //')
curl -X POST "<your-webhook-url>" \
  -H "X-Webhook-Signature: sha256=$SIG" \
  -H "Content-Type: application/json" \
  --data-raw "$BODY"
```

## Troubleshooting

<AccordionGroup>
  <Accordion title="The dialog keeps waiting for the first payload">
    Check that your system posts to the exact **Webhook URL** and sends `Authorization: Bearer <secret>`. Click **Check again** after you resend.
  </Accordion>
  <Accordion title="The event arrived but no fields can be mapped">
    The body wasn't a JSON object with values in it. Send an object such as `{"title": "..."}`, not an array or an empty body, then click **Check again**.
  </Accordion>
  <Accordion title="Signals are titled 'Webhook signal'">
    Events that arrive before you save a mapping still become signals. Resolve uses a top-level `title` key if there is one, and otherwise falls back to `Webhook signal`. Save a mapping to fix new events.
  </Accordion>
  <Accordion title="There's no payload to pick from when editing">
    The picker shows the last stored event, and stored event bodies expire after 90 days. Fire the source once more, then map.
  </Accordion>
  <Accordion title="Everything arrives as Medium severity">
    Your system sends severity values Resolve doesn't recognize. Add rows to **Severity Mapping** in the edit view, for example `p1` → critical. See [Edit a source](#edit-a-source).
  </Accordion>
</AccordionGroup>
