A webhook signal is a URL that your monitoring tool calls each time an alert fires, so Resolve sees the alert within seconds. You create one per tool, map the tool's JSON fields to a title, severity, and service, and decide whether CloudThinker starts a root cause analysis (RCA) on its own.

## How an alert flows

An alert that reaches the webhook doesn't become an incident directly. It goes through [Pulse](/guide/pulse/overview) first.

```mermaid
flowchart LR
    A["Monitoring tool"] -->|POST| B["Webhook URL"]
    B --> C["Pulse: suppress noise, group into clusters"]
    C -->|actionable| D["Incident"]
    D -->|Auto-investigate on| E["RCA starts"]
```

A **signal** is one raw event Pulse received. Pulse marks some signals as suppressed (noise) and groups the rest into clusters. A **cluster** is a group of related signals that Pulse treats as one problem. Only an actionable cluster turns into an incident.

## Prerequisites

- The workspace **Admin** role.
- Admin access to the monitoring tool, so you can add a webhook to it.
- One real alert payload you can trigger on demand, or a sample of its JSON.

## Create the webhook

<Steps>
  <Step title="Open the platform">
    Go to **Resolve → Integrations** and select your tool, for example Datadog, Grafana, or PagerDuty.
  </Step>
  <Step title="Add a signal">
    Under **Signals to Resolve**, click **Add signal** (or **Add another signal**). The **Create Webhook** dialog opens with three steps.
  </Step>
  <Step title="Basic Info">
    Keep or change **Webhook Name** (it defaults to `<Tool> Webhook`) and add an optional **Description**. Click **Next**.
  </Step>
  <Step title="Configure">
    Check **Field Mapping** and **Severity Mapping**. Both come pre-filled for the tool you picked. Leave **Send directly to CloudThinker** off ([why](#decide-when-rca-starts)). Follow the **Setup Guide** for that tool at the bottom of the step. Click **Next**.
  </Step>
  <Step title="Advanced">
    Pick an **Auth Method** and set **Auto-investigate** (both explained below). Click **Create**.
  </Step>
</Steps>

**Success state:** a dialog shows the **Webhook URL**, the secret under **Authentication Setup**, and **Integration Examples** with **cURL**, **JavaScript**, **Python**, and **Node.js** tabs. Copy the URL and secret now, then paste them into your monitoring tool. The **cURL** tab is the fastest way to send a test.

<Tip>
Copy the secret before you click **Done**. If you lose it, go to **Resolve → Integrations**, open the tool, and under **Signals to Resolve** open the webhook row's **Manage** menu (**⋯**) → **Regenerate credentials**. That invalidates the current token and secret, so every tool using them needs the new value.
</Tip>

## Map the fields

Each mapping field takes a path into the alert's JSON. Only **Title Path** is required.

- Use dotted keys, like `event.data.title`, and `[n]` for a list item, like `alerts[0].labels.severity`. A leading `$.` is accepted and dropped.
- A path can have at most 8 segments. Keys that contain a dot can't be addressed, and there are no fallback paths.
- A path must end at a single text or number value. A path that ends at a list or object maps to nothing.

| Field | What it fills in |
|---|---|
| **Title Path** | The incident title. Required. |
| **Severity Path** | The severity level, translated by **Severity Mapping**. |
| **Description Path** | The incident description. |
| **Service Path** | The affected service. Helps Pulse group related alerts. |
| **Resource ID Path** | The affected resource's identifier. |
| **Resource Name Path** | The affected resource's name. |
| **Timestamp Path** | When the event started. |

Your tool decides the payload shape. In Datadog, for example, you write the JSON yourself in the webhook's **Payload** field, using Datadog's template variables. The Datadog preset reads `title`, `body`, and `alert_type`. Add a `service` key with one service name, because the preset's default **Service Path** (`tags`) points at a list and maps to nothing:

```json
{
  "title": "$EVENT_TITLE",
  "body": "$EVENT_MSG",
  "alert_type": "$ALERT_TYPE",
  "service": "web-api"
}
```

| Field | Path | Example value |
|---|---|---|
| **Title Path** | `title` | High CPU on web-server-01 |
| **Description Path** | `body` | CPU usage exceeded 90% for 5 minutes |
| **Severity Path** | `alert_type` | error |
| **Service Path** | `service` (change it from `tags`) | web-api |

A fixed `service` value applies to every monitor that notifies this webhook. Datadog's `$ALERT_TYPE` sends `error`, `warning`, `info`, or `success`, but the Datadog preset's **Severity Mapping** covers `alert`, `warn`, `ok`, and `no data`. Add rows for the values you actually send.

**Severity Mapping** translates the tool's own words into CloudThinker's five levels: critical, high, medium, low, and info. The generic preset maps `warning` to medium and `error` to high, for example. Add a row for any value your tool sends that isn't covered.

If your tool isn't listed, use [Custom source](/guide/incident/webhook-integrations/custom-source) instead. It captures one real payload and lets you click the fields to map.

## Choose authentication

| Auth Method | Your tool sends | Use when |
|---|---|---|
| **Bearer Token** | `Authorization: Bearer <secret>` | The tool lets you add a custom header. Default for most tools. |
| **HMAC Signature** | A signature header computed from the body, such as `X-PagerDuty-Signature` | The tool signs its webhooks, like PagerDuty. Set the header name in **HMAC Signature Header**. If the tool generates its own signing secret, paste it into **Provider signing secret**. |
| **API Key** | The key in a header you name | The tool only supports API key headers, like CloudWatch through EventBridge. Set **API Key Header** and an optional **Key Prefix**. |
| **No Authentication** | Nothing | Only for a quick test. Anyone with the URL could send alerts. |

## Decide when RCA starts

**Auto-investigate** is on by default. CloudThinker starts one root cause investigation when this webhook creates an incident. Turn it off and CloudThinker investigates only when someone asks.

| Setting | Effect |
|---|---|
| **Auto-investigate** off | No automatic RCA from this webhook. |
| **Auto-investigate** on | Every incident from this webhook gets an RCA. |
| **Auto-investigate** on, with **Only from a minimum severity** | Pick a floor, for example **High and above**. Alerts below it still group with related alerts, but get no automatic RCA. |

The **On duty** switch in the **Resolve → Investigation** header also has to be on. When it shows **Paused**, incidents still open, but no RCA starts until someone starts it. See [Resolve settings](/guide/incident/settings).

**Send directly to CloudThinker** (on the **Configure** step, off by default) skips Pulse filtering and grouping. CloudThinker then judges each event on its own. Leave it off unless the tool already deduplicates its alerts.

## Test the whole path

<Steps>
  <Step title="Fire one real alert">
    Trigger a representative alert from your tool, or send the request from the **cURL** tab in **Integration Examples**. A successful delivery returns `200` with `"success": true`.
  </Step>
  <Step title="Check Pulse">
    Open **Resolve → Pulse** and find the signal with the title you mapped.
  </Step>
  <Step title="Check the incident">
    If the cluster is actionable, open **Resolve → Investigation**. With **Auto-investigate** and **On duty** both on, the incident shows **AI is handling**.
  </Step>
</Steps>

**Success state:** the signal appears in Pulse with the right title, severity, and service, and an eligible incident shows **AI is handling**. A `200` alone only proves delivery.

Test one normal alert and one critical alert, so you know both severity mappings work.

## Limits and responses

| Response | When |
|---|---|
| `200` with `"success": true` | The delivery was accepted. |
| `401` or `403` | Credentials are missing or wrong, or the webhook is disabled. |
| `404` | The webhook URL doesn't exist. |
| `413` | The body is larger than 1 MB. |
| `429` | Too many requests, or too many failed auth attempts. Retry after the time in the `Retry-After` header when it's present. |

Pulse treats a delivery as a duplicate when its source, resource, title, severity, and event time (to the minute) match a signal from the last hour. A duplicate adds to that signal's count instead of creating a new one. A cluster closes after 12 hours with no new signal, or when a person resolves it. See [Cluster lifecycle](/guide/pulse/clusters#cluster-lifecycle).

## Troubleshooting

<AccordionGroup>
  <Accordion title="The tool reports 401 or 403">
    **Cause:** the auth header doesn't match the **Auth Method**. **Check:** the header name and secret in your tool against **Authentication Setup**. **Fix:** paste the secret again, or use **Regenerate credentials** in the webhook row's **Manage** menu under **Resolve → Integrations**.
  </Accordion>
  <Accordion title="Delivery succeeds but nothing appears in Pulse">
    **Cause:** Pulse suppressed the alert as noise, or the time window hides it. **Check:** widen the window on **Resolve → Pulse**. **Fix:** see [Pulse clusters](/guide/pulse/clusters) for how suppression works.
  </Accordion>
  <Accordion title="Signals arrive with an empty title or the wrong severity">
    **Cause:** a path doesn't match the payload, or the tool's severity value has no mapping row. **Fix:** compare the paths against a real payload, then add the missing value to **Severity Mapping**.
  </Accordion>
  <Accordion title="An incident opened but no RCA started">
    **Cause:** **Auto-investigate** is off, the severity is below the floor, or **On duty** shows **Paused**. **Fix:** check all three, or start the investigation by hand.
  </Accordion>
</AccordionGroup>
