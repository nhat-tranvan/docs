Incident memory is the set of notes CloudThinker writes at the end of a [root cause investigation](/guide/incident/root-cause-analysis) and reads at the start of the next one. When the same service fails the same way again, CloudThinker starts from what your team already learned instead of from zero.

## Prerequisites

- Resolve receiving alerts from at least one source. See [Connect Pulse sources](/guide/pulse/setup).
- The workspace **Admin** role to start investigations. Developers and Viewers can read the results. See [Roles](/guide/security/roles).
- Nothing to switch on: incident memory is on by default. In a self-hosted deployment, an instance administrator can turn it off.

## What CloudThinker records

CloudThinker writes memory itself. You don't fill in a form, and not every incident produces an entry. Each entry is one of three kinds, and an entry that breaks its rule is discarded when CloudThinker reads memory back.

| Kind | What it holds | Kept only if |
|---|---|---|
| **Recollection** | One incident's story: symptom, root cause, what changed, the fix, and a check that proves the fix | It's tied to a specific incident |
| **Observation** | A finding from a live investigation | It includes an `Action:` line telling a responder what to do |
| **Lesson** | A pattern seen across incidents | It cites at least two source incidents |

CloudThinker writes or updates a recollection after any run where it actually investigated and reached a disposition (it saved an assessment, a severity and a close decision). It writes nothing for a plain question, an aborted run, or a run that never reached a disposition. When an incident reopens, CloudThinker updates that incident's existing recollection instead of adding a second one.

Every recollection follows the same five-line shape. This example shows what one looks like:

```text
Symptom: checkout-api 5xx rate above 20% on target group tg-checkout at 14:02 (CloudWatch)
Root cause: Inferred. Connection pool exhausted after max connections was lowered
Origin changed: unknown
Fix: operator-applied. Pool size restored to its previous value
Verify-with: 5xx rate on tg-checkout over 15 minutes; expected below 1%
```

CloudThinker keeps observed facts, inferences and unknown history separate. A field it can't support says `unknown` rather than a guess.

## How recall works

When a new investigation starts, CloudThinker reads memory before it forms any hypothesis:

1. It loads valid entries, most recently updated first, up to 20 across all three kinds. It never reads the whole history.
2. It looks for a matching recollection: the same symptom on the same service or component.
3. If the matching incident was resolved before, it runs one cheap check from that recollection's `Verify-with:` line.
   - **Check passes:** the old fix still holds. CloudThinker reads the current evidence to decide the disposition. A repeated report of the same episode isn't counted as a new occurrence.
   - **Check fails:** CloudThinker investigates the current fault on its own terms. It doesn't assume the old cause came back.
4. It treats every recalled entry as a lead, not as evidence. The verdict still rests on data from your systems, and memory never upgrades an **Inferred** cause to **Verified**.

Incident memory isn't listed in **Settings → Memory**, which shows [workspace memory](/guide/memory) items. To see what CloudThinker checked, click **Watch live** while it runs, or open **More actions → Open AI Conversation** afterwards.

## Confirm a fix held

A recollection that records an applied fix starts as **Unverified**. A follow-up check turns it into **Verified** or **Failed**, which decides whether later investigations trust it.

<Steps>
  <Step title="Open the investigation conversation">
    Go to **Resolve → Investigation**, select the incident, and open **More actions → Open AI Conversation**.
  </Step>
  <Step title="Enable the follow-up card">
    When CloudThinker applied a fix and recorded a `Verify-with:` check, it proposes a follow-up as a card in the conversation. Enable the card. Nothing is scheduled until you do.

    **Success state:** the follow-up becomes an [automation](/guide/automation/automations) that runs at the proposed time and posts back into this conversation.
  </Step>
  <Step title="Or ask for one yourself">
    If no card appeared, ask in the same conversation:

    ```text
    Tomorrow at 09:00, re-run the Verify-with check for this incident and update its recollection with the result.
    ```
  </Step>
  <Step title="Read the result">
    When the follow-up runs, it reports the check result in the conversation and sets the recollection's outcome.
  </Step>
</Steps>

### Verification outcomes

| Outcome | Meaning | Effect on later investigations |
|---|---|---|
| **Unverified** | No conclusive check yet. The default for any entry without an outcome. | Used as a lead |
| **Verified** | A follow-up check confirmed the expected result | Used as a lead |
| **Failed** | The expected result didn't hold | A failed lesson is never shown again as guidance. A failed recollection or observation stays as a counter-example, so the same assumption isn't repeated. |

## How memory stays accurate

There's no screen for editing incident memory. CloudThinker maintains it as it works:

- When new evidence contradicts a sentence in a past recollection, CloudThinker edits that sentence and states the observation that corrects it.
- An unsupported historical claim is marked unverified, not deleted. A different fault today doesn't erase a supported older incident.
- Two lessons that contradict each other are merged into one corrected lesson, or the obsolete one is deleted.
- An outdated entry is edited in place rather than duplicated.

You help by letting investigations finish, settling each remediation suggestion with **Mark as Done** or **Dismiss** and a note on what you actually did, and enabling follow-up checks.

## Troubleshooting

<AccordionGroup>
  <Accordion title="A repeat incident started from scratch">
    **Cause:** the earlier run never reached a disposition, so no recollection was written. Or the new incident has a different symptom, service or component. **Check:** open the earlier incident and confirm it shows a **Current assessment** and a closed outcome. **Fix:** let investigations run to a verdict. For a custom webhook, map the **Service** and **Resource** fields so incidents name the component consistently. See [custom source](/guide/incident/webhook-integrations/custom-source).
  </Accordion>
  <Accordion title="CloudThinker proposed a fix that failed last time">
    **Cause:** the earlier fix was never checked, so its recollection stayed **Unverified**. **Fix:** enable the follow-up card next time, or ask for a follow-up check in the conversation as shown above.
  </Accordion>
  <Accordion title="The follow-up check never ran">
    **Cause:** the card was never enabled. A proposed follow-up isn't an automation until you enable it. **Check:** look for the follow-up under your [automations](/guide/automation/automations). **Fix:** enable the card in the conversation, or ask CloudThinker to schedule the check.
  </Accordion>
</AccordionGroup>
