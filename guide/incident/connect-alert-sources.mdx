[Resolve](/guide/incident/overview) investigates the alerts you send it, and every source arrives one of three ways: a webhook, an AWS polling source, or a chat channel. This page finds your path and sends you to the one page that sets it up.

## How an alert reaches Resolve

1. Your source delivers the alert: a webhook call, a polled AWS service, or a message in a chat channel Resolve watches.
2. [Pulse](/guide/pulse/overview) drops duplicates and noise. What survives is a **signal**.
3. Pulse groups related signals into a **cluster**: one problem, however many alerts it produced.
4. A cluster that holds an actionable signal is filed as an incident — matched to an open one, or opened as a new one. While **On duty**, CloudThinker investigates it on its own.

Whichever path you take, you set it up in one place: **Resolve → Integrations**. Every path needs the workspace **Admin** role and admin access to the tool that produces the alerts. See [Roles](/guide/security/roles).

Delivery and investigation are separate settings. While **On duty** shows **Paused**, your sources keep delivering and an actionable cluster is still filed as an incident with status **Open**: what waits is automatic triage and investigation, until someone clicks **Investigate**. See [What starts an investigation](/guide/incident/settings#what-starts-an-investigation).

## Choose your path

| What you have | Which path to take | The page that does it |
|---|---|---|
| A monitoring or alerting tool CloudThinker lists, such as Datadog, Grafana, or PagerDuty | Add a webhook signal. The field mapping and severity mapping arrive filled in for that tool. | [Webhook signals](/guide/incident/webhook-integrations/overview) |
| A tool or in-house system CloudThinker doesn't list, such as an uptime checker or a cron job | Create a custom source, send it one real event, then click the fields in that event to map them. | [Add a custom signal source](/guide/incident/webhook-integrations/custom-source) |
| AWS CloudWatch alarms | Create the AWS CloudWatch webhook, then forward alarm state changes to it with Amazon EventBridge. No code to maintain. | [Connect CloudWatch alarms](/guide/incident/webhook-integrations/cloudwatch) |
| AWS services CloudThinker reads for you: CloudTrail, AWS Health, AWS GuardDuty, AWS IAM Access Analyzer, and AWS Config | Turn on a polling source: CloudThinker reads the service on a schedule instead of waiting for a webhook. Nothing to paste into AWS, but you need an [AWS connection](/guide/connections/aws). | [Connect Pulse sources](/guide/pulse/setup#connect-a-source) |
| A Slack or Microsoft Teams channel where people report problems | Add the channel under **Listen for incidents**. Messages people post become signals; in Slack, messages from bots are skipped. | [Connect Pulse sources](/guide/pulse/setup#connect-a-source) |
| A deploy script or app that should start an agent run rather than an incident | Create an Automation webhook trigger instead. It runs an [Automation](/guide/automation/automations) and opens no incident. | [Inbound webhooks](/guide/webhooks/overview) |
| Something already connected, and you're not sure it's working | Read the platform's readiness badge, then confirm one signal in Pulse. | [Resolve Integrations](/guide/incident/integrations#read-readiness) |

<Tip>
A successful response from a webhook only proves delivery. Confirm one signal on **Resolve → Pulse** before you rely on any source.
</Tip>

## Tools with a preset

A **preset** is the field mapping and severity mapping Resolve fills in when you pick a tool, so you don't have to work out which part of the payload holds the title or the severity. These tools have one:

| Kind of tool | Tools with a preset |
|---|---|
| Monitoring | Datadog, Grafana, Prometheus, Splunk, Zabbix, Elastic (ELK), Nagios, SolarWinds, PRTG, LogicMonitor, Sumo Logic, Pingdom |
| Cloud Monitoring | AWS CloudWatch, Azure Monitor, GCP Monitoring |
| APM (application performance monitoring) | New Relic, Dynatrace, AppDynamics |
| Error Tracking | Sentry |
| AIOps | BigPanda |
| Incident Management | PagerDuty, Opsgenie, ServiceNow, Jira Service Management, incident.io, Splunk On-Call |

A preset also picks the authentication the tool supports: PagerDuty signs its webhooks, and CloudWatch sends a named key header.

A filled-in mapping isn't a verified one. Check it against a real payload before you trust it, because a preset can point at a field your tool doesn't send: the Datadog preset's service path is one example. See [Map the fields](/guide/incident/webhook-integrations/overview#map-the-fields).

Anything not in this table goes through a custom source, where you map the fields by clicking them in a payload your system really sent.
