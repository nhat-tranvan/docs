Log an incident when a problem reaches you before any alert does: a customer email, a teammate in chat, a dashboard that looks wrong. You describe what's happening, attach what you have, and CloudThinker starts a root-cause investigation as soon as you submit. You don't need an alert source connected.

## Before you start

- The workspace **Admin** role. Developers and Viewers can read incidents but can't log them. Roles are fixed, so there's no way to grant just this permission. See [Roles](/guide/security/roles).
- A [connection](/guide/connections/overview) to the systems involved, so the investigation can check real data.
- Optional: screenshots, log exports, or error output to attach. Save logs as `.txt`, since `.log` files aren't accepted.

## Log an incident

<Steps>
  <Step title="Open the form">
    Go to **Resolve → Investigation** and click **Log Incident**.
  </Step>
  <Step title="Pick a template (optional)">
    A **Quick Start Template** fills in a title prefix, a description outline, and a severity. Edit anything it fills in. For example, **API Outage** sets the title to `[API Outage] ` and the context to:

    ```text
    Affected API:
    Error Type: (5xx, timeout, connection refused)
    First Detected:
    Impact: (users affected, dependent services)
    Error Rate:
    ```

    | Template | Prefills severity |
    |---|---|
    | API Outage | High |
    | Database Issue | High |
    | Deployment Failure | Medium |
    | Service Degradation | Medium |
    | Infrastructure Alert | Medium |
  </Step>
  <Step title="Describe the problem">
    | Field | Required | What to enter |
    |---|---|---|
    | **What's happening?** | Yes | A one-line summary. This becomes the incident title. |
    | **Context** | No | Symptoms, impact, timing, and anything already tried |
    | Attachments | No | Click **Attach**, drag and drop, or paste. Up to 5 files, 25 MB each (spreadsheets and CSV up to 100 MB). Accepted types include images (PNG, JPG, GIF, WebP), PDF, TXT, Markdown, JSON, YAML, XML, CSV, Office documents, and ZIP archives. |
    | **Severity** | Yes | **Critical**, **High**, **Medium**, **Low**, or **Info**. Starts at **Medium**. |
    | **Occurred At** | No | When it started, in your browser's local time. Defaults to now. You can backdate up to 30 days, not into the future. |

    Specific context gives the investigation a better starting point. For example:

    ```text
    What's happening?
    Checkout API returning 502s for EU customers

    Context
    Service: checkout-api (EKS cluster prod-eu)
    First reported: 14:05 UTC by support, three customer tickets
    Impact: roughly 1 in 5 checkout requests fail, EU only
    Recent change: payment-client v2.3 deployed at 13:50 UTC
    Already tried: restarted two pods, no change
    ```
  </Step>
  <Step title="Submit">
    Click **Log Incident**.

    **Success state:** the new incident opens selected in **Resolve → Investigation**, and RCA has already started. It shows under **AI is handling**, with a **Watch live** button in the header.
  </Step>
</Steps>

## What happens next

1. CloudThinker reads your description and attachments, then checks your connected systems to test explanations.
2. Progress appears in the **Investigation timeline** as it happens. Click **Watch live** to follow the conversation.
3. When it finishes, the incident moves to **Needs your decision** with a written verdict, a causal graph, and remediation suggestions.

[Investigation and RCA](/guide/incident/root-cause-analysis) explains how to read the result and settle each suggestion.

A logged incident is a real incident, so test with care. If **Post incident updates** is on in [Resolve integrations](/guide/incident/integrations#turn-on-outcomes), its channel gets a message when the incident opens, changes status, and resolves. Whether anyone is paged depends on your [On-call](/guide/incident/oncall) setup.

## Log it, or let Pulse catch it?

| Situation | Do this |
|---|---|
| A customer or teammate reports a problem | Log an incident |
| You want to investigate before any monitor fires | Log an incident |
| Your alerting tool can send webhooks | Connect it as a [Pulse source](/guide/pulse/setup) so future alerts become incidents on their own |
| Pulse already grouped the alerts | Work from the existing incident instead of logging a duplicate. Check first: search for a word from the alert title in **Search investigations...** on **Resolve → Investigation**, or in **Search signals...** on **Resolve → Pulse**. See [Clusters](/guide/pulse/clusters). |

## Troubleshooting

| Problem | Fix |
|---|---|
| No **Log Incident** button | Your role can't edit incidents. Ask a workspace Admin. |
| **Log Incident** is greyed out | A file is still uploading or failed validation (wrong type or too large). Remove the file or wait for the upload. |
| Can't pick a date | **Occurred At** only accepts the last 30 days and nothing in the future. |
| Verdict is **Cause unproven** or **Not Found** | The investigation couldn't read the right system. Add the missing [connection](/guide/connections/overview), then open **More actions → Open AI Conversation** and ask again with more detail. See [Re-investigation](/guide/incident/root-cause-analysis#re-investigation). |
