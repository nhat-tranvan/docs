Bring Your Own Key (BYOK) runs the AI-model calls behind agent responses on your own AWS Bedrock or Anthropic credentials instead of platform credits. The organization Owner sets up an organization key under **Admin Settings → BYOK**, and every workspace uses it by default. A workspace admin can give one workspace its own key instead.

## Why BYOK

- **Your own spend.** Model calls on your key bill to your AWS or Anthropic account, not to CloudThinker credits.
- **Your own quotas.** Your provider limits apply, not platform credit limits.
- **Your choice of model.** Pick the model for each mode and module, or keep the defaults.
- **Data residency on Bedrock.** Pick an AWS region to keep inference inside the US, the EU, or Asia Pacific.

## Prerequisites

- A Scale, Scale+, or Enterprise plan. See [Pricing & Plans](/guide/billing/pricing).
- The Owner role for the organization key, or the workspace admin role for a workspace key. Other members see the key status but not the credentials.
- One of these credentials:
  - An AWS IAM role that CloudThinker assumes, or an IAM access key, with Bedrock invoke permissions. See [Prepare AWS Bedrock](#prepare-aws-bedrock).
  - An Anthropic Console API key. It starts with `sk-ant`.

## Prepare AWS Bedrock

Skip this section if you use an Anthropic API key.

First, open [Amazon Bedrock](https://console.aws.amazon.com/bedrock/) in the AWS Console. If Bedrock asks for the Anthropic use case form, submit it once for your AWS account. See the [AWS model access documentation](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html). For GPT models, see [OpenAI models in Amazon Bedrock](https://developers.openai.com/api/docs/guides/amazon-bedrock).

Then pick how CloudThinker signs in to Bedrock:

- **IAM role (recommended).** CloudThinker assumes a role in your AWS account and gets short-lived credentials. It stores no AWS key, so you have nothing to rotate.
- **Access key.** CloudThinker stores an IAM user's access key.

### IAM role

CloudThinker shows the trust policy and the permissions policy in the setup form, with your External ID filled in. Copy them from there.

<Steps>
  <Step title="Start the setup">
    Go to **Admin Settings → BYOK**, select **AWS Bedrock**, and set **Sign in with** to **IAM role**.
  </Step>
  <Step title="Create the role with the trust policy">
    In the AWS Console, create an IAM role with a custom trust policy. Paste the policy from **1. Trust CloudThinker**. It lets CloudThinker assume the role only with your External ID. Each organization or workspace key has its own External ID.
  </Step>
  <Step title="Attach the Bedrock policy">
    Attach the policy from **2. Allow Bedrock** to the role. Replace `111122223333` with your AWS account ID. The policy allows `bedrock:InvokeModel*` and, for GPT models, `bedrock-mantle:CreateInference`.
  </Step>
  <Step title="Copy the role ARN">
    Copy the role ARN, such as `arn:aws:iam::123456789012:role/CloudThinkerAccessRole`. You enter it in **3. Role ARN**. Then continue with [Connect your key](#connect-your-key).
  </Step>
</Steps>

### Access key

<Steps>
  <Step title="Create the IAM user and policy">
    Create a user and attach a policy that allows Bedrock to invoke the models. Drop the `openai` ARNs and the `bedrock-mantle` statement if you pick no GPT model.

    ```bash
    aws iam create-user --user-name bedrock-byok-user

    cat > bedrock-policy.json << 'EOF'
    {
      "Version": "2012-10-17",
      "Statement": [
        {
          "Effect": "Allow",
          "Action": [
            "bedrock:InvokeModel",
            "bedrock:InvokeModelWithResponseStream"
          ],
          "Resource": [
            "arn:aws:bedrock:*::foundation-model/anthropic.claude-*",
            "arn:aws:bedrock:*:*:inference-profile/*.anthropic.claude-*",
            "arn:aws:bedrock:*::foundation-model/openai.*",
            "arn:aws:bedrock:*:*:inference-profile/global.openai.*"
          ]
        },
        {
          "Effect": "Allow",
          "Action": ["bedrock-mantle:CreateInference"],
          "Resource": "arn:aws:bedrock-mantle:*:*:project/*"
        },
        {
          "Effect": "Allow",
          "Action": ["sts:GetSessionToken"],
          "Resource": "*"
        }
      ]
    }
    EOF

    aws iam put-user-policy \
      --user-name bedrock-byok-user \
      --policy-name BedrockInvokePolicy \
      --policy-document file://bedrock-policy.json
    ```

    These commands need an AWS profile with `iam:CreateUser` and `iam:PutUserPolicy`.
  </Step>
  <Step title="Create an access key">
    ```bash
    aws iam create-access-key --user-name bedrock-byok-user
    ```

    Save the `AccessKeyId` and the `SecretAccessKey` from the output. You enter them in CloudThinker.
  </Step>
</Steps>

<Tip>
The `anthropic.claude-*` wildcard covers the models CloudThinker adds later. For a tighter policy, list each model ID from [Supported models](#supported-models). Add each inference profile too, such as `us.anthropic.claude-opus-5`.
</Tip>

## What runs on your key

Each row in **Step 3** is one kind of work. A row you set to **CloudThinker credits** runs on the platform and is billed as usual.

| Row | Covers | Default model follows |
|---|---|---|
| **Light**, **Pro**, **Ultra** | Chat turns in that mode | Its own release default |
| **Review** | [Review](/guide/code-review/overview) of pull and merge requests | Its own release default |
| **Cyber** | [Cyber](/guide/security/cyber-overview) pentests, Cyber chat, and Code Audit | Its own release default |
| **Resolve** | [Resolve](/guide/incident/overview) root cause analysis | Its own release default |
| **Optimize** | [Optimize](/guide/cost-optimization/overview) | The **Ultra** row |
| **Background tasks** | Supporting work that runs behind a turn | The **Light** row |

The model list comes from your provider and changes as new models ship. The picker only offers models your provider serves on this key and region. If a saved pick shows **Model retired, pick another**, choose a new model for that row.

## Choose a Bedrock region

**Region** decides where Bedrock may serve your requests. You pick a region; CloudThinker picks the matching Bedrock route.

| You pick | Bedrock serves requests from |
|---|---|
| **Global (recommended)** | Any commercial AWS region. Widest model choice. |
| A US or Canada region, such as `us-east-1` | US regions |
| An EU region, such as `eu-west-1` | EU regions |
| An Asia Pacific region, such as `ap-southeast-1` | Asia Pacific regions |
| South America (Sao Paulo) | Any commercial AWS region, same as Global |

<Warning>
A regional pick narrows the model list to what Bedrock serves in that geography. If your data must stay in one geography, keep a regional pick and check after setup that every row still runs on your key. Switching the key to **Global** widens the models but lets Bedrock serve requests from any commercial region.
</Warning>

## Organization and workspace keys

**This workspace** decides which key the workspace runs on:

| Choice | Result |
|---|---|
| **Organization** | Turns run on the organization key. If it isn't active, they spend CloudThinker credits. |
| **Workspace** | Turns run on a key set up for this workspace only. |
| **Off** | Turns spend CloudThinker credits, even when the organization has a key. |

The line under the choice tells you what's in effect, for example "Turns run on the organization's AWS Bedrock key." To force every workspace onto the organization key, the Owner turns on **Require the organization key in every workspace** under **Organization key**. Workspace Admins then can't add their own key or turn BYOK off.

## Manage a key

| Action | What it does |
|---|---|
| **Rotate key** | Replace the credentials. CloudThinker verifies the new ones with **Verify and save** and keeps your model picks. |
| **Edit models** | Choose which of the provider's models members can pick. Leave at least one on. |
| **Re-verify** | Test the saved credentials again. |
| **Pause** / **Activate** | Stop or restart calls on the key. A paused key keeps its credentials and shows **Saved, paused**. |
| **Remove** | Delete the key. Every row goes back to CloudThinker credits. |

## Use more than one credential

A scope, the organization or one workspace, can hold several credentials, for example a Bedrock role and an Anthropic key. Click **Add a credential** below the key cards to connect another one.

The **What runs on which credential** table picks a credential and a model for each row. Click **Save** after you change it. A row left on **CloudThinker credits** spends credits as usual. When you remove a credential, its rows go back to CloudThinker credits.

## Workspace keys

Each workspace has a **BYOK** tab in its settings. **Which key this workspace runs on** has three choices:

| Choice | What runs |
|---|---|
| **Organization** | The organization key. This is the default. |
| **Workspace** | A key for this workspace only. A workspace admin connects it in the same tab, with the same steps as [Connect your key](#connect-your-key). |
| **Off** | CloudThinker credits, even when the organization has a key. |

To require the organization key everywhere, the Owner turns on **Require the organization key in every workspace** under **Admin Settings → BYOK**. Workspace admins then cannot use their own key or turn the key off. Personal workspaces cannot use BYOK.

If the provider rejects the credentials (expired token, revoked key, access denied), CloudThinker turns the key off:

- The key card shows **Disabled after error** or **Key expired**, with the provider's error code.
