An organization is the top-level account in CloudThinker. It owns billing and the member list, and it contains one or more [workspaces](/guide/workspaces) where the actual work happens.

## Prerequisites

- Most tasks on this page need an organization **Owner** or **Admin**. Developers and Viewers can't open **Settings → Organization**, even when they're Admin of a workspace through an override. Such a workspace Admin can open two pages there from a direct link, **Guardrails** and **BYOK**. A workspace Admin manages that workspace in **Settings → Workspace**, including its own BYOK key.
- Anyone except the Owner can [leave an organization](#leave-an-organization).

## How organizations and workspaces fit together

When you sign up, CloudThinker creates an organization named after you (for example, "Jane's Organization") and makes you its Owner. Onboarding then creates your first workspace inside it.

| Lives in the organization | Lives in each workspace |
|---|---|
| Plan and billing | [Connections](/guide/connections/overview) and [credentials](/guide/credentials) |
| Member list and organization roles | [Custom agents](/guide/agents/customize), [skills](/guide/skills/overview), and [memory](/guide/memory) |
| [BYOK](/guide/byok), [SSO and provisioning](/guide/security/sso), [audit logs](/guide/security/audit-logs) | Conversations, artifacts, and module data (Optimize, Review, Cyber, Resolve) |
| [Usage](/guide/billing/usage) and [credit limits](/guide/billing/credit-limits) (set here, one cap per workspace) | [Approvals](/guide/approvals/overview), [notifications](/guide/notifications), and workspace members |

Approvals are configured inside each workspace. Credit limits are set by an Owner or Admin in **Settings → Organization → Billing**, with one cap per workspace. Keep production and non-production in separate workspaces when one needs stricter approvals or a tighter budget. See [choose a layout](/guide/workspaces#choose-a-layout).

## Open organization settings

Organization controls live in **Settings → Organization**, separate from **Settings → Workspace**, which covers one workspace at a time.

<Steps>
  <Step title="Open Settings">
    Click the workspace menu at the top of the sidebar, then **Settings**. You can also press ⌘⇧, (Ctrl+Shift+, on Windows and Linux).
  </Step>
  <Step title="Pick the Organization tab">
    Click **Organization** at the top of Settings.

    **Success state:** the side list shows the organization pages, starting with **General**, **Workspaces**, and **Members**.
  </Step>
</Steps>

[Organization settings](/guide/admin-settings) lists every page there, what it sets, and the guide for each. Which pages you see depends on your organization role and on what's enabled for your organization; the [role table below](#organization-roles) shows what each role can change. **Workspaces** is the only place a workspace can be deleted.

## Invite members

<Steps>
  <Step title="Open Members">
    Go to **Settings → Organization → Members** and click **Invite people**.
  </Step>
  <Step title="Add email addresses">
    Type an address in **Enter an email** and press Enter to add it. Add as many as you need for this batch.
  </Step>
  <Step title="Choose a role">
    Pick **Admin**, **Developer**, or **Viewer** in the role menu. Developer is the default. You can't invite someone as Owner.

    One role applies to every address in this batch. To invite people with different roles, send separate batches.
  </Step>
  <Step title="Send">
    Click **Invite**.

    **Success state:** each invitee appears at the top of the members list with **Invited** and an expiry, and receives an invitation email. Invitations expire after 7 days.
  </Step>
</Steps>

To pick workspaces for Developers and Viewers while you invite them, use **Invite members** in the workspace menu at the top of the sidebar instead. Its dialog has **Select workspaces**. Admins don't need this, because they get every workspace automatically.

<Warning>
If you invite a Developer or Viewer without selecting a workspace, they join the organization but can't open any workspace until you grant access. See [workspace members](/guide/workspace-users).
</Warning>

**What the invitee does:** they open the link in the email and sign in or sign up with the address you invited. A different address is rejected. Someone who already belongs to another organization keeps it, and both show in their workspace menu.

## Organization roles

Every member has one organization role. The organization **Owner** is the highest role and pays for the organization. Organization **Admins** can set up everything in the organization except the Owner-only rows in [Roles](/guide/security/roles#organization-permissions). Owners and Admins are Admins in every workspace. Developers and Viewers see the organization name and the workspaces they're assigned to. They don't see the organization member list, only the members of their workspaces on each workspace's **Members** page.

| Permission | Owner | Admin | Developer | Viewer |
|---|:---:|:---:|:---:|:---:|
| Edit organization name and description | ✓ | ✓ | | |
| Invite and remove members, change roles | ✓ | ✓† | | |
| Create and delete workspaces | ✓ | ✓ | | |
| Admin access to every workspace | ✓ | ✓ | | |
| View usage, set credit limits | ✓ | ✓ | | |
| Manage plan and billing | ✓ | | | |
| Configure BYOK and SSO | ✓ | | | |
| Change [capabilities](/guide/capabilities) for every workspace | ✓ | | | |
| Request an ownership transfer | ✓ | | | |
| Work in assigned workspaces | ✓ | ✓ | ✓ | View only* |

\*Viewers can open conversations, findings, and dashboards, but can't chat with agents, run skills, or change anything.

†Admins can change roles for and remove Developers and Viewers only. Admins can invite a new member as Admin, but only the Owner can promote an existing member to Admin, change an Admin's role, or remove an Admin.

People added through SSO just-in-time sign-in or SCIM get the **Auto-assigned organization role** you set on the connection (Viewer by default). With SCIM, you can also set a role per IdP group. See [SSO](/guide/security/sso) and [SCIM group mapping](/guide/security/scim#map-groups-to-workspaces).

You can raise or lower a Developer's or Viewer's role inside a single workspace. See [workspace roles](/guide/workspace-users#workspace-roles). "Member" is a legacy role name and works like Developer.

## Manage members and invitations

Rename the organization on **Settings → Organization → General**: click **Edit** next to **Organization name**, change **Organization Name** (and optionally **Description**), then click **Save Changes**. Everything else lives in **Settings → Organization → Members**, where each person is one row with an actions menu (**...**).

| Task | How |
|---|---|
| Change a member's role | Pick a new value in the role menu on their row |
| Change which workspaces a Developer or Viewer can open | Click **Edit workspace access** in the row's actions menu |
| Remove a member | Click **Remove** in the row's actions menu and confirm. They lose access to every workspace in the organization |
| Activate a member | Click **Activate member** in the actions menu of a row marked **Inactive** |
| Resend or revoke an invitation | Open the actions menu on the invitation row, then click **Resend invitation** or **Revoke invitation** |

On an older per-seat subscription, a member shows as **Inactive** when they were provisioned (for example, through SSO) while the organization had no free seat. Inactive members don't use a seat. Activating them uses one.

### What happens when you remove someone

| Item | What happens |
|---|---|
| Workspace access | Removed from every workspace in the organization. Pending workspace invitations to their email are canceled |
| [Automations](/guide/automation/automations) they own | Turned off. Each one shows "Its owner no longer has access to this workspace." A workspace Admin clicks **Take ownership**, then turns it back on. It then runs as the new owner, with their access |
| Approvals | They're taken out of every approver group, so pending requests go to the remaining approvers |
| Workspaces they created | Stay in the organization with everything in them. Owners and Admins keep access |
| Their seat (older per-seat subscriptions) | Freed |

<Warning>
Before you remove someone who owns scheduled Automations, decide who takes them over. Otherwise those runs stop silently until a workspace Admin takes ownership.
</Warning>

## Seats

Team, Scale, and Enterprise include unlimited members. Adding a member does not increase your plan price or monthly credits. Team includes 3 workspaces and Scale includes 10. See [plans and pricing](/guide/billing/pricing).

<Note>
  Seat management applies only to older subscriptions billed per seat. On those subscriptions, active members and pending invitations hold seats. Invitations expire after 7 days. The Owner manages seats from **Seats → Manage** on **Settings → Organization → General**. New paid plans do not require seat purchases.
</Note>

## Control spend

Credits are pooled at the organization level, and you cap each workspace's share of them in the **Credit limits** section of **Settings → Organization → Billing**. The section shows only when credit limits are enabled for your organization.

| Setting | What it does |
|---|---|
| **Default monthly limit per workspace** | A credit cap for every workspace without its own override, or **Unlimited** |
| **Per-workspace limits** | A different cap or enforcement mode for one workspace |
| **When a workspace hits its monthly limit** | **Throttle** stops paid credit spend in that workspace. Chat on the Light model continues on the 100 free daily credits. See [usage](/guide/billing/usage). **Notify only** blocks nothing |
| **Alert the owner at 80%** and **Alert the owner at 100%** | Two switches, so you can turn on either or both. Alerts go to the Owner only, in-app and by email |

<Warning>
On **Throttle**, a workspace that hits its limit stops running agents on paid credits, mid-incident or not. Put production on **Notify only** or give it a high cap, and use **Throttle** for sandboxes.
</Warning>

Track consumption in **Settings → Organization → Usage**. See [credit limits](/guide/billing/credit-limits) and [usage](/guide/billing/usage).

## Transfer ownership

Each organization has one Owner. There's no transfer button in the app. To move ownership, have the current Owner email [support@cloudthinker.io](mailto:support@cloudthinker.io) with the organization name and the new Owner's email.

- The new Owner must already be an active member of the organization.
- The old Owner becomes an Admin.

<Tip>
Request the transfer before the Owner leaves your company, while they can still send the email.
</Tip>

## Leave an organization

Admins, Developers, and Viewers can leave. Click the workspace menu at the top of the sidebar, click **Leave organization** under your organization's workspaces, and confirm.

Leaving has the same effects as being removed. See [what happens when you remove someone](#what-happens-when-you-remove-someone).

The Owner can't leave. [Transfer ownership](#transfer-ownership) first. Members provisioned through SCIM are removed in your identity provider instead.

## Troubleshooting

<AccordionGroup>
  <Accordion title="Settings → Organization says Organization admin access required">
    **Cause:** your organization role is Developer or Viewer. Being Admin of a workspace through an override doesn't open organization settings.

    **Fix:** ask an organization Owner or Admin to change your role. For workspace settings such as the workspace BYOK key, use **Settings → Workspace** instead.
  </Accordion>
  <Accordion title="The invite button says Seats full">
    **Cause:** on an older per-seat subscription, active members plus pending invitations have used every seat. New paid plans include unlimited members.

    **Fix:** cancel invitations nobody will accept, remove members who left, or ask the Owner to add seats from **Seats → Manage** on **Settings → Organization → General**.
  </Accordion>
  <Accordion title="I can't remove a member">
    **Cause:** one of these rules applies:

    - Admins can't remove other Admins or the Owner.
    - The organization Owner can't be removed.
    - Members provisioned through SCIM have to be removed in your identity provider. The error reads "This member was provisioned via SCIM."

    **Fix:** ask the Owner, or deprovision the user in your identity provider. See [SCIM](/guide/security/scim).
  </Accordion>
  <Accordion title="A new teammate signed in but sees no workspace">
    **Cause:** they're a Developer or Viewer with no workspace assigned.

    **Fix:** go to **Settings → Organization → Members**, click **Edit workspace access** in their row's actions menu, select the workspaces, and click **Save Changes**.
  </Accordion>
</AccordionGroup>
