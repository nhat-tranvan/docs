CloudThinker reads your Kubernetes cluster through a read-only service account and answers questions about it in chat. This walkthrough takes you from an empty workspace to a cluster health check and a failing-pod investigation in about 15 minutes.

## What you need

| Requirement | Why |
|-------------|-----|
| A cluster whose API server is reachable from the internet | Commands run in the CloudThinker cloud, so a private-only endpoint fails the connection test |
| `kubectl` access that can create a namespace, a ClusterRole, and a ClusterRoleBinding | You create the read-only account CloudThinker signs in as |
| Optional: [Metrics Server](https://github.com/kubernetes-sigs/metrics-server) | Without it you still get pod status, events, and node conditions, but no live CPU and memory numbers |

<Info>
A workspace holds **one** Kubernetes connection, and CloudThinker works in the kubeconfig's **current context**. Pick the one cluster you want inspected.
</Info>

## The scenario

A platform team runs a production cluster across several namespaces. Alerts fire now and then, and each investigation means someone runs `kubectl get`, `describe`, and `logs` across dozens of pods to line up events, restarts, and resource usage.

## Step 1: Connect the cluster

<Steps>
  <Step title="Create a read-only service account">
    Save the manifest from the [Kubernetes connection guide](/guide/connections/kubernetes#required-permissions) as `cloudthinker-reader.yaml` and apply it:

    ```bash
    kubectl apply -f cloudthinker-reader.yaml
    ```

    This creates the `cloudthinker` namespace, a `cloudthinker-reader` service account with `get`, `list`, and `watch` on workloads, nodes, events, logs, and metrics, and a long-lived token Secret. It does not grant access to Secrets.
  </Step>
  <Step title="Build a kubeconfig for that account">
    Run the script in the [connection guide](/guide/connections/kubernetes#setup) to write `cloudthinker-kubeconfig.yaml` with the token and CA certificate embedded. Then test it:

    ```bash
    kubectl --kubeconfig cloudthinker-kubeconfig.yaml get nodes
    ```

    If your nodes are listed, CloudThinker's own connection test will pass too. It runs the same command.
  </Step>
  <Step title="Upload it in CloudThinker">
    Open **Connections** in the sidebar, select **Kubernetes**, upload the file in the **KUBECONFIG** field, and click **Connect**.

    The status moves through **Connecting** and **Verifying** to **Connected**.
  </Step>
</Steps>

<Warning>
Don't upload your everyday kubeconfig. Files that point to local paths or sign in through an `exec` plugin (such as a cloud CLI) depend on tools on your machine and fail in CloudThinker. The token-based file from step 2 avoids both.
</Warning>

## Step 2: Check cluster health

Start with a quick check that the connection sees what you expect:

```text
Check the Kubernetes connection: list the namespaces, the node count, and any nodes that are not Ready
```

You get the namespace list, the node count, and each node's status. If usage numbers are missing, the answer tells you Metrics Server is not installed.

Then ask for the wider picture. These prompts each cover one layer of the cluster:

| Goal | Example prompt | What you get back |
|------|----------------|-------------------|
| Node pressure | `Which nodes are under memory or disk pressure, and what is using the most memory?` | Node conditions, capacity and allocatable resources, and top consumers (with Metrics Server) |
| Sizing | `Analyze pod resource utilization in the production namespace` | Requests and limits compared with real usage, with pods flagged as over- or under-provisioned |
| Idle capacity | `Show nodes with less than 30% CPU utilization` | Underused nodes and how pods are spread across them |
| Autoscaling | `Recommend HPA policies for the web deployments` | Deployments with no autoscaler or too few replicas, and suggested policies |

<Frame>
  <img src="/images/use-cases/kubernetes-health-monitoring/02-pod-resource-utilization.jpg" alt="Pod resource utilization analysis showing CPU and memory usage per pod" />

In the team's cluster, the sizing prompt flagged two services running at about 20% CPU (over-provisioned) and one, `payment-processor`, running above 80% CPU and close to its memory limit. That pod was at risk of OOM (out-of-memory) kills. The autoscaling prompt then showed it had only 2 replicas and no Horizontal Pod Autoscaler (HPA).

## Step 3: Investigate a failing pod

When something is already broken, name the namespace and describe the symptom:

```text
Which pods in the payments namespace are crash-looping, and what do their logs say?
```

CloudThinker finds the crash-looping, pending, or restarting pods, reads their logs and warning events, and explains the likely cause in one answer. Follow up in the same conversation to narrow it down:

```text
Why can't the pending pods in payments be scheduled?
Compare the memory limit of payment-processor with its current usage
```

For scheduling problems, the answer compares pod requests with what each node can still allocate. For restarts, it ties the restarts to the logs, events, and resource limits.

### Applying a fix

The read-only account can't change anything. If you ask for a change such as `scale`, `rollout restart`, `cordon`, `drain`, or `apply`, CloudThinker pauses for your approval first, and the read-only role makes the command fail with `403`. To allow a specific change, bind a separate Role with only those verbs in the namespaces involved. See [Approvals](/guide/approvals/overview) and [Write access](/guide/connections/kubernetes#write-access).

## Run it on a schedule

Once a prompt gives you a useful answer, you can rerun it on a schedule so the health check lands before anyone is paged. See [Automations](/guide/automation/automations).

## Troubleshooting

<AccordionGroup>
  <Accordion title="The connection test can't reach the cluster">
    The API server address in the kubeconfig isn't reachable from the internet. Check that it isn't VPN-only and that any API server allowlist permits outside access.
  </Accordion>
  <Accordion title="Answers have no CPU or memory numbers">
    Metrics Server isn't installed or isn't ready. Run `kubectl top nodes` to check. Pod status, events, and node conditions still work without it.
  </Accordion>
  <Accordion title="An answer mentions a 403 on some resource">
    The ClusterRole doesn't cover that resource. The error names it, so add it to the role (or leave it out on purpose, as with Secrets).
  </Accordion>
  <Accordion title="Answers are about the wrong cluster">
    CloudThinker uses the kubeconfig's current context. Rebuild the file from the cluster you want and upload it to the existing connection.
  </Accordion>
</AccordionGroup>
