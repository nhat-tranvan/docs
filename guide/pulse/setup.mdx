Pulse only sees what you send it. This page gets one alert source flowing into Pulse and shows you how to confirm it works before you rely on it.

## Prerequisites

- A CloudThinker workspace with permission to manage Resolve integrations.
- Access to the tool that produces your alerts (for example CloudWatch, Datadog or Grafana), so you can add a webhook or fire a test alert.
- For AWS polling: an [AWS connection](/guide/connections/aws) in the workspace.
- For chat: Slack or Microsoft Teams connected to CloudThinker ([Slack](/guide/slack-integration), [Teams](/guide/teams-integration)).

## Pick a signal path

Each platform on **Resolve → Integrations** can feed Pulse in up to three ways. Pick the one your tool supports.

| Signal path | Shown as | Best for |
|---|---|---|
| Webhook | **Webhook** | Monitoring tools that can POST an alert (CloudWatch through SNS, Datadog, Grafana, PagerDuty and more), or any in-house system through **Custom source**. |
| Polling | **Polling source** | AWS services CloudThinker reads for you: CloudTrail, AWS Health, AWS GuardDuty, AWS IAM Access Analyzer and AWS Config. |
| Chat | **Chat channel** | Slack or Teams channels where people and bots already post incident chatter. |

## Connect a source

<Steps>
  <Step title="Open the platform">
    Go to **Resolve → Integrations** and select your platform. Use the search field if the list is long. For a system with no card of its own, select **Custom source**.
  </Step>
  <Step title="Check the connection">
    In the **Connection** section, connect the account or workspace if the platform needs one. Platforms marked **Needs connection** can't add signals until this is done.
  </Step>
  <Step title="Add a signal">
    In **Signals to Resolve**, click **Add signal** (or **Add another signal**) and follow the path for your source:

    <Tabs>
      <Tab title="Webhook">
        Copy the webhook URL into your monitoring tool. For a vendor platform, the field mapping and severity mapping are preset. For **Custom source**, name the source, send one real alert, then click the payload fields that hold the **Incident title** (required), **Severity**, **Service**, **Resource** and **Description**. Paths are dotted, like `event.data.title`, never `$.event.data.title`. Full walkthroughs: [CloudWatch](/guide/incident/webhook-integrations/cloudwatch) and [custom source](/guide/incident/webhook-integrations/custom-source).
      </Tab>
      <Tab title="AWS polling">
        Each AWS service appears as a row with a switch. Turn on the services you want Pulse to read. If you have more than one AWS connection, each row names the connection it reads.
      </Tab>
      <Tab title="Chat channel">
        In **Listen for incidents**, add the channels Resolve should watch for incident mentions and operational context.
      </Tab>
    </Tabs>
  </Step>
  <Step title="Send a test alert">
    Trigger a real or test alert in the source tool, then open **Resolve → Pulse** and set the lane to **All**.

    **Success state:** the alert appears as a cluster, and the platform shows **Ready** on **Resolve → Integrations**.
  </Step>
</Steps>

<Tip>
A connected account alone doesn't prove events arrive. Always confirm one signal in Pulse before you count on a source.
</Tip>

## Webhook options that change behavior

Open a webhook from its platform's **Signals to Resolve** section to edit these.

| Setting | Default | What it does |
|---|---|---|
| **Auto-investigate** | On | CloudThinker starts one root cause investigation when this webhook's alert leads to an incident. Off means it investigates only when you ask. |
| **Only from a minimum severity** | Off | Lower-severity alerts still group into clusters, but don't start an investigation. Turning it on starts at **High and above**. |
| **Send directly to CloudThinker** | Off | Skips Pulse filtering and grouping. While **On duty** is on, CloudThinker judges each event itself. Use it only for low-volume sources where every event matters. |

The workspace **On duty** switch on **Resolve → Investigation** still decides whether any investigation starts automatically. See [Settings](/guide/incident/settings).

## Read the readiness badge

| Badge | Meaning | Fix |
|---|---|---|
| **Ready** | At least one signal path works. | Nothing to do. |
| **Partially ready** | Some paths work, others don't. | Open the platform and check each signal row. |
| **Needs setup** | Connected, but no signal path is set up. | Add a signal. |
| **Needs connection** | The platform needs an account connection first. | Connect it in the **Connection** section. |
| **Needs attention** | Something is failing, such as an unhealthy connection. | Open the platform and follow the row's hint. |
| **Not configured** | You haven't touched this platform. | Ignore it, or set it up. |

## Troubleshooting

<AccordionGroup>
  <Accordion title="Pulse still says No signals yet">
    **Cause:** the source never sent, or sent to the wrong URL. **Check:** the delivery log in your monitoring tool. **Fix:** paste the webhook URL again and fire a test alert.
  </Accordion>
  <Accordion title="The alert arrived but no cluster appeared">
    **Cause:** suppression dropped it, often as a duplicate of an alert sent in the last hour. **Check:** the **All** lane and the platform's signal row. **Fix:** send a different alert, or see [noise suppression](/guide/pulse/clusters#noise-suppression).
  </Accordion>
  <Accordion title="Custom source clusters have no useful title">
    **Cause:** the field mapping points at the wrong path. **Fix:** edit the webhook, send a fresh payload and pick the field again.
  </Accordion>
  <Accordion title="An AWS polling row shows a badge and won't switch on">
    **Cause:** the AWS connection behind it is unhealthy or lacks permission. **Fix:** check the [AWS connection](/guide/connections/aws).
  </Accordion>
</AccordionGroup>
