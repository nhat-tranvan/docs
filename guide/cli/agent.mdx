`cloudthinker agent` runs a coding agent where your code already is. It reads and edits files and runs commands on your machine, while the model, your workspace memory, and your [connections](/guide/connections/overview) stay in CloudThinker.

## Why run it locally

- **Your repository, untouched by uploads.** The agent works in the current directory instead of a copy in someone else's sandbox.
- **Your shell.** It runs the same commands you would run, with the tools and credentials already on that machine.
- **One workspace.** The session bills, remembers, and reasons against the same workspace as the web app.

## Start a session

<Steps>
  <Step title="Change into the repository">
    ```bash
    cd ~/code/payments-api
    ```
  </Step>

  <Step title="Start the agent">
    ```bash
    cloudthinker
    ```

    A bare `cloudthinker` is the same command as `cloudthinker agent`. It checks your login first, and offers the browser login when there is none, so a new install reaches a session in one command.

    **Success state:** the agent starts an interactive session in the current directory. The first run prints `downloading cloudthinker-agent <version>` while it fetches the matching agent build.
  </Step>

  <Step title="Ask for the change you want">
    Describe the outcome, not the file list. The agent explores the repository itself, proposes the edits, and runs the commands it needs to check its work.
  </Step>
</Steps>

## One-shot and continued runs

The agent takes its own options, and every argument after `agent` reaches it verbatim:

```bash
cloudthinker agent -p "Add a health check endpoint to the API"   # non-interactive, then exit
cloudthinker agent -c                                            # continue the previous session
cloudthinker agent --model <pattern>                             # pick a model for this session
cloudthinker agent -- --help                                     # the agent's own options
```

Options belonging to the CLI itself come first, before `agent`:

```bash
cloudthinker --workspace Production agent
```

Use `--` when an agent option shares a name with a CLI option, for example `cloudthinker agent -- --url http://localhost:3000`. Everything after `--` belongs to the agent.

## How the agent build is installed

The agent ships as a bundle in the same release as the CLI, not as a separate download you manage.

1. The first `cloudthinker agent` after an install or an update downloads the bundle for your platform.
2. The CLI checks it against the release's SHA-256 sidecar before unpacking it.
3. It installs to `~/.cloudthinker/agent/bin/<version>/` and reuses that build on later runs.
4. A CLI update installs the matching bundle on the next run and prunes the older one.

The CLI and the agent version always move together, so `cloudthinker update` is the only step needed to move both forward.

## Platform support

The local agent runs on macOS (Apple Silicon and Intel) and Linux (x86_64 and arm64). On any other platform the CLI reports that no agent build exists for it rather than falling back to something different.

## Troubleshooting

<AccordionGroup>
  <Accordion title="It asks you to log in every time">
    Something is overriding the stored credential, usually a leftover `CLOUDTHINKER_TOKEN` in the shell. Unset it and run `cloudthinker login` once. See [Authentication](/guide/cli/authentication).
  </Accordion>

  <Accordion title="The agent starts in the wrong workspace">
    The agent inherits the workspace the CLI resolved. Check it with `cloudthinker whoami`, and pin it for one session with `cloudthinker --workspace <name> agent`.
  </Accordion>

  <Accordion title="A warning names CLOUDTHINKER_AGENT_BIN">
    That variable points the CLI at a local agent build instead of the installed release. Unset it to go back to the released bundle.
  </Accordion>
</AccordionGroup>
