Connect GitLab and CloudThinker agents can read your projects, merge requests, issues, and CI/CD pipelines, and [Review](/guide/code-review/overview) can post AI code reviews on merge requests. You sign in with **OAuth** on GitLab.com, or paste a **project or group access token** for GitLab.com or a self-managed instance.

## Prerequisites

- Access to the GitLab projects you want agents to read.
- For the token method: the **Maintainer** or **Owner** role on the project or group, so you can create access tokens.
- Edit permission on connections in your CloudThinker workspace.

## Choose a method

| Method | Use it when | Comments appear as |
|--------|-------------|--------------------|
| **OAuth** | You're on GitLab.com and want the fastest setup | The GitLab user who signed in |
| **Access Token** | You run self-managed GitLab, or you want access limited to one project or group | A bot user tied to the token |

## Setup

Open the connection first. In the sidebar, click **More → Workspace settings → Connections**. On the **Builtin Connections** tab, search for **GitLab** and click **Connect**. The **Connect GitLab** dialog opens with two tabs.

<Tabs>
  <Tab title="OAuth">
    <Steps>
      <Step title="Start the sign-in">
        On the **OAuth** tab, click **Connect to GitLab**. GitLab opens and lists what CloudThinker asks for: read and write repository access, API access for webhooks and merge requests, and your profile (email, username).
      </Step>
      <Step title="Authorize CloudThinker">
        Sign in as a GitLab user who can see the projects you want, then click **Authorize**.

        **Success state:** you land back in CloudThinker with **GitLab Connected!** and GitLab shows **Connected** on the **Builtin Connections** tab.
      </Step>
    </Steps>
  </Tab>
  <Tab title="Access Token">
    <Steps>
      <Step title="Create the token in GitLab">
        In GitLab, open the project or group and go to **Settings → Access Tokens**. Click **Add new token** and set:

        - **Role**: `Developer` or higher
        - **Scopes**: `api`
        - **Expiration date**: a date that matches your rotation policy

        Click **Create** and copy the token. It starts with `glpat-`.
      </Step>
      <Step title="Enter the connection details">
        In the **Connect GitLab** dialog, open the **Access Token** tab and fill in the fields from [Connection details](#connection-details).
      </Step>
      <Step title="Validate and connect">
        Click **Validate Token**. CloudThinker shows **Token works** with the number of projects the token can see, then click **Connect**.

        **Success state:** CloudThinker shows **Connected to GitLab** and GitLab shows **Connected** on the **Builtin Connections** tab.
      </Step>
    </Steps>
  </Tab>
</Tabs>

<Note>
GitLab doesn't send merge request events to CloudThinker on its own. Before Review can comment, add a webhook in the project or group by following [Configure webhooks](/guide/code-review/provider-auth#configure-webhooks). Agent questions work without it.
</Note>

## Connection details

These fields appear only on the **Access Token** tab. OAuth has no fields: GitLab issues the credentials and CloudThinker stores them.

| Field | Description | Example |
|-------|-------------|---------|
| **GitLab URL** | Your instance URL with no trailing path | `https://gitlab.com` or `https://gitlab.example.com` |
| **Token Type** | **Project Access Token** reaches one project. **Group Access Token** reaches every project in the group | **Group Access Token** |
| **Access Token** | The token you created in GitLab | `glpat-<your-token>` |

## Required permissions

| Method | What decides access |
|--------|---------------------|
| **OAuth** | Everything the signed-in GitLab user can see |
| **Project or group access token** | The `api` scope plus the token's role, limited to that project or group |

A token needs the **Developer** role or higher. Guest and Reporter tokens can read but can't post comments on merge requests, so Review can't post its findings.

<Tip>
Use a group access token for the group that owns your services. Access stays inside that group, comments come from a bot user instead of a teammate, and revoking it affects nothing else.
</Tip>

## Control access in CloudThinker

Two settings on the connection's detail panel narrow what agents do. Open **Connections**, select **GitLab**, and look under **Settings**.

| Setting | Options | What it does |
|---------|---------|--------------|
| **Repository access** | **All** or **Selected** | **All** lets agents read every project the credential reaches, including new ones. **Selected** limits agents to the projects you pick, and new projects stay excluded until you add them. |
| **Allow writes** | On (default) or off | On: agents can propose changes, and your [Rules and Approval mode](/guide/approvals/overview) decide each one. Off: agents can only read, and every change is refused. |

These settings only narrow what GitLab already grants. Choosing which projects Review runs on is a separate step in [Review setup](/guide/code-review/setup).

## Agent capabilities

Reads run without asking. Writes need **Allow writes** on and pass through your Rules and Approval mode first.

| Capability | What agents can do |
|------------|--------------------|
| **Projects** | List the projects the connection reaches and read their code and history |
| **Merge requests** | Summarize open merge requests, their approvals, and discussion |
| **Pipelines** | Find failing pipelines and read job logs to explain the failure |
| **Issues** | Read issues for triage and delivery context |
| **Changes** | Create branches, comment, or open merge requests, after approval |

### Verify the connection

```text
List the GitLab projects you can reach and how many open merge requests each one has
```

A working connection names your real projects and counts. If projects are missing, compare the token type with where those projects live.

### Example prompts

```text
Which open merge requests in the platform group have had no review for more than 3 days?
Why did the latest pipeline on main fail in the api project?
Summarize the merge requests merged into main across our GitLab projects this week
```

## Troubleshooting

<Accordion title="Validate Token fails">
The token is expired or revoked, lacks the `api` scope, or the **GitLab URL** is wrong. Check that the URL has no trailing path, create a new token with the `api` scope and the **Developer** role, and validate again.
</Accordion>

<Accordion title="GitLab at your host did not respond in time">
CloudThinker couldn't reach your self-managed instance. Confirm the URL opens from outside your network, or that your firewall allows CloudThinker to reach it, then try again.
</Accordion>

<Accordion title="An agent can't find a project">
A project token reaches one project, and a group token reaches only that group and its subgroups. Use a group token for the owning group, or sign in with OAuth as a user who can see the project. Then check that **Repository access** includes it.
</Accordion>

<Accordion title="Connected, but Review doesn't comment on merge requests">
The webhook is missing or incomplete, or the token's role is below **Developer**. Add the webhook from [Configure webhooks](/guide/code-review/provider-auth#configure-webhooks) and check the token's role.
</Accordion>

<Accordion title="Reconnect GitLab to renew its OAuth credentials.">
GitLab no longer accepts the saved sign-in, for example after the user revoked CloudThinker's access. Open the connection and click **Connect** to sign in again.
</Accordion>

## Security

<ConnectionSecurity />

- **Prefer project or group tokens.** They keep access inside the projects you choose and post as a bot user, so no one's personal account speaks for CloudThinker.
- **Set an expiration date.** Rotate the token before it lapses, or Review and agents lose access on that day.
