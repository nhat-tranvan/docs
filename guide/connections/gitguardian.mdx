Connect a GitGuardian workspace to let CloudThinker agents list and triage secret incidents, trace each exposed credential to its sources and occurrences, and review honeytokens. The connection signs in with a GitGuardian **Personal Access Token (PAT)** plus your dashboard URL, so the same setup works for the US, EU, and self-hosted instances.

## Prerequisites

- A GitGuardian workspace that holds the incidents you want agents to read.
- Permission to create a Personal Access Token in that workspace.
- The **Admin** role in your CloudThinker workspace, which can add and edit connections. See [Roles](/guide/security/roles).
- Your dashboard URL. Use the address you sign in at:

| Instance | GitGuardian URL |
|----------|-----------------|
| US (SaaS) | `https://dashboard.gitguardian.com` |
| EU (SaaS) | `https://dashboard.eu1.gitguardian.com` |
| Self-hosted | Your instance URL, for example `https://gitguardian.example.com` |

## Setup

<Steps>
  <Step title="Create a Personal Access Token">
    Sign in to GitGuardian. In the sidebar, open **Settings → API → Personal Access Tokens** and click **Create token**:

    - **Name**: `cloudthinker`
    - **Expiration**: pick a date that matches your rotation policy
    - **Scopes**: tick the read variant of `incidents`, `secrets`, and `sources` (for example `incidents:read`). That covers the verify and example prompts. Add others from [Required permissions](#required-permissions) only if you need them.

    Copy the token right away. GitGuardian shows it once.
  </Step>
  <Step title="Add the connection in CloudThinker">
    In the sidebar, click **More → Workspace settings → Connections**, stay on the **Builtin Connections** tab, and select **GitGuardian**. Fill in:

    - **GITGUARDIAN_URL**: your dashboard or instance URL from the table above
    - **GITGUARDIAN_PERSONAL_ACCESS_TOKEN**: the token you just created

    Click **Connect**.

    **Success state:** GitGuardian shows **Connected** in the Connections list. Then open a new chat and send the [verify prompt](#verify-the-connection) to confirm the token's scopes.
  </Step>
</Steps>

<Warning>
If you lose the token, you can't view it again. Create a new one in GitGuardian and paste it into the connection.
</Warning>

## Connection details

| Field | Description | Example |
|-------|-------------|---------|
| **GITGUARDIAN_URL** | Dashboard or self-hosted instance URL. CloudThinker works out the API endpoint from it. | `https://dashboard.eu1.gitguardian.com` |
| **GITGUARDIAN_PERSONAL_ACCESS_TOKEN** | Personal Access Token from the workspace | `<your-token>` |

To reach a second GitGuardian workspace, add it as a separate connection with its own token.

## Required permissions

Each PAT scope unlocks one family of agent capabilities. Where GitGuardian offers a `:read` and a `:write` variant, pick `:read`. If an agent says it can't do something, the token is usually missing that scope.

| Scope | Enables |
|-------|---------|
| `incidents` | List, inspect, and triage secret incidents. Minimum set. |
| `secrets` | Read detected secrets and where each one occurs. Minimum set. |
| `sources` | List and inspect the monitored sources (repositories). Minimum set. |
| `scan` | Scan content for secrets on request |
| `honeytokens` | Read to list honeytokens. Write to create them. |
| `custom_tags` | Read and manage custom tags |
| `audit_logs` | Read the workspace audit log |

<Tip>
A PAT also inherits the workspace role of the person who creates it. Create it from the least-privileged member who still has the access you need, and pick read access whenever a scope offers it.
</Tip>

## Agent capabilities

| Capability | What agents can do | Scope needed | Approval |
|------------|--------------------|--------------|----------|
| **Incident triage** | List and inspect secret incidents with their status and severity | `incidents` | No |
| **Incident investigation** | Show the sources and occurrences behind an exposed credential | `incidents`, `secrets`, `sources` | No |
| **Token inspection** | Report the scopes the connected token carries | Any | No |
| **Honeytokens** | List honeytokens and their status | `honeytokens` read | No |
| **Honeytoken creation** | Create a new honeytoken | `honeytokens` write | Through Approvals |

Reads run without asking. Creating a honeytoken needs `honeytokens:write` and a token created by a **Manager**, and it only happens when you ask for it.

<ApprovalDefault />

To be asked before every honeytoken is created, choose **Manual**. Once CloudThinker turns on [Rule enforcement](/guide/approvals/rules#troubleshooting) for your workspace, an **Ask first** [Rule](/guide/approvals/rules) can single out honeytoken creation.

### Verify the connection

```text
Check the GitGuardian connection, list the scopes on the token, and count open secret incidents
```

Expect the list of scopes on the token and a count of open incidents, meaning incidents in **Triggered** or **Assigned** status. A scope you expected but don't see means the token needs updating.

### Example prompts

```text
List open GitGuardian incidents sorted by severity, with the repository for each one
Investigate the newest GitGuardian incident and summarize the exposed credential and its sources
```

## Troubleshooting

<Accordion title="Connect fails or requests return 401">
The token is wrong, expired, or revoked. Create a new Personal Access Token. In **More → Workspace settings → Connections**, open **GitGuardian**, click the pencil icon on the connection's row, click **Replace…**, paste the token into **GITGUARDIAN_PERSONAL_ACCESS_TOKEN**, and click **Save and test**.
</Accordion>

<Accordion title="Requests return 403">
The token lacks the scope for that request, or its creator's workspace role is too low. Add the scope in GitGuardian (honeytoken creation needs **Manager**), then update the connection with the new token.
</Accordion>

<Accordion title="An agent says a capability isn't available">
The token is missing the matching scope. Compare the request against [Required permissions](#required-permissions), create a token with that scope, and update the connection.
</Accordion>

<Accordion title="No incidents, or the endpoint can't be reached">
**GITGUARDIAN_URL** points at the wrong region or instance. A US token doesn't work against the EU dashboard. Use the exact address you sign in at.
</Accordion>

## Security

<ConnectionSecurity />

- **Read scopes first**: add `honeytokens:write` or a Manager-role token only if you want agents to create honeytokens.
- **Dedicated token**: name it `cloudthinker` so you can revoke it in GitGuardian without breaking other tools.
