Connect Icinga so CloudThinker can check hosts and services, then acknowledge or recheck one. The connection uses the credentials described below, with access limited by the account behind it.

## Prerequisites

- Access to the Icinga account or service containing the records you want to investigate.
- Permission to prepare the credential below, or an administrator who can prepare it for you.
- The **Admin** role in your CloudThinker workspace to add a connection. See [Roles](/guide/security/roles).
- A network path from CloudThinker to the service. For private services, see [Reaching private services](/guide/connections/overview#reaching-private-services).

## Setup

<Steps>
  <Step title="Prepare the credential">
    Ask the Icinga administrator for a dedicated ApiUser and its password. Use the Icinga 2 API address and the CA certificate that issued its server certificate.

    See the [Icinga documentation](https://icinga.com/docs/icinga-2/latest/doc/12-icinga2-api/) for the provider’s credential and access controls. Keep secrets out of chat messages.
  </Step>
  <Step title="Add the connection">
    Open **Settings → Workspace → Connections**, find **Icinga**, and click **Connect**. Fill in the fields in [Connection details](#connection-details), then click **Connect**.

    **Success state:** the connection shows a **Connected** status. Use the verification prompt below to check that it reaches the intended account and records.
  </Step>
  <Step title="Check the scope">
    Open a conversation, select the new connection with **#**, and ask for a read-only summary. Check the account, region, and resources in the answer before using it for an investigation.
  </Step>
</Steps>

## Connection details

| Field | Required | What to enter |
|---|---|---|
| **API URL** | Yes | The Icinga 2 API address, usually port 5665, such as https://icinga.example.com:5665. |
| **API user** | Yes | An ApiUser object. Reads need status/query and objects/query/Host, Service, and Downtime; changes also need actions/acknowledge-problem, remove-acknowledgement, schedule-downtime, remove-downtime, and reschedule-check. |
| **API password** | Yes | The password of that ApiUser. |
| **CA certificate (optional)** | Optional | PEM of the CA that issued the API certificate, usually /var/lib/icinga2/certs/ca.crt on the master. Leave empty to use public trust. The certificate and hostname are always checked. |

Use the address and credential from the same account or deployment. Keep any region, organization, or page selection aligned with that account.

## Required permissions

Reads need status/query and objects/query/Host, objects/query/Service, and objects/query/Downtime. Add only the action permissions needed for acknowledgement, downtime, and rescheduling.

<Tip>
Start with read access to the smallest useful scope. This guide covers investigation; broad administrative or write access is unnecessary for these reads.
</Tip>

## Agent capabilities

| Capability | What you can ask for |
|---|---|
| **Host and service problems** | Check hosts and services, then acknowledge or recheck one. |
| **Downtimes and acknowledgements** | Inspect downtimes and acknowledgements within the connected account’s scope. |
| **Approved monitoring actions** | Acknowledge a problem, remove an acknowledgement, manage downtime, or request a recheck when authorized. |

Icinga 2 API permissions are separate from Icinga Web permissions. A web login alone does not provide the required ApiUser access.

Reads inspect host and service status. Acknowledging or removing an acknowledgement, scheduling or ending downtime, and requesting a recheck are changes governed by [Approvals](/guide/approvals/overview). A permission error is not an empty result; ask which checks failed when the answer is incomplete.

### Verify the connection

```text
Using this Icinga connection, summarize its account or service scope and host and service problems. Report any access failures without changing anything.
```

Check that the answer names the expected service and returns current records, or explains why a read failed. An empty collection alone is not proof that the entire service is healthy.

### Example prompts

```text
Summarize host and service problems in Icinga and highlight items needing attention.
Review downtimes and acknowledgements and explain the limits of the data you could read.
```

## Troubleshooting

<Accordion title="Authentication fails">
  Check that the credential belongs to the account or deployment selected in the form. Replace a revoked or expired credential in the connection; do not paste it into the conversation.
</Accordion>
<Accordion title="Some records are missing or access is denied">
  Check the credential’s role and resource scope against [Required permissions](#required-permissions). Ask CloudThinker to name the failed check. Do not interpret a denied read as an empty collection.
</Accordion>
<Accordion title="The service cannot be reached">
  Check the service address, region, and network allowlist. If the form accepts a CA certificate, supply the CA that issued the service’s certificate. For private services, check the network route from CloudThinker.
</Accordion>

## Security

<ConnectionSecurity />

- Keep the credential scoped to the resources this workspace needs. Replace it in CloudThinker when you rotate or revoke it at the provider.
