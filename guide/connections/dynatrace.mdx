Connect a Dynatrace environment to let CloudThinker agents list open problems, run DQL (Dynatrace Query Language) against logs, metrics, spans, and events in Grail, review vulnerabilities, and find the entities a problem touches. The connection uses the official Dynatrace MCP server, signed in with one **platform token** for one environment.

## Prerequisites

- A Dynatrace SaaS environment on the Dynatrace Platform, with the data you want agents to read.
- Permission to create platform tokens for that environment.
- Your environment URL in the Platform format: `https://<environment-id>.apps.dynatrace.com`.

## Setup

<Steps>
  <Step title="Find your environment URL">
    Sign in to Dynatrace and copy the address from your browser up to `.apps.dynatrace.com`, for example `https://abc12345.apps.dynatrace.com`.

    Use the `apps.dynatrace.com` address, not a classic `live.dynatrace.com` one. The MCP server only talks to Platform APIs.
  </Step>
  <Step title="Create a platform token">
    Create a Dynatrace **platform token** named `cloudthinker`. Grant `app-engine:apps:run` plus the read scopes for the data you want agents to query (see [Required permissions](#required-permissions)).

    Copy the token right away. Dynatrace may not show it again.
  </Step>
  <Step title="Add the connection in CloudThinker">
    Open **Workspace Settings → Connections**, stay on the **Builtin Connections** tab, and select **Dynatrace**. Fill in:

    - **DT_ENVIRONMENT**: your environment URL
    - **DT_PLATFORM_TOKEN**: the token you just created

    Click **Connect**.

    **Success state:** the **Connect Dynatrace** dialog closes without an error. Run the verify prompt below to confirm the token can read your environment.
  </Step>
</Steps>

<Warning>
Use a **platform token**, not a classic Dynatrace API token. Classic API tokens don't carry the Platform scopes the MCP server needs, so most requests fail with 401 or 403.
</Warning>

## Connection details

| Field | Description | Example |
|-------|-------------|---------|
| **DT_ENVIRONMENT** | Dynatrace Platform environment URL | `https://abc12345.apps.dynatrace.com` |
| **DT_PLATFORM_TOKEN** | Platform token for that environment | `<your-platform-token>` |

To reach another environment, add it as a separate connection with its own token.

## Required permissions

Start with `app-engine:apps:run` and add only the read scopes for the data types agents should query.

| Scope | What it enables |
|-------|-----------------|
| `app-engine:apps:run` | Required. Runs the Dynatrace MCP tools |
| `storage:buckets:read` | Discover the Grail buckets the token can read |
| `storage:logs:read` | Query logs with DQL |
| `storage:metrics:read` | Query metrics with DQL |
| `storage:spans:read` | Query traces and spans with DQL |
| `storage:events:read` | Query events with DQL |
| `storage:entities:read` | Query monitored entities with DQL |
| `storage:smartscape:read` | Query Smartscape topology with DQL |
| `storage:security.events:read` | Query security events with DQL |
| `storage:bizevents:read` | Query business events with DQL |
| `storage:user.events:read` | Query user events with DQL |
| `storage:user.sessions:read` | Query user sessions with DQL |
| `storage:system:read` | Query system data with DQL |
| `storage:files:read` | Use lookup data in DQL `load` statements |
| `document:documents:write` | Optional. Lets agents create a Dynatrace notebook |

Davis analyzers and the Slack, email, event, and workflow tools need their own Dynatrace scopes beyond this table. Add them only if you want agents to use those tools, using the scope names in the Dynatrace MCP server documentation.

<Tip>
If DQL works for one data type and fails for another, the token is missing that type's `storage:*:read` scope. Add it in Dynatrace and update the token in the connection.
</Tip>

## Agent capabilities

| Capability | What agents can do | Approval |
|------------|--------------------|----------|
| **Environment check** | Confirm the connection and read basic environment info | No |
| **Problems** | List open and recent problems and the services or hosts they affect | No |
| **Vulnerabilities** | List vulnerabilities, filtered by risk score, such as 7.0 and above | No |
| **Entities** | Find monitored entities by name | No |
| **DQL** | Validate a query, then run it with a small record limit | No |
| **DQL help** | Turn a plain-language question into DQL, or explain an existing query | No |
| **Kubernetes events and exceptions** | List Kubernetes events for a cluster or workload, and recent exceptions | No |
| **Davis analyzers** | List the available Davis analyzers and run one on a time window | No |
| **Notebooks** | Create a Dynatrace notebook with the findings | Yes |
| **Notifications and events** | Send a Slack message or email through Dynatrace, send an event, or create a notification workflow | Yes |

Agents validate each DQL query before running it and start with 50 to 100 records, so a query doesn't burn through your Grail query budget. Every write goes through [Approvals](/guide/approvals/overview), and a rejected call isn't retried.

### Verify the connection

```text
Run Dynatrace discovery and list open problems and high-risk vulnerabilities
```

Expect your environment info, the open problems with their affected entities, and any vulnerabilities with a risk score of 7.0 or higher. If the token has the Davis scopes, the list of Davis analyzers appears too.

### Example prompts

```text
Which Dynatrace problems are open in production right now, and which services do they affect?
Query Dynatrace logs for errors from the checkout service in the last 30 minutes
List Dynatrace vulnerabilities with a risk score of 7 or higher on internet-facing services
Show the Kubernetes events for the payments workload in the last hour
```

Name a service, entity, or bucket and a short time window in large environments. Narrow queries return faster and use less Grail budget.

## Troubleshooting

<Accordion title="Connect fails or every request returns 401">
The token is missing, expired, revoked, or a classic API token. Create a new platform token with `app-engine:apps:run`, edit the connection, and paste it into **DT_PLATFORM_TOKEN**. Also check that **DT_ENVIRONMENT** uses `apps.dynatrace.com`, not `live.dynatrace.com`.
</Accordion>

<Accordion title="Some queries return 403">
The token lacks the scope for that data type. For example, log queries need `storage:logs:read`. Add the scope in Dynatrace and update the connection.
</Accordion>

<Accordion title="A DQL query returns no rows">
The query may target a bucket the token can't read, a time range with no data, or a misspelled entity. Ask the agent to find the entity by name first, then rerun the query on a known service and a short window.
</Accordion>

<Accordion title="Requests return 429">
The Grail query budget is used up. Narrow the time window and record limit, then ask again.
</Accordion>

<Accordion title="An entity or problem isn't found (404)">
The entity was renamed or the id is wrong. Ask the agent to look it up by name instead of by id.
</Accordion>

## Security

<ConnectionSecurity />

- **Platform token, read scopes first**: add `document:documents:write` or any notification scope only if you want agents to create notebooks or send messages through Dynatrace.
- **One token per connection**: create a token used only by CloudThinker so you can revoke it without breaking other tools.
