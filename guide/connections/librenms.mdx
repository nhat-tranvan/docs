Connect LibreNMS so CloudThinker can inspect device health and alerts and review maintenance needs. The connection uses a LibreNMS API token.

## Prerequisites

- Access to the LibreNMS account or installation containing the data you want to investigate.
- A workspace role that can add connections. See [Roles](/guide/security/roles).
- An HTTPS route from CloudThinker to the provider API. For a private service, see [Reaching private services](/guide/connections/overview#reaching-private-services). Access through your browser or local SSH tunnel alone is insufficient.

## Setup

<Steps>
  <Step title="Prepare access">
    Ask your LibreNMS administrator for an API token associated with a user that can view the intended devices and alerts. Use the same HTTPS address as the LibreNMS installation. For a private certificate authority, obtain its PEM certificate before connecting.

    See the [provider documentation](https://docs.librenms.org/API/API-Docs/) for its current access requirements.
  </Step>
  <Step title="Add the connection">
    Open **Connections**, find **LibreNMS**, and choose **Connect**. Enter the fields in [Connection details](#connection-details), then click **Connect**. Enter credentials only in the connection form; do not include them in a chat message.

    **Success state:** the connection shows **Connected**. This confirms the connection was established; run the verification prompt below to check the data access needed for an investigation.
  </Step>
  <Step title="Check the intended scope">
    Run the verification prompt below. Confirm the returned account, project, or resource names belong to the intended scope before asking for a deeper investigation. If a section fails, check its permissions rather than interpreting the failure as an empty result.
  </Step>
</Steps>

## Connection details

| Field | Description | Example |
|-------|-------------|---------|
| **LibreNMS URL** | HTTPS address of the LibreNMS installation. | https://librenms.example.com |
| **API token** | Dedicated user’s API access token. | Copy from LibreNMS |
| **CA certificate (optional)** | Private issuing CA certificate; empty uses public trust. | Leave empty for public trust |

## Required permissions

A global-read user can read device and alert information. Alert acknowledgement and maintenance changes require the matching administrative rights. Restrict the token to a dedicated user instead of sharing a personal administrator token.

## Agent capabilities

| Capability | What CloudThinker can do |
|------------|-------------------------|
| **Devices** | Review device state and details for a selected device. |
| **Alerts** | Inspect alert severity, state, and affected devices. |
| **Maintenance** | Review the target before scheduling an approved maintenance change. |

A connection failure is not evidence that a device is down. Returned device and alert lists are bounded. Read the current state after an uncertain change before asking to repeat it.

Agents can acknowledge alerts, remove alert muting, and manage the supported maintenance operations through [Approvals](/guide/approvals/overview). Identify the exact alert or device and the intended maintenance window before approval. Device maintenance silences every alert on that device and can only be ended early in the LibreNMS UI.

### Verify the connection

```text
Summarize LibreNMS device health and active alerts, identifying any failed inventory reads
```

Expect named resources or a clear empty result for each successful read. Keep any permission errors separate from the resources that were successfully inspected.

### Example prompts

```text
Investigate the highest-severity LibreNMS alerts and show their affected devices
Show the current health details of the selected LibreNMS device
```

Use a resource returned by the verification step and a short time range where relevant. Narrow requests are easier to verify than account-wide conclusions.

## Troubleshooting

<Accordion title="Credentials are rejected">
Check the credential fields belong to the same account and have not expired or been revoked. Replace credentials in the connection form, then rerun the verification prompt.
</Accordion>

<Accordion title="Certificate or hostname validation fails">
Check LibreNMS URL is the final HTTPS address and matches the server certificate. Supply the complete issuing CA certificate when your installation uses a private CA.
</Accordion>

<Accordion title="Requests fail or results are incomplete">
Check the provider’s availability, the selected resource scope, and any returned permission or rate-limit message. Narrow the request before retrying. For a private API, confirm the network route from CloudThinker itself, not only from your workstation.
</Accordion>

## Security

<ConnectionSecurity />

- Keep access limited to the intended account and resources. Replace or revoke credentials when the connection is no longer needed.
- Review the exact resource and proposed change before approving a write. An uncertain result needs a fresh read before retrying.
