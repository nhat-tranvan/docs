Connect CircleCI so CloudThinker agents can read pipeline status, pull build and test logs to find why a run failed, spot flaky tests, and validate your `.circleci/config.yml`. The connection uses a CircleCI personal API token, so agents reach exactly the projects the token's user can see.

## Prerequisites

- A CircleCI account that can see the organization and projects you want agents to investigate.
- At least one project that account follows. Agents discover projects from the followed list. To follow one, sign in to CircleCI as the token's user, open **Projects**, and click **Follow Project** next to each repository.
- For flaky tests and job test results: your jobs must upload JUnit results with `store_test_results`. Without it, CircleCI has no test data to return.
- To let agents start or rerun pipelines: the same account needs permission to trigger pipelines on those projects.
- For a self-hosted CircleCI Server: the server must be reachable from CloudThinker over HTTPS. See [Reaching private services](/guide/connections/overview#reaching-private-services).

## Setup

<Steps>
  <Step title="Create a personal API token">
    In CircleCI, open **User Settings → Personal API Tokens** ([app.circleci.com/settings/user/tokens](https://app.circleci.com/settings/user/tokens)) and click **Create New Token**. Name it `cloudthinker`.

    Copy the token right away. CircleCI shows it only once.
  </Step>
  <Step title="Add the connection">
    Open **More → Workspace settings → Connections**, stay on the **Builtin Connections** tab, and select **CircleCI**. Fill in:
    - **CIRCLECI_TOKEN**: the token you just created.
    - **CIRCLECI_BASE_URL**: leave it as `https://circleci.com` for CircleCI cloud. Change it only for a self-hosted CircleCI Server install.

    Click **Connect**.

    **Success state:** the dialog closes and the connection shows **Connected**.
  </Step>
  <Step title="Confirm the token works">
    Run the prompt in [Verify the connection](#verify-the-connection). CloudThinker doesn't check the token with CircleCI when you connect, so a **Connected** status alone doesn't prove the token is valid.
  </Step>
</Steps>

## Connection details

| Field | Required | Description | Example |
|-------|----------|-------------|---------|
| **CIRCLECI_TOKEN** | Yes | Personal API token. It carries the access of the user who created it | `CCIPAT_...` |
| **CIRCLECI_BASE_URL** | No | Host of your CircleCI install. Host only, no trailing path | `https://circleci.com` |

There's no organization or project ID to enter. Agents resolve them from the token's followed projects.

## Required permissions

A personal API token has the same access as the CircleCI user who created it. That user's project access is the ceiling on what agents can read or change.

| What you want agents to do | What the token's user needs |
|----------------------------|-----------------------------|
| Read status, logs, test results, artifacts | Read access to the project |
| Start a pipeline, rerun a workflow, run evaluation tests | Permission to trigger pipelines on the project |
| Roll back a deployment | A rollback pipeline set up for the project in CircleCI **Deploys**, plus permission to trigger pipelines on it |

**Evaluation tests** are CircleCI's prompt-template tests: the agent runs them as a pipeline on CircleCI.

<Tip>
Create the token under a dedicated CircleCI user that only belongs to the projects you want investigated. That user needs membership in your GitHub or Bitbucket organization, so a VCS machine user is the usual pattern. Check whether it counts as a user on your CircleCI plan. Write actions still go through [Approvals](/guide/approvals/overview), so the token sets the ceiling and Approvals decides each action.
</Tip>

## Agent capabilities

| Capability | What agents can do |
|------------|--------------------|
| **Project discovery** | List followed projects and their organizations |
| **Pipeline status** | Read the latest pipeline status for a project and branch |
| **Failure triage** | Pull build failure logs and job test results to find the failing step |
| **Flaky tests** | Find tests that pass and fail on the same code |
| **Config validation** | Check a `.circleci/config.yml` and explain errors |
| **Artifacts** | List the artifacts a job produced |
| **Usage review** | Download usage data and flag underused resource classes (paid plans only) |
| **Pipeline controls** | Run a pipeline, rerun a workflow, run evaluation tests, roll back a deployment. **Each goes through your Approvals** |

Before any write, the agent tells you what will happen (for example, "starts a pipeline on `gh/acme/api` branch `main`") and shows the exact inputs. A rollback also lists the current and target versions and asks you to confirm the target.

<ApprovalDefault />

To be asked every time, choose **Manual** as your [Approval mode](/guide/approvals/approval-mode) so a person approves every change. Once CloudThinker turns on [Rule enforcement](/guide/approvals/rules#troubleshooting) for your workspace, an **Ask first** [Rule](/guide/approvals/rules) can narrow that to this connection alone.

### Verify the connection

```text
List my followed CircleCI projects and show the latest pipeline status for each
```

Expect each followed project by slug (such as `gh/acme/api`) with its latest pipeline status. A project you expected but don't see isn't followed by the token's user.

### Example prompts

```text
The main branch of gh/acme/api failed on CircleCI. Pull the failure logs and tell me which step broke and why
Which tests in gh/acme/api are flaky, and how often does each one fail?
```

## Troubleshooting

<Accordion title="Every request returns 401 Unauthorized">
The token is missing, expired, or revoked. Create a new personal API token and update the **CIRCLECI_TOKEN** field on the connection.
</Accordion>

<Accordion title="Reads work but starting or rerunning a pipeline returns a permission error">
The token's user can read the project but can't trigger pipelines on it. Create the token under a user with trigger permission on that project, then update the connection.
</Accordion>

<Accordion title="The connection is Connected but no projects appear">
The token's user follows no projects. Follow at least one project in CircleCI, then ask again.
</Accordion>

<Accordion title="Flaky tests or job test results come back empty">
The jobs don't upload test results. Add a `store_test_results` step that points at your JUnit XML output, let a few pipelines run, then ask again.
</Accordion>

<Accordion title="A project returns 404">
Project slugs need a VCS prefix: `gh/<org>/<repo>` for GitHub or `bb/<org>/<repo>` for Bitbucket. Ask the agent to list your followed projects and use the slug from that list.
</Accordion>

<Accordion title="Usage analysis asks for an organization ID">
Usage data needs the organization UUID, which no CircleCI API call returns. Copy it from **Organization Settings → Overview → Organization ID** in CircleCI and paste it into the chat. The usage API is paid-plan only and covers up to 32 days per request.
</Accordion>

<Accordion title="A self-hosted install returns 404 or auth errors">
**CIRCLECI_BASE_URL** is still `https://circleci.com`, or it includes a path. Set it to your CircleCI Server host only, such as `https://circleci.example.com`.
</Accordion>

## Security

<ConnectionSecurity />

- **Use a dedicated user**: CircleCI personal tokens have no scopes of their own, so the token user's project membership is the only way to limit reach.
- **Keep controls approval-gated**: a pipeline run bills compute and can deploy. Leave these actions behind [Approval mode](/guide/approvals/approval-mode) rather than auto-approving them.
