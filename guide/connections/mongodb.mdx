Connect a MongoDB deployment or MongoDB Atlas cluster to let CloudThinker agents inspect databases, collections, indexes, and query plans. You give CloudThinker one connection string for a dedicated database user, and the connection always runs in read-only mode: agents can query and explain, but can't insert, update, drop, or create indexes.

## Prerequisites

- A MongoDB deployment or Atlas cluster CloudThinker can reach over the network. Agents connect from CloudThinker's managed sandbox, so `localhost` and private addresses resolve there, not on your network.
- Permission to create a database user: `userAdmin` on `admin` for self-hosted MongoDB, or **Project Owner** in Atlas.

## Setup

<Steps>
  <Step title="Create a read-only user">
    <Tabs>
      <Tab title="Self-hosted MongoDB">
        Connect with `mongosh` as an admin, then create the user on the `admin` database:

        ```javascript
        use admin
        db.createUser({
          user: "cloudthinker_readonly",
          pwd: "<secure-password>",
          roles: [
            { role: "readAnyDatabase", db: "admin" },
            { role: "clusterMonitor", db: "admin" }
          ]
        })
        ```
      </Tab>
      <Tab title="MongoDB Atlas">
        In Atlas, open **Security → Database Access** and click **Add New Database User**. Choose **Password** authentication, enter `cloudthinker_readonly` and a strong password, and under **Database User Privileges** pick the built-in role **Read Any Database**. Click **Add User**.

        For server status, logs, and replica lag, also add the **clusterMonitor** role under **Specific Privileges**.
      </Tab>
    </Tabs>
  </Step>
  <Step title="Open network access">
    Allow CloudThinker to reach the deployment. For self-hosted MongoDB, allow inbound connections on port `27017` in your firewall or security group and make sure `bindIp` in `mongod.conf` isn't only `127.0.0.1`. In Atlas, add an entry under **Security → Network Access → IP Access List**.
  </Step>
  <Step title="Build the connection string">
    <Tabs>
      <Tab title="Self-hosted MongoDB">
        ```text
        mongodb://cloudthinker_readonly:<secure-password>@mongo.example.com:27017/?authSource=admin&tls=true&appName=CloudThinker
        ```

        Drop `tls=true` only if the server doesn't support TLS.
      </Tab>
      <Tab title="MongoDB Atlas">
        On your cluster, click **Connect**, choose **Drivers**, and copy the `mongodb+srv://` string. Put in the user and password from step 1:

        ```text
        mongodb+srv://cloudthinker_readonly:<secure-password>@cluster0.abcde.mongodb.net/?appName=CloudThinker
        ```

        Atlas turns on TLS for `mongodb+srv://` strings automatically.
      </Tab>
    </Tabs>

    `appName=CloudThinker` labels the connection in your MongoDB logs. URL-encode special characters in the password (`@` becomes `%40`).
  </Step>
  <Step title="Add the connection in CloudThinker">
    Open **Connections** in the sidebar, select **MongoDB**, and click **Connect**. Paste the string into **MDB_MCP_CONNECTION_STRING** and click **Connect**.

    **Success state:** the connection shows **Testing**, then **Connected**. CloudThinker then runs a one-time, read-only [discovery](/guide/connections/overview) of your databases and collections.
  </Step>
</Steps>

## Connection details

| Field | Required | Description | Example |
|-------|----------|-------------|---------|
| **MDB_MCP_CONNECTION_STRING** | Yes | Full MongoDB URI with user, password, host, and options | `mongodb+srv://cloudthinker_readonly:<password>@cluster0.abcde.mongodb.net/` |

Useful options in the string:

| Option | Use it when |
|--------|-------------|
| `authSource=admin` | The user lives on the `admin` database and the string names a different database |
| `tls=true` | The server supports TLS and the scheme is `mongodb://` |
| `readPreference=secondaryPreferred` | You want agent reads to go to secondaries and stay off the primary |
| `appName=CloudThinker` | You want to spot CloudThinker sessions in logs and `currentOp` |

## Required permissions

| Role | What it unlocks |
|------|-----------------|
| `readAnyDatabase` | List databases and collections, sample documents, run `find`, `aggregate`, and `count`, and read indexes and query plans |
| `clusterMonitor` | Server status, replica set status and lag, and recent server logs |

<Tip>
To limit agents to one database, grant `read` on that database instead of `readAnyDatabase`. Never grant `readWrite`, `dbAdmin`, or `root`: the connection is read-only anyway, so extra roles add risk without adding capability.
</Tip>

## Agent capabilities

| Capability | What agents can do |
|------------|--------------------|
| **Inventory** | List databases and collections with document counts and storage size |
| **Schema** | Infer field names and types from sampled documents |
| **Queries** | Run bounded `find`, `aggregate`, and `count` queries to answer questions about your data |
| **Index review** | List indexes per collection and check whether a query uses one with `explain` |
| **Server health** | Read server logs, connections, and replica status (needs `clusterMonitor`) |

Agents can't write. Insert, update, delete, drop, and index-creation tools are switched off for this connection, so a request like "drop the sessions collection" can't run. Agents can still recommend an index for you to create.

### Verify the connection

```text
List the MongoDB databases with their collection counts and storage size
```

Expect each database name with its collections and size. On Atlas, the `local` and `config` system databases are skipped because Atlas blocks access to them.

### Example prompts

```text
Which queries on the orders collection scan the whole collection, and what index would fix them?
Show the indexes on every collection in the shop database and flag ones that look redundant
What does a typical document in users look like? List its fields and types
```

## Troubleshooting

<Accordion title="Authentication failed">
The user, password, or auth database is wrong. If you created the user on `admin` and the string names another database, add `authSource=admin`. In Atlas, check the user exists under **Database Access** and that special characters in the password are URL-encoded.
</Accordion>

<Accordion title="Server selection timed out, or connection refused">
CloudThinker can't reach the deployment. In Atlas, check the **IP Access List**. For self-hosted MongoDB, check your firewall and that `bindIp` isn't only `127.0.0.1`. A deployment on a private network needs a reachable endpoint first.
</Accordion>

<Accordion title="not authorized on admin to execute command (serverStatus, replSetGetStatus, getLog)">
The user is missing `clusterMonitor`. Add it on the `admin` database, then ask the agent again. Queries against your data keep working without it.
</Accordion>

<Accordion title="An agent says a write is blocked by read-only mode">
This is expected. The MongoDB connection is read-only. Make the change yourself, or ask the agent for the exact command to run.
</Accordion>

## Security

<ConnectionSecurity />

- **Read-only on two layers**: the connection itself can't write, and a user with only `read` or `readAnyDatabase` can't either, even if the string leaks.
- **Use TLS**: use `mongodb+srv://` on Atlas, or `tls=true` on self-hosted MongoDB, so credentials and query results are encrypted in transit.
