Connect your Rancher server so CloudThinker can list the clusters, projects, and nodes Rancher manages, report cluster health and node readiness, and show who holds Rancher access to a cluster or project. The connection uses a **Rancher API token** and is **read-only by design**: agents can describe what Rancher manages and cannot change any of it.

## Prerequisites

- A Rancher server that serves the Rancher Kubernetes API (Rancher 2.8 and later), reachable from the internet over **HTTPS**. Commands run in the CloudThinker cloud. For an internal Rancher, see [Reaching private services](/guide/connections/overview#reaching-private-services) for the egress IP allowlist.
- Permission in Rancher to create a user and assign cluster and project roles.
- Optional: the **PEM certificate** of your private certificate authority, if Rancher's certificate is not publicly trusted.

<Info>
A workspace holds **one** Rancher connection. To inspect workloads, pods, and Kubernetes RBAC inside a cluster, add a [Kubernetes connection](/guide/connections/kubernetes) as well.
</Info>

## Setup

<Steps>
  <Step title="Create a dedicated Rancher user">
    Add a user for CloudThinker instead of reusing a person's account. The token you create next inherits this user's access, so a dedicated user keeps the scope visible and easy to revoke.

    1. Open **☰ → Users & Authentication → Users** and click **Create**.
    2. In each cluster you want inspected, open **Cluster and Project Members**. Add the user on the **Cluster Membership** tab with the cluster role, and on the **Project Membership** tab with the project role, from [Required permissions](#required-permissions).
  </Step>
  <Step title="Create an API key">
    Sign in as that user, open the **user avatar → Account & API Keys** in the upper right, and click **Create API Key**.

    - **Expiry**: pick a date that matches your rotation schedule. Rancher caps it at the server's `auth-token-max-ttl-minutes` setting, which you can check in **☰ → Global Settings → Settings**, and uses the cap without warning if you ask for longer. When the key expires, the connection switches to **Error**. Create a new key and swap it in through [Rotate a credential](/guide/connections/overview#rotate-a-credential).
    - **Scope**: leave it as **No Scope**. A scoped key only works against one cluster's Kubernetes API, which this connection does not use.

    Copy the **Bearer Token**. Rancher shows it only once.
  </Step>
  <Step title="Add the connection in CloudThinker">
    Open **Connections** in the sidebar, select **Rancher**, and fill in the fields from [Connection details](#connection-details). Click **Connect**.

    **Success state:** the connection shows **Connecting** and **Verifying**, then a **Connected** status. CloudThinker reads one cluster from Rancher to prove the token works.
  </Step>
</Steps>

## Connection details

| Field | Description | Example |
|-------|-------------|---------|
| **Rancher URL** | The HTTPS address you sign in to. No API path, query string, fragment, or credentials | `https://rancher.example.com` |
| **API token** | The Bearer Token from the API key, with no quotes, spaces, or line breaks | |
| **CA certificate bundle** | Optional. PEM certificates of a private certificate authority, under 256 KB, with no private key | `-----BEGIN CERTIFICATE-----...` |

TLS verification is always on, because the token travels with every request. If Rancher uses a private CA, paste that CA's certificate chain into **CA certificate bundle**. CloudThinker also refuses redirects, so the URL must be the address Rancher answers on directly.

## Required permissions

The token's user needs **read** access to clusters, nodes, projects, and cluster and project role bindings. Start from Rancher's built-in roles:

| Role | Where | What it gives |
|------|-------|---------------|
| **Cluster Member** | Each cluster to inspect | Views most cluster-level resources. Also lets the user create projects. The connection never uses that, since it sends reads only, but a leaked token could. Use a custom role for strict least privilege |
| **Read Only** | Each project to inspect | Views everything in the project, with no create, update, or delete |
| **Custom role** | Instead of Cluster Member | Only the reads the connection makes. Create it in **☰ → Users & Authentication → Role Templates**, on the **Cluster** tab |

A custom role needs one rule: API group `management.cattle.io`, resources `clusters`, `nodes`, `projects`, `clusterroletemplatebindings`, and `projectroletemplatebindings`, verbs `get` and `list`.

<Tip>
A Rancher API key has no read-only switch, so the token can see exactly what its user can see. Narrow access through the user's roles. Write permissions never help, because the connection has no way to send a change.
</Tip>

## What this connection cannot reach

The connection only sends read requests to Rancher's management resources. These stay out of reach even if the token's user could read them:

- Secrets, kubeconfigs, API tokens, and cluster registration tokens
- Cloud credentials, authentication settings, and global settings
- Any change to Rancher: creating, updating, deleting, or scaling
- The older Rancher `v3` API

Ask an agent to change something in Rancher and it tells you the connection cannot, and that nothing changed.

## Agent capabilities

| Capability | What agents do |
|------------|----------------|
| **Cluster inventory** | List the clusters Rancher manages, their projects, and their nodes |
| **Cluster health** | Report the current conditions of one cluster and the readiness of its nodes |
| **Who has access** | Show which users, groups, and service accounts hold a role on one cluster or project |
| **Project scope** | Show which cluster a project belongs to |

Each lookup returns one page of at most 50 rows. When Rancher does not report a total, agents say "returned 12" rather than "12 exist", so narrow the question to one cluster or project on large fleets. Whenever a message mentions Rancher, agents query it live instead of reusing a result from an earlier message.

### Verify the connection

```text
Summarize the clusters Rancher manages, their projects, and node health
```

You get a list of clusters with their projects and a count of ready and not-ready nodes.

### Example prompts

```text
Show the health conditions and node readiness of the prod-sea cluster
Who holds Rancher access to the prod-sea cluster, and is anything broader than it needs to be?
List the projects on staging-cluster and any nodes that are not ready
```

## Troubleshooting

<Accordion title="Rancher rejected the API token">
The key expired, was deleted, or was copied incompletely. Rancher shows the Bearer Token only once, so create a new key under **Account & API Keys** and update the connection.
</Accordion>

<Accordion title="Rancher accepted the token but it lacks read access to managed clusters">
The token signs in, but its user cannot read clusters. Give that user **Cluster Member** (or a custom read role) on the clusters you want inspected, then test the connection again.
</Accordion>

<Accordion title="The Rancher server did not expose the management.cattle.io RK-API">
RK-API is Rancher's Kubernetes-style management API, served under `/apis/management.cattle.io/v3`. The URL points somewhere other than the Rancher server root, or the Rancher release is older than 2.8. Reconnect with the plain Rancher address and check your version.
</Accordion>

<Accordion title="Could not reach the Rancher server">
Nothing answered, or the address redirected elsewhere. Check that the host is reachable from the internet, that the URL is the address Rancher answers on directly, and, for a private CA, that the bundle holds the CA that issued Rancher's certificate.
</Accordion>

<Accordion title="Rancher URL must use HTTPS outside local development">
The address starts with `http://`, which would send the token in clear text. Serve Rancher over HTTPS and reconnect with an `https://` URL.
</Accordion>

<Accordion title="Invalid Rancher CA certificate bundle or connection configuration">
The bundle is not plain PEM certificates, or the token has quotes, spaces, or line breaks around it. Paste only the CA certificate chain, never a private key, and re-copy the Bearer Token as one line.
</Accordion>

<Accordion title="Connection 'rancher' already exists. Only one instance is allowed.">
This workspace already has a Rancher connection. Edit that connection, or disconnect it first.
</Accordion>

<Accordion title="An agent reports fewer clusters than Rancher shows">
The token's user cannot see the rest, or the answer came from a single page of results. Check the user's cluster roles first, then ask about the specific cluster or project.
</Accordion>

## Security

<ConnectionSecurity />

- **Narrow through roles.** The token sees exactly what its user sees, so the user's roles are your only scope control.
- **Read-only by construction.** The connection can only send read requests, so no permission you grant lets an agent change Rancher.
