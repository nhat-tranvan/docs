Connect Neon to let CloudThinker agents list your projects, branches, and computes, inspect table schemas, and find slow queries, plus run SQL, branches, and migrations after approval. Neon connects with **OAuth** through Neon's hosted MCP server (MCP is the protocol agents use to call a service's tools), so you don't create or paste an API key.

<Warning>
Neon has no read-only switch, and under the default Approval mode AI can approve a write on its own, such as a branch delete or reset. Add an [Ask first or Deny Rule](#write-access) before you connect an account with production projects.
</Warning>

---

## Prerequisites

- A Neon account that can see the projects you want to investigate.
- The workspace Admin role in CloudThinker to add the connection. See [How access works](/guide/connections/overview#how-access-works).
- Optional: the `pg_stat_statements` extension on the databases where you want slow-query analysis. Run `CREATE EXTENSION IF NOT EXISTS pg_stat_statements;` in the Neon Console **SQL Editor** (or any Postgres client), once on each database you want analyzed.

## Setup

<Steps>
  <Step title="Open the Neon connection">
    In CloudThinker, go to **Connections → Neon** and click **Connect**.
  </Step>
  <Step title="Authorize CloudThinker in Neon">
    CloudThinker opens Neon in a new window. Sign in with the Neon account that owns or can access your projects, then approve access. Neon's OAuth has no read-only option, so CloudThinker gets the same access as that account.

    If the window doesn't open, your browser blocked the pop-up. CloudThinker shows a dialog instead: click **Open Neon** in it.
  </Step>
  <Step title="Return to CloudThinker">
    Switch back to the CloudThinker tab. If you used the **Open Neon** dialog, it closes on its own once the connection is ready.

    **Success state:** Neon shows a **Connected** status.
  </Step>
  <Step title="Run the verify prompt">
    Run the [verify prompt](#verify-the-connection) to confirm the authorized account sees the projects you expect.

    **Success state:** CloudThinker lists your Neon organizations and projects with their branches and computes.
  </Step>
</Steps>

## Connection details

Neon has no fields to fill in. Neon issues OAuth tokens during authorization and CloudThinker stores them for you.

A workspace holds one Neon connection. To use a different Neon account, click **Disconnect** on the Neon connection, then click **Connect** and sign in with the other account.

---

## Required permissions

CloudThinker gets the same access as the Neon account you authorize. Neon's OAuth has no read-only option, so pick the account deliberately.

| Agents can | Needs |
|------------|-------|
| List projects, branches, computes, and tables; read schemas | Access to the project in Neon |
| Analyze slow queries | Access to the project, plus `pg_stat_statements` enabled on the database |
| Run SQL, create or delete branches, reset a branch, apply migrations, tune queries, set up Neon Auth or the Data API | Write access in Neon, plus a pass through [approvals](/guide/approvals/overview) |

Every Neon organization member sees every project in that organization. To limit what agents reach, authorize with a separate Neon account that isn't in the organization, and share only the projects agents need with it. Those appear as shared projects. For production, that's the safe default: a dedicated account shared only on the projects agents need, plus an **Ask first** Rule added before you connect.

## Agent capabilities

| Capability | Description |
|------------|-------------|
| **Project discovery** | List organizations, your projects and shared projects, branch computes, and database tables |
| **Schema audit** | Describe a project and the schemas of its tables |
| **Slow query audit** | List the slowest queries and run a read-only `EXPLAIN` on `SELECT` statements |
| **SQL** | Run a statement or a transaction. CloudThinker shows the exact SQL first and says whether it changes schema or data. |
| **Branches** | Create, delete, or reset a branch from its parent |
| **Migrations and tuning** | Prepare a migration or query tuning, show you the result, then complete it as a separate approved step |
| **Neon Auth and Data API** | Provision and configure [Neon Auth](https://neon.com/docs/neon-auth/overview) (managed sign-in for your app's users, stored in your database), and provision the [Data API](https://neon.com/docs/data-api/get-started) (an HTTP API over your database tables). Both are writes that change how your app's users sign in or reach data, so they go through approvals |

Running SQL or `EXPLAIN` on a compute that has scaled to zero wakes it, and Neon bills the compute time while it runs.

CloudThinker never completes a migration in the same step that prepared it. You see what will change before anything is applied.

<Tip>
Neon Auth and the Data API change what your app's users can reach. Add an **Ask first** Rule for them so a person approves each one, even when the mode would let AI decide.
</Tip>

Check my Neon connection: list my organizations and projects with their branches and computes

## Write access

There's no read-only switch on Neon. Each SQL statement, branch change, and migration goes through your [Rules](/guide/approvals/rules) first, then your [Approval mode](/guide/approvals/approval-mode). New workspaces start on Auto mode with Rules plus AI, where unclear cases ask a person (shown as **Auto · Rules + AI · Ask me**). Accepted Rules decide first, AI judges any write no Rule covers, and anything AI isn't sure about waits for a person. See [The two modes](/guide/approvals/approval-mode#the-two-modes).

- **Approve production writes**: add an **Ask first** Rule on the Neon connection so a person approves every SQL statement and migration.
- **Make it effectively read-only**: add a **Deny** Rule on the Neon connection that covers every operation. Every statement through Neon's SQL tool counts as a change, a `SELECT` included, so Deny stops all SQL. Listing projects, branches, and tables, schema reads, and the slow-query list keep working.

To build either Rule:

<Steps>
  <Step title="Ask for the Rule">
    In a chat, type `/create-policy Ask first for every write on the Neon connection`. To block instead, ask for a **Deny** Rule.
  </Step>
  <Step title="Check the proposal">
    Open **Approvals** in the sidebar, then **Rules → Needs review**, and open the Rule. Check that **Effect** is **Ask first** (or **Deny**), the Rule carries the **Every operation** badge, and **Connections** names your Neon connection. **What would change** should show recent Neon writes as asking first (or refused).
  </Step>
  <Step title="Accept it">
    Select the Rule and click **Accept**.

    **Success state:** a toast confirms the accepted Rule, and it moves to the **Active** tab.
  </Step>
</Steps>

## Troubleshooting

<Accordion title="The authorization window closes but Neon never shows Connected">
Your browser may be signed in to a different Neon account, or the pop-up was blocked. Sign in to the right Neon account in the same browser, then click **Connect** again.
</Accordion>

<Accordion title="Agents can't find a project you expect">
You authorized a Neon account without access to that project. Click **Disconnect**, then **Connect** with an account that can see it. Projects shared with you appear as shared projects.
</Accordion>

<Accordion title="Slow query analysis returns nothing or fails">
The database doesn't have `pg_stat_statements` enabled. Run `CREATE EXTENSION IF NOT EXISTS pg_stat_statements;`, run some traffic, and ask again. Schema inspection and SQL still work without it.
</Accordion>

<Accordion title="Slow query results are empty after a quiet period">
Neon doesn't keep `pg_stat_statements` data when a compute scales to zero, so the history starts over each time it wakes. If you need longer history, turn off scale to zero on the compute you investigate.
</Accordion>

<Accordion title="Neon shows an error after it worked before">
The OAuth authorization expired or was revoked in Neon. Click **Connect** in the error alert on the connection to authorize again.
</Accordion>

## Security

<ConnectionSecurity />

- **No connection strings by default**: agents don't fetch a database connection string unless you ask for one. A connection string includes the database password, and it shows in the chat, so anyone who can read the conversation can read it.
- **Data path**: agents call Neon's hosted MCP server at `https://mcp.neon.tech/mcp`. SQL, branch, and migration requests and their results pass through it, and the results show in the chat, so they're kept with the conversation. CloudThinker stores the OAuth tokens.
- **Cutting access**: click **Disconnect** on the Neon connection. If the grant is revoked on the Neon side instead, the connection shows an error until someone authorizes again.
- **Rejection is final**: if you decline a SQL statement or migration, CloudThinker doesn't retry it. It asks how you want to proceed.
