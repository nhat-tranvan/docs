Connect Sentry to let CloudThinker agents search issues, read the events and traces behind them, and pull root-cause signals during incident response and release triage. You sign in to Sentry once through OAuth, so there's no auth token to create or paste.

## Prerequisites

- A Sentry account that belongs to the organization and teams you want agents to investigate.
- Permission in that organization to authorize a third-party app.
- Sentry's hosted service at sentry.io. The connection always goes through Sentry's hosted MCP server and has no URL field, so a self-hosted Sentry can't connect.

## Setup

<Steps>
  <Step title="Start the connection">
    Open **Connections** in the sidebar, select **Sentry**, and click **Connect**. CloudThinker opens Sentry's authorization page.
  </Step>
  <Step title="Authorize CloudThinker">
    Sign in to the Sentry account that can see the right organization, then approve access. If your browser is signed in to a different Sentry account, sign out of it first.
  </Step>
  <Step title="Return to CloudThinker">
    Sentry sends you back to CloudThinker, which stores the tokens for you.

    **Success state:** the connection shows **Connected**. Run the prompt in [Verify the connection](#verify-the-connection) in a new chat to see which projects the account reaches.
  </Step>
</Steps>

## Connection details

There are no fields to fill in.

| Item | Value |
|------|-------|
| **Authentication** | OAuth. Sentry issues the tokens and CloudThinker stores them |
| **Endpoint** | `https://mcp.sentry.dev/mcp`, Sentry's hosted MCP server |

## Required permissions

Agents see the organizations, projects, and teams the authorizing Sentry account sees. CloudThinker can't narrow that grant, so to limit what agents reach, authorize with an account that only belongs to the teams you want investigated.

<Tip>
The capabilities below are all reads. Sentry's MCP server decides which other tools exist, and CloudThinker treats any tool the server doesn't mark as read-only as a write. Writes go through [Approvals](/guide/approvals/overview) before they run, and a **Deny** [Rule](/guide/approvals/rules) refuses them outright.
</Tip>

## Agent capabilities

| Capability | What agents can do |
|------------|--------------------|
| **Scoping** | List organizations, projects, and teams to pick where to look |
| **Issue search** | Search and inspect issues across projects |
| **Events and traces** | Read the individual events and distributed traces behind an issue |
| **Root-cause signals** | Pull the stack traces, tags, and context Sentry attaches to an issue |
| **Release triage** | Line up new errors against recent releases |

Agents combine Sentry with your other connections during an investigation. For example, they can match a spike in a Sentry issue to a deploy in your CI system or a metric change in your monitoring tool. See [Root cause analysis](/guide/incident/root-cause-analysis).

### Verify the connection

Ask CloudThinker in a new chat:

```text
List my Sentry projects and summarize the top unresolved issues
```

Expect the projects the authorizing account can see, each with its top unresolved issues and how often they occur. A project you expected but don't see is outside that account's access.

### Example prompts

```text
New Sentry errors in the payments project since the last release, ranked by affected users
Show the trace behind the checkout timeout issue and where it spends the most time
Which issues regressed in release 2.14.0 of web, and which tags (browser, region) do they share?
```

## Troubleshooting

<Accordion title="The OAuth flow doesn't complete">
Your browser is probably signed in to the wrong Sentry account, or to none. Sign in to the right account in Sentry, then click **Connect** again.
</Accordion>

<Accordion title="The agent can't find a project you expected">
The authorizing account isn't a member of that project's team or organization. Add the account to that team in Sentry, or disconnect and connect again with an account that has access.
</Accordion>

<Accordion title="The connection worked, then stopped">
Access was probably revoked in Sentry. Open the Sentry connection, click **Connect**, and authorize again with the same account. The connection keeps its agents, settings, and memory. To switch to a different account, disconnect and connect again instead.
</Accordion>

## Security

<ConnectionSecurity />

- **Scope by account**: the connection sees exactly what the authorizing Sentry account sees. A dedicated account with limited team membership keeps agents out of projects they don't need.
- **Revoke when unused**: remove CloudThinker under **User Settings → Authorized Applications** in Sentry (`sentry.io/settings/account/authorizations/`), then delete the connection in CloudThinker.
