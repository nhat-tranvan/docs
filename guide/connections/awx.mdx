Connect AWX to let CloudThinker agents find failed jobs and read their output, inspect inventories, hosts, and projects, and launch a job template once you approve. The connection signs in with one AWX **access token** and runs the `awx` command line tool against your server.

## Prerequisites

- An AWX server, or an Ansible Automation Platform controller, reachable from CloudThinker over HTTPS.
- An AWX user for CloudThinker with access to the organizations, inventories, and templates agents should reach.

## Setup

<Steps>
  <Step title="Create a user for CloudThinker">
    In AWX, create a user such as `cloudthinker` and give it roles only on the resources agents need (see [Required permissions](#required-permissions)). A dedicated user keeps the token's reach small and easy to revoke.
  </Step>
  <Step title="Create an access token">
    Sign in as that user. Go to **Access → Users**, open the user, select the **Tokens** tab, and click **Add**:

    - **Application**: leave empty
    - **Scope**: **Read** to monitor only, or **Write** if agents should launch and change things

    Copy the token. AWX shows it only once.
  </Step>
  <Step title="Add the connection in CloudThinker">
    Open **Workspace Settings → Connections**, stay on the **Builtin Connections** tab, and select **AWX**. Fill in:

    - **TOWER_HOST**: your AWX address, such as `https://awx.example.com`
    - **TOWER_OAUTH_TOKEN**: the token you copied

    Click **Connect**. CloudThinker runs `awx me` with the token to confirm it can sign in.

    **Success state:** the **Connect AWX** dialog closes without an error. Run the verify prompt below.
  </Step>
</Steps>

## Connection details

| Field | Description | Example |
|-------|-------------|---------|
| **TOWER_HOST** | Base URL of your AWX server, HTTPS | `https://awx.example.com` |
| **TOWER_OAUTH_TOKEN** | Access token for the CloudThinker user | `<your-token>` |

## Required permissions

Two things decide what agents can do: the token's scope and the user's roles in AWX. The token can never do more than the user.

| Goal | Token scope | AWX roles for the user |
|------|-------------|------------------------|
| Monitor jobs, inventories, and projects | **Read** | **Read** on the organizations or resources to watch |
| Launch selected job templates | **Write** | **Execute** on those job templates or workflow templates |
| Sync projects | **Write** | **Update** on those projects |
| Change hosts and groups | **Write** | **Admin** on those inventories |

<Tip>
Start with a Read token. Switch to Write only for the templates you want agents to run, and grant **Execute** per template rather than a broad organization role.
</Tip>

## Agent capabilities

| Capability | What agents can do | Approval |
|------------|--------------------|----------|
| **Discovery** | Summarize the signed-in user, organizations, inventories, projects, job templates, workflow templates, and recent jobs | No |
| **Jobs** | List jobs and workflow jobs by status, read job details, and read output of finished jobs | No |
| **Inventories** | Inspect inventories, hosts, and groups | No |
| **Projects** | Check project source control and sync status | No |
| **Templates and credentials** | Read job templates, workflow templates, and credential metadata. Credential secrets are never returned | No |
| **Launch** | Launch a job template or workflow template with extra variables, then follow it to completion | Yes |
| **Control and sync** | Cancel a running job, or sync a project from source control | Yes |
| **Change resources** | Create, modify, or delete hosts, groups, and other AWX resources | Yes |

Every write goes through [Approvals](/guide/approvals/overview), and a rejected request isn't retried. With a Read token, AWX refuses writes even after approval.

### Verify the connection

```text
Run AWX discovery and summarize my organizations, inventories, job templates, and the last few jobs with their status
```

Expect the user CloudThinker signed in as, then the names and counts of each resource type, then recent jobs with a status such as **successful** or **failed**.

### Example prompts

```text
List AWX jobs that failed in the last 24 hours and show the error from each job's output
Which AWX projects failed their last source control sync?
Launch the deploy-web job template with extra vars version=2.1.0 and tell me when it finishes
```

Use the real template, inventory, or project name. Agents look names up first and won't guess IDs.

## Troubleshooting

<Accordion title="Connect fails">
CloudThinker couldn't run `awx me` against **TOWER_HOST**. Check that the address is HTTPS and reachable from the internet, and that the token hasn't expired or been revoked. Create a new token if needed, edit the connection, and paste it in.
</Accordion>

<Accordion title="Requests return 401">
The token is missing, expired, or revoked. Create a new token for the CloudThinker user and update **TOWER_OAUTH_TOKEN**.
</Accordion>

<Accordion title="Launch or sync is refused">
The token has **Read** scope, or the user lacks **Execute** on the template or **Update** on the project. Create a Write token or grant the role in AWX, then ask again.
</Accordion>

<Accordion title="Lists come back empty">
The user can't see those resources. Grant **Read** on the organizations or inventories agents should reach. No need to reconnect; roles apply on the next request.
</Accordion>

<Accordion title="Job output is empty">
AWX returns output only after a job finishes. Ask again once the job's status is **successful** or **failed**.
</Accordion>

## Security

<ConnectionSecurity />

- **Read scope first**: use a Write token only when agents should launch or change things, and scope the user's roles to those templates.
- **HTTPS only**: always use an HTTPS **TOWER_HOST**. Plain HTTP sends the token in clear text.
