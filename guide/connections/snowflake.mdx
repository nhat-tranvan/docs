Connect Snowflake to let CloudThinker show which warehouses burn the most credits, rank slow and failing queries, and measure time travel and failsafe storage. CloudThinker calls the Snowflake SQL REST API with a **programmatic access token** (PAT) for a service user, and a new connection only reads until you turn on **Allow writes**.

---

## Prerequisites

- `ACCOUNTADMIN`, or an equivalent role, to create a role, a service user, a network policy, and a token.
- A warehouse the role can use. The connection test needs no compute, so it can pass while real analysis fails without one.

---

## Setup

<Steps>
  <Step title="Create a read-only role">
    Run as `ACCOUNTADMIN`. Replace `COMPUTE_WH` with the warehouse the agent should run on:
    ```sql
    USE ROLE ACCOUNTADMIN;

    CREATE ROLE IF NOT EXISTS CT_READONLY;
    GRANT DATABASE ROLE SNOWFLAKE.USAGE_VIEWER      TO ROLE CT_READONLY;
    GRANT DATABASE ROLE SNOWFLAKE.OBJECT_VIEWER     TO ROLE CT_READONLY;
    GRANT DATABASE ROLE SNOWFLAKE.GOVERNANCE_VIEWER TO ROLE CT_READONLY;
    GRANT MONITOR USAGE ON ACCOUNT                  TO ROLE CT_READONLY;
    GRANT USAGE ON WAREHOUSE COMPUTE_WH             TO ROLE CT_READONLY;
    ```
  </Step>
  <Step title="Create a service user">
    A `SERVICE` user has no password, MFA, or SSO, so the token is its only way in:
    ```sql
    CREATE USER IF NOT EXISTS SVC_CLOUDTHINKER
      TYPE = SERVICE
      DEFAULT_ROLE = CT_READONLY
      DEFAULT_WAREHOUSE = COMPUTE_WH
      COMMENT = 'CloudThinker connection';
    GRANT ROLE CT_READONLY TO USER SVC_CLOUDTHINKER;
    ```
  </Step>
  <Step title="Attach a network policy">
    Snowflake refuses token sign-in until the user has a network policy. Ask your CloudThinker contact for the current CloudThinker egress IP addresses and put them in `ALLOWED_IP_LIST`:
    ```sql
    CREATE NETWORK POLICY IF NOT EXISTS CT_POLICY ALLOWED_IP_LIST = ('<cloudthinker-egress-ip-1>', '<cloudthinker-egress-ip-2>');
    ALTER USER SVC_CLOUDTHINKER SET NETWORK_POLICY = CT_POLICY;
    ```
    On a throwaway test account only, `('0.0.0.0/0')` lets you try the connection before you have the list. Never leave it on a production account.
  </Step>
  <Step title="Create a programmatic access token">
    ```sql
    ALTER USER SVC_CLOUDTHINKER ADD PROGRAMMATIC ACCESS TOKEN CT_TOKEN
      ROLE_RESTRICTION = 'CT_READONLY'
      DAYS_TO_EXPIRY = 90;
    ```
    Copy the token now. Snowflake shows it only once, and it stops working on the expiry day. Set a calendar reminder a week before then to [rotate it](#rotate-the-token).
  </Step>
  <Step title="Add the connection in CloudThinker">
    Go to **Connections → Snowflake**, fill in the fields from [Connection details](#connection-details), and click **Connect**.

    **Success state:** Snowflake shows a **Connected** status, and the message names what the token resolved to, for example `Connected to MYORG-MYACCOUNT (AWS_US_WEST_2), role CT_READONLY, warehouse COMPUTE_WH`.
  </Step>
</Steps>

## Connection details

| Field | Required | Description | Default |
|-------|----------|-------------|---------|
| **Account identifier** | Yes | `MYORG-MYACCOUNT`, from **Snowsight → Account details**, or run `SELECT CURRENT_ORGANIZATION_NAME() \|\| '-' \|\| CURRENT_ACCOUNT_NAME();`. Not the full URL | |
| **Programmatic access token** | Yes | The token from Setup step 4. Not an account password | |
| **Role** | No | Role the connection uses. Must be inside the token's `ROLE_RESTRICTION` | User's default role |
| **Warehouse** | No | Warehouse billed for the credits this connection uses | User's default warehouse |

An identifier written with an underscore (`MYORG_MYACCOUNT`) also works.

---

## Required permissions

| Grant | What it unlocks |
|-------|-----------------|
| `SNOWFLAKE.USAGE_VIEWER` | Credit metering and storage history |
| `SNOWFLAKE.OBJECT_VIEWER` | Database, schema, and table inventory |
| `SNOWFLAKE.GOVERNANCE_VIEWER` | `QUERY_HISTORY`, which slow-query and error answers need |
| `MONITOR USAGE ON ACCOUNT` | Account-level usage views |
| `USAGE ON WAREHOUSE` | Compute to run the analysis queries |

<Tip>
`GOVERNANCE_VIEWER` is the grant people miss. Without it, credit and storage answers work but every slow-query and error answer fails. Keep the token's `ROLE_RESTRICTION` on this read-only role so the connection can't reach anything else.
</Tip>

## Agent capabilities

| Capability | Description |
|------------|-------------|
| **Account discovery** | Identity, warehouses, databases, and which `ACCOUNT_USAGE` views the role can read |
| **Credit analysis** | Metered credits per warehouse and per day, over a stated window (30 days by default) |
| **Query health** | Slowest queries, recurring error types, and queries that spill to remote storage |
| **Storage review** | Largest tables, time travel and failsafe overhead, and per-database growth |
| **Inventory** | Schemas, roles, and this connection's own grants |
| **Warehouse control** | With **Allow writes** on: suspend or resume one named warehouse |

CloudThinker reports Snowflake spend in credits, never in money. The price per credit isn't readable through this connection.

### Verify the connection

```text
List my Snowflake warehouses and which ACCOUNT_USAGE views this connection can read
```

**Success state:** CloudThinker lists your warehouses and marks each `ACCOUNT_USAGE` view as readable or blocked, with the `GRANT` that fixes a blocked one.

### Example prompts

```text
Which Snowflake warehouses burned the most credits in the last 30 days?
Show the slowest Snowflake queries this week and any errors that keep recurring
Where are time travel and failsafe adding the most storage?
```

## Write access

**Allow writes** is off on new Snowflake connections. With it on, each write goes through your [Rules](/guide/approvals/rules) and [Approval mode](/guide/approvals/approval-mode).

Write means exactly two actions, not arbitrary SQL:

- Suspend or resume one named warehouse.
- Keep measured findings in a `CT_FINDINGS` table. CloudThinker creates it in the one schema where the role has `CREATE TABLE`. If the role can write to several schemas, it asks you which one. You can also name it in your prompt, for example `MONITORING.ALERTS`.

Resizing a warehouse, changing a resource monitor, or lowering `DATA_RETENTION_TIME_IN_DAYS` is still handed to you as a statement to run in Snowsight.

**Allow writes** only lets CloudThinker ask. The role still needs the grants, and with a read-only token Snowflake denies every write. To turn writes on:

<Steps>
  <Step title="Create a write role and token">
    Replace `DEV_WH` with the warehouses the agent may suspend, and `MONITORING.ALERTS` with the schema for `CT_FINDINGS`. Grant `OPERATE` only on warehouses the agent may suspend, never a shared production warehouse:
    ```sql
    USE ROLE ACCOUNTADMIN;

    CREATE ROLE IF NOT EXISTS CT_READWRITE;
    GRANT DATABASE ROLE SNOWFLAKE.USAGE_VIEWER      TO ROLE CT_READWRITE;
    GRANT DATABASE ROLE SNOWFLAKE.OBJECT_VIEWER     TO ROLE CT_READWRITE;
    GRANT DATABASE ROLE SNOWFLAKE.GOVERNANCE_VIEWER TO ROLE CT_READWRITE;
    GRANT MONITOR USAGE ON ACCOUNT                  TO ROLE CT_READWRITE;
    GRANT USAGE ON WAREHOUSE COMPUTE_WH             TO ROLE CT_READWRITE;

    GRANT USAGE, OPERATE, MONITOR ON WAREHOUSE DEV_WH     TO ROLE CT_READWRITE;
    GRANT USAGE ON DATABASE MONITORING                    TO ROLE CT_READWRITE;
    GRANT USAGE, CREATE TABLE ON SCHEMA MONITORING.ALERTS TO ROLE CT_READWRITE;

    GRANT ROLE CT_READWRITE TO USER SVC_CLOUDTHINKER;
    ALTER USER SVC_CLOUDTHINKER ADD PROGRAMMATIC ACCESS TOKEN CT_TOKEN_RW
      ROLE_RESTRICTION = 'CT_READWRITE'
      DAYS_TO_EXPIRY = 90;
    ```
    Copy the new token.
  </Step>
  <Step title="Update the connection">
    Open **Connections**, select Snowflake, click the pencil icon on the account's row, and in **Edit Instance** click **Replace…**. Paste the new token into **Programmatic access token**, set **Role** to `CT_READWRITE`, and click **Save and test**.
  </Step>
  <Step title="Turn on Allow writes">
    On the same detail panel, turn on the **Allow writes** switch.
  </Step>
</Steps>

<Warning>
Two or more Snowflake connections in one workspace turn writes off for all of them, because an approved write can't name which account it targets. Also, a suspend can't be made conditional: a query can start between CloudThinker's busy check and the suspend and lose its compute.
</Warning>

## Rotate the token

<Steps>
  <Step title="Create the new token">
    Run Setup step 4 again with a new token name, such as `CT_TOKEN_2`. Keep the old token until the swap is done.
  </Step>
  <Step title="Replace it in CloudThinker">
    Open **Connections**, select Snowflake, click the pencil icon on the account's row, and in **Edit Instance** click **Replace…**. Paste the new token and click **Save and test**.

    **Success state:** the test passes and the connection stays **Connected**. If it fails, CloudThinker keeps the previous token.
  </Step>
  <Step title="Remove the old token">
    Run `ALTER USER SVC_CLOUDTHINKER REMOVE PROGRAMMATIC ACCESS TOKEN CT_TOKEN;`.
  </Step>
</Steps>

## Troubleshooting

<Accordion title="Authentication fails at once (390403)">
The service user has no network policy. Run `ALTER USER SVC_CLOUDTHINKER SET NETWORK_POLICY = CT_POLICY;`.
</Accordion>

<Accordion title="It worked yesterday and fails today (390318)">
The token expired or was revoked. Create a new one (Setup step 4) and [rotate it](#rotate-the-token) into the connection.
</Accordion>

<Accordion title="Object does not exist or not authorized (002003)">
The role is missing a database role. Run the verify prompt: CloudThinker lists every `ACCOUNT_USAGE` view it can't read and the exact `GRANT` for each.
</Accordion>

<Accordion title="Connected, but every query fails (090073)">
A resource monitor is over quota, or the warehouse is suspended and can't resume. No `GRANT` fixes this. An account admin raises or resets the resource monitor. The status stays **Connected** because the token is valid and the test needs no compute.
</Accordion>

<Accordion title="No active warehouse selected (000606)">
The service user has no `DEFAULT_WAREHOUSE` and the connection has none. Set **Warehouse**, or give the user a default.
</Accordion>

<Accordion title="Role not authorized (090105)">
The role is outside the token's `ROLE_RESTRICTION`. Use a role the token allows, or clear **Role** to use the user's default.
</Accordion>

<Accordion title="A section comes back empty">
Not an error. `ACCOUNT_USAGE` lags by up to a few hours and keeps 365 days of history, so a short window on a quiet account can return no rows.
</Accordion>

## Security

<ConnectionSecurity />

- **Dedicated service user**: a `TYPE = SERVICE` user has no password, MFA, or SSO, so the token is the only way in and its activity is easy to audit.
- **Restrict and expire the token**: `ROLE_RESTRICTION` caps what the connection can reach, and `DAYS_TO_EXPIRY` forces rotation.
