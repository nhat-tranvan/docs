Connect your HashiCorp Vault cluster to let CloudThinker agents check seal status and health, list what a secret path holds, audit policies, auth methods, and audit devices, and issue short-lived database or cloud credentials after you approve. Agents run the official `vault` CLI in CloudThinker's sandbox and sign in with a **token** or an **AppRole** (a role ID plus a secret ID that Vault exchanges for a short-lived token).

## Prerequisites

- A Vault address CloudThinker can reach over the network, such as a public DNS name or an HCP Vault Dedicated endpoint. `localhost` and private addresses resolve inside CloudThinker's sandbox, not on your network.
- Permission to write a policy and create a token or an AppRole.
- For Vault Enterprise or HCP Vault Dedicated: the namespace your secrets live in. HCP uses `admin` by default.

<Info>
A workspace holds one Vault connection. What agents can reach is exactly what the policy on your token or AppRole allows. Vault denies everything else by default.
</Info>

## Choose an auth method

| Method | Use it when | Trade-off |
|--------|-------------|-----------|
| **AppRole** | Production clusters | Rotate the secret ID without reissuing a token. Each session logs in and gets a fresh short-lived token |
| **Token** | Trials and dev clusters | Quickest to set up. The token lives until its TTL runs out, so you replace it on that schedule |

## Setup

<Steps>
  <Step title="Write a least-privilege policy">
    Start with read and list on the paths agents should see. Replace `secret` with your KV mount name and narrow the paths to what you need. This example assumes a KV v2 mount:

    ```bash
    vault policy write cloudthinker-read - <<EOF
    path "secret/data/*" {
      capabilities = ["read"]
    }
    path "secret/metadata/*" {
      capabilities = ["read", "list"]
    }
    path "sys/mounts" {
      capabilities = ["read"]
    }
    path "sys/auth" {
      capabilities = ["read"]
    }
    EOF
    ```

    See [Required permissions](#required-permissions) to add policy audits or dynamic credentials.
  </Step>
  <Step title="Create the credential">
    <Tabs>
      <Tab title="AppRole">
        Enable AppRole (skip if it's already on), bind a role to the policy, then fetch the role ID and a secret ID:

        ```bash
        vault auth enable approle

        vault write auth/approle/role/cloudthinker \
          token_policies=cloudthinker-read \
          token_ttl=1h \
          token_max_ttl=4h \
          secret_id_ttl=720h

        vault read auth/approle/role/cloudthinker/role-id
        vault write -f auth/approle/role/cloudthinker/secret-id
        ```

        Copy the `role_id` and the `secret_id` from the output.
      </Tab>
      <Tab title="Token">
        Create a token bound to the policy:

        ```bash
        vault token create \
          -policy=cloudthinker-read \
          -ttl=720h \
          -display-name=cloudthinker
        ```

        Copy the `token` value from the output.
      </Tab>
    </Tabs>
  </Step>
  <Step title="Add the connection in CloudThinker">
    Open **Connections** in the sidebar and select **HashiCorp Vault**. Enter **VAULT_ADDR**, set **VAULT_NAMESPACE** if you use Enterprise or HCP, pick **AppRole** or **Token** in **VAULT_AUTH_METHOD**, and fill in the credential fields that appear. Click **Connect**.

    **Success state:** the connection shows **Testing**, then **Connected**. For a token, CloudThinker runs `vault token lookup`. For AppRole, it logs in through `auth/approle/login` and checks that Vault returns a token.
  </Step>
</Steps>

## Connection details

| Field | Required | Description | Example |
|-------|----------|-------------|---------|
| **VAULT_ADDR** | Yes | Full Vault URL, including scheme and port | `https://vault.example.com:8200` |
| **VAULT_NAMESPACE** | No | Enterprise or HCP namespace. Leave blank for open-source Vault | `admin` |
| **VAULT_AUTH_METHOD** | Yes | **Token** (default) or **AppRole** | **AppRole** |
| **VAULT_TOKEN** | Token only | The token from `vault token create` | |
| **VAULT_ROLE_ID** | AppRole only | The AppRole `role_id` | |
| **VAULT_SECRET_ID** | AppRole only | The AppRole `secret_id` | |

## Required permissions

Grant only the rows you need. Each row adds paths to the policy from setup.

| You want agents to | Add to the policy |
|--------------------|-------------------|
| List keys and read metadata on KV v2 secrets | `read` on `<mount>/data/*`, `read` and `list` on `<mount>/metadata/*` |
| List secret engines and auth methods | `read` on `sys/mounts` and `sys/auth` |
| Audit policies | `read` and `list` on `sys/policies/acl` and `sys/policies/acl/*` |
| List audit devices | `read` and `sudo` on `sys/audit` |
| Issue dynamic credentials | `read` on `<engine>/creds/<role>`, such as `database/creds/readonly` |
| Revoke or renew leases | `update` on `sys/leases/revoke` and `sys/leases/renew` |
| Write or delete KV secrets | `create`, `update`, and `delete` on the matching `data/`, `delete/`, or `destroy/` paths |

The health check (`sys/health`) and `vault token lookup` on the caller's own token work under Vault's built-in `default` policy, so you don't need to add them.

<Tip>
Start read-only. Add the write rows only when you have a workflow that needs them. Even then, every write waits for approval in CloudThinker.
</Tip>

## Agent capabilities

| Capability | What agents can do | Approval |
|------------|--------------------|----------|
| **Health** | Check seal status, version, mounted secret engines, and auth methods | No |
| **Secret discovery** | List paths and the keys a secret holds, and tell KV v1 from KV v2 | No |
| **Policy audit** | Read the current token's policies and TTL, list and read policies, list audit devices and AppRole roles | No |
| **Dynamic credentials** | Issue short-lived database or cloud credentials from a secrets engine | Yes |
| **Lease management** | Revoke or renew a credential lease | Yes |
| **Secret and config changes** | Write, delete, or destroy KV versions, write policies, enable or disable mounts, auth methods, and audit devices | Yes |

Agents report keys and metadata, not secret values, and never print your token or secret ID. Issuing a dynamic credential looks like a read in Vault, but it creates a lease, so CloudThinker treats it as a write. Writes go through [Approvals](/guide/approvals/overview) before they run.

### Verify the connection

```text
Check Vault health and seal status, and list the mounted secret engines and auth methods
```

Expect the seal status, the Vault version, and a list of mounts such as `secret/` (KV v2) and auth methods such as `approle/`.

### Example prompts

```text
Which keys does secret/myapp/config hold, and when was it last updated?
What policies and TTL does the current Vault token have?
Issue a database credential from the readonly role and tell me when the lease expires
```

## Troubleshooting

<Accordion title="Connection fails with &quot;no such host&quot; or connection refused">
**VAULT_ADDR** points at an address CloudThinker can't reach. `localhost`, `127.0.0.1`, and private hostnames resolve inside the sandbox. Use a public DNS name or your HCP endpoint. A Vault behind a firewall or VPN needs a reachable endpoint or allowlisted access first.
</Accordion>

<Accordion title="unsupported protocol scheme">
The address is missing its scheme. Use `https://vault.example.com:8200`, not `vault.example.com:8200`.
</Accordion>

<Accordion title="Invalid Vault token configuration, or Invalid Vault AppRole configuration">
A credential field for the selected auth method is empty. Fill in **VAULT_TOKEN** for **Token**, or both **VAULT_ROLE_ID** and **VAULT_SECRET_ID** for **AppRole**.
</Accordion>

<Accordion title="403 permission denied">
Vault returns 403 both when the policy doesn't cover a path and when the path doesn't exist, so a 403 never proves a secret is missing. Ask the agent which policies the token has, then add `read` or `list` on the path. For KV v2, reading `secret/myapp` needs the policy on `secret/data/myapp`.
</Accordion>

<Accordion title="&quot;no handler for route&quot; on HCP or Enterprise">
**VAULT_NAMESPACE** is empty or wrong. Set it to the namespace your secrets live in. HCP Vault Dedicated uses `admin` by default.
</Accordion>

<Accordion title="invalid secret_id">
The AppRole secret ID passed its `secret_id_ttl`. Generate a new one, paste it into **VAULT_SECRET_ID**, and connect again:

```bash
vault write -f auth/approle/role/cloudthinker/secret-id
```
</Accordion>

<Accordion title="Every request fails and health shows sealed: true">
The cluster is sealed, so no read or write can succeed. A Vault operator must unseal it with `vault operator unseal`.
</Accordion>

## Security

<ConnectionSecurity />

- **Prefer AppRole in production**: each session gets a token that expires in the TTL you set, and you rotate the secret ID without touching the role.
- **Keep secret values out of chat**: agents list keys by default. If you ask for a value, it appears in the conversation, so ask only when you need it.
- **Revoke leases you no longer need**: ask the agent to revoke a dynamic credential once the task is done, instead of waiting for it to expire.
