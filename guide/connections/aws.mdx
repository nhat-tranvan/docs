CloudThinker runs the AWS CLI against your account to answer questions about compute, storage, identity, cost, and monitoring. You connect with an IAM role that CloudThinker assumes for short-lived credentials (recommended), or with an IAM user's access keys.

## Prerequisites

- An AWS account where you can create IAM roles (or IAM users, for the access-key method).
- Access to [AWS CloudShell](https://console.aws.amazon.com/cloudshell/home) in that account. The setup script runs there, so you install nothing.
- For cost questions and [Optimize](/guide/cost-optimization/overview): Cost Explorer turned on in the account. AWS can take up to 24 hours to activate it on a new account.

## Setup

Open the connect dialog first: in the sidebar, click **More → Workspace settings → Connections**, select **Amazon Web Services**, and click **Connect**. Then follow the tab for the method you pick at the top of the dialog.

<Tabs>
  <Tab title="Role-Based (recommended)">
    The dialog generates an **External ID** (a secret that only your role's trust policy and CloudThinker know) and builds a setup script around it.

    <Steps>
      <Step title="Name the account">
        Fill in **Alias** (for example `production`) and **Description** (for example `Production AWS account, main workloads`). Agents read the description to pick the right account. **Default AWS region (optional)** is only a starting point: agents can use any region the role can reach.
      </Step>
      <Step title="Open CloudShell">
        Click **Open CloudShell** and sign in to the AWS account you want to connect.
      </Step>
      <Step title="Run the setup script">
        Click **Copy Script to Clipboard**, paste it into CloudShell, and press Enter. The script:

        1. Stops if a role named `CloudThinkerAccessRole` already exists.
        2. Creates `CloudThinkerAccessRole` with a trust policy that only CloudThinker can assume, and only with your External ID.
        3. Attaches the AWS managed `ReadOnlyAccess` policy.
        4. Prints the role's ARN.

        The end of the output looks like this:

        ```text
        ==========================================
          ✅ Setup Complete!
        ==========================================

        Copy this Role ARN and paste it in the connection form:

        arn:aws:iam::123456789012:role/CloudThinkerAccessRole
        ```
      </Step>
      <Step title="Paste the Role ARN and connect">
        Paste the ARN into **AWS Role ARN**. Leave **AWS External ID** as it is: it's filled in for you and must match the script. Click **Connect**.

        **Success state:** the status moves through **Connecting** and **Verifying**, and the account shows a **Connected** status.
      </Step>
    </Steps>

    Prefer to create the role yourself, for example in Terraform or CloudFormation? Expand **Manual steps** in the dialog. It shows the trust policy with your External ID and the CloudThinker principal filled in. The shape is:

    ```json
    {
      "Version": "2012-10-17",
      "Statement": [
        {
          "Effect": "Allow",
          "Principal": { "AWS": "<CloudThinker principal shown in the dialog>" },
          "Action": "sts:AssumeRole",
          "Condition": {
            "StringEquals": { "sts:ExternalId": "<your External ID>" }
          }
        }
      ]
    }
    ```
  </Tab>
  <Tab title="Access Keys">
    Use this only when your organization doesn't allow cross-account roles. Access keys are long-lived, so you have to rotate them yourself.

    <Steps>
      <Step title="Name the account">
        Select **Access Keys** at the top of the dialog. Fill in **Alias**, **Description**, and optionally **Default AWS region (optional)**.
      </Step>
      <Step title="Run the setup script in CloudShell">
        Click **Open CloudShell**, then **Copy Script to Clipboard**, and run it in CloudShell. It creates an IAM user named `CloudThinkerUser`, attaches `ReadOnlyAccess`, creates an access key, and prints `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`.
      </Step>
      <Step title="Enter the keys and connect">
        Paste both values into the **AWS_ACCESS_KEY_ID** and **AWS_SECRET_ACCESS_KEY** fields and click **Connect**. AWS shows the secret only once, so copy it before you close CloudShell.

        **Success state:** the account shows a **Connected** status.
      </Step>
    </Steps>
  </Tab>
</Tabs>

### Connect more accounts

Each AWS account is its own connection. Click **Connect** again on **Amazon Web Services**, give the account its own alias, and run the script from that dialog in the new account's CloudShell. Always copy the script from the dialog you're completing, so the trust policy carries the External ID that dialog shows.

## Connection details

| Field | Method | Description | Example |
|---|---|---|---|
| **Alias** | Both | Short name for this account. Blank picks one for you. | `production` |
| **Description** | Both | What the account is. Agents use it to choose between accounts. | `Production AWS account` |
| **Default AWS region (optional)** | Both | Starting region. Agents can use other regions the credential allows. | `us-east-1` |
| **AWS Role ARN** | Role-Based | ARN printed by the setup script | `arn:aws:iam::123456789012:role/CloudThinkerAccessRole` |
| **AWS External ID** | Role-Based | Generated by CloudThinker. Read-only, must match the trust policy. | Filled in for you |
| **AWS_ACCESS_KEY_ID** | Access Keys | The IAM user's access key ID | `AKIA...` |
| **AWS_SECRET_ACCESS_KEY** | Access Keys | The IAM user's secret key | Shown once by AWS |

After connecting, set **Environment** (**Production**, **Staging**, **Development**, or **Not set**) in **Edit Instance** so [approval rules](/guide/approvals/rules) can treat accounts differently. **Not set** counts as production.

## Required permissions

The setup scripts attach the AWS managed `ReadOnlyAccess` policy. It lets agents describe and list resources across services, read CloudWatch metrics, and read Cost Explorer. It can't create, change, or delete anything.

| You want | Grant |
|---|---|
| Inventory, health, and security questions | `ReadOnlyAccess` (what the script attaches) |
| Optimize cost data | Cost Explorer reads. The cost refresh needs `ce:GetCostAndUsage`. Commitment coverage uses the reservation and Savings Plans `ce:Get*` reads. All are in `ReadOnlyAccess`. |
| Agents to make specific changes | Add only those actions to the role, then see [Write access](#write-access) |

<Tip>
`ReadOnlyAccess` can read data as well as configuration, such as S3 objects. If that's broader than you want, swap it for a custom read policy. A missing permission only limits the feature that needs it. It never disconnects the account.
</Tip>

## Agent capabilities

| Area | What CloudThinker does |
|---|---|
| **Inventory** | Lists and describes compute, storage, networking, and managed services across regions |
| **Identity** | Reviews IAM roles, users, and policies for risky or unused access |
| **Cost** | Breaks down spend by service, account, and tag, and checks Reserved Instance and Savings Plans coverage. Feeds [Optimize](/guide/cost-optimization/overview). |
| **Monitoring** | Reads CloudWatch metrics and alarms to explain a spike or an outage |
| **Changes** | Runs AWS CLI writes only when **Allow writes** is on, the role permits them, and your approval settings allow them |

### Verify the connection

```text
Which AWS account ID and regions can you reach through my AWS connection?
```

The answer names your real 12-digit account ID.

### Example prompts

```text
Break down last month's AWS spend by service and flag anything that grew more than 20% from the month before
List IAM users and roles that haven't been used in 90 days
Find EC2 instances in us-east-1 with average CPU under 10% over the last two weeks
```

## Write access

**Allow writes** on the connection's detail panel controls whether agents may change anything in AWS. It's on by default for AWS, but the role the script creates is read-only, so AWS itself refuses every write until you grant more.

| IAM permissions | Allow writes | Result |
|---|---|---|
| `ReadOnlyAccess` only | On or off | Read-only. AWS rejects any change. |
| Extra write actions granted | Off | Read-only. CloudThinker refuses every change before it reaches AWS. |
| Extra write actions granted | On | Agents can propose changes. Your [Rules and Approval mode](/guide/approvals/overview) decide each one. |

## Troubleshooting

<Accordion title="The script says CloudThinkerAccessRole already exists">
**Cause:** an earlier setup in this account created the role, likely with a different External ID.

**Fix:** if no other CloudThinker connection uses that role, delete it (`aws iam delete-role --role-name CloudThinkerAccessRole`, after detaching its policies) and run the new script. Otherwise, use **Manual steps** to update the existing role's trust policy with the External ID shown in this dialog.
</Accordion>

<Accordion title="The test fails with AccessDenied on sts:AssumeRole">
**Cause:** the trust policy doesn't match what CloudThinker presents.

**Check:** the ARN you pasted is the one the script printed, and the trust policy's `sts:ExternalId` matches **AWS External ID** in the dialog exactly.

**Fix:** re-run the setup from a fresh dialog, or correct the trust policy and click **Retry**.
</Accordion>

<Accordion title="The connection shows Error and scheduled work stopped">
**Cause:** three background credential failures in a row (a deleted role, a broken trust policy, or a revoked key) switch the connection to **Error**. Optimize cost refreshes, scheduled automations, and Pulse polling pause for it, and workspace admins get one notification.

**Fix:** repair the role or key in AWS, then click **Retry** on the connection, or **Replace credentials** to enter new keys. Scheduled work resumes on its next cycle once the status is **Connected**.
</Accordion>

<Accordion title="Cost questions return no data">
**Check:** Cost Explorer is turned on in the AWS Billing console, and at least 24 hours have passed since you turned it on. For a member account in AWS Organizations, the management account may block member access to Cost Explorer.

**Fix:** turn on Cost Explorer, or connect the management account to see costs for the whole organization.
</Accordion>


## Security

<ConnectionSecurity />

- **Prefer the role.** CloudThinker assumes the role through AWS STS and gets short-lived credentials, so there's no long-lived secret to leak. The External ID stops anyone else from using your role through CloudThinker.
- **Audit with CloudTrail.** Every call agents make is an ordinary AWS API call. Filter CloudTrail by `CloudThinkerAccessRole` (or `CloudThinkerUser`) to see exactly what ran.
