Connect Secureframe so [CloudThinker](/guide/agents/overview) can show framework progress, explain failing and at-risk tests, and find people, devices, policies, and vendors that need attention. The connection uses a Secureframe **API key and secret** and only reads.

## Prerequisites

- A Secureframe user with the **Super Admin** access role. Only Super Admins can create API keys.
- Your Secureframe region: US (`app.secureframe.com`) or UK (`app-uk.secureframe.com`).
- The **Admin** role in your CloudThinker workspace. See [Roles](/guide/security/roles).

## Setup

<Steps>
  <Step title="Create the API key in Secureframe">
    In Secureframe, open your profile in the top right, then click **Company Settings**. Open the **API keys** tab and click **Create API Key**. Assign an **Owner**, such as a dedicated service user, add an **API Key Name** such as `cloudthinker`, then click **Generate Key**.

    Copy the key and the secret. Secureframe shows the secret only once. See [Secureframe's API key instructions](https://support.secureframe.com/en/articles/15111555-secureframe-developer-portal-api).
  </Step>
  <Step title="Connect in CloudThinker">
    Open **Settings → Workspace → Connections**, open the **Discover** tab, and select **Secureframe**. Click **Connect**, fill in the fields below, then click **Connect** in the dialog. CloudThinker reads your frameworks and counts failing tests.

    **Success state:** the connection shows a **Connected** status and a message such as `Connected to Secureframe (us); <count> frameworks, <count> failing tests.` CloudThinker then opens a chat that takes a read-only deep look at the connection ("Often takes about 15 min. You can leave the chat."). To run it again later, open the card's **More** menu and choose **Try in chat**.
  </Step>
</Steps>

## Connection details

| Field | Required | Description |
|---|---|---|
| **API key** | Yes | The key from **Company Settings → API keys**. Create it for a dedicated service user with the least role that can read |
| **API secret** | Yes | The secret shown once when you create the API key |
| **Region** | Yes | **US (api.secureframe.com)**, the default, or **UK (api-uk.secureframe.com)**. Pick UK if you sign in at `app-uk.secureframe.com` |

## Required permissions

A Secureframe API key runs with the permissions of the user it belongs to, and Secureframe has no read-only key. If the owner's role can change tests or another area, the key can too.

| Owner access | Used for |
|---|---|
| Read frameworks and tests | Framework progress, failing and at-risk tests, and the connection check |
| Read integrations | Integrations that are disconnected |
| Read personnel, devices, and policies | Onboarding, device checks, and policy acceptance |
| Read vendors and tasks | High-risk vendors and overdue tasks |

<Tip>
Make the key's owner a dedicated service user with a custom role that can only read. CloudThinker never writes, but a read-only role keeps the key harmless if it leaks.
</Tip>

## Agent capabilities

| Capability | What agents can read |
|---|---|
| **Framework progress** | Each framework's passing, failing, and at-risk tests, and its percent passing |
| **Failing tests** | Failing or at-risk tests, when each first failed, the failure message, the recommended fix, the owner, and the controls and frameworks it maps to |
| **Integrations** | Integrations by status, so agents can flag ones that stop tests from running |
| **Personnel readiness** | People behind on onboarding, devices that fail checks such as disk encryption, and published policies without full acceptance |
| **Vendors and tasks** | High-risk vendors and overdue tasks |

Secureframe doesn't expose the resources behind a failing test, so agents give its failure message and remediation instead. A section that failed is unavailable data, not an empty list.

Agents can't enable, disable, or pass a test, reassign one, upload evidence, or archive anything. Make those changes in Secureframe.

### Verify the connection

```text
Summarize my Secureframe account: progress per framework, the oldest failing tests, and integrations that are disconnected.
```

### Example prompts

```text
Which Secureframe tests are failing for SOC 2, and how do I fix the oldest one?
Who has unfinished onboarding tasks, and which devices fail a security check?
Which published policies still lack acceptance from everyone in scope?
```

## Troubleshooting

<Accordion title="Secureframe rejected the API key and secret. Check both, and the region of your tenant.">
Check that you copied both values whole and that **Region** matches the address you sign in at. If you lost the secret, generate a new key.
</Accordion>

<Accordion title="The API key's user cannot read frameworks. Give the service user a role that can read.">
The key's owner can't read frameworks. Give that user a role with read access, then connect again.
</Accordion>

<Accordion title="The API key's user cannot read tests. Give the service user a role that can read.">
The owner can read frameworks but not tests. Widen the role's read access, then connect again. During an investigation, HTTP 403 on another area means the role can't read that area.
</Accordion>

<Accordion title="Secureframe rate-limited the credential. Try again in a minute.">
Secureframe limited the number of requests. Wait a minute, then ask about one area at a time.
</Accordion>

<Accordion title="Could not reach the Secureframe API over HTTPS. Check the network path.">
CloudThinker couldn't reach Secureframe for your region. Check **Region**, then connect again.
</Accordion>

## Security

<ConnectionSecurity />

- The key can do whatever its owner's role allows, so give the owner a read-only role, not a Super Admin account.
- Revoke the key in **Company Settings → API keys** when you disconnect, and create a new one if the secret is exposed.
