Connect Buildkite so CloudThinker agents can measure pipeline health, find why a build failed from its logs and annotations, and check agent capacity. The connection uses a Buildkite API access token, and the scopes you grant it are the hard limit on what agents can do.

## Prerequisites

- A Buildkite account with access to the organization you want agents to monitor.
- Permission to create an API access token for that organization.

## Setup

<Steps>
  <Step title="Create an API access token">
    In Buildkite, go to **Personal Settings → API Access Tokens → New API Access Token** ([buildkite.com/user/api-access-tokens/new](https://buildkite.com/user/api-access-tokens/new)) and set:
    - **Description**: `cloudthinker`
    - **Organization access**: the organization CloudThinker should reach
    - **REST API scopes**: the read scopes in [Required permissions](#required-permissions). Add `write_builds` only if you want agents to retry, unblock, rebuild, or cancel.

    Copy the token right away. Buildkite shows it only once.
  </Step>
  <Step title="Add the connection">
    In CloudThinker, go to **Connections**, find **Buildkite**, and click **Connect**. Paste the token into **BUILDKITE_API_TOKEN** and click **Connect**.

    **Success state:** the connection shows a **Connected** status.
  </Step>
  <Step title="Confirm the token works">
    Run the prompt in [Verify the connection](#verify-the-connection). Buildkite accepts the connection even with a bad token and only rejects it when an agent makes its first call, so a **Connected** status alone doesn't prove the token is valid.
  </Step>
</Steps>

## Connection details

| Field | Description |
|-------|-------------|
| **BUILDKITE_API_TOKEN** | Buildkite API access token. Its scopes decide which operations succeed |

There's no organization slug to enter. Agents resolve it from the token. CloudThinker sends the token to Buildkite's hosted MCP server at `https://mcp.buildkite.com/direct`, which passes it to the Buildkite REST API.

## Required permissions

| Scope | Enables |
|-------|---------|
| `read_organizations` | Resolving the organization the token can reach |
| `read_pipelines` | Pipeline inventory and details |
| `read_builds` | Builds, jobs, annotations, and failure summaries |
| `read_build_logs` | Reading, searching, and tailing job logs |
| `read_artifacts` | Build and job artifacts |
| `read_agents` | Agent connection state and capacity |
| `read_clusters` | Clusters and cluster queues |
| `read_user` | Looking up the token's own user |
| `write_builds` | Retry a job, unblock a job, rebuild, and cancel. Optional |

<Tip>
Leave `write_builds` off for a monitoring-only connection. Agents keep every read, and Buildkite itself refuses any change, so you aren't relying on approvals alone.
</Tip>

## Agent capabilities

| Capability | What agents can do |
|------------|--------------------|
| **Discovery** | List pipelines, recent builds, agents, and clusters in the organization |
| **Pipeline health** | Report pass rate, failure streak, and builds stuck longer than a threshold |
| **Failed-build triage** | Cross-reference Buildkite's failure summary with job logs, annotations, and failed tests |
| **Logs and artifacts** | Read, search, and tail a job's log; list and fetch build and job artifacts |
| **Capacity** | Show agent connection state, clusters, and cluster queues |
| **Build controls** | Retry a job, unblock a job, rebuild a build, cancel a build. **Each asks for approval** |

A build waiting on a manual block step reports `passed` in the Buildkite API. Agents check for the gate, name the block step, and leave the build out of the pass rate, so a held deploy never shows up as a green pipeline. Before unblocking, the agent quotes the block step's label and the build's annotations so you know which gate you're releasing.

Agents can't create or edit pipelines, clusters, queues, or schedules, and they don't read job environment variables. Buildkite Test Engine data isn't available through this connection.

### Verify the connection

```text
List my Buildkite pipelines and show the latest build status for each
```

Expect each pipeline by slug with its newest build state. A 401 here means the token is invalid even though the connection shows **Connected**.

### Example prompts

```text
Which Buildkite pipelines are failing right now, and how long is each failure streak?
Build 42 of the web pipeline failed. Pull the logs and annotations and tell me the cause
Show Buildkite agent capacity and any builds stuck for more than an hour
```

## Troubleshooting

<Accordion title="Connected, but every request returns 401">
The token is invalid, expired, or revoked. Create a new API access token and update **BUILDKITE_API_TOKEN** on the connection.
</Accordion>

<Accordion title="403 on reads">
The token is missing a read scope. Check it against [Required permissions](#required-permissions) and edit the token's scopes in Buildkite. You don't need a new token.
</Accordion>

<Accordion title="Retry, unblock, rebuild, or cancel fails with a permission error">
The token doesn't have `write_builds`. Add the scope in Buildkite, or keep the connection read-only and run the action in Buildkite yourself.
</Accordion>

<Accordion title="The gate state shows as unknown">
The check for a manual block step failed, usually because of a rate limit. The agent treats the build as unfinished and leaves it out of the pass rate. Unknown never means ungated. Ask again in a minute.
</Accordion>

<Accordion title="404 on a pipeline that exists">
A pipeline name was used where Buildkite expects the slug. Ask the agent to list your pipelines and use the slug from that list.
</Accordion>

<Accordion title="429 rate limited">
The request covered too many pipelines or builds. Scope the question to one pipeline, or ask for fewer recent builds.
</Accordion>

## Security

<ConnectionSecurity />

- **Scope the token, not just the approval**: Buildkite enforces token scopes. A token without `write_builds` can't change CI state at all.
- **Treat unblock as a release**: a block step is usually a deploy gate someone added on purpose. Approve an unblock only after reading the label the agent quotes.
