Connect Backstage to let CloudThinker agents read your Software Catalog: which services exist, who owns them, what they depend on, and which entries are missing an owner, lifecycle, repository link, or docs link. The connection uses a **static external access token**, a fixed token you add to your Backstage configuration for one caller. The only change agents can make is to a catalog **location** (the URL of a YAML file Backstage ingests entities from), and each one goes through your workspace's Approvals.

## Prerequisites

- A Backstage instance CloudThinker can reach over `https`. For one behind a firewall, see [Reaching private services](/guide/connections/overview#reaching-private-services).
- Access to your Backstage app configuration and permission to restart Backstage.
- The **Admin** role in the CloudThinker workspace, which you need to add connections. See [Roles](/guide/security/roles).

<Info>
A workspace holds one Backstage connection. CloudThinker accepts an `http` address only on a [self-hosted deployment](/guide/deployment/overview).
</Info>

## Setup

<Steps>
  <Step title="Generate a token">
    The token can be any string without whitespace that is long enough not to be guessed. One way to make one:

    ```bash
    node -p 'require("crypto").randomBytes(24).toString("base64")'
    ```

    Keep it in a secret manager or an environment variable, and use it only for CloudThinker so you can revoke it on its own.
  </Step>
  <Step title="Add it to your Backstage configuration">
    Add a `static` entry under `backend.auth.externalAccess`, restricted to the catalog plugin:

    ```yaml
    backend:
      auth:
        externalAccess:
          - type: static
            options:
              token: ${CLOUDTHINKER_TOKEN}
              subject: cloudthinker
            accessRestrictions:
              - plugin: catalog
    ```

    Set `CLOUDTHINKER_TOKEN` in the Backstage backend's environment, for example from a Kubernetes secret, before you restart.

    `subject` names the caller in Backstage's logs. `plugin: catalog` rejects calls to any other plugin. Without `accessRestrictions`, the token reaches every plugin you run. See [Backstage's service-to-service auth guide](https://backstage.io/docs/auth/service-to-service-auth) for the full options.
  </Step>
  <Step title="Restart Backstage">
    Backstage reads external access tokens at startup, so the token works only after a restart. Then test the token and find the URL to enter:

    ```bash
    curl -H "Authorization: Bearer $CLOUDTHINKER_TOKEN" \
      "https://backstage.example.com/api/catalog/entities/by-query?limit=1"
    ```

    If the frontend and backend run on different hosts or ports, such as `:7007`, try the backend address. The address that returns JSON, without `/api/...`, is your **Backstage URL**.
  </Step>
  <Step title="Add the connection in CloudThinker">
    Open **More → Workspace settings → Connections**, select **Backstage**, and enter:
    - **Backstage URL**: the backend root, such as `https://backstage.example.com`
    - **Service token**: the token you generated

    Click **Connect**.

    **Success state:** the connection shows **Connecting** and **Verifying**, then **Connected**. CloudThinker reads one catalog entity to prove the URL and token work.
  </Step>
</Steps>

<Note>
Enter the root only. Don't add `/api/catalog`, any other path, a query string, a fragment, or credentials. CloudThinker adds the catalog path itself and rejects a URL that carries anything else. It also doesn't follow redirects, so use the address Backstage answers on directly.
</Note>

## Connection details

| Field | Description | Example |
|-------|-------------|---------|
| **Backstage URL** | Backstage backend root over `https`, with no path, query, fragment, or credentials | `https://backstage.example.com` |
| **Service token** | The static external access token from your Backstage configuration, on one line | |

## Required permissions

With `plugin: catalog`, the token can read the whole catalog and also register and remove locations. On a default Backstage instance, only CloudThinker's approval stops those writes, unless you turn on Backstage's permissions framework.

| Restriction on the token | Effect |
|--------------------------|--------|
| **`plugin: catalog`** | Reaches the Software Catalog only. Set this |
| **No restrictions** | Reaches every plugin in your Backstage instance. Avoid this |

Agents need catalog read access for everything except location changes. Registering, updating, or removing a location also needs catalog create, update, and delete access on locations.

<Warning>
Backstage's `permission` and `permissionAttribute` restrictions work only when the permissions framework is on, and it's off by default. Until then, the `plugin` restriction is the only limit Backstage itself enforces.
</Warning>

## Agent capabilities

| Capability | What agents can do | Approval |
|------------|--------------------|----------|
| **Catalog overview** | Summarize entities by kind, type, owner, namespace, system, and domain. Reads 15 entities by default, 50 at most | No |
| **Metadata gaps** | Count entities missing an owner, lifecycle, source repository link, or documentation link, within the same 15 to 50 entities | No |
| **Service context** | For one named entity: owner, lifecycle, system, domain, source repository, docs, APIs, dependencies, and relations | No |
| **Location lookup** | Read one registered catalog location by ID | No |
| **Location changes** | Register a location, point an existing one at a new target, or remove one | Yes |

Answers are bounded, so agents say "returned 15" rather than "15 exist". For a large catalog, ask about one named entity, which reads that entity's full context. A missing owner means nobody filled in that field in Backstage, not that the service has no owner, and agents report it that way.

### Verify the connection

```text
Summarize our Backstage catalog: which kinds of entities it has and who owns them
```

Expect a breakdown by kind and owner, a count of entries missing key metadata, and a note on how many entities the answer covers.

### Example prompts

```text
Which components in Backstage have no owner set?
What are the owner, system, and dependencies of the payments-api component?
Which Backstage entries are missing a documentation link, and which should we fix first?
```

## Location changes

Agents can't create, edit, or delete catalog entities. Entities come from the locations Backstage ingests, so you edit them at the source. The one write this connection makes is to a location, and each one goes through [Approvals](/guide/approvals/overview).

<ApprovalDefault />

To be asked about every location change, choose **Manual**, or turn off **Allow writes** on the connection's detail panel to block them outright. Once CloudThinker turns on [Rule enforcement](/guide/approvals/rules#troubleshooting) for your workspace, an **Ask first** [Rule](/guide/approvals/rules) can cover the Backstage connection on its own.

Before it requests approval, the agent states the action, the location ID or target URL, and the URL prefix it treats as yours, such as `https://github.com/acme/catalog/`. There's no setting for this prefix: the agent takes it from your request, so name it in your prompt and check it in the approval. Two rules limit what an approval can do:

- The new target must be an `https` URL under the approved prefix. Anything else is refused before a request is sent.
- Updating or removing a location first reads its current target and checks it's under the same prefix, so an approval can't touch another team's location.

<Warning>
Removing a location removes the entities it produced from your catalog. Read the target in the request before you approve.
</Warning>

## Troubleshooting

<Accordion title="Failed to connect to Backstage">
CloudThinker shows this one message for every connection failure. Check in this order:
- The URL is the backend root and doesn't redirect.
- The token is in `backend.auth.externalAccess`, matches exactly, and Backstage was restarted after you added it.
- `accessRestrictions` includes `plugin: catalog`.
- Backstage is reachable from CloudThinker.
</Accordion>

<Accordion title="Invalid Backstage URL, or Invalid Backstage connection configuration">
The URL has a path, query, fragment, or credentials, or the token is empty or contains a line break. Enter the plain root and paste the token as one line with no quotes.
</Accordion>

<Accordion title="Backstage URL must use HTTPS outside local development">
The URL starts with `http://`. Despite the wording, `http` is also accepted on a [self-hosted deployment](/guide/deployment/overview) of CloudThinker. On CloudThinker Cloud, serve Backstage over `https`.
</Accordion>

<Accordion title="The agent reports fewer entities than Backstage shows">
An overview reads at most 50 entities. Ask about one named entity instead of the whole catalog.
</Accordion>

<Accordion title="An agent says it can't edit a catalog entity">
That's expected, and no permission changes it. Edit the entity's YAML at its source. An agent can register, repoint, or remove the location for you, through your Approvals.
</Accordion>

<Accordion title="Updating a location fails">
Your Backstage release can't update a catalog location in place. Ask the agent to remove the location and register the new target instead.
</Accordion>

## Security

<ConnectionSecurity />

- **Restrict the token to the catalog**: one `plugin: catalog` line keeps it from reaching every other plugin you run.
- **Rotate by replacing the entry**: a static token never expires on its own. Replace it in your Backstage configuration and restart. A workspace holds one Backstage connection, so there's no pencil icon to edit it. Open **More → Workspace settings → Connections**, select **Backstage**, click **Disconnect**, then connect again with the new **Service token**. Discovery runs again and **Allow writes** goes back to on. See [Rotate a credential](/guide/connections/overview#rotate-a-credential).
