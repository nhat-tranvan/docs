Connect Backlog by Nulab so [CloudThinker](/guide/agents/overview) can read your projects, issues, milestones, wikis, and pull requests, and create or update them when you ask. Backlog authenticates with an API key, and the key has the same project access as the Backlog user who issued it.

## Prerequisites

- A Backlog user who belongs to every project you want CloudThinker to read.
- API access turned on for your space. If your space restricts it, a space administrator must enable it first.
- Write permission on a project for that user, only if you want agents to create or update issues, wiki pages, or pull requests there.

## Setup

<Steps>
  <Step title="Create an API key in Backlog">
    In Backlog, open your profile menu and go to **Personal Settings → API**. Enter a memo such as `cloudthinker`, register the key, and copy it.

    Issue the key from the user whose access you want CloudThinker to have. Anyone holding the key acts as that user.
  </Step>
  <Step title="Open Backlog in CloudThinker">
    In the sidebar, click **More → Workspace settings → Connections**. On the **Builtin Connections** tab, search for **Backlog** and click **Connect**.
  </Step>
  <Step title="Enter the domain and key">
    Fill in **BACKLOG_DOMAIN** with your full space host, such as `myorg.backlog.com` or `myorg.backlog.jp`. Paste the key into **BACKLOG_API_KEY**, then click **Connect**.

    **Success state:** CloudThinker tests the key and Backlog shows a **Connected** status.
  </Step>
</Steps>

## Connection details

| Field | What to enter | Example |
|---|---|---|
| **BACKLOG_DOMAIN** | The full host of your Backlog space, not only the space key | `myorg.backlog.com` |
| **BACKLOG_API_KEY** | The API key from **Personal Settings → API** | (secret) |

## Required permissions

Backlog has no per-key scopes. The key can do whatever its user can do in Backlog.

| To let agents | The key's user needs |
|---|---|
| Read projects, issues, milestones, wikis, documents, repositories, and pull requests | Membership in those projects |
| Create or update issues, comments, milestones, wiki pages, or pull requests | Write permission on the project |

Reads run without asking. Writes go through [Approvals](/guide/approvals/overview): your Approval mode and rules decide whether CloudThinker asks you first or refuses. CloudThinker only proposes a write when you name the item and the change in the conversation.

<Tip>
Issue the key from a dedicated Backlog user that belongs only to the projects CloudThinker needs. Give it write permission only on projects where you want agents to file or update tickets.
</Tip>

## Agent capabilities

| Capability | What CloudThinker does |
|---|---|
| **Space discovery** | Lists your space, the connected user, projects with their keys, priorities, and resolutions |
| **Issue tracking** | Searches, reads, and counts issues; creates and updates issues and adds comments after approval |
| **Milestones** | Lists milestones and what each holds; creates or updates them after approval |
| **Wikis and documents** | Reads project wikis and documents; creates or updates wiki pages after approval |
| **Git and pull requests** | Reads repositories and pull requests in a project |
| **Ticket context in Review** | Pulls the Backlog issue a merge or pull request references (for example `PROJ-123`) into [Review](/guide/code-review/overview) |
| **Follow-up tickets in Resolve** | Files and updates follow-up tickets after an incident, once you turn on the outcome in [Resolve integrations](/guide/incident/integrations) |

### Verify the connection

```text
List my Backlog projects with their keys, then show the five most recently updated open issues in one of them
```

You should get project names with keys like `PLATFORM`, and issue keys like `PLATFORM-42` that you can open in Backlog.

### Example prompts

```text
Summarize the open issues in the PLATFORM project and flag anything past its due date
What does the 2.4 milestone in PLATFORM still have open, grouped by assignee?
Add a comment to PLATFORM-118 saying the fix is deployed to staging
```

The third prompt is a write, so CloudThinker shows the comment and waits for approval before posting it.

## Troubleshooting

<Accordion title="The connection test fails with 401 Unauthorized">
The key is wrong, was deleted, or API access is off for the space. Create a new key under **Personal Settings → API**, confirm with a space administrator that API access is allowed, then update **BACKLOG_API_KEY** on the connection.
</Accordion>

<Accordion title="Requests return 404 or reach the wrong space">
**BACKLOG_DOMAIN** holds only the space key (`myorg`) or the wrong region. Enter the full host exactly as it appears in your browser, such as `myorg.backlog.com` or `myorg.backlog.jp`, and reconnect.
</Accordion>

<Accordion title="The connection works but projects or issues are missing">
The key's user isn't a member of those projects. Add the user to the project in Backlog, then ask CloudThinker to list your projects again.
</Accordion>

<Accordion title="Creating or updating an issue fails with a permission error">
The key's user can read the project but can't write to it. Give that user write permission on the project, or reissue the key from a user who has it, then approve the action again.
</Accordion>

<Accordion title="Results stop partway on a large project">
CloudThinker caps very large Backlog responses so replies stay readable. Narrow the request to one project, milestone, status, or assignee, or ask for a count first and then drill in.
</Accordion>

## Security

<ConnectionSecurity />

- **The key is the user.** It carries every permission of the Backlog user who issued it, so issue it from a dedicated, least-privilege user and delete it in Backlog when you remove the connection.
- **Approval-gated writes.** Keep issue, wiki, and milestone changes behind your [Approval rules](/guide/approvals/rules) rather than giving the key broad write access.
