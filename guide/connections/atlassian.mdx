Connect your Atlassian Cloud site to let CloudThinker agents search Jira issues and Confluence pages, read the ticket behind a code change, and create or update issues and pages through your approvals. One connection covers both Jira and Confluence: it signs in with **OAuth** through the Atlassian MCP server (formerly Rovo MCP Server) and acts with the permissions of the person who authorizes it.

## Prerequisites

- A CloudThinker workspace on the **Scale** plan or above. On lower plans the button reads **Upgrade to Connect**.
- An Atlassian Cloud site with Jira, Confluence, or both.
- An Atlassian **organization admin** for the one-time domain step, if your organization hasn't done it yet.
- The **Atlassian MCP server** (formerly Rovo MCP Server) available on your organization. If **Connectors → Atlassian MCP server** doesn't appear in Atlassian Administration, sort that out with Atlassian first.
- Permission to manage connections in your CloudThinker workspace.

<Info>
This connection doesn't reach Jira Service Management alerts or on-call schedules. Atlassian only exposes those through an API token, so they have their own [Jira Service Management](/guide/connections/jsm) connection.
</Info>

## Setup

<Steps>
  <Step title="Allow the CloudThinker domain in Atlassian">
    An organization admin goes to [admin.atlassian.com](https://admin.atlassian.com), opens **Connectors → Atlassian MCP server**, and clicks **Add domain**. Enter:

    ```text
    https://app.cloudthinker.io/**
    ```

    Type it exactly. The `/**` wildcard allows every CloudThinker callback path under that domain.

    <Frame>
      <img src="/images/atlassian-integration.png" alt="Atlassian Administration, Rovo MCP Server page, with https://app.cloudthinker.io/** listed under Your domains" />
    </Frame>

    **Success state:** the domain appears in the list of allowed domains. You only do this once per Atlassian organization.
  </Step>
  <Step title="Start the connection in CloudThinker">
    In the sidebar, click **More → Workspace settings → Connections**, stay on the **Builtin Connections** tab, select **Atlassian**, and click **Connect**. Atlassian opens in a new window. If your browser blocks it, a dialog appears instead: click **Open Atlassian**.
  </Step>
  <Step title="Authorize access">
    Sign in with the Atlassian account agents should act as, pick the site, and approve access. The window closes on its own.

    **Success state:** Atlassian shows a **Connected** status in CloudThinker.
  </Step>
</Steps>

## Connection details

There are no fields to fill in. Atlassian issues the OAuth tokens and CloudThinker stores them.

| Item | Value |
|------|-------|
| **Sign-in** | OAuth with the Atlassian account that authorizes |
| **Allowed domain** (Atlassian side) | `https://app.cloudthinker.io/**` |
| **Products reached** | Jira and Confluence on the site or sites you approve during authorization |

A workspace holds one Atlassian connection. To switch accounts, disconnect it and connect again with the other account.

## Required permissions

- **Organization admin**, once, to add the CloudThinker domain.
- After that, agents see and change only what the **authorizing account** can in Jira and Confluence. If that person can't open a project or space, neither can the agent.

<Tip>
Authorize from a dedicated Atlassian account that belongs only to the projects and spaces agents need. Connecting with a personal account ties the connection to that person's access and job. The dedicated account needs Jira and Confluence product access, so it counts as a user on your Atlassian plan.
</Tip>

## Agent capabilities

| Capability | What agents can do | Approval |
|------------|--------------------|----------|
| **Jira search** | Find issues with JQL or plain language, read issue details, comments, and links | No |
| **Jira projects** | List visible projects and their issue types | No |
| **Confluence search** | Search and read pages and spaces | No |
| **Jira updates** | Create, edit, transition, or comment on an issue | Yes |
| **Confluence updates** | Create or update a page, or add a comment | Yes |

Changes go through [Approvals](/guide/approvals/overview). The Atlassian MCP server doesn't expose Jira automation rules, board settings, or Confluence space permissions, so agents can't review those.

Other parts of CloudThinker use the same connection:

| Where | What it does |
|-------|--------------|
| [Resolve integrations](/guide/incident/integrations) | **Create follow-up tickets** and **Keep tickets updated** in a Jira project (set the **Jira project key**, like `ENG`). **Publish postmortems** to a Confluence space (set the **Confluence space key**, like `OPS`). |
| [Runbooks](/guide/incident/runbooks) | Reads fix procedures from a Confluence space during root cause analysis. |
| [Review extensions](/guide/code-review/extensions) | The **Jira / Confluence** extension reads the ticket or spec page linked in a pull request description and checks the change against it. |

### Verify the connection

```text
List the Jira projects the connected account can see, and the five most recently updated issues in the first three
```

Expect your projects by key with a few recent issues. If a project is missing, the authorizing account can't open it. In prompts, "me" and "I" mean that account, not the person chatting.

### Example prompts

```text
Find open Jira bugs in the PAY project labeled production, grouped by assignee
Search Confluence for our database failover runbook and summarize the steps
Create a Jira task in OPS to rotate the expiring TLS certificate on api.example.com
```

The last prompt creates an issue, which counts as a change in Jira.

## Troubleshooting

<Accordion title="The button says Upgrade to Connect">
Your CloudThinker plan doesn't include the Atlassian connection. It needs the Scale plan or above. See [Pricing](/guide/billing/pricing).
</Accordion>

<Accordion title="Atlassian refuses the authorization">
The CloudThinker domain isn't allowed in your organization. Ask an organization admin to check **Connectors → Atlassian MCP server** and confirm `https://app.cloudthinker.io/**` is in the list of allowed domains, then click **Connect** again.
</Accordion>

<Accordion title="Permission errors even though the domain is allowed">
Your organization enforces an IP allowlist. Those rules are managed in Atlassian Administration, separate from the MCP server settings, and apply to these requests too. Have your admin add CloudThinker's egress IP addresses to that allowlist. These docs don't publish CloudThinker's egress IP list: ask your CloudThinker contact, or [contact us](https://cloudthinker.io/contact).
</Accordion>

<Accordion title="It worked before, now requests fail with 401">
The OAuth grant expired or was revoked, or the authorizing account was deactivated, for example when that person left. Reconnect Atlassian from **More → Workspace settings → Connections**, ideally with a dedicated account. The account owner can also revoke the grant in their Atlassian profile under **Connected apps**.
</Accordion>

<Accordion title="A project or space is missing">
Agents act as the authorizing account. Give that account access to the project or space in Atlassian, then ask again. No reconnect is needed.
</Accordion>

<Accordion title="Agents can't see JSM alerts or who's on call">
That's expected. Alerts and schedules need the separate [Jira Service Management](/guide/connections/jsm) connection.
</Accordion>

## Security

<ConnectionSecurity />

- **User-bounded access**: every read and write runs as the authorizing account, so its Jira and Confluence permissions are the real limit.
- **Domain control stays with you**: an organization admin can remove the CloudThinker domain from the **Atlassian MCP server** page at any time to cut off access.
