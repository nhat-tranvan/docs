A Worker runs the agent on a machine you control — your laptop, a server, or a CI runner — instead of CloudThinker Cloud. You choose where each chat and each Automation runs, and the agent works in one folder you name.

<Note>
**Preview** — Workers ship with the [CloudThinker CLI](/guide/cli/overview), which is in early access. Command names and flags may change before general availability.
</Note>

## Why a Worker

- **Reach a private machine.** The agent edits files and runs commands where your code and tools already live, without exposing them to the cloud.
- **Keep credentials in the cloud.** A connection command runs in CloudThinker Cloud with its credential injected there. A credential never leaves the cloud onto a Worker.
- **Share one machine, or keep it personal.** A personal Worker is visible only to you. A shared Worker is visible to every authorized member of the workspace.
- **Route Automations too.** A scheduled Automation can run on a Worker every time it fires.
- **Fall back to nothing.** When a Worker is unavailable, the run reports the error. It does not silently move to the cloud.

## Choose where a chat runs

You pick where a chat runs in the composer, before the first message. After the first message, the choice is fixed for that conversation.

<Steps>
  <Step title="Open the + menu">
    Open the **+** menu beside the chat prompt box. The **Run in** row appears when there is a choice — a Worker, a Desktop folder, or a load retry.

    <Frame>
      <img src="/images/workers/01-plus-menu-run-in-row.png" alt="The + menu with a Run in row showing CloudThinker Cloud" />
    </Frame>
  </Step>
  <Step title="Select Run in">
    Select **Run in**, then choose **CloudThinker Cloud** or a Worker by name.

    **Success state:** a chip appears in the toolbar with the Worker's name. Its tooltip says what runs where.

    <Frame>
      <img src="/images/workers/02-worker-chip-tooltip.png" alt="The toolbar chip for a Worker, with a tooltip that explains what runs where" />
    </Frame>
  </Step>
  <Step title="Send the first message">
    Send your first message. The conversation is now bound to that Worker.

    **Success state:** the chip shows a lock and becomes read-only. A fork or a Room thread inherits where it runs.
  </Step>
</Steps>

When the only choice is CloudThinker Cloud, the **Run in** row does not appear, and the chat runs in the cloud.

## Set up a Worker

You register and run a Worker from the CLI. Install and log in first — see [CLI](/guide/cli/overview).

<Steps>
  <Step title="Register the Worker">
    ```bash
    cloudthinker worker outpost create "my-laptop" --shared
    ```

    Omit `--shared` for a personal Worker. List what the workspace has with `cloudthinker worker outpost ls`.
  </Step>
  <Step title="Serve one folder">
    ```bash
    cloudthinker worker start --outpost "my-laptop" --workdir ~/projects/app
    ```

    File tools are confined to `--workdir`. Shell commands run there, under your own OS account. The process serves work over outward HTTPS until you interrupt it.
  </Step>
  <Step title="Confirm it is available">
    ```bash
    cloudthinker worker status --outpost "my-laptop"
    ```

    **Success state:** the status reads available. Registration alone is not enough — the Worker first passes server-driven file, shell, cancel, and artifact checks before the workspace can select it.
  </Step>
</Steps>

To keep a Worker running across logins, install it as a service with `cloudthinker worker service install --outpost "my-laptop" --workdir ~/projects/app` on Linux (`systemd --user`) or macOS (`launchd`). Retire a Worker with `cloudthinker worker outpost archive "my-laptop"`.

## Workspace Connections

**Workspace Connections** is a switch on the Worker. It controls whether the run may use the connections saved in your workspace. It does not move the whole run to the cloud.

| Switch | A connection command | File tools and plain shell |
|--------|----------------------|----------------------------|
| **On** | Runs in CloudThinker Cloud, with the credential injected there | Run on the Worker |
| **Off** | Does not run; the agent is told the connection is unavailable | Run on the Worker |

CloudThinker Cloud always has the switch on. The first message fixes the switch together with the Worker, and later messages cannot change it. For an Automation, flipping the switch takes effect on the next run.

## What always runs in CloudThinker Cloud

A few workloads read state that only CloudThinker Cloud holds. In a Worker conversation, each one reports an error instead of running on the Worker:

- A [Cyber](/guide/security/cyber-overview) pentest run and its report download.
- A browser-driven session.
- Repository code-graph indexing.

## Automations

An [Automation](/guide/automation/automations) stores the same Worker and **Workspace Connections** switch. Open the Automation form, set **Run in**, then set the switch. Only a workspace admin can change where an Automation runs.

## FAQ

<AccordionGroup>
  <Accordion title="Can I change where a chat runs after the first message?">
    No. The first message fixes the Worker and the switch. Start a new conversation to run somewhere else.
  </Accordion>
  <Accordion title="Does a Worker see my connection credentials?">
    No. A connection command runs in CloudThinker Cloud with its credential injected there. The credential never reaches the Worker.
  </Accordion>
  <Accordion title="What happens when a Worker goes offline?">
    The run reports the error. It does not fall back to CloudThinker Cloud.
  </Accordion>
  <Accordion title="Who can see a Worker?">
    A personal Worker is visible only to you. A shared Worker is visible to authorized members of the workspace. Use `--shared` when you register it.
  </Accordion>
</AccordionGroup>
