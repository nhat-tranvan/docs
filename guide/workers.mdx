A Worker is a folder on a machine you run (a laptop, a server, or a CI runner) where CloudThinker can read files and run commands. You pick a Worker before a chat starts, and the agent works there instead of in CloudThinker Cloud, the hosted environment every chat uses by default.

<Note>
**Beta.** Workers ship with the [CloudThinker CLI](/guide/cli/overview), which is in early access. Command names and flags may change before general availability.
</Note>

## Why use a Worker

- **Work where your code lives.** The agent edits files and runs your own tools in a private repository or on an internal host, with no inbound port opened. The Worker connects outward over HTTPS.
- **Credentials stay in the cloud.** Commands that use a workspace connection, such as AWS or Kubernetes, still run in the CloudThinker managed sandbox. The credential never reaches your machine.
- **Your folder's rules apply.** The agent follows the instruction files and Skills you keep in the folder.
- **Personal or shared.** Only you can use a personal Worker. A shared Worker is available to everyone in the workspace, including Automations.

## Prerequisites

- The CloudThinker CLI installed on the machine, on Linux or macOS. See [CLI](/guide/cli/overview).
- A folder you want the agent to work in, such as a repository checkout.
- To create a shared Worker: workspace settings permission (workspace Admin). See [Roles](/guide/security/roles).
- **Allow Workers** turned on in workspace settings. It is on unless an admin turned it off.

## Set up a Worker

<Steps>
  <Step title="Open the Worker setup dialog">
    In a new chat, open the **+** menu beside the prompt box, select **Run in**, then select **New worker**. Admins can also go to **Admin Settings → Sandboxes** and select **Create worker** in the **Workers** section.
  </Step>
  <Step title="Name the Worker">
    Enter a **Worker name**, for example `payments-api`. Turn on **Share with workspace** if teammates and Automations should use it. Select **Create worker**.

    **Success state:** the dialog shows a command and the note "The link expires in 10 minutes."
  </Step>
  <Step title="Run the command in your project folder">
    Copy the command, open a terminal in the folder you want to serve, and run it. It looks like this:

    ```bash
    cloudthinker --url https://app.cloudthinker.io worker start --register <reference> --workdir "$PWD"
    ```

    The Worker stores its credential on this machine, then runs file, shell, cancel, and artifact upload checks. It keeps running in the foreground until you press Ctrl-C.

    **Success state:** the terminal prints `Waiting for work.` and the dialog shows **`<name>` is verified**. If the command expired, select **New command**.
  </Step>
  <Step title="Start a chat on the Worker">
    Select **Start a chat**. A new chat opens with the Worker selected.
  </Step>
</Steps>

You can do the same from a terminal. `cloudthinker worker outpost create payments-api --shared` registers a Worker (omit `--shared` for a personal one), and `cloudthinker worker start --outpost payments-api --workdir "$PWD"` serves the folder. The CLI calls a Worker an outpost.

## Choose where a chat runs

<Steps>
  <Step title="Pick the Worker">
    In a new chat, open the **+** menu and select **Run in**. Choose **CloudThinker Cloud** or a Worker by name.

    <Frame>
      <img src="/images/workers/01-plus-menu-run-in-row.png" alt="The + menu with a Run in row showing CloudThinker Cloud" />
    </Frame>

    **Success state:** a chip with the Worker's name appears in the toolbar. Its tooltip says what runs where.

    <Frame>
      <img src="/images/workers/02-worker-chip-tooltip.png" alt="The toolbar chip for a Worker, with a tooltip that explains what runs where" />
    </Frame>
  </Step>
  <Step title="Send the first message">
    Ask for something that uses the folder:

    ```text
    Run the test suite and fix the first failing test. Show me the diff before you commit.
    ```

    **Success state:** the chip locks. The conversation stays on that Worker for its whole life, including forks. To run somewhere else, start a new conversation.
  </Step>
</Steps>

The composer remembers your last choice for the workspace, so the next new chat starts on the same Worker.

If the folder is a git repository, you can turn on **New worktree** and pick a base branch. The Worker then works on a `cloudthinker/<id>` branch in a separate worktree, so your main checkout stays untouched. This needs git 2.38 or newer on the machine.

## What a Worker can reach

| The agent does this | Where it reaches |
|---|---|
| Reads, writes, edits, or lists files with a file tool | Only inside `--workdir`. Paths outside it, including `..`, are rejected. |
| Runs a shell command | The whole machine, as your OS account, using `/bin/bash`. `--workdir` is only the starting directory. |
| Uses a workspace connection (AWS, Kubernetes, and more) | The CloudThinker managed sandbox, with the credential injected there. |

<Warning>
Shell commands on a Worker are not sandboxed. They can read `~/.ssh`, write outside the folder, and reach your network. Run the Worker under an account whose access you accept, and use [Approvals](/guide/approvals/overview) to review shell actions on sensitive machines.
</Warning>

Shell commands get a reduced environment: `PATH`, `HOME`, `LANG`, `TERM`, `USER`, and `TMPDIR`. Pass one more variable by name with `--env NAME` (the value comes from the Worker's own environment; repeat for more), or pass everything with `--inherit-env`.

Every shell command, background task start or stop, and file write is recorded in **Admin Settings → Audit Logs** under the **Command** filter. The record keeps a redacted preview of the command, never its output. Reads are not recorded.

### The CloudThinker managed sandbox switch

The **CloudThinker managed sandbox** switch in the **Run in** menu decides whether the run can use your workspace connections. It doesn't move file or shell work off the Worker.

<Frame>
  <img src="/images/workers/03-workspace-connections-switch.png" alt="The Run in menu with the CloudThinker managed sandbox switch and its description" />
</Frame>

| Switch | Connection commands | File tools and shell |
|---|---|---|
| **On** | Run in the CloudThinker managed sandbox | Run on the Worker |
| **Off** | Don't run. CloudThinker tells you the connection is unavailable. | Run on the Worker |

The first message fixes the switch along with the Worker.

### What stays in CloudThinker Cloud

[Cyber](/guide/security/cyber-overview) runs and browser sessions need CloudThinker Cloud. In a Worker conversation they return an error, and nothing silently moves to the cloud. Start a new conversation in CloudThinker Cloud for those.

## Folder rules and Skills

On the first turn, the agent reads the instruction files at the root of the folder: `AGENTS.override.md`, `AGENTS.md`, `CLAUDE.md`, and `GEMINI.md`. It also lists the Skills in `.agents/skills/`. Each Skill is a folder with a `SKILL.md` whose frontmatter has a `description`, and the agent loads it when a task matches. Set `disable-model-invocation: true` to hide one. See [Skill format](/guide/skills/skill-format).

## Keep a Worker running

`worker start` stops when you close the terminal. To keep it up, add `--background` to the same command. That installs a per-user service (a systemd user unit on Linux, a LaunchAgent on macOS) and prints the status, logs, and stop commands.

| Command (prefix `cloudthinker worker`) | What it does |
|---|---|
| `service install --outpost <name> --workdir <path>` | Register the service without starting it. On Linux, add `--enable-linger` to keep it running after logout. |
| `service start` / `service stop` | Start it, or stop it after current work drains. |
| `service status --json` | Show its state, last exit code, and where the logs are. |
| `service uninstall` | Remove the service. The credential and Worker stay. |
| `status --outpost <name>` | Show availability and CLI version as the workspace sees it. |
| `doctor` | Check version, network, clock, credential, folder, and service. Prints one fix per problem. |
| `outpost ls` / `outpost archive <name>` | List Workers, or retire one after its open work finishes. |

Useful `worker start` flags: `--concurrency <1-32>` (default 4), `--label <name>` for the folder's display name, and `--health-addr 127.0.0.1:9464` for `/healthz` and Prometheus `/metrics` endpoints.

## Run an Automation on a Worker

In the [Automation](/guide/automation/automations) form, set **Run in** to a shared Worker. Automations can't use personal Workers, and only workspace admins can change where an Automation runs. A change to the managed sandbox switch applies from the next run.

## Troubleshooting

<AccordionGroup>
  <Accordion title="The dialog says Verification failed">
    One of the startup checks failed. Stop the Worker, run `cloudthinker worker doctor` in the folder, apply the fix it prints, then select **New command** and run it again. If it says **Your CLI is out of date**, run `cloudthinker update` first.
  </Accordion>
  <Accordion title="The Worker shows Offline">
    The process stopped or lost the network. Check that `worker start` or the service is still running with `cloudthinker worker status --outpost <name>`. The Worker reconnects on its own after sleep or a network change.
  </Accordion>
  <Accordion title="A shell command can't find a variable or tool">
    Only `PATH`, `HOME`, `LANG`, `TERM`, `USER`, and `TMPDIR` are passed by default. Restart the Worker with `--env NAME` for each variable, or `--inherit-env`.
  </Accordion>
  <Accordion title="The Worker exits with WORKDIR_IDENTITY_CHANGED">
    The folder was replaced, for example deleted and recloned. Run `worker start` once with the same `--outpost` and `--workdir` plus `--reset-folder`. Conversations that used the old folder stay unavailable.
  </Accordion>
  <Accordion title="The credential expired or was revoked (exit code 3)">
    A credential stays valid for 30 days after its last use and rotates on its own while the Worker runs. If it expires, enroll again with a new command from **Admin Settings → Sandboxes**, or **Run in → New worker**.
  </Accordion>
  <Accordion title="A teammate gets EXECUTOR_TARGET_PRIVATE">
    They tried to use your personal Worker. Create a shared Worker instead.
  </Accordion>
</AccordionGroup>
