Every skill is a `SKILL.md` file: a short YAML header (frontmatter) that names the skill and says when to use it, followed by Markdown instructions. This page covers the rules a file must pass to load and the writing patterns that make agents follow it.

## Minimal valid skill

Copy this, change the name, description, and rules, and it will load:

```markdown
---
name: security-review-checklist
description: Enforce our SQL and secrets rules when reviewing code. Use for any pull request review or security question about code.
---

## SQL injection

- Flag SQL built with string concatenation or f-strings.
- Require parameterized queries or ORM methods.

## Secrets

- Flag hardcoded credentials, tokens, and API keys.
- Require secrets to come from a secrets manager or environment variables.
```

| Part | Required | Purpose |
|---|---|---|
| Frontmatter (between the `---` lines) | Yes | Holds `name` and `description`. It must be valid YAML. |
| Instruction body | Yes | The Markdown rules the agent reads when it uses the skill. |
| One `##` heading per rule group | Recommended | Keeps rules easy to scan for you and the agent. |
| Good and bad examples | Recommended | Anchors each rule to something concrete. |

## Frontmatter fields

| Field | Required | Rules |
|---|---|---|
| `name` | Yes | Starts with a letter or digit, then letters, digits, `_`, or `-`. Uppercase letters are allowed. No spaces. Up to 255 characters. Must not match a skill CloudThinker ships in the [Skills Hub](https://www.cloudthinker.io/skills). |
| `description` | Yes | A non-empty sentence saying what the skill does and when to use it. Agents read descriptions to decide which skill fits a task, so a vague one means the skill rarely gets picked. Quote it if it contains a colon: `description: "Use when: reviewing PRs"`. Up to 2,000 characters. |
| `argument-hint` | No | Text shown next to the skill in the chat `/` menu, such as `<service-name>`, to tell people what to type after the command. It doesn't change behavior. Whatever people type after `/skill-name` reaches the agent as part of their message. |

Name examples:

| Name | Valid? |
|---|---|
| `security-checklist` | Yes |
| `security_checklist` | Yes |
| `Security-Checklist` | Yes |
| `Security Checklist` | No (space) |
| `-checklist` | No (must start with a letter or digit) |

<Note>
When you create a skill with **Write skill instructions**, CloudThinker builds the frontmatter from the **Skill name** and **Description** fields for you. You only write the frontmatter yourself when you upload a `.zip` or edit `SKILL.md` by hand.
</Note>

## Zip package layout

Use a `.zip` when a skill needs supporting files, or to move a skill between workspaces. Upload it from **Settings → Skills → New Skill → Upload zip file**.

```text
security-review-checklist.zip
└── security-review-checklist/
    ├── SKILL.md            required
    ├── references/         optional: longer docs the skill points to
    ├── scripts/            optional: scripts the skill runs
    └── schemas/            optional: schemas the skill validates against
```

- Put `SKILL.md` at the root of the zip or inside one top-level folder.
- Only `scripts/`, `schemas/`, and `references/` are kept. Other files and folders are ignored.
- Refer to supporting files from `SKILL.md` by relative path. Agents don't read them automatically: they open a file when the instructions point to it, for example:

  ```markdown
  For the escalation order, read references/escalation-matrix.md.
  ```

- For a script, name it and say when to run it, for example "Run `scripts/check_tags.sh` with the account ID." The agent runs it with the same command tool it uses for any other command, so the script gets your workspace [Credentials](/guide/credentials) as environment variables, and any write it makes goes through [Approvals](/guide/approvals/overview) like any other command.

## Limits

| Item | Limit |
|---|---|
| Instructions field, or `SKILL.md` when you edit it in the app | 50,000 characters |
| Description | 2,000 characters |
| Skill name | 255 characters |
| Zip upload size | 5 MB |
| Files in a zip | 1,024 |
| Zip size after extraction | 50 MB |

## Write instructions agents follow

**Write only what the agent doesn't already know.** Agents already understand SQL injection. They don't know your rules about it.

```markdown
<!-- Too general: the agent already knows this -->
SQL injection is a vulnerability where attackers run arbitrary SQL
through unsanitized input, so always be careful with queries...

<!-- Useful: your specific rules -->
## SQL injection
- Flag `execute()` calls that take f-strings or `.format()`.
- Require the `db.query(sql, params)` helper for every new query.
```

**Match the rule style to how much freedom you want:**

| Freedom | Style | Use it for |
|---|---|---|
| High | Principles and guidelines | Architecture advice, exploratory reviews |
| Medium | Checklists with examples | Standard reviews, security checks |
| Low | Exact templates and fixed fields | Output formats, mandatory sections |

**Show, don't describe.** A pair of examples beats a paragraph:

```markdown
## Naming
- `remaining_retries`, not `r`
- `is_authenticated`, not `auth`
- Booleans start with `is_`, `has_`, or `should_`.
```

**Keep one topic per skill.** Separate security rules from performance rules so you can make each available in different places. If a skill runs past about 300 lines, split it: that's advice for keeping agents on track, well below the 50,000-character hard limit.

## Complete example

A pull request standards skill you can adapt:

````markdown
---
name: pr-review-standards
description: Enforce our pull request standards for size, tests, and docs. Use when reviewing any merge request or pull request.
argument-hint: <pull request link>
---

## Size

- Flag pull requests over 500 changed lines as "needs splitting" and suggest split points.
- Generated files (migrations, lockfiles) don't count toward the limit.

## Tests

- Require tests for every new public function.
- Flag deleted tests that have no matching feature removal.

## Docs

- Flag breaking API changes without a migration note.
- Require a README update when a new environment variable is added.

## Comment format

```
**[severity]** Short title

What is wrong and why it matters.

**Suggestion:** How to fix it.
```

Severity is one of `critical`, `warning`, `suggestion`, `nitpick`.
````

After you save it, tick **Review** under **Available in** so it applies to pull request reviews. See [custom skills](/guide/skills/custom-skills#choose-where-the-skill-applies).

## Troubleshooting

<AccordionGroup>
  <Accordion title="Upload fails with Failed to upload skill to executor">
    The most common cause is the frontmatter: it's missing, it has a YAML error, or `name` or `description` is empty. Check that `SKILL.md` starts with `---`, that the header closes with `---`, and that both fields have values. Put a description that contains a colon in quotes. Also check that `name` follows the naming rules above.
  </Accordion>
  <Accordion title="No SKILL.md found in zip archive">
    `SKILL.md` must be at the zip root or one folder down, and the file name is case-sensitive. Rename `skill.md` to `SKILL.md` and zip again.
  </Accordion>
  <Accordion title="Manual edit rejected: name must match">
    When you edit an existing skill by hand, the `name` in the frontmatter must stay exactly the same. To rename a skill, download it, change the name, and upload it as a new skill. Then delete the old skill, and re-tick **Available in** on the new one, since it starts on **Chat** only.
  </Accordion>
  <Accordion title="My scripts or docs are missing after upload">
    Only files inside `scripts/`, `schemas/`, and `references/` next to `SKILL.md` are kept. Move other files into one of those folders.
  </Accordion>
  <Accordion title="The skill loads but agents rarely use it">
    Rewrite the `description` to say when to use the skill, with the words people actually type ("Use when reviewing a pull request"). Then make the rules concrete and add examples.
  </Accordion>
</AccordionGroup>
