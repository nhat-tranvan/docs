**Find the real vulnerabilities in your running app, and fix them.**

Cyber is the Frontier Investigation Agent for application security, designed to proactively secure applications across the entire development lifecycle. It tests your running app, verifies every finding with request and response proof, and drafts the fix as a merge request.

<CyberScene />

A scanner lists what might be wrong. Cyber verifies it: a confirmed finding from a test run is a problem Cyber reproduced against your running app, with the requests and responses behind it, and a source finding carries the verification that decided it. A check it couldn't run, such as a protected page with no test user, is marked limited rather than clean.

## How it works

Cyber tests two surfaces. A [test run](/guide/security/security-testing) dynamically tests the running app; a [Code Audit](/guide/security/code-audit) reads the source behind it. A test run goes like this:

| Stage | What happens |
| --- | --- |
| 1. Register the app | You add an **App**: one application URL plus what to test, **Web application** or **API**. That choice sets which OWASP categories the coverage report measures. |
| 2. Prove ownership | You publish a DNS TXT record for the domain. Cyber won't run against a domain until it shows **Verified**. |
| 3. Set the boundaries | You add optional test users, a repository, and API docs, then include or exclude paths and pick an intensity. |
| 4. Test | CloudThinker explores the app, runs security tests within scope, and records each request and response. You watch the run live and can stop it. |
| 5. Prove and fix | Each finding carries its evidence. You triage it, open a fix pull request with the agent, and reverify or rerun to confirm the fix. |

A Code Audit skips steps 1 to 3: you pick a connected repository and branch, and the audit scans the code, investigates what it finds, and verifies each candidate against the commit it pinned. It then follows that branch, re-auditing it on a schedule or on every push, and watches the branch's dependencies for new [library advisories](/guide/security/cyber-libraries).

Click **Cyber** in the sidebar to open the overview: your apps, their latest results, and recent activity. The sidebar lists the **Apps** you test and, under them, the **Repositories** Code Audit follows.

## Safety model

Cyber sends real test traffic to your app, so every run is fenced in by settings you control: the target, the paths it may touch, the test users it signs in as, and how hard it pushes.

| Control | What it protects |
| --- | --- |
| **Domain ownership** | Runs are blocked until a DNS TXT record proves you control the domain. Only a workspace admin can claim and verify a domain. |
| **Scope** | **Include** and **Exclude** path rules. Excluded paths stay off-limits. |
| **Intensity** | How hard the run pushes, from **Safe** to **Deep dive**. See the [intensity table](/guide/security/security-testing#choose-access-and-intensity). |
| **Test users** | Dedicated accounts you create for testing. Cyber signs in as them, never as your real users. A scheduled run signs in only with a **Long-lived token** user, so without one it can't test or recheck anything behind the login. See [Add test users](/guide/security/security-testing#add-test-users). |
| **Stop run** | Cancels a run at any point. Findings already saved stay available. A stopped run doesn't produce a run report. |

<Warning>
  Aggressive (the UI's **Recommended** level) sends writes that create and edit test data. Full and Deep dive can permanently change or delete data inside the saved scope. Point anything above Safe at staging with test accounts, not production.
</Warning>

## Before your first run

Settle these with your platform team before you launch, so the run isn't blocked or paged on.

| Question | Answer |
| --- | --- |
| Who can launch a run? | Workspace Admins and Developers. Viewers can only look. Any role that can run can pick any intensity, so limit who holds those roles. See [Roles](/guide/security/roles). |
| Where does the traffic come from? | CloudThinker's cloud, not your network. This guide doesn't list source IP ranges or an identifying header. If your WAF or IDS will block or alert on security-test traffic, [contact us](https://cloudthinker.io/contact) for the current details first. |
| Can it test an internal or VPN-only app? | No. The target must be a domain name that CloudThinker can reach. IP addresses, CIDR ranges and `localhost` aren't accepted as targets. |
| How long does a run take? | It depends on app size and intensity. Every run stops at three hours at most. |
| Does a run cost credits? | Yes. Every Cyber run uses credits, and Deep dive uses the most. A manual Deep dive run can take a credit limit. See [Usage](/guide/billing/usage). |
| What data does Cyber keep? | The requests, responses, and screenshots that prove each finding, stored as evidence. Passwords, tokens, cookies, and keys are replaced with placeholders, but other response data is kept, so use test accounts with no real customer data. See [Data protection](/guide/security/data-protection). |
| Can I limit the request rate? | No. There's no rate setting. To reduce load, narrow the scope or use a lower intensity. |
| Do I need permission beyond DNS proof? | Yes, if you don't own the hosting. DNS proves you control the domain, not that you may test the infrastructure under it. Check your hosting or cloud provider's security testing policy and get written approval for third-party assets. |

## Key concepts

| Term | Meaning |
| --- | --- |
| App | One saved target: a URL, its framework, access settings, findings, and run history |
| Access level | Set by what you provide. **Black-box** is public access only, **Gray-box** adds test users, **White-box** adds a repository, with or without test users. |
| Confirmed | A verified finding: Cyber reproduced it, with request and response proof attached |
| Needs verification | A candidate Cyber couldn't prove yet. Treat it as a lead, not a vulnerability. |
| Stale | An app whose last completed scan is more than 30 days old |
| Tracked branch | One repository branch Code Audit follows across audits, keeping its findings and its library inventory |
