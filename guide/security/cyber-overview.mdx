Cyber runs a penetration test (pentest) against a web application or API you own: it attacks the running app, keeps the requests and responses that prove each problem, and helps you fix and retest it. You decide the target, the paths it may touch, the test users it signs in as, and how hard it pushes.

<CyberScene />

Scanners list what might be wrong. Cyber tries the attack and shows you the proof, so your team spends its time on issues that reproduce instead of arguing about false positives. A check it couldn't run, such as a protected page with no test user, stays marked as limited. It is never reported as clean.

## How it works

| Stage | What happens |
| --- | --- |
| 1. Register the app | You add an **App**: one application URL plus one framework, **OWASP Web** or **OWASP API**. The framework sets which OWASP categories the coverage report measures. |
| 2. Prove ownership | You publish a DNS TXT record for the domain. Cyber won't run against a domain until it shows **Verified**. |
| 3. Set the boundaries | You add optional test users, a repository, and API docs, then include or exclude paths and pick an intensity. |
| 4. Attack | CloudThinker explores the app, tries attacks within scope, and records each request and response. You watch the run live and can stop it. |
| 5. Prove and fix | Each finding carries its evidence. You triage it, open a fix pull request with the agent, and reverify or rerun to confirm the fix. |

## Safety model

Cyber sends real attack traffic, so every run is fenced in by settings you control.

| Control | What it protects |
| --- | --- |
| **Domain ownership** | Runs are blocked until a DNS TXT record proves you control the domain. Only a workspace admin can claim and verify a domain. |
| **Scope** | **Include** and **Exclude** path rules. Excluded paths stay off-limits. |
| **Intensity** | How hard the run pushes. See the table below. |
| **Test users** | Dedicated accounts you create for testing. Cyber signs in as them, never as your real users. |
| **Stop run** | Cancels a run at any point. Findings already saved stay available. |

| Intensity | What it sends | Run it against |
| --- | --- | --- |
| **Safe** | Reads routes and responses. Avoids intentional data changes | Staging or production |
| **Aggressive** | Submits forms and tests business flows. Can create or edit test data | Staging, or production only if test records there are acceptable |
| **Full** | Destructive requests, including `DELETE`. Asks you to confirm first | Staging only |
| **Deep dive** | Everything Full sends, over several passes. Asks you to confirm first | Staging only |

<Warning>
  Full and Deep dive can permanently change or delete data inside the saved scope. Point them at staging with test accounts, not production.
</Warning>

## Before your first run

Settle these with your platform team before you launch, so the run isn't blocked or paged on.

| Question | Answer |
| --- | --- |
| Who can launch a run? | Workspace Admins and Developers. Viewers can only look. Any role that can run can pick any intensity, so limit who holds those roles. See [Roles](/guide/security/roles). |
| Where does the traffic come from? | CloudThinker's cloud, not your network. This guide doesn't list source IP ranges or an identifying header. If your WAF or IDS will block or alert on attack traffic, get the current details from your CloudThinker contact first. |
| Can it test an internal or VPN-only app? | No. The target must be a domain name that CloudThinker can reach. IP addresses, CIDR ranges and `localhost` aren't accepted as targets. |
| How long does a run take? | It depends on app size and intensity. Every run stops at three hours at most. |
| Can I limit the request rate? | No. There's no rate setting. To reduce load, narrow the scope or use a lower intensity. |
| Do I need permission beyond DNS proof? | Yes, if you don't own the hosting. DNS proves you control the domain, not that you may attack the infrastructure under it. Check your hosting or cloud provider's pentest policy and get written approval for third-party assets. |

## Key concepts

| Term | Meaning |
| --- | --- |
| App | One saved target: a URL, its framework, access settings, findings, and run history |
| Access level | Set by what you provide. **Black-box** is public access only, **Gray-box** adds test users, **White-box** adds a repository. |
| Confirmed | A finding whose attack reproduced, with evidence attached |
| Needs verification | A candidate Cyber couldn't prove yet. Treat it as a lead, not a vulnerability. |
| Stale | An app whose last completed scan is more than 30 days old |
