Cyber tests running applications with **Pentest** and inspects repository code with **Code Audit**. Both give you evidence and remediation guidance, with separate results for each capability.

<Note>Figures show CloudThinker release 0.23.8 with illustrative demo data.</Note>

## How it works

1. **Choose the starting point.** Use Pentest for an application you are authorized to test, or Code Audit for a connected repository branch.
2. **Set the boundaries.** For Pentest, verify domain ownership and configure scope, test users, and optional source context. For Code Audit, select a repository and branch.
3. **Run the checks.** CloudThinker tests the application or analyzes a fixed code revision. Missing access and incomplete checks remain visible as limitations.
4. **Review the evidence.** Read the attack path or source assessment before deciding what to fix. A candidate that still needs review is not a confirmed vulnerability.
5. **Reassess after a fix.** Run another pentest or code audit against the changed application or code. Creating a ticket or merging a fix does not establish a new verdict.

<Note>
  Cyber is in beta. Code Audit can be unavailable even when Pentest is enabled; its absence does not mean your repository passed an audit.
</Note>

## What you can do

| Capability | What you do | Learn more |
| --- | --- | --- |
| Test a running application | Configure one application target, choose testing intensity, and run now or on a schedule | [Run a pentest](/guide/security/pentest) |
| Triage Pentest findings | Read proof, track work in a table or board, dismiss non-issues, and request retesting | [Triage security findings](/guide/security/cyber-findings) |
| Audit source code | Run static checks, security review, and verification on a connected repository branch | [Run a code audit](/guide/security/code-audit) |

| Share Pentest evidence | Export selected confirmed findings or download a run's assessment document | [Create Cyber reports](/guide/security/cyber-reports) |

## Read the workspace overview

Open **Cyber** from the navigation menu to see workspace security activity and enter the available capabilities. When Code Audit is available, open **Pentest** to choose an app or **Code Audit** to inspect tracked branches and audit history. Otherwise, the app list lives directly on Overview.

When only Pentest is available, the overview shows the workspace verdict, fix progress, a trend of open findings, recent runs, and the app list. An app with no completed scan has no assessed security verdict. An app whose last completed scan is more than 30 days old is marked stale.

Each Pentest app keeps its findings and run history across scans. Its header links the overview, runs, findings, reports, and settings. Coverage describes what the selected OWASP framework could assess; missing inputs do not become clean results.

Code Audit tracks source findings by repository branch. A completed audit publishes its findings to the branch view, while each audit report keeps the evidence for the revision it assessed. Failed or cancelled attempts leave the last published branch findings intact.

## Key concepts

| Concept | Meaning |
| --- | --- |
| Pentest app | One saved application target, its access configuration, findings, and run history |
| Access level | Black-box for public access, gray-box with test users, or white-box with source context |
| Intensity | Safe uses read-only requests; Aggressive allows active testing; Full allows destructive operations within scope |
| Pentest triage | Your work stage, separate from the assessment of whether a vulnerability is present or fixed |
| Tracked branch | A connected repository branch whose source findings persist across completed code audits |
| Library inventory | Collected dependencies at an assessed revision; it does not prove what is deployed |
