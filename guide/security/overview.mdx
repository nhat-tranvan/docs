CloudThinker agents read your cloud accounts, clusters, and tools through connections you add, and can change them only when Approvals allows it. This page collects the facts a security reviewer asks for, with a link to the page that covers each control in depth.

## At a glance

| Question | Answer | Details |
|---|---|---|
| Where does CloudThinker run? | A CloudThinker-managed cloud service at `app.cloudthinker.io` by default. Dedicated, self-hosted, and air-gapped deployments are in early access. | [Deployment](/guide/deployment/overview) |
| Where do agent commands run? | In a CloudThinker managed sandbox, or on a machine you control (a Worker, in beta). | [Self-hosted sandboxes](/guide/workers) |
| How do agents reach my systems? | Only through [connections](/guide/connections/overview) a workspace Admin adds, with the credentials and permissions you grant. | [Connections](/guide/connections/overview) |
| Can agents change things on their own? | Reads always run. Every write goes through Rules and the Approval mode, and can wait for a person or be refused. | [Approvals](/guide/approvals/overview) |
| Who can sign in, and how? | Email and password, an authenticator app as a second factor, or SSO with SAML 2.0 or OIDC. | [Single sign-on](/guide/security/sso) |
| Who can do what? | Organization roles and workspace roles: Admin, Developer, Viewer, plus an organization Owner. | [Roles](/guide/security/roles) |
| Are secrets kept out of chat and model calls? | Pasted secrets are caught before a message sends. Known secrets and protected identifiers are replaced with placeholders before the model or the screen sees them. | [Data protection](/guide/security/data-protection) |
| Is there an audit trail? | Yes. User, agent, and system actions across the organization, kept 90 days by default, exportable as CSV. | [Audit logs](/guide/security/audit-logs) |
| Can we use our own LLM account? | Yes, with BYOK on Scale, Scale+, and Enterprise plans. | [BYOK](/guide/byok) |

## Data CloudThinker handles

| Data | Why CloudThinker holds it | How it's protected |
|---|---|---|
| Connection credentials (cloud keys, tokens, database logins) | So agents can query the systems you connected | Encrypted at rest. Injected into the managed sandbox when a command runs, never sent to a Worker. |
| Workspace [credentials](/guide/credentials) (other API keys a command needs) | So a command can call a vendor API without anyone pasting a key | Encrypted at rest, never sent back to the browser. Chat shows key names only. |
| Conversations, findings, reports, and artifacts | The record of what agents found and did | Scoped to the workspace and visible by role. Known secrets are replaced with placeholders before they're stored. |
| Account passwords | Email and password sign-in | Stored as bcrypt hashes, never in plain text. |
| Unsent chat drafts | So a page reload doesn't lose your typing | Kept only in your browser, cleared on log out. Never sent to CloudThinker. |

Model calls go to CloudThinker's LLM provider unless your organization uses [BYOK](/guide/byok), which routes them through your own AWS Bedrock or Anthropic key.

## Where agents run

Every chat and Automation runs in one of two places:

- **CloudThinker Cloud.** Commands run in an isolated, CloudThinker-managed sandbox. Connection credentials are injected there for the command and aren't printed back.
- **A Worker.** A machine you control, such as a laptop, server, or CI runner, runs file tools and shell commands in one folder you name. A connection command still runs in the managed sandbox, so the credential stays in the cloud. Workers are in beta.

A run doesn't fall back from a Worker to the cloud. If the Worker is unavailable, the run reports an error. See [Self-hosted sandboxes](/guide/workers).

## Who can act

Access works at two levels. An organization role applies across every workspace. A workspace role sets what a member can do inside one workspace.

| Workspace role | Can do |
|---|---|
| **Admin** | Manage connections, credentials, members, Approvals, Guardrails, and settings |
| **Developer** | Chat with agents and work findings, reviews, and scans |
| **Viewer** | View dashboards, findings, and incidents. Can't chat with agents or change anything. |

Organization Owners and Admins hold workspace Admin in every workspace. Full matrix: [Roles](/guide/security/roles).

### Sign-in controls

| Control | Where | Plans |
|---|---|---|
| Authenticator app (TOTP) with one-time backup codes | **Account Settings → 2FA** | All |
| SSO with SAML 2.0 or OIDC, domain verification, and enforced SSO | **Admin Settings → Identity and access** | Scale, Scale+, Enterprise |
| SCIM user and group sync | **Admin Settings → Identity and access** | Scale, Scale+, Enterprise |

See [Single sign-on](/guide/security/sso) and [SCIM](/guide/security/scim).

## How agent changes are approved

A **write** is any agent call that changes a connected system, such as restarting a service. Reads always run. Each write passes these checks in order:

1. A built-in list of calls that never run. Nothing can override it.
2. Your **Rules**, which allow, ask first, or deny a named kind of write.
3. The **Approval mode** for the run: **Manual** asks a person for every write. **Auto** lets AI judgment allow a safe write, then asks you or refuses the rest.
4. The approver, who approves or declines.

New workspaces start on **Auto · Rules + AI · Ask me**. To require a person for every write, switch the workspace to **Manual**. See [Approvals](/guide/approvals/overview) and [Approval mode](/guide/approvals/approval-mode).

## Audit and retention

**Admin Settings → Audit Logs** shows one timeline of user, agent, and system actions across all workspaces: connection changes, approval decisions, credential changes, member changes, and module activity. Each entry records the actor, the workspace, and the outcome.

| Fact | Value |
|---|---|
| Who can view | Organization Owner and Admin |
| Plans | Scale, Scale+, Enterprise |
| Retention | 90 days by default, then deleted automatically |
| Export | **Export CSV**, respecting your current filters |

Credential entries never include the value or the key name. See [Audit logs](/guide/security/audit-logs).

## Encryption and sessions

| Layer | What CloudThinker does |
|---|---|
| In transit | The app and API are served over HTTPS |
| Stored secrets | Connection credentials, workspace credentials, and integration tokens are encrypted at rest |
| Passwords | Hashed with bcrypt |
| Sessions | Access tokens are signed with RS256. Refresh tokens rotate on use and are stored as hashes. |

## Before you connect production

- Start each connection with read-only credentials, scoped to the accounts and regions agents need.
- Keep production workspaces on **Manual**, or add Rules that ask first for the writes you care about.
- Turn on 2FA for every Owner and Admin, or enforce SSO.
- Give each member the lowest role that fits.
- Check the built-in protections in **Admin Settings → Guardrails**, and add patterns for your own ID formats.
