CloudThinker agents can read — and, with approval, change — your cloud infrastructure, so access to the platform itself is controlled with multi-factor authentication (MFA), single sign-on (SSO), and role-based permissions. Every agent action is logged with the user who initiated it and the approval it went through.

## Authentication methods

| Method | Description |
| --- | --- |
| Email & password | Standard sign-in with secure password requirements |
| Multi-factor authentication | Six-digit codes from an authenticator app (TOTP) plus one-time backup codes |
| Single sign-on (SSO) | SAML 2.0 or OIDC with your identity provider, on Scale, Scale+, and Enterprise plans |

## Multi-factor authentication

Add a second factor to your own account:

<Steps>
  <Step title="Open your account settings">
    Open your account menu and go to **Account Settings → 2FA**.
  </Step>
  <Step title="Set up the authenticator">
    Start MFA setup and scan the QR code with an authenticator app (Google Authenticator, Authy, 1Password, and more).
  </Step>
  <Step title="Confirm with a code">
    Enter the 6-digit code from your authenticator to finish setup.
  </Step>
  <Step title="Save your backup codes">
    Download and store the one-time backup codes. At sign-in, you can enter an 8-character backup code instead of an authenticator code.
  </Step>
</Steps>

<Warning>
Each backup code works once. If you lose your authenticator and all backup codes, account recovery requires identity verification through support.
</Warning>

## Single sign-on

[SSO](/guide/security/sso) is available on Scale, Scale+, and Enterprise plans and is configured by the organization Owner in **Admin Settings → Identity and access**:

- **Domain verification** — prove ownership of your email domain with a DNS TXT record before setting up SSO
- **SAML 2.0 or OIDC** — choose the protocol your identity provider supports
- **Require SSO** — optionally disable all other sign-in methods for your users
- **Provisioning** — invite users manually, auto-create accounts on first SSO login (JIT), or sync your directory with [SCIM](/guide/security/scim)

## Roles and permissions

Access is controlled at two levels. An organization role applies across every workspace; a workspace role can grant a specific member a different level in one workspace.

### Organization roles

| Role | What it grants | Role in each workspace |
|------|----------------|------------------------|
| **Owner** | Full control: billing, SSO, BYOK, members, workspaces, organization deletion | Admin |
| **Admin** | Manage members, create workspaces, manage credit limits | Admin |
| **Developer** | Work in assigned workspaces; no organization administration | Developer |
| **Viewer** | Read-only view of assigned workspaces | Viewer |

### Workspace roles

| Role | What it grants |
|------|----------------|
| **Admin** | Everything in the workspace: connections, members, settings, approval policies, knowledge, automations, deletion |
| **Developer** | Chat with agents, edit dashboards, customize agents, work Optimize findings, act on code reviews, run Cyber scans |
| **Viewer** | View dashboards, findings, incidents, and settings; cannot chat with agents or change anything |

### Permission matrix

| Action | Admin | Developer | Viewer |
|--------|-------|-----------|--------|
| View dashboards, findings, and incidents | Yes | Yes | Yes |
| Chat with agents | Yes | Yes | No |
| Edit dashboards and customize agents | Yes | Yes | No |
| Work Optimize findings and code reviews | Yes | Yes | No |
| Manage connections | Yes | No | No |
| Manage workspace members and settings | Yes | No | No |
| Manage approval policies and automations | Yes | No | No |
| Billing and subscription | Organization Owner only | — | — |

## Data security

| Layer | Protection |
|-------|------------|
| **Transit** | TLS for all connections |
| **At rest** | Encrypted databases and backups |
| **Secrets** | Cloud credentials and tokens stored encrypted |

[BYOK](/guide/byok) is about model access, not encryption keys: workspaces on Scale, Scale+, and Enterprise plans can route LLM inference through their own AWS Bedrock credentials for cost control and data residency.

## Audit logs

Organization activity — sign-ins, administrative changes, and agent actions — is recorded in **Admin Settings → Audit Logs**, available on Scale, Scale+, and Enterprise plans. Filter by user, action, and date, and export entries for compliance review.

## Security best practices

- **Enable MFA** for every member, especially Owners and Admins — or enforce SSO and let your identity provider require it.
- **Assign the minimum role** each member needs, and review access quarterly.
- **Use read-only cloud credentials** where possible, scoped to the services and regions agents need.
- **Rotate credentials** — cloud keys, SCIM tokens, and webhook secrets — on a regular schedule.
- **Review audit logs** for unexpected administrative changes or sign-ins.

For security questionnaires and compliance documentation, contact [security@cloudthinker.io](mailto:security@cloudthinker.io).
