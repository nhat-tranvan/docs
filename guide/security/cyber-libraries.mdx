The **Libraries** section in [Code Audit](/guide/security/code-audit) shows collected dependency versions and advisory evidence. Library version matches and application impact are separate from source-finding verification.

<Note>Figures show CloudThinker release 0.23.8 with illustrative demo data.</Note>

## Prerequisites

- Code Audit and library checking available in your installation.
- A connected repository with supported, resolved dependency files.
- A completed library inventory for ongoing branch monitoring.

## Inspect the inventory

Open an audit report for the libraries collected at that audit's revision. Open the tracked branch to see its last complete inventory and current advisory results.

| Field or state | How to read it |
| --- | --- |
| **Inventory** | The commit whose dependencies were collected |
| **Extracted** | When collection ran |
| **Complete extraction** | Collection completed for its supported scope |
| **Incomplete extraction** | Some dependency information is missing; do not assume full coverage |
| **Stale inventory** | Checks still use an older complete inventory; run another scan to refresh it |
| **Last successful advisory check** | When advisory checking last succeeded |
| **Advisory evidence as of** | The freshness of the saved vulnerability evidence |

A repository inventory does not establish which libraries are deployed. An unresolved package or an incomplete extraction is not evidence of safety.

## Read vulnerability evidence

Select a library to inspect its version, usage locations, and saved advisory evidence. Review the advisory and its affected versions before deciding how to remediate it.

A matching advisory identifies a potentially affected dependency. Application impact assessment adds repository-specific evidence about whether the vulnerable behavior affects your code. An uncertain assessment retains the missing evidence or conditions.

A not-affected impact assessment does not erase the underlying advisory match. Source findings, dependency evidence, and runtime Pentest proof answer different questions.

Historical alert links keep the evidence they refer to, even after the branch upgrades a dependency. Use the report's Download action to share that assessment.

## Control monitoring

After a complete inventory is published, advisory monitoring can check for newly disclosed vulnerabilities without another source audit. It is separate from scheduled source audits.

- **Pause monitoring** stops refreshes while preserving saved evidence.
- **Resume monitoring** enables refreshes again.
- A later source audit preserves a pause you explicitly chose.

**Monitoring on** does not mean a check has finished. Read the last successful check time and evidence freshness. Paused, delayed, stale, and unresolved coverage cannot be treated as clean solely because no new alert appears.

## Troubleshooting

<AccordionGroup>
  <Accordion title="A complete inventory is needed">
    Run a Code Audit with supported, resolved dependency files. Monitoring requires a complete published inventory.
  </Accordion>
  <Accordion title="Checks cover the last complete inventory">
    Run another scan to collect the current revision. Existing checks continue to use the retained complete snapshot.
  </Accordion>
  <Accordion title="Advisory monitoring is paused or delayed">
    Resume a paused monitor when you want current checks. For delayed checks, read the saved timestamps; retained evidence remains available while checking retries.
  </Accordion>
  <Accordion title="Libraries are unavailable but source auditing works">
    Library checking can be disabled independently of source auditing. Ask your administrator about availability; saved evidence does not certify current coverage.
  </Accordion>
</AccordionGroup>
