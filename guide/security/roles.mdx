Every person in CloudThinker has one organization role, and that role decides which workspaces they can open and what they can do there. Use this page to give each person the smallest role that covers their job. Every row matches a permission check CloudThinker enforces.

## How organization and workspace roles combine

An **organization** is your company account: billing, members and identity settings. A **workspace** is a separate area inside it with its own connections, agents, findings and conversations. See [Concepts](/guide/concepts) for the full model.

| Organization role | Which workspaces | Role inside a workspace |
|---|---|---|
| **Owner** | Every workspace, automatically | Admin, fixed |
| **Admin** | Every workspace, automatically | Admin, fixed |
| **Developer** | Only workspaces they're added to | Developer, unless you set an override |
| **Viewer** | Only workspaces they're added to | Viewer, unless you set an override |

- **Override**: a different role for one person in one workspace. It can raise or lower their role, for example making a Developer the Admin of their team's workspace, or a Viewer in a workspace they should only read. Owners and Admins can't be overridden. Set it in [workspace members](/guide/workspace-users).
- **Member** is a legacy organization role. It works exactly like Developer.
- **Owner**: each organization has exactly one. You can't invite someone as Owner or pick the role for them. There's no transfer control in the app: the current Owner emails support to [transfer ownership](/guide/organization#transfer-ownership), and the old Owner becomes an Admin.

## Organization permissions

Organization settings live in **Admin Settings**, which only Owners and Admins can open. A workspace Admin who isn't an organization Admin (for example, a Developer with an Admin override) can open one page there, **Guardrails**, and nothing else. They set their workspace's own LLM key in **More → Workspace settings → BYOK** instead.

| Action | Owner | Admin | Developer | Viewer |
|---|:-:|:-:|:-:|:-:|
| See the organization name and the workspaces they can open | Yes | Yes | Yes | Yes |
| See the full member list, in **Admin Settings → Organization** | Yes | Yes | No | No |
| Rename the organization | Yes | Yes | No | No |
| Invite members as Developer, Viewer or Admin | Yes | Yes | No | No |
| Remove members | Yes | Yes, except Admins and the Owner | No | No |
| Change a member's role to Developer or Viewer | Yes | Yes, except Admins and the Owner | No | No |
| Change an existing member's role to Admin | Yes | No | No | No |
| Choose which workspaces a Developer or Viewer can open | Yes | Yes | No | No |
| Create workspaces | Yes | Yes | No | No |
| Delete workspaces, in **Admin Settings → Workspaces** | Yes | Yes | No | No |
| View [usage](/guide/billing/usage) | Yes | Yes | No | No |
| Set [workspace credit limits](/guide/billing/credit-limits) | Yes | Yes | No | No |
| Manage organization [guardrails](/guide/security/custom-guardrails) | Yes | Yes | No | No |
| View [audit logs](/guide/security/audit-logs) | Yes | Yes | No | No |
| Manage the [subscription](/guide/billing/subscription) and payment | Yes | No | No | No |
| Manage organization [BYOK](/guide/byok) (your own LLM credentials), in **Admin Settings → BYOK** | Yes | No | No | No |
| Change anything in **Admin Settings → Identity and access**: [SSO](/guide/security/sso), [SCIM](/guide/security/scim), domain verification and auto-assigned workspaces | Yes | No | No | No |
| Restrict which email domains can be invited | Yes | No | No | No |
| Change [Capabilities](/guide/capabilities) (who decides which capabilities run in your workspaces) | Yes | No | No | No |
| Request an ownership transfer (by email to support) | Yes | No | No | No |
| Delete the organization (only when the Owner is the last active member) | Yes | No | No | No |

Admins can invite someone as Admin but can't promote an existing member to Admin. Nobody can be invited as Owner.

## Workspace permissions

These apply inside one workspace. Organization Owners and Admins always get the Admin column. Deleting a workspace isn't a workspace permission: only organization Owners and Admins can do it, from **Admin Settings → Workspaces**. Viewers are strictly read-only: they can't chat with CloudThinker or start any agent work.

| Area | Viewer | Developer | Admin |
|---|---|---|---|
| General workspace pages: findings, incidents, agents, connections, knowledge, memory | View | View | View |
| Chat with CloudThinker | No | Yes | Yes |
| Rename and star conversations | No | Yes | Yes |
| Delete conversations | No | No | Yes |
| Dashboards | View | Create and edit | Create and edit |
| [Custom agents](/guide/agents/customize) | View | Create and edit | Create and edit |
| [Automations](/guide/automation/automations) | View | View | Create, edit, run, delete |
| [Optimize](/guide/cost-optimization/overview) scans and findings | View | Run and manage | Run and manage |
| Optimize [recommendations](/guide/cost-optimization/recommendations) | View | Assign | Assign and edit |
| [Review](/guide/code-review/overview) reviews | View | Re-run, resolve findings, apply fixes, merge | Same, plus set up repositories and review mode, and delete |
| Review [Learnings](/guide/code-review/convention-rules) | View | View | Edit |
| [Cyber](/guide/security/cyber-overview) tests | View | Create, edit, run | Create, edit, run, delete |
| [Resolve](/guide/incident/overview) incidents and alerts | View | View | Edit and delete |
| [Pulse](/guide/pulse/overview) settings | View | View | Manage |
| [Connections](/guide/connections/overview), including cloud accounts | View | View | Add, edit, remove |
| [Custom skills](/guide/skills/custom-skills) | View | View | Create, edit, delete |
| [Credentials](/guide/credentials) | No | No | View and manage |
| [Knowledge](/guide/knowledge) bases | View | View | Manage |
| [Memory](/guide/memory) | View | View | Manage |
| [Approval rules and mode](/guide/approvals/overview) | View | View | Manage |
| [Notifications](/guide/notifications) and [webhooks](/guide/webhooks/overview) | View | View | Manage |
| Workspace [guardrails](/guide/security/custom-guardrails) | No | No | Manage |
| Workspace [members](/guide/workspace-users) and roles | View | View | Manage |
| [Branding](/guide/workspace-branding) and general settings, including workspace [capabilities](/guide/capabilities) | View | View | Manage |
| Workspace [BYOK](/guide/byok), in **More → Workspace settings → BYOK** | No | No | Manage |
| Leave the workspace (organization Owners and Admins can't leave individual workspaces) | Yes | Yes | Yes |

<Note>
  Developers can apply fixes and merge pull requests from Review. If someone shouldn't merge, give them Viewer in that workspace.
</Note>

Who can approve an agent's action is set separately from these roles. See [Approvers](/guide/approvals/approvers).

## Choose a role

| Person | Organization role | Why |
|---|---|---|
| Platform lead who also owns billing and SSO | Owner | Only the Owner manages the subscription, BYOK and identity |
| Engineering manager who adds people and workspaces | Admin | Manages members and workspaces without payment or SSO control |
| Engineer who chats with CloudThinker, runs Cyber tests and works Review findings | Developer | Day-to-day work without changing connections or settings |
| Engineer who owns one team's workspace | Developer, with an Admin override in that workspace | Admin power stays inside one workspace |
| Auditor, executive or stakeholder who only reads | Viewer | Sees results and can't change anything or start agent work |

Every role uses a seat on per-seat plans, Viewer included, and so does each pending invitation until it expires after 7 days. **Inactive** members (provisioned while no seat was free) don't use one until you activate them. See [Add or remove seats](/guide/billing/subscription#add-or-remove-seats).

If you provision people with [SCIM](/guide/security/scim), new members get the **Auto-assigned organization role** you set there, **Viewer** by default.

## What changes when a role changes

- The new role applies from the person's next request. They don't need to sign out.
- If someone loses access to a workspace (for example, an Admin demoted to Developer who was never added to it), the [automations](/guide/automation/automations) they own there are turned off. A workspace Admin can [take ownership](/guide/automation/autonomous-agents) and turn them back on.
- Removing someone from the organization removes them from every workspace. Members provisioned through SCIM are removed in your identity provider instead.
- Role changes, invites and removals are recorded in [audit logs](/guide/security/audit-logs).
